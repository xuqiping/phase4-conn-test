# 3.3 资源约束与取舍逻辑

## Must≤60%资源规则

DSDM方法论的核心规则：**Must-have需求消耗的资源应≤总资源的60%**。原因：

| 超过60%的后果 | 说明 |
|---|---|
| 没有缓冲 | 任何Must延迟→整体延迟，无弹性 |
| Should和Could被压缩 | 重要但不紧急的需求永无出头之日 |
| Won't桶为空 | 没有"不做"的声明→隐性需求堆叠 |
| 团队过劳 | 100%排满=0%弹性→必然加班或延期 |

### 如何将Must降到60%以下

| 方法 | 操作 |
|---|---|
| **MVP思维** | "如果只能做3个功能，哪3个？" → 3个=Must，其余降桶 |
| **拆分需求** | 把大需求拆为"核心(Must)+增强(Should)"，核心进Must |
| **时间约束** | Must=时间盒内必须完成的最低交付 |
| **业务方协商** | 与业务方逐一确认："这个不做，版本能发吗？" |

## 时间盒(Timebox)驱动的截断

MoSCoW与时间盒结合：**固定时间，调整范围**——而非固定范围，调整时间。

```
时间盒逻辑：
  固定：Sprint时长（2周/1月）
  变量：交付范围

填充顺序：
  1. Must全部排入 → 确认可在时间盒内完成
  2. Should按优先级排入 → 到时间盒80%为止
  3. Could按优先级排入 → 到时间盒100%为止
  4. 时间到了 → 从Could开始砍，必要时砍Should
  5. Must = 不可砍的红线
```

| 时间盒状态 | 行动 |
|---|---|
| Must完成了，时间还有 | 继续做Should → Could |
| Must完不成 | 重新评估：Must是真Must还是Should伪装的？ |
| 时间到了Should没做完 | Should降为下次的Should，Must必须保住 |

## Won't桶的管理

### Won't≠"永远不会做"

| 误解 | 正确理解 |
|---|---|
| Won't=永远不做 | Won't=**本次/本版本/本Sprint**不做 |
| Won't的需求被遗忘了 | Won't的需求保留在需求池，下次重新评估 |
| Won't桶是垃圾桶 | Won't桶是**显式声明**——比"默默忽略"尊重100倍 |

### Won't桶的沟通价值

```
传统做法：
  "这个需求我们后面再看看吧" → 利益方以为在做了 → 遗忘 → 怨气

MoSCoW做法：
  "这个需求本次Won't-have，原因是XXX，预计Y版本再评估" → 利益方有明确预期 → 减少追问
```

## C/W需求的"低成本捡漏"

Could和Won't中有一些**极低成本**的需求可以"顺便做"：

| 判断标准 | 说明 |
|---|---|
| Effort<0.5人天 | 几乎不占资源 |
| 不阻塞主流程 | 做了不会影响Must的交付 |
| 有复用价值 | 做了可以简化后续工作 |

> 警惕"捡漏变膨胀"——5个0.5人天的Could=2.5人天，可能挤占Should/Must的缓冲。[来源:📚训练知识 | 📚中]
