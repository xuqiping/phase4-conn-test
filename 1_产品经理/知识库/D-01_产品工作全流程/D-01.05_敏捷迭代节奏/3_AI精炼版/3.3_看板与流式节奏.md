# 3.3 看板与流式节奏

## 看板 vs Scrum节奏对比

| 维度 | Scrum | 看板 |
|---|---|---|
| 节奏来源 | 固定时间盒（Sprint） | WIP限制+拉式流转 |
| 计划方式 | Sprint Planning | Just-in-Time（到做到拉） |
| 承诺方式 | Sprint Goal+Forecast | SLA/周期时间承诺 |
| 变更策略 | Sprint内尽量不变 | 随时可调整队列优先级 |
| 复盘时机 | Sprint Retro | 定期（通常2周）或按需 |
| 交付频率 | Sprint结束时 | 持续（随时可交付） |
| 适合工作类型 | 产品功能开发 | 运维/支持/Bug修复/持续性工作 |

[来源:Kanban Guide/Agile Alliance | 置信度:🔍高]

## 看板核心度量

| 度量 | 定义 | 如何用 | 健康值 |
|---|---|---|---|
| WIP（在制品） | 当前正在处理的工作项数 | 控制WIP≤团队人数×1.5 | 稳定不超限 |
| 吞吐量（Throughput） | 单位时间完成的工作项数 | 预测交付时间 = 队列长度/吞吐量 | 稳定或缓慢上升 |
| 周期时间（Cycle Time） | 从"开始做"到"完成"的时间 | 识别瓶颈（哪个阶段CT最长） | CP95<Sprint周期 |
| 前置时间（Lead Time） | 从"提出需求"到"交付"的时间 | 客户感知的响应速度 | 与SLA对齐 |
| 流效率（Flow Efficiency） | 活跃工作时间/总周期时间 | 识别等待浪费 | >15%即良好（多数<10%） |

[来源:《Actionable Agile Metrics》/Daniel Vacanti | 置信度:🔍高]

## WIP限制原则

**Little's Law**：`平均前置时间 = 在制品数量 / 吞吐量`

→ 要缩短前置时间，要么**减少WIP**，要么**提升吞吐量**。
→ 减少WIP是立即见效的，提升吞吐量需要时间。

### WIP限制设置方法

1. **从当前WIP开始**：先统计当前平均WIP，设限=当前值
2. **逐步收紧**：每2周减1，观察影响（吞吐量不变→继续减；吞吐量下降→回退）
3. **按列设限**：每个看板列有独立WIP限制（如"开发中"≤3，"测试中"≤2）
4. **全局WIP**：整条看板的总WIP限制（团队人数×1.5是起点）

[来源:Kanban Guide | 置信度:🔍高]

## 看板节奏与迭代复盘

看板没有固定Sprint，但仍然需要定期复盘：

| 实践 | 频率 | 时长 | 产出 |
|---|---|---|---|
| 看板站会 | 每日 | 15min | 阻塞识别+优先级确认 |
| 交付复盘 | 双周 | 1h | 吞吐量趋势+瓶颈分析+改进项 |
| 服务交付回顾 | 月度 | 1.5h | SLA达成率+改进计划 |

## 从看板到Scrum的迁移信号

| 信号 | 含义 |
|---|---|
| 工作项类型统一为"功能需求" | 支持类/Bug类减少→更像产品开发 |
| 需要稳定的交付承诺 | 看板的弹性承诺不够→需要Sprint Forecast |
| 团队需要更多仪式感 | 看板太"松"→需要Planning/Review结构 |
| 干系人需要固定的Review节奏 | 看板"随时可看"不满足→需要Sprint Review |
