## 3.1 验收标准（Acceptance Criteria）

> **规则**：每条功能需求（FR-xxx）至少映射 1 条验收标准（AC-xxx），每条 AC 必须**可独立测试**（能断言通过/不通过，不写「体验好」「速度快」这类不可测的话）。
> **写法**：用 **EARS 语法**或 **Given/When/Then**，二选一，全文统一。
> - EARS：`WHEN [触发条件], THE SYSTEM SHALL [系统行为]`（事件驱动）；`WHILE [状态]...`（状态驱动）；`IF [异常条件], THEN THE SYSTEM SHALL [应对]`（异常）；`WHERE [上下文]...`（可选行为）
> - GWT：`Given [前置] / When [动作] / Then [预期]`
> **联动类需求**（父勾选→子全选这类）特别适合 IF-THEN/WHEN 句式，正反向都要写。

| AC 编号 | 对应需求 | 验收标准（EARS / GWT） | 验证方式 |
|---|---|---|---|
| AC-001 | FR-001 | WHEN 密码连续错误5次, THE SYSTEM SHALL 锁定账户15分钟 | 自动化测试 |
| AC-002 | FR-001 | IF 账户被锁定, THEN THE SYSTEM SHALL 在登录页显示剩余锁定时长 | 人工验收 |

> 「验证方式」：能自动化且结果可断言 → 自动化测试（Phase 3 转测试用例，**优先**这条路）；必须人介入 → 人工验收（进 Phase 3 测试方案 / Phase 4 User-Ops 逐项验证）。
> **闭环**：每条 AC 必须在 `testing_strategy.md` 的「AC 映射表」里有唯一落点（验证方式标注一致）；Phase 4 逐条核对。一条 AC 悬空 = 没做完。

### 3.2 追溯编号体系（全链路）

> FR/AC 是全链路的公共编号——出问题时能回答「这个需求实现没、测了没、在哪」。

| 环节 | 编号用法 |
|---|---|
| PRD（本文件） | 需求 `FR-xxx` → 验收 `AC-xxx`（此处定义，是唯一出处） |
| plan.md | 每个 Step 标注「对应需求：FR-xxx」 |
| 自动化测试 | 测试用例名/注释带 `AC-xxx`（如 `// AC-001`） |
| 人工测试方案 | 用例表带「对应 AC」列 |
| commit message | 带 FR 号，如 `feat: FR-003 登录失败锁定` |
| 开发进度 | 代码类记录的「对应编号」填 plan Step / FR / AC |
