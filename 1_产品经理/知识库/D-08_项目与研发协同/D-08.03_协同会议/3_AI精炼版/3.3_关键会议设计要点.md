## 一、每日站会（Daily Standup / Daily Scrum）

### 设计规格

| 维度 | 标准 |
|---|---|
| 时长 | ≤15min |
| 频率 | 每日同一时间 |
| 参与者 | 开发团队（Scrum Master引导；PM可选参与） |
| 产出 | 阻塞清单（谁/什么问题/需要什么/何时开始阻塞） |

### 三问变体

**经典三问**（已过时但仍常见）：
1. 昨天做了什么？ 2. 今天计划做什么？ 3. 有什么阻塞？

**问题**：经典三问容易变成"流水账汇报"——每人30秒念做了什么，没有实质性同步。

**改版：Walk the Board**——沿着看板从右到左走：
1. 看板最右端（即将完成/已完成的项）→ 有什么即将交付？
2. 阻塞的项（标红旗的）→ 有什么阻塞？需要谁帮助？
3. 即将到期的里程碑 → 有风险吗？

**改版优势**：聚焦"流动"而非"个人汇报"——站会关注的是工作项的流动，不是每个人的日程 `[来源:Jason Yip·"It's Not Just Standing Up" | 置信度:🔍高]`

### PM的站会参与法则

- **PM不是站会的主持人**（Scrum Master才是）
- **PM参与目的**：识别阻塞+确认优先级变化——不是为了"汇报进度"
- **PM发言原则**：只在"我影响了团队的阻塞"或"优先级有变化"时发言

## 二、Sprint Planning（迭代规划会）

### 设计规格

| 维度 | 标准 |
|---|---|
| 时长 | 2周迭代≤4h / 1周迭代≤2h |
| 频率 | 每迭代初 |
| 参与者 | 全团队（PM作为Product Owner参与） |
| 产出 | Sprint目标 + Sprint Backlog |

### Two-Pass Planning（实务推荐）

**第一遍（What）**——PM主导：
- 本轮Sprint目标是什么？
- 哪些需求进本轮？（基于优先级+容量+依赖）
- 产出：Sprint目标 + 选取的需求列表

**第二遍（How）**——Tech Lead主导：
- 怎么做？任务拆分
- 工时估算
- 产出：Sprint Backlog（任务板）

**常见问题与对策**：

| 问题 | 根因 | 对策 |
|---|---|---|
| Planning超时 | 需求未提前准备 | 提前1天发需求材料，No Prep No Meeting |
| 容量总是超额承诺 | 聚焦因子高估 | 用前3轮实际吞吐量80%为本轮容量上限 |
| 任务拆不下去 | 需求太模糊 | 退回需求细化，不进Sprint |

## 三、Sprint Review（迭代评审会）

### 设计规格

| 维度 | 标准 |
|---|---|
| 时长 | 2周迭代≤2h |
| 频率 | 每迭代末 |
| 参与者 | 全团队+利益相关方（邀请制） |
| 产出 | 反馈清单 + 待排期变更项 |

### 关键原则

1. **Demo驱动**：Review不是"讲PPT"，是**演示可工作的软件**——没有可演示的成果=没有Review
2. **利益相关方在场**：业务方/运营/设计等的反馈必须当场收集，不能"事后发邮件"
3. **不做决策**：Review是检视和收集反馈，不做范围/排期决策——决策另开会或在Planning中做

**PM角色**：展示产品成果（Demo主角）+ 收集反馈 + 解答业务方问题

## 四、Sprint Retro（迭代回顾会）

### 设计规格

| 维度 | 标准 |
|---|---|
| 时长 | 2周迭代60-90min |
| 频率 | 每迭代末（Review之后） |
| 参与者 | 仅开发团队（不邀请管理层/利益相关方） |
| 产出 | ≤3个行动项 + 可选工作协议更新 |

### Retro格式轮换（避免疲劳）

| 格式 | 适合时机 | 步骤 |
|---|---|---|
| **Start/Stop/Continue** | 通用 | 3列：该开始做什么/该停止做什么/该继续做什么 |
| **Mad/Sad/Glad** | 情绪主导的迭代 | 3列：什么让你生气/难过/高兴 |
| **4Ls** | 正向偏重 | Liked/Learned/Lacked/Longed for |
| **Sailboat** | 可视化 | 风=推动力 / 锚=阻力 / 岛=目标 / 暗礁=风险 |
| **Timeline** | 长迭代复盘 | 画时间线+标关键事件+标感受曲线 |

**Retro铁律**：
1. **心理安全是前提**——没有心理安全的Retro只会收获沉默或空话 `[来源:Google Project Aristotle | 置信度:🔍高]`
2. **管理层不在场**——Retro是团队内部的自省空间，管理层在场会压制真实表达
3. **最多3个行动项**——10个行动项=0个行动项，3个行动项有Owner和截止日=可执行

## 五、需求评审会

### 设计规格

| 维度 | 标准 |
|---|---|
| 时长 | 60-120min（按需求复杂度） |
| 频率 | 按需（需求准备好时） |
| 参与者 | PM（主导）+ Tech Lead + QA + 设计 |
| 产出 | 评审结论（通过/有条件通过/打回）+ 待修改项清单 |

### PM主持法则

1. **讲Why而非What**——评审会上开发最想知道"为什么做这个"（业务上下文），而非"PRD每个字段写什么"
2. **提前发材料**——PRD至少提前24小时发出，No Prep No Meeting
3. **收敛决策**——评审结束必须有明确结论：✅通过 / ⚠️有条件通过（附修改清单）/ ❌打回重做
4. **区分"必须改"和"建议改"**——每个反馈标优先级，避免所有反馈都变成"必须改"
