# 02 - 系统设置页(全局默认值)

> 状态:**✅ 完全完成**(后端全量测试 51 通过 + 前端 build 通过 + 端到端验证通过)
> 实施日期:2026-06-15

## 一、目标

让管理员在后台配置**全局默认值**,而不是硬编码:
- 默认设备上限(新用户注册时 `device_limit` 的默认值,当前硬编码为 1)
- 默认离线缓存分钟数(当前硬编码为 0)
- 匿名试用天数(当前 `AuthConstants.ANONYMOUS_FULL_TRIAL_DAYS = 7`)
- (可选)免费模块更换间隔(当前 30 天)

## 二、现状调研(关键发现)

- **`system_settings` 表已存在**(key-value 结构:`setting_key`/`setting_value`/`description`,`uk_system_settings_key` 唯一约束),迁移定义在 `V1__create_auth_schema.sql:86`。当前表里 **0 条数据**。
- **实体类已存在**:`com.superprogrammer.settings.entity.SystemSetting`(MyBatis-Plus 风格,但项目 repository 实际都用 JdbcTemplate)。
- **但缺少 repository / service / controller** —— `settings` 包下只有实体类,没有任何数据访问或接口层。需要全部新建。
- **当前默认值硬编码位置**:
  - 注册用户默认 `device_limit=1, offline_cache_minutes=0`:`UserRepository.java:37`(INSERT 写死 `1, 0`)
  - 匿名试用天数:`AuthConstants.ANONYMOUS_FULL_TRIAL_DAYS = 7`(常量)

## 三、设计要点

### 配置项 key 约定(存入 system_settings.setting_key)
- `default_device_limit`(int,默认 1)
- `default_offline_cache_minutes`(int,默认 0)
- `anonymous_trial_days`(int,默认 7)

> 采用 key-value 通用表,而不是给每个配置加列。理由:表已经存在、通用、扩展容易。

### 后端新建文件
1. **`server/.../settings/dto/SystemSettingDto.java`** — record(key/value/description)
2. **`server/.../settings/dto/SystemSettingsBundle.java`** — record,把所有配置聚合成一个对象返回/接收(前端一次请求拿全部)
3. **`server/.../settings/repository/SystemSettingRepository.java`** — `@Repository` + JdbcTemplate:
   - `findAll()` → List
   - `getValue(key, defaultVal)` → String(找不到返回默认值)
   - `upsert(key, value, description, adminUserId)` — 用 PostgreSQL `ON CONFLICT (setting_key) DO UPDATE`
4. **`server/.../admin/service/AdminSettingsService.java`** — 读写 bundle,带类型转换(int parse)
5. **`server/.../admin/controller/AdminSettingsController.java`**:
   - `GET /api/admin/settings` → 返回 bundle
   - `PUT /api/admin/settings` → 接收 bundle,upsert

### 后端改动(让硬编码改为读配置)
- `UserRepository.insertPendingReviewUser`:device_limit/offline_cache_minutes 不再写死,从 AdminSettingsService 取默认值(注意避免循环依赖,可把"读取默认值"放到上层 UserService,repository 收参数)。
- `AuthConstants.ANONYMOUS_FULL_TRIAL_DAYS`:改为从配置读,`AnonymousTrialService` 注入 AdminSettingsService。
- ⚠️ 这两处改动**有破坏性**(改变现有注册/试用行为),需配套测试。

### 前端新建/改动
- **新建** `admin-web/src/api/settings.ts` — `getSettings()` / `updateSettings(bundle)`
- **新建** `admin-web/src/views/SettingsView.vue` — n-form 展示 3 个配置项,保存调 PUT
- **改动** `admin-web/src/types/index.ts` — 加 `SystemSettings` interface
- **改动** `admin-web/src/router/index.ts` — 加 `{ path: 'settings', name: 'settings' }`
- **改动** `admin-web/src/views/Layout.vue` — menuOptions 加"系统设置"项

## 四、验证
1. `GET /api/admin/settings` 未配置时返回默认值(1/0/7)。
2. `PUT /api/admin/settings` 保存后,`GET` 返回新值;DB `system_settings` 表有记录。
3. 注册一个新用户,确认其 `device_limit` = 配置的默认值(而非硬编码 1)。
4. 匿名试用设备确认试用天数 = 配置值。
5. `npm run build` 通过。

## 五、风险/边界
- 改 `UserRepository`/`AuthConstants` 是**行为变更**,务必加/改测试。
- 本期不做:邮件/短信 provider 配置、支付配置(第一版不接支付)。
- 配置读取建议加内存缓存(这些值极少变),但第一版可直接每次查库。
