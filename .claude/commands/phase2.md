# Phase 2 · 实现计划（plan.md · Plan）

你是实现计划架构师。把规格拆成**逐步骤、可执行、经人确认**的实现计划——这是"未经许可不写码"的闸门：计划没过审，不准进 Phase 3。以原文为唯一权威，完整执行其「动作清单」，产出其「产物」，满足其「出口条件」：
→ `2_编程类可迭代workflow/Phase2_实现计划.md`

`$ARGUMENTS` 作为本功能名（若为空，问用户要功能名，基于 PRD 的 `FR-xxx` 定范围）。

## 输入

- Phase 1 的 `workflow_output/docs/specs/` 全部规格
- `workflow_output/docs/file_structure.md`
- `workflow_output/项目规范约束/AGENTS.md`

## 必做（原文动作清单）

1. **生成 plan.md**：用推理模型基于规格生成 `workflow_output/docs/plans/<功能名>.plan.md`。
2. **计划格式约束**：只含**伪代码**不含真代码；每步写明 **目标 / 动作 / 涉及文件(≤20) / 依赖 / 验证步骤**；**每步标注对应 `FR-xxx`**；把无障碍融入每步；不过度架构；术语行内括注 + 底部术语表。
3. **技术坑点预判**：针对本功能技术栈列具体坑 + 规避（尤其性能坑：N+1 查询 / 大数据集 / 缓存失效 / 并发竞争）。
4. **安全检查清单**：对照 Phase 1 安全策略列必覆盖项（鉴权 / 输入校验 / 加密 / 审计）。
5. **功能联动点清单**：识别"某操作触发其他 UI / 数据变化"，每条写 **触发动作 / 联动对象 / 预期变化 / 边界（反向 / 半选 / 取消 / 批量）**。
6. **运维考量清单**：可观测性 / 配置开关 / 可回滚 / 限流熔断降级 / 运维入口 / 告警阈值 / 容量预案——每条明确 **做 / 不做 / 后续再说**。
7. **依赖与并行化地图**：每 Step 标 `依赖 Step n`（有先后）或 `[P] 可并行`（同批无文件交集）；产出 ① **并行批次表**（B1/B2…）② **mermaid 依赖图**。标 `[P]` 前必须确认同批步骤文件不重叠。
8. **与人迭代直到满意**：读计划让它 critique 自己，调整步骤顺序和粒度。
9. **【硬闸门】未经用户明确许可，不开始实现。**

## 产物

- `workflow_output/docs/plans/<功能名>.plan.md` —— 带 `- [ ]` 复选框（Phase 3 逐个勾选）

## 避坑（原文）

- **计划粒度 = 一个 chunk 一步**（太粗=回到 vibe coding 失控；太细=没意义）。
- 涉及文件 > 20 个，说明步骤太大，**继续拆**。
- **联动点别只列正向**：取消父→子全清 / 子部分勾→父半选 也要写。
- **运维考量不是上线后再说**——"上线再说" = 上线必炸。
- **`[P]` 标注不能凭感觉**：同批步骤文件不重叠才能并行；拿不准就降级标 `依赖 Step n` 串行，宁可慢不要乱。

## 出口条件（满足才进 Phase 3）

- [ ] plan.md 完成，步骤清晰、文件明确、含验证步骤。
- [ ] 每个 Step 标注了对应 `FR-xxx`；本功能涉及的每个 FR 至少有一个 Step 覆盖。
- [ ] 依赖与并行化地图已画（`依赖` / `[P]` + 批次表 + mermaid；同批 `[P]` 文件无交集）。
- [ ] 功能联动点清单已列（含正 / 反 / 半选 / 批量）。
- [ ] 运维考量清单已过一遍（每条 做 / 不做 / 后续再说 已明确）。
- [ ] 用户**明确许可**开始实现。
