## 技术实现坑点预判与规避措施

| 技术点 | 可能的坑 | 规避措施 | 验证方式 |
|---|---|---|---|
| refresh 旋转 | 旧 refresh 拉黑后并行请求竞态（多 tab 同时刷新互踢） | 拉黑 TTL=旧 token 剩余有效期（与 logout 同范式）；前端已有单飞刷新（request.ts 防并发） | 旧 refresh 二次使用 → 401；新 refresh 正常换新 |
| TOTP 自实现 | 时钟偏移/时间步长边界误拒；secret 泄露 | RFC6238 ±1 窗口容忍；secret 服务端 AES 加密存 system_settings 通用加密 KV（已有）；恢复码 8 组一次性格式 | 篡改 1 位 code → 401；恢复码可用一次 |
| testConnection 修复 | admin 全局 provider 与用户 provider 两个入口漏一个 | 收口到 `LlmProviderService` 单点 validate（createProvider 前） | 用户自填内网 endpoint test → 400 |
| MediaStorage 回源 | Ark 返回 CDN URL 偶尔带重定向 → 校验首跳后跳内网 | validate 首跳 + WebClient 跟随重定向属低风险（Ark CDN 可信）——注释声明 | 假造 task 结果内网 URL → 拒 |
| Jsoup 重定向 | followRedirects(false) 破坏正常搜索结果抓取 | 手动跟随：读 3xx Location → assertPublicUrl → 再抓，最多 3 跳 | 302 跳 169.254.169.254 → 拒 |
| sidecar 回调 HMAC | 双侧部署不同步导致回调全断（发布顺序） | 兼容期双轨：带 HMAC 头验 HMAC，不带则回落静态 token（热更键切换强制期）；sidecar 同步改造 | 旧 sidecar + 新 backend 回调仍通 |
| AES 默认密钥 fail-fast | 本地开发没设 secret 起不来 | 弱密钥判定仅在 `APP_CORS_ALLOWED_ORIGINS` 非空（生产态）时 fail-fast，dev 放行+WARN | 生产态默认密钥 → 拒启动 |
| 蜜罐端点 | 扫描器高频打蜜罐刷爆事件表 | 同 IP 60s 聚合一条（Redis 计数）；只记不响应内容（404 伪装） | curl /.env → 404 + HIGH 事件落库 |
| 注销软删 | 审计/流水法定留存 vs 删除权冲突 | 只匿名化身份字段（username/email/avatar→deleted_xxx）+踢全部 token；业务数据保留脱敏口径写入隐私文本 | 注销后旧 token 全 401；用户名不可再登录 |
| dependency-check | 全量 NVD 首跑下载库极慢/离线失败 | 不绑构建生命周期，独立 profile `mvn -P deps-check`；失败不阻断本地构建 | profile 跑出报告 |

- [x] **Step 1：SEC-FR-004+ A4 refresh token 旋转** ✅ `2ee9bd18`（2026-08-15）
  - **目标**：refresh token 用后即失效（旋转），7 天重放窗口封死。
  - **动作**：`AuthService.refreshToken` 改造伪代码：`验旧 refresh（黑名单+sid）→ 拉黑旧 refresh jti（TTL=剩余有效期）→ 签发新 access + 新 refresh（同 sid=会话延续，沿 S2 范式）→ 响应体加 refreshToken 字段 → metrics.rotated`；重放检出（黑名单命中）记 `security.auth.refresh.replayed` + MEDIUM 事件；开关 `security.auth.refresh-rotation.enabled`（关=旧行为）；Redis 故障跳过拉黑 WARN。
  - **文件**：`AuthService.java`、`RuleConfigController.java`（EDITABLE_KEYS）、`BizMetrics.java`、`AuthController`（如响应 DTO 需扩）、测试×1
  - **依赖**：无 `[P]`
  - **验证**：同一 refresh 连续两次换 token，第二次 401；前端 `applyTokenPair` 无改动正常续期；开关关回到复用行为。

- [x] **Step 2：SEC-FR-006 A6 管理员 TOTP** ✅ `4dc6444f`（2026-08-15）
  - **目标**：admin 角色登录需密码+TOTP 双因素。
  - **动作**：①新建 `auth/totp/TotpService`（RFC6238 自实现：Base32 secret+HmacSHA1/SHA256+30s 步长 ±1 窗口容忍，零新依赖）；②绑定流：admin 发起绑定 → 生成 secret+otpauth:// URI → 前端二维码 → 首次验 code 确认 → secret AES 加密入 system_settings 通用 KV；③登录流：admin 密码过且已绑定 → 返回 `mfaRequired` 不发 token → 前端第二屏输 code/恢复码 → 验过发双 token；④8 组恢复码（一次性，用后即废）；⑤`security.auth.totp.required` 开关（关=不触发第二屏）。
  - **文件**：`TotpService.java`（新）、`AuthService.java`（登录分流）、`AuthController.java`（绑定+验证端点）、`MfaController` 或并入 auth、前端 `LoginView`+`stores/auth.ts` 二步屏、`RuleConfigController.java`、测试×2

## 术语表

- **refresh 旋转（rotation）**：每次用 refresh 换新 access 时同时换新 refresh，旧的立即作废——偷到的旧票只能用一次
- **TOTP**：基于时间的一次性密码（RFC6238），手机验证器 App 按「共享密钥+当前时间」每 30 秒算一个 6 位码
- **恢复码**：TOTP 绑定时一次性发放的备用码，手机丢了用来救场，每张只能用一次
- **DNS rebinding**：校验时域名解析到公网 IP、连接时再解析到内网 IP 的双解析把戏；连接期 IP 绑定（解析一次后钉住该 IP 连接）可根治
- **蜜罐（honeypot）**：故意暴露的假端点（如 /.env），正常人不会访问，访问者基本是扫描器——命中即报警
- **FIM**：文件完整性监控，对关键文件记哈希基线，再算不一致=被改过
- **/MIR 镜像**：robocopy 的「让目标与源完全一致」模式——源被勒索加密后同步会把异地点的好备份也覆盖成坏的
