# 09 - 个人记忆与冲突解决

## 功能简介
对话中抽取用户事实记忆、分类（用户记忆块）、新旧记忆冲突裁决（保留/合并/替换）、用户可在面板查看/删除/批量解决冲突。

## 记忆检索模式（V28/V31，用户可选）
召回入口 [MemoryService.buildMemoryContext(userId, query)](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 按系统设置 `rag.memory.retrieval-mode` 分流：
- **LLM_FULL_CONTEXT**（默认，向后兼容）：全量 `confidence≥0.5` 记忆灌入 LLM 上下文。简单但易联想泄漏（没问也输出）。
- **EMBEDDING_VECTOR**：当前 query 经 `LlmGateway.embed(query, MEMORY_EMBED_MODEL)` → pgvector `<=>` 余弦距离 top-K（`similarity=1-distance≥0.35`，`LIMIT 5`），仅注入强相关记忆；**无命中 → 不注入**（return null，不回退全量）；空 query → 不注入。复用写入侧 embed 链，召回侧不再裸跑全量。
- **VECTOR_KEYWORD**（V31 新增，推荐）：向量 top-K ∪ 关键词(实体列) 召回 → 去重截断（`HYBRID_MAX=8`）注入；**并集 0 命中 → LLM-key 兜底**。专治纯向量漏的"实体桥接"类（记忆"女儿3岁" `key=child_age value=3岁`，query"带女儿去玩"靠实体"女儿"召回）。见下文「混合检索原理」。
- 设置项：[SystemSettingService.getMemoryRetrievalMode()](../../backend/src/main/java/com/superprogrammer/system/service/SystemSettingService.java)（key `rag.memory.retrieval-mode`），前端 [RagMemorySettingsTab.vue](../../frontend/src/components/settings/RagMemorySettingsTab.vue) 下拉，见 [21-系统设置](21-系统设置.md)。
- 向量检索 SQL：[UserMemoryMapper.findTopKByVector](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java)（`embedding IS NOT NULL`，仿 `findNearestBlock`；FLAGGED 行 conflictId≠null 也参与检索）。
- 线程：`buildMemoryContext` 在 ChatSessionService 方法体内同步调（与 `resolveRagForChat` 同 scope，stream/non-stream 均 servlet 线程，非 reactor-nio），embed/LLM 兜底阻塞调用同既有 RAG 检索，不新增 block 风险。

### 混合检索原理（VECTOR_KEYWORD，V31）
纯向量只看"表面语义像不像"，不看"逻辑上相不相关"——"女儿3岁" embed 靠近 {年龄/儿童}，"带女儿去玩" embed 靠近 {游玩/景点}，余弦距离远 → 漏召。任何纯向量方案救不了，换 embed 模型也不行。
混合召回三段式（[MemoryService.buildHybridContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)）：
1. **向量 top-K**（既有链路，`findTopKByVector`）。
2. **关键词召回**（[UserMemoryMapper.findByKeyword](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java)）：query 分词（CJK 2-gram + 字母数字整段，[MemoryService.tokenize](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)，`KEYWORD_MAX=8`）→ ILIKE 命中 `entities::text` / `memory_key` / `memory_value` / `memory_key_zh` / `block_label`（五列并查，无 top-K LIMIT，仅 LIMIT 200 防病态）。**per-block_label 阈值筛选**（[MemoryService.applyKeywordPerBlockThreshold](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)）：按 block_label 分组，各组各自阈值 N（设置 `rag.memory.keyword-per-block-threshold`，默认10，0=禁用）；组内 ≤ N 全留，组内 > N 则命中 `entities`/`memory_key`/`memory_key_zh`（高优）的行不卡阈值全留、低优（`memory_value`/`block_label` 命中）补到 N。取代旧全局 LIMIT 10。噪声 gram（如"去玩"）天然自滤——不是任何召回词子串就撞不上五列。
3. **并集 0 命中 → LLM-key 兜底**（[MemoryConflictJudge.selectRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java)）：拉全部 clean 记忆的 `key=>value` 列表灌 LLM 挑相关 key，按 key 装载 value 注入。即"先加载标签(key)→LLM 判→再加载内容"的正确落地，**仅漏召时触发，非常驻路径**（省 token+加速，不每轮加 LLM）。
- 任一子链路异常不致命：向量挂→仅关键词；关键词挂→仅向量；都空→兜底；兜底也空→不注入（return null）。
- LLM 兜底 prompt（`SELECT_KEYS_PROMPT`）召回优先（"宁多选"），避免漏。

### 实体标签（V31）
- 列：`user_memories.entities` JSONB（[V31 迁移](../../backend/src/main/resources/db/migration/V31__user_memories_entities.sql)，可空，老行 NULL=仅参与向量）。
- 写入：[MemoryConflictJudge.extract](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 顺带抽实体（复用既有 extract LLM 调用，**0 额外调用**），存 `["女儿","北京"]`。落库经 [MemoryService.applyClean](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) → `entitiesJson` 序列化 → mapper `::jsonb`。
- 用途：VECTOR_KEYWORD 关键词召回的索引源。其他模式不读此列。
- **老数据回填**：启用 V31 前写入的老记忆 entities=NULL。admin 在 [RagMemorySettingsTab.vue](../../frontend/src/components/settings/RagMemorySettingsTab.vue) 点「回填实体标签」→ `POST /api/system/settings/rag-memory/backfill-entities`（[SystemSettingController](../../backend/src/main/java/com/superprogrammer/system/controller/SystemSettingController.java)，`role:manage`）→ [MemoryService.backfillEntitiesAsync](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 异步跑（fire-and-forget 到 `memoryTaskExecutor`，无 HTTP 超时）。
  - batch LLM 调用（≤20 条/批，[MemoryConflictJudge.batchExtractEntities](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java)）。
  - 幂等：只查 `entities IS NULL`；LLM 抽不出实体的行落 `entities='[]'`（标记已处理，重跑跳过，不残留 NULL）。
  - 不 bump `updated_at`（不扰动记忆列表排序）；进度见后端日志 `memoryBackfill`。
  - **排坑（别和 RAG 索引轮询混）**：点完按钮后日志刷屏 `SELECT ... knowledge_index_jobs ... FOR UPDATE SKIP LOCKED`（Total: 0）是 [IndexJobWorker.poll()](../../backend/src/main/java/com/superprogrammer/knowledge/service/IndexJobWorker.java) 每 5s（`knowledge.index.poll-ms`）认领 **RAG 索引队列**的正常背景噪声，**和记忆回填无关**，永远响。回填日志走独立线程 `memoryTaskExecutor`、前缀 `memoryBackfill`，两者并行不阻塞。验证回填是否真跑了：grep `memoryBackfill`——0 行会打 `无待回填行（全部已处理）`，跑了会打 `待回填 N 行` / `chunk 完成` / `完成，更新 X 行`；info 级，日志级别 ≥ WARN 看不到。

### 中文标签 + 召回词袋变体（V32）
治"实体桥接"漏召的根因补救：英文 `memory_key`（如 `child_name`）+ value 可能只是专名（"啊闪"），桥接词"女儿"无处可搜 → query「带女儿去玩」0 命中（纯从 value 抽 entities 永远抽不到"女儿"，因为 value 里没有）。V32 双管齐下：
- **列**：`user_memories.memory_key_zh` TEXT（[V32 迁移](../../backend/src/main/resources/db/migration/V32__user_memories_memory_key_zh.sql)，可空）存中文主标签（"女儿"）。
- **entities 扩成召回词袋**：V31 原只抽原文字面词；V32 改抽三类 = ① key_zh 标签（必含）② 同义变体 1-3（女儿→孩子/小孩/闺女；公司→单位/企业）③ value 专名。例 `value="啊闪" key=child_name key_zh="女儿"` → `entities:["女儿","孩子","小孩","啊闪"]`。**角色词必含**（value 只有专名时从 key 语义补角色词+变体），否则 query 用称谓时召回不到。变体污染（"孩子"同时命中儿女）可接受，LLM 下游消歧。`readEntities` 上限 6→10 容纳变体。
- **三列并查**：[findByKeyword](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) 现搜 `entities::text OR memory_key OR memory_value OR memory_key_zh OR block_label`（五列并查），任一命中即召回。`memory_key` 让英文键（child_name）也成为召回锚点；`block_label` 让 query 命中信息块标签（如「家庭」「个人信息」）即召回整块记忆。**per-block_label 阈值筛选（V34）**：[applyKeywordPerBlockThreshold](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 按 block_label 分组各自阈值 N（默认10，0=禁用），组内 > N 时优先留高优（entities/memory_key/memory_key_zh 命中，不卡阈值），低优（memory_value/block_label）补到 N。
- **写入**：[MemoryConflictJudge.extract](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 顺带抽 key_zh + 变体词袋（**0 额外调用**，复用 extract LLM）；[ExtractedFact](../../backend/src/main/java/com/superprogrammer/chat/service/internal/ExtractedFact.java) record 加 `keyZh`；[applyClean](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 落 `memory_key_zh`（insert/updateCleanMemory 均带）。
- **老数据回填**：复用既有「回填实体标签」端点（`POST /api/system/settings/rag-memory/backfill-entities`），查询扩为 `entities IS NULL OR memory_key_zh IS NULL`（补 V31 老数据 + V31 回填过但缺 key_zh 的行）；[batchExtractEntities](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 返回 `Map<Long,BackfillRow(entities,keyZh)>`；mapper `updateEntities`→`updateEntitiesAndKeyZh`（同时更两列，不 bump updated_at）；空 entities→`"[]"`、空 keyZh→`""`（非 null，幂等标记，重跑跳过）。
- **前端**：记忆面板加「名称」列（key_zh，[chat.ts](../../frontend/src/api/chat.ts) `UserMemory` 加 `memoryKeyZh`）+「信息块」列（blockLabel）+「创建」列（createdAt），复用既有 `formatTime`（绝对时间；微信相对样式是后续要求，未做）。

## 异步与缓存（扩容优化）
- **异步模式**：`getMemoryProcessMode` 全局设置（[SystemSettingService](../../backend/src/main/java/com/superprogrammer/system/service/SystemSettingService.java)）控制。
  - `ASYNC`（默认）：stream + 非 stream 路径都 fire-and-forget 到 `memoryTaskExecutor`，**不 gate 回复**；冲突落 DB 后靠前端轮询浮现。
  - `HYBRID`：同步 `processMemory`，askText 追问即时追加进回复（gate 回复），保留为可选。
  - `interceptConflict`（PENDING 答复判定）**保持同步**——仅 PENDING 存在时触发，语义须回复前判定。
- **前端浮现**：[chat store](../../frontend/src/stores/chat.ts) 常驻 3s 轮询 `GET /chat/memories/conflicts`（抄 DocumentManager conditional setInterval 范式），`activeConflictCount` 驱动 ChatView 记忆按钮 `n-badge` 角标。无 SSE/WS push 通道。
- **写入异常不静默**：applyClean 真异常（插不进也更新不了）→ `MemoryService.memoryIncidents`（per-user ConcurrentMap）记消息 + ERROR 日志，不再 catch 吞。前端轮询顺带取 `GET /chat/memories/incident`（取即清）→ ChatView `watch(memoryIncident)` 弹 `useMessage().error` 6s。
- **Redis 查询缓存**：[MemoryQueryCache](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryQueryCache.java)（`StringRedisTemplate`，prefix `mem:`，TTL 60s）缓存 `findDistinctKeys` + `findCleanByBlock`，砍每轮 DB 往返。**写时失效**（`evictUser`）：applyClean / createFlagged / flag / resolve / deleteMemory / clearMemories；纯 TTL 不够（会漏冲突），正确性靠 evict。范式照抄 VisibilitySetService。
- 内部组件：`chat/service/internal/`
  - [MemoryBlockClassifier.java](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryBlockClassifier.java) — 记忆分类
  - [MemoryConflictJudge.java](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) — 冲突裁决
  - ExtractedFact、JudgeResult、RouteResult（DTO）

## 冲突状态机（MemoryConflictService）
- **PENDING**：new 事实暂存快照（不入 user_memories），锁会话（每 session+user 仅 1 个 PENDING，`findActivePending` 只查 PENDING），带 askText 追加进当轮回复问用户。超时未答 → 懒触发 `flag()` 转 FLAGGED。
- **FLAGGED**：new 立即带 `conflict_id` 入库 + old 同组打标（绕 `(user_id, memory_key)` clean 唯一约束，新旧双值共存）。面板可见（`findActiveByUser` 含 FLAGGED），用户 batch-resolve。**不占 PENDING 锁**。
- **RESOLVED**：用户决定（KEEP_NEW / KEEP_OLD / KEEP_BOTH / DISCARD）后落库。**KEEP_BOTH = 合并成一条 clean**（value 去重 join `，`，survivor 清 conflict_id，删多余行，重 embed），非旧"双行共存"——见「待增修改 6」。
- **一句话多冲突**：首轮冲突建 PENDING + 单一 askText（一句话只问一次）；同轮后续冲突 `createFlagged` 直建 FLAGGED（不丢事实、不阻塞、进面板待办），不再降级 clean。

- 实体：`chat/entity/` UserMemory、MemoryConflict
- DTO：UserMemoryVO、MemoryCandidateVO、MemoryBlockHit、MemoryConflictVO、MemoryConflictResolveRequest、MemoryConflictBatchResolveRequest

### 标签语言 + 全量超阈值两阶段（V33）
两个新系统设置（均在 [RagMemorySettingsTab.vue](../../frontend/src/components/settings/RagMemorySettingsTab.vue)，admin）：
- **记忆标签语言** `rag.memory.key-language` = `EN`(默认,向后兼容) / `ZH`。控制**注入上下文里 key 的展示语言**——`[MemoryService.formatLine](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)`：ZH 用 `memory_key_zh`（空回退英文 key），EN 用 `memory_key`。仅展示层，不影响 key 匹配/去重/冲突（这些始终用英文 `memory_key`）。
- **全量记忆阈值** `rag.memory.full-context-threshold` = int（默认 20，0=禁用）。仅 **LLM_FULL_CONTEXT** 模式生效：记忆条数 > 阈值 且 query 非空 → 不再全量灌 value，改两阶段「先加载全部 key → [MemoryConflictJudge.selectRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 让 LLM 选相关 key → 只装相关 value+category」（复用既有 hybrid 兜底链 [MemoryService.filterRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)）。省 token + 治联想泄漏。LLM 选空/异常 → 不注入（宁缺毋滥，与 hybrid 0命中兜底一致）；query 空/未超阈值 → 走原全量。VECTOR_KEYWORD / EMBEDDING_VECTOR 已是定向召回，不受此阈值影响。

### 关键词召回 per-block 阈值（V34）
- **设置** `rag.memory.keyword-per-block-threshold` = int（默认 10，0=禁用）。仅 **VECTOR_KEYWORD** 模式生效。前端 [RagMemorySettingsTab.vue](../../frontend/src/components/settings/RagMemorySettingsTab.vue) 「关键词召回块阈值」（混合模式才可改）。
- **作用**：[MemoryService.applyKeywordPerBlockThreshold](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 把关键词召回结果按 `block_label` 分组（null 视作 ""），各组各自阈值 N：
  - 组内命中 ≤ N → 全留（如"职业"块只命中 3 条，3 条全要）。
  - 组内 > N → 命中高优字段（`entities`/`memory_key`/`memory_key_zh`，由 [isHighPriorityHit](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 对 tokens 子串判定）的行**不卡阈值全留**（哪怕 15 条都留），低优（仅 `memory_value`/`block_label` 命中）补到 N。
- **动机**：用户记忆可能某块爆炸（"偏好"几十条），无脑全灌噪声大、token 费；高优字段命中 = 该行确实被 query 指名道姓撞上（实体/标签/键），低优只是值/块模糊蹭中。优先级排序后既不漏强相关，又压住噪声块。N=0 禁用 = 回退旧"仅 HYBRID_MAX 截断"行为。
- **链路位置**：[findByKeyword](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) 去掉旧全局 `LIMIT 10`（改 LIMIT 200 防病态），per-block 筛选在 Java 端做（SQL 不带行级优先级标记，Java 用 tokens 复判高优/低优）；筛选后并入向量 top-K → `HYBRID_MAX=8` 截断 → 0 命中 LLM 兜底。
- 设置走 KV 表 upsert，**无迁移**。VO/Request 加 `keywordPerBlockThreshold` 字段。

## 项目记忆 home + 可见性混合（V34，取代 V33 纯可见性标签）
> V33「一条记忆属多 scope」是可见性标签语义，但唯一索引 V29 仍 `(user_id,memory_key)` scope-orthogonal → **用户实测撞墙**：global 已有 `child_name`、写目标切到项目 1 再加女儿名 → INSERT 撞 `uk_user_memories_user_key_clean` 报「记忆写入失败：child_name」。根因：dedup 查询 `findSameKeyClean` scope-filtered（只看写目标 scope），但唯一索引无视 scope → 写目标看不到的老行把 INSERT 顶爆，catch 兜底 `againSames` 也 scope-blind → 走「真异常」弹 incident。用户需求明确为**两件事都要**：① 每个项目独立存自己的 `child_name`（global/P1/P2 各一条共存）；② 一条记忆也能跨项目共享（改一次多处生效）。纯可见性标签模型（V33）和纯分区模型都只能满足其一 → 改**混合模型**。

### 两套正交概念
| 概念 | 列 | 管什么 |
|---|---|---|
| **home（写归属/唯一性槽）** | `user_memories.home_project_id`（NULL=global home） | key 在 `(user, home)` 内唯一；决定"能不能再插" |
| **可见性（读注入/共享）** | `is_global` + `user_memory_projects`（V33 既有，不动） | 决定"读时哪些 scope 拉它" |

一条记忆 = 恰好一个 home + 任意多可见性标签。
- **每项目独立**：`(home=NULL, key=child_name)` / `(home=P1, key=child_name)` / `(home=P2, key=child_name)` 三条不同 home → 唯一索引放行共存。
- **跨项目共享**：`(home=P1, key=child_name)` 想让 P2 也见 → `user_memory_projects` 加 P2 行；想让 global 也见 → `is_global=true`。改 value 一次全可见 scope 生效。home 仍只 P1 → 不与 P2-native 那条撞唯一约束。

### 读语义（确认方案 A，保持现状）
读侧零改动。`SCOPE_FILTER` 先按开关踢无关项目（`mem_include_global` + `mem_read_project_ids[]`），剩的里面同 key 多条 → **全注入** LLM（global 一条 + 项目一条都进 prompt，符合"总记忆+项目记忆并存"心智，不项目级覆盖）。home 不参与读可见性过滤。
