# 3.3 MVP验证设计

## 定义

MVP验证是用**最低成本**验证需求真实性的实验方法。不做完整功能，而是设计"信号触发器"——看用户是否真的会来找/会用。[来源:Eric Ries·The Lean Startup | 🔍高 | 2011]

> MVP验证不是"做最小产品"，而是"做最小实验"——产品是手段，验证假设才是目的。[来源:📚训练知识]

## 四种MVP验证方法

### 方法1：假门测试（Fake Door / Painted Door）

| 要素 | 内容 |
|---|---|
| **原理** | 在UI上放一个按钮/入口，点击后告知"功能开发中"，统计点击率 |
| **验证假设** | 用户是否真的会来找这个功能 |
| **成本** | 极低（1-2天开发） |
| **风险** | 用户期望落空→不满；需控制告知方式 |
| **通过标准** | 点击率>5% = 有需求信号；<1% = 伪需求嫌疑 |
| **适用** | C端功能型需求 |

### 方法2：原型测试（Prototype Testing）

| 要素 | 内容 |
|---|---|
| **原理** | 做一个可交互原型（Figma/InVision），让目标用户试用并反馈 |
| **验证假设** | 用户能理解功能吗？会按预期使用吗？ |
| **成本** | 低（3-5天设计） |
| **风险** | 原型≠真实体验，"愿意用"≠"真的用" |
| **通过标准** | 5/8用户能独立完成任务 = 可行；<3/8 = 需重新设计 |
| **适用** | 交互/体验型需求 |

### 方法3：数据验证（Data Validation）

| 要素 | 内容 |
|---|---|
| **原理** | 从已有行为数据中寻找需求信号的痕迹 |
| **验证假设** | 用户已经在做类似的事/寻找类似的功能 |
| **成本** | 极低（数据分析1-2天） |
| **风险** | 相关性≠因果性；数据可能被误读 |
| **通过标准** | 搜索日志/功能使用数据/路径分析有明确信号 |
| **适用** | 已有产品迭代/数据充足时 |

### 方法4：梯度验证（Gradient Testing）

| 要素 | 内容 |
|---|---|
| **原理** | 先做最简版本（V0.1），根据使用数据决定是否加码，逐步验证 |
| **验证假设** | 功能上线后真实使用率是否达到预期 |
| **成本** | 递增（V0.1成本低，逐步追加） |
| **风险** | V0.1太粗糙给用户留下坏印象 |
| **通过标准** | V0.1使用率>10% → 做V0.2；<5% → 不追加 |
| **适用** | 不确定需求价值时的"试水"策略 |

## MVP验证决策树

```
需求不确定性判断
├── 不确定性低（已有强行为数据支撑）
│   └── 数据验证 → 确认后直接开发
├── 不确定性中（有场景但缺行为数据）
│   └── 假门测试/原型测试 → 验证通过→开发
├── 不确定性高（只有内部/单点来源）
│   └── 梯度验证（V0.1→数据决定→V0.2/终止）
└── 不确定性极高（AI推理/竞品跟风）
    └── 先做JTBD验证 → 通过→假门测试 → 通过→原型测试
```

## MVP验证的6条红线

| 红线 | 原因 | 正解 |
|---|---|---|
| 不能用假门测试B端核心流程 | B端用户信任成本高 | 用访谈+原型验证 |
| 不能对付费用户做假门 | 影响付费体验 | 用免费/新用户群体 |
| 不能用原型测试替代数据验证 | "愿意用"≠"真的用" | 原型验证≠发布决策 |
| 不能跳过验证直接开发 | 如果是伪需求=浪费大量开发资源 | 至少做1种验证 |
| 不能用单次验证下结论 | 样本不足/偶然性 | 至少2种方法交叉验证 |
| 不能因验证失败而归因为"执行不好" | 验证失败可能=需求本身就是伪的 | 诚实面对验证结果 |
