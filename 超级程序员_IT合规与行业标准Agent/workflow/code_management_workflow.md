# Code Management Workflow

## Purpose

基于企业代码管理制度知识框架，提供代码资产全生命周期管理的标准化执行路径，覆盖分级分类、Git工作流演进、质量门禁、AI代码治理、开源合规、防泄密六大核心领域。

## Prerequisites

- 已明确组织规模（小团队/大团队/跨国企业）
- 已了解现有代码托管平台（GitHub/GitLab/Bitbucket/自研）

## Steps

### Step 1: 代码资产分级分类

**Goal**: 建立四级代码资产分类体系并定义每级的权限矩阵与保护策略
**Completion criterion**: 输出完整的代码资产分类清单，包含分级标签、RBAC/ABAC混合权限矩阵、访问控制规则

读取知识库中代码资产四级分类框架 [参考: Agents知识库/0_超级编程行业知识库/13_IT合规与行业标准.md > 代码资产四级分类]。
按以下顺序执行：
1. 盘点全部代码资产，按业务关键性分为A核心/B业务/C通用/D公开四级
2. 为每级定义RBAC基础角色（架构师/TL/开发/实习生/外包）+ ABAC动态属性（项目阶段/紧急度/合规要求）
3. 制定每级的最小权限集合：A级需VP审批+双人控制，B级需TL审批，C级开放给正式员工，D级可对外开源
4. 输出《代码资产分级分类表》与《权限矩阵说明书》

### Step 2: Git工作流选型与实施

**Goal**: 根据团队规模与发布频率选择并实施合适的Git工作流
**Completion criterion**: 选定Git工作流模型并输出分支策略文档，包含分支命名规范、合并规则、保护规则

基于组织特征选择工作流 [参考: Agents知识库/0_超级编程行业知识库/13_IT合规与行业标准.md > Git工作流演进]：
- 小团队（<10人）+ 低频发布 → GitHub Flow
- 大团队（>50人）+ 高频发布 → Trunk-Based + Feature Toggle
- 中等团队 → GitLab Flow 或分支保护策略
执行：
1. 输出《Git工作流选型决策记录》（ADR格式）
2. 配置分支保护规则：main分支需PR+审查+CI通过+无冲突
3. 定义Feature分支命名规范：`feature/{JIRA-ID}-{brief-desc}`
4. 制定合并策略：squash merge用于功能分支，rebase用于长期分支

### Step 3: 四级质量门禁建设

**Goal**: 建立从本地提交到生产部署的四级质量门禁体系
**Completion criterion**: 四级门禁全部配置完成，每级有明确的通过/阻断标准

依据四级质量门禁框架 [参考: Agents知识库/0_超级编程行业知识库/13_IT合规与行业标准.md > 四级质量门禁]：
1. 本地pre-commit门禁：配置husky/lint-staged，强制代码格式化（Prettier/Black）+ 静态检查（ESLint/pylint）+ 单测通过率100%
2. PR自动化扫描：集成SonarQube/Snyk，高危漏洞阻断合并，代码覆盖率下降阻断
3. 人类审查+AI审查：要求至少1人审查+AI辅助（GitHub Copilot Review/Amazon CodeGuru），审查清单包含安全性/性能/可读性
4. 生产部署前验证： staging环境自动化回归测试 + 灰度发布健康检查（错误率<0.1%，P99延迟<基线120%）
输出：《质量门禁配置手册》与《阻断事件处理流程》

### Step 4: AI生成代码治理策略

**Goal**: 建立AI生成代码的三级治理框架，平衡效率与风险
**Completion criterion**: 输出AI代码使用政策文档，明确三级治理的具体场景与审批流程

参考AI代码三级治理框架 [参考: Agents知识库/0_超级编程行业知识库/13_IT合规与行业标准.md > AI生成代码三级治理]：
1. 自由使用级（补全/测试）：允许使用GitHub Copilot等工具生成单行补全、单元测试、文档注释，无需审批
2. 审批使用级（完整函数/模块）：AI生成超过20行的逻辑需标注`// AI-generated`，经TL审查后方可合并
3. 禁止使用级（高敏感领域）：认证/加密/支付/个人隐私处理代码严禁AI生成，必须使用人工编写+双人审查
执行：
- 在CI中集成AI代码检测工具（如GitHub的AI检测标签或自定义脚本）
- 建立《AI代码使用登记簿》，记录审批级与禁止级的例外申请
- 每季度审计AI代码占比与缺陷率，输出治理报告

### Step 5: 开源合规全链路建设

**Goal**: 建立从准入到持续监控的开源合规全链路，规避许可证风险
**Completion criterion**: 开源合规流程覆盖全部依赖，SBOM可自动生成，GPL/AGPL组件已清理或替换

依据开源合规全链路框架 [参考: Agents知识库/0_超级编程行业知识库/13_IT合规与行业标准.md > 开源合规全链路]：
1. 准入审查：新引入依赖前填写《开源组件准入表》，审查许可证类型（MIT/Apache-2.0友好；GPL/AGPL入黑名单）
2. CI扫描：Pipeline集成FOSSology/ScanCode，每次构建自动生成SBOM（SPDX/CycloneDX格式）
3. 持续漏洞监控：订阅SNYK/OSV数据库，高危CVE 24小时内推送告警，7天内必须修复或降级
4. 案例学习：输出《开源合规风险案例集》（包含GPL违规被诉200万元案例的教训）

### Step 6: 代码防泄密分层模型实施

**Goal**: 根据代码资产分级实施差异化的防泄密技术措施
**Completion criterion**: 三级防护体系全部落地，核心代码VDI+水印已部署，审计日志可追溯6个月

参考代码防泄密分层模型 [参考: Agents知识库/0_超级编程行业知识库/13_IT合规与行业标准.md > 代码防泄密分层模型]：
1. 核心代码（A级）：VDI虚拟桌面访问 + 屏幕水印（含用户名+时间戳）+ USB/剪贴板禁用 + 操作录屏
2. 重要代码（B级）：MFA多因素认证 + 全量审计日志 + DLP终端监控 + 定期账号稽核
3. 普通代码（C/D级）：标准SSO接入 + 常规审计 + 离职账号自动回收
执行：
- 部署DLP系统（如Digital Guardian/McAfee DLP），配置代码类敏感数据识别规则
- 核心研发人员签署《代码保密协议》，明确竞业限制与泄密追责条款
- 每月执行一次代码访问审计，识别异常访问模式（如非工作时间大量下载）

## Post-Workflow

1. 读取 `checklist/code_management_workflow_checklist.md`
2. 交叉验证每级门禁、每项治理策略、每个合规检查点
3. 全部通过后输出《代码管理制度总纲》并归档
