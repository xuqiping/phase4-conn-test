## 调用链路（关键路径）

```
注册：RegisterModal → authApi.register → AuthController.register → AuthService.register
     → 建 users + PASSWORD 凭证(verified=TRUE) + EMAIL 凭证(verified=FALSE) → 异步发激活邮件

手机登录：SmsLoginTab → 滑块前置 → authApi.sendSmsCode(captchaToken) → CaptchaService.verify(单次有效)
     → SmsService.sendCode(限流三档) → 输码 → authApi.loginBySms → SmsService.verifyAndLogin
     → 新号自动建号 + issueTokensForSms → JWT

微信登录：QrcodeLoginTab → authApi.getWechatRedirectUrl → 跳微信授权 → 回调 GET /callback
     → WechatAuthService.exchange(state 校验防CSRF) → 新号建号 → 302 前端 fragment 传 token

找回密码：ForgotPasswordModal → authApi.forgotPassword → PasswordResetService.forgot(统一话术防枚举)
     → 发邮件/短信 → ResetPasswordView → authApi.resetPassword → PasswordResetService.reset
     → PasswordPolicy + 更新密码 + kickAllSessions(删 session:user:{userId})

安全设置：SecuritySettingsTab → authApi.getCredentials → CredentialController.list
     绑邮箱：authApi.bindEmail → CredentialService.bindEmail(建 verified=FALSE) + EmailService.sendVerifyEmail
     解绑：authApi.unbindCredential → CredentialService.unbind(至少留一种)
     改密：authApi.changePassword → CredentialService.changePassword(验旧+Policy+踢会话) → 前端 logout 跳登录
```

## 技术清单与原理注解

### AJ-Captcha 滑块验证码（BLOCKPuzzle）
- **采用技术**：`com.anji-plus:spring-boot-starter-captcha:1.3.0` + `aj.captcha.cache-type=redis`
- **一句话原理**：后端返背景图(带缺口)+滑块图+AES密钥，前端拖滑块到缺口位，轨迹 AES-ECB 加密回传，后端校验 x 坐标。
- **大白话**：拼图验证——给张缺了块的图，把滑块拖到缺口处对上。
- **生活化案例**：像把积木塞回对应的坑里，对准了才放行。
- **踩坑 1**：BLOCKPuzzle 后端只校验 x 坐标，前端发固定 y=5；AES-ECB 模式 Web Crypto API 不支持，必须用 crypto-js；redis 缓存实现跨实例 + 单次有效（用完删 token）。
- **踩坑 2（Phase4 实证，三连环）**：①starter 是 Boot2 时代产物，自动配置走 `META-INF/spring.factories`——**Boot 3.x 已废弃该机制**，自动配置从不生效，`CaptchaService` bean 必须手动装配；②工厂签名是 `getInstance(Properties)`，传 null 直接 NPE；③**配置前缀必须是 `aj.captcha`**（非 `captcha:`），写错属性不绑定。现 `CaptchaConfig` 委托官方 `AjCaptchaServiceAutoConfiguration` 构建 + 自写 `CaptchaCacheServiceRedisImpl`（官方 jar 只带 local 内存实现）注册进工厂 `cacheService` map（key=type()="redis" 小写，与 StorageType 枚举常量名一致）。
- **遗留**：`GET /api/auth/captcha` 运行时取图失败 500（bean 装配已通，底图加载待查；SMS 未开启用不到，低优先级）。

### crypto-js AES-ECB 轨迹加密
- **采用技术**：`crypto-js@4.2.0`
- **一句话原理**：前端用后端给的 secretKey 做 AES-ECB 加密 `pointJson(x,y)` → 组装成 captchaVerification 串回传。
- **大白话**：把"拖到哪个位置"这个答案加密传输，防中间人篡改坐标。
- **踩坑**：Web Crypto API 不支持 ECB 模式，故引 crypto-js（唯一非原生依赖原因）。

### 多凭证账号模型（user_credential 表）
- **一句话原理**：一个用户 N 把"钥匙"（密码/邮箱/手机/微信），任一把 verified=TRUE 即可登录。
- **大白话**：以前一人一把密码钥匙，现在一人一串钥匙环，哪把都开门。
- **生活化案例**：家门能钥匙开、能指纹开、能密码开——任意一种就行。
- **关键约束**：解绑至少留一种（防失联）；未验证邮箱不可找回密码；identifier 脱敏展示。

### SessionService 单点登录 + 踢会话
- **一句话原理**：登录写 `session:user:{userId}=sid` 进 Redis，JWT 带 sid claim，请求比对 sid 不符即拒。
- **大白话**：同一账号同时只一处能在线，新登录踢旧。
- **两套删键语义**：`clearSession(sid)` 比对 sid 只删自己（防 logout-bomb）；`kickAllSessions()` 无条件全删（改密/重置密码强语义）。
- **踩坑（Chunk G 修复）**：PasswordResetService 原直接 `delete("session:"+userId)` 键前缀错（实际 `session:user:`），踢会话不生效；改走 kickAllSessions 统一。

### 微信扫码 token fragment 传递
- **一句话原理**：后端回调把 JWT 放 URL fragment（`#/login?token=xxx`）而非 query string。
- **大白话**：token 放在 # 后面，浏览器不发 # 后内容给服务器，不进 access log/referer。
- **生活化案例**：像把密码写在信封内层，邮递员（服务器日志）看不到。

### 统一话术防账号枚举
- **一句话原理**：找回密码/重发邮件无论账号存不存在都返同一句话。
- **大白话**：不告诉攻击者"这个邮箱注册没注册"，都回"若存在已发送"。
- **配套**：user==null 分支跑 dummy bcrypt 抹平时序侧信道（沉淀约束 6）。

## 数据库表注解（V102__auth_multi_credential.sql）

### user_credential（用户凭证表）
- **用途**：存每个用户的多种登录凭证，一个用户 N 行。
- **生活化比喻**：钥匙环——一人一环，环上 N 把钥匙。
- **关键字段**：
  - `user_id` BIGINT：归属用户（FK users.id）
  - `credential_type` VARCHAR(20)：PASSWORD/EMAIL/PHONE/WECHAT/DINGTALK
  - `identifier` VARCHAR(200)：凭证标识（username/邮箱/手机/unionid）
  - `secret` VARCHAR(100)：仅 PASSWORD 存 BCrypt 哈希，余 null
  - `verified` BOOLEAN：是否验证（未验证邮箱不可找回密码）
  - `verified_at` TIMESTAMPTZ：首次验证时间
  - `deleted` SMALLINT：软删（@TableLogic），解绑置 1
- **索引**：uk_credential_type_identifier（部分唯一索引 where deleted=0，软删不参与唯一约束）/ uk_user_credential_type / idx_credential_user
- **users 表加列**：email_verified / phone / wechat_unionid / wechat_openid（兼容旧登录路径）

> **踩坑批注**：迁移号 V101 被 RAG 占用，本功能用 V102；存量数据 EMAIL verified 全置 FALSE（防找回漏洞）；唯一索引用 WHERE deleted=0 部分索引，软删凭证可重新绑定。
> **踩坑批注（Phase4）**：V102 建表漏了 BaseEntity 的 created_by/updated_by 列——实体字段会被 MyBatis-Plus 编进 SELECT/INSERT 列清单，首次真实 DB 访问即 `字段 "created_by" 不存在`（单测 mock mapper 不暴露）。V110 已补。**凡新建表：核对 BaseEntity 全字段（id/created_by/created_at/updated_by/updated_at/deleted/version）都有对应列。**

## 12x 真实邮箱接入 + 安全加固（2026-08-22，commit e5eab956/7acd54b2/9f51a6df/774b4104/4e30d3c6）

### 代码位置
- `auth/service/mail/MailSender.java` — 发信传输抽象（provider()+send()）；`AliyunMailSender`/`SmtpMailSender` 两实现，`EmailService` 按快照 provider 路由

- `auth/service/ProgressiveCaptchaGuard.java` — 渐进式滑块门槛：`captcha:need:{scope}:{key}` 30min 窗，失败≥2 触发，成功清零；触发未带 token 抛 40107「请先完成滑块验证」
- `auth/controller/EmailVerifyController.java` — +`POST /api/auth/register/email-code`（公开，白名单两处同步）
- `AuthService.register` — 查重/密码策略后验码（不烧码），EMAIL 凭证直接 verified=TRUE；`AuthController.register` 不再发激活链接
- `CredentialController.bindEmail` — 账号已绑 TOTP → 强制校验两步码
- `billing/service/PaymentOrderService.java` — createOrder 前置闸：无 verified EMAIL 凭证 → 400（B5）
- 前端：`AuthChannelSettingsTab.vue`（通道类型+测试发信）、`RegisterModal.vue`（验证码行+60s 倒计时+滑块）、`PasswordLoginTab.vue`/`ForgotPasswordModal.vue`（40107 触发滑块）、`RechargeDialog.vue`（邮箱门槛引导链接）、`api/request.ts`（错误对象挂业务码 code）

### 技术原理大白话
- **MailSender 抽象**：发信业务（模板/token/限流）与运输层（阿里云 API / SMTP 协议）解耦——换邮局不改信件。配置页「测试发信」不要求 enabled=true：先测通再开开关。
- **注册码替代激活链接**：注册前证明邮箱归属，建号即 verified——假邮箱根本建不了号（烧 LLM 配额链断根）。激活链接流程保留给「改绑邮箱」场景。
- **渐进式滑块**：好人无感（0 失败=0 验证），坏人第二三次失败就要过滑块——成本不对称：滑块对人是 2 秒，对脚本是要接打码平台烧钱。
- **充值邮箱门**：积分=钱，丢号=丢钱；邮箱是资金找回的最后兜底通道，没验证邮箱不许充钱——先系安全带再上路。

### 踩坑批注
- MailSendQuotaService 曾误入 Chunk A 提交（untracked 被 git add 扫入）——功能在 B3 才接线，历史无妨但注意「新文件随下个 chunk 走」的约定。
- `EmailService` 构造器两连改（+quota/+guard）——单测直接 new 构造的地方全部要同步，IDE 编译错最诚实。
- 前端 NModal 走 teleport，vitest stub 后 `wrapper.text()` 恒空——DOM 断言别写，按项目惯例探 vm 状态（defineExpose/响应式属性）。

## 12x 开关回退（2026-08-23，commit f4d05a55）：邮箱验证总开关

### 代码位置
- 开关键：`auth.channel.mail.verification-required`（V146 seed 默认 false）——读取口 `AuthChannelSettingService.isEmailVerificationRequired()`
- 消费三处：`AuthService.registerInternal`（关=邮箱可选不验码，EMAIL 凭证 verified=FALSE）、`EmailService.sendRegisterCode`（关=直接 400 无需验证码）、`PaymentOrderService.createOrder`（关=B5 门跳过）
- 透出：`AuthPublicConfigController` /api/auth/channels +`registerEmailCodeRequired`；admin UI=AuthChannelSettingsTab 邮件卡「邮箱验证总开关」
- 前端：`RegisterModal.vue` prop `emailCodeRequired`（LoginView 从 channels 传入）——验证码行 v-if、邮箱必填规则 computed 动态化

### 技术原理大白话
- **总开关而非代码回退**：B1/B5 代码一行没删，全部挂在一个 DB 开关下——真邮接入后网页上翻一下就复活，不用再发版。像电闸：装修期拉掉，入住推上。
- **开关关时 EMAIL 凭证 verified=FALSE**：没验过的邮箱不能当已验证——否则找回密码会把重置信发到没证明过归属的邮箱，等于把钥匙交给自称房主的人。
- **B5 门跟着关**：邮件通道没接时无人能验证邮箱，硬门=充值全废——门和通道是同一根生命线，共用一个开关。

### 踩坑批注
- Mockito 严格模式：开关关的分支不再调 `credentialService.findByUserIdRaw`，多余 stub 会炸 UnnecessaryStubbingException——分支测试只 stub 分支内用到的。
- NModal teleport 坑新例：attachTo document.body + afterEach 清 `document.body.innerHTML`，否则上一个用例的弹窗残留污染 DOM 断言。
