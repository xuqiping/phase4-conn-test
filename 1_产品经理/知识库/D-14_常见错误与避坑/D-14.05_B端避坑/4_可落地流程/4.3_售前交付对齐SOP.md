# 售前交付对齐 SOP

## 适用场景
大客户签单前/POC启动前/售前做出超出标准产品范围的承诺时，需要对齐售前承诺与交付能力。

## 前置条件
- 已有产品功能清单和roadmap
- 已有交付团队的能力边界定义（能交付什么/不能交付什么/交付周期多久）
- 已有POC标准流程和成功标准模板

## 步骤

### Step 1 售前承诺清单梳理
售前每做一个承诺，必须记录入《承诺清单》：

| 字段 | 内容 | 承诺级别 |
|---|---|---|
| 功能承诺 | 具体功能的描述 | 🟢已交付 / 🟡roadmap内 / 🔴未规划 |
| 性能承诺 | 并发/响应/可用性指标 | 🟢已验证 / 🟡理论可达 / 🔴未验证 |
| 集成承诺 | 与客户现有系统的对接方案 | 🟢有标准API / 🟡需定制开发 / 🔴无技术方案 |
| 时间承诺 | 交付/上线时间节点 | 🟢标准周期内 / 🟡需加排期 / 🔴不现实 |

承诺级别规则：
- 🟢绿色承诺：产品已交付且验证过，可以直接写入合同
- 🟡黄色承诺：roadmap内但未交付，可以写入合同但必须标注版本/时间，附"如延期则XX"条款
- 🔴红色承诺：未规划/未验证，**绝不写入合同**，只能口头表达"我们会评估"

### Step 2 三方对齐会
每个大单（ARR>50万或定制需求>3个）签约前，必须召开三方对齐会：

**参会人**：售前负责人 + 交付负责人 + 产品负责人

**议程**：
1. 售前逐条过承诺清单，说明每个承诺的客户背景和必要性
2. 交付逐条评估每个承诺的可行性、周期和成本
3. 产品逐条确认每个承诺与产品roadmap的一致性
4. 三方对不一致项达成共识：修改承诺/调整排期/加收费/删除承诺

**关键规则**：交付团队对🔴红色承诺有一票否决权——如果交付说"做不到"，售前必须撤回承诺

### Step 3 合同条款对齐
对齐会后的承诺清单转化为合同条款：

| 条款类型 | 内容 | 保障措施 |
|---|---|---|
| 核心交付项 | 🟢绿色承诺的完整列表 | 验收标准+SLA |
| roadmap交付项 | 🟡黄色承诺的版本/时间 | 如延期则替代方案或退款条款 |
| 不包含项 | 明确列出"不在本次交付范围内"的功能 | 防止客户理解偏差 |
| 定制开发项 | 定制需求+费用+维护责任+SLA | 单独报价+单独验收 |

### Step 4 POC边界定义
如果签约前需要POC：

**必须定义**：
1. **成功标准**：3-5个可量化的指标（如：XX流程跑通/XX数据对接成功/XX并发下响应<2s）
2. **时间边界**：POC周期≤2周（超过2周不是POC是项目）
3. **不做清单**：明确POC范围外的事项（如：不做性能压测/不做多租户配置/不做定制开发）
4. **退出条件**：POC失败时双方的权利（客户可退定金/我方可终止评估）

**POC红线**：
- POC不收费→周期≤2周→只验证核心假设
- 超过2周→转为付费项目→重新签合同
- 售前不能承诺"POC期间免费定制开发"

### Step 5 交付交接
签约后，售前向交付做正式交接：

**交接清单**：
1. 客户业务背景和决策链
2. 承诺清单（对齐后版本）+合同对应条款
3. POC结果（如有）+客户反馈
4. 客户关键人联系方式和沟通偏好
5. 已知风险和应对预案

**交接红线**：交付团队未收到正式交接清单前，不得启动交付工作——没有交接=售前还在改承诺

### Step 6 售后回溯
客户验收后/上线3个月后，回溯：

| 回溯项 | 目的 |
|---|---|
| 承诺vs交付差异 | 哪些承诺没兑现？根因是什么？ |
| 客户实际满意度 vs 续费意愿 | 验证是否有ROI幻觉 |
| 售前承诺升级建议 | 哪些🟡已交付可升级为🟢？ |
| 交付成本 vs 预估 | 是否有成本超支？下次如何更准预估？ |

## 红线
- 🔴红色承诺绝不写入合同——这是法律和信誉的底线
- 交付团队有一票否决权——如果交付说"做不到"，就必须修改承诺
- POC超过2周必须转为付费项目——否则交付团队被白嫖
- 售前佣金分两段发放——签单50%+验收50%——交付质量与售前收入绑定
- 每季度统计"承诺兑现率"并纳入售前KPI——兑现率<80%扣绩效
