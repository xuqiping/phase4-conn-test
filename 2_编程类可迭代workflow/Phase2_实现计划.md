# Phase 2 · 实现计划（plan.md · Plan）

> 类型：流程步骤 · **Phase 2**
> 版本：v1.3（v1.1 增技术坑点预判 + 安全检查清单；v1.2 增性能考虑；v1.3 增功能联动点清单 + 运维考量清单）
> 对应模式：**Plan-Implement-Run 的 Plan 步** · 铁律：**#1 规格先行、#2 拆小迭代块**

## 目标

把规格拆成一份**逐步骤、可执行、经人确认**的实现计划。这是「未经许可不写码」的闸门——计划没过审，不准进 Phase 3。

## 输入

- Phase 1 的 `workflow_output/docs/specs/` 全部规格
- `workflow_output/docs/file_structure.md`
- `workflow_output/项目规范约束/AGENTS.md`

## 动作清单

1. **生成 plan.md**：用推理模型，基于规格生成 `workflow_output/docs/plans/<功能名>.plan.md`。
2. **计划格式约束**：
   - 只含**伪代码**，不含真代码
   - 每步写明：**目标 / 动作 / 涉及文件（≤20个）/ 依赖 / 验证步骤**
   - 把无障碍性（accessibility）融入每步，不单列一步
   - 不要过度架构（keep it simple）
   - **专业术语批注**：术语首次出现时**行内括注一句大白话**，并在**底部维护术语表**（术语 \| 大白话 \| 简单案例）。主文专业度不变，批注只作辅助。
3. **【新增】技术坑点预判**：针对本功能用到的技术栈/方案，列出可能的坑和规避措施（详见配套模板的「技术实现坑点预判与规避措施」section）；**特别关注性能相关的坑**（N+1 查询、大数据集处理、缓存失效、并发竞争等）。
4. **【新增】安全检查清单**：对照 Phase 1 的安全策略，列出本功能必须覆盖的安全检查项（鉴权/输入校验/加密/审计等）。
5. **【新增】功能联动点清单**：识别本功能里"某个操作会触发其他 UI / 数据变化"的联动点，逐条列出并写成 plan.md 的独立 chunk。每条写明：**触发动作 / 联动对象 / 预期变化 / 边界（反向、半选、取消、批量）**。典型例子：
   - 父勾选框勾上 → 所有子勾选框全选（且要覆盖：取消父 → 子全清；子全勾 → 父自动勾上；子部分勾 → 父半选）
   - 主表单提交成功 → 副表/草稿清空
   - 切换租户 / 切换组织 → 列表、权限、缓存重新加载
   - 删除父记录 → 子记录级联处理（删 / 软删 / 拦截）

   > 这是最容易被"做完主功能就以为完事"而漏掉的部分。交互联动不做，Phase 4 一验就翻车。
6. **【新增】运维考量清单**：从"上线后要怎么运维它"反推开发期必须配合埋好的事，逐条写进 plan.md，让 Phase 3 写码时就埋上（运维能力是开发期埋出来的，上线后补不回来）。至少想过以下每一项并明确**做 / 不做 / 后续再说**：
   - **可观测性**：关键路径打日志（含 traceId / 请求 id）、埋监控指标、健康检查端点
   - **配置开关**：高危 / 灰度 / 实验性功能用配置开关控制，出问题能关掉而不用回滚发版
   - **可回滚**：数据库变更可回滚（配合 Flyway）、数据迁移可逆、不写"只能进不能退"的结构变更
   - **限流 / 熔断 / 降级**：依赖第三方时设超时、熔断、降级路径（缓存兜底 / 默认值 / 友好报错）
   - **运维入口**：是否需要后台运维页面或脚本（手动重试、查日志、修脏数据、补单、对账）
   - **告警阈值**：哪些指标异常该告警、告警发给谁
   - **容量 / 性能预案**：预估数据量增长、是否有大表分区 / 归档需求

   > 原则：**不是每条都要做，但每条都要想过并落字**。"上线再说"= 上线必炸。
7. **与人迭代直到满意**：读计划，让它 critique 自己，调整步骤顺序和粒度。
8. **【硬闸门】未经你的明确许可，不开始实现。**

## 避坑点

- **计划粒度 = 一个 chunk 一步**。太粗（「实现整个用户系统」）= 回到 vibe coding 的失控；太细（「写一个 if 语句」）= 没意义。理想是「一个功能点 / 一个函数族」。
- 涉及文件 > 20 个，说明这步太大，**继续拆**。
- 计划是建议不是圣旨——Phase 3 发现不合理可偏离，但要回来更新 plan.md 并注明原因。
- **【新增】技术坑点预判别写得太泛**。「这个技术可能有坑」= 没意义；要具体到「用 X 库做 Y 时，Z 场景会有性能问题，规避措施是 A」。
- **【新增】安全检查不是走形式**。清单里的每一项，Phase 3 都要实际验证并标记完成。
- **【新增】功能联动点别只列正向**：父勾选联动子，光写"勾上→全选"不够，还得写"取消父→子全清""子全勾→父自动勾上""子部分勾→父半选"。漏掉反向 / 半选 / 批量边界，Phase 4 验收照样翻车。
- **【新增】运维考量不是上线后再说**：等上线了才发现"没日志、没监控、改个配置要发版、出问题没法手动兜底"——全是开发期没埋运维接口的债。计划阶段过一遍运维清单，Phase 3 才知道在哪里埋点、留开关、留运维入口。

## 出口条件（满足才进 Phase 3）

- [ ] plan.md 完成，步骤清晰、文件明确、含验证步骤。
- [ ] **【新增】功能联动点清单已列出**（含正向 / 反向 / 半选 / 批量边界）。
- [ ] **【新增】运维考量清单已过一遍**（可观测性 / 配置开关 / 可回滚 / 限流熔断 / 运维入口 / 告警阈值 / 容量预案，每条明确做 / 不做 / 后续再说）。
- [ ] 你**明确许可**开始实现。
