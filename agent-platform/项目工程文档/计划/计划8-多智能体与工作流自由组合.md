> 创建时间：2026-06-02  
> 重写时间：2026-06-03  
> 当前定位：组合协议层、Python LangGraph sidecar、checkpoint/resume、前端运行时体验、`SKILL` / `AGENT_REF` 真实回调执行已完成最小闭环；后续重点转向真实环境联调、部署配置和 `WORKFLOW_REF` 递归执行治理。

## 一、当前项目真实状态

项目已经完成以下基础能力：

- 后端：Spring Boot 3.2.5、MyBatis-Plus、Flyway、JWT/RBAC、WebFlux/WebSocket、LLM Gateway。
- 前端：Vue 3、TypeScript、Vite、Naive UI、Vue Flow 工作流画布。
- 已有业务模块：Agent 管理、Skill 管理、Workflow CRUD、Chat 会话、流式输出、执行日志、用户级模型配置。
- 已有运行时：`OrchestrationEngine` 支持 Agent / Workflow 模式；计划8新增 `RuntimeGateway`，可在 mock 和 Python sidecar 之间切换。
- 已有工作流存储：`workflows`、`workflow_nodes`、`workflow_edges`。
- 已有执行日志：`execution_logs`、`execution_step_logs`。
- 当前已完成：多 Agent/Workflow 引用节点、统一跨服务执行协议、Python LangGraph sidecar、checkpoint/resume、`SKILL` / `AGENT_REF` 真实执行、执行监控结果展示和 callback 错误传播。
- 当前未完成：`WORKFLOW_REF` 真实递归执行、真实 LLM Router、跨 Workflow 对象级权限校验、部署环境手工联调和浏览器级 E2E。

因此计划 8 不应该直接重写执行引擎，也不应该在 Java 中复制 LangGraph 的复杂图调度能力。正确下一步是先建立可测试的协议和网关闭环。

## 二、目标架构

### 2.1 分层职责

| 能力 | Java Spring Boot | Python LangGraph sidecar |
|------|------------------|--------------------------|
| 用户、认证、权限 | 负责 | 不负责 |
| Agent/Workflow 元数据 | 负责 | 不负责 |
| 模型供应商/API Key 管理 | 负责 | 通过 Java 注入或代理获取 |
| Vue Flow 画布 JSON 保存 | 负责 | 不负责 |
| 标准执行协议定义 | 负责 | 遵守协议 |
| Vue Flow -> WorkflowDefinition | 负责 | 可二次校验 |
| WorkflowDefinition -> StateGraph | 不负责 | 负责 |
| routing/condition/subgraph/parallel/join | 不重复实现 | 负责 |
| checkpoint/resume | 保存外部引用 | 负责 |
| 执行日志、审计、前端转发 | 负责 | 产生事件 |

### 2.2 推荐运行链路

1. 前端保存 Vue Flow 节点和边到 Java 数据库。
2. 用户从 Chat 或 Workflow 页面触发执行。
3. Java 校验用户权限、读取 Agent/Workflow、转换为标准 `WorkflowDefinition`。
4. Java 生成 `ExecutionRequest`，调用 sidecar 的 `/api/runtime/executions`。
5. sidecar 编译并执行 LangGraph，持续返回 `ExecutionEvent`。
6. Java 保存执行事件、父子执行链和 checkpoint 引用。
7. Java 通过 SSE/WebSocket 转发事件给前端。
8. 前端展示执行进度、节点状态、输出和错误。

### 下一步只做阶段一：组合协议层最小闭环

- 不实现 Java 复杂图调度。
- 不实现 parallel/join/checkpoint/resume 内核。

- 不改变现有 Chat 流式主链路。

阶段一完成后，项目应该具备一个可替换的运行时边界：mock sidecar 可以替换成 Python LangGraph sidecar，而 Java 侧协议、日志、权限和前端事件展示不需要重写。

## 六、阶段一任务拆解

### Task 1：定义 runtime DTO 与枚举

目标：让 Java 侧拥有稳定的跨服务协议对象。

修改：

- 新增 `com.superprogrammer.runtime.dto` 包。
- DTO 使用 Lombok `@Data`、`@Builder`、`@NoArgsConstructor`、`@AllArgsConstructor`。
- `config`、`input`、`output`、`metadata` 先使用 `Map<String, Object>`，避免阶段一过早绑定具体 schema。

验收：

- `mvn -q -DskipTests compile` 通过。
- Jackson 可以序列化/反序列化 `WorkflowDefinition` 和 `ExecutionEvent`。

### Task 2：实现 WorkflowDefinitionAssembler

目标：把现有数据库工作流转为标准 `WorkflowDefinition`。

规则：

- `WorkflowNode.nodeId` -> `RuntimeNode.id`。
- `WorkflowNode.type` 统一转大写。
- `WorkflowNode.config` 是 JSON 字符串，解析为 `Map<String, Object>`；为空时使用空对象。
- `WorkflowEdge.sourceNodeId` -> `RuntimeEdge.source`。
- `WorkflowEdge.targetNodeId` -> `RuntimeEdge.target`。
- 非法 JSON config 抛出 `BusinessException(ErrorCode.PARAMS_ERROR, "工作流节点配置不是合法 JSON")`。

验收：

- 测试覆盖 START/SKILL/END 基础转换。
- 测试覆盖 AGENT_REF config 中的 `agentId`。
- 测试覆盖 WORKFLOW_REF config 中的 `workflowId`。
- 测试覆盖非法 config 报错。

### Task 3：扩展执行日志结构

目标：执行日志能表达嵌套执行链和 sidecar checkpoint 引用。

数据库迁移 `V12__extend_execution_logs_for_runtime.sql` 增加：

```sql
ALTER TABLE execution_logs
    ADD COLUMN parent_execution_id BIGINT,
    ADD COLUMN root_execution_id BIGINT,
    ADD COLUMN source_type VARCHAR(30),
    ADD COLUMN source_id BIGINT,
    ADD COLUMN node_id VARCHAR(100),
    ADD COLUMN external_thread_id VARCHAR(200),
    ADD COLUMN checkpoint_ref VARCHAR(500),
    ADD COLUMN trace_id VARCHAR(100);

CREATE INDEX idx_execution_logs_root_execution_id ON execution_logs(root_execution_id);
CREATE INDEX idx_execution_logs_parent_execution_id ON execution_logs(parent_execution_id);
CREATE INDEX idx_execution_logs_trace_id ON execution_logs(trace_id);
```

同时同步：

- `ExecutionLog` 实体字段。
- `schema-h2.sql` 测试表字段。
- `ExecutionLogService` 创建和更新方法。

验收：

- H2 测试环境启动通过。
- 能创建 root execution 和 child execution。
- 能保存 `externalThreadId` 与 `checkpointRef`。

### Task 4：实现 RuntimeGateway 与 MockRuntimeGateway

目标：先不依赖 Python 服务，也能打通 Java 侧执行闭环。

接口建议：

```java
public interface RuntimeGateway {
    Flux<ExecutionEvent> run(ExecutionRequest request);
}
```

`MockRuntimeGateway` 行为：

1. 发送 `EXECUTION_STARTED`。
2. 按节点顺序发送 `NODE_STARTED` 和 `NODE_COMPLETED`。
3. 发送 `EXECUTION_COMPLETED`。
4. 每个事件带上 `executionId`、`rootExecutionId`、`nodeId`、`traceId`。
5. metadata 中返回 `externalThreadId=mock-thread-{executionId}`。

验收：

- 单元测试断言事件顺序稳定。
- 单元测试断言 metadata 中存在 `externalThreadId`。

### Task 5：实现 RuntimeExecutionService

目标：提供阶段一最小执行入口，串起定义转换、执行日志、mock sidecar 和事件保存。

建议方法：

```java
public Flux<ExecutionEvent> runWorkflow(Long workflowId, Long userId, Map<String, Object> input)
```

职责：

- 读取 workflow detail。
- 调用 `WorkflowDefinitionAssembler`。
- 创建 root `ExecutionLog`。
- 生成 `ExecutionRequest`。
- 调用 `RuntimeGateway.run()`。
- 对每个事件更新执行日志 `nodeLogs` 或追加事件快照。
- 收到完成事件时标记 execution success。
- 收到错误时标记 execution failed。

验收：

- 测试能从 workflowId 生成 request。
- 测试能接收 mock 事件并最终把 execution 标记为 SUCCESS。
- 测试失败事件会把 execution 标记为 FAILED。

### Task 6：配置 SidecarRuntimeGateway 骨架

目标：为阶段三真实 Python sidecar 留出替换点。

配置：

```yaml
runtime:
  gateway:
    mode: mock
    sidecar-base-url: http://localhost:8090
```

规则：

- `mode=mock` 使用 `MockRuntimeGateway`。
- `mode=sidecar` 使用 `SidecarRuntimeGateway`。
- 阶段一 `SidecarRuntimeGateway` 只保留接口骨架和配置，不要求真实连通。

验收：

- 默认配置不影响现有测试。
- Spring context 能加载 mock gateway。

### Task 7：前端类型预留

目标：避免后续阶段二新增节点时类型分散修改。

修改：

- `frontend/src/types/workflow.ts` 增加 `WorkflowNodeType` 联合类型。
- `NodeData` 增加 `agentId?: number`、`workflowId?: number`、`sourceType?: string`。

验收：

- `npm test -- --run` 通过。
- 现有画布保存/加载类型不破坏。

## 九、风险与控制

| 风险 | 说明 | 控制方式 |
|------|------|----------|
| Java 重复实现图执行 | 会和 LangGraph sidecar 方向冲突 | Java 只做协议、日志、网关，不做复杂调度 |
| 协议过早复杂化 | 一次定义太多字段会拖慢阶段一 | 阶段一只支持 START/END/SKILL/AGENT_REF/WORKFLOW_REF |
| 执行日志膨胀 | 事件流持续写入可能导致 nodeLogs 太大 | 阶段一先快照，后续拆 execution_events 表 |
| 权限穿透 | Workflow 引用无权限 Agent | 阶段二开始加入引用对象权限校验 |
| sidecar 调试困难 | Java/Python 双服务排错复杂 | 所有事件必须携带 traceId/rootExecutionId/nodeId |
| checkpoint 存储割裂 | Java 和 LangGraph 都有状态 | Java 只保存 externalThreadId/checkpointRef，不保存 LangGraph 内部状态 |

## 十、推荐执行顺序

1. 先完成 Task 1-3：协议 DTO、转换器、执行日志扩展。
2. 再完成 Task 4-5：mock gateway 和 RuntimeExecutionService。
3. 然后完成 Task 6：sidecar gateway 配置骨架。
4. 最后完成 Task 7：前端类型预留。
5. 阶段一合并前运行后端完整测试和前端测试。

完成阶段一后，再进入阶段二做画布引用节点。不要跳过阶段一直接做 LangGraph，否则后续 Java 侧日志、权限、事件协议和前端展示都会返工。

## 十一、结论

计划 8 的真实下一步不是“马上接 LangGraph”，而是先把平台升级为可插拔运行时架构：

> Java 侧先形成标准组合协议和 mock sidecar 执行闭环；Python LangGraph 作为后续可替换的真实执行面接入。

这样能最大化复用当前已完成的 Spring Boot、Vue Flow、LLM Gateway、Chat、执行日志和权限体系，同时避免在 Java 中重复实现复杂图运行时。
