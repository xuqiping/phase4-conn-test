## AI需求去重与合并

### 一、为什么传统去重不够

传统需求去重依赖**关键词匹配**（Levenshtein距离、TF-IDF相似度），存在三大盲区：
- **语义等价但用词不同**："搜索结果太慢" vs "查找速度需要优化" → 关键词0重叠，语义100%重复
- **部分重叠**："希望增加筛选条件" vs "筛选功能太少了" → 子集关系，应合并
- **上下文关联**："支付页没有优惠券入口" vs "优惠券不好找" → 不同入口描述同一痛点

LLM的语义理解能力天然解决了前两类问题，但对第三类（推理型关联）仍需额外设计。

### 二、AI去重三阶段流程

```
Stage 1: 向量化粗筛
  - 所有需求 → Embedding向量
  - 余弦相似度 > 0.85 的对 → 候选重复组
  - 复杂度: O(n²) → 用FAISS/Milvus降到O(n·log n)

Stage 2: LLM精细判别
  - 对每组候选重复，用LLM判定：
    - A.完全重复 → 保留最详细的，其余标记为duplicate
    - B.子集关系 → 创建父子关系
    - C.关联不同 → 分别保留，建立link
  - Prompt关键要素：需求原文A + 需求原文B + 产品上下文 + 判定规则

Stage 3: 合并输出
  - 保留需求 + 合并元数据（来源数、首次/最近提及时间、渠道分布）
  - 父子关系维护
  - 生成去重报告（重复率、Top重复主题）
```

### 三、去重精度优化

| 问题 | 解法 |
|---|---|
| 误合并（不同需求被判相同） | 提高LLM判别阈值；加入"差异点"必填字段 |
| 漏合并（相同需求被判不同） | 降低向量相似度阈值到0.75，扩大候选集 |
| 产品版本差异 | 加入版本上下文："v2.0之前反馈的搜索慢可能是老问题" |
| 多语言混合 | 前置翻译归一化或使用多语言Embedding模型 |

### 四、合并后的元数据管理

每条合并需求应保留：
- **原始来源追溯**：所有被合并的需求原文（供回查）
- **渠道分布**：NPS/工单/社交媒体/访谈各占比例
- **时间趋势**：首次提及→最近提及的时间跨度
- **情感聚合**：各来源的情感分布
