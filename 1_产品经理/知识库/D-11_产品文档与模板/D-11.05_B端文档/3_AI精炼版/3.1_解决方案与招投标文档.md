# 解决方案与招投标文档

## 一、解决方案文档（Solution Deck）

解决方案文档是B端PM/售前的**签约利器**——客户看完就知道"你懂我，你能解决"。

### 8段式解决方案文档

| 段落 | 内容 | 检验标准 | 常见坑 |
|---|---|---|---|
| 1. 客户痛点 | 用客户语言描述其业务痛点（不是你的产品痛点） | 客户点头认同 | 自说自话，客户不认 |
| 2. 行业洞察 | 同行业最佳实践+趋势 | 有数据/案例支撑 | 堆概念无实质 |
| 3. 解决方案概述 | 一页纸说清"我们怎么解决" | 客户能向老板复述 | 技术黑话太多 |
| 4. 方案详解 | 分模块详细讲解+架构图+流程图 | 技术和业务都能看懂 | 只画架构不连业务 |
| 5. 实施路径 | 分阶段交付计划+里程碑 | 每阶段有验证指标 | 只画甘特图无交付标准 |
| 6. 成功案例 | 同行业/同场景成功案例 | 客户能代入 | 案例与客户行业不匹配 |
| 7. 服务保障 | SLA/售后/培训/升级 | 承诺具体可量化 | 只写"7×24服务" |
| 8. 投资回报 | TCO分析/ROI计算 | 有计算过程可验证 | 只给结论不给过程 |

### Customer Deck核心叙事逻辑

**SCQA框架**（情境→冲突→问题→答案）：
1. **S(ituation)**：客户当前的业务情境
2. **C(omplication)**：面临的新挑战/变化/压力
3. **Q(uestion)**：怎么破？
4. **A(nswer)**：我们的方案

> ⚠️ **核心原则**：解决方案文档的**前3段决定客户是否继续看后5段**。如果前3段客户不认同"你懂我"，后面再完美也不会看。[来源：训练知识 | 置信度：📚中]

## 二、招投标文档

招投标文档是**合规性优先**的B端特殊文档——先"不废标"，再"能中标"。

### 招投标文档三层结构

| 层级 | 内容 | 合规要求 |
|---|---|---|
| **商务部分** | 公司资质/营业执照/财务报表/案例证明 | 必须与招标文件要求逐项对应 |
| **技术部分** | 方案响应/技术架构/实施计划/团队资质 | 必须响应每个技术评分项 |
| **报价部分** | 分项报价/总报价/折扣说明 | 必须按招标文件格式报价 |

### 常见废标点（Top5）

| 废标原因 | 具体表现 | 防范 |
|---|---|---|
| 1. 资质不达标 | 营业执照/认证/案例数量不满足 | 投标前逐项核对资质要求 |
| 2. 响应不全 | 漏响应某个评分项 | 对照评分表逐项打勾 |
| 3. 格式违规 | 报价格式/签字盖章不合规 | 专人做形式审查 |
| 4. 超范围承诺 | 偏离招标要求的承诺 | 偏离表逐条标注+澄清 |
| 5. 逾期提交 | 未在截止时间前提交 | 提前24小时完成 |

### 技术方案评分逻辑

| 得分维度 | 占比 | 提分策略 |
|---|---|---|
| 方案完整性 | 30% | 逐项响应+案例佐证 |
| 技术先进性 | 25% | 引入AI/云原生等前沿技术点 |
| 实施可行性 | 20% | 详细的实施计划+风险预案 |
| 团队资质 | 15% | PMP/PMP-ACP/行业认证 |
| 售后服务 | 10% | SLA量化承诺+本地化服务 |

## 三、常见误区

| 误区 | 后果 | 正解 |
|---|---|---|
| 方案写成产品手册 | 客户觉得"你在推销不是解决" | 从客户痛点出发而非产品功能出发 |
| 标书照搬上次的 | 格式/资质不匹配→废标 | 每次逐项核对招标文件 |
| 忽略决策人视角 | 只有技术没有ROI | 高管只看2页：痛点+ROI |
| 不做偏离表 | 暗藏偏离→废标风险 | 逐条对比+明确偏离|
