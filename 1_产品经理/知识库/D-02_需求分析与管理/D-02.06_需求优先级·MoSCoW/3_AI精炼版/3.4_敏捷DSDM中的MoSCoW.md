# 3.4 敏捷DSDM中的MoSCoW

## DSDM方法论中的MoSCoW

MoSCoW最早来自DSDM（Dynamic Systems Development Method），是敏捷方法中**时间盒驱动开发**的核心优先级工具。DSDM的核心理念：**固定时间与质量，调整范围**（而非固定范围，调整时间）。

| DSDM原则 | 与MoSCoW的关系 |
|---|---|
| **以业务为导向** | Must=业务底线，不支持则无价值 |
| **按时交付** | 时间盒固定→MoSCoW分桶保证Must一定交付 |
| **持续协作** | MoSCoW分桶需业务方+开发方共同确认 |
| **质量不可妥协** | 即使时间紧迫也不降低Must的质量 |
| **迭代增量** | 当前版本=M+部分S，下版本=剩余S+C |

## Sprint规划中的MoSCoW

### Sprint Backlog填充逻辑

```
1. Sprint产能确认（如：团队Velocity=40故事点）

2. Must排入：
   - 确认所有Must需求的故事点总和
   - Must点数 ≤ 产能的60%（如40×0.6=24点）
   - 超过→与业务方协商降桶

3. Should排入：
   - 按RICE排序的Should依次排入
   - 到产能80%停止（如40×0.8=32点）

4. Could排入：
   - 按RICE排序的Could依次排入
   - 到产能100%停止（如40点）

5. Won't声明：
   - 明确列出本次Sprint不做的需求+原因
```

### Sprint中的MoSCoW动态调整

| 情况 | 调整策略 |
|---|---|
| Must开发遇阻 | 从Should/Could调人，必须保住Must |
| Should提前完成 | 从Could中提升下一个 |
| Must确实完不成 | 紧急与业务方协商：拆分Must或延期Sprint |
| 新增紧急需求 | 除非是Must，否则放入下次Sprint；若是Must，替换一个Should |

## 版本规划中的MoSCoW分层

| 版本 | 包含桶 | 目标 |
|---|---|---|
| **V1.0 MVP** | 仅Must | 最小可用——能用就行 |
| **V1.1** | Must + 高优Should | 核心体验提升 |
| **V1.2** | Must + Should + 部分Could | 完整体验 |
| **V2.0** | 重新评估MoSCoW | 新周期的优先级 |

## MoSCoW vs Scrum Product Backlog

| 维度 | MoSCoW | Scrum PBI优先级 |
|---|---|---|
| 分类粒度 | 4桶 | 1-N的排名 |
| 取舍显式性 | Won't桶显式声明"不做" | 低排名≈不做但不明确 |
| 资源约束 | Must≤60%规则 | 无硬性限制 |
| 适用阶段 | 版本/Sprint规划 | Product Backlog全量管理 |
| 组合使用 | MoSCoW分类+Product Backlog排序 | — |
