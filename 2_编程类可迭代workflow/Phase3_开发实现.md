# Phase 3 · 开发实现（Implement + 沉淀规范）

> 类型：流程步骤 · **Phase 3**
> 版本：v1.9（v1.1 增功能级人工测试方案；v1.2 增功能完成产出功能 README；v1.3 增安全检查验证；v1.4 增功能代码速查表 Feature Map；v1.5 功能速查表增「技术原理大白话注解」；v1.6 建表必须用 Flyway + 速查表增「表用途 / 字段用处 / 表关联」大白话注解；v1.7 把 Feature Map 明确为「粗略功能-代码速查表」，新增「用户操作手册 User-Ops」作为细化到动作的傻瓜式操作文档；v1.8 开发进度改为每一轮对话结束必更新，明确进度内容要求，所有文档硬限 5000 tokens，超限时打桩拆分为「总路由.md + 实际文件」；**v1.9 测试方案与 User-Ops 增「功能联动用例」对齐 Phase 2「功能联动点清单」，chunk 循环增「运维埋点验证」对齐 Phase 2「运维考量清单」**）
> 对应模式：**Plan-Implement-Run 的 Implement 步** · 铁律：**#2 拆chunk、#3 上下文、#6 人在环路、#7 commit存档点、#8 沉淀规范**
> 定位：本 Phase 是你原有流程「进入开发→每步更新进度+沉淀规范」的强化版。

## 目标

按 plan.md 逐 chunk 实现，每个 chunk 走完**「写→测→提交→沉淀」**小循环。每个功能先判定要不要人工测试（需要就先出测试方案），功能做完再产出**功能 README** + **粗略功能-代码速查表 Feature Map** + **细化用户操作手册 User-Ops（用户可见功能）**。commit 当存档点，规范当复利。

## 输入

- Phase 2 的 `workflow_output/docs/plans/<功能名>.plan.md`
- 相关源码文件 + `AGENTS.md` + 对应 spec（喂给 AI 的上下文）

## 动作清单

### A. 功能级预处理（每开始一个新功能时做一次）

1. **判断该功能是否需要人工交互测试**：本功能是否涉及 UI 交互 / 主观体验（视觉、体感）/ 真实第三方调用 / 需人工确认的流程？
   - **需要** → 在 `workflow_output/docs/测试方案/` 下生成 `<功能名>测试方案.md`（骨架见 [项目模板/workflow_output/docs/测试方案/_模板测试方案.md](项目模板/workflow_output/docs/测试方案/_模板测试方案.md)）：前置条件、测试用例（步骤+预期）、**功能联动用例**、边界/异常场景、通过标准。这是该功能的人工测试基准——开发时照它自验，Phase 4 也照它做人工验收。
   - **【v1.9 新增】功能联动用例**：对应 plan.md 的「功能联动点清单」逐条写测试用例——**触发动作 → 联动对象是否按预期变化**，且必须覆盖正向 / 反向 / 半选 / 批量边界（例：父勾选框勾上→子全选；取消父→子全清；子全勾→父自动勾上；子部分勾→父半选）。联动点清单里列了几条，测试用例就至少有几条，不能漏。
   - **不需要** → 跳过。该功能用自动化测试（单元/集成/E2E）覆盖即可，**不产测试方案文档**。

> 判定原则：**能自动化且结果可断言的，不写人工测试方案；凡是「要人点点看 / 看一眼对不对 / 走真实外部依赖」的，必须写。**

### B. chunk 级循环（每个 chunk 重复）

1. **勾选 plan**：在 plan.md 里把当前步骤标为进行中。
2. **上下文打包**：把要改的代码、相关文件、AGENTS.md、对应 spec（以及**本功能的测试方案，若有** + **security_strategy.md**）喂给 AI（铁律 #3）。明确告诉它**不要碰**什么。
3. **实现该 chunk**：一次只做一个功能点 / 函数族。禁止大块单体输出。
4. **【新增】安全检查验证 + 运维埋点验证**：对照 plan.md 的「安全检查清单」，确认本 chunk 涉及的安全项已完成并验证；对照「运维考量清单」，确认本 chunk 该埋的运维能力已埋上（关键路径日志含 traceId、监控指标、配置开关、健康检查、降级路径等）。**运维能力在写码当下就埋，不要留到功能收尾或上线才补——那时已经埋不进去了。**
5. **自动化测试**：写并跑该 chunk 的自动化测试（TDD 优先）。让 AI 跑测试套件，失败就让它 debug。
6. **commit 当存档点**（铁律 #7）：自动化测试通过后立即 `git commit`，消息清晰。这就是你的回滚锚点。
7. **更新开发进度**（**每一轮对话结束都必须做**，不是等某个 chunk 或功能做完才写）：在 `workflow_output/开发进度/<功能名>/` 下新建或追加 `开发进度n.md`，记录本轮做了什么。进度内容分两类填——
   - **文档/理论类**：步骤、产出文件、文件路径、被谁引用、引用位置。
   - **代码类**：实现的功能、对应 plan.md/PRD 编号、涉及文件、关键代码位置、测试结果、commit SHA。
   - 单文件不得超过 **5000 tokens**；接近或超过时，新建 `开发进度<n+1>.md`，或在功能目录下建 `总路由.md` 做索引指向各实际进度文件。
8. **沉淀规范**（你的核心优势动作）：判断本 chunk 是否产出**通用能力/约定**——
   - 是 → 更新 `workflow_output/项目规范约束/AGENTS.md`（或新建 XX约束.md）。例如：建立了鉴权、中英双语、商业授权等，后续模块都基于它。**【v1.9】也包括运维约定**：日志格式与 traceId 规范、监控指标命名、配置开关使用规范、健康检查约定、降级策略——第一次定下，后续模块照抄。
   - 否 → 跳过。
9. **定下一步**：同步写进开发进度总览，循环回步骤 1。

### C. 功能完成收尾（该功能所有 chunk 完成后做一次）

1. **判定受众类型并产出功能 README**：在 `workflow_output/开发进度/<功能名>/README.md` 产出功能 README（骨架见 [项目模板/workflow_output/开发进度/_模板功能README.md](项目模板/workflow_output/开发进度/_模板功能README.md)）。
   - **A 技术类**（用户看不见的：中间件、迁移、内部工具）→ 只写技术说明
   - **B 用户类**（终端用户能感知的：UI、业务功能）→ 写**用户地图**（谁用、什么场景、什么效益）+ 简要技术说明
   - **C 两者** → 用户地图 + 技术说明都写

   > 功能 README 是最终汇编成项目文档的零件：各功能「用户地图」汇成项目文档的「产品价值」章，「技术说明」汇成「技术文档」章。

2. **产出粗略功能-代码速查表 Feature Map**：在 `workflow_output/docs/feature-map/<功能名>.feature-map.md` 产出功能代码速查表（骨架见 [项目模板/workflow_output/docs/feature-map/_模板.feature-map.md](项目模板/workflow_output/docs/feature-map/_模板.feature-map.md)）。这份表是**面向开发者/维护者**的粗略速查：
   - 该功能涉及的所有代码文件位置（前端/后端/数据库/配置/测试等）
   - 关键调用链路
   - 每个文件的作用说明和重点关注点
   - **技术清单与原理注解（大白话版）**：对每个**关键技术 / 关键文件**，写清——
     - **采用技术**：用了什么（技术名要准，如 JWT、Vue3 Composition API、Redis 缓存、WebSocket）
     - **一句话原理**：这技术本质干啥（一句话）
     - **大白话展开**：用日常语言讲清原理，不写代码也能懂
     - **大白话案例**：一个生活化的比喻（游乐场手环、Excel 公式……），让人秒懂
     - **为什么用它**（可选）：选型理由，顺带说清"为啥不用别的"
     - **踩坑批注**：用 `>` 引用块写本功能的坑 / 约束 / 提示（这就是"注解"）
   - **数据库表与 SQL 注解（Flyway）**——**仅涉及建表的功能填**：
     - **建表必须用 Flyway 管理迁移**：脚本放 `src/main/resources/db/migration/V<版本号>__<描述>.sql`，已执行脚本不可改，改结构就加新版本脚本（其他栈替换等价工具：Prisma migrate / Alembic / Liquibase）
     - **.sql 脚本本身要带注释**：表头写表用途、字段行内注释、关联说明（SQL 是数据结构最终真相）
     - **表用途**：大白话一句话（这表存什么，一行代表什么）
     - **每个字段的用处**（大白话）+ 类型 + 约束 / 索引
     - **表与表的关联**（一对多 / 一对一 / 多对多）+ 生活化比喻
     - **建表踩坑批注**：外键/常用查询字段加索引、金额用 DECIMAL、大字段拆副表、状态字段写明取值含义

   > Feature Map 是维护期的救命文档：后续修 bug、加功能、新成员 onboarding，都能按图索骥——**技术原理注解让你"看图就懂为啥这么写"，建表注解让你"看图就懂表结构"，都不用逆向读代码 / 翻 SQL 猜意图**。

3. **【v1.7 新增】产出细化用户操作手册 User-Ops（用户可见功能）**：若该功能属于 **B 用户类** 或 **C 两者**（终端用户能感知），在 `workflow_output/docs/user-ops/<功能名>用户操作手册.md` 产出用户操作手册（骨架见 [项目模板/workflow_output/docs/user-ops/_模板.用户操作手册.md](项目模板/workflow_output/docs/user-ops/_模板.用户操作手册.md)），按「功能 → 操作步骤 → 界面变化 → 预期结果」细化到每个动作：
   - 功能入口在哪（菜单 / 按钮 / 链接 / 快捷键 / 桌面端窗口入口）
   - 每一步用户要点击/输入/选择什么
   - 每步操作后界面会发生什么变化（页面跳转、弹窗、数据刷新、提示消息、窗口切换）
   - 最终完成标志是什么（看到什么、数据变成什么）
   - 常见异常与恢复（如提交失败、网络超时、权限不足、表单校验失败）

   > 功能 README 的「用户地图」回答「谁用、什么场景、有什么价值」；**用户操作手册回答"怎么一步步点出来"**。两者互补：用户地图给决策者/新成员讲价值，用户操作手册给测试人员/最终用户/客服做验收和培训。**Phase 4 会按本手册逐项做傻瓜式操作验证**。

## D. 文档规模与拆分规则（硬规则）

**所有 Phase 3 产出的文档都不得超过 5000 tokens**：开发进度、Feature Map、User-Ops、功能 README、测试方案、AGENTS.md 更新段等。

### 为什么要限 5000 tokens

- AI 上下文有限，单文件过大时会被截断或稀释关键信息。
- 维护期查找信息困难，小文件 + 索引才是可维护的结构。
- 5000 tokens 约等于 3000~4000 汉字（含格式），足够记录一个完整主题。

### 超限时的拆分模式

#### 模式一：同主题顺序拆分（推荐用于开发进度）

```
workflow_output/开发进度/<功能名>/
├── <功能名>开发进度总览.md
├── <功能名>开发进度1.md   ← 第 1~3 轮对话
├── <功能名>开发进度2.md   ← 第 4~6 轮对话
└── <功能名>开发进度3.md   ← 第 7~n 轮对话
```

- 每轮对话写进当前 `开发进度n.md`。
- 当前文件接近 5000 tokens 时，收尾并新建 `开发进度<n+1>.md`。
- `开发进度总览.md` 中记录最新文件编号和主题。

#### 模式二：总路由索引（推荐用于文件数量多、需要按主题检索时）

```
workflow_output/开发进度/<功能名>/
├── 总路由.md                ← 按轮次/主题汇总，指向实际文件
├── <功能名>开发进度总览.md
├── <功能名>开发进度1.md
├── <功能名>开发进度2.md
└── ...
```

- `总路由.md` 本身也不超过 5000 tokens。
- 每条索引包含：轮次、日期、主题、关键结论、链接到实际文件。
- 当索引项过多时，可按主题再拆分二级路由。

#### 模式三：其他文档的拆分

| 文档类型 | 拆分方式 |
|---|---|
| Feature Map | 技术清单过长 → 拆「技术清单.md」+ 原 Feature Map 保留总览并指向它 |
| User-Ops | 子功能过多 → 拆成 `<功能名>.<子功能>.user-ops.md` + 总路由 |
| 功能 README | 用户地图和技术说明都很大 → 拆成 `用户地图.md` + `技术说明.md` |
| 测试方案 | 用例过多 → 按正常/异常/边界拆分子文件 |
| AGENTS.md | 约束过多 → 拆成 `XX约束.md` 并在 AGENTS.md 中索引 |

### 操作习惯

1. **写之前先估算 tokens**：复制当前文件内容到 token 计数器（或让 AI 估算）。
2. **写到 4000 tokens 就预警**：准备收尾、创建下一个文件或路由。
3. **每个文件开头写清楚它是什么**：避免打开后不知道这是总览、路由还是详细记录。
4. **不要等超限了才拆**：提前规划拆分主题，比被迫拆分更清晰。

## 避坑点

- **Never commit code you can't explain**（铁律 #6）。AI 写出看不懂的代码，逼它加注释或重写成更简单的，否则别提交。
- 不要让 AI「一口气实现五步」。失控的征兆：上下文爆炸、重复造轮子、命名打架。**停下来倒退，拆更小。**
- **人工测试方案不要滥用**：纯逻辑、可断言的功能别写，否则文档膨胀。只给「机器测不了、必须人介入」的场景写。
- **功能 README 按受众写**：纯技术功能别硬凑用户地图，面向用户的功能别只写技术说明。
- **Feature Map 要及时更新**：代码改了就更新对应 Feature Map，否则速查表会变误导图。建议每次功能重构/新增相关文件后回查一次。
- **【v1.7】用户操作手册也要随 UI 流程更新**：改了按钮位置、改了操作顺序、加了新步骤，必须同步改 `workflow_output/docs/user-ops/` 里对应手册，否则 Phase 4 验收会按旧流程走，测试和培训也会误导。
- **【v1.5】技术原理注解要"真大白话"**：原理和案例以"不会写代码的人也能懂"为准——别堆术语、别贴大段源码，能用日常比喻（手环、Excel……）讲清就别绕。批注（`>`）只放踩坑/约束/提示，别塞废话，否则注解反而盖住速查表本身。
- **【v1.6】建表必须走 Flyway，别手写 SQL 直接在库里执行**：直接敲 `CREATE TABLE` 建的表，换环境 / 上线时全丢，团队也看不到结构变更历史。一律用 Flyway 版本脚本（`V<n>__描述.sql`），结构演进才有迹可循、可回滚、可复现；**已执行的脚本不能再改，改结构就加新版本号脚本**。
- **【v1.6】建表注解（表 / 字段 / 关联）也用大白话**：表用途一行话、字段写"这字段存啥"、关联配生活比喻（顾客↔小票、学生↔社团）。**.sql 脚本本身也要带注释**——SQL 文件是结构最终真相，注释别只写在 Feature Map 里；二者都写，Feature Map 是速查大白话版，.sql 是权威版。
- 沉淀规范别偷懒——这一步省了，下一个模块就要重新踩坑。它是 Context Engineering 的复利来源。
- **【v1.8】所有文档守好 5000 tokens 上限**：开发进度、Feature Map、User-Ops、功能 README、测试方案都不例外。写到 4000 tokens 就预警，超限不拆等于给未来的自己挖坑——AI 读不下、人也找不到。
