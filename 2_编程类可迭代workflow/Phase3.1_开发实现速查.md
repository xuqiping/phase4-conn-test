# Phase 3.1 · 开发实现速查（恢复开发先看这个）

> 类型：流程步骤 · **Phase 3 的浓缩速查版**
> 对应：[Phase3_开发实现.md](Phase3_开发实现.md) 的 v1.9 规则打桩版
> 用法：每次恢复开发时读这一份即可启动；规则拿不准 / 文档版本号变了 / 遇到新场景时，回看 Phase3 全文以原文为准。
> 铁律：**#2 拆chunk、#3 上下文、#6 人在环路、#7 commit存档点、#8 沉淀规范**

## 一、恢复开发的标准启动动作

> **硬规则：每个功能开工 = 新会话**（上下文工程 Isolate，详见方法论核心「四板斧」）。别在旧会话里连做新功能——旧细节稀释新上下文。新会话只带「进度文件 + 速查 + 规格」启动，不带探索垃圾。

1. 读 `workflow_output/开发进度/<功能名>/开发进度总览.md`（+ 最新 `开发进度n.md`）→ 知道**做到哪、下一步是哪个 chunk、上次卡在哪**。
2. 读本份速查 → 知道**这个 chunk 怎么走、做完要产什么**。
3. 开干。规则有疑问再回 Phase3 全文。

## 二、chunk 级小循环（每个 chunk 重复，9 步）

| # | 动作 | 要点 |
|---|---|---|
| ① | 勾选 plan | 在 plan.md 把当前步骤标进行中 |
| ② | 上下文打包 | 要改的代码 + 相关文件 + AGENTS.md + 对应 spec +（若有）测试方案 + security_strategy.md 喂给 AI；**明确告诉它不要碰什么** |
| ③ | 实现该 chunk | 一次一个功能点/函数族；禁止大块单体输出 |
| ④ | 安全检查验证 + 运维埋点验证 | 对照 plan.md 的「安全检查清单」+「运维考量清单」，本 chunk 涉及项已完成；**运维能力（日志含 traceId / 监控指标 / 配置开关 / 健康检查 / 降级路径）写码当下就埋，别留到收尾** |
| ⑤ | 自动化测试 | TDD 优先；让 AI 跑测试套件，失败让它 debug；**用例名/注释带 AC 编号**（如 `// AC-001`）；**每条 AC 优先转自动测试，转不了的才进人工测试方案**（testing_strategy 的 AC 映射表是闭环依据） |
| ⑥ | commit 当存档点 | 自动化测试通过后**立即** `git commit`，消息清晰**带 FR 号** = 回滚锚点；**commit 前必跑 `scripts/check_all` 最小质量门，全绿才提交** |
| ⑦ | **更新开发进度**（每轮对话结束必做） | `workflow_output/开发进度/<功能名>/开发进度n.md`，记本轮做了什么（见下方「进度内容」）|
| ⑧ | 沉淀规范 | 产出通用能力/约定 → 更新 `workflow_output/项目规范约束/AGENTS.md` 或新建 `XX约束.md`；**「推翻常规做法」的决定 → 在 `docs/adr/` 记一篇 ADR**；否则跳过 |
| ⑨ | 定下一步 | 同步写进开发进度总览，回到步骤 ① |

### 进度内容（⑦要记什么）

- **文档/理论类**：步骤、产出文件、文件路径、被谁引用、引用位置。
- **代码类**：实现的功能、对应 plan.md/PRD 编号、涉及文件、关键代码位置、测试结果、commit SHA。

## 三、功能级预处理（每开始一个新功能做一次）

判定该功能要不要**人工交互测试**：
- 涉及 UI 交互 / 主观体验（视觉体感）/ 真实第三方调用 / 需人工确认的流程 → **需要**：在 `workflow_output/docs/测试方案/` 产 `<功能名>测试方案.md`，**含「功能联动用例」**（对齐 plan.md 的「功能联动点清单」逐条验证：触发动作 → 联动对象是否按预期变化，含正向 / 反向 / 半选 / 批量）。
- 能自动化且结果可断言的 → **不需要**，不产文档。

> 判定原则：**机器测不了、必须人介入的才写人工测试方案；否则只做自动化测试。**

## 四、功能完成收尾（该功能所有 chunk 做完后，产出清单）

| 产出 | 路径 | 何时产 |
|---|---|---|
| 功能 README | `workflow_output/开发进度/<功能名>/README.md` | 必产。按受众：A 纯技术→只写技术说明；B 用户类→用户地图+技术说明；C 两者都写 |
| Feature Map（功能-代码速查表） | `workflow_output/docs/feature-map/<功能名>.feature-map.md` | 必产。含技术原理大白话注解；涉建表加表用途/字段用处/表关联注解（建表用 Flyway） |
| User-Ops（用户操作手册） | `workflow_output/docs/user-ops/<功能名>用户操作手册.md` | 仅 B/C 类产；细化到「功能→步骤→界面变化→预期结果」 |
| 测试方案 | `workflow_output/docs/测试方案/<功能名>测试方案.md` | 仅需人工交互测试的功能产 |
| AGENTS.md 更新 | `workflow_output/项目规范约束/AGENTS.md` | 产出通用能力/约定时织入 |

> **功能交付后再归档（非收尾必做，防进度文件膨胀）**：功能走完 Phase 4/5 交付后，把逐轮 `开发进度1..n.md` 压缩成 `<功能名>开发历程总结.md`（关键决策/踩坑/最终结果），原始文件移入 `archive/<功能名>/`，全局进度总览只留一行摘要。机制详见全局进度总览模板的「归档机制」。Feature Map/User-Ops/README/测试方案**不归档**（长期参考）。

## 五、文档规模硬规则（5000 tokens 上限）

所有 Phase 3 产出文档不得超过 **5000 tokens**（约 3000~4000 汉字）。写到 **4000 tokens 预警**。
**机器校验**：`python scripts/check_docs.py` 自动查超限/失效链接/孤立文档（已并入 `check_all`，commit 前必跑）。

超限拆分三模式：
- **同主题顺序拆分**（开发进度首选）：`开发进度n.md` 满了 → 新建 `开发进度<n+1>.md`，总览记最新编号。
- **总路由索引**（文件多/需按主题检索）：建 `总路由.md`（自身也 ≤5000 tokens）指向各实际文件。
- **其他文档**：Feature Map 拆「技术清单.md」；User-Ops 按 `<功能>.<子功能>.user-ops.md`；README 拆「用户地图.md/技术说明.md」；测试方案按正常/异常/边界拆。

## 六、避坑速记

- **Never commit code you can't explain**（铁律 #6）——看不懂的代码逼 AI 加注释或改简单，否则别提交。
- 别让 AI 一口气实现五步——失控征兆：上下文爆炸、重复造轮子、命名打架，**停下来拆更小**。
- 人工测试方案别滥用——纯逻辑可断言的功能别写，否则文档膨胀。
- 建表必须走 Flyway（`V<n>__描述.sql`），**已执行脚本不可改**，改结构加新版本号；别手写 SQL 直接入库。**新脚本执行后回写 `specs/db_schema.md`**（ER 图 / 数据字典 / 版本清单各补一笔）。
- 大白话注解要真大白话——别堆术语、别贴源码，用日常比喻（手环、Excel）讲清。
- **commit 前必跑 `scripts/check_all`**——一条命令跑完 lint/类型检查/测试，失败日志贴回给 AI 修；绕过质量门（`--no-verify`）= 把错误埋进存档点。
- 代码改了要回查对应 Feature Map，UI 流程改了要同步改 User-Ops。
- **【v1.9】功能联动要三处对齐**：plan 联动点清单 → 测试方案联动用例 → User-Ops 界面变化；尤其测**反向 / 半选**（取消父、子部分勾），只测正向必漏 bug。
- **【v1.9】运维埋点别攒到收尾**：日志 / 监控 / 开关 / 健康检查 / 降级，跟着对应业务代码的 chunk 当下埋、当下 commit，攒到最后补 = 补不进或补错地方。
- **【上下文工程】主会话只做决策和整合，重活开 subagent**：独立调研（读 5+ 文件才下结论）、批量机械修改（跨文件重命名/统一 import）、review、plan 里 `[P] 可并行` 的步骤 → 开 subagent 独立上下文跑，主会话只收结论。判定一句话：**中间过程主会话需要看吗？不需要 → subagent。**
- **【上下文工程】会话变慢 / 变笨 = 上下文太重**：别硬撑，新开会话，把「做到哪、下一步」写进进度文件带过去。
- **【上下文工程】AGENTS.md / CLAUDE.md 本身要克制**：聚焦「每次开工都需要的规则」，目标 ≤400 行；细节拆 `XX约束.md` 只留索引。2026 经验是**聚焦的 400 行上下文文件常优于 4000 行的**——膨胀的规则文件本身就是上下文污染。Phase 5 迭代收尾定期瘦身。
