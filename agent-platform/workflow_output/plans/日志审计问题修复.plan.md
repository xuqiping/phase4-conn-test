### Chunk 4 · 智能对话审计（两阶段：意图 + 带 token 快照的完成行）（#1 对话 + #7 chat）

- **目标**：用户发对话进审计；**模型调用完成**后落第二行，带 model/输入输出 tokens/消耗积分（值取自计费 side-channel，单一计算源不发散）；规避 SSE AOP 坑。
- **动作（伪代码）**：
  - **第一行·submit 意图**：`ChatSessionService.sendMessage(userId, request)`（4 个 controller 端点共同咽喉）用户消息持久化后编程式 `record(fromMdc("chat","send_message","chat_session",sessionId, detail={agentId,targetType,traceId}, SUCCESS))`；**不**带 prompt 原文（隐私+体积）。

- **涉及文件**：`ChatSessionService.java`、`LlmGateway.java`(或 chat stream 出口，P3 定位)、`application.yml`、（依赖 Chunk 7 的 trace_id 关联）。

## 二、技术坑点预判（含性能坑）

1. **【性能·临界】hash 链 advisory lock 串行化写入**：`insertChained` 取 `pg_advisory_xact_lock(810_202_608L)` → **所有审计 INSERT 全局串行**。新增 chat 高频 + 媒体终态后写入压力上升。规避：① 审计异步小池（core1/max2）天然限流，不放大池（放大也串行无用）；② 监控 `droppedCount`（已 WARN 带计数）；③ chat 加 `AUDIT_CHAT_ENABLED` 开关，极端时可关。**不可**为提速绕过 hash 链（破坏完整性）。
2. **【性能】username LIKE 全表扫**：`username LIKE '%x%'` 前导通配不走索引。规避：V94 建 `idx_audit_username(username,created_at)`；前端账号筛选用前缀匹配语义（`like 'x%'`，MyBatis-Plus `like` 默认双侧 `%` → 改 `likeRight`）；admin 工具低频可接受，文档注明。
3. **【正确性·硬约束】严禁 UPDATE audit_logs**：V90 REVOKE UPDATE + V93 hash 链。中文显示**必须**显示层字典，**绝不**回写历史行。回写=断链+DB 拒绝。P3 若发现"老行中文显示不全"→靠字典回落，**不**修数据。
4. **【正确性】worker 无 MDC**：媒体终态/任何 `@Async` 线程内 `MDC.get` 全 null。规避：worker 审计走 `recordTask` 显式传 userId/username/clientIp（从任务行取），**禁**在 worker 调 `fromMdc`（会落 null 身份/IP，等于 #1 #6 没修）。
5. **【正确性】chat SSE 的 AOP 坑**：`@Around` 对返回 `SseEmitter` 的方法在**方法返回时**（即 emitter 创建瞬间）记录，非流完成。语义上"用户发了消息"=submit 时刻，看似可用，但 4 个端点（2 普通 + 2 流）去重麻烦。规避：**不用 AOP**，在 `ChatSessionService.sendMessage` 单咽喉编程式落一次。
6. **【性能·体积】审计表无限增长**：append-only 永不删。chat 审计显著放大行数。规避：见运维考量（分区/归档"后续再说"但落字）；detail 严控体积（prompt 截断 50 字或不存）。
7. **【安全】XFF 无条件信任**：`MdcUserFilter.clientIp` 直接信 XFF 首段（无 trusted-proxy 门控），可伪造 IP。`AuthService.currentClientIp` 才有 `isTrustedProxy` 门控。本计划**不**改此（属安全加固独立项），但记入残留风险：审计 IP 可被伪造，排障时知悉。
8. **【正确性】下载端点 AOP + 文件流**：下载方法返回 `ResponseEntity<Resource>`/流，`@AuditLog` `@Around` 在 proceed 后记录，正常。但若流式写出异常，aspect catch → FAIL 行，原异常上抛 → 客户端收不完整文件。可接受（失败本应留痕）。注意 `buildDetail` 会序列化参数，下载方法参数含 `HttpServletResponse` → 被 skip（已处理，L82）。
9. **【迁移】V94 `ALTER TABLE ADD COLUMN` 无默认**：`client_ip` nullable，旧任务行 NULL，worker 终态对旧任务记 IP=NULL（可接受，新任务起带 IP）。
10. **【正确性·关联键】媒体禁用 traceId 关联**：媒体 worker 是 DB 轮询异步线程，**无 MDC traceId**（实测 worker 代码零 MDC 引用），且与 submit 不同请求不同 traceId。强行用 traceId 关联→断链。**必须用 taskId 作 targetId 显式关联**。chat 才可用 traceId（同请求 submit→completion 共 traceId，且 billing side-channel 同线程）。
11. **【正确性·单一计算源】token/积分禁二次算价**：chat completion 行的 tokens/points **复用 UsageCollector 同一组计算值**（doOnComplete 处传同一对象给 usage+audit），**绝不**在 audit 侧再调 PricingService 重算——否则两份数据与账单总览发散。媒体 pointsConsumed **取 chargeMedia 返回值**（已扣的实际值），不重算。
12. **【正确性·submit targetId】AOP 取不到返回值**：`@AuditLog` 的 `firstLongArg` 只看入参，媒体 submit 入参是 `@RequestBody`（无 Long）→ targetId=null。故媒体 submit **必须**改编程式（service 内 taskId 生成后落），否则 #8 关联失效。chat submit 入参有 sessionId（Long）可作 targetId，AOP 可保留——但本计划 chat 走编程式单咽喉统一。
13. **【性能·关联查询】trace_id 索引**：admin 按审计行 traceId 反查 llm_usage_logs，无索引则全表扫。V95 必建 `idx_usage_trace`。taskId 查询复用既有索引或加 `idx_usage_task`。
14. **【运维·两套审计表容量】**：本需求后 audit_logs + llm_usage_logs 双表都因 chat 加速增长。llm_usage_logs 已是异步攒批写（独立池），audit_logs 走 hash 链串行。两表都要纳入容量预案（运维表「后续再说」分区/归档）。

## 四、功能联动点清单（正向必漏 bug）

1. **模块下拉 × 动作筛选**：选模块后动作输入框仍可任意填（动作按码精确匹配）。边界：模块选「媒体」+动作填 `image_gen_success` → 命中；动作填中文「图片生成」→ **查不出**（码值匹配）。→ 文档+placeholder 注明"动作填英文码"。
2. **账号 × 用户ID 同时填**：AND 语义（两条件都满足）。边界：只填账号→按账号模糊；只填 ID→精确；都填→交集。reset→两清。
3. **时间段 × 翻页**：带时间段筛选翻页，每页查询都带时间段参数（已有，核对不丢）。改条件重查→页码回 1（已有）。
4. **模块下拉 × 中文显示**：下拉显示中文 label、提交 value=码；列表模块列显示 `moduleLabel`（中文）。边界：码值无字典命中→回落原码（不空）。
5. **重置按钮**：清 username/userId/module/action/result/traceId/时间段全部，重查第 1 页。→ 加 username 后必须纳入 reset（防遗漏致"重置后仍带账号筛选"假象）。
6. **worker 终态审计 × 任务归属**：媒体任务终态审计 userId 取任务行 `user_id`（非当前 worker 线程无身份）。边界：系统调用任务 user_id=NULL→审计 userId=NULL（可接受）。
7. **媒体 submit 行 × success 行关联**：两行同 `targetType=media_gen_task` + 同 `targetId=taskId`。边界：① 正常→两行齐全可串；② submit 成功但 worker 还没跑完→只见 submit 行（success 行待终态）；③ submit 成功 worker 失败→success 行 result=FAIL；④ 任务被删/超时无终态→只见 submit 行（文档注明"无终态行=任务未完成或被清理"）。前端「查看同任务」=按 targetId 过滤。
8. **chat submit 行 × completion 行关联**：两行同 traceId + 同 sessionId。边界：① 流正常完成→两行齐全；② 流中途断→只见 submit 行无 completion（或 completion FAIL）；③ 一次请求多模型调用→completion 行只放主应答摘要，完整明细靠 traceId 跳 llm_usage_logs。
9. **审计行 × 账单调用明细（drill-down）**：详情弹窗「查看调用明细」按钮，有 traceId 走 traceId、有 targetId(taskId) 走 taskId 跳账单总览预填筛选。边界：① chat 行→按 traceId 过滤（≥1 条）；② 媒体行→按 taskId 过滤（≥1 条 kind=VIDEO/IMAGE）；③ llm_usage_logs.trace_id NULL 的存量行→按钮禁用/提示"旧数据无关联"；④ 账单页未带 query→正常进，带 query→预填+自动查。

## 七、术语表

- **显示层字典**：DB 存英文码，前端/VO 渲染时翻译成中文。不动 DB 数据。
- **hash 链**：每行审计 HMAC 上一行 hash，串成链，防插/改/删（V93）。
- **advisory lock**：Postgres 事务级建议锁，保证"读末行→插新行"原子，防双链分叉。
- **MDC**：SLF4J 线程本地上下文，存 userId/clientIp，请求线程独有，异步线程需 TaskDecorator 透传。
- **盖戳（stamp）**：submit 时把 clientIp 写进任务行持久化，worker 终态读出来用——解决异步线程无 MDC。
- **咽喉点（chokepoint）**：多个入口共经的单一方法/服务，在此埋一次逻辑即覆盖全部入口。
