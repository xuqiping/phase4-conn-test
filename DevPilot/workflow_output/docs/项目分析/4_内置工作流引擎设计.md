# 4 · 内置工作流引擎设计

> 核心差异化：把 `2_编程类可迭代workflow`（Phase 0~6 + SDD + 人在环路）从「文档流程」变成「产品引擎」。
> 设计原则：**方法论的铁律一条不丢，文档感一丝不露**——零代码用户感知到的是「向导」，引擎底下跑的是完整 SDD。

## 1. 工作流铁律 → 产品机制映射

| 工作流铁律（来源：0_方法论核心/总览） | 产品机制 | 用户感知 |
|---|---|---|
| specs before code | 需求确认卡片流，全部确认才解锁「开工」 | 「先跟 AI 把需求对清楚」 |
| 未经许可不写码 | 「开工」按钮是唯一的代码触发点 | 「我点头它才动」 |
| commit 当存档点 | 存档点时间轴 + 一键回滚 | 「每一步都能反悔」 |
| 人在环路 | 审批卡片：计划批准/安全检查/上线确认 | 「关键事都问我」 |
| 每步沉淀规范 | 引擎自动维护 AGENTS.md/PRD/plan/进度文档 | 不可见（专业模式可查） |
| 文档 5000 tokens 拆分 | 引擎内部分片存储，用户只见结构化视图 | 不可见 |
| 术语行内括注 | 大白话翻译层 + 术语气泡 | 「看不懂的词点一下就懂」 |
| 质量与漂移度量 | 项目驾驶舱健康度指标 | 「这个项目健不健康一眼看到」 |

## 2. 阶段状态机（Phase → 用户旅程）

### 阶段 0「打磨想法」（= Phase 0 商业前置分析）

- **形态**：访谈式对话。引擎按固定提纲追问：解决什么问题 → 做给谁 → 有谁在做（引擎联网查竞品）→ 怎么赚钱 → 做多大范围。
- **产物**：项目分析报告（自动写入 `workflow_output/docs/项目分析/`），用户看到的是一份「这个想法值不值得做」的大白话评估 + 三个建议（值得做/先缩小范围/再想想）。
- **关卡**：用户确认「值得做」→ 选项目规模（见 §3 分级）→ 进需求期。
- **可跳过**：L0 规模（一次性脚本）跳过本阶段。

### 阶段 1「说清楚需求」（= Phase 1 规格沉淀）

- **形态**：引擎基于阶段 0 报告起草 PRD + 架构/数据模型/安全/性能规格（内部），对外呈现**功能卡片流**——每张卡 = 一个 FR：大白话描述 + 验收标准（AC）+ 估复杂度。
- **关卡**：卡片全部「确认」→ 引擎生成完整 specs → 进计划期。卡片可「改一改」（对话修改）可「砍掉」（砍到 MVP 外，进需求池）。
- **主动反问**：需求有歧义时引擎必须追问（FR-B16），不许自行假设——这是「不踩 vibe coding 意图偏差坑」的关键卡点。

### 阶段 2「定施工计划」（= Phase 2 实现计划）

- **形态**：引擎把规格拆成 chunk 计划，呈现为**看板**：每列一个里程碑，每卡一个 chunk（含技术坑点预判的大白话翻译：「这一步可能卡在 XX，备选方案是 YY」）。
- **关卡**：用户点「开工」——这是全产品最重要的仪式感按钮。点之前引擎只准备不写码。

### 阶段 3「建造中」（= Phase 3 开发实现）

- **形态**：chunk → 沙箱任务，中栏为任务卡片流 + 进度叙事流；每个 chunk 完成自动 commit（存档点）+ 自动更新开发进度文档 + 沉淀规范。
- **人在环路点**：用户可随时插话（追加需求→进需求池待评估，不打断当前 chunk）；每个里程碑结束出「里程碑小结」大白话卡片。
- **自动化纪律**（用户不可见）：每个功能开工=新会话/上下文隔离；commit 前跑最小质量门；文档同步。

### 阶段 4「验收」（= Phase 4 运行验证）

- **形态**：测试方案自动转「点一点」验收清单；引擎先做自动化冒烟（截图/接口探测），把「我测过的」和「需要你亲手点的」分开。
- **关卡**：清单全绿 → 「准备上线」解锁；有「有问题」项 → 自动生成修复任务回阶段 3，修完只回归受影响项。
- **双 AI review**（工作流 Phase 4 的 spawn review）：引擎自动跑第二模型对抗式 review，结果摘要用大白话呈现。

### 阶段 5「上线」（= Phase 5 发布迭代）

- **形态**：三步部署向导（选托管方 → 填域名/密钥 → 发布）。安全卡点（FR-B12）在此强制执行。
- **产物**：部署手册自动生成；进「运营中」状态。

### 阶段 6「改需求」（= Phase 6 变更管理，常驻入口）

- **形态**：「我要改需求」按钮 → 对话描述变更 → 引擎出**影响评估大白话报告**（会影响哪几个功能/大约多少工作量/哪些验收要重做）→ 用户确认 → 复用阶段 2~5 流水线走一遍增量。

## 3. 项目规模分级（L0~L3 文档分级的产品化）

建项目时让用户选规模，引擎据此裁剪工作流严格度——这是工作流「文档分级裁剪表」的直接落地：

| 用户选项 | 对应级别 | 裁剪行为 |
|---|---|---|
| 「随便试试 / 一次性脚本」 | L0 | 跳过阶段 0/1，直接对话开写（允许 vibe coding），无存档点强制 |
| 「小工具 / 验证想法」 | L1 | 简版需求卡片（3 张内）+ 简计划 + 存档点，无验收清单强制 |
| 「正式产品（默认）」 | L2 | 全流程，安全卡点强制 |
| 「要给别人用 / 有对接方」 | L3 | 全流程 + 对外 API 文档 + 架构决策记录 + 多环境配置 |

选小了引擎会在复杂度超限时建议升级；选大了允许降级（已产文档不删）。

## 4. 引擎架构（内部实现视角）

```
用户操作层（卡片/按钮/对话）  ← 桌面客户端主窗口
   ↓
阶段状态机（Phase State Machine）—— 记录当前阶段、关卡通过状态，本地运行
   ↓
产物生成器（Artifact Generators）—— PRD/plan/AGENTS.md/进度/验收清单 的模板化生成+增量更新
   ↓
任务编排器（Task Orchestrator）—— chunk → 本地任务 → subagent 分派（实现/review/文档沉淀）
   ↓
本地执行层（对照 Codex CLI：系统级沙箱 + 工具集 + MCP 客户端）
```

> **本地化原则（2026-08-13 定调）**：状态机、产物、编排全部跑在桌面客户端本地（项目产物落在用户项目目录的 `workflow_output/`，与手工版工作流同构）；云端只有账号/Token 计费/模型转发三件事。用户断网时仅模型调用受阻，工作流数据永不丢失。

关键设计：
- **状态机即真相源**：所有阶段推进、关卡、回退由状态机裁决（本地代码层），UI 只渲染状态——防止长对话中「AI 忘了流程」。
- **产物双写**：所有规格文档同时存 ①机器可读版（AGENTS.md/PRD.md，喂给执行 agent）②用户可读版（大白话卡片，喂给 UI）。
- **上下文工程四板斧内置**：每个 chunk 开工新会话（Isolate）、规格摘要注入（Select/Compress）、产物落盘（Write）——用户工作流的方法论直接编码进编排器。
- **工作流即技能**：引擎的工作流定义存为可配置 YAML（跟随 `2_编程类可迭代workflow` 版本号），且整段流程可被 Skills 生成器封装——「电商 MVP 工作流」「小程序工作流」等行业变体可作为技能包分发，与工作流引擎共用状态机。

## 5. 不可绕过的卡点（安全与质量底线）

| 卡点 | 触发 | 可否跳过 |
|---|---|---|
| 需求确认 | 阶段 1→2 | L1+ 不可 |
| 计划批准（开工按钮） | 阶段 2→3 | L1+ 不可 |
| 安全清单扫描 | 阶段 4→5 | L2+ 不可，Free 档统一按 L2 执行 |
| 上线确认 | 阶段 5 | 不可 |
| 变更影响确认 | 阶段 6 | 不可 |

## 6. 多轮开发、进度查看与断点续跑（用户高频追问，单独成章）

零代码用户的真实使用方式是「今天做一点、明天做一点、想到新需求再加」——多轮迭代与跨天续跑是**主场景**而非边缘场景。

### 6.1 进度从哪来（继承工作流三条纪律的产品化）

| 工作流纪律 | 引擎机制 | 用户看到 |
|---|---|---|
| 每一轮对话结束必更新开发进度 | 每个 chunk/对话结束，引擎自动把「做了什么/下一步/遗留问题」写入 `workflow_output/开发进度/` | 驾驶舱轮次时间线实时更新 |
| 质量与漂移度量每轮手填 | 引擎自动统计：缺陷数（规格内/外）、文档同步待办、spec 覆盖率 | 驾驶舱健康度指标 |
| 进度文件归档（功能交付后压缩归档） | 一轮迭代结束后，逐轮进度自动压缩为历程总结归档 | 轮次历史可查但不刷屏 |

### 6.2 多轮开发的形态

- **小改/加功能**：在驾驶舱点「继续下一轮」→ 走增量流水线（阶段 1 简版需求卡 → 计划 → 建造 → 验收），每轮是一个新里程碑批次，存档点接续累积。
- **动已有功能**：走阶段 6 变更向导（影响评估大白话 → 确认 → 增量流水线）。
- **轮次即版本**：第 N 轮 = 项目的一个版本快照，可整体回滚到任意一轮结束时的状态。

### 6.3 断点续跑为什么可靠（架构级答案）

传统聊天式 AI 编程「关掉窗口就断片」，因为上下文活在对话里。DevPilot 的上下文活在**三处落盘数据**里：

1. **状态机**（本地 SQLite）：项目当前阶段、关卡状态、轮次、chunk 位置——打开客户端即恢复 UI 到离开时的样子；
2. **进度文档**（workflow_output/）：每轮沉淀的「做了什么/下一步/坑点」——AI 续跑时凭它+规格摘要重建工作记忆，无需翻历史对话（这正是工作流「每个功能开工=新会话」纪律的意义：上下文隔离本来就假设 AI 不靠记忆干活）；
3. **Git 存档点**：代码本身的状态真相源。

所以：关电脑、隔天、甚至把项目目录拷到另一台装了 DevPilot 的电脑，都能无损续跑。**「进度文档既是给人看的仪表盘，也是给 AI 的接力棒」**——一份数据，两种读者。

## 7. 与 Codex 的本质差异（一句话总结）

Codex 的工作流在**用户脑子里**（用户自己决定怎么拆任务、什么时候审、怎么验）；DevPilot 的工作流在**产品里**——这是「工具」与「合伙人」的分界线，也是对非程序员市场的准入证。
