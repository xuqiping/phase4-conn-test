# P06_验收与安全卡点 · 测试方案

> 范围：FR-033/040/052 中需要人工确认、真实 UI 交互、真实第三方（Playwright/浏览器）或需人工判断的用例。
> 自动化可断言的用例由单元/集成测试覆盖；本方案聚焦**功能联动、主观体验、危险操作、真实第三方**。

## 环境

- 桌面端（Tauri dev）+ 本地 mock 网关 + 一个已走完 P05（建造完成）的 Node 脚本项目。
- 项目规模分别准备 L1（安全不拦截）与 L2（安全强制卡点）各一个。
- 测试前确保项目 `workflow_output/docs/测试方案/` 下至少有一份测试方案 markdown（可借用 P05 测试方案或手写 3 条 TC）。

## 用例

### TC-01 验收清单自动生成（正）

- **触发**：项目进入「accept」阶段后打开 Accept 视图。
- **预期**：
  1. 系统自动读取 `workflow_output/docs/测试方案/*.md`，按 TC 标题拆分为清单项。
  2. 每条清单显示标题、操作步骤、预期结果、method（自动/人工）。
  3. 初始状态均为 pending。
- **边界**：若目录下无测试方案，显示「未找到测试方案，请补充」；不崩溃。

### TC-02 自动/人工项分流（正）

- **触发**：清单中存在「自动化」字样或 Playwright/测试命令描述的项，以及纯人工描述项。
- **预期**：
  1. 含自动化字样的项 method = auto，显示「运行自动冒烟」按钮。
  2. 纯描述项 method = manual，显示复选框/通过/不通过按钮。
- **边界**：无法判定时默认 manual，不误标为 auto。

### TC-03 自动冒烟执行与截图留证（正 / 真实第三方）

- **触发**：点击 auto 项旁的「运行自动冒烟」。
- **预期**：
  1. 若本机 Node + Playwright 可用，启动 Chromium 执行对应脚本。
  2. 执行通过后该项变为 pass，evidence_path 指向截图文件。
  3. 截图能在 Accept 视图点击查看。
- **边界**：Playwright 不可用时该项保持 pending，提示「请先安装 Node 与 Playwright」；不崩溃。

### TC-04 元素圈选生成修复任务（正 / 人工）

- **触发**：在预览窗格点击某元素，点「有问题」，输入「登录按钮颜色太浅」。
- **预期**：
  1. 弹出对话框确认后，Build 视图出现一条 source='fix' 的 pending task。
  2. 该 task 的 instructions 包含元素 selector 与问题描述。
  3. Accept 视图对应验收项显示「已关联修复任务 #n」。
- **边界**：取消圈选不生成任务；同一验收项只能关联一个未完成的 fix_task。

### TC-05 L2 安全扫描拦截进入验收（反）

- **触发**：L2 项目建造完成后，点击 Build 视图「进入验收」。
- **环境**：项目源码中故意写入硬编码密钥（如 `const API_KEY = "sk-123456"`）。
- **预期**：
  1. 系统执行安全扫描并发现高危 finding。
  2. 状态机停留在 build，弹出大白话修复清单。
  3. Accept 视图不可用（或显示扫描未通过）。
- **边界**：修复并重新扫描通过后，可再次点击「进入验收」成功进入。

### TC-06 L1 安全扫描警告但不拦截（边界）

- **触发**：L1 项目同样写入硬编码密钥，点击「进入验收」。
- **预期**：
  1. 系统执行扫描并发现 finding，显示警告。
  2. 但仍允许进入验收阶段（L1 不强制拦截）。
- **边界**：修复建议仍可查看。

### TC-07 全部验收项通过才能发布（正 / 联动）

- **触发**：Accept 视图中所有验收项标记为 pass/na。
- **预期**：
  1. 底部「发布」按钮从禁用变为可用。
  2. 点击后调用 `request_release`，状态机推进到 deploy。
- **边界**：任一 item 为 fail 或 pending → 按钮禁用；点击提示「还有未通过/未验收项」。

### TC-08 修复任务完成后验收项重置（联动 / 反向）

- **触发**：对某 fail 项生成修复任务，在 Build 视图执行完成该 fix_task。
- **预期**：
  1. 修复任务完成后，Accept 视图对应验收项自动从 fail 重置为 pending。
  2. 用户需重新确认/运行冒烟后该项才能变 pass。
- **边界**：修复任务失败则验收项保持 fail。

### TC-09 重新生成清单保留历史 run（批量 / 反向）

- **触发**：用户修改 `workflow_output/docs/测试方案/*.md` 后，在 Accept 视图点击「重新生成清单」。
- **预期**：
  1. 旧清单被清空，按新 Markdown 重建。
  2. `acceptance_runs` 历史记录保留，可查看旧结果。
- **边界**：未做任何修改时点「重新生成」应幂等（无重复 run 记录）。

### TC-10 预览窗格设备尺寸与刷新（人工）

- **触发**：Accept 视图右侧预览本地 dev server；切换 mobile / tablet / desktop；点击刷新。
- **预期**：
  1. 预览容器尺寸按设备切换，页面重排。
  2. 刷新后重新加载当前 URL，保持当前尺寸。
- **边界**：dev server 未启动时显示友好提示而非空白/报错。

### TC-11 发布被阻断后补测再发布（正）

- **触发**：某 auto 项冒烟失败导致发布按钮禁用；修复问题后重新运行冒烟并通过。
- **预期**：
  1. 重新通过后该项变 pass。
  2. 发布按钮自动启用。
  3. 点击发布后状态机进入 deploy。
- **边界**：修复期间不自动重置其他已通过项。

## 缺陷定级

| 级别 | 标准 |
|---|---|
| P0 | 安全卡点被绕过、发布按钮状态与 Rust 校验不一致、圈选生成任务导致数据丢失、Playwright 不可用造成崩溃 |
| P1 | 清单解析漏项、自动/人工分类错误、截图未保存、设备尺寸切换失效 |
| P2 | UI 文案/样式、历史 run 显示顺序 |

## 通过标准

- 全部 P0/P1 用例通过。
- `scripts/check_all.sh` 全绿，`check_docs.py` 无 FAIL。
- 真实 LLM/Playwright 端到端冒烟：若目标环境不具备 Node/Playwright，至少完成 TC-01/02/04/05/06/07/10，TC-03/11 记为「环境受限待补跑」。
