## 一句话定位

用 **Spec → Plan → Implement → Run** 的现代循环驱动一个软件项目——前置商业分析决定「值不值得做」，规格先行决定「做什么」，小步快跑+人在环路决定「做得稳」，每一步沉淀下来的规范成为下一个模块的地基。

## 方法论锚点（先读这个再往下）

本工作流不是凭空设计，是三条主线收敛的结果，详见 **[0_方法论核心.md](0_方法论核心.md)**：

| 演进主线 | 一句话 | 本流程吸收了什么 |
|---|---|---|
| **Vibe Coding**（Karpathy 原版） | 凭直觉、AI 写、不细管 | 保留了「快速迭代」的节奏感，但只用在原型/一次性脚本 |
| **Context Engineering**（新范式） | 把丰富上下文「提前铺好」喂给 AI | 每步沉淀规范 = 持续织入上下文；项目级 AGENTS.md、file_structure.md |
| **Spec-Driven Development (SDD)** | **specs before code**，规格跨会话/跨 agent 保留上下文 | Phase 1 规格沉淀、Phase 2 实现计划，全程文档驱动 |

> 关键洞察：你原有的「商业前置分析」和「每步沉淀规范」两段，恰恰是 SDD 都没有、而现代最佳实践在补的东西——这是你的优势层，本流程把它放在 C 位。

## 主链（按顺序执行）

```
Phase 0           →   Phase 1         →   Phase 2        →   Phase 3        →   Phase 4       →   Phase 5
商业前置分析          规格沉淀            实现计划           开发实现           运行验证          发布迭代
(值不值得做)         (spec.md / PRD)   (plan.md 拆chunk) (Implement+沉淀)  (Run + review)   (MVP→反馈→迭代)
                                                                                                    ↓ 有存量代码后，改 / 增 / 删已有功能
                                                                       Phase 6 变更管理（复用 Phase2~5 + 影响评估/回归/文档同步/废弃）
```

> **specs before code** 从 Phase 1 贯穿全程；**未经许可不写码** 在 Phase 2 锁死；**commit 当存档点** 在 Phase 3 落地；**需人工测试的功能先出测试方案**、**每一轮对话结束更新开发进度**、**功能完成产功能 README + 粗略 Feature Map（含技术原理注解 + 建表 Flyway 注解）+ 细化用户操作手册 User-Ops（B/C 类功能）** 在 Phase 3 落地；**所有文档守 5000 tokens 上限，超限时打桩拆分为总路由 + 实际文件** 在 Phase 3 落地；**专业术语行内括注+底部术语表** 在 Phase 1/2 落地；**快速启动速查表** 在 Phase 4 落地；**用户操作手册全量验证 + 桌面端自动化测试** 在 Phase 4 落地；**部署手册** 在 Phase 5 落地；**改 / 增 / 删已有功能走 Phase 6 变更管理**（影响评估 → 回归 → 文档同步 → 废弃）。
> 每步产物是下一步输入：Phase 0 出项目分析报告 → Phase 1 出 specs/(含术语表) → Phase 2 出 plans/(含术语表) → Phase 3 出代码+**每一轮对话的开发进度**+规范+测试方案(按需)+功能README+**粗略 Feature Map(含技术注解+建表注解)**+**细化 User-Ops(B/C类)** → Phase 4 出验证/review/性能评测+**用户操作手册全量验证记录**+**桌面端测试记录**+快速启动速查表 → Phase 5 出部署手册+迭代记录 →（改 / 删已有功能）**Phase 6 出影响评估 + 变更记录 + 同步文档**。

## 文件命名约定

- `0_` 前缀 = 方法/元层（总览、方法论、项目模板）——可独立调用、跨步骤复用。
- `PhaseN_` 前缀 = 主链执行步骤，按 0→5 顺序走。
- `1_实例产物/` = 实跑产出的真实项目，不参与流程定义。
- 项目内部采用 **SDD 标准英文命名**（PRD.md / spec / plan.md / AGENTS.md / file_structure.md / .github/prompts/），与 Claude Code / Kiro / GitHub Spec Kit 等全球 AI 编程生态对齐，AI agent 能直接识别。

## 文档分级裁剪表（先定级别，再决定产哪些文档）

> 全套 20+ 文档产物不是每个项目都要背。**开工前先定项目级别**，级别决定必产清单；级别可升降，升级时补产物、降级不删已产文档。
> 底线不变（方法论核心）：**再小也要 specs before code；再赶也要 commit 当存档点；再信任也要 review。**

| 级别 | 场景 | 必产 | 可省 |
|---|---|---|---|
| **L0 一次性脚本** | 跑完就扔的工具/demos | 无（允许 vibe coding） | 全部文档 |
| **L1 小工具 / MVP 首版** | 短期验证、内部小工具 | PRD 简版（含验收标准）+ plan.md + 开发进度 + commit 纪律 + 涉及存储时 db_schema.md | User-Ops、Feature Map 技术原理注解、独立的 security_strategy / performance_goals（并入 PRD 非功能需求）、部署手册、测试方案文档 |
| **L2 正式产品** | 长期维护的产品（本流程主战场） | **全链**：Phase 0→5 全部必产文档 | —— |
| **L3 对外 / 有依赖方** | 有第三方接入、合规要求 | 全链 + 对外 API 文档 + ADR（架构决策记录）+ 监控告警说明 + 多环境配置说明 + 安全响应约定 | —— |

> 判定拿不准就往上升一级——文档少了维护期补不回来，多了只是多写几页。
