## 一、三层演进：Vibe Coding → Context Engineering → SDD

AI 编程在 2025→2026 走过三个阶段，理解这条线，就理解了本工作流每个设计选择的来源。

### 1. Vibe Coding（Karpathy 原版，2025 初）
- **核心**：凭直觉描述需求，AI 写代码，人不细管细节，能跑就行。
- **适用**：一次性脚本、hackathon、demo、扔掉也不心疼的原型。
- **致命伤**：**~3 个月撞墙**。项目一大，AI 上下文丢失、重复造轮子、架构混乱，变成「像 10 个互不说话的开发者各写各的」。
- **本流程态度**：保留它的「快速迭代」节奏感，但只允许用在 Phase 5 的探索性原型，**绝不用于正式项目的主链**。

### 2. Context Engineering（新范式，2025 中→末）
- **核心**：LLM 的输出质量上限 = 你喂给它的上下文质量。把项目信息「提前铺好」（mise en place，厨房的「各就各位」），AI 才不瞎猜。
- **关键产物**：
  - 项目级 AI 指令文件：`CLAUDE.md` / `AGENTS.md`（规则、风格、禁忌）
  - `file_structure.md`（告诉 AI 每个文件/目录干嘛）
  - 可复用 prompt 模板（plan/implement/run/review）
  - Claude Skills（把脆弱的重复提示固化为可复用能力）
- **本流程态度**：你的「**每步沉淀规范**」天然就是 Context Engineering——每完成一步，把通用能力织回 `workflow_output/项目规范约束/AGENTS.md`。这是你的原生优势。

### 3. Spec-Driven Development / SDD（最系统，2025 末→2026）
- **核心**：**specs before code**。编码前先写规格，规格跨会话、跨 agent 保留上下文，避免「每次重开对话都要从头解释项目」。
- **代表工具**：Kiro (AWS)、GitHub Spec Kit、OpenSpec、Tessl。
- **关键产物**：`spec.md` / `PRD.md` → `plan.md` → 代码。规格是「唯一真相源」。
- **本流程态度**：Phase 1（规格沉淀）+ Phase 2（实现计划）就是 SDD 的落地。

> **一句话总结这条线**：Vibe Coding 是「写」，Context Engineering 是「喂」，SDD 是「先写规格再喂」。本工作流 = SDD 的骨架 + Context Engineering 的规范沉淀 + 你独有的商业前置层。

## 二、9 条铁律（执行时的硬约束）

提炼自 Addy Osmani 2026 工作流，每条都对应本流程的具体动作。

### 铁律 1：规格先行（specs before code）
- 不要拿模糊愿望直接让 AI 写码。先和 AI **brainstorm 详细规格**（让它反问直到挖清需求和边界），编成 `spec.md`（需求 + 架构 + 数据模型 + 测试策略）。
- 再用推理模型基于 spec 生成项目计划，**迭代到连贯完整**才动手。
- 这叫 **「15 分钟瀑布」**（waterfall in 15 minutes）——快速但结构化的规划，让后面的编码顺畅十倍。
- **落地**：Phase 1。

### 铁律 2：拆成小迭代块（chunk）
- 永远不要让 AI 一次性产出大块单体代码。一个函数、一个 bug、一个功能地来。
- 大块输出 = 上下文爆炸 + 不可读 + 重复造轮子。一旦失控，**停下来倒退，把问题拆小**。
- 配合 TDD：每个 chunk 先有测试。
- **落地**：Phase 2 拆 plan、Phase 3 逐 chunk 实现。

### 铁律 3：提供充分上下文（context packing）
- 喂给 AI 所有它需要的：要改的代码、技术约束、已知坑、参考实现、官方文档。
- 怀疑它不知道时，主动贴进来（gitingest / repo2txt / Context7 / 手动复制）。
- 明确告诉它**不要关注什么**（省 token）。
- **落地**：Phase 3 每次开 chunk 前，把相关文件 + `AGENTS.md` + 对应 spec 喂进去。

### 铁律 4：选对模型，必要时换（model musical chairs）
- 不同模型有不同「性格」。一个卡住或平庸，**直接换一个**，甚至并行两个交叉验证。
- 用你能用的最新、最强模型——质量差异显著，值得付费。
- **落地**：Phase 1/2 规划用推理强模型；Phase 3 实现可换更快的；Phase 4 review 用「另一个模型」交叉审。

### 铁律 5：贯穿 SDLC，不止写码
- AI 不只用来写代码：Claude Code / Codex CLI / Gemini CLI 做命令行 agent；Jules / Copilot Agent 做异步 agent（克隆仓库到云 VM，后台跑完开 PR）；Conductor 多 agent 并行。
- 但**监督使用**：随时准备介入，不要让 agent 无人值守跑完整功能。
- **落地**：Phase 3/4 可用 agent 执行，Phase 5 可用异步 agent 后台跑。

### 铁律 6：人在环路，验证/测试/审查一切（never commit code you can't explain）
- LLM 「过度自信且爱犯错」，带着完全的信心写出 bug 和胡话，**不会主动告诉你错了**。
- 把每段 AI 代码当代**初级开发者的提交**：读、跑、测。
- **额外招数**：spawn 第二个 AI（或另一个模型）review 第一个 AI 的代码。AI 写的代码需要**比人写的更严格的审查**——它常「表面正确，暗藏缺陷」。
- **落地**：Phase 4。

### 铁律 7：频繁提交，版本控制当安全网
- 把 **commit 当游戏存档点**。每完成一个小任务、每次成功编辑，立即 commit。
- AI 下一步如果搞砸，你随时回滚到上个存档，不丢几小时工作。
- 小 commit + 好消息 = 天然的开发日志，方便 review 和 git bisect 定位 bug。
- 用 **worktree / 分支隔离 AI 实验**：大胆重构，失败就扔掉那个 worktree，主线无损。
- **落地**：Phase 3。

### 铁律 8：用规则和示例定制 AI 行为
- 不要接受 AI 的默认风格。用 `AGENTS.md` / `CLAUDE.md` 写明：项目代码风格、lint 规则、禁忌函数、偏好范式。
- 提供**内联示例**：「这是我们实现 X 的方式，Y 照着来」。LLM 擅长模仿，给一两个样本它就顺着写。
- 加「反幻觉条款」：不确定就问，不要编；修 bug 时在注释里简述理由。
- **落地**：Phase 0 尾建 `AGENTS.md`，Phase 3 持续更新。

### 铁律 9：测试和自动化是力量倍增器
- CI/CD、lint、类型检查、code review bot——AI 在「能自动抓错」的环境里才飞得起来。
- agent 可以被设定为「所有测试通过才算完成」。把 lint 错误、测试失败日志贴回给 AI，它会拼命修。
- 终极形态：**AI-on-AI review**（AIs 审 AIs），能抓出单个模型漏掉的错。
- **落地**：Phase 3 测试、Phase 4 验证、Phase 5 发布后接 CI。

## 三、Plan-Implement-Run 三步模式

这是本工作流 Phase 2/3/4 的直接骨架。核心思想：**强制 AI 先生成计划、经人确认，再实现，再运行验证**——而不是单次 prompt 一把梭。

### 前置：把项目信息写成 markdown 放 `workflow_output/docs/`
把 AI 当「需要清晰指引的新员工」，用 markdown 文档交代：应用概览、技术栈、规格、数据库 schema、文件目录结构、编码规范。这些文档就是它的「入职手册」。

### Step 1 · Plan（→ Phase 2）
- 让 AI **深度思考**，生成实现计划 `workflow_output/docs/plans/xxx.plan.md`。
- 计划只含伪代码，不含真代码；每步写明目标、动作、涉及文件（≤20个）、依赖、验证步骤。
- **与人迭代直到满意**。
- **铁律：未经许可，不开始实现。**

### Step 2 · Implement（→ Phase 3）
- 逐步执行计划，**每完成一步在 plan.md 里勾选 done** 再进下一步。
- 实现并跑单元测试。
- 计划只是建议，不合理可偏离，但要和人同步。

### Step 3 · Run（→ Phase 4）
- 让 AI 运行应用（web 用 Playwright MCP 导航、点击、截图；基础设施用 terraform plan/apply）。
- 发现问题就修，形成「写码→运行→修」的紧反馈环。

## 四、上下文工程四板斧（防上下文膨胀）

铁律 #3 讲「喂什么」，这节讲「怎么防喂撑」。长会话里上下文稀释、旧信息干扰是实跑真实痛点——LLM 上下文窗口再大，**信噪比下降 = 输出质量下降**。Anthropic《Effective context engineering for AI agents》把上下文工程拆成四板斧，本流程对应落地：

| 板斧 | 一句话 | 本流程落地 |
|---|---|---|
| **Write（写出去）** | 大块中间产物不留在对话里，写到文件 | 进度 / 规格 / Feature Map 全落 `workflow_output/` 文件；对话只引用路径，不贴全文 |
| **Select（只取相关）** | 开 chunk 前只喂本 chunk 相关上下文 | Phase 3.1 步骤②「上下文打包」：只喂要改的代码 + 相关文件 + 对应 spec，并明确告诉 AI「不要碰什么」 |
| **Compress（压缩摘要）** | 长历史压成结论 | 进度总览 = 各轮 `开发进度n.md` 的压缩视图；功能完成产 Feature Map / README 作为「压缩后的全貌」；功能完结归档（见条目 12） |
| **Isolate（隔离窗口）** | 重活扔进 subagent 独立上下文，主会话只收结论 | 见下方「拆 subagent 判定线」 |

### 拆 subagent 的判定线（Isolate 落地）

主会话上下文是稀缺资源，**只用来做决策和整合**。出现以下信号 → 开 subagent（独立上下文窗口），主会话只留结论：

- **独立调研**：要读 5+ 个文件才能下结论的探查（如「这个功能现在实现到哪了」「某依赖到底怎么用」）→ subagent 读完全量，只回结论。
- **批量机械修改**：跨多文件的同构改动（重命名、批量加注释、统一 import 风格）→ subagent 跑完只回 diff 摘要。
- **review**：Phase 4 spawn 第二个 AI（铁律 #6）天然就是 Isolate——审查在独立窗口进行，结论回流主会话。
- **并行子任务**：plan 里标 `[P] 可并行` 的步骤（见 Phase 2 依赖与并行化地图），可各开一个 worktree subagent 同时跑，互不污染主会话。

> 判定原则一句话：**这件事的中间过程，主会话需要看吗？** 不需要 → subagent。需要（如关键决策、你全程盯的实现）→ 留主会话。

### 长会话纪律（防稀释）

- **每个功能开工 = 新会话**：别在一个会话里连做多个功能，旧功能的细节会稀释新功能的上下文。新会话启动读：Phase 3.1 速查 + 进度总览 + 最新 `开发进度n.md`（Phase 3.1 启动动作已固化，按它走）。
- **一个会话尽量别跨 Phase**：Phase 1 规格会话做完，进 Phase 2 就开新会话，带规格文件过去，不带规划期的探索垃圾。
- **会话变慢 / 变笨 = 上下文太重的信号**：果断新开会话，把「当前做到哪、下一步」写进进度文件带过去，而不是在臃肿会话里硬撑。

## 五、一个人公司适配（哪些可以简化）

上述是「最强大」的全套。一个人用，按项目体量裁剪（与 [0_工作流总览.md](0_工作流总览.md) 的「文档分级裁剪表 L0~L3」一一对应）：

| 场景 | 级别 | 用到哪些 |
|---|---|---|
| **一次性脚本 / 快速试验** | L0 | 跳过 Phase 0，直接 Phase 1 口述规格 → Phase 3 写 → 跑。允许 vibe coding。 |
| **小工具 / MVP 首版** | L1 | PRD 简版（含验收标准）+ plan + 进度 + commit 纪律；其余文档可省。 |
| **正式产品（要长期维护）** | L2 | 全链 Phase 0→5 都走，不要偷工。这是本工作流的主战场。 |
| **对外 / 有依赖方** | L3 | 全链 + API 文档 + ADR + 监控告警 + 安全约定。 |
| **大功能模块迭代** | —— | 从 Phase 2 开始（规格已存在），走 Phase 2→3→4→5。 |
| **可省** | —— | Phase 5 的异步 agent（Jules/Copilot Agent）、Conductor 多 agent 并行——团队大了再上，一个人监控多 agent 心智负担太重，主用一个 + 一个 review agent 即可。 |

> 核心原则不变：**再小也要 specs before code；再赶也要 commit 当存档点；再信任也要 review。** 这三条是底线，其余可裁。

## 六、工具服务于流程（与 2026 SDD 工具的关系）

2026 年主流 SDD 工具（GitHub Spec Kit / OpenSpec / AWS Kiro）把「spec→plan→tasks→implement」做成了带命令、带校验的脚手架。本流程的态度（详见 [需改进的地方/2. SDD工具化评估.md](需改进的地方/2. SDD工具化评估.md)）：

1. **优势层不可让渡**：本流程的**商业前置分析（Phase 0）、运维考量清单、功能联动点清单、大白话术语注解**——这四样是现成工具都没有、而本流程的核心差异化。任何工具化方案都保留这四层，并作为「宪法/steering」注入工具上下文。
2. **概念吸收 > 整体迁移**：好概念逐条吸收进现有 markdown 约定（delta→条目 20、EARS→条目 3、hooks→条目 8、constitution→AGENTS.md 项目宪法），保持**工具无关**——换 agent（Claude Code / Codex / Gemini）不换流程。
3. **校验机器化、判断人化**：确定性校验（token / 链接 / 追溯编号 / 漂移计数）交给 `check_all` + hooks；商业与体验判断留在人在环路。
4. **流程自身也迭代**：每次实跑真实项目后，把「哪个工具新做法值得吸收」沉淀回 `1. 问题与需改进点.md`。

> 一句话：**工具服务于流程，不是替代流程**。本流程是骨架，工具是手脚——手脚可以换，骨架（Phase 0 的商业判断 + specs before code + 人在环路）不动。
