# 3.1 5Why与根因分析方法

## 定义

5Why分析法（Five Whys Analysis）是通过连续追问"为什么"来穿透表层现象、直达根本原因的需求分析方法。由丰田生产系统创始人大野耐一提出，最初用于制造业的根因追溯，后成为PM需求分析的标配工具。[来源:Toyota Production System | 🔍高 | 1950s]

> 核心判断：5Why不是"问5次为什么"，而是"问到你发现可以采取行动的根因为止"。可能3次就到，也可能需要7次。[来源:📚训练知识]

## 5Why全流程

### 标准流程

```
Step 1: 描述表层现象（用户说了什么/做了什么）
Step 2: 第一次提问"为什么？"→ 得到L1原因
Step 3: 对L1原因再提问"为什么？"→ 得到L2原因
Step 4: 重复直到触及以下任一状态：
  a) 找到了可行动的根因 → 停止，设计对策
  b) 超出产品可控范围 → 停止，标记约束
  c) 推理开始循环（A→B→A）→ 停止，重新定义问题
Step 5: 验证根因（跨用户/场景交叉验证）
```

### 实战案例：C端需求5Why

```
现象：用户反馈"我要导出Excel"
  Why1: 为什么需要导出？→ 要把数据给老板看
  Why2: 为什么不用系统直接分享？→ 老板不看系统
  Why3: 为什么不看系统？→ 老板只在手机上看，系统无移动端
  Why4: 为什么不可以在电脑上看？→ 老板常出差，带着手机但不愿开电脑
  Why5: 为什么出差就不看系统？→ 系统登录需要VPN+Token，出差时太麻烦

根因：移动端访问门槛过高（非导出功能缺失）
对策：优化移动端访问体验 > 做导出功能
```

### 实战案例：B端需求5Why

```
现象：客户要求"增加审批流自定义功能"
  Why1: 为什么需要自定义？→ 现有审批流不满足组织架构变化
  Why2: 组织架构怎么变了？→ 新增了区域管理层级
  Why3: 为什么现有流程不支持？→ 现有流程只支持三级审批
  Why4: 为什么只做了三级？→ 设计时按单一业务线建模，没考虑集团化
  Why5: 为什么现在才意识到？→ 客户从单业务线扩展到多区域

根因：审批模型架构不支持多层级组织（非审批流UI问题）
对策：重构审批模型 → 远比加个"自定义审批流"更彻底
```

## 根因鱼骨图（Ishikawa Diagram）

当5Why发现根因不止一个时，使用鱼骨图梳理多维度根因：

```
需求现象（鱼头）
  ├── 人员因素（人）
  │   └── 用户能力/认知差异/使用习惯
  ├── 流程因素（法）
  │   └── 操作步骤/审批流/协作模式
  ├── 技术因素（机）
  │   └── 系统限制/性能瓶颈/兼容性
  ├── 数据因素（料）
  │   └── 数据缺失/数据格式/数据实时性
  └── 环境因素（环）
      └── 移动/弱网/多设备/合规
```

## 需求分层模型

| 层级 | 名称 | 内容 | 分析方法 |
|---|---|---|---|
| **L0 业务目标** | 为什么要做这个产品/功能 | 5Why追问到战略级 | 对齐业务目标 |
| **L1 用户场景** | 用户在什么场景下遇到什么问题 | 5Why + JTBD | 场景还原 |
| **L2 功能需求** | 需要什么功能来解决 | 用户故事映射 | 功能范围界定 |
| **L3 非功能需求** | 性能/安全/可用性等约束 | 约束分析 | 约束识别 |
| **L4 实现约束** | 技术栈/时间/资源约束 | 技术评审 | 可行性判断 |

## 5Why的常见误用

| 误用 | 表现 | 正解 |
|---|---|---|
| **机械式追问5次** | 不关注回答质量，只为凑够5次 | 每次追问都要有意义增量 |
| **把5Why当唯一工具** | 所有需求都用5Why分析 | 5Why适合"问题驱动"需求，"机会驱动"需求用JTBD |
| **5Why后直接出方案** | 找到根因就跳到解决方案 | 根因→需求条目→还要经过真伪判断(→D-02.03) |
| **单人5Why** | PM一个人坐那推理 | 至少2人交叉验证，避免逻辑自洽但脱离现实 |
| **忽略组织因素** | 只分析用户/产品层面 | B端需求必须分析组织/流程/利益相关方因素 |
