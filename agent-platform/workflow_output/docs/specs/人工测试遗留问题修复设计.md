## 1. 积分负数核查结论（7x-1 / 7x-2）

### 1.1 现状事实

| 事实 | 位置 |
|---|---|
| `user_points_balance` 表 CHECK (`balance_points >= 0`) | `V92__security_baseline.sql:19-20` |
| `project_group_wallets` 表 CHECK (`balance_points >= 0`) | `V133__project_group.sql` |
| 个人钱包扣款 = 条件 UPDATE（`balance + delta >= 0` 不满足则 0 行受影响 → 抛余额不足） | `UserPointsBalanceMapper.java:29-32` |
| 组池扣款 = 同款条件 UPDATE | `ProjectGroupWalletMapper.java:22-29` |
| 媒体任务（V155 预扣版）：提交即 HOLD，余额/组池 < 预估直接拒，任务行删除 | `MediaGenTaskService.java:265-275`（视频）、`:436-441`（图片）、`MediaBillingService.java:198-217` |
| 媒体任务（存量不 HOLD）：结算时扣费失败 → 任务 FAILED **不交付**（fail-closed） | `MediaGenTaskWorker.java:262-268`、`:337-343` |
| 聊天：答案已发给用户后才扣费，扣费异常被吞（计费铁律：答案送达优先） | `LlmBillingService.java:110-121` |
| 组池结算不足 → BACKSTOP 记组长个人账（设计口径，流水留痕） | `ProjectGroupWalletService`（BACKSTOP 逻辑，见《项目组与积分划拨设计》） |

### 1.2 结论

**积分不可能为负。** 两道保险：
1. 应用层：所有扣款走条件 UPDATE，`balance + delta < 0` 时影响 0 行，事务抛「积分不足」。
2. 数据库层：即使有代码绕过应用层，CHECK 约束直接拒绝写入。

**余额 10 扣 15（或 300）的实际结局——「不能扣」发生在何时决定是否白嫖**：

| 场景 | 拦截时刻 | 结局 | 是否白嫖 |
|---|---|---|---|
| 图片/视频生成 | **执行前**（提交时） | 预估 > 余额 → 任务直接拒绝、不创建、不执行 | 否（没产出） |
| 存量媒体任务（升级前提交、无 HOLD） | **交付前**（结算时） | 扣费失败 → 任务 FAILED，产出不交付 | 否（付不了钱拿不到货） |
| 聊天（现状） | **交付后**（流尾实扣） | 答案已发 → 实扣失败 → 异常被吞 | **是——唯一白嫖口子** |
| 聊天（§4 HOLD 修复后） | **执行前**（发起时） | hold = min(预估上限, 可用) 冻不住 → 消息拒发，明确话术 | 否 |

白嫖 = 拿到服务没付钱。媒体路径「不能扣」的代价是服务也不给（拒绝执行 / 拒绝交付），不构成白嫖；只有聊天是「服务先给、钱后收、收不到拉倒」——§4 聊天 HOLD 专为闭环此口子，与「是否允许负数」无关。

### 1.3 修复内容（仅文档漂移清理）

| 项 | 位置 | 改法 |
|---|---|---|
| 实体类注释仍写「可负」 | `UserPointsBalanceEntity.java:13`、`:25` | 注释改为「DB CHECK 保证非负；扣款走条件 UPDATE」 |
| 原始规格 B6 写「负数记欠款」 | `docs/specs/积分计费系统.md` §B6 | 改口径为「V92 后 DB 层不可负；欠款语义不存在」，记录变更原因（V92 晚于该规格） |
| 人工测试文件 | `人工测试问题/7x_积分系统.md` 未解决 2 项 | 实现完成后勾销并注明本节 |

### 1.4 测试策略

- 单测：条件 UPDATE 边界（余额恰等扣款、余额差 1）。

## 2. 降职回收限额（17x-1）——真漏洞

### 2.1 问题原文

> 组长/管理员给成员分配了额度后，自己的使用额度需要相应的被扣减……当我给一个人设置为管理员时给他分配了 200 积分，他给别人分配了 100 积分，他剩余可分配就变成了 100，但限额还是 200，等我把他管理员身份拿走时，他的限额还是 200，但是他已经分配的 100 没有被收回，还在被分配了的成员下，导致最终 200 积分变成 300 积分，被薅羊毛。

### 2.2 现状事实（已亲核）

| 事实 | 位置 |
|---|---|
| 降职（MANAGER→MEMBER）只做两件事：下级改挂组长 + 改角色，**quota 不动** | `ProjectGroupService.java:462-470` |
| `requireMember` 普通查询，**无 FOR UPDATE 行锁**（对比：配额落行/邀请接受/管理扣费均持管理行 FOR UPDATE） | `ProjectGroupService.java:489-495` |
| 管理本人消耗双卡（allocatable 卡 + addUsed quota 卡）**仅对 ROLE_MANAGER 生效**——降职后管理卡失效，只剩成员 quota 卡 | `ProjectGroupWalletService.java:119-130` |
| 成员卡 = `used + cost <= quota` 条件 UPDATE，各自只守自己的 quota | `ProjectGroupMemberMapper.java:63-66` |

**超发链复演**（组池共 200）：
1. 组长给 A 设管理员、quota=200 → A 给 B 配 quota=100（占 A 预算，A 可分配 4000→3000 类比成立）。
2. 组长把 A 降职：B 改挂组长（quota=100 保留），**A 的 quota 仍是 200**。
3. A 花 200 + B 花 100 = 300 > 组池 200。池耗尽后：媒体提交 HOLD 被拒；**聊天答案照发不计费**（白嫖）；媒体结算组池不足 → **BACKSTOP 扣组长个人钱包（组长是受害者）**。

**次生洞**（agent 探查，行号待 Phase 2 落地时复核）：
- 降职后 PENDING 邀请被接受：`allocated_by_user_id` 指向已是 MEMBER 的行，`insertMemberRow` 的 MANAGER 硬校验被跳过（`ProjectGroupInviteService.java:147` 一带）。
- 全链路无 `Σ下级 quota ≤ 组池` 的显式校验（现靠池 CHECK + BACKSTOP 兜底）。

### 2.3 修复设计

**核心规则：降职时按「已被下级占用」同步收缩 ex-manager 的限额。**

`updateMemberRole` 降职分支改造（同一事务内，顺序执行）：

1. **加锁**：`requireMember` 改用 `selectByGroupUserForUpdate`（复用 V156 已有锁原语），防止「降职 × 消耗/配额」并发打穿。锁序与 `doChargeGroup`（组池→成员行）同向。
2. **reparentChildren**（现有逻辑保留）：下级改挂组长。
3. **缩额**（新增）：
   - `quota != null` 且直接下级 quota 全部非空：`quotaNew = max(used, quota − Σ直接下级 quota)`。例：200 − 100 = 100 → A 仍可自用 100，B 用 100，总额 200 守恒（贴合问题原话「限额还是 200 → 应为 100」）。
   - **任一直接下级 quota 为 NULL（不限额成员）**：无法计算差值，保守取 `quotaNew = used`（视全部剩余已被下级占用；与 `allocatable` 对「不限额下级按 0 可分配」的既有口径同向）。
   - 下限取 `used`：不能把已花掉的额度收走（与既有「调预算下限=已占用」口径一致）。
   - `quota == null`（不限额管理）：保持 null。不限额时本无 quota 可双算，池 CHECK 仍守绝对上限，不产生新超发。
4. **留痕**：缩额写组账本新类型 `MEMBER_RECLAIM`（实现期修正：原定 `MEMBER_QUOTA_ADJUST`，但缩额=收回授权，记 RECLAIM 才能让「净额=ΣALLOCATE−ΣRECLAIM」正确反映有效授权；QUOTA_ADJUST 仅用于限额↔不限边界，delta=0。见 §8.2），remark 记「管理降职缩额」。
5. **PENDING 邀请收口**（次生洞）：邀请接受时校验 `allocated_by` 行**当前**角色仍为 MANAGER；不是（降职/移除/组外 admin 代发）则该成员落行改挂组长（组长侧无预算上限硬卡天然跳过）。

**显式不做**：`Σquota ≤ 组池` 全局校验。理由：池 CHECK + BACKSTOP + 上述缩额后，超发口子已闭；全局 Σ 校验在动态调额场景下限制过死（组长可以后补池）。记录为设计取舍。

### 2.4 数据模型

- 无新列（复用 `quota_limit_points` / `used_points`）。
- 组账本新流水类型：`MEMBER_QUOTA_ADJUST`（delta 为 quota 变化，ref = member 行），与 §8.2 共用定义。

### 2.5 测试策略

- **单测**（扩 `MemberBudgetServiceTest` / 新 `updateMemberRole` 测试）：
  - 算例 200/100：降职后 A quota=100；A 已用 150 时降职 → quota=max(150, 200−100)=150。
  - 不限额管理降职 → quota 仍 null。
  - 并发：降职事务与 `doChargeGroup` 互斥（锁序回归）。
  - PENDING 邀请在降职后接受 → 落行挂组长且过组长 allocatable 硬校验。
- **人工测试**：复演问题原话全流程（设管理 200 → A 分 B 100 → 降职 A → 核对 A 限额 100、组内总额不再超 200）。

### 2.6 安全考量

- FOR UPDATE 锁消除「边降职边消耗/边配额」竞态。
- 缩额留痕 + `@AuditLog`（任免已是敏感操作）。
- BACKSTOP 保持不变（兜底而非主防线）。

### 2.7 开放问题

- **Q1**：降职后剩余自用额度取 `quota − Σ下级 quota`（推荐，贴合问题原话）还是更保守的 `= used`（剩余可分配全回收）？

## 3. 预估口径 + 画布预估（17x-2 / 2x）

### 3.1 问题原文

> 17x-2：无限画布、视频生成、图片生成中，在检测剩余积分是否超过预计消耗积分时，需要展示并核对该账号**剩余项目内积分**够不够预计消耗，而不是整个项目组剩余够不够。
> 2x（资产库和无限画布）：画布提交前无预估消耗显示。

### 3.2 现状事实

| 事实 | 位置 |
|---|---|
| 预估接口 gid 模式 `balance` = 组池余额，**不查成员 quota−used** | `MediaGenTaskService.java:786-793`（`estimatePreview`） |
| `/mine` 已返回 `myQuota/myUsed/myAllocatable`，但预估链未消费 | `ProjectGroupService.java:310-358` |
| 提交侧三重卡已在：池 < est 拒；成员 `used+est > quota` 拒；HOLD 预扣（**used 同步预占**，即 quota−used 已含在途） | `MediaGenTaskService.java:265-275`/`:436-441`；`MediaBillingService.java:198-217` |
| 生成页有预估 + 红字（组池口径） | `ImageGenView.vue:164-172`、`VideoGenView.vue:254-262` |
| **画布提交无任何预估调用** | `CanvasView.vue:1280`（视频）、`:1433`（图片） |
| 画布图片参数面板与生成页是两套独立实现 | `PropertyPanel.vue:971-976` vs `ImageGenView.vue:373-378` |

**定性**：钱是安全的（提交侧三重卡 + HOLD），这是**展示口径缺口**——预检显示「组池够」但提交被「成员限额」拒绝，用户困惑；画布则完全无预估。

### 3.3 修复设计

**后端**——`estimatePreview` 返回扩展（向后兼容，老字段保留）：

```
{
  estimatedPoints, balance,                    // 老字段（组池口径）不动
  personalScope: {                             // gid 模式新增；个人模式为 null
    quota, used,                               // null = 不限额
    inProjectAvailable,                        // quota==null ? null : quota−used（含在途 HOLD）
    bindingConstraint,                         // MEMBER | POOL | BOTH | NONE（哪层先卡住）
    affordable                                 // min(个人可用, 池) >= est
  }
}
```

`affordable`（顶层）改为 `personalScope == null ? 池够 : min(个人, 池) >= est`。

**管理成员的双卡口径**（与提交侧 `doChargeGroup` 对齐，否则预估又和提交不一致）：
- `inProjectAvailable`：MEMBER 行 = `quota − used`；MANAGER 行（quota 非空）= `min(allocatable, quota − used)`（管理自身消耗同时吃「可分配须保留下级预留」和「限额」两张卡）。
- 不限额 MANAGER/MEMBER（quota=null）：`inProjectAvailable = null` → 只看池。

**前端**——三处统一：
1. 生成页（图/视频）：红字按 `bindingConstraint` 分层提示——`MEMBER`：「项目内剩余 X 不足（你的限额 Y − 已用 Z）」；`POOL`：「项目组池剩余 X 不足」；`BOTH` 取更紧的。
2. **画布**：视频节点、图片节点参数面板提交按钮旁加预估 chip「预估 X 积分 · 项目内剩余 Y」，输入防抖调 `GET /api/media/estimate?projectGroupId=`；不足红字。两个画布提交点（`CanvasView.vue:1280/1433`）接同一预估。
3. 不限额成员：`inProjectAvailable=null` → 只显示池口径（现状文案）。

## 4. 聊天实时 token 与并行管控（9x-1）

### 4.1 问题原文

> 在对话生成结果的过程中，能实时看到 token 的消耗值吗？如果不行的话，我怎么对用户并行消耗任务做管控，比如用户在无限画布中使用 llm 模型，在智能对话中也在同步使用 llm，那如果积分在过程中用超了，剩余积分已经不够扣了，怎么办？

### 4.2 现状事实

| 事实 | 位置 |
|---|---|
| 聊天后付：预检只查余额 > 0 | `PointsWalletService.requireAffordable:66-75` |
| 答案发完才扣费；扣费异常被吞（答案送达优先，平台担损） | `LlmGateway.java:103`/`:171-184`、`LlmBillingService.java:110-121` |
| usage 只在流尾可知（OpenAI `include_usage` / Claude `message_delta`） | `OpenAICompatibleProvider.java:121-148`、`ClaudeProvider.java:122-156` |
| `StreamEvent` 协议无 usage 字段（CHUNK/DONE/ERROR 等） | `StreamEvent.java:14-54` |
| 前端聊天界面无消耗显示；画布 LLM 节点（非流式）无消耗 | `CanvasNodeRunnerService.java:96`/`:167-175` |
| 并行闸门：余额 < 100 时 Redis 限 in-flight ≤ 1（fail-open），余额充足时无限制 | `InflightGateService.java:68-117` |
| **SSE 回退 bug（亲核）**：流装配抛 `INSUFFICIENT_POINTS`（或任何异常）→ 外层 catch → 同步 `sendMessage` 重答 → 再失败 → 用户只见「服务器内部错误」；积分不足话术到不了前端；已发 chunk 后回退还有双答风险 | `ChatController.java:315-341` |

**定性**：真缺口 ×3——① 协议/前端无消耗可见性；② 聊天无 HOLD，余额够开局就能免费超完（并行放大）；③ SSE 回退路径吞业务话术。

### 4.3 修复设计（三层）

**层 1：协议 + 显示（消耗可见）**

- `StreamEvent` 的 DONE 事件增 `usage` 字段：`{promptTokens, completionTokens, totalTokens, points}`——服务端从现有 usage sink（doOnComplete）取，拼进 DONE 再发。
- 前端智能对话：回答尾部显示「本次消耗 N tokens ≈ X 积分」（DONE 校准精确值）。
- 流中实时计数（**Q2=B 拍板**）：服务端累计 chunk 字符、按系数估 token，每约 1 秒或每 N 个 chunk 发 `StreamEvent` 新类型 `PROGRESS`（载荷 `{estimatedTokens, estimatedPoints}`）；DONE 到达后以精确 usage 校准。系数（1 token ≈ 多少字符）入 system_settings 可配。
- 画布 LLM 节点：非流式响应本就带 usage（`CanvasNodeRunnerService` 落库侧已有），`dataPatch` 透传 → 节点角标显示本次消耗。

**层 2：聊天 HOLD（并行管控，对称媒体 V155）**

- 流开始前（**Q4=B 拍板：不加帽，理论上限全额冻**）：`hold = est 全额`，其中 `est = prompt 估算 tokens × 入价 + maxTokens × 出价`（prompt = 历史+本轮消息字符 ÷ 系数折算，系数与 PROGRESS 共用；只算输出侧会导致长上下文每次都补扣差额）。**可用 < est → 直接拒发**（不做 min 截断——min 后 hold 永不失败，「余额不够不开局」失效且常态化滚 DEBT；DEBT 只兜漏网窗口）。复用 `walletService.chargeIdempotent` / `groupWalletService.chargeGroup`（组模式下 used 同步预占），kind=`CHAT-HOLD`，幂等键 `chat-hold-{messageId}`。
  - **maxTokens 来源**（优先级）：请求显式参数 → 模型/Provider 配置缺省 → 系统设置兜底（如 8192）。Phase 2 落地时确认现状有无请求级参数，无则只用配置缺省。
  - **计价模式适用域**：HOLD 仅适用 TOKEN 计价模型（hold = token 上限 × 单价）。若价表存在按次计费（PER_CALL）聊天模型，hold = 单次单价；SECOND 模式不适用于聊天（无时长概念），若出现则跳过 HOLD 仅走预检（记录取舍）。
- hold 失败（余额 < hold）→ 直接拒绝发起，错误话术「积分不足，预估需要 X，当前可用 Y」（进入层 3 修复后的通路）。
- 流尾：按 usage 精确多退少补（补扣 kind=CHAT、退差 REFUND，同媒体 V155 语义）。
- 用户主动停止（**Q3=B 拍板：按已产字符折算收费**）：settle = min(hold, 字符折算成本)——折算系数与 PROGRESS 计数共用（见层 1），退差 `hold − settle`；若 provider 在取消时仍返回精确 usage 则优先精确值。usage 完全不可知的异常中断：全额退 hold（兜底，损失有界）。
- 效果：并行 N 路时每路开局即预扣，钱包/组池条件 UPDATE 天然防超扣——「过程中用超」不再可能超过已 hold 的份额。

**层 3：SSE 回退修复（话术到达）**

`ChatController.java:315` 外层 catch 分流：

1. 异常为 `BusinessException`（INSUFFICIENT_POINTS 等）且**未发出任何 chunk** → 直接 `emitter.send(ERROR 事件带业务话术)` + DONE + complete，**不走同步重答**。
2. 已发出 chunk 的任何异常 → 不重答（防双答/双计费），发 ERROR + DONE 收尾。
3. 仅「未发 chunk + 非业务异常（技术失败）」保留现状同步回退。

**层 4：结算兜底「扣到 0 + 欠款记账」（没拦住也扣）**

HOLD 拦截后的残留窗口（代码 bug 漏入口 / 实耗冲破 HOLD 帽 / 存量路径绕过）用结算腿兜底：

- 结算时 `balance < cost` → 无条件 `UPDATE balance = 0`（把剩下的扣走；注意条件 UPDATE 是全有全无，扣 0 行就是一分没扣，故此腿必须单独写「扣到 0」语句），差额记 `points_ledger` 新 kind=`DEBT`（欠款在流水，balance 列不动，DB CHECK 不破——即原规格 B6「负数记欠款」语义的落地形态）。
- 欠款生效期间：`requireAffordable` 等所有消费入口加查「欠款余额 > 0 即拒」，欠款不清不能再消费。
- 充值自动冲抵：充值到账先还 DEBT（记 `DEBT_REPAY` 流水），余数才进 balance——白嫖变赊账，钱跑不掉。
- 组内链式兜底：组池不足 → BACKSTOP 组长个人钱包（现有）→ 组长个人也不足 → **组长 DEBT 记账**（兜底到底，不再有平台担损终点）。
- 适用域：聊天结算 + 任何结算腿差额（媒体补扣差额同理适用）；媒体主路径仍 fail-closed（交付前拦截），DEBT 只兜漏网。
- 前端：钱包页显示欠款金额与「充值后将自动偿还」提示；充值页同理。

### 4.4 数据模型

V157（与 §6 的 remark 同一迁移文件）：`user_points_balance` 增列 `debt_points NUMERIC(18,2) NOT NULL DEFAULT 0`——欠款**冗余列**（欠多少直接存在钱包行上，避免每次消费入口去 SUM 大流水表；DEBT/DEBT_REPAY 流水仍全量记 points_ledger 作明细）。

### 4.5 测试策略

- 单测：HOLD 多退少补/取消全额退的幂等性（复用媒体 V155 测试范式）；SSE 回退三分支（mock emitter 计数 chunk 发送）。
- **人工测试**：① 余额 1 积分发起聊天 → 收到「积分不足」明确话术（非「服务器内部错误」）；② 画布 LLM + 智能对话并行 → 双方各自 HOLD、流尾各自显示精确消耗、余额明细可见 CHAT-HOLD 补扣/退差流水；③ 流中回答区实时计数跳动、DONE 后校准。

### 4.6 安全考量

- HOLD 复用条件 UPDATE：并发多流不会超扣（余额不够 hold 第二路直接拒）。
- 幂等键防重放/重复补扣。
- fail-open 的 InflightGate 保留为第二道闸（HOLD 后其作用弱化，不拆）。
- usage 显示不影响计费源（显示取自同一 sink，只读）。

### 4.7 开放问题

- **Q2**：流中实时计数用纯前端字符估算（推荐，零协议改动，误差 ±20% 内、DONE 校准）还是服务端周期 PROGRESS 事件（准但加协议与后端负担）？
  - 服务端周期PROGRESS事件，尽量准
- **Q3**：用户主动停止的回答——全额退 hold（推荐，实现简单、口径=平台担损一次）还是按已产字符折算收费？
  - 当然按已产生字符折算收费

**平台侧推导宽×高（方式 2），比例 + 档位在平台层「同传」。**

- **任务详情/资产**：产出记录存最终 `size=WxH`（上游返回 `data.size`，官方已保证回显），前端展示实际尺寸。

- 现象：配置 `http://localhost:5173/reset-password`，邮件链接被 QQ 邮箱改写成 `https://wx.mail.qq.com/xmspamcheck/http%3A%2F%2Flocalhost...` 后该页 404。
- 定性：非平台代码 bug——QQ 邮箱对邮件内链接做安全检查跳转，其检查服务够不到 localhost（开发机不可公网访问），改写页本身打不开。生产公网域名无此问题。
- 修复：邮件模板在链接下方加**纯文本 URL + 「若点击无效，请复制此链接到浏览器打开」**提示（`EmailService.sendResetEmail` 模板）；用户文档注明开发环境现象与复制链接做法。

**问题 ②：直接访问 `/reset-password` 显示的是手机号+验证码表单**
- 真因（已核）：`ResetPasswordView.vue:171-174`——URL 无 token 且无 channel 参数时**默认落到 SMS 表单**，而 SMS 重置后端未实现（提交必报「暂未实现」）＝死路；EMAIL 重置又必须从邮件链接带 token 进入。
- 修复：无 token 访问时不再默认 SMS——EMAIL 渠道启用时显示引导页「请通过邮件中的重置链接进入」+「重新发送重置邮件」入口（跳登录页忘记密码弹窗）；SMS 分支仅在 `channel=sms` 显式传入**且** SMS 渠道已启用时渲染（`GET /api/auth/channels` 判断，未启用不露出）。

### 8.3 修复设计

**8.3.1 昵称三处补齐（20x-1）**
- `user-balances` / `recharges` / 排行 三个响应增 `name`；前端列显示 `name（username）`，name 缺省回退 username。
- 复用 `/admin/user-options` 的双匹配先例；keyword 筛选同步匹配 name。

**8.3.2 成员分配流水（20x-2 数据源，与 §2 共用）**
- 组账本新类型（**实现期修正**：降职缩额从 QUOTA_ADJUST 改记 RECLAIM，净额等式才成立）：
  - `MEMBER_ALLOCATE`：配额落行/调增时记（delta=+增加额，ref_type=MEMBER、ref_id=成员 userId）。
  - `MEMBER_RECLAIM`：调减/降职缩额时记（delta=−减少额）。
  - `MEMBER_QUOTA_ADJUST`：限额↔不限互转边界留痕（delta=0，remark 记前后值），不进毛额/净额聚合。
- 落点：`updateQuota` 三分支、邀请接受配额落行（insertMemberRow 复活+新插两径）、降职缩额——统一走 `recordMemberQuotaLedger` 私有方法（同事务；old==new 不落行；balance_after 照抄当前池余额做快照，非资金腿）。
- **语义约定**：这是「配额授予历史」，不是资金流水（不进 points_ledger，不动钱包）——quota 是限额不是余额；对账等式（D4）白名单显式排除 MEMBER_*。

**8.3.3 项目内余额视图（20x-2 展示）**
- 新端点 `GET /billing/admin/group-allocations`：行 = (用户 × 项目组)：
  `name, username, 组名, quota, used, 项目内剩余(quota−used), 累计被分配(毛额=Σ MEMBER_ALLOCATE), 净划拨(Σ MEMBER_ALLOCATE − Σ MEMBER_RECLAIM), 最近分配时间`。毛额回答「历史上一共分到过多少」，净额回答「现在还留着多少授权」。
- 前端：账单总览新「项目组分配」tab（表格 + 用户/组筛选）；「用户余额」tab 行可展开跳转该用户的项目组分配明细（二期可选）。

**8.3.4 划拨对账（20x-3，白嫖探针）**
- 新端点 `GET /billing/admin/group-reconcile`：
  - 全平台卡：`划拨净额 = Σ(GROUP_ALLOCATE) − Σ(GROUP_RECLAIM)`；`组池余额合计`；`组内累计消耗`；`累计退款`；`BACKSTOP 合计`。
  - 恒等式：**划入净额 + 累计退款 − 累计消耗 = 组池余额合计**。
  - 每组一行（组名/划入净额/消耗/退款/当前余额/差值），差值 ≠ 0 标红（数据 bug / 白嫖探针）。
- 前端：账单总览新「项目组对账」tab：顶部恒等式卡（平/不平状态），下钻异常组。
- 双账本交叉校验（组账本 vs points_ledger 镜像腿）在同端点附带（不一致也标红）。

### 8.4 数据模型

无表迁移。组账本复用 `project_group_ledger`（type 扩枚举 + remark），聚合查询按需补索引（Phase 2 评估 `(group_id, type)` 组合索引）。

### 8.5 测试策略

## 12. 术语表

| 术语 | 大白话 | 简单案例 |
|---|---|---|
| HOLD 预扣 | 先按预估把积分冻住扣掉，完事多退少补 | 图片预估 15 分先扣 15，实际只值 10 分就退 5 分 |
| 条件 UPDATE | 扣款 SQL 自带「扣完不能是负数」的判断，不满足就不扣 | `UPDATE ... SET balance=balance-15 WHERE balance>=15`，余额 10 时影响 0 行 |
| FOR UPDATE 行锁 | 事务里先把这行数据锁住再算账，别人只能排队 | 管理边花钱边给下级配额，两件事排队执行不会算错 |
| BACKSTOP 兜底 | 组池钱不够结账时，记到组长个人钱包头上 | 成员花超组池，差额从组长个人余额扣 |
| quota / used | 给成员设的限额 / 已花掉的数；项目内剩余 = quota − used | 限额 100 用了 30，剩 70 |
| allocatable（可分配） | 管理手里还能往下分的额度 = 自己额度 − 子树已花 − 已分给下级的 | 管理 200，下级共被配 100、已花 20 → 可分配 80 |
| 子树 | 某管理下面挂的所有人（含再往下） | 管理 A → 成员 B、C；B 再带 D：A 的子树 = B、C、D |
| WxH 推导 | 平台把「比例 + 清晰度档」换算成具体宽×高像素再传上游 | 16:9 + 2K → 2731x1536 |
| 像素档（2K/3K/4K） | 上游的清晰度档位；不传比例时图的宽高由模型自己定 | 只传 2K，出图约 200 万像素，比例随机 |
| SSE | 服务器持续往浏览器推数据的流式连接 | 聊天回答一个字一个字往外蹦 |
| usage sink | 流结束后上游返回的真实用量统计落库的通道 | 回答生成完才知道用了 1234 个 token |
| 幂等键 | 同一操作的防重指纹，重复请求只生效一次 | 网络重试导致退款指令发两次，只退一次 |
| fail-open / fail-closed | 依赖的服务挂了时放行 / 拒绝 | Redis 挂了闸门放行（fail-open）；价表缺失提交必拒（fail-closed） |
| 对账恒等式 | 划进来 − 花掉 + 退回 = 现在剩的，两边对不上就是有 bug | 划入 1000、消耗 300、退款 50，池里就该是 750 |
| capability JSON | 配置每个模型支持哪些参数（档位/比例/区间）的数据块 | 5.0-lite 配了 [2K,3K,4K]，pro 配 [1K,1.5K,2K] |
