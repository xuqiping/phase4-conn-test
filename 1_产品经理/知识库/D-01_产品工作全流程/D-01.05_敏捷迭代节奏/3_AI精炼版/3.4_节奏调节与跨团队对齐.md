# 3.4 节奏调节与跨团队对齐

## 节奏不匹配的5个信号

| 信号 | 根因 | 调节方向 |
|---|---|---|
| 每次Sprint都延时 | 节奏太快/拆分不够/承诺过度 | 减少Sprint容量或延长周期 |
| Retro总是同样的改进项 | 节奏问题被反复暴露但未解决 | 聚焦1条改进项+2周内验证 |
| 团队疲劳/倦怠 | 节奏过紧无喘息空间 | 增加缓冲/减少仪式/减少容量 |
| 需求总是Sprint中途插入 | 外部节奏与Sprint不匹配 | 容量缓冲或看板处理插队 |
| 干系人抱怨"看不到进展" | Review节奏与干系人期望不匹配 | 增加演示/缩短Sprint |

[来源:📚训练知识+行业实践 | 置信度:🔍高]

## 节奏调节四原则

1. **渐进调整**：每次只改1个变量（周期/容量/仪式），观察2个Sprint后再决定
2. **对症下药**：不是所有问题都是节奏问题——先排除"需求质量差/技术债多/人员不足"
3. **团队参与决策**：节奏是团队的节奏，不是经理的节奏——Retro时集体讨论
4. **数据驱动调节**：用Velocity趋势/交付速率/缺陷率做客观判断

## 节奏调节矩阵

| 问题 | 1周Sprint | 2周Sprint | 看板 |
|---|---|---|---|
| 延时频繁 | → 2周Sprint | → 减少容量 | 不适用 |
| 反馈太慢 | 已是最快 | → Review提前 | 缩短交付周期 |
| 需求插队多 | → 看板混合 | → 20%缓冲+看板通道 | 天然支持 |
| 团队疲劳 | → 2周Sprint | → 减少仪式 | 天然更轻松 |
| 多团队不同步 | → 对齐为2周 | → Scrum of Scrums | → 看板+定期同步 |

## 跨团队节奏对齐

### Scrum of Scrums（SoS）

| 项 | 内容 |
|---|---|
| 频率 | 每日或每2-3天一次 |
| 时长 | 15min |
| 参与者 | 各Scrum团队的1名代表 |
| 议程 | ① 自上次SoS后完成了什么 ② 下次SoS前要做什么 ③ 有什么阻塞跨团队的问题 ④ 有什么跨团队依赖需要协调 |

### 多团队同步策略

| 策略 | 做法 | 适用场景 |
|---|---|---|
| 统一Sprint节奏 | 所有团队同期开始/结束Sprint | 团队间依赖强 |
| 错峰Sprint | 团队错开1周开始 | 系统集成需要滚动测试 |
| PI Planning（SAFe） | 5个Sprint的跨团队联合规划 | 大型组织/强依赖 |
| LeSS | 1个Product Backlog+多团队共享 | 同一产品多团队 |

### 跨团队依赖管理

- **显式化依赖**：在Planning时标记跨团队依赖→分配对接人
- **接口先行**：前后端约定API→各自并行开发
- **集成火车**：统一时间点做集成→避免"永远集成不完"

[来源:SAFe/LeSS/Scrum Guide | 置信度:🔍高]

## 远程/混合团队的节奏适配

2025-2026趋势：远程/混合团队需要更强的节奏仪式感。

| 挑战 | 应对 |
|---|---|
| 时区差异 | 缩短同步窗口→异步优先+每日1次同步 |
| 仪式感缺失 | 增加虚拟白板/在线站会→保留仪式结构 |
| 上下文断裂 | 文档化决策→Confluence/Notion做知识库 |
| 信任下降 | 更频繁的Review+更透明的看板 |
