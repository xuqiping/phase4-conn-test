## 二、阶段二：技术选型

### 2.1 推荐架构组合 ⭐首选

```
前端层:    React + TypeScript + Tailwind CSS + Ant Design Pro
           ↓ HTTPS/REST API
后端层:    Go + Gin框架 + gRPC内部通信
           ├── Bot接入层: 飞书/钉钉/企微/Slack SDK封装
           ├── 消息处理: 接收→解析→分类→去重→语义标签
           ├── 定时调度: Asynq + Redis 分布式任务队列
           ├── 报告引擎: Go template + 通义千问/豆包AI API
           └── 推送层: 群推送/单聊/邮件/云文档同步
数据层:    PostgreSQL 16 (业务数据)
           ├── Redis 7 (缓存/队列/会话)
           └── MinIO (报告归档/附件存储)
```

### 2.2 各模块技术选型

| 模块 | 首选方案 | 备选方案 | 理由 |
|------|----------|----------|------|
| 后端框架 | **Go + Gin** | Node.js + Express | 高性能、高并发、编译型语言 |
| Bot接入 | **各平台官方SDK** | 自建Webhook网关 | 官方SDK稳定性高、文档完善 |
| 消息解析 | **自研+正则+关键词** | NLP模型 | MVP阶段规则引擎足够 |
| 定时调度 | **Asynq + Redis** | APScheduler | 分布式、支持Cron、可重试 |
| 报告模板 | **Go template** | Handlebars | 与Go生态集成好、性能高 |
| AI总结 | **通义千问/豆包API** | 本地LLM | 成本低、中文效果好 |
| 数据存储 | **PostgreSQL 16** | MySQL | 支持JSON、全文搜索、稳定性高 |
| 缓存队列 | **Redis 7** | RabbitMQ | 多功能、生态成熟 |
| 对象存储 | **MinIO** | AWS S3 | 开源、可私有化部署 |
| 部署 | **Docker Compose** | K8s | MVP阶段简单高效 |

### 2.3 预期性能指标

| 指标 | 目标 | 预期达成 |
|------|------|----------|
| 消息处理延迟 | <1s | ✅ Go高并发轻松支持 |
| 报告生成时间 | <30s | ✅ AI API调用为主 |
| 系统并发 | >1000 QPS | ✅ Gin框架支持 |
| 数据存储 | >100万条消息 | ✅ PostgreSQL轻松支持 |
| 部署成本 | <¥500/月 | ✅ 单台云服务器即可 |

## 三、阶段三：竞品反向挖掘

### 3.1 竞品矩阵

| 竞品 | 定位 | 商业模式 | 核心槽点 |
|------|------|----------|----------|
| **钉钉AI表格** | 平台内置自动化 | 免费（平台功能） | 平台锁定、功能受限、不能跨平台 |
| **飞书多维表格** | 平台内置自动化 | 免费（平台功能） | 平台锁定、学习成本、模板僵化 |
| **企业微信智能总结** | 平台内置AI功能 | 免费（平台功能） | 功能浅层、不能自定义、隐私担忧 |
| **Zapier** | 通用自动化平台 | $20-$599/月 | 按任务计费贵、中文支持差、学习成本高 |

| **八爪鱼RPA** | RPA工具 | 企业级定价 | 学习成本高、非专为报告设计 |
| **WorkBuddy** | AI办公助手 | 订阅制 | 部署复杂、企业级稳定性待验证 |
| **Geekbot/Standuply** | Slack专用Bot | $3-5/人/月 | 仅支持Slack、国内无法使用 |

### 3.2 差评分类统计

| 分类 | 数量 | 占比 | 核心问题 |
|------|------|------|---------|
| 功能缺失类 | 18 | 47% | 跨平台汇总、自定义模板、数据导出 |
| 体验问题类 | 16 | 42% | 平台锁定、学习成本高、配置复杂 |
| 服务问题类 | 3 | 8% | 同步不稳定、数据丢失、隐私担忧 |
| 定价问题类 | 1 | 3% | 按任务计费导致成本飙升 |

### 3.3 关键洞察

1. **跨平台消息汇总是最大空白**：现有方案均为单平台（钉钉/飞书/企微各自为政），用户工作信息分散在多个IM中，急需统一汇总能力
2. **定时任务+自动推送是刚需**：用户强烈期望"设置一次，永久自动运行"
3. **低门槛使用决定 adoption**：成功案例多为"3步搭建""零代码"
4. **数据安全是企业决策关键**：企业用户关注"数据仅限内部流转""本地私有化部署"
5. **模板化+个性化需平衡**：既需要规范格式，又需要适配不同岗位/行业的个性化需求

## 四、阶段四：需求深度拆解

### 4.1 核心需求四层拆解

**需求1：自动汇总工作内容生成日报/周报**

| 层级 | 拆解内容 |
|------|---------|
| **表层诉求** | "我要自动生成周报/日报"、"不想手动写周报" |
| **行为痛点** | 每周五下午花1-2小时回忆工作、翻聊天记录、整理格式；容易遗漏；加班写报告 |
| **底层动机** | 效率（节省时间）、掌控（不遗漏工作）、安全（年底有记录）、愉悦（减少痛苦） |
| **人性欲望** | 安全需求→对工作记录的确定性；尊重需求→高效工作者的自我认同；自我实现→把时间花在更有价值的事上 |

**需求2：跨平台消息汇总**

| 层级 | 拆解内容 |
|------|---------|
| **表层诉求** | "微信、钉钉、企微、邮件都有工作信息"、"信息太分散" |
| **行为痛点** | 需要在多个APP之间切换查找信息；不同平台信息格式不同；手动复制粘贴汇总 |
| **底层动机** | 效率（减少切换）、掌控（信息统一管理）、安全（不遗漏重要信息） |
| **人性欲望** | 安全需求→信息不遗漏的确定性；效率需求→减少无效劳动 |
