# 计划8：多智能体与工作流自由组合

> 创建时间：2026-06-02  
> 目标：实现 Agent 与 Workflow 之间的自由组合、嵌套调用和可观测执行。

---

## 一、背景

当前平台已经具备：

- Agent 管理与技能配置
- Workflow 画布编排
- Chat 运行时
- LLM Gateway
- 执行日志
- 流式输出
- 用户级模型配置

下一阶段需要把这些能力从“单 Agent / 单 Workflow 执行”升级为“多个 Agent 与多个 Workflow 可以互相组合”。典型目标包括：

- 一个 Workflow 节点可以调用一个 Agent。
- 一个 Workflow 节点可以调用另一个 Workflow。
- 一个 Agent 的技能可以委托给 Workflow。
- 多个 Agent 可以按路由、条件、并行、串行方式协同。
- 执行过程可以持久化、恢复、追踪和调试。

---

## 二、框架调研结论

### 2.1 推荐框架：LangGraph

推荐将 **LangGraph** 作为核心参考框架和长期集成方向。

选择理由：

- 支持图式状态编排，天然适合 Agent / Workflow 节点组合。
- 支持 subgraph，可以把一个子工作流作为父工作流节点使用。
- 支持 durable execution，可保存执行进度并恢复执行。
- 支持 human-in-the-loop，后续可扩展人工审批节点。
- 状态流转、条件分支、循环、并行等能力与当前 Vue Flow 画布模型匹配度高。

参考资料：

- LangGraph Durable Execution: https://docs.langchain.com/oss/python/langgraph/durable-execution
- LangGraph Subgraphs: https://docs.langchain.com/oss/python/langgraph/use-subgraphs

### 2.2 其他框架对比

| 框架 | 优点 | 局限 | 结论 |
|------|------|------|------|
| LangGraph | 图编排、子图、持久化执行、人工介入 | Python/JS 生态，与当前 Java 后端需桥接 | 最推荐 |
| CrewAI | 角色型 Agent 团队上手快 | 对复杂工作流、细粒度状态和可恢复执行支持弱 | 可参考，不做核心 |
| AutoGen / Microsoft Agent Framework | 多 Agent 对话、企业 SDK 方向明确 | 当前项目是 Spring Boot + Vue，集成成本较高 | 后续评估 |
| OpenAI Agents SDK | Handoff、tools、追踪能力清晰 | 更适合轻量多 Agent，对复杂图工作流不如 LangGraph | 可用于单 Agent / handoff 参考 |
| Google ADK | Gemini 生态、多 Agent 支持 | 平台绑定更强 | 非当前主选 |

OpenAI Agents SDK 参考：

- https://openai.github.io/openai-agents-js/guides/multi-agent/

## 三、总体建议

### 3.1 不建议立即重写为 LangGraph

当前平台已有完整的：

- Spring Boot 用户与权限体系
- 模型供应商管理
- Vue Flow 工作流画布
- OrchestrationEngine
- 执行日志
- Chat 流式输出

如果直接迁移到 LangGraph，会带来较大的重构成本，并削弱已有 Java 后端能力。

### 3.2 修正后的推荐路线：Java 控制面 + Python LangGraph 执行面

不建议在 Java 里重复实现 LangGraph 的执行内核。否则后续接入 Python + LangGraph 时，Java 中的复杂图调度、checkpoint、resume、parallel/join 等代码会被替换，存在返工风险。

更合理的分工：

| 层 | Java Spring Boot | Python LangGraph |
|----|------------------|------------------|
| 用户/权限 | 负责 | 不负责 |
| Agent/Workflow 元数据管理 | 负责 | 不负责 |
| 模型供应商/API Key 管理 | 负责 | 可通过 Java 获取配置 |
| Vue Flow 画布 JSON 保存 | 负责 | 不负责 |
| 图定义转换协议 | 负责定义标准 JSON | 负责转换为 StateGraph |
| 图执行引擎 | 不重复实现 | 负责 |
| routing/condition/parallel/subgraph | 不重复实现 | 负责 |
| checkpoint/resume | 只保存摘要或外部引用 | 负责 |
| 执行日志/审计 | 主存储 | 回传事件 |
| SSE/WebSocket 前端转发 | 负责网关转发 | 产生执行事件 |

Java 应该优先实现的是：

- 统一执行协议
- WorkflowDefinition / AgentDefinition 标准 JSON
- Vue Flow JSON 到标准图定义的转换
- 调用 Python sidecar 的运行时网关
- 执行日志、权限、审计、配置管理

Java 不应该重复实现的是：

- 复杂图调度
- checkpoint / resume 内核
- subgraph runtime
- parallel / join runtime
- human-in-the-loop runtime

### 3.3 目标路线：LangGraph Sidecar

目标架构中引入独立 LangGraph 服务：

- Spring Boot 继续负责用户、权限、配置、数据库、模型供应商。
- Python LangGraph 服务负责复杂图执行。
- 二者通过 REST / SSE / WebSocket 通信。
- PostgreSQL 继续作为 Java 侧 execution log 存储。
- LangGraph checkpointer 负责 thread/checkpoint 持久化，可使用 Postgres / SQLite / Redis 等。

## 四、核心设计

### 4.1 LangGraph 中 Agent / Workflow 的呈现方式

LangGraph 通常不是以 Markdown 文本作为运行时主载体。它的核心是代码中的图：

- graph / StateGraph
- node 函数或 runnable
- edge / conditional edge
- state schema
- checkpointer

典型形态：

```python
builder = StateGraph(State)
builder.add_node("agent_a", agent_a_node)
builder.add_node("agent_b", agent_b_node)
builder.add_edge(START, "agent_a")
builder.add_conditional_edges("agent_a", route)
graph = builder.compile(checkpointer=checkpointer)
```

因此需要区分三类内容：

| 类型 | LangGraph 中的形态 | 本项目建议存储 |
|------|--------------------|----------------|
| Agent / Workflow 定义 | 代码动态构建的 graph、node、edge、state schema | Java 数据库保存可视化定义 |
| 运行时状态 | thread、checkpoint、state snapshot | LangGraph checkpointer |
| 业务配置 | prompt、tools、模型、参数、权限 | Java 数据库 |

### 4.2 存储边界

本项目建议：

| 内容 | 存储方式 |
|------|----------|
| Agent 名称、描述、头像、权限、所属用户 | Java 数据库 |
| Agent Prompt、模型、工具配置 | Java 数据库 |
| Workflow 画布 JSON | Java 数据库 |
| Workflow 节点/边 | Java 数据库 |
| LangGraph Python 代码模板 | Python sidecar 代码仓库 |
| Java Workflow JSON -> LangGraph graph 的转换逻辑 | Python sidecar |
| 每次执行的 thread/checkpoint | LangGraph checkpointer |
| 执行日志、审计、前端展示记录 | Java 数据库 |
| Markdown | 仅用于模板导入导出、Prompt 文档化、案例说明 |

不建议把 Markdown 作为正式运行时配置源。原因：

- 权限控制困难
- 版本管理困难
- 引用关系和并发修改难处理
- 执行日志和审计不方便关联
- 不适合前端画布的结构化编辑

推荐模式：

1. 前端 Vue Flow 保存 Workflow JSON 到 Java 数据库。
2. Java 调 Python sidecar：`POST /compile-and-run`。
3. Python 将 JSON 转成 LangGraph `StateGraph`。
4. LangGraph 执行并用 checkpointer 保存 thread/checkpoint。
5. Python 流式返回事件给 Java。
6. Java 保存执行日志并转发给前端。

### 4.3 统一执行协议

Java 侧不直接实现 `Executable` 图执行内核，而是定义跨服务协议。

建议核心协议对象：

- `AgentDefinition`
- `WorkflowDefinition`
- `ExecutionRequest`
- `ExecutionEvent`
- `ExecutionResult`

示例：

```json
{
  "executionId": "exec-001",
  "userId": 1,
  "workflow": {
    "id": 10,
    "nodes": [],
    "edges": []
  },
  "input": {},
  "runtime": {
    "stream": true,
    "checkpoint": true
  }
}
```

### 4.4 新增节点类型

| 节点类型 | 说明 |
|----------|------|
| AGENT_REF | 引用并执行一个已有 Agent |
| WORKFLOW_REF | 引用并执行一个已有 Workflow |
| ROUTER | 根据用户输入或上下文选择下一个 Agent / Workflow |
| CONDITION | 条件判断与分支选择 |
| PARALLEL | 并行执行多个子节点 |
| JOIN | 聚合并行分支结果 |
| HUMAN_APPROVAL | 人工确认或审批节点 |
| TOOL_CALL | 调用 HTTP/API/代码工具 |

### 4.5 统一输入输出结构

建议所有 Agent / Workflow / Tool 节点统一使用：

```json
{
  "input": {},
  "context": {},
  "memory": {},
  "output": {},
  "metadata": {}
}
```

字段说明：

| 字段 | 说明 |
|------|------|
| input | 当前节点输入 |
| context | 当前执行链上下文 |
| memory | 用户长期记忆或会话记忆 |
| output | 当前节点输出 |
| metadata | 模型、耗时、token、traceId 等元信息 |

### 4.6 父子执行链

执行日志需要支持嵌套关系：

| 字段 | 说明 |
|------|------|
| executionId | 当前执行 ID |
| parentExecutionId | 父执行 ID |
| rootExecutionId | 根执行 ID |
| nodeId | 当前节点 ID |
| sourceType | AGENT / WORKFLOW / SKILL / TOOL |
| sourceId | 被调用对象 ID |
| status | RUNNING / SUCCESS / FAILED / CANCELLED / WAITING |
| inputSnapshot | 输入快照 |
| outputSnapshot | 输出快照 |
| errorMessage | 错误信息 |

## 五、分阶段实施计划

### 阶段一：组合协议层

目标：先定义 Java 与 Python LangGraph sidecar 之间的统一执行协议，不实现 Java 图执行内核。

任务：

1. 新增 `AgentDefinition` / `WorkflowDefinition` / `ExecutionRequest` / `ExecutionEvent` / `ExecutionResult`。
2. 定义 Vue Flow JSON 到标准 `WorkflowDefinition` 的转换规则。
3. 定义 Java 调 Python sidecar 的 REST/SSE 接口。
4. 执行日志增加 `parentExecutionId` / `rootExecutionId` / `externalThreadId` / `checkpointRef`。
5. 增加协议转换和执行事件解析测试。

验收标准：

- Java 可以输出标准 `WorkflowDefinition`。
- Java 可以调用 mock sidecar 并接收 `ExecutionEvent`。
- Java 可以保存执行事件和父子执行链。
- 不在 Java 中实现复杂图调度。

### 阶段二：画布支持引用节点

目标：前端可以拖入已有 Agent / Workflow。

任务：

1. Vue Flow 增加 `AGENT_REF` 节点。
2. Vue Flow 增加 `WORKFLOW_REF` 节点。
3. 节点属性面板支持选择已有 Agent / Workflow。
4. 保存时将引用关系写入 Workflow 节点 config。
5. 执行时将引用关系转为标准 `WorkflowDefinition`。

验收标准：

- 用户可以在画布中拖入一个 Agent 节点。
- 用户可以在画布中拖入一个 Workflow 节点。
- 保存后刷新页面引用不丢失。
- Java 可以把引用节点序列化为 sidecar 可执行定义。

### 阶段三：Python LangGraph Sidecar

目标：引入 Python LangGraph 服务，负责真实图执行。

任务：

1. 创建 Python sidecar 服务。
2. 实现 `/compile-and-run`。
3. 将 `WorkflowDefinition` 转换为 LangGraph `StateGraph`。
4. 支持 AGENT_REF / WORKFLOW_REF / CONDITION / ROUTER 基础节点。
5. 通过 SSE 返回 `ExecutionEvent`。

验收标准：

- Java 调用 sidecar 后可以执行一个包含 Agent 引用的 Workflow。
- Java 可以接收 sidecar 返回的事件流。
- 前端可以看到执行进度。

### 阶段四：持久化执行与恢复

目标：使用 LangGraph checkpointer 实现 durable execution。

任务：

1. 为 sidecar 配置 checkpointer。
2. Java 保存 `externalThreadId` / `checkpointRef`。
3. 支持失败后恢复执行。
4. 支持人工审批节点进入 WAITING 状态。
5. 支持取消和重试执行。

验收标准：

- 执行失败后可以从失败节点重试。
- 人工审批节点可以暂停流程。
- 用户确认后流程可以继续执行。

### 阶段五：高级控制流与治理

目标：补齐自由组合的高级能力。

任务：

1. ROUTER 支持规则路由和 LLM 路由。
2. PARALLEL / JOIN 支持并行聚合。
3. 增加最大递归深度和循环检测。
4. 增加跨 Agent / Workflow 权限校验。
5. 增加上下文裁剪、摘要和 token 预算控制。

---

## 六、推荐下一步

优先启动 **阶段一：组合协议层**。

建议先做最小闭环：

1. 定义标准 `WorkflowDefinition` JSON。
2. 定义 `ExecutionRequest` / `ExecutionEvent`。
3. 增加 Java -> mock sidecar 的调用接口。
4. 执行日志支持 `parentExecutionId` / `externalThreadId` / `checkpointRef`。
5. 用测试验证 Java 能转换画布定义、调用 sidecar、保存事件。

不要先在 Java 中做复杂图执行。先把跨服务协议和存储边界打稳，再接 Python LangGraph。

---

## 七、风险与注意事项

| 风险 | 说明 | 应对 |
|------|------|------|
| 循环调用 | Workflow A 调 B，B 又调 A | 增加最大深度和循环检测 |
| 上下文膨胀 | 多 Agent 串联导致上下文过大 | 引入上下文裁剪和摘要 |
| 日志爆炸 | 并行和嵌套执行导致日志量快速增长 | 分层日志与按需加载 |
| 权限穿透 | 用户通过 Workflow 调用无权限 Agent | 执行前校验被引用对象权限 |
| 调试困难 | 多层嵌套后难定位失败节点 | traceId + parentExecutionId + nodeId |

---

## 八、结论

推荐选型：

> **以 LangGraph 作为执行内核，Java 只做平台控制面、配置存储、协议转换、执行网关和审计日志。**

该路线最符合当前项目现状：

- 保留 Spring Boot + Vue Flow 已有投资。
- 避免 Java 重复实现 LangGraph 执行内核。
- Agent / Workflow 定义以数据库结构化存储为主，Markdown 仅用于导入导出和文档化。
- Python LangGraph 负责真正的 graph、subgraph、checkpoint、resume、parallel/join。
- Java 后续接入 Python sidecar 时不会被废弃。
