# 4.2 SOP 5Why根因分析执行流程

> 📅 2026-07-11 ｜ 🔴红线：5Why分析禁止PM单人闭门推理，至少2人参与交叉验证 ｜ 角色：需求分析执行PM

## 背景

5Why是最常用的需求分析方法，但执行质量参差不齐。差的5Why只做浅层追问+逻辑自洽，好的5Why穿透到可行动根因+交叉验证。本SOP确保5Why执行质量稳定。

## 目标

从需求现象出发，通过结构化追问找到可行动的根因，输出需求根因清单+对策建议。

## 关键结果

1. 5Why追溯链（现象→根因）
2. 根因清单（含置信度标注）
3. 对策建议（从根因出发的设计方向）

## 执行步骤

### Phase 1：准备（30min）

| 步骤 | 动作 | 检查项 |
|---|---|---|
| 1.1 | 明确分析对象——哪个需求现象要追溯 | □ 现象描述是否具体客观？ |
| 1.2 | 准备支撑数据——用户原话/行为数据/工单 | □ 有原始证据支撑？ |
| 1.3 | 邀请协作人——至少1位不同角色(开发/设计/运营) | □ 视角多样化？ |

### Phase 2：5Why追溯（60-90min）

```
现象描述（写在白板/文档顶端）
  │
  ├─ Why1: 为什么会出现这个现象？
  │  ├─ 候选原因A（来源：用户原话）→ 选择
  │  ├─ 候选原因B（来源：数据推断）
  │  └─ 候选原因C（来源：团队推测）
  │
  ├─ Why2: 为什么A？（对选中原因继续追问）
  │  └─ ...
  │
  ├─ Why3-5: 继续...
  │
  └─ 终止条件：
     □ 找到了可行动的根因 → 进入Phase 3
     □ 超出产品可控范围 → 标记约束，进入Phase 3
     □ 逻辑循环 → 回退重新定义现象
```

### Phase 3：验证与输出（30min）

| 步骤 | 动作 | 输出 |
|---|---|---|
| 3.1 | 交叉验证：用不同数据源验证根因 | 验证记录 |
| 3.2 | 多路径检查：同一现象是否有另一条5Why路径 | 替代根因（如有） |
| 3.3 | 写根因清单 | 根因+置信度+对策方向 |
| 3.4 | 确认根因是否在产品可控范围内 | 在范围内→设计对策；超出范围→标约束 |

### 输出模板

```markdown
## 5Why分析记录

### 分析对象
现象：[具体现象描述]
数据来源：[用户原话/行为数据/工单号]

### 追溯链
现象 → Why1(A) → Why2(B) → Why3(C) → Why4(D) → 根因(E)

### 多路径验证
| 路径 | 终点 | 置信度 | 是否可行动 |
|---|---|---|---|
| 主路径(A→B→C→D→E) | ... | 🔍高/📚中/⚠️低 | 是/否 |
| 替代路径(A→F→G) | ... | 📚中 | 是/否 |

### 根因清单
| 根因ID | 根因描述 | 置信度 | 可行动性 | 对策方向 |
|---|---|---|---|---|
| RC-001 | ... | 🔍高 | 是 | ... |

### 下一步
→ 对策方向进入真伪与价值判断(D-02.03)
```

## 输出格式

Markdown格式的5Why分析记录，存入项目知识库。
