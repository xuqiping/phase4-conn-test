# WordPress五年Feature项目——范围蔓延的灾难案例

## 基本信息

| 字段 | 内容 |
|---|---|
| 时间 | 2020-2025 |
| 主角 | Automattic（WordPress母公司）/ Matt Mullenweg |
| 性质 | 范围失控导致项目极度延期的教科书级案例 |

## 背景

WordPress Gutenberg编辑器计划从经典编辑器升级为区块编辑器，原本是一个"编辑器升级"项目，但：
- Mullenweg把项目范围不断扩大——从编辑器→全站编辑→区块主题→协作编辑
- 项目时间从最初的1~2年扩展到5年仍未完成全部愿景
- 社区反馈两极分化——部分用户拥抱区块编辑，部分用户死守经典编辑器 `[来源:WordPress官方博客+社区讨论 | 置信度:📚中 | 2020-2025]`

## 范围蔓延路径

```
阶段1：Gutenberg编辑器（2017-2018）
  → 核心范围：可视化区块编辑器替代经典编辑器
  → 结果：5.0版本发布，社区争议大但基础交付完成

阶段2：全站编辑FSE（2019-2022）
  → 范围扩张：从"编辑文章"扩展到"编辑全站"
  → 问题：概念复杂度飙升，用户学习曲线陡峭

阶段3：区块主题+协作编辑（2022-2025+）
  → 再扩张：主题系统重构+实时多人协作
  → 问题：原团队已疲惫，社区情绪从"期待"变为"焦虑"
```

**核心失误**：没有定义"Gutenberg 1.0的成功标准"——"编辑器可用"就发布，还是"全站可用"才发布？没有清晰的DoD导致范围无限扩张。

## 教训启示

1. **没有DoD的项目没有终点**：如果"完成"的定义不清晰，"加功能"的诱惑会一直存在——项目永远做不完
2. **愿景≠范围**：Mullenweg的愿景是好的（全站区块化），但应该按"小步交付"切分——每个阶段有独立的DoD和交付价值
3. **社区/用户参与是范围控制的外部力量**：开源项目的用户反馈是"天然的范围控制机制"——如果更早更认真地响应"我只需要编辑器好用"的反馈，会避免很多范围蔓延
4. **沉没成本是范围蔓延的帮凶**：已经投入3年了→"再做1年就能完成全站编辑"→再投入→又发现新范围——沉没成本让决策者难以下决心"砍范围收工"
