# Data Governance Workflow

## Purpose

基于数据治理知识体系，为用户提供数据治理体系建设（DAMA-DMBOK+DCMM五级成熟度）、数据标准代码化（Data Contract/Standard as Code）、数据血缘追踪（OpenLineage/Neo4j）、数据质量管控（六维模型/AI驱动规则）、元数据管理（DataHub/主动元数据）及治理组织架构（CDO→Data Owner→Steward→DQ Council）的技术方案支持。覆盖AI训练数据血缘21.9亿美元市场、Data Observability五支柱、LLM驱动主动元数据感知等2026核心演进趋势。

## Prerequisites

- 用户已明确数据治理场景或问题
- 知识库文件 `06_大数据处理与BI.md` 及子目录文件可访问

## Steps

### Step 1: 识别数据治理需求场景

**Goal**: 明确用户的数据治理需求类型、治理成熟度和关键痛点
**Completion criterion**: 已确定场景标签、治理成熟度、数据资产规模和合规要求

1. 读取用户消息，提取以下信息：
   - 场景类型：治理体系搭建 / 数据标准制定 / 数据血缘建设 / 数据质量提升 / 元数据管理 / 治理组织设计 / AI数据治理
   - 治理成熟度（参考DCMM五级）：L1初始级（无治理） / L2受管理级（部分部门有规范） / L3稳健级（企业级数据管理制度） / L4量化管理级（数据质量度量+持续改进） / L5优化级（AI驱动自动治理）
   - 数据资产规模：数据源数量（个/十/百/千）、数据量（TB/PB）、数据消费者（业务部门数/分析师数/数据产品数）
   - 关键痛点：数据找不到（数据资产目录缺失） / 数据不敢用（质量不可信） / 数据不一致（同名不同义） / 变更影响不明（血缘缺失） / 合规风险（审计追溯困难） / AI训练数据问题（偏见/毒性/版权）
   - 合规要求：等保 / 数据安全法 / 个人信息保护法 / 行业监管（金融/医疗/电信） / 信创要求
   - 现有工具：是否有数据目录/血缘工具/质量工具/元数据平台

2. 对照知识库中的核心教训初步判断：
   - 80% BI项目失败根因是跳过治理直接搞AI BI → 治理是BI和AI的前置条件
   - 数据找不到 → 元数据管理+数据资产目录（DataHub）
   - 同名不同义 → 语义层独立化（dbt Semantic Layer/Cube.dev）+ 数据标准
   - 质量不可信 → 六维数据质量模型+AI驱动规则+Data Observability
   - AI训练数据问题 → AI训练数据血缘+六维质量评估+去偏见处理

3. 如有信息缺失，向用户追问不超过2个澄清问题。

### Step 2: 输出数据治理方案

**Goal**: 产出针对性的数据治理体系建设或优化方案
**Completion criterion**: 输出包含治理框架设计、技术工具选型、实施路径、组织保障

根据Step 1确定的场景，按以下分支处理：

**分支A — 治理体系整体搭建**：
1. 输出治理框架设计（基于DAMA-DMBOK+DCMM）：
   - 战略层：数据战略对齐业务战略、数据资产估值模型、数据治理ROI度量
   - 管理层：数据治理委员会（CDO/CTO/业务VP组成）、数据Owner制度（每个核心业务域指定Owner）、数据Steward（执行层 steward 负责日常治理）、数据质量委员会（DQ Council定期评审）
   - 制度层：数据分类分级制度（公开/内部/机密/绝密）、数据质量管理制度、元数据管理制度、数据安全管理制度、数据生命周期管理制度
   - 技术层：数据标准平台、数据质量平台、数据血缘平台、元数据管理平台、数据资产目录
2. 给出DCMM五级成熟度评估模型：
   - L1→L2：制定基本的数据管理制度、数据目录初步建立、数据质量手工检查
   - L2→L3：企业级数据治理组织成立、数据标准统一制定、数据质量自动监控、元数据自动采集
   - L3→L4：数据质量量化度量（六维指标Dashboard）、数据血缘全链路追踪、变更影响分析自动化、数据资产价值评估
   - L4→L5：AI驱动数据质量规则生成、主动元数据感知（LLM自动理解数据语义）、数据治理自愈（自动修复数据问题）、数据产品化（数据API/数据服务目录）
3. 输出实施路线图（通常12-24个月）：
   - Phase 1（1-3月）：治理组织搭建、数据资产盘点（盘点所有数据源/表/字段/业务含义）、痛点梳理（Top 10数据问题）、Quick Win（解决最痛的1-2个问题）
   - Phase 2（4-9月）：数据标准制定（核心业务域指标口径统一）、数据质量规则上线（六维模型）、元数据平台部署、血缘关系采集
   - Phase 3（10-15月）：数据资产目录上线（业务人员可自助找数据）、数据质量Dashboard、血缘影响分析、变更管理流程
   - Phase 4（16-24月）：AI驱动治理（自动规则生成/主动元数据/智能推荐）、数据产品化、治理成熟度评估（DCMM L4+）
4. 附关键成功因素：高层支持（CDO汇报CEO）、业务驱动（从业务痛点出发而非IT视角）、小步快跑（每个阶段有可见成果）、度量驱动（数据质量KPI纳入部门考核）。

**分支B — 数据标准与代码化**：
1. 输出数据标准体系：
   - 业务术语标准：统一业务词汇表（如"活跃用户"精确定义：DAU=当日启动App的去重用户数，MAU=最近30天启动App的去重用户数）、术语Owner、变更流程
   - 指标口径标准：原子指标（不可拆分，如订单金额=商品金额+运费-优惠）+ 派生指标（原子指标+时间周期+修饰词，如近7天GMV=Sum(订单金额) WHERE 订单日期≥Today-7）+ 复合指标（派生指标运算，如客单价=GMV/订单数）
   - 数据元标准：字段命名规范（词根法：user_id, order_amount, create_time）、数据类型规范（金额Decimal(18,4)、时间Timestamp）、值域规范（性别：0=未知/1=男/2=女）
   - 参考标准：DAMA-DMBOK国际框架、DCMM国标（GB/T 36073-2018）、行业数据模型（FS-LDM金融逻辑数据模型、OneData阿里体系）
2. 给出Data Contract（标准代码化）实施：
   - 概念：将数据标准以代码形式定义（JSON/YAML），嵌入数据管道（Pipeline as Code），实现标准即代码（Standard as Code）
   - 技术实现：dbt tests（字段类型/非空/唯一/外键/自定义SQL校验）、Great Expectations（Python API/CLI/Airflow集成）、Deequ（Spark原生、Amazon开源）、Soda Core（声明式数据质量检查）
   - 集成位置：数据入湖/入仓时自动校验（Airflow DAG中嵌入校验Task）、不合格数据进入隔离区（Quarantine Zone）、告警通知（Slack/邮件/工单）
   - 版本管理：Data Contract版本化（Git管理）、变更审批流程（PR Review+数据Owner审批）、向后兼容性检查
3. 输出标准落地检查清单：
   - 字段命名符合规范（命名规则+词根校验）
   - 数据类型正确（金额不存Float、时间有时区、ID不为空）
   - 枚举值在范围内（状态码/性别/地区编码）
   - 业务术语与词汇表一致（"GMV"在所有报表中口径相同）
   - 指标定义可追溯（每个派生指标可追溯到原子指标和计算逻辑）

**分支C — 数据血缘与影响分析**：
1. 输出血缘采集技术选型：
   - OpenLineage（推荐）：现代数据栈事实标准、Marquez后端、REST API推送、支持Spark/Flink/dbt/Airflow/Great Expectations等20+集成、JSON格式血缘事件、开源免费
   - Apache Atlas：Hadoop生态原生、与Hive/HBase/Kafka深度集成、类型系统灵活、但社区活跃度下降、UI体验一般
   - DataHub（血缘是元数据的一部分）：与OpenLineage集成（OpenLineage事件→DataHub ingestion）、血缘+元数据+数据质量一体化、LinkedIn开源、社区活跃
   - 自研方案：SQL解析（基于ANTLR/Tree-sitter提取SELECT/FROM/JOIN/INSERT）、日志分析（从ETL日志中提取表依赖）、元数据扫描（从Hive Metastore/数据库系统表提取关系）
   - 选型建议：新建平台→OpenLineage+DataHub组合；已有Atlas→评估迁移成本；简单场景→自研SQL解析
2. 给出血缘应用场景：
   - 影响分析：字段变更前自动分析影响范围（哪些报表/哪些下游表/哪些数据产品受影响）、变更风险评估、通知受影响Owner
   - 根因分析：数据质量问题追溯（从报表异常→追溯ETL任务→追溯上游数据源→定位问题根因）、缩短MTTR（从小时到天缩短到分钟）
   - 合规审计：数据全生命周期追踪（谁生产/谁消费/谁修改/何时删除）、GDPR/个人信息保护法删除请求追溯（找到所有副本和派生数据）
   - AI训练数据血缘（21.9亿美元新市场）：追踪训练数据来源（原始数据→清洗→标注→训练集→模型版本）、版权追溯（训练数据版权归属）、偏见检测（训练数据人口统计分布）
3. 输出血缘可视化设计：
   - 图数据库选型：Neo4j（原生图存储、Cypher查询、百万节点可视化流畅、商业版功能丰富）、JanusGraph（开源、分布式、Gremlin查询、适合超大规模）、ArangoDB（多模型、AQL查询、文档+图混合）
   - 可视化设计：节点（表/字段/报表/数据产品）、边（ETL依赖/查询引用/模型训练消费）、过滤（按业务域/按时间范围/按数据敏感度）、路径分析（两节点间所有路径/最短路径）
   - 交互功能：点击节点查看详情（元数据/质量评分/Owner信息）、双击下钻（表→字段级血缘）、右键操作（申请访问/发起变更/查看质量报告）
4. 附血缘质量保障：血缘完整性（覆盖率目标>95%）、血缘准确性（抽样验证、人工核对）、血缘时效性（实时采集 vs 定时扫描）、血缘粒度（表级→字段级→表达式级）。

**分支D — 数据质量管控**：
1. 输出六维数据质量模型：
   - 完整性（Completeness）：必填字段非空率、记录缺失率、外键关联完整率
   - 准确性（Accuracy）：与权威数据源对比一致性、业务规则校验（如订单金额=商品金额+运费-优惠）、数值范围合理性（如年龄0-150）
   - 一致性（Consistency）：跨系统同一实体数据一致（如用户手机号在CRM和订单系统一致）、编码一致性（如地区编码统一使用国标）、时间一致性（如时区统一为UTC+8）
   - 唯一性（Uniqueness）：主键唯一率、业务键去重（如同一用户多条记录）、重复数据处理策略（Merge/Pick First/Flag）
   - 及时性（Timeliness）：数据延迟（从产生到可用的时间）、刷新频率符合SLA（如实时数据延迟<5分钟、T+1数据次日8点前可用）、陈旧数据标识（如超过30天未更新的数据标记为"可能过期"）
   - 有效性（Validity）：格式有效性（邮箱/手机号/身份证号正则校验）、值域有效性（枚举值在范围内）、类型有效性（数值字段不含字母）
2. 给出数据质量规则管理：
   - AI驱动规则生成：LLM分析字段名+样本数据→自动生成质量规则（如字段名为"email"→自动添加邮箱格式校验规则）、规则推荐置信度评分、人工审核确认
   - 规则分类：静态规则（固定阈值，如非空率>99%）、动态规则（基于历史统计分布，如均值±3σ）、关联规则（跨字段校验，如订单日期≥用户注册日期）
   - 规则执行：Airflow DAG嵌入质量检查Task、Spark/Deequ批量校验、Flink实时校验（数据入湖时实时拦截不合格数据）
3. 输出Data Observability五支柱：
   - 新鲜度（Freshness）：数据最后更新时间监控、延迟告警（如超过预期30分钟未更新）
   - 容量（Volume）：数据量异常监控（突增/突降）、与历史同期对比（如本周订单量仅为上周的50%）
   - 分布（Distribution）：字段值分布变化（如性别比例突然从50:50变为90:10）、异常值检测（Isolation Forest/LOF）
   - Schema（Schema）：表结构变更监控（字段新增/删除/类型变更）、变更审批流程、下游影响通知
   - 血缘（Lineage）：上下游健康状态传递（上游出问题→自动标记下游表"可能受影响"）、数据质量评分沿血缘传播
   - 工具选型：Monte Carlo（商业）、Metaplane（商业）、Bigeye（商业）、Soda（开源）、Great Expectations（开源）
4. 附质量改进闭环：发现问题→根因分析（血缘追溯）→制定修复方案→修复数据（回填/重跑/补丁）→验证修复→更新规则防止复发→知识沉淀（问题Case库）。

**分支E — 元数据管理与数据资产目录**：
1. 输出元数据管理架构：
   - 技术元数据：表结构（字段名/类型/注释）、存储信息（路径/格式/压缩/分桶）、计算信息（ETL任务/调度频率/Owner）、血缘关系
   - 业务元数据：业务含义（字段业务解释）、业务Owner、数据敏感度（公开/内部/机密）、数据质量评分、使用统计（查询次数/使用者）
   - 操作元数据：任务执行日志（开始时间/结束时间/状态/错误信息）、资源消耗（CPU/内存/IO）、告警记录
   - 管理元数据：数据分类分级标签、合规要求（等保/PIPL/GDPR）、生命周期策略（保留期限/归档规则/删除策略）
2. 给出元数据平台选型：
   - DataHub（LinkedIn开源，推荐）：元数据图谱、数据资产目录、数据质量集成、数据血缘可视化、AI主动感知、REST API丰富、社区活跃、2026开源首选
   - Apache Atlas（Hadoop生态）：与Hive/HBase/Kafka原生集成、标签分类系统、安全与血缘、但UI和生态活跃度弱于DataHub
   - Collibra（商业）：企业级元数据管理、数据字典、数据治理工作流、数据市场、适合大型金融/电信企业
   - Amundsen（Lyft开源）：数据发现优先、搜索体验好、与Presto/Hive集成、但功能较单一
   - 选型建议：新建平台+现代数据栈→DataHub；已有Atlas+重度Hadoop生态→Atlas+DataHub混合；大型金融合规严格→Collibra
3. 输出主动元数据（Active Metadata）实施：
   - 概念：元数据不再被动扫描采集，而是主动感知数据变化、主动推荐、主动治理
   - LLM驱动：字段名/样本数据→LLM自动推断业务含义→自动补充元数据→人工确认；相似字段自动推荐统一口径；数据表自动分类（订单/用户/商品/日志）
   - 自动化触发：Schema变更→自动评估影响→自动通知Owner→自动更新血缘；数据质量下降→自动创建JIRA工单→自动推荐修复方案
   - 智能推荐：基于查询历史推荐相关数据表（"查询订单表的用户也查询了用户表和商品表"）；基于血缘推荐上下游数据（"你可能还需要了解这个表的来源"）
4. 附数据资产目录运营：
   - 搜索优化：全文检索（表名/字段名/业务描述/标签）、自动补全、同义词（"DAU"和"日活"）、搜索排名（质量评分高/使用频率高/血缘中心度高优先）
   - 用户分层：数据工程师（技术元数据为主）、数据分析师（业务元数据+血缘+质量）、业务人员（简单搜索+报表推荐）、数据管理员（治理Dashboard+审核工作流）
   - 资产价值评估：数据使用频率（查询次数×用户数）、数据质量评分、数据更新频率、数据血缘下游影响范围、业务价值（支撑多少报表/多少决策/多少收入）

将结果保存到 `output/data_governance.md` 或直接在对话中呈现。

## Post-Workflow

1. 记录完成状态到 `task/current_task.md`。
2. 如需深入某一具体技术（如"DataHub主动元数据LLM集成配置"、"OpenLineage+Marquez血缘采集Spark集成"），在当前 Agent 内继续追问并输出。
