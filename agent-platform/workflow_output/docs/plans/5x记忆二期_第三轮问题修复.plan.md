**目标**：项目通道（共享总结 + 成员个人压缩 toPersonal）按 direction 生成，前端徽标（已就绪）能显示「输入/输出」。

**动作（伪代码）**：
1. `V102__memory_project_entry_direction.sql`：`memory_project_entries` 加 `direction VARCHAR(8) CHECK IN ('INPUT','OUTPUT','BOTH') NOT NULL DEFAULT 'BOTH'`；回填推导——有 `source_turn_id` 无 `source_turn_input_id` → OUTPUT；只有 input → INPUT；都有或都无（文件记忆/综合蒸馏）→ BOTH。
2. `MemoryRoutingService` 落条目时按蒸馏源写实际 direction（不再全 BOTH）。
3. `MemoryConsolidationService.summarizeProjectScope`：读 `req.direction`；非 BOTH 时条目过滤 `direction = req.direction OR direction = 'BOTH'`（综合条目双计入）；按 tag 分组不变；`writeProjectSummaryAndCoverage(..., direction, ...)` 参数化，替换 :321 硬编码 "BOTH"。请求不传/BOTH → 行为与现在完全一致（老调用零回归）。
4. toPersonal 成员通道共用该写入点，自动获益。
5. 防重复膨胀：BOTH 条目会进 INPUT 与 OUTPUT 两份总结——coverage 唯一键 4 列含 summary_id，不冲突；总结内容里同一 BOTH 条目只出现一次（按 summary 分组天然隔离）。

**涉及文件**：V102 sql、`MemoryProjectEntry.java`、`MemoryRoutingService.java`、`MemoryConsolidationService.java`、单测 ×3（三方向过滤 / BOTH 双计入 / 默认兼容）。

**动作（伪代码）**：

4. 全量回复后的异步收录照旧（同项目幂等去重已有），不重复收录。

## 技术坑点预判

1. **V101 配对键**：join 键必须与写入侧配对逻辑逐字一致，先读代码再写 SQL；回填前先 count 评估量级。
2. **direction 过滤**：BOTH 条目双计入是设计（综合内容两向都该有），但总结生成 token 翻倍——LLM 调用按 tag 组数×方向数增长，重试预算别炸。
3. **SSE 协议**：确认回复也走既有 SSE 帧结构（前端复用渲染），别旁路纯 JSON 破坏流式协议。
4. **死循环防呆**：确认后的全量回复链路必须带 flag 跳过 quickCheck，否则再命中再确认无限套娃。
5. **vitest/后端测试目录**：chat 套件 372+ 绿是回归基线，每 chunk 跑全量。
