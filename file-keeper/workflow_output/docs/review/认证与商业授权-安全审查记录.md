## 一、结论速览

当前授权模式（尤其是**离线授权模式**）存在**可被实际破解的严重风险**，其中一类是密码学选型层面的**根本性缺陷**，非几行代码可修复。

- **2 个 P0**（根本性 / 设计层）：对称签名密钥必然外泄可伪造 token；JWT secret 默认兜底值形同虚设。
- **2 个 P1**（实现缺口 / 高危）：token 内嵌绝对过期时间被解析但未校验，授权可无限续期；files/processes/clipboard 特权命令在 Rust 侧无二次校验，门禁纯前端。
- **2 个 P2**（机制薄弱）：设备身份全客户端生成可刷试用；系统时钟回拨 + JS `Date.now()` 过期判定。

**底线判断**：当前状态接近「挡君子不挡小人」。最该先动的是 **P0-1（换非对称签名）** 与 **P1-2（特权命令加 Rust 侧校验）**。

## 三、详细发现

### P0-1 · HMAC 对称签名，密钥必然驻留客户端（根本性缺陷）

**代码定位**
- 客户端验签：`src-tauri/src/commands/auth.rs:118-135` `verify_offline_token_signature()`，用 `jwt_secret()` 取 secret 做 HMAC 验签。
- 服务端签名：`server/.../authorization/service/OfflineTokenSigner.java:20-24` `sign()`，同一 secret、同一 `HmacSHA256`。
- 算法：HMAC-SHA256（**对称**），payload 形如 `userId|deviceId|offlineUsableUntil|allowedModules|hmac`。

**为什么是根本性缺陷**
离线校验必须在无网络下验证签名。HMAC 是对称算法 —— **客户端要验签就必须持有 secret**。而客户端跑在用户自己的机器上，用户对二进制与运行环境有完全控制权。因此：
1. 攻击者从二进制 / 进程环境变量 / 启动包装脚本里 dump 出 secret；
2. 用同一 `OfflineTokenSigner` 逻辑自己签发任意 token —— 任意 userId、deviceId、模块、有效期。

**结论**：只要离线校验走 HMAC，密钥外泄就是**结构性必然**，签名校验这道防线对逆向者形同虚设。模块列表虽被签名覆盖（攻击者加不了新模块），但可任意伪造「自己原本就有的模块 + 任意有效期」。

**修复方向**：改用**非对称签名（Ed25519 / ES256 / RSA-PSS）**。服务端用私钥签（私钥永不离开服务器），客户端只内嵌**公钥**验签。公钥泄露也签不出 token，从根本上解决。详见 plan.md。

---

### P0-2 · JWT secret 默认兜底值硬编码明文，服务端默认空串

**代码定位**
- 客户端：`src-tauri/src/commands/auth.rs:183-186`
  ```rust
  fn jwt_secret() -> String {
      std::env::var("FILE_KEEPER_JWT_SECRET")
          .unwrap_or_else(|_| "file-keeper-local-dev-jwt-secret-at-least-32-bytes".to_string())
  }
  ```
  该默认值**明文写在源码**，且被单测 `auth.rs:246` 当已知值直接使用，等于公开。
- 服务端：`server/src/main/resources/application.yml:40` `secret: ${FILE_KEEPER_JWT_SECRET:}` —— 未设时默认**空串**。

**攻击场景**
- 生产打包/分发时若忘了设 `FILE_KEEPER_JWT_SECRET`：客户端回退到公开的 dev 字符串，攻击者无需逆向即可伪造 token（把自己的客户端进程环境变量设为该公开串，签出来的 token 自己就接受）。
- 即便设了，也回到 P0-1：secret 终究在客户端，只是「提取成本」问题。

**修复方向**：①生产强制校验 secret 已设置且非默认值，缺失则拒绝启动；②随 P0-1 一并切非对称后，客户端不再需要任何 secret，本问题自然消失。

### P1-1 · 绝对过期时间被解析却未校验 → 授权可无限续期

**代码定位**
- `src-tauri/src/commands/auth.rs:146`：`let _offline_usable_until_epoch_milli = parts[2]...` —— 注意前缀下划线，**变量解析后从未使用**。
- 实际过期逻辑在 `auth.rs:50`：
  ```rust
  if set_at.elapsed() > Duration::from_secs(offline_duration_secs.max(0) as u64) { return false; }
  ```
  其中 `set_at` = 上次调用 `set_offline_token` 的时刻（`auth.rs:79` 每次重置为 `Instant::now()`），`offline_duration_secs` = **前端传入**（`commercialAuthStore.ts:173` 在 JS 里算的 `(until-now)/1000`）。

**攻击场景（可复现）**
token 签名只覆盖模块列表与那个被忽略的时间戳，**不覆盖** `offline_seconds`。攻击者只要拿到过一次合法 token（如 7 天试用、或已购但被退订），反复调用：
```js
invoke('set_offline_token', { token: <旧token>, offlineSeconds: 999999999 })
```
`set_at` 每次重置为 now、duration 巨大 → **已签发授权永久有效**。被设计用来防这一点的绝对过期时间，恰恰被忽略了。

**修复方向**：在 payload 内放绝对 `not_after`，签名覆盖「签发时刻 + 有效期」，Rust 侧用 `now > not_after` 判定，且**不允许把 duration 作为外部参数喂入**（由 token 自身决定有效期）。

### P1-2 · files/processes/clipboard 特权命令 Rust 侧无二次校验

**代码定位**
- 全仓 Rust 侧调用 `is_module_allowed` 做拦截的**只有** `src-tauri/src/commands/work_report.rs:31/94/136` 三处（work-report 模块）。
- `files` / `processes` / `clipboard` 门禁全在 `src/App.vue:860-861` `canUseTab() → isModuleAllowed()`，仅控制 Tab 显隐，纯 UI 层。

**攻击场景**
杀进程、截图/OCR、剪贴板监听这些真正的特权 Tauri 命令，Rust 侧没有任何授权检查。攻击者绕过前端、直接 `invoke('kill_process', ...)` 即可。**进程 / 剪贴板 / 截图模块当前基本等于没上锁。**

> 此项与 [06-认证与商业授权.feature-map.md 第 8 节 TODO 第 3 项](../feature-map/06-认证与商业授权.feature-map.md) 已记录的缺口一致，本审查给出可利用性确认。

**修复方向**：把 work_report 的 Rust 侧拦截模式推广到杀进程、截图/OCR、剪贴板监听全部特权命令。性价比最高的一步。

### P2-1 · 设备身份全客户端生成

**代码定位 / 现象**（见 feature-map 6.7）
`deviceId = crypto.randomUUID()`、`fingerprintHash` 基于浏览器环境特征，持久化于 `file-keeper-auth.json` 并在 localStorage 备份「防清除」。

**问题**：deviceId 客户端随机生成、客户端持久化、客户端可任意篡改；所谓「防清除」的 localStorage 备份删两个键即失效。→ 7 天匿名全功能试用可无限刷新（换 deviceId 即可），`deviceLimit` 设备上限也能刷 deviceId 绕过。

**修复方向**：设备指纹改服务端签发（客户端只持有），或结合机器硬件特征在服务端计算；匿名试用绑定到难以复制的标识并服务端记录试用历史。

---

### P2-2 · 系统时钟回拨 + JS 过期判定

**代码定位**：`src/stores/commercialAuthStore.ts:211-224`（`getUsableClientAuthorization` / `hasValidOfflineClientAuthorization`）用 `Date.now()`（墙上时钟）。

**问题**：改系统时间即可回拨延长；配合 P1-1 的重注入，客户端几乎无法「承认过期」。Rust 侧 `Instant`（单调时钟）稍好，但只挡 `set_at` 之后，挡不住组合拳。

**修复方向**：关键过期判定下沉 Rust 单调时钟 + 服务端在线复核（能用网时强制走一次）。

## 四、做对的地方（客观记录）

- `auth.rs:172-181` 签名比较用常量时间 `constant_time_eq`，防侧信道，加分项。
- token 的**模块列表被签名覆盖**，攻击者无法凭空给自己加模块（只能续期 / 伪造同模块），部分限制了爆破面。
- `work_report.rs` 做了 Rust 侧二次校验，是正确范例，只是尚未推广。

## 五、加固建议（按优先级）

### 根治（必须，否则离线模式防不住逆向者）
1. **对称 HMAC → 非对称签名（Ed25519 / RSA-PSS / ES256）**。服务端私钥签、客户端内嵌公钥验签 —— 解决 P0-1（[plan.md Chunk 1](../plans/安全加固-离线授权与门禁.plan.md)）。
2. **真正校验 token 内绝对过期时间**，签名覆盖有效期，客户端不允许外部喂入 duration —— 解决 P1-1（plan.md Chunk 1）。

### 短期（显著抬高门槛）
3. 生产强制校验 `FILE_KEEPER_JWT_SECRET` 已设且非默认值，缺失拒绝启动 —— 修 P0-2。
4. **work_report 的 Rust 拦截模式推广到杀进程 / 截图 OCR / 剪贴板监听全部特权命令** —— 修 P1-2（plan.md Chunk 2，性价比最高）。
5. 设备指纹改服务端签发，匿名试用绑定难复制标识 —— 修 P2-1。

### 纵深防御（对「patch 二进制跳过校验」终极攻击）
6. 即便换非对称，攻击者仍可改二进制让 `is_module_allowed` 恒返回 true。纯软件无法 100% 防，只能：关键校验下沉编译后 Rust（非易改 JS）、校验逻辑做混淆 / 完整性自校验、高敏操作能用网时强制服务端在线复核。**建议文档如实标注为「延缓型防护」而非「绝对防护」。**
