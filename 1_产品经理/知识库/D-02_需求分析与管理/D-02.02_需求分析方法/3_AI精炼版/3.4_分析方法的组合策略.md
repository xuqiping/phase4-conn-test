# 3.4 分析方法的组合策略

## 方法组合决策树

```
需求场景判断
├── "用户明确说了一个问题"
│   └── 5Why根因分析 → 找到根因 → 用户故事映射组织响应方案
├── "需求很多但零散"
│   └── 用户故事映射 → 全景视图 → 依赖分析 → 冲突检测
├── "需求间关系不清"
│   └── 依赖矩阵 → 识别关键路径 → 需求分解
├── "B端复杂业务流"
│   └── 流程图+状态图 → 5Why → 故事映射
├── "新市场/0→1，需求模糊"
│   └── JTBD → 5Why → 故事映射（控制MVP范围）
└── "AI辅助场景"
    └── AI初分析（聚类+遗漏检查）→ 人工5Why/故事映射精分析
```

## B端 vs C端分析方法差异

| 维度 | C端需求分析 | B端需求分析 |
|---|---|---|
| **优先方法** | 用户故事映射+5Why | 流程图+状态图+依赖分析 |
| **深度** | 表层→2-3层即够 | 需穿透到组织/流程/权限 |
| **关注点** | 用户体验+情感需求 | 业务闭环+流程合规+数据一致 |
| **常见遗漏** | 异常路径、空状态 | 权限矩阵、数据流转、多角色协作 |
| **需求分解粒度** | Story级即可 | 需分解到任务级+验收标准 |
| **依赖复杂度** | 低-中 | 高（跨部门/跨系统/跨角色） |
| **建模工具偏好** | 故事地图 > 流程图 | 流程图+状态图 > 故事地图 |

## 分析深度控制

| 产品阶段 | 推荐深度 | 过度分析信号 | 分析不足信号 |
|---|---|---|---|
| **探索期** | L1+关键需求L2 | 每个需求都做5Why+故事地图 | 只列需求不分析关联 |
| **成长期** | L2+依赖分析 | 画出100个故事才敢动手 | 不做依赖分析导致串行延期 |
| **成熟期** | L2+L3+约束分析 | 过度建模，3周分析2周开发 | 忽略非功能需求 |

> **过度分析是需求分析的另一大病**——分析不是目的，可决策的洞察才是目的。如果一个5Why做了3小时还没出结论，说明问题定义有误。[来源:📚训练知识]

## 分析方法的反模式

| 反模式 | 表现 | 危害 | 正解 |
|---|---|---|---|
| **分析瘫痪** | 每个需求都反复分析不出结论 | 项目永远启动不了 | 设时间盒，2h内出结论 |
| **方法教条主义** | 所有需求必须用同一套方法 | 简单需求过度分析 | 按场景选择方法 |
| **忽视约束** | 只分析用户需求不分析约束 | 需求分析完美但做不了 | 约束分析=需求分析的另一半 |
| **单人分析** | PM一个人关门分析 | 视角单一，盲区多 | 至少2人交叉分析+技术评审 |
| **一次分析定终身** | 需求分析做完不改 | 现实变化后分析结论失效 | 需求分析是迭代的，不是一次性的 |
