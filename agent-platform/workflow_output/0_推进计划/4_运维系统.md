# 顶级运维系统 · 规划设计

> 版本：v1.0 · 2026-08-09
> 关联文档：[3_日志系统.md](3_日志系统.md)（共用 Grafana/告警通道）、[5_安全体系.md](5_安全体系.md)、[2_数据看板.md](2_数据看板.md)（业务侧看板，本文是系统侧）、[99-部署要求](../../项目工程文档/项目功能介绍/速查表/99-部署要求.md)
> 部署约束：Windows Server 单机，无 K8s，无专职运维 → 选型原则：**单二进制、低资源、少组件、自动化优先**。

---

## 一、目标：四个「可」

| 维度 | 现状 | 目标 |
|---|---|---|
| **可观测** | 只有日志文件，无指标 | JVM/接口/LLM/工作流/队列指标全量采集，Grafana 一屏看清系统健康状况 |
| **可告警** | 出问题靠用户反馈 | 宕机/错误率/磁盘/LLM 配额异常 → 5 分钟内钉钉+邮件到人 |
| **可恢复** | 无备份策略文档 | PG/文件/Redis 定时备份 + 异地副本 + **每季度恢复演练**，RTO≤1h、RPO≤24h |
| **可发布** | 手工打包拷贝 | 标准化发布/回滚流程 + 健康检查门禁，发布事故 10 分钟回滚 |

## 二、总体架构

```
                 ┌──────────────── Grafana（看板 + 告警统一入口）────────────────┐
                 │                                                              │
  Prometheus ◄───┤  /actuator/prometheus (Java)   windows_exporter (主机)        │
  (指标库)       │  sidecar /metrics (Python)     PG exporter(可选,或用SQL采集)   │
                 │                                                              │
  VictoriaLogs ──┤  日志检索（见 3_日志系统.md P2）                               │
                 │                                                              │
  Alertmanager ──┴──► 钉钉 webhook / 邮件 SMTP ──► 运维负责人                    │
```

**选型结论：**
- **Prometheus + Grafana + Alertmanager**：事实标准，Windows 均有原生单二进制，三者合计内存 <500MB。
- **windows_exporter**：采集 CPU/内存/磁盘/网络（微软官方生态）。
- **不引入** K8s/Zabbix/Nightingale——单机场景过度设计。
- 业务看板（积分消耗、模型成本）已在 [2_数据看板.md](2_数据看板.md) 规划，本文不重复，只做**系统/技术层**看板。

## 三、分阶段实施

### P0 · 指标采集 + 健康检查（纯代码） — 预估 3~4 人日

| # | 事项 | 落点 |
|---|---|---|
| 1 | **Actuator + Prometheus registry** | `pom.xml` 加 `spring-boot-starter-actuator` + `micrometer-registry-prometheus`；`application.yml` 暴露 `health,info,prometheus` 三个端点；**端点仅内网/localhost 可达**（Nginx 不反代 `/actuator`，防信息泄露） |
| 2 | **JVM/HTTP 基础指标** | Actuator 自带：heap/GC/线程池/Tomcat 连接数/HTTP QPS+延迟直方图（`management.metrics.web.server.request.autotime.enabled`） |
| 3 | **业务自定义指标**（本项目核心） | `common/metrics/BizMetrics.java` 统一注册，全部低基数 tag： |
| | ① LLM：`llm.calls.total{provider,model,result}` / `llm.tokens.total{provider,model,direction=in|out}` / `llm.latency` 直方图 | `llm/LlmGateway.java` 统一埋点（所有调用都过这个咽喉） |
| | ② 工作流：`workflow.executions.total{status}` / `workflow.duration` | `execution/service/ExecutionLogService.java` |
| | ③ RAG 索引队列：`knowledge.index.queue.depth` Gauge / `indexed.total{result}` | `knowledge/service/IndexJobWorker.java`（治「5s 轮询不可见」） |
| | ④ 记忆管线：`memory.pipeline.duration` / `memory.incidents.total` | `chat/service/MemoryService.java`（recordIncident 处） |
| | ⑤ 登录：`auth.login.total{result=success|fail}` / 注册限流触发数 | `auth/service/AuthService.java` |
| 4 | **sidecar 指标** | FastAPI 加 `prometheus-fastapi-instrumentator`：图执行次数/耗时/节点失败率 |
| 5 | **健康检查聚合** | `/actuator/health` 已含 PG/Redis；新增 sidecar HealthIndicator（HTTP 探活）+ 磁盘水位 indicator |

**红线**：userId/traceId/agentId 等高基数值**永远不进 metric tag**（时序库会爆炸），只进日志/span。

**P0 验收：** `curl localhost:8080/actuator/prometheus | grep llm_calls_total` 有数据；聊一轮天 → 对应 provider/model 计数 +1。

### P1 · Grafana 看板 + 告警 — 预估 3~4 人日

| # | 事项 |
|---|---|
| 1 | 服务器装 Prometheus / Grafana / Alertmanager / windows_exporter（均 WinSW 注册为 Windows 服务，开机自启） |
| 2 | **四个预置看板**（JSON 存入 `项目工程文档/运维/grafana-dashboards/` 版本化管理）：<br>① 系统总览：CPU/内存/磁盘/JVM heap/GC/Tomcat 线程<br>② 接口质量：QPS、P95/P99 延迟、4xx/5xx 率（按 uri 聚合）<br>③ AI 核心链路：LLM 调用量/成功率/延迟/token 消耗趋势（按 provider+model）、工作流执行成功率、索引队列深度<br>④ 安全态势：登录失败趋势、限流触发、审计写入量（联动安全体系） |
| 3 | **告警规则**（Alertmanager → 钉钉群机器人 webhook + 邮件兜底）： |

| 告警 | 条件 | 级别 |
|---|---|---|
| 服务宕机 | `up==0` 持续 1min | 🔴 critical |
| 磁盘水位 | 磁盘可用 <15% | 🔴 critical |
| 接口 5xx 率 | 5min 内 5xx/QPS >5% | 🟠 warning |
| LLM 失败率 | 单 provider 5min 失败率 >30%（= RB-001 类故障早期信号） | 🟠 warning |
| 索引队列积压 | queue.depth >1000 持续 10min | 🟠 warning |
| 内存 | JVM heap 使用 >85% 持续 10min | 🟡 info |
| 登录爆破 | 单 IP 登录失败 >10 次/min | 🟠 warning（联动安全体系） |

**P1 验收：** 手动 kill 后端进程 → 5 分钟内钉钉群收到 critical 告警；Grafana 四个看板数据齐全。

### P2 · 备份恢复体系 — 预估 2~3 人日

| # | 事项 | 说明 |
|---|---|---|
| 1 | **PG 备份** | 每日 02:00 `pg_dump -Fc`（Windows 计划任务 + bat 脚本），保留 7 天日备 + 4 周周备；备份完成写事件日志，失败触发告警 |
| 2 | **文件备份** | `uploads/` 目录每日 robocopy 增量镜像（删文档清字节策略落地后此目录即为全量用户文件） |
| 3 | **Redis** | 黑名单/缓存类数据可丢，默认 RDB 快照即可，不投入精力 |
| 4 | **异地副本** | 备份目录每周同步到另一台机器/对象存储（没有异地副本的备份 = 没有备份） |
| 5 | **恢复演练** | 每季度一次：在隔离环境从备份恢复 PG + 文件，启动应用抽查数据；演练记录入《运维手册》 |
| 6 | **目标** | RPO ≤ 24h（日备），RTO ≤ 1h |

### P3 · 发布/回滚标准化 + 运维手册 — 预估 2~3 人日

| # | 事项 |
|---|---|
| 1 | **发布脚本化**：`deploy.bat`（停服→备份当前 jar/dist→拷贝新包→起服→轮询 `/actuator/health` 直到 UP→失败自动回滚旧包）；基于现有 [99-部署要求](../../项目工程文档/项目功能介绍/速查表/99-部署要求.md) 傻瓜流程升级 |
| 2 | **Flyway 门禁**：发布脚本先跑 `flyway:repair` 对齐 checksum（本机已踩过坑，见团队备忘），迁移失败即中止发布 |
| 3 | **回滚策略**：jar/dist 保留最近 3 版；DB 迁移坚持「只增不删、向后兼容」原则使旧版代码可跑在新 schema 上 |
| 4 | **《运维手册.md》**（入 `项目工程文档/运维/`）：日常巡检清单（每日：告警清零/磁盘/备份成功标记；每周：错误日志趋势/慢查询；每季：恢复演练）、常见故障 runbook（LLM 超时→查 provider 状态；队列积压→重启 IndexJobWorker；线程打满→grep `io-8080-exec` 速查表 22 已备） |
| 5 | **服务化兜底**：后端 jar / sidecar / VictoriaLogs / Prometheus 等全部 WinSW 注册为服务，崩溃自动重启 + 开机自启 |

## 四、与既有模块的关系

- **数据看板（业务层）**：积分消耗/模型成本/用户活跃 → 见 [2_数据看板.md](2_数据看板.md)，数据源是 PG 业务表；本文的 Grafana 是**系统层**，数据源是 Prometheus。两者互补不重复。
- **执行监控页**：`速查表/13-执行监控` 是用户视角的单条执行追踪；本文是运维视角的系统聚合指标。
