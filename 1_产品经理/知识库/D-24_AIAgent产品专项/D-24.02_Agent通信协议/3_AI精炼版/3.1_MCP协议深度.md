# 3.1 MCP协议深度：从工具调用标准到生产级智能体基础设施

## 一、MCP 是什么：发起与托管

**MCP（Model Context Protocol，模型上下文协议）**：Anthropic 于 2024-11 开源发布的协议，用于标准化"大模型/Agent 与外部工具、数据源、系统"之间的连接，让任何 LLM/Agent 都能用统一接口调用任何工具/数据源——业内类比"AI 界的 USB-C 接口"。2025-12 Anthropic 把 MCP 捐赠给 Linux 基金会旗下新成立的 Agentic AI Foundation，避免单一厂商锁死，由社区共同治理。[来源:Anthropic/Linux基金会 | 🔍高 | 2024-11/2025-12/2026-07]

**为什么需要 MCP**：
- 协议前时代——每接一个工具都要写一套定制集成（OpenAI function calling / Anthropic tool use / 自研 wrapper 都是厂商专属），N个模型×M个工具的集成成本是 N×M 爆炸
- MCP 时代——MCP Server 统一封装工具/数据源能力，任何 MCP-aware 的 Client（Claude Desktop / Cursor / Cline / VS Code / Windsurf / Replit / Zed / 自研Agent）都能"即插即用"调用，集成成本降为 N+M 线性

## 二、MCP 2026-07-28 史上最大修订：转向生产级智能体基础设施

**2026-07-28 MCP发布史上最大修订候选规范**——从单纯的"工具调用协议"转型为"生产级智能体基础设施"，三大新增能力：[来源:MCP官方/Linux基金会 | 🔍高 | 2026-07-28]

1. **全链路可治理**——新增 Task Lifecycle 管理（任务创建/委派/中断/恢复/取消）、Permission Boundary（权限分层）、Rate Limit（限流），让 Agent 调用工具从"无状态函数调用"升级为"有状态任务编排"
2. **调用全流程可追溯**——新增 Invocation Log（调用日志）、Audit Trail（审计轨迹）、Provenance Chain（来源链），让每次工具调用都可回溯到具体 Agent/任务/用户，满足企业合规审计需求
3. **可观测性**——新增 Telemetry（遥测）、Metrics（指标）、Tracing（分布式追踪），让 Agent 工具调用性能/错误率/链路可视化，解决 Agent 生产环境"黑盒不可观测"痛点

> 修订前的 MCP 只是"工具调用标准"，修订后 MCP 转型为"Agent 工程化基础设施"。PM 必须懂：用旧版 MCP 做生产 Agent 会缺可观测/可审计/可治理能力，必须升级到 2026-07-28 候选规范才能上生产。

## 三、MCP 核心架构

| 组件 | 作用 | 典例 |
|---|---|---|
| **MCP Client** | 发起工具调用的 Agent/应用端，向 Server 发请求 | Claude Desktop / Cursor / Cline / VS Code / Windsurf / 自研Agent |
| **MCP Server** | 封装工具/数据源能力，响应 Client 请求 | GitHub MCP Server / Slack MCP Server / 自研业务MCP Server |
| **Transport** | Client-Server 之间的通信层 | stdio（本地子进程）/ HTTP+SSE（远程流式）/ Streamable HTTP（修订新增） |
| **Resource** | 静态数据资源（文件/数据库表/文档） | 数据库 Schema / 文件系统 / API Schema 文档 |
| **Tool** | 可调用的工具函数（带 name/description/inputSchema） | 数据库查询 / API 调用 / 文件读写 / SaaS 操作 |
| **Prompt** | 预定义的提示词模板（带参数） | 代码 review 模板 / 报告生成模板 / SQL 生成模板 |

**MCP 协议交互流程**：
1. Client 启动 → 发 list_tools/list_resources/list_prompts 请求
2. Server 返回 tools/resources/prompts 元信息（含 JSON Schema）
3. Agent 决定调哪个 tool → Client 发 call_tool 请求（带参数）
4. Server 执行工具 → 返回结果（支持流式增量更新）
5. Client 把结果回传给 Agent → Agent 继续推理

## 五、MCP 三种集成模式

**1. stdio 集成（本地）**——Agent 启动 MCP Server 为子进程，通过 stdin/stdout 通信；适合本地 IDE Agent（Cursor/Claude Desktop）；最简单
**2. HTTP+SSE 集成（远程）**——MCP Server 部署为 HTTP 服务，Agent 通过 HTTP+SSE 通信；适合云 Agent / 多用户 Agent / 团队共享 MCP Server；需处理鉴权/限流/可观测
**3. Streamable HTTP 集成（修订新增）**——单端点双向流式 HTTP，比 SSE 更轻量；2026-07-28 修订推荐，未来替代 HTTP+SSE

## 六、MCP 常见坑

- 工具 Schema 设计错误（参数描述模糊/类型缺失/缺少必填标识）导致 Agent 调用幻觉
- 异步工具未声明流式响应，Agent 长时间空等导致超时
- 未做权限分层，Agent 越权调用敏感工具（删数据库/转账/发邮件）
- 旧版 MCP 无调用日志，生产环境出问题无法回溯（必须升级 2026-07-28 修订版）
- MCP Server 单点无降级，工具故障直接拖垮 Agent
- HTTP+SSE 模式未做限流，高频调用导致后端崩溃

## 七、MCP 局限与替代方案

| 局限 | 替代/补充方案 |
|---|---|
| 仅解决工具调用，不解决 Agent 间协作 | 用 A2A 补 Agent 间任务委派 |
| 仅解决工具调用，不解决前端交互 | 用 AG-UI 补前端过程可视化 |
| 仅解决工具调用，不解决能力封装复用 | 用 Skills 补领域 know-how 复用 |
| 仅解决中心化场景，边缘协同弱 | 用 ACP 补边缘本地协同 |
| 修订前缺乏治理能力（已修订） | 升级 2026-07-28 候选规范 |

> MCP 是五协议生态的核心，但不是全部。完整 Agent 产品需 MCP+A2A+AG-UI+Skills+ACP（按需）组合。详见 3.3 五协议对照表与协议选型决策树。
