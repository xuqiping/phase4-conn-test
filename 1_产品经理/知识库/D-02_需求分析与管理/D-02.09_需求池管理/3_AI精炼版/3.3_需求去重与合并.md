## 需求去重与合并

### 一、为什么需求会重复

| 重复来源 | 典型场景 | 频率 |
|---|---|---|
| 多渠道提交 | 客服+销售+用户反馈同时提相同需求 | 40% |
| 表述不同实质相同 | "导出功能"vs"下载数据"vs"数据导出" | 30% |
| 子需求独立提交 | 大需求被拆成多个小需求分别提交 | 20% |
| 历史需求重新提 | 之前搁置的需求被不同人重新提交 | 10% |

[来源:行业实践经验 | 置信度:📚中 | 日期:2026-07]

### 二、去重识别方法

**方法1：关键词匹配（自动化）**
- 对需求标题和描述做关键词提取+语义相似度计算
- 相似度 > 0.8的标记为"疑似重复"
- 工具：Jira_duplicates插件、Notion AI相似度检测

**方法2：结构化标签匹配**
- 对已有标签（类型+影响面+来源）做交叉匹配
- 同类型+同影响面+不同来源 → 大概率重复

**方法3：人工Review（兜底）**
- PM定期Review"新建"状态的需求
- 识别重复后标记"合并至REQ-XXX"

### 三、合并策略

**策略1：同一需求合并**（表述不同实质相同）
- 保留最早提交的为主需求
- 后续提交标记为"已合并至REQ-XXX"
- 保留所有来源信息（"来自客服3条+销售2条+用户5条"——来源数量本身是价值信号）

**策略2：子需求合并为父需求**
- 独立提交的多个小需求如果属于同一Feature → 创建父Feature，子需求归入
- 保持子需求的独立跟踪（验收方便），但排期以父需求为单位

**策略3：相关需求关联（非合并）**
- 需求A和B有依赖关系但不完全相同 → 建立关联关系而非合并
- 标注："A依赖B"或"A与B应同步交付"

### 四、去重的工作流

```
新需求提交
  → 自动关键词匹配（疑似重复标记）
  → PM Review确认
  → 确认重复 → 合并至主需求 + 保留来源信息
  → 确认不重复 → 进入正常评估流程
  → 确认关联 → 建立依赖关系 + 分别评估
```

### 五、去重的度量

| 指标 | 定义 | 健康值 |
|---|---|---|
| 重复率 | 重复需求 / 总提交需求 | <15% |
| 合并率 | 已合并需求 / 识别的重复需求 | >80% |
| 去重延迟 | 从提交到识别重复的天数 | ≤3天 |
| 遗漏率 | 后续发现的未识别重复 / 总重复 | <5% |

### 六、避免重复的组织机制

1. **提交前搜索**：要求提交人在提交前搜索需求池，确认无重复
2. **统一入口**：所有需求通过同一渠道提交（避免微信群/邮件/口头多渠道散落）
3. **定期清理**：每月做一次需求池清洗——识别重复/搁置到期/信息不全的需求
