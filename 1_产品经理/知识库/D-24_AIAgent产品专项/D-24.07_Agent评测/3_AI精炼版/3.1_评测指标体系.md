# 3.1 评测指标体系

## 一、Agent 评测 vs LLM 评测的本质差异

[来源:CSDN《多步骤 Agent + 工具调用测评标准与数据集全景》| 🔍高 | 2026-02]

| 维度 | 经典 LLM 评测 | Agent 评测 |
|---|---|---|
| 交互范式 | 一问一答静态闭环 | 动态闭环：观察 → 规划 → 工具调用 → 读取结果 → 更新状态 → 再次规划 |
| 状态可重现性 | 单步独立，结果可重现 | stateful，每步改变后续状态，结果不再独立可重现 |
| 错误累积 | 单步错误不传导 | 多步错误累积放大（单步 90% 十步后可能 35%） |
| 输出依赖 | 仅依赖 prompt | 依赖外部工具与环境，失败可能是工具错而非模型错 |
| 评估指标 | 准确率/BLEU/ROUGE | 任务完成率 + 工具调用正确率 + 多步连贯性 + 成本 + 延迟 + 鲁棒性 |
| 代表基准 | MMLU/HumanEval/GPQA | SWE-bench/TAU-bench/Tool Decathlon/GAIA/WebArena/MAST |

**三大根本差异**：
1. **状态管理**——每步改变后续状态，结果不再独立可重现。一个 Agent 在 T1 时刻的输出会影响 T2 时刻的输入，这是经典 LLM 基准假设失效的核心
2. **多步推理**——错误累积放大。单步准确率 90% 看起来不错，但十步后准确率可能衰减到 0.9^10 ≈ 35%。Agent 评测必须评估多步连贯性
3. **工具依赖**——外部环境干扰，失败可能是工具错而非模型错。"现代 Agent 不只是单次 LLM 调用，它们维护上下文、调用工具、读写内部数据库，必须可靠地完成任务。这打破了经典 LLM 基准的所有基本假设"

**PM 认知要点**：MMLU 90% 不代表能处理公司报销审批流程。Agent 评测不能用 LLM 评测套路，必须建立 Agent 专属评测体系。语义鸿沟（Semantic Gap）是 2026 主要危机。

[来源:腾讯云《告别评测集过拟合》| 🔍高 | 2026-07]

## 二、四维评估框架

[来源:腾讯云《告别盲盒式上线》/知乎《Agent 评估、安全、监控与人机协同》| 🔍高 | 2026-05/07]

| 维度 | 评什么 | 核心指标 | 标杆值/阈值 |
|---|---|---|---|
| **准确率** | Agent 端到端把任务做对吗 | 任务完成率 / 工具选择准确度 / 工具执行成功率 / 多步连贯性 | SWE-bench sota < 50% / Tool Decathlon sota < 30% |
| **成本** | 做一次任务烧多少 Token/USD | 单次请求成本 / Token 消耗 / 月度总成本 | Token 燃烧炉单次数十万 Token 是反面教材 |
| **延迟** | 用户体验上的响应快慢 | P50/P95/P99 延迟 / 首字延迟 / 总耗时 | P99 延迟需与业务 SLA 匹配 |
| **鲁棒性** | 边角场景、对抗输入、工具失败下能扛住吗 | 红队通过率 / 工具失败恢复率 / 越狱防护率 | ASB 安全基准 + Azure AI Red Teaming |

**Gartner 4.2 倍警示**：缺乏系统化评测体系的 Agent 项目，上线后故障率是成熟项目的 4.2 倍。四维缺一不可——只看准确率会忽视成本失控（Token 燃烧炉）、只看延迟会忽视鲁棒性（被越狱）。

[来源:腾讯云/Gartner | 🔍高 | 2026-07]

## 三、12 指标体系

[来源:51CTO《生产级 AI Agent 评估体系全面解析：从 12 指标框架到持续评估闭环》| 🔍高 | 2026-06]

| 类别 | 指标 | 定义 | 告警阈值 |
|---|---|---|---|
| **任务完成** | 1.1 Task Success Rate 任务完成率 | 端到端完成任务的比率（Agent 评测第一指标） | < sota*70% 告警 |
| **任务完成** | 1.2 Task Quality Score 任务质量 | 完成任务的质量评分（LLM-as-Judge） | < 4/5 告警 |
| **任务完成** | 1.3 Partial Credit 部分给分 | 完成多少给相应分数（避免 0/1 二元） | - |
| **工具调用** | 5.1 Tool Selection Accuracy 工具选择准确度 | 选对工具的比率 | < 90% 告警 |
| **工具调用** | 5.2 Tool Execution Success 工具执行成功率 | 工具调用成功的比率（参数正确性） | < 95% 告警 |
| **工具调用** | 5.3 Multi-Step Coherence 多步连贯性 | 多步推理的连贯性与一致性 | 单步 90% 十步 < 35% 告警 |
| **成本** | 6.1 Cost per Query 单次请求成本 | 单次对话的 Token/USD 成本 | > 预算 120% 告警 |
| **成本** | 6.2 Token Consumption Token 消耗 | 总/平均 Token 消耗 | 月度超预算告警 |
| **延迟** | 7.1 P99 Latency P99 延迟 | 99 分位延迟 | > SLA 告警 |
| **延迟** | 7.2 First Token Latency 首字延迟 | 首字返回延迟 | > 3s 告警 |
| **鲁棒性** | 8.1 Adversarial Pass Rate 对抗通过率 | 越狱/注入攻击下的通过率 | < 95% 告警 |
| **鲁棒性** | 8.2 Tool Failure Recovery 工具失败恢复率 | 工具失败后能正确恢复的比率 | < 90% 告警 |

**校准方法论 5 条硬规则**（51CTO 2026-06）：
1. 不能只看准确率，必须四维并行
2. 单次实验无意义，必须重复 ≥3 次取均值+方差
3. 指标要有基线（baseline）才能判断好坏
4. 指标要标置信区间（confidence interval）
5. 指标必须能归因（不是"准确率低"而是"准确率低是因为工具选择准确度低"）

## 四、效率智能体定义

[来源:腾讯云《2026 年做 Agents 应该看这篇全面的技术综述》| 🔍高 | 2026-03]

**效率智能体（Efficient Agent）定义**：在固定的成本预算（如 Token 数、延迟、计算量）下最大化任务成功率，或在相同的效果下最小化成本。

**三核心组件**：
1. **预算限制器（Budget Limiter）**——Token/延迟/计算量硬限制，超预算触发降级或终止
2. **任务成功率优化器**——在预算内最大化完成率，参考 5.1 Tool Selection/5.2 Tool Execution
3. **成本-效果权衡器**——动态决策"花更多 Token 是否值得"（如简单问答→直接答，复杂推理→多步深思考）

**PM 认知要点**：
- 效率智能体把"成本"从评测维度升级为"约束条件"——不是事后看成本，而是事前定预算
- Token 燃烧炉事故根因就是没把成本当约束——单次对话数十万 Token 无人拦截
- 效率智能体是 2026 主流方向，单看任务完成率不看效率的 Agent 必然被生产淘汰

## 五、工具调用正确率三连

[来源:51CTO/CSDN | 🔍高 | 2026]

**工具调用正确率不是单一指标，是三连**：

| 子指标 | 评什么 | 典型失败 | 工程实现 |
|---|---|---|---|
| **Tool Selection Accuracy** | Agent 选对工具吗 | 用户问"查天气"Agent 选了"发邮件"工具 | 比对预期工具 vs 实际工具 |
| **Tool Execution Success** | Agent 调对参数了吗 | 选对了天气工具但参数错误（缺城市） | 比对工具调用成功 vs 失败 |
| **Multi-Step Coherence** | 多步工具调用顺序对吗 | 第 3 步依赖第 1 步结果但顺序错乱 | 比对预期调用序列 vs 实际序列 |

**为什么必须三连**：
- 只看 Selection 会漏 Execution（选对但参数错）
- 只看 Execution 会漏 Coherence（每步对但整体流程错）
- SWE-bench / TAU-bench / Tool Decathlon 都按三连打分

## 六、失败模式归因

[来源:CSDN《Agent Harness 综述》/腾讯云 | 🔍高 | 2026-05/07]

Agent 评测不只是跑分，更是"为什么不行"的归因。Agent Harness 综述指出 Verification 必须回答："结果对不对？失败到底是模型错了、工具错了、上下文错了，还是测试环境错了？"

| 失败类型 | 现象 | 归因方法 | 修复方向 |
|---|---|---|---|
| **模型错** | 推理错误/胡乱答 | 同 prompt 多次跑取方差 | 升级模型/调 prompt |
| **工具错** | 工具调用失败/参数错 | 检查工具调用日志 | 修工具 Schema/加容错 |
| **上下文错** | Context Rot 淹没 | 检查上下文规模+Lost in the Middle | 加 Compaction（D-24.06） |
| **测试环境错** | 基准本身有 bug | 检查基准 ground truth | 修基准/换基准 |
| **框架错** | Harness 设计不合理 | Claude Code 100% vs 14% 实验 | 改 Harness（D-24.04） |
| **数据污染** | 跑分虚高生产差 | 检测评测集是否在训练语料 | Continuous Eval 自适应 |
| **过拟合** | 基准上好但泛化差 | 用 OOD 数据测 | 多基准交叉验证 |

**88% 项目失败的根因**（Gartner 腾讯云 2026-07 引）：缺乏可观测性与科学评估体系是 88% Agent 试点项目无法跨越生产鸿沟的核心根因——不是模型不行，是评测/可观测体系缺失导致失败无法归因、无法修复、无法迭代。
