# 3.2 行动协作与自动优化层

## 一、L3 行动协作层

行动协作层让模型不仅推理还能"行动"——推理+调用工具+反思，是Agent的提示词基石。

### 1.1 ReAct (Reasoning + Acting)

**核心**：模型循环执行Thought（思考）→Action（行动/工具调用）→Observation（观察结果），把推理与工具调用交错执行。 [来源:ReAct原论文(Princeton) | 🔍高]

**ReAct提示词结构**：
```
Thought 1: 我需要先查用户余额
Action 1: query_balance(user_id)
Observation 1: 余额=5000
Thought 2: 用户余额够支付，需要校验密码
Action 2: verify_password(...)
Observation 2: 密码正确
Thought 3: 可以执行支付
Action 3: execute_payment(...)
Observation 3: 支付成功
Final Answer: 支付完成，订单号XXX
```

**适用**：需调用多工具/API的Agent任务
**关键设计**：① 工具描述清晰 ② Action格式严格 ③ 中断与超时控制 ④ 最大步数限制（详见 D-19.01 Agent护栏）

### 1.2 Plan-and-Execute (规划-执行分离)

**核心**：先用Planner生成完整计划→Executor逐步执行→遇错回到Planner重新规划。 [来源:Plan-Execute实践 | 📚中]

**与ReAct区别**：
- ReAct：边推理边执行，无全局规划
- Plan-Execute：先全局规划再执行，适合长流程任务

**适用**：步骤多、需全局规划的任务（多文件重构、长流程自动化）

### 1.3 Reflexion (反思学习)

**核心**：Agent失败后基于外部反馈（环境/评估器）做反思→生成教训→下次任务带入教训改进。 [来源:Reflexion原论文 | 🔍高]

**流程**：
```
任务 → 执行 → 评估(成功/失败) → 若失败：反思(找原因+生成教训) → 下次任务带入教训
```

**与Self-Refine区别**：Self-Refine是单次任务内自我批判；Reflexion是跨任务积累教训

### 1.4 工具调用提示词设计

**工具描述最佳实践**：[来源:Function Call实践 | 🔍高]
- 描述精准：用1-2句话说清工具做什么+不做什么
- 参数说明：每个参数类型+约束+示例
- 错误码说明：常见错误码+应对策略
- 给"何时不调用"的反例

**MCP（Model Context Protocol）**：[详见 D-24.02 Agent通信协议]
- Anthropic提出的工具调用标准化协议
- 把工具/资源/Prompt作为MCP Server统一暴露给Agent
- 解决"每个Agent写一遍工具集成"的碎片化问题

## 二、L4 自动优化层

自动优化层是2026年最前沿——程序自动搜索/编译/优化提示词，告别人工玄学调优。

### 2.1 DSPy（Deterministic Sentential Python）

**核心**：用声明式编程定义"输入→输出"映射+自动编译器优化提示词。 [来源:DSPy论文(Stanford) | 🔍高 | 2026]

**与传统Prompt对比**：
| 维度 | 传统手工Prompt | DSPy |
|---|---|---|
| 写法 | 反复试错+经验调优 | 声明输入输出+自动编译 |
| 优化 | 人工反复改 | 程序自动优化（基于训练数据） |
| 可维护 | 难（玄学） | 易（代码版本管理） |
| 模型迁移 | 难（换模型提示词失效） | 易（重新编译） |
| 评测 | 主观 | 客观MMetric |

**典型应用**：复杂模块化任务、需要确定性输出、有训练数据、模型可能切换的场景

**与手工Prompt关系**：[来源:CSDN/腾讯云 | 🔍高 | 2026-07]
- 不是替代而是工程化升级
- 简单场景仍用手工Prompt
- 复杂模块化任务用DSPy更稳健
- 2026 MLOps & LLMOps峰会发布《后Prompt Engineering时代的工程化范式》报告，DSPy是核心

### 2.2 APE (Automatic Prompt Engineer)

**核心**：让LLM自己生成多个候选Prompt→在测试集上评估→选最优Prompt。 [来源:APE论文 | 🔍高]

**流程**：
```
任务描述+少量示例 → LLM生成N个候选Prompt → 在测试集上评估 → 选Top-K
```

**适用**：有明确度量指标+测试集的任务

### 2.3 OPRO (Optimization by PROmpting)

**核心**：用LLM作为优化器，把"优化Prompt"本身作为优化问题，迭代搜索更优Prompt。 [来源:OPRO论文(Google) | 🔍高]

**与APE区别**：APE是生成+选择；OPRO是迭代优化（每一轮基于上轮结果改进Prompt）

### 2.4 Loop Engineering（回路工程）

**核心**：2026年新兴趋势——从"控制模型"到"控制智能体"。 [来源:钛媒体 | 🔍高 | 2026-06]

**理念**：AI产品不再试图"一次说清指令"，而是构建"目标-执行-评估-调整"的回路，让Agent在多轮交互中收敛到目标。提示词不再是单次输入而是回路中的一个组件。

**对PM启示**：产品设计从"调好单次Prompt"转向"设计回路"

| Langfuse | 开源LLM可观测 | 自托管+提示词+追踪 |

### 3.2 提示词AB测试

**流程**：[来源:LLM应用工程实践 | 📚中]
1. 假设：新Prompt在X指标上提升≥Y%
2. 流量分桶：10%流量给新Prompt，90%给旧Prompt
3. 度量：错误率/采纳率/用户满意度/成本
4. 显著性：样本量充足且p<0.05才上线

### 3.3 提示词回归测试

**回归测试库设计**：
- 黄金集（Golden Set）：人工标注的高质量输入输出对
- 边界集（Edge Cases）：模型易出错的边界输入
- 多样性集（Diversity）：覆盖子场景的多样化输入

**测试维度**：
- 准确性：输出与黄金集对齐度
- 格式合规：JSON/Schema是否严格遵守
- 鲁棒性：边界case是否不崩
- 成本：Token消耗+延迟
- 安全：是否越界/越狱

### 3.4 提示词监控与告警

| 监控项 | 告警阈值 | 应对 |
|---|---|---|
| 输出格式违规率 | >2% | 加格式约束+重试机制 |
| Token消耗暴涨 | >均值×1.5 | 检查上下文/示例膨胀 |
| 用户负反馈率 | >5% | 紧急回滚+诊断 |
| 工具调用错误率 | >3% | 检查工具描述/参数约束 |
| 越狱成功率 | >0.1% | 加红线+边界测试 |

### 3.5 提示词工程化的PM职责

| 阶段 | PM职责 | 工程师职责 |
|---|---|---|
| 设计 | 定义任务目标+成功标准+黄金集 | 提供工具能力边界 |
| 实现 | 写提示词初版+设计Few-shot | 集成Prompt到产品+做评测框架 |
| 上线 | 设计AB测试+监控指标+告警阈值 | 落地监控+回归+自动重试 |
| 迭代 | 分析Badcase+提出Prompt改进 | 实施改进+回归测试+灰度放量 |
