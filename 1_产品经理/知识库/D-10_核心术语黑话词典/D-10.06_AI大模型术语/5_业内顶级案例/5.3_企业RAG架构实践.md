# 案例：企业RAG架构实践——RAG/Embedding/向量数据库的企业落地

## 术语映射

| 术语 | 在本案例中的体现 |
|---|---|
| RAG | 企业知识库问答的标准架构：用户提问→向量检索→LLM生成 |
| Embedding | 文档先切分再用Embedding模型转为向量，是RAG的"索引基础" |
| 向量数据库 | 存储Embedding向量并支持相似度检索（ANN），选型影响检索质量和成本 |
| 幻觉 | RAG的设计目标之一就是降低幻觉——用真实文档约束LLM输出，但不完全消除 |
| Token | RAG的检索结果作为上下文注入，会消耗大量Token——需做切粒度与召回量权衡 |
| 上下文窗口 | 检索结果+用户问题+系统Prompt不能超出上下文窗口限制 |

## 典型企业RAG架构

```
用户问题 → Embedding → 向量检索(Top-K) → 重排序(Reranker) → 
拼接上下文 → LLM生成 → 输出+引用溯源
```

## 产品决策启示

1. **评估指标不是"能不能用"而是"准不准"**：RAG的核心指标是检索召回率和生成准确率，需要设计评测集持续监测
2. **切粒度是关键变量**：文档切太大则检索不精准，切太小则上下文不完整——需按业务场景调优
3. **幻觉仍有残余**：即使用了RAG，LLM仍可能"误读"检索结果——对高风险场景需加后处理校验
4. **成本公式**：总成本=向量存储成本+检索成本+LLM推理成本；检索量增大→Token消耗增大→成本非线性增长
