# 4.2 SOP RICE评分工作坊流程

## 适用场景

PM团队需要对一批需求（10-30个）进行RICE评分，确保评分一致性和可解释性。

## 前置条件

- 候选需求清单已确定（含需求描述）
- 产品数据可查（MAU/功能渗透率等）
- 技术团队可参与Effort估算环节

## SOP步骤

### Phase 1：准备（Day 1）

| 步骤 | 操作 | 产出 |
|---|---|---|
| 1.1 需求清单确认 | 确保每个需求描述清晰、可独立交付 | 需求清单表 |
| 1.2 数据准备 | 提前查询各需求可能的Reach数据 | Reach参考数据 |
| 1.3 参与者确认 | PM+技术负责人+运营/业务代表 | 参与者名单 |
| 1.4 评分标准对齐 | 打印评分标准（3.2碎片），全员阅读 | 评分参考卡 |

### Phase 2：工作坊（Day 2，2-3小时）

| 环节 | 时长 | 操作 | 产出 |
|---|---|---|---|
| **开场** | 10min | 解释RICE框架、评分标准、工作坊流程 | 全员理解评分语言 |
| **独立评分** | 30min | 每人独立对每个需求打RICE四维度 | 个人评分表 |
| **Reach校准** | 20min | 展示数据→讨论差异→达成一致 | 统一Reach值 |
| **Impact校准** | 20min | 讨论评分差异→校准到共识 | 统一Impact值 |
| **Confidence校准** | 15min | 确认每个维度的数据来源→打Confidence | 统一Confidence值 |
| **Effort确认** | 30min | 技术负责人给出Effort估算+说明 | 统一Effort值 |
| **计算排序** | 10min | 现场计算RICE得分→排序 | 初步排序表 |
| **冲突校验** | 15min | 讨论排名异常的需求（RICE高但直觉不对 / RICE低但必须做） | 调整说明 |

### Phase 3：输出与归档（Day 3）

| 步骤 | 操作 | 产出 |
|---|---|---|
| 3.1 整理最终评分 | 合并工作坊结果，生成最终RICE评分表 | RICE评分总表 |
| 3.2 KANO交叉标注 | 如有KANO数据，在RICE表上加KANO标注 | 交叉评分表 |
| 3.3 低Confidence清单 | 列出Confidence<80%的需求+验证计划 | 验证计划 |
| 3.4 优先级输出 | 按RICE排序+KANO校验→最终优先级清单 | 优先级清单 |
| 3.5 归档 | 评分数据+讨论记录归档 | 供复盘参考 |

## 校准检查清单

```
□ Impact分值分布是否合理？（不应该50%都打3分）
□ Confidence是否诚实？（无数据≠100%）
□ Effort是否由技术团队确认？
□ Reach的"受影响用户"定义是否一致？
□ 低Confidence需求是否有验证计划？
□ M类需求（如有KANO数据）是否优先保障？
```

## 常见问题与应对

| 问题 | 原因 | 应对 |
|---|---|---|
| Impact评分全部打3 | "都重要"心理 | 强制要求3分≤20%的需求 |
| Confidence全部打100% | 不愿承认猜测 | 要求每项标注数据来源，无数据=50% |
| Effort估不准 | 技术团队未参与 | 必须技术负责人参与Effort环节 |
| RICE排序与直觉冲突 | 可能是评分偏差，也可能是直觉偏差 | 先检查评分是否合理，再决定调分还是调直觉 |
