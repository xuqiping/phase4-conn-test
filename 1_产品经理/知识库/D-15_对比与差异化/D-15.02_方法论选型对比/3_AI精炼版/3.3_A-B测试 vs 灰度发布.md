## 一、2种验证方法定义

### A/B测试（A/B Testing）

**定义**：将用户随机分为两组（或多组），对照组使用现有版本（A），实验组使用新版本（B），在相同时间段内收集数据，通过统计检验判断新版本是否显著优于旧版本。

**核心理念**：用数据说话——不依赖主观判断，通过随机对照实验消除混杂因素，建立因果关系。

**适用场景**：功能优化方案选择、UI设计对比、算法效果验证、转化率提升。

### 灰度发布（Grayscale Release / Canary Release）

**定义**：将新版本逐步推给部分用户（如1%→5%→20%→100%），在扩大范围过程中监控系统指标和用户反馈，发现问题可快速回滚，问题确认无碍后全量发布。

**核心理念**：控制风险——不是"哪个版本更好"的问题，而是"新版本是否安全"的问题。

**适用场景**：新版本上线风险控制、大功能渐进式发布、高并发系统稳定性验证。

## 二、本质区别

| 对比维度 | A/B测试 | 灰度发布 |
|---|---|---|
| **核心目标** | 比较"哪个更好"（效果验证） | 验证"是否安全"（风险控制） |
| **实验设计** | 随机分组+同期对照+统计检验 | 逐步放量+监控告警+可回滚 |
| **用户分组** | 随机均分（50/50或按比例） | 按比例递增（1%→5%→20%→100%） |
| **持续时间** | 固定周期（通常1-4周，需满足样本量） | 不固定（观察至指标稳定即可扩大） |
| **统计要求** | 严格（需计算样本量、显著性水平、统计功效） | 宽松（主要看指标是否异常波动） |
| **决策标准** | 统计显著性（p<0.05）+ 效果量 | 指标稳定性+无严重bug+无客诉异常 |
| **回滚机制** | 测试结束自动恢复（实验期间两组并存） | 随时可回滚到旧版本 |
| **能回答的问题** | "新版比旧版好多少？" | "新版会不会出问题？" |

## 三、关键差异深入

### 1. A/B测试的统计基础

A/B测试的核心是**假设检验**：
- **原假设（H0）**：A版和B版没有差异
- **备择假设（H1）**：B版优于A版
- **显著性水平（α）**：通常设0.05——即"当A和B实际无差异时，错误地认为B更好"的概率不超过5%
- **统计功效（Power=1-β）**：通常目标0.8——即"B确实更好时，能检测出来"的概率不低于80%

**样本量计算**：需要的样本量取决于基线转化率、最小可检测效应（MDE）、显著性水平和统计功效。基线转化率越低、MDE越小，需要的样本量越大。

### 2. 灰度发布的监控维度

灰度发布关注**工程指标**而非**业务指标**：
- **系统健康**：崩溃率/错误率/响应时间/CPU&内存占用
- **业务指标**：核心转化率/留存率（主要看是否下降，不要求显著提升）
- **用户反馈**：客诉率/应用商店评分/社区反馈

## 四、常见坑与最佳实践

### A/B测试常见坑

| ⚠️常见坑 | ✅最佳实践 |
|---|---|
| 样本量不足就下结论 | 上线前计算所需样本量，达到样本量后再看结果 |
| 提前停止实验（看到显著就停） | 预设实验周期，不中途停止（否则产生"偷看偏误"） |
| 同时跑多个AB测试互相干扰 | 互斥实验设计或分层实验（如Google的分层实验框架） |
| 只看平均值不看分布 | 检查分位数分布，防止"平均提升但部分用户严重下降" |
| 统计显著但效果量极小 | 同时报告效果量（Effect Size），判断业务意义 |

### 灰度发布常见坑

| ⚠️常见坑 | ✅最佳实践 |
|---|---|
| 灰度比例跳跃太大（1%→50%） | 循序渐进：1%→5%→10%→20%→50%→100% |
| 灰度期间不监控或只看技术指标 | 技术指标+业务指标+用户反馈三维度同时监控 |
| 灰度时间太短就全量 | 每个灰度阶段至少观察24-48小时，确保覆盖不同时段用户 |
| 灰度用户不是随机选取 | 按用户ID哈希随机分配，确保灰度用户具有代表性 |

## 五、组合使用策略

### A/B测试 + 灰度发布的典型组合流程

```
Step 1: A/B测试验证效果
  ├─ 随机分两组：对照组（旧版）vs 实验组（新版）
  ├─ 运行2周，收集数据
  └─ 统计检验：新版显著优于旧版？
     ├─ 否 → 放弃或优化方案
     └─ 是 → Step 2

Step 2: 灰度发布控制风险
  ├─ 5%用户灰度，监控24-48h
  │   ├─ 异常 → 回滚，排查问题
  │   └─ 正常 → 扩大到20%
  ├─ 20%用户灰度，监控48h
  │   ├─ 异常 → 回滚
  │   └─ 正常 → 扩大到50%
  ├─ 50%用户灰度，监控48h
  │   ├─ 异常 → 回滚
  │   └─ 正常 → 全量发布
  └─ 100%全量
```

### 何时只用灰度发布（不需要A/B测试）

- **紧急修复**：修bug后只需灰度验证不出问题，不需要AB比较效果
- **技术重构**：底层架构优化不改变用户体验，只需灰度验证功能正常
- **合规要求**：法规要求的功能（如隐私协议更新），只需灰度确保平稳上线

### 何时只用A/B测试（不需要灰度发布）

- **非工程变更**：如文案优化、推荐算法参数调整——不涉及代码部署风险
- **服务端实验**：服务端配置开关控制，无客户端发版——天然支持即时回滚
