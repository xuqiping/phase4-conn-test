| 项目 | 内容 |

| **产品** | 微信（WeChat） |

## 灰度发布体系架构

### 多层灰度策略

微信的灰度发布采用**多维度交叉**的灰度策略：

1. **按比例灰度**：1%→5%→10%→20%→50%→100%
2. **按地域灰度**：先在低密度地区（如西藏/青海）发布→验证无异常→扩大到二线城市→一线城市
3. **按用户画像灰度**：先灰度高活跃/高容错用户→再扩展到普通用户→最后覆盖低活跃用户
4. **按平台灰度**：先iOS/后Android（或反过来，取决于发版策略）

### 监控体系（核心）

| 监控层 | 监控内容 | 告警阈值 | 响应动作 |
|---|---|---|---|
| **系统层** | 崩溃率/ANR率/启动时间 | 崩溃率>0.3% | 自动回滚 |
| **网络层** | 请求成功率/响应时间 | 成功率<99.5% | 扩大灰度暂停+排查 |
| **业务层** | 核心功能完成率（发消息/支付/朋友圈） | 下降>2% | 人工评估+决策 |
| **用户反馈层** | 客诉率/应用商店评分 | 客诉率上升>50% | 人工评估+决策 |

### 灰度发布SOP（简化版）

```
Phase 1: 内测（0.1%）
  → 团队+内部用户使用，验证基本功能
  → 持续24h

Phase 2: 小范围灰度（1-5%）
  → 按地域+用户画像选取
  → 监控4层指标，持续48h
  → 任何告警→回滚

Phase 3: 中范围灰度（10-20%）
  → 扩大到更多地域和用户群
  → 监控4层指标，持续48h
  → 关注长尾问题（低频场景的bug）

Phase 4: 大范围灰度（50%）
  → 接近全量，关注系统负载和性能
  → 监控4层指标，持续24h

Phase 5: 全量发布（100%）
  → 持续监控72h
  → 保留快速回滚能力
```

## 关键启示

1. **监控比灰度比例更重要**：1%灰度没有监控等于0%灰度——问题不在于"推给多少人"，而在于"能否及时发现异常"。
2. **多维度灰度比单一比例灰度更安全**：按地域+用户画像+平台交叉灰度，能在最小范围内暴露最多类型的问题。
3. **自动回滚是底线**：系统层指标（崩溃率/ANR率）触发自动回滚，不等待人工决策——人工决策速度跟不上10亿用户的影响规模。
4. **灰度不是A/B测试的替代品**：微信灰度发布的目的是"验证安全"，不是"比较效果"——效果验证通过A/B测试在灰度前完成。
