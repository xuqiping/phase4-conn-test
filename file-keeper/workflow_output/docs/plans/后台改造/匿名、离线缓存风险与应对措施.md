# 匿名、离线缓存风险与应对措施

> 本文档记录 File Keeper 商业授权系统中，**匿名试用设备**与**登录用户离线缓存**两类机制的安全风险、已实施的加固措施以及后续建议。
>
> 最后更新：2026-06-15

## 一、匿名设备链路风险与加固

### 1.1 原始风险

匿名设备试用期是商业版的获客入口，但也最容易被滥用：

| 风险 | 说明 |
|---|---|
| 无限刷新 deviceId | 客户端每次生成新的 `deviceId`，服务端就视为新设备，重新获得 7 天全功能试用 |
| 伪造 fingerprintHash | 原实现中指纹哈希是随机字符串，攻击者可随意更换 |
| 清除本地存储 | 原 `file-keeper-auth.json` 位于应用数据目录，技术用户仍可删除后重新注册 |
| 缺少运营手段 | 后台无法识别同一 IP / 指纹的批量注册，也无法限制试用重置次数 |

### 1.2 已实施加固

#### 1.2.1 服务端：注册频率限制

- 同一 **IP** 每天最多注册 **5** 个匿名设备
- 同一 **fingerprintHash** 每天最多注册 **3** 次
- 使用 Redis 计数，超限返回 `429 Too Many Requests`

相关代码：
- `server/.../device/service/AnonymousTrialRateLimiter.java`
- `server/.../device/service/AnonymousTrialService.java`

#### 1.2.2 服务端：设备元信息采集

`anonymous_device_trials` 表新增字段：

- `first_seen_ip` — 首次注册来源 IP
- `user_agent_hash` — User-Agent 哈希
- `trial_reset_count` — 被管理员重置试用次数

相关迁移：
- `server/.../db/migration/V3__harden_anonymous_trial.sql`

#### 1.2.3 服务端：试用重置次数限制

管理员在后台“重置试用”时，单个设备累计最多 **3 次**，超过后按钮禁用并返回 `422`。

相关代码：
- `server/.../admin/service/AdminAnonymousDeviceService.java`
- `admin-web/src/views/AnonymousDevicesView.vue`

#### 1.2.4 客户端：双存储 + 环境指纹

- 主存储：`@tauri-apps/plugin-store`（应用数据目录）
- 备份：`localStorage`
- 主存储被删除时，从备份恢复设备身份
- `fingerprintHash` 基于 UA / platform / hardwareConcurrency / deviceMemory / 屏幕特征计算，不再随机生成

相关代码：
- `file-keeper/src/api/commercialAuth.ts`

#### 1.2.5 运营后台：异常识别

匿名设备运营页新增：

- 来源 IP 列
- 重置次数列，≥1 黄色、≥3 红色
- 按 IP 筛选
- “高频重置”快速筛选（≥2 / ≥3）
- “IP 滥用统计”弹窗，展示同一 IP 下设备数

相关代码：
- `admin-web/src/views/AnonymousDevicesView.vue`
- `server/.../device/repository/AnonymousDeviceAdminRepository.java`

### 1.3 剩余风险

| 风险 | 说明 | 建议 |
|---|---|---|
| VM / 虚拟机刷量 | 攻击者可用虚拟机 + 代理 IP 绕过 IP / 指纹限制 | 接入行为风控、设备信誉分、验证码挑战 |
| 硬件指纹可变性有限 | 基于浏览器特征的指纹仍可被修改 | 对桌面端可采集更稳定的硬件特征，但需权衡隐私合规 |
| 真实用户共享 IP | 企业/校园出口 IP 可能被多人共用 | 阈值需根据实际数据调优，避免误杀 |

## 二、登录用户离线缓存风险与加固

### 2.1 原始风险

登录用户的授权支持 `offlineCacheMinutes` 断网使用：

| 风险 | 说明 |
|---|---|
| 系统时间回拨 | 原 `commercialAuthStore` 用 `Date.now()` 判断 `offlineUsableUntil`，回拨系统时间即可让缓存不过期 |
| 内存篡改 | 攻击者通过 DevTools 修改 Pinia store 中的 `clientAuthorization.offlineUsableUntil` 或模块权限 |
| 伪造授权对象 | 直接构造 `ClientAuthorizationSnapshot` 对象，标所有模块为 allowed |
| 禁用后仍可使用 | 用户/设备被管理员禁用后，已离线的客户端在缓存有效期内不会感知，仍能继续使用 |

### 2.2 已实施加固

#### 2.2.1 服务端：签发离线授权 Token

`AuthorizationService.authenticatedSnapshot()` 现在为登录用户生成一个 **HMAC-SHA256 签名**的离线 token，结构为：

```
base64url(userId|deviceId|offlineUsableUntilEpochMilli|allowedModules|signature)
```

- Token 由服务端用 `file-keeper.auth.jwt.secret` 签名
- 客户端无法伪造或篡改允许的模块列表与过期时间

相关代码：
- `server/.../authorization/service/OfflineTokenSigner.java`
- `server/.../authorization/service/AuthorizationService.java`

#### 2.2.2 Rust 层：签名校验 + 防时间回拨

新增 `src-tauri/src/commands/auth.rs`：

- `set_offline_token(token, offline_seconds)` — 接收并保存 token，同时记录 `Instant::now()`（单调时钟）
- `check_offline_access(module_code)` — 验证 token 签名，检查从保存到现在经过的单调时间是否超过 `offline_seconds`，并校验模块是否在允许列表
- `clear_offline_token()` — 清除本地缓存

由于使用 `Instant::now()` 计算经过时间，**回拨系统时间无法延长离线缓存**。

#### 2.2.3 前端：离线模式下走 Rust 校验结果

`commercialAuthStore` 改动：

- 获取/刷新登录授权后，调用 `set_offline_token` 把 token 交给 Rust 层
- 离线模式下，`isModuleAllowed()` 不再信任 JS 内存中的权限，而是使用 Rust 预校验结果
- 授权失败或主动刷新时，调用 `clear_offline_token`

相关代码：
- `file-keeper/src/stores/commercialAuthStore.ts`
- `file-keeper/src-tauri/src/commands/auth.rs`

#### 2.2.4 服务端：联网时间同步异常检测

为防止用户通过修改系统时间绕过离线缓存，新增了客户端/服务端时间比对机制：

- 桌面端每次请求 `/api/client/authorization` 时附带 `clientTimestamp`（本地 `Date.now()`）
- 服务端比较 `clientTimestamp` 与服务器当前时间
- 偏差超过 **5 分钟**时，`user_devices.time_sync_anomaly_count` 自动 +1
- 管理后台“用户详情 → 设备列表”显示“时间异常次数”，大于 0 时红色标记

相关代码：
- `server/.../authorization/controller/ClientAuthorizationController.java`
- `server/.../authorization/service/AuthorizationService.java`
- `server/.../device/repository/DeviceRepository.java`
- `server/.../db/migration/V4__device_time_sync_anomaly.sql`
- `file-keeper/src/api/commercialAuth.ts`
- `file-keeper/src/stores/commercialAuthStore.ts`
- `admin-web/src/views/UserDetailView.vue`

### 2.3 剩余风险

| 风险 | 说明 | 建议 |
|---|---|---|
| 禁用后离线仍可用 | 这是“离线可用”的固有矛盾，缓存期内无法实时吊销 | 缩短缓存时间；敏感操作强制联网校验；设备上线心跳 |
| Rust 层 secret 提取 | 桌面应用代码在用户机器上，技术用户可从二进制中提取 JWT secret | 使用更长的强密钥；混淆打包；未来可接入硬件安全模块 |
| 应用重启后缓存丢失 | 当前设计不持久化 `clientAuthorization`，重启即失效 | 这是安全特性，但会降低用户体验；如需持久化，必须加密存储 |
| 关键操作离线可用 | 如果文件删除/导出等敏感操作不联网，离线缓存被破解后仍可执行 | 对敏感操作增加“强制联网校验” |

## 四、后续建议

### 4.1 短期（1-2 周）

1. 清理 `src-tauri/target` 后重新运行 `cargo test`，确认 Rust 离线 token 单元测试通过
2. 手动跑 Tauri 端到端：断网后验证 `files` 可用、`processes` 不可用，回拨系统时间后不可用
3. 在运营后台增加“同一 IP 设备数”快捷筛选，而非仅弹窗

### 4.2 中期（1 个月）

1. 敏感操作强制联网：文件删除、批量导出、修改设置前必须联网校验一次授权
2. 设备上线心跳：应用恢复网络后 5 秒内刷新授权，若收到 403 立即清空缓存并提示
3. 匿名设备行为风控：对短时间内大量注册、同一 UA 多设备等模式增加告警

### 4.3 长期（按需）

1. Rust 端使用更安全的密钥存储方式（如编译时注入 + 混淆）
2. 引入设备信誉体系，结合 IP、UA、指纹、行为评分动态调整试用策略
3. 对高价值商业客户，考虑引入硬件绑定或云端实时授权
