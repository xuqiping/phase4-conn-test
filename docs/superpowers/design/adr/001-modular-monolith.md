## 背景

多 Agent 智能体平台是一个新项目，核心需求包括：

- 14 个子 Agent 的管理和编排
- 51 个工作流的可视化编辑和执行
- 用户认证和权限管理
- 工作流执行引擎

团队需要选择合适的架构风格来构建这个平台。候选方案包括：模块化单体、微服务架构、六边形架构。

### 项目约束条件

1. **团队规模**：当前 1-3 人开发团队
2. **项目阶段**：从零启动的 MVP 阶段
3. **交付周期**：需要在较短周期内交付可用版本
4. **运维能力**：没有专职 DevOps 工程师
5. **业务复杂度**：4 个核心领域（auth/agent/workflow/execution），领域边界清晰
6. **未来规划**：可能需要独立扩展执行引擎

---

## 决策

**采用模块化单体（Modular Monolith）架构**。

具体来说：
- 使用 Spring Boot 单进程部署
- 通过包结构划分 4 个逻辑模块：auth、agent、workflow、execution
- 模块间通过 Facade 接口通信，禁止直接依赖其他模块的 Service 实现
- 数据库共享但表按模块划分，避免跨模块表关联
- 为未来微服务拆分预留接口抽象层

## 替代方案比较

### 方案A：微服务架构

```
每个模块独立部署为服务，通过 HTTP/RPC 通信。

┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
│ Auth │  │Agent │  │Flow  │  │ Exec │
│ Svc  │  │ Svc  │  │ Svc  │  │ Svc  │
└──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
   │         │         │         │
   └─────────┴─────────┴─────────┘
              API Gateway
```

| 维度 | 评分 | 说明 |
|------|------|------|
| 开发效率 | ★★☆☆☆ | 需要搭建服务发现、配置中心、API 网关等基础设施 |
| 部署复杂度 | ★☆☆☆☆ | 4 个服务 + 基础设施组件，运维负担重 |
| 独立扩展 | ★★★★★ | 每个服务可以独立扩缩容 |
| 团队要求 | ★☆☆☆☆ | 需要专职 DevOps，小团队难以胜任 |
| 交付速度 | ★★☆☆☆ | 初期基础设施搭建耗时长 |

### 方案B：模块化单体（已采纳）

```
单进程中按包结构划分模块，模块间通过接口通信。

┌──────────────────────────────────────┐
│          Spring Boot 单进程           │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐│
│  │ Auth │ │Agent │ │Flow  │ │ Exec ││
│  │ 模块  │ │ 模块  │ │ 模块  │ │ 模块  ││
│  └──────┘ └──────┘ └──────┘ └──────┘│
└──────────────────────────────────────┘
```

| 维度 | 评分 | 说明 |
|------|------|------|
| 开发效率 | ★★★★★ | 单项目开发，无需管理服务间通信 |
| 部署复杂度 | ★★★★☆ | 单进程部署，运维简单 |
| 独立扩展 | ★★☆☆☆ | 无法独立扩缩容（可通过多实例补偿） |
| 团队要求 | ★★★★★ | 1-3 人团队即可高效开发 |
| 交付速度 | ★★★★★ | 快速启动，快速迭代 |

### 方案C：六边形架构（端口-适配器）

```
核心领域在中心，通过端口和适配器与外部交互。

          ┌─────────────┐
          │  Web适配器   │
          └──────┬──────┘
                 │
┌──────────┐  ┌──┴───────┐  ┌──────────┐
│ DB适配器  │──│  核心领域  │──│ API适配器 │
└──────────┘  └──┬───────┘  └──────────┘
                 │
          ┌──────┴──────┐
          │ 消息队列适配器│
          └─────────────┘
```

| 维度 | 评分 | 说明 |
|------|------|------|
| 开发效率 | ★★★☆☆ | 需要定义大量端口接口，初期开发较慢 |
| 部署复杂度 | ★★★★☆ | 仍然是单进程部署 |
| 独立扩展 | ★★☆☆☆ | 与模块化单体相同 |
| 团队要求 | ★★★☆☆ | 需要团队对六边形架构有较深理解 |
| 交付速度 | ★★★☆☆ | 接口定义增加开发量 |

### 综合对比

| 维度 | 微服务 | 模块化单体 | 六边形架构 |
|------|--------|-----------|-----------|
| 开发效率 | 低 | **高** | 中 |
| 运维成本 | 高 | **低** | 低 |
| 初期交付速度 | 低 | **高** | 中 |
| 可扩展性 | 高 | 中 | 中 |
| 拆分友好度 | N/A | **高** | 高 |
| 学习成本 | 高 | **低** | 中 |
| 适合团队规模 | 5+ 人 | **1-5 人** | 3-5 人 |

## 后果

### 正面后果

1. **快速启动**：单项目、单进程，快速搭建开发环境，快速迭代
2. **低运维成本**：一个 JAR 包部署，不需要服务发现、配置中心等基础设施
3. **开发效率高**：模块间直接方法调用，无需序列化/反序列化，调试方便
4. **事务简单**：模块间共享数据库连接，事务管理简单可靠
5. **拆分预留**：通过 Facade 接口隔离模块，未来可按模块拆分为微服务

### 负面后果

1. **无法独立扩展**：执行引擎如果负载高，只能整体扩容
2. **耦合风险**：如果不严格遵循模块边界，容易产生隐式耦合
3. **单点故障**：一个模块的严重 Bug 可能影响整个系统
4. **技术锁定**：所有模块必须使用相同的技术栈

### 缓解措施

1. **独立扩展**：多实例部署 + Nginx 负载均衡，Phase 3 将 execution 拆分为独立服务
2. **耦合风险**：通过 ArchUnit 测试强制模块边界约束
3. **单点故障**：多实例部署 + 健康检查 + 自动重启
4. **技术锁定**：使用标准接口抽象，关键模块（如执行引擎）预留可替换设计

## 模块边界守卫规则

为确保模块边界的严格性，引入以下规则：

### 代码层面的约束

```java
// 1. 模块间只能通过 Facade 接口通信
// 正确：
@Autowired
private AgentFacade agentFacade; // 接口

// 错误：
@Autowired
private AgentServiceImpl agentService; // 实现

// 2. 禁止跨模块直接查询数据库
// 正确：
AgentDTO agent = agentFacade.getAgentSummary(agentId);

// 错误：
@Autowired
private AgentRepository agentRepository; // 其他模块的Repository
```

### 架构测试（ArchUnit）

```java
@ArchTest
static final ArchRule moduleDependencyRule = slices().matching("com.platform.(*)..")
    .should().notDependOnEachOther();

@ArchTest
static final ArchRule facadeOnlyRule = noClasses()
    .that().resideInAPackage("com.platform.workflow..")
    .should().dependOnClassesThat()
    .resideInAPackage("com.platform.agent.service.impl..");
```

## 拆分路径规划

当需要从模块化单体拆分为微服务时，推荐路径：

```
第一步：拆分 execution 模块
  原因：执行引擎是 CPU 密集型，最需要独立扩展
  方式：将 execution 包提取为独立 Spring Boot 项目
  通信：HTTP REST（复用现有 Facade 接口）

第二步：拆分 auth 模块
  原因：认证服务通常是共享基础设施
  方式：将 auth 包提取为独立服务
  通信：JWT Token 验证不依赖网络调用

第三步：按需拆分 agent 和 workflow
  原因：仅当有明确的独立扩展需求
  方式：独立部署，引入消息队列异步通信
```
