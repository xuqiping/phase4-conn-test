## 一、背景与目标

安全审查认定离线授权存在根因级缺陷：对称签名密钥必然外泄（P0-1）、过期时间未校验可无限续期（P1-1）、特权命令无 Rust 侧门禁（P1-2）、secret 默认兜底（P0-2）。

**本计划目标（必做）**
- 消除 P0-1：离线/授权 token 改 **Ed25519 非对称签名**，客户端只内嵌公钥。
- 消除 P1-1：token 内 **绝对 `not_after` 强校验**，签名覆盖有效期，移除外部 `duration` 入参。
- 消除 P1-2：所有特权 Tauri 命令在 **Rust 侧强制门禁**。
- 消除 P0-2：生产强制校验私钥已配置。

**不在本计划（P2，待排期）**：设备指纹服务端签发（P2-1）、单调时钟 + 在线复核（P2-2）。

## 二、核心设计：统一「签名授权凭据」

> 关键决策：不再区分「在线 modules 快照」与「离线 token」两套机制，统一为**一份服务端签名的授权凭据**，客户端始终同步给 Rust、Rust 始终凭它门禁。

- **凭据 payload**（签名覆盖）：`userId | deviceId | issuedAt | notAfter | allowedModules[]`
- **签名**：Ed25519，服务端私钥签，客户端内嵌公钥验。
- **有效期语义**：在线态服务端发**短** `notAfter`（如 24h）并频繁刷新；离线态发**长** `notAfter`（= `offlineUsableUntil`）。**过期判定统一为 Rust 侧 `now > notAfter`**。
- **门禁**：特权命令入口调 `require_module(code)` → Rust 验签 + 查 `notAfter` + 查模块列表，任一不过即拒。
- 这套设计同时解决 P0-1 / P1-1 / P1-2，且在线/离线行为一致。

## 四、技术坑点预判

1. **旧 token 失效**：切换签名算法后，用户本地缓存的旧 HMAC token 验签必失败。策略：捕获失败 → 前端清缓存 + 提示联网刷新一次。可接受。
2. **payload 字节一致性**：Ed25519 验签要求客户端重构的待签字节与服务端**逐字节一致**。必须固定 payload 序列化规范（分隔符、字段顺序、无填充），并在两侧加跨语言一致性测试（服务端签、客户端验的固定向量）。
3. **JWT 是否一并迁移**：当前 JWT 也用 `FILE_KEEPER_JWT_SECRET`（HMAC）。建议 JWT 暂不动（服务端自验自签，密钥不出服务端，风险低），仅授权凭据迁 Ed25519。若想统一，另立小变更。
4. **在线态门禁正确性**：Rust 侧原 `is_module_allowed` 只看离线 token，在线但无离线 token 时会误拒。统一凭据设计（在线也发短凭据并同步 Rust）已规避，但实施 Chunk 2/3 时务必覆盖「在线态特权命令」用例。
5. **密钥轮换**：私钥泄露后需能轮换。设计上公钥内嵌意味着轮换需发版；建议同时支持「公钥版本号」字段，为未来多公钥留扩展。
6. **Java 17 Ed25519 可用性**：`java.security` 自 JDK 15 支持 Ed25519（`KeyFactory.getInstance("Ed25519")` / `Signature.getInstance("Ed25519")`），Java 17 满足。需在目标 JDK 验证。

## 五、安全检查清单（实施后逐项确认）

- [ ] 客户端二进制中**不存在任何对称 secret**（grep `JWT_SECRET` / 旧默认串应为 0 命中运行路径）。
- [ ] 客户端只内嵌**公钥**；私钥仅在服务端 env/secret store。
- [ ] `not_after` 在 Rust 侧被强校验，且无任何「外部 duration 续期」路径。
- [ ] 杀进程 / 截图 OCR / 剪贴板监听**每个**特权命令入口都有 `require_module`。
- [ ] 服务端缺失私钥时**拒绝启动**（非静默兜底）。
- [ ] 伪造 / 篡改 / 过期 token 均有自动化测试覆盖且断言拒绝。

## 六、性能考虑

- Ed25519 验签 ~ 几十微秒，每次特权命令调用一次，可忽略。
- payload 序列化保持紧凑（沿用 `|` 分隔 + base64url），不引入 JSON 解析开销。
- Rust 门禁为纯内存查表 + 一次验签，无 I/O，不阻塞 UI 线程。

## 七、测试策略

- 单元：Rust `auth.rs` 内联测试扩容（见 4.1）；Java `OfflineTokenSignerTest` → `SignedEntitlementSignerTest`。
- 跨语言一致性：固定向量（服务端签的 token，客户端 Rust 必须验过；篡改一字节必拒）。
- 集成：在线授权 → 特权命令放行；退订/降级后刷新 → 特权命令拒绝；断网 + notAfter 内 → 放行；断网 + notAfter 过 → 拒绝。

## 八、回滚预案

- 风险点：新签名器有跨语言字节不一致 bug，导致全员离线失效。
- 回滚锚点：保留 `OfflineTokenSigner`（HMAC）一个版本周期不删，通过 feature flag（配置项）切换签名器。
- 回滚步骤：服务端 config 切回 HMAC 签名器 → 客户端发紧急版回退验签 → 强制在线刷新。
- 兜底：即便签名层失效，服务端在线授权不受影响（在线态本就服务端说了算），仅离线态回退到「必须联网」。
