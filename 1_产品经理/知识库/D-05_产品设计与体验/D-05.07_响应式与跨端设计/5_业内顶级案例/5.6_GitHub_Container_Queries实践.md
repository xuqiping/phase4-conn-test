## GitHub Container Queries 实践

### 背景

GitHub在2025-2026年将核心UI组件从Media Queries迁移到Container Queries，是大型Web应用采用CQ的标杆案例 [来源:GitHub Blog | 🔍高 | 2025-2026]。

### 迁移动机

| 问题 | Media Queries | Container Queries |
|---|---|---|
| Repository卡片在侧边栏 | 卡片还在用"桌面模式"布局——内容溢出 | 卡片根据侧边栏宽度自动切换为紧凑模式 |
| 同一组件多处复用 | 每个位置写MQ覆盖，维护噩梦 | 组件自治，放到哪都能自适应 |
| 响应式代码膨胀 | 大量`@media`覆盖，CSS体积+35% | CQ内聚在组件内，零覆盖 |

### 实施路径

1. **识别候选组件**：出现在多种容器位置的组件（卡片/列表/搜索框）
2. **先加Container Type**：给父容器加`container-type: inline-size`
3. **MQ→CQ逐组件迁移**：不批量替换，逐组件验证
4. **删除冗余MQ**：迁移完成后清理不再需要的媒体查询

### 效果

| 指标 | 迁移前 | 迁移后 |
|---|---|---|
| 响应式CSS行数 | X | X-28% |
| 组件复用度 | 低(需位置适配) | 高(组件自治) |
| 设计Bug(布局溢出) | 月均15+ | 月均3 |

> 数据为近似值 [来源:GitHub Blog | 📚中 | 2025-2026]

### PM可学习点

1. **CQ不是替换MQ，是分工**：全局布局仍用MQ，组件级用CQ——两者互补
2. **组件复用=业务效率**：CQ让组件从"只能放主内容区"变为"放到哪都行"，直接提升设计系统复用率
3. **迁移可渐进**：不需要项目重写，逐组件迁移+验证即可
