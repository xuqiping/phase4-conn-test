# 多Agent智能体平台 — 数据库设计文档

> 数据库：PostgreSQL 16 | 共 13 张表，4 个模块
> 主键策略：`GENERATED ALWAYS AS IDENTITY`（自增）
> 软删除：所有业务表含 `deleted` 字段（0=正常，1=已删除）
> 乐观锁：所有业务表含 `version` 字段
> 审计字段：`created_by / created_at / updated_by / updated_at`（MyBatis-Plus 自动填充）

---

## 六、完整关联关系

| 关系 | 类型 | 外键 | 说明 |
|------|------|------|------|
| users → user_roles → roles | N:N | user_roles.user_id → users.id | 一个用户可有多个角色 |
| roles → role_permissions → permissions | N:N | role_permissions.role_id → roles.id | 一个角色可有多个权限 |
| agent_groups → agents | 1:N | agents.group_id → agent_groups.id | 一个分组下多个Agent |
| users → agents | 1:N | agents.created_by → users.id | 用户创建的Agent |
| agents → skills | 1:N | skills.agent_id → agents.id | 一个Agent有多个技能 |
| skills → skill_steps | 1:N | skill_steps.skill_id → skills.id | 一个技能有多个步骤 |
| users → workflows | 1:N | workflows.owner_id → users.id | 用户拥有的工作流 |
| workflows → workflow_nodes | 1:N | workflow_nodes.workflow_id → workflows.id | 一个工作流多个节点 |
| workflows → workflow_edges | 1:N | workflow_edges.workflow_id → workflows.id | 一个工作流多条边 |
| workflows → execution_logs | 1:N | execution_logs.workflow_id → workflows.id | 一个工作流多次执行 |
| users → execution_logs | 1:N | execution_logs.triggered_by → users.id | 用户触发的执行 |

## 八、企业级精准知识库 RAG Trace 基座（V101）

> 这 5 张表只保存配置版本、运行状态、Hash 和关联键；默认不保存完整 Prompt、Chunk、密钥或敏感模型响应。

| 表 | 一行代表什么 | 关键关联/字段 |
|---|---|---|
| `rag_pipeline_versions` | 一套不可变的检索“配方” | `version_code/config_snapshot/config_hash/status` |
| `rag_retrieval_runs` | 用户发起的一次完整知识检索 | `trace_id/pipeline_version_id/query_hash/status/result_state` |
| `rag_ranking_runs` | 一次重排流程，多批 LLM 可共用 | `retrieval_run_id/configured_mode/effective_mode/fallback_reason` |
| `rag_model_calls` | RAG 内部的一次模型调用摘要 | `retrieval_run_id/ranking_run_id/model_request_id/provider_request_id/call_purpose` |
| `rag_fallback_events` | 一次明确记录的故障降级 | `retrieval_run_id/ranking_run_id/stage/reason_code` |

关联关系：一个 retrieval run 可有多个 ranking run；一个 ranking run 可有多次模型调用和降级事件。生活化理解是“一张总工单下面有重排子工单，每次外部模型请求都有自己的流水号”。

索引重点：`trace_id` 支持日志反查，`retrieval_run_id/ranking_run_id` 支持时间线聚合，`tenant_id+user_id+started_at` 支持用户历史查询。

### 8.1 `rag_ranking_configs`（V103）

一行代表一套当前生效或历史归档的知识库重排配置。`kb_id` 有值表示某个知识库自己的覆盖配置；为空表示管理员默认配置。

| 字段 | 用途 |
|---|---|
| `ranking_mode` | `LLM/RERANK/DISABLED`，决定当前使用大模型、专用重排模型或只使用 RRF |
| `model` | 明确选择的模型；DISABLED 可空，其他模式必填 |
| `candidate_limit/final_limit/batch_size` | 控制候选数、最终证据数和 LLM 每批数量 |
| `timeout_ms/fallback_policy` | 超时与失败后允许采取的明确行为 |
| `high_accuracy_enabled` | 是否允许更多补检索或批次预算 |
| `config_version` | 缓存、Trace 和评测使用的配置版本 |

唯一约束保证每个 KB 只有一条 ACTIVE 配置、每个租户只有一条 ACTIVE 管理员默认。运行时解析顺序固定为“KB 覆盖 → 管理员默认 → 报错”，禁止自动选择模型列表第一项。
