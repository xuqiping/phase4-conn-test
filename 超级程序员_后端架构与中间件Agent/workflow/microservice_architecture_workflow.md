# Microservice & Distributed Architecture Workflow

## Purpose

基于微服务与分布式架构知识体系，为用户提供微服务拆分策略、服务治理组件选型（注册中心/配置中心/网关）、分布式事务方案、限流熔断降级策略、多租户架构设计等技术方案支持。覆盖DDD领域驱动设计、Bounded Context、康威定律、渐进式演进等核心理论。

## Prerequisites

- 用户已明确微服务/分布式架构场景或问题
- 知识库文件 `02_网络架构与中间件.md` 及子目录文件可访问

## Steps

### Step 1: 识别微服务/分布式需求场景

**Goal**: 明确用户的架构需求类型和当前系统状态
**Completion criterion**: 已确定场景标签、当前架构阶段、规模约束和稳定性要求

1. 读取用户消息，提取以下信息：
   - 场景类型：服务拆分策略 / 基础设施选型（注册中心/配置中心/网关） / 分布式事务方案 / 限流熔断降级 / 多租户架构 / 渐进式演进路径
   - 当前架构阶段：单体应用 / 模块化单体 / 宏服务（5-10个服务） / 已拆分微服务 / 未知
   - 团队与规模：团队人数（是否<50人）、日活用户量（是否<100万）、服务数量预期
   - 稳定性要求：是否需要金融级可靠性、是否涉及资金交易、可用性目标（几个9）
   - 特殊约束：SaaS多租户需求、数据一致性要求（强一致/最终一致）、合规要求

2. 对照知识库中的核心决策点初步判断：
   - 团队<50人/日活<100万 → 建议单体或宏服务（5-10个），避免过早拆分
   - 涉及金融交易/强一致 → 关注分布式事务（SAGA/TCC/2PC）和消息队列可靠性
   - SaaS商业化 → 评估多租户三模式（完全共享/独立DB/独立部署）

3. 如有信息缺失，向用户追问不超过2个澄清问题。

### Step 2: 输出微服务/分布式架构方案

**Goal**: 产出针对性的架构设计方案
**Completion criterion**: 输出包含架构设计、组件选型、关键决策理由、风险与缓解措施

根据Step 1确定的场景，按以下分支处理：

**分支A — 服务拆分策略**：
1. 输出拆分方法论：DDD领域驱动设计指导拆分，Bounded Context定义服务边界，Event Storming识别领域事件。
2. 给出渐进式拆分路径：单体→模块化单体→宏服务→微服务，标注每个阶段的触发条件和团队规模要求。
3. 输出康威定律应用：组织架构与架构对齐建议。
4. 给出具体拆分案例（如电商系统：用户/订单/库存/支付/物流等边界划分）。

**分支B — 基础设施四件套选型**：
1. **注册中心**：对比Nacos（AP优先、本地缓存、K8s原生支持）vs Consul（CP强一致、多数据中心），给出选型建议。
2. **配置中心**：对比Apollo（三层模型、灰度发布）vs Nacos（一体化），给出配置管理策略和Vault密钥管理方案。
3. **API网关**：对比Envoy/Kong/自建Gateway，给出多层网关架构设计（边缘网关→BFF→业务网关）。
4. **分布式事务**：用PACELC模型替代CAP做一致性决策，输出SAGA（长事务/编排式/协同式）/TCC/2PC/Seata选型对比，附具体业务场景匹配表。

**分支C — 稳定性铁三角**：
1. **限流**：对比4算法（计数器/漏桶/令牌桶/滑动窗口），给出令牌桶作为推荐方案及参数配置模板。
2. **熔断**：输出三态熔断器状态机（Closed/Open/Half-Open），附Sentinel配置示例和触发阈值设计。
3. **降级**：输出四级降级矩阵（核心/重要/次要/装饰），附降级开关设计和兜底策略。
4. 给出完整的多层防御架构：网关层限流→服务层熔断→缓存层兜底→数据库最终防线。

**分支D — 多租户架构**：
1. 输出三模式选型对比：完全共享（Shared Schema，成本低）/ 独立DB（Schema隔离，合规高）/ 独立部署（资源隔离，大客户）。
2. 给出租户隔离策略：DB层（Schema隔离/行级隔离字段）、缓存层（Key前缀）、MQ层（Namespace）。
3. 附SaaS商业化决策树：按客户规模选档的标准。

将结果保存到 `output/microservice_architecture.md` 或直接在对话中呈现。

### Step 3: 验证与交付

**Goal**: 确保架构方案合理、可落地、与知识库一致
**Completion criterion**: 已通过 checklist 逐项核对

1. 读取 `checklist/microservice_architecture_workflow_checklist.md`。
2. 逐项核对输出是否覆盖要求的知识点。
3. 确认所有关键论断均能在知识库中找到支撑。
4. 如有遗漏或偏差，补充修正。
5. 向用户交付最终答案。

## Post-Workflow

1. 记录完成状态到 `task/current_task.md`。
2. 如需深入某一具体组件（如"Sentinel熔断参数调优"、"Seata SAGA模式实战"），在当前 Agent 内继续追问并输出。
