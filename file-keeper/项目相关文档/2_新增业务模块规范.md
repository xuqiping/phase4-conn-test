# File Keeper 新增业务模块规范

> 本规范用于指导后续新增业务模块的开发，确保新模块与商业售卖版账号权限、设备授权、匿名试用、离线缓存、管理后台等现有设计保持一致，不产生冲突。
>
> 版本：2026-06-20
> 依据：`商业售卖版账号权限与授权系统实施计划.md`

---

## 一、总则

### 1.1 新增模块必须先纳入授权体系

任何需要按账号售卖、按设备控制、按时间到期的新功能，**必须**先在后端完成授权接入，再开发桌面端入口和管理后台配置页面。

禁止出现以下情况：
- 桌面端直接绕过 `commercialAuthStore.isModuleAllowed()` 判断
- 后端接口不校验模块授权就直接返回核心数据
- 管理后台无法为新模块设置授权/到期时间

### 1.2 实施顺序

严格遵循：
```
服务端数据库/API → 管理后台配置页 → 桌面端 UI 入口 → Rust 二次校验（关键操作）
```

### 1.3 模块代码注册

新增模块必须首先在 `AuthConstants` 中注册标准 `moduleCode`：

```java
// server/src/main/java/com/superprogrammer/security/AuthConstants.java
public static final String MODULE_FILES = "files";
public static final String MODULE_PROCESSES = "processes";
public static final String MODULE_CLIPBOARD = "clipboard";
// 新增：
public static final String MODULE_XXX = "xxx";
```

`moduleCode` 规则：
- 全小写英文
- 使用单数名词
- 多个单词用 `-` 连接，例如 `smart-tags`
- 长度不超过 32 字符
- 禁止与现有 `files`、`processes`、`clipboard` 重复或语义冲突

### 1.4 模块注册检查清单

新增模块前必须确认：
- [ ] `moduleCode` 已在 `AuthConstants` 注册
- [ ] 后端 `MODULE_CODES` 列表已包含新模块
- [ ] 前端 `MODULE_LABEL_MAP` 已添加中文名
- [ ] 管理后台授权编辑器和系统设置已支持该模块
- [ ] 桌面端 `useModuleAccess` 或 `isModuleAllowed` 已生效
- [ ] 关键 Rust 命令已加入二次校验（如适用）

## 二、数据库规范

### 2.1 Flyway 迁移

新增模块如涉及数据表，必须创建新的 Flyway 迁移文件，命名格式：
```
Vx__short_description.sql
```

规则：
- 版本号必须递增
- 迁移脚本必须兼容 PostgreSQL 和 H2（测试数据库）
- `ALTER TABLE ADD COLUMN` 必须单条语句
- 字段类型变更使用 `ALTER COLUMN ... SET DATA TYPE`
- 新增表必须包含 `created_by/created_at/updated_by/updated_at/deleted` 字段

### 2.2 与授权表的关系

如果模块需要记录用户数据，建议通过 `user_id` 关联 `users` 表，**不要**通过模块权限反推用户关系。

模块授权状态以 `user_module_entitlements` 表为准，业务数据表不存储授权状态。

### 2.3 CHECK 约束

涉及 `module_code` 的字段必须加 CHECK 约束，且包含所有已注册模块：

```sql
CONSTRAINT ck_user_module_entitlements_module CHECK (
    module_code IN ('files', 'processes', 'clipboard', 'xxx')
)
```

## 三、后端规范

### 3.1 授权服务接入

新增模块必须让 `AuthorizationService` 识别。修改：
- `server/.../authorization/service/AuthorizationService.java`

将新 `moduleCode` 加入 `MODULE_CODES` 常量列表：

```java
private static final List<String> MODULE_CODES = List.of(
    AuthConstants.MODULE_FILES,
    AuthConstants.MODULE_PROCESSES,
    AuthConstants.MODULE_CLIPBOARD,
    AuthConstants.MODULE_XXX
);
```

### 3.2 客户端接口授权校验

如果新增模块提供客户端接口，Controller 必须：
1. 从 `AuthorizationService` 获取用户权益快照
2. 检查 `moduleCode` 是否 `allowed`
3. 未授权返回 `403` 或对应业务错误

示例：
```java
public R<SomeData> getSomeData(Authentication auth, @RequestParam String deviceId) {
    AuthPrincipal principal = (AuthPrincipal) auth.getPrincipal();
    AuthorizationSnapshot snapshot = authorizationService.authenticatedSnapshot(
        principal.userId(), deviceId, System.currentTimeMillis()
    );
    boolean allowed = snapshot.modules().stream()
        .anyMatch(m -> AuthConstants.MODULE_XXX.equals(m.moduleCode()) && m.allowed());
    if (!allowed) {
        return R.fail(ErrorCode.FORBIDDEN, "未授权访问 xxx 模块");
    }
    // ... 返回数据
}
```

### 3.3 匿名用户访问控制

如果匿名用户也需要使用新模块：
- 必须在 `AnonymousTrialService.anonymousModules()` 中决定试用期内/过期后是否允许
- 默认匿名过期后只允许已选择的 `freeModuleCode`，新增模块不能自动变成免费模块
- 如需让新模块成为可选免费模块，必须同步修改前端 `FreeModuleSelector`

### 3.4 离线 Token 支持

`AuthorizationService.authenticatedSnapshot()` 会自动将 `MODULE_CODES` 中 `allowed` 的模块写入离线 Token。新增模块只要加入列表，无需额外修改离线 Token 签名逻辑。

### 3.5 管理后台 API

新增模块若需管理端配置，必须：
- 在 `AdminEntitlementController` 或新建 Admin Controller 中提供 API
- 使用 `@RequirePermission` 或 `hasRole("SUPER_ADMIN")` 保护
- 高风险操作记录审计日志 `admin_audit_logs`

### 3.6 错误码

新增模块特定业务错误优先复用现有 `ErrorCode`：
- `FORBIDDEN(403)` — 无模块权限
- `UNPROCESSABLE(422)` — 业务规则违反
- 如需新增错误码，在 `ErrorCode` 枚举中添加，并确保前端能处理

## 四、桌面端规范

### 4.1 模块入口门禁

所有新增模块的入口必须在 `App.vue` 或对应 Tab 中通过 `commercialAuthStore.isModuleAllowed()` 控制。

示例：
```vue
<n-tab-pane name="xxx" tab="新模块">
  <UnauthorizedModulePanel
    v-if="!commercialAuthStore.isModuleAllowed('xxx')"
    module-code="xxx"
  />
  <XxxManagement v-else />
</n-tab-pane>
```

### 4.2 关键操作 Rust 二次校验

如果新模块涉及敏感本地能力（如结束进程、截图、剪贴板监听、文件删除、网络请求等），必须在 Rust 命令中加入授权校验：

1. 前端调用 Rust 命令时传入 `offlineToken` 或模块信息
2. Rust 端调用 `check_offline_access` 或独立校验逻辑
3. 未授权直接拒绝执行

参考：
- `file-keeper/src-tauri/src/commands/auth.rs`

### 4.3 匿名用户处理

新模块若支持匿名用户：
- 试用期内：全功能可用
- 试用期后：仅在用户选择的免费模块为当前模块时可用
- 离线时：不可用（匿名必须联网）

### 4.4 离线缓存处理

登录用户离线使用新模块时：
- 模块权限由 Rust 离线 Token 校验决定
- 前端不要仅依赖 JS 内存中的权限
- 缓存过期后应提示用户联网刷新

### 4.5 状态展示

在 `EntitlementStatus.vue` 或新增状态组件中展示新模块授权状态：
- 已授权且未过期
- 已授权但已过期
- 未授权
- 匿名试用中
- 匿名过期后作为免费模块

## 五、管理后台规范

### 5.1 用户授权编辑器

`UserEntitlementEditor.vue` 或等效组件必须：
- 显示新模块的授权开关
- 支持设置到期时间
- 保存时调用 `/api/admin/users/{id}/entitlements`

如果新增模块有额外配置（如配额、限制），应扩展授权编辑器或新建配置卡片。

### 5.2 系统设置默认值

如果新模块需要全局默认配置（如默认配额、开关），必须：
- 在 `SystemSetting` 表中新增配置项
- 在 `SystemSettingsBundle` DTO 中添加字段
- 在 `SystemSettingService` 中添加读取方法
- 在 `admin-web/src/views/SettingsView.vue` 中添加编辑 UI

### 5.3 Dashboard 统计

如果新模块需要在 Dashboard 展示统计指标：
- 在 `DashboardStats` DTO 中添加字段
- 在 `AdminStatsService` 中实现统计逻辑
- 在 `DashboardView.vue` 中添加展示卡片

### 5.4 设备/匿名设备管理

如果新模块的设备限制需要特殊处理（如按设备独立授权），应评估是否扩展 `user_devices` 表或新建关联表。

## 六、安全规范

### 6.1 禁止上传业务数据

新增模块必须遵循：
- 不上传文件收藏路径、剪贴板内容、截图内容、进程列表等业务数据
- 可上传授权校验所需的元数据（如 deviceId、模块代码、时间戳）

### 6.2 审计日志

新增管理后台高风险操作必须记录审计日志：
- 授权变更
- 设备禁用/启用/解绑
- 用户禁用/启用
- 系统设置变更

### 6.3 权限最小化

新增接口默认需要认证，对外暴露接口前必须评估：
- 是否需要管理员权限
- 是否需要登录用户权限
- 是否允许匿名访问

## 七、测试规范

### 7.1 必须编写的测试

新增模块必须包含：
- 后端：模块授权判定测试
- 后端：匿名用户模块权限测试
- 后端：离线 Token 包含新模块测试
- 桌面端：模块入口显示/隐藏测试
- 桌面端：未授权状态展示测试
- 管理后台：授权编辑器保存测试

### 7.2 TDD 步骤示例

```
1. 写测试：新模块未授权时后端返回 403
2. 运行测试，确认失败
3. 实现后端授权校验
4. 重新运行测试，确认通过
5. 写测试：管理后台可为用户授权新模块
6. 运行测试，确认失败
7. 实现管理后台授权 API 和 UI
8. 重新运行测试，确认通过
9. 写测试：桌面端未授权时显示未授权面板
10. 实现桌面端门禁
11. 重新运行测试，确认通过
```

### 7.3 验证命令

提交前必须运行：
```bash
mvn -f "file-keeper/server/pom.xml" test
npm --prefix "file-keeper/admin-web" test
npm --prefix "file-keeper/admin-web" run build
npm --prefix "file-keeper" test
npm --prefix "file-keeper" run build
cargo test --manifest-path "file-keeper/src-tauri/Cargo.toml"
```

## 九、禁止事项

1. **禁止**新增模块后直接放行，不做授权校验
2. **禁止**在前端隐藏模块入口但保留深层路由可访问
3. **禁止**把用户业务数据作为授权依据上传到服务端
4. **禁止**新增管理员接口但不记录审计日志
5. **禁止**修改现有 `moduleCode` 语义（如把 `files` 改成其他含义）
6. **禁止**离线 Token 中允许未授权的模块
7. **禁止**未测试直接合并到主分支

- [ ] 测试覆盖新增代码
