# 3.5 交互状态与异常处理

## D.05 核心交互状态模型

数字产品中的7种核心状态：

| 状态 | 用户感受 | 设计要点 |
|---|---|---|
| **理想态** | "一切正常，我能完成目标" | 核心流程丝滑、主要功能可达 |
| **空状态** | "什么都没有" | 引导创建/导入/首屏示例；而非一片空白 |
| **加载态** | "要等多久？" | 骨架屏/进度条/趣味动效；明确预期等待时间 |
| **错误态** | "出错了" | 清晰说明"什么错了+怎么办"；可操作修复 |
| **部分数据态** | "有些信息不完整" | 提示补充+区分完整/不完整体验 |
| **离线态** | "没网了" | 离线可用功能+缓存+同步提示 |
| **权限受限态** | "我不能做这个" | 说明原因+引导申请/升级 |

## I.07 异常处理设计模式

### 加载体验设计

| 方案 | 适用场景 | 优势 | 风险 |
|---|---|---|---|
| 骨架屏(Skeleton) | 列表/卡片内容加载 | 视觉连续、预期形状 | 不适合复杂交互页 |
| 进度条 | 可预知进度(下载/上传) | 用户可控感 | 进度不准比没有更糟 |
| Spinner | 简短等待(<2s) | 通用 | 成本感无预期 |
| 趣味动效 | 品牌向等待页 | 降低焦虑感 | 动效不能掩盖慢速度 |

**时长设计规则**：
- <100ms → 即时响应，无加载指示
- 100ms-1s → Spinner/微型加载
- 1s-10s → 骨架屏/进度条
- >10s → 分步加载+后台任务通知

### 错误处理三原则

1. **可见性**：错误信息必须被用户看见（不被遮挡、醒目颜色）
2. **可理解**：用用户语言解释（不说"Error 500"，说"服务器暂时无法响应"）
3. **可行动**：提供修复路径（重试/返回/联系客服）

### Toast/Snackbar vs Alert vs Modal

| 组件 | 用途 | 中断程度 | 自动消失 |
|---|---|---|---|
| Toast | 轻量反馈（已保存/已复制） | 非中断 | ✅2-4s |
| Snackbar | 可操作轻提示（撤销操作） | 低中断 | ✅5-8s |
| Alert/Dialog | 需确认的重要操作 | 中断 | ❌需用户关闭 |
| Full-page Error | 严重错误/系统级故障 | 全中断 | ❌需用户操作 |

## E.03 常见坑

| 坑 | 表现 | 修法 |
|---|---|---|
| 空状态一片白 | 新用户什么内容都看不到 | 空状态引导+示例数据+创建按钮 |
| 加载无反馈 | 点了按钮没反应 | 即刻反馈（按钮变灰/Spinner） |
| 错误语气冰冷 | "操作失败"无任何引导 | "网络不给力，点击重试"+可操作按钮 |
| 离线无提示 | 断网后操作全部丢失 | 离线检测+本地缓存+恢复同步 |
| 权限报错只弹窗 | "无权访问"后用户无处可去 | 解释原因+引导申请权限/升级 |
