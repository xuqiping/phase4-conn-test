## 一、推送通知权限演进

### 1.1 Android推送权限变更（Android 13+致命变化）

**Android 13（API 33）——POST_NOTIFICATIONS运行时权限**

这是Android推送领域近年来最大的破坏性变更：Android 13之前，App安装后默认拥有推送权限；Android 13+起，推送变为**运行时权限**，必须由用户主动授权。

| 维度 | Android 12及以下 | Android 13+ |
|---|---|---|
| 推送权限 | 默认开启，用户可在设置中关闭 | 默认关闭，须弹窗请求用户授权 |
| 权限名称 | 无独立权限 | `POST_NOTIFICATIONS`(API 33) |
| 用户拒绝后 | 推送投递成功但被系统静默 | 推送通道降级，部分通知不展示 |
| 适配要求 | 无 | target API 33+(2024年强制)须声明并请求该权限 |

**PM必须做的适配动作**：
1. **target API升级**：升到API 33+时必须声明`POST_NOTIFICATIONS`权限并实现请求逻辑
2. **引导设计**：首次推送请求弹窗前，先展示"为什么需要推送通知"的预引导页，提高授权率
3. **回退策略**：用户拒绝后，不做二次频繁弹窗（系统会拒绝），但在Settings页提供"开启推送"入口
4. **渠道(Channel)配置**：Android 8+的通知渠道须正确配置，用户拒绝某渠道不影响其他渠道

> **数据影响**：Android 13+推送权限授权率行业平均约45-60%（相比Android 12的~95%默认通过率大幅下降）。PM需在产品数据中跟踪推送授权率指标。

[来源:Android Developers官方文档 | 置信度:🔍高 | 2025-2026]

**Android 14（API 34）补充变更**：
- 前台服务类型声明：使用前台服务的App须声明具体类型（dataSync/health/location/mediaPlayback等），不当声明会导致拒审或崩溃
- 非导出组件：注册了intent-filter的Receiver/Service默认须显式声明`android:exported`，推送相关Receiver需正确配置

### 1.2 iOS推送权限机制

| 维度 | 要求 | PM关注点 |
|---|---|---|
| APNs配置 | 须在Apple Developer Console配置推送证书/Key | 开发/生产环境用不同证书 |
| 推送权限弹窗 | 首次请求时系统弹窗，用户可"允许/不允许" | 预引导页提高授权率；拒绝后无法再次系统弹窗 |
| Provisional Authorization | iOS 12+特性：可发送"静默推送"，用户不弹窗即可收到通知 | 适合低频通知场景，但用户可随时关闭 |
| Critical Alerts | 紧急警报通知，可绕过静音/专注模式，须申请特殊 entitlement | 医疗/安全类App才可申请 |
| ATT对推送的影响 | 推送本身不依赖ATT，但如果推送含个性化内容（如基于行为推荐），则涉及ATT | 个性化推送文案须遵守ATT框架 |

**iOS推送授权率最佳实践**：
- **Pre-permission策略**：在系统弹窗前，先弹自定义引导页说明推送价值，用户点击"好的"后再触发系统弹窗 → 授权率提升至70-80%（相比直接系统弹窗的40-50%）
- **场景驱动请求**：不在App启动时请求，而在用户完成某操作后请求（如完成订单后请求"订单状态通知"）→ 授权率提升显著

[来源:Apple Developer Push Notifications | 置信度:🔍高 | 2025-2026]

### 1.3 Android国内推送特殊性

中国大陆Android生态碎片化严重，Google FCM不可用，各厂商有自研推送通道：

| 推送通道 | 适用厂商 | 特点 |
|---|---|---|
| 华为推送(HMS Push Kit) | 华为设备 | 系统级长连接，到达率高 |
| 小米推送(MiPush) | 小米设备 | 系统级，支持透传/通知栏 |
| OPPO推送 | OPPO/OnePlus设备 | 系统级，需用户主动开启 |
| vivo推送 | vivo设备 | 系统级，支持应用分组 |
| 个推/友盟推送 | 全平台聚合SDK | 一套SDK适配多厂商，但到达率不如系统级通道 |

> **PM关建决策**：国内推送必须做"聚合推送"方案——集成个推/友盟等第三方SDK + 厂商通道（华为/小米/OPPO/vivo），通过聚合SDK根据设备品牌自动路由到对应系统级通道，最大化到达率。

[来源:个推/友盟推送官方文档 | 置信度:📚中 | 2025-2026]

### 1.4 微信小程序订阅消息

微信小程序的推送机制与App完全不同，经历了从"模板消息"到"订阅消息"的演进：

| 维度 | 旧版模板消息(已废弃) | 订阅消息(现行) |
|---|---|---|
| 生命周期 | 2020年1月10日下线 | 2020年起至今 |
| 触发方式 | 用户触发交互后48小时内可发 | 用户须主动"订阅"(点击授权) |
| 一次性 vs 长期 | 无区分 | 一次性订阅（每条消息需用户授权一次）+ 长期订阅（医疗/政务等限定类目） |
| 模板限制 | 固定行业模板 | 须在小程序后台申请模板，审核通过后可用 |
| 发送频率 | 无硬限制 | 一次性订阅：用户授权1次→发送1条；长期订阅：无频率限制 |

**PM注意**：
- 订阅消息的"一次性"是最易踩坑设计——用户点击"允许"只能发1条消息，不能持续推送。产品交互须在恰当场景引导用户重复授权。
- 长期订阅仅对特定类目开放（政务民生/医疗/交通等），大多数消费类小程序只能用一次性订阅消息。

[来源:微信开放文档订阅消息 | 置信度:🔍高 | 2025-2026]

## 二、位置权限演进与适配

### 2.1 Android位置权限分层

| 权限 | API Level | 用途 | 要求 |
|---|---|---|---|
| ACCESS_COARSE_LOCATION | API 1+ | 大致位置（基站/Wi-Fi） | runtime permission |
| ACCESS_FINE_LOCATION | API 1+ | 精确位置(GPS) | runtime permission |
| ACCESS_BACKGROUND_LOCATION | API 29+ | 后台位置 | 须单独申请，且需解释为何需后台定位 |

**Android 10关键变化**：后台位置采集须用户通过Settings页单独授予（非运行时弹窗可获取），且Google Play要求target API 29+的App须做"后台位置使用声明"。

**Android 11关键变化**：位置权限仅可实现"仅这次"（one-time）授权，用户可限制为一次性使用。

### 2.2 iOS位置权限

| 权限 | 说明 | 获取方式 |
|---|---|---|
| When In Use | 前台使用时定位 | 标准运行时权限弹窗 |
| Always | 始终定位（含后台） | 先申请When In Use → 后续再引导升级为Always |
| Precise/Approximate | 精确/大致位置 | iOS 14+用户可选择大致位置，App须适配降级场景 |

> **Apple审核严格要求**：申请Always权限的App必须说明后台定位的必要性，否则按5.1.5拒绝。

[来源:Apple/Android官方文档 | 置信度:🔍高 | 2025-2026]

## 三、其他权限关键变更

### 3.1 相机与麦克风

- **Android 14+**：前台服务类型为camera/microphone时须在manifest声明complement类型
- **iOS 15+**：相机/麦克风权限申请须填写Info.plist中的Usage Description，且说明文字审核日趋严格——不能只是"用于拍照"，须说明具体功能用途

### 3.2 存储权限（Android Scoped Storage）

| Android版本 | 存储权限变化 | PM影响 |
|---|---|---|
| Android 10 | Scoped Storage引入（可opt-out） | App只能访问自己目录和媒体文件 |
| Android 11 | Scoped Storage强制启用（不可opt-out） | 必须适配Scoped Storage，旧式文件共享方式失效 |
| Android 13+ | Photo Picker替代READ_EXTERNAL_STORAGE | 推荐使用Photo Picker API获取图片/视频，无需请求存储权限 |

> **PM决策**：Android 13+推荐用Photo Picker替代传统文件选择器——减少权限请求，提升审核通过率，同时改善用户隐私体验。

[来源:Android Developers Storage | 置信度:🔍高 | 2025-2026]

### 3.3 权限申请最佳实践

```
原则1: 按需请求 — 功能使用时才请求权限，不在App启动时一次性请求所有权限
原则2: 预引导 — 系统弹窗前用自定义页面解释权限用途，展示"为什么需要" → 提高3-5倍授权率
原则3: 优雅降级 — 用户拒绝后提供替代方案（如拒绝定位→手动选择城市）
原则4: 不重复请求 — 用户拒绝后不频繁弹窗，引导到Settings页说明开启方式
原则5: 透明告知 — 每个权限申请都须有清晰的使用说明（Info.plist Usage Description / Android shouldShowRequestPermissionRationale）
```
