# 08 - 智能对话与流式

## 功能简介
对话会话管理、聊天目标（Agent/工作流）选择、消息发送、SSE 流式回复、WebSocket 通道、历史消息。

## 后端 (backend)
- 控制器：[ChatController.java](../../backend/src/main/java/com/superprogrammer/chat/controller/ChatController.java)
  - 会话：`POST /api/chat/sessions` `GET /sessions` `GET /sessions/{id}` `PUT /sessions/{id}` `DELETE /sessions/{id}` `DELETE /sessions/batch`(批量删，body=Long[]) `PUT /sessions/{id}/target`(切换 Agent/工作流目标) `GET /sessions/{id}/messages`
  - 聊天目标：`GET /targets`
  - 发消息：`POST /sessions/{id}/messages` `POST /messages`（非流式）`POST /sessions/{id}/messages/stream` `POST /messages/stream`（SSE 流式）
- 记忆自服务（对话联动，详见 [09-个人记忆与冲突解决](09-个人记忆与冲突解决.md)）：[MemoryController.java](../../backend/src/main/java/com/superprogrammer/chat/controller/MemoryController.java) `/api/chat/memories`
  - `GET /memories`(列) `PUT/{id}`(行内编辑) `DELETE/{id}` `DELETE`(清空) `DELETE/batch` `POST/preview`(注入预览) `GET/{id}/scopes` `PUT/{id}/scopes`
  - 冲突：`GET /conflicts` `PUT /conflicts/{id}/resolve` `POST /conflicts/batch-resolve`
  - **状态轮询（前端常驻 3s 轮询）**：`GET /memories/status`(processingCount+conflictCount，驱动顶部「记忆记录中…」状态条) `GET /memories/incident`(写入异常，取即清) `GET /memories/rag-mode`(用户级只读全局开关)
- WebSocket：
  - [WebSocketConfig.java](../../backend/src/main/java/com/superprogrammer/chat/config/WebSocketConfig.java)
  - [ChatWebSocketHandler.java](../../backend/src/main/java/com/superprogrammer/chat/websocket/ChatWebSocketHandler.java)
  - [WebSocketAuthInterceptor.java](../../backend/src/main/java/com/superprogrammer/chat/websocket/WebSocketAuthInterceptor.java)
- 服务：`chat/service/` ChatSessionService、ChatTargetService（编排走 [engine](11-工作流执行与编排引擎.md)）
- DTO：ChatRequest、ChatResponse、StreamEvent、SessionVO、ChatTargetVO
- 实体：`chat/entity/` ChatSession、ChatMessage

## ⚠️ 调试注意
- 流式路径在 reactor-http-nio 线程，**禁 `.block()`**；LLM/WebClient 须 `subscribeOn(boundedElastic)`。复现 bug 必须打 streaming 端点，non-stream servlet 跑通会掩盖问题。
- **`doStream` 用裸 `new Thread()`**（[ChatController.java:126](../../backend/src/main/java/com/superprogrammer/chat/controller/ChatController.java#L126)）而非线程池，每条流式请求起一个无上限线程，`blockLast(120s)`；LLM 挂则线程挂 120s，异常还 fallback 同步 `sendMessage` 再调一次 LLM。高并发或 LLM 慢时**线程无限膨胀**——是 [RB-001 死亡螺旋](../项目漏洞核查/运行时bug.md) 的线程耗尽贡献源之一。
- 记忆 `status`/`incident` 轮询本应秒回（count + map remove）。若它们开始 15s 超时 = **Tomcat 线程池被打满**（被挂死的 LLM/streaming 调用吃光），不是端点本身慢——见 [运行时bug.md](../项目漏洞核查/运行时bug.md) RB-001。
