# 5.1 Intercom RICE发源与实践

## 案例

2016年，Intercom产品团队在博客发表《Prioritizing Product Work with RICE》，系统提出RICE框架。Intercom当时面临的挑战：产品团队从3人增长到40+人，需求从几十个膨胀到数百个，传统的"谁嗓门大听谁的"和"老板拍板"方式已无法支撑规模化决策。

## Intercom的痛点

| 痛点 | 描述 |
|---|---|
| **直觉偏见** | PM倾向于做自己喜欢的功能，而非最有价值的功能 |
| **政治驱动** | 销售/运营/老板各自推动自己关心的需求，无统一语言 |
| **不可解释** | 为什么选A不选B？"感觉A更重要"→无法复盘 |
| **短期偏好** | 紧急但不重要的需求挤占重要但不紧急的需求 |

## RICE的设计哲学

1. **量化而非定性**：用分数替代"高/中/低"的模糊分类
2. **多维度而非单维度**：不只看"价值"或"成本"，而是四维交叉
3. **信心度惩罚猜测**：Confidence维度让猜测付现代价
4. **除以Effort**：促进"高ROI优先"而非"高价值优先"
5. **可讨论**：每个维度都可以被挑战和修正，分数是讨论的**起点**

## Intercom的实践要点

| 实践 | 说明 |
|---|---|
| **Reach用真实数据** | 不允许猜测Reach——必须查产品数据 |
| **Impact用离散5档** | 避免"伪精度"(如Impact=2.3) |
| **Confidence诚实打分** | 要求每个维度标注数据来源 |
| **Effort由工程师确认** | PM不允许自估Effort |
| **分数是讨论起点** | 不允许"RICE说了算"——最终决策仍需PM判断 |

## 对PM的启示

> Intercom的RICE不是"算法决策"——是"结构化讨论"工具。分数的权力来自"你能否解释每一维度的依据"，而非"分数最高就做"。[来源:Intercom Blog·RICE:简单的优先级管理方法 | 🔍高 | 2016]
