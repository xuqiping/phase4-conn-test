# 5.3 B端SaaS RICE评估实践

## 案例

B端SaaS产品的RICE评估与C端有本质差异——用户少但ARPU高、决策链长、需求来源复杂（客户/销售/实施/合规）。以下是B端SaaS的RICE适配方法论。

## B端RICE的三个关键适配

### 适配一：Reach无法用"人数"

B端的用户数量远少于C端，但单用户价值极高。简单用"人数"做Reach会导致：

| 错误做法 | 问题 | 正确做法 |
|---|---|---|
| 用MAU计Reach | 10个客户×5个用户=50人，RICE极低 | 用**ARR权重**：Reach = 受影响客户ARR之和 / 总ARR |
| 给大客户需求Impact=3 | 大客户≠高价值（可能是定制需求） | Impact仍按**功能本身的影响力**打分，客户重要性放入Confidence |

**B端Reach公式**：
```
Reach(ARR) = 受影响客户的年度经常性收入之和 / 总ARR × 100
```

> 例：总ARR=1000万，需求影响3个大客户共200万ARR → Reach=20

### 适配二：客户分层的RICE分别计算

B端客户的KANO+RICE分布差异巨大——大客户和小客户的需求几乎完全不同：

| 客户层 | 需求特征 | RICE特点 |
|---|---|---|
| **大客户(ARR Top 20%)** | 深度定制、集成、合规 | Reach低但Mandatory高 |
| **中客户(ARR 中间)** | 通用功能、效率提升 | RICE正常运作 |
| **小客户(ARR 长尾)** | 简化操作、价格敏感 | Reach高但Impact低 |

**策略**：大客户需求用RICE-M(M=2-∞)，中客户用标准RICE，小客户用RICE + 成本约束（Effort占比高时不做）。

### 适配三：销售/CS驱动的需求评估

B端需求大量来自销售赢单和客户成功续约，而非产品主动规划：

| 需求来源 | RICE适配 | 说明 |
|---|---|---|
| 销售赢单需求 | RICE-M，M=赢单概率×ARR增量 | "不做这个功能就不签单"→M=∞ |
| CS续约需求 | RICE-M，M=流失风险×ARR | "不做就续约不了"→M=流失风险的ARR |
| 产品主动规划 | 标准RICE | 无特殊权重 |
| 合规/安全 | M=∞ | 不做=罚款/法律风险 |
