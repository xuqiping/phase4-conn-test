# 5类冲突场景话术模板

## 使用说明
本模板覆盖PM在沟通协作中最常见的5类冲突场景。每类提供：冲突描述、错误话术、正确话术、底层逻辑。话术不是"话术"——是思维方式的体现。

---

## 场景1：开发说"做不了"

**冲突描述**：PM提了需求，开发直接说"做不了"，PM不知道该坚持还是放弃。

| 维度 | 内容 |
|---|---|
| ❌错误话术 | "这个必须做，你自己想办法" / "那算了，不做了" |
| ✅正确话术 | "理解有技术难度。能帮我理解一下具体是哪个环节做不了吗？是技术完全不可行，还是时间/资源不够？如果是时间问题，我们看看能不能分期；如果是技术约束，有没有替代方案能达成同样的用户目标？" |
| 底层逻辑 | 用5层深挖法把"做不了"拆解为具体约束——"做不了"是结论不是原因，PM需要的是原因 |
| 关键原则 | 先理解约束，再谈方案；对事不对人；用"用户目标"而非"功能需求"来重新定义问题 |

**话术变体（按情境）**：

| 情境 | 话术 |
|---|---|
| 开发态度消极 | "我知道最近排期很紧，这个需求我也不想硬推。我们一起看看有没有最小实现方案——先把核心链路做出来，后续迭代优化？" |
| 开发给了技术理由 | "感谢解释。那按你说的技术约束，如果我们调整X方案为Y方案，能不能实现？用户核心诉求是Z，不一定非要X方式。" |
| 开发说"永远做不了" | "如果当前架构不支持，那我们评估一下：是放到技术重构后的路线图里，还是现在找替代方案？你建议哪个？" |

## 场景2：设计审美分歧

**冲突描述**：PM觉得设计不够直观/不够好，设计师觉得PM不懂设计，双方陷入主观争论。

| 维度 | 内容 |
|---|---|
| ❌错误话术 | "这个不好看，改一下" / "你不懂用户" |
| ✅正确话术 | "我看到这个设计在X方面很有创意。我担心的是Y场景下用户可能困惑——能不能我们一起做个5用户快速测试来验证？如果用户没问题，我接受这个方案。" |
| 底层逻辑 | 把主观审美争论转化为客观用户测试——用数据替代直觉，用测试替代争论 |
| 关键原则 | 不评判"美丑"，只讨论"是否解决了用户问题"；回归业务目标 |

**话术变体（按情境）**：

| 情境 | 话术 |
|---|---|
| 分歧在于一致性 | "我理解你想在这里做创新。但我们的设计系统里同类组件都是X样式，如果我们改了Y，其他页面要不要跟着改？我们评估一下一致性成本。" |
| 分歧在于信息层级 | "我关注的是用户第一眼看到的是不是最重要的信息。我们能不能用热力图/眼动测试来验证一下信息层级是否合理？" |
| 分歧在于交互复杂度 | "这个交互很精致。但我担心新用户的学习成本——我们看看能不能保留核心交互，简化辅助交互？" |

## 场景3：运营/销售过度承诺

**冲突描述**：销售对客户承诺了产品还没有的功能，或运营定了上线日期但产品还没开发完。

| 维度 | 内容 |
|---|---|
| ❌错误话术 | "你们怎么能乱承诺！" / "这个做不了，你们自己去解释" |
| ✅正确话术 | "我知道承诺客户是为了成单/推节奏。现在的情况是X功能预计Y时间能上线。我建议这样处理：1）先用现有功能的Z组合来满足客户核心诉求；2）X功能排在下个版本优先级最高；3）我和你一起跟客户沟通时间线。你觉得呢？" |
| 底层逻辑 | 不指责过去（承诺已发生），聚焦未来（怎么收拾残局）——把"PM vs 销售"变为"PM+销售 vs 问题" |
| 关键原则 | 先解决客户问题，再建立流程防止复发；不甩锅但也不背锅 |

**话术变体（按情境）**：

| 情境 | 话术 |
|---|---|
| 销售承诺了不存在的功能 | "我理解这个功能对成单很重要。目前产品没有这个功能，最快X周能做出来。在此期间，我们可以用Y方式作为过渡方案。建议我们一起制定一个'销售承诺PM审核流程'，以后避免类似情况——我也保证审核不超过24小时。" |
| 运营定了上线日期但产品没跟上 | "我看到运营排了X号推广。目前产品进度是Y，如果按原计划上线有Z风险。我们有两个选择：A）产品赶工X号上线但可能质量打折扣；B）推广推迟1周到X+7号。我建议B，你评估一下推广推迟的影响？" |

## 场景4：向上汇报坏消息

**冲突描述**：项目出了问题/要延期，PM不敢跟老板说，或者说了但方式不对导致老板暴怒。

| 维度 | 内容 |
|---|---|
| ❌错误话术 | "老板，出事了…" / "项目要延期了"（没有原因没有方案） |
| ✅正确话术 | "老板，同步一个风险：项目有延期风险，可能延X天。根因是Y。我已做了Z应对措施，目前最坏情况是延X天。需要您决策的是W。如果您同意Z方案，我预计能把延期控制在X-2天内。" |
| 底层逻辑 | 坏消息+根因+方案+影响范围+需要决策=完整的坏消息汇报。老板暴怒的不是"有坏消息"而是"没有方案" |
| 关键原则 | 24小时内汇报；带着方案而非问题；说清最坏情况；给出需要老板做的决策 |

**话术变体（按情境）**：

| 情境 | 话术 |
|---|---|
| 技术问题导致延期 | "老板，技术团队发现X问题，影响上线时间。根因是Y。技术团队评估了3个方案：A方案需+5天但风险低，B方案需+2天但风险中，C方案不延期但可能影响稳定性。我建议A方案。需要您确认是否接受延期5天。" |
| 需求变更导致延期 | "老板，业务方在X节点提了新需求Y。如果加进去，项目延期Z天。如果不加，按原计划上线，Y放入下个版本。我建议先按原计划上线——Y不是上线必须的。需要您拍板。" |
| 人员离职影响项目 | "老板，X同学提了离职，他负责Y模块。影响评估：短期内Z工作无人接手。我的应对方案是：1）A同学暂代Y模块；2）X同学离职前完成知识交接文档；3）启动招聘。需要您确认是否紧急招聘。" |

## 场景5：跨部门推不动

**冲突描述**：PM需要其他部门配合但推不动——对方说"没排期"或"不是我们的优先级"。

| 维度 | 内容 |
|---|---|
| ❌错误话术 | "这个是公司战略，你们必须配合" / "你们不配合我没办法" |
| ✅正确话术 | "我理解你们有自己的优先级。这个项目对你们部门的OKR也有X贡献——如果我们对齐一下OKR，把这件事纳入你们Q3目标，资源是不是好排一些？如果确实排不开，我们一起评估：是调整项目范围还是调整时间线？" |
| 底层逻辑 | 用OKR对齐替代权力施压——跨部门协作不是"谁求谁"，而是"共同目标对齐"。如果对方OKR里没有这个项目，先解决OKR对齐问题 |
| 关键原则 | 先找共同利益，再谈资源分配；用数据/OKR说话而非用权力/情绪说话 |

**话术变体（按情境）**：

| 情境 | 话术 |
|---|---|
| 对方说"没排期" | "理解。你们本季度的重点是什么？我们看看这个项目能不能和你们的重点对齐——如果能对齐，排期就好说了。如果确实对不上，我们评估是否调整项目时间线。" |
| 对方说"不是我们的事" | "我查了一下RACI矩阵，这件事你们部门是R（执行者），我们部门是A（负责人）。如果你们确实没资源，我们需要一起升级到各自的部门负责人，重新分配RACI。你建议怎么升级？" |
| 对方消极配合 | "我注意到最近几次交付都有延迟。是不是遇到了什么困难？我能做什么来帮你们排除障碍？我们目标是把这个项目做成，不是互相为难。" |

## 通用话术原则

| 原则 | 说明 |
|---|---|
| 先共情再解决 | "我理解…"不是废话——它让对方从防御模式切换到合作模式 |
| 对事不对人 | 说"这个方案有X风险"而非"你的方案有问题" |
| 给选项而非给指令 | "A还是B？"比"你应该做A"更容易被接受 |
| 用数据/OKR替代情绪 | "数据显示X"比"我觉得X"更有说服力 |
| 聚焦未来而非追责 | "怎么解决"比"谁的错"更重要——追责留到复盘 |
