# 服务器更新再部署说明（代码更新后重新上线）

> 受众：改完代码要把新版本推上服务器的你 / 部署人 / AI。
> 前提：服务器已按 `部署手册终.md` 完成首次部署（WinSW 服务 `agent-backend`、Nginx、PG、Redis 都在跑）。
> 本文只管「**增量更新**」——代码变了，重新打包、替换、重启、验证、回滚。**不涉及**首次安装。

## 〇、什么时候只要更新前后端就够了

| 变更类型 | 要动什么 |
|---|---|
| 只改了 Java/Vue 代码 | 换 jar + 换 dist，**就这两样**（最常见） |
| 新增/改了 Flyway 迁移（`db/migration/V*.sql`） | 同上——迁移打进 jar，**后端启动时 Flyway 自动补跑**，不用手工执行 SQL |
| 新增/改了环境变量（application.yml 引了新 `${XXX}`） | 换 jar + 改 WinSW XML 的 `<env>` 或系统环境变量 + 重启服务 |
| 改了 Nginx 配置 | 换 dist + 改 nginx.conf + `nginx -s reload` |
| 改了 ops-config（监控/巡检脚本） | 同步对应文件，按 `ops-config\文件说明.md` 重启对应组件 |

**判断有没有新迁移**：`git log --oneline -- backend/src/main/resources/db/migration/` 对比服务器上次部署的版本号（Flyway 版本表 `flyway_schema_history` 里 `MAX(version)`）。

## 一、开发机打包（在本仓库根执行）

```powershell
# 后端（在 agent-platform/backend/ 下）：产出 target/agent-platform-0.1.0-SNAPSHOT.jar
mvn package -DskipTests

# 前端（在 agent-platform/frontend/ 下）：产出 dist/（build = vue-tsc + vite build，类型错误会直接失败）
npm run build
```

打完后**记录新包指纹**（后面验证要用）：

```powershell
(Get-Item backend\target\agent-platform-0.1.0-SNAPSHOT.jar).Length          # jar 字节数
Select-String -Path frontend\dist\index.html -Pattern 'assets/index-[^"]+\.js'  # 前端 bundle hash
```

## 二、上传到服务器

把两样东西传到服务器（RDP 剪贴板 / 共享目录 / scp 均可）：

- `agent-platform-0.1.0-SNAPSHOT.jar`
- 整个 `dist\` 目录

## 三、服务器替换 + 重启（管理员 PowerShell）

⚠️ **顺序不能反**：先停服务再换 jar——不停就拷会被文件锁挡住，拷了个寂寞（服务还在跑旧 jar）。

```powershell
# 1. 停后端服务（jar 解锁）
Stop-Service agent-backend

# 2. 备份旧 jar 留退路（回滚用，见 §五）
Copy-Item "E:\agent-platform\agent-platform-0.1.0-SNAPSHOT.jar" "E:\agent-platform\agent-platform-0.1.0-SNAPSHOT.jar.bak" -Force

# 3. 覆盖新 jar + 新前端 dist
Copy-Item "上传位置\agent-platform-0.1.0-SNAPSHOT.jar" "E:\agent-platform\" -Force
Remove-Item "E:\agent-platform\frontend\dist" -Recurse -Force
Copy-Item "上传位置\dist" "E:\agent-platform\frontend\dist" -Recurse

# 4. 起服务
Start-Service agent-backend
```

前端 dist 是**纯静态文件**：Nginx 不用重启、不用 reload，覆盖即生效。

## 四、验证（逐项打勾，别跳）

```powershell
# ① 服务状态 = Running
Get-Service agent-backend

# ② 健康检查（Spring Boot 启动慢，等 30~60s 再查）
curl http://localhost:8080/actuator/health
#   期望 {"status":"UP"}；DOWN/超时 → 看 §六 排错

# ③ Flyway 迁移是否补跑成功（有新迁移时查）
#   PG 里执行：SELECT version, success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 3;
#   最新行 success=t 即过；success=f → 看后端日志 migration 报错

# ④ jar 真是新的——字节数对比 §一 记录的指纹
(Get-Item "E:\agent-platform\agent-platform-0.1.0-SNAPSHOT.jar").Length

# ⑤ 前端真是新的——浏览器开平台页，Ctrl+F5 强刷，F12 → Network → 找 index-*.js
#   hash 必须 = §一 记录的 bundle hash；不对 = 旧缓存（再强刷/无痕）或 dist 没覆盖成功
```

**功能冒烟**：登录一次（admin 或测试号）→ 点一遍本次修的功能 → 正常即收工。
最后**自己浏览器 Ctrl+F5 强刷**——index.html 有缓存，不强刷可能还跑旧 JS（踩过：服务器滑块修复"不生效"，实为浏览器跑旧 bundle）。

## 五、回滚（新版本炸了）

```powershell
Stop-Service agent-backend
Copy-Item "E:\agent-platform\agent-platform-0.1.0-SNAPSHOT.jar.bak" "E:\agent-platform\agent-platform-0.1.0-SNAPSHOT.jar" -Force
Start-Service agent-backend
```

⚠️ 若这次更新**带 Flyway 迁移且已跑过**：jar 回滚后旧代码可能不认识新表结构——回滚前先想清楚迁移是否向后兼容（加列/加表一般兼容；删列/改类型不兼容）。dist 回滚同理需留旧 dist 备份（要回滚前端时，把上传前的旧 dist 也复制一份留底）。

## 六、起不来的常见死因（看日志先）

日志位置：WinSW XML（`ops-config\运维\winsw\agent-backend.xml`）同目录的 `agent-backend.out.log` / `agent-backend.err.log`。

| 症状 | 死因 | 处理 |
|---|---|---|
| 服务秒挂，日志 FlywayException | 迁移脚本报错（CHECK 约束/语法） | 按报错改迁移或手工修库后 `flyway repair` 思路修版本表 |
| 启动报「环境变量未配置」 | 新代码引了新 `${ENV}` 而服务器没设 | WinSW XML `<env>` 补上或 `setx /M` 后重开窗口再启 |
| 健康检查超时，日志端口被占 | 旧 java 进程没死透 | `Get-Process java` → `Stop-Process -Id <PID> -Force` → 再启 |
| 页面还是旧功能 | 浏览器缓存旧 bundle | Ctrl+F5 / 无痕；还不行查 dist 是否真覆盖了 |
| API 全 502 | Nginx 起了但后端没起 | 回到 ①② 查后端 |

## 七、一键脚本（可选）

`ops-config` 里有 `deploy.bat`（按本包路径改好的），流程同上；手顺了就脚本化，但**头几次更新建议手工走一遍 §三§四**，熟悉每步的验证点。
