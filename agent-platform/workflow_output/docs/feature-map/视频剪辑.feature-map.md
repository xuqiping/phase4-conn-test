# 视频剪辑 · Feature Map（功能-代码速查）

> 后端 FFmpeg 多轨渲染 + 剪映草稿导出。关联 [plan](../plans/视频剪辑合并.plan.md) / [user-ops](./视频剪辑用户操作手册.md) / [开发进度](../../开发进度/视频剪辑合并与E2E.md) / [快速启动速查表](../run-guide/快速启动速查表.md#视频剪辑)。

## 一句话描述

用户在 `/video-edit` 页以多轨时间线方式组合视频段、音频轨、字幕，后端用 FFmpeg 单遍 filter_complex 渲染成片（h264/aac），并支持导出剪映草稿 zip。

## 调用链路

**素材库**：`VideoEditView.onMounted` → `mediaEditApi.listAssets` → `GET /api/media/edit/assets` → `MediaAssetService.listGeneratedAssets` → 查 `stored_files` 里 `source='GEN'` 且归属当前用户的视频。

**上传素材**：`VideoEditView.handleVideoUpload/handleAudioUpload` → `mediaEditApi.uploadAsset` → `POST /api/files/upload` → `FileStorageService` → 返回 `fileId` → 前端加入对应轨末尾。

**提交渲染**：`VideoEditView.onSubmit` → `mediaEditApi.submit(buildSpec())` → `POST /api/media/edit/submit` → `MediaEditController.submit` → `MediaAssetService.validate`（归属/格式/上限 + V2 规范化）→ `MediaEditTaskService.submit` → 建 PENDING 行 → 返回 `{id,status}` → 前端 `startPolling(id)`。

**异步渲染**：`MediaEditTaskWorker.poll`（@Scheduled）→ `claimBatch`（`FOR UPDATE SKIP LOCKED`）→ `mediaEditTaskExecutor.process` → 素材 copy 到 temp → `FfmpegEditProvider.render` → FFmpeg 子进程 → 成功写入 `stored_files`（source=EDIT）→ `markSucceeded`。

**轮询/下载**：前端每 3s `GET /api/media/edit/tasks/{id}` → SUCCEEDED 且 `videoUrl` 非空 → axios 拉 `GET /api/media/edit/tasks/{id}/download`（带 Authorization header）→ `URL.createObjectURL` 播放/下载。

**剪映草稿**：`VideoEditView.onExportDraft` → `POST /api/media/edit/export-draft?absolutePath=false` → `DraftExportService.prepare`（校验 + normalize）+ `streamZip` → 浏览器下载 zip。

## 技术清单与原理注解（大白话版）

#### 1. FFmpeg filter_complex 单遍渲染 — `FfmpegEditProvider.java`

- **采用技术**：FFmpeg `filter_complex` + ProcessBuilder 参数数组（不经 shell）。
- **一句话原理**：把视频、音频、字幕三条流水线一次性拼成一条 FFmpeg 滤镜图，输入源统一处理，输出一个 mp4。
- **大白话展开**：像厨房「一条流水线」——视频段先裁剪/缩放/补黑帧（切菜），再按顺序 concat（装盘）；各段音频按时间轴对齐后混音（调酱）；字幕像贴纸一张张叠在画面上；最后统一打包成盒（mp4）。
- **为什么用它**：单进程单遍比多进程转码快、质量损失小、音画同步简单。

> 📌 批注（Windows 坑）：`drawtext=fontfile='C:/Windows/Fonts/simhei.ttf'` 里的 `C:` 会被 filtergraph 解析器当成 option 分隔符，直接炸。代码已修：字体拷进 per-task workDir，用相对名 `font.ttf`；`ProcessBuilder.directory(workDir)` 设 CWD；单引号包路径在 7.1.1 **不**保护冒号，故相对名无引号。Linux 无此问题但统一走同一逻辑。

#### 2. SKIP LOCKED 任务认领 — `MediaEditTaskWorker.java`

- **采用技术**：PostgreSQL `FOR UPDATE SKIP LOCKED` + `locked_until` 过期锁。
- **一句话原理**：多个 worker 并发抢任务时，只拿没被别的线程锁住且未过期的行；服务崩溃重启后过期行会被重新认领，自动续跑。
- **大白话案例**：像医院叫号机——多个窗口同时叫号，但只叫「没人且没过期」的号；患者临时跑了（服务崩溃），过号后自动重新叫。

#### 3. EditSpec V2 多轨模型 — `EditSpec.java`

- **采用技术**：JSONB 存储的剪辑意图（VIDEO/AUDIO/TEXT track）。
- **一句话原理**：用「轨」和「段」描述最终成片结构，而不是早期 plan 里的 clips/texts 分离；后端 normalize 后统一处理。
- **大白话案例**：像视频编辑软件的「时间线」——上面几条轨道，视频轨道、音频轨道、字幕轨道，每条轨道里放若干片段，后端照着这个时间线渲染。

#### 4. 剪映草稿导出 — `DraftExportService.java`

- **采用技术**：JSON 生成 + zip 流式打包。
- **一句话原理**：不渲染，只生成剪映能读懂的草稿 JSON 和素材包，让用户在剪映里继续精剪。
- **为什么用它**：当前后端渲染是「快速成片」，复杂调色/转场仍依赖专业剪辑软件；导出草稿是衔接用户工作流的桥。

## 数据库表与 SQL 注解（Flyway V87）

### 迁移脚本：`V87__media_edit_tasks.sql`

- **脚本作用**：建 `media_edit_tasks` 表 + `media:edit` 权限 seed（仅 admin 默认拥有）。
> 📌 批注：任务表不软删（同 `media_gen_tasks`），append-only，未来靠归档清理。

### 表：`media_edit_tasks`（视频剪辑渲染任务）

> 大白话：一张「剪辑订单流水」，记录谁、什么时候、按什么意图、渲染成没成功。

| 字段 | 类型 | 用途（大白话） | 约束 / 索引 |
|---|---|---|---|
| id | BIGINT | 任务唯一编号 | 主键，GENERATED ALWAYS AS IDENTITY |
| user_id | BIGINT | 谁提交的 | 索引 `(user_id, created_at)` |
| status | VARCHAR(20) | 状态：PENDING/RUNNING/SUCCEEDED/FAILED/DOWNLOAD_FAILED | 非空 |
| edit_spec | JSONB | 完整剪辑意图（tracks/segments/texts/output） | 非空 |
| result_file_id | VARCHAR(128) | 成片在 `stored_files` 里的编号 | SUCCEEDED 后填 |
| error_msg | VARCHAR(256) | 失败原因（FFmpeg 日志尾部，截断） | |
| attempt | INTEGER | 认领/重试次数 | 默认 0 |
| locked_until | TIMESTAMPTZ | 锁过期时间 | 索引 `(status, created_at)` |
| created_at / updated_at | TIMESTAMPTZ | 创建/更新时间 | 默认 NOW() |

### 表关联

- **`media_edit_tasks.result_file_id` → `stored_files.file_id`（一对一）**：一个任务成功后产出一份存储文件；成品复用既有 stored_files 咽喉点。
  > 像「订单 ↔ 出货单」：任务（订单）完成后对应一张 stored_files（出货单），下载从 stored_files 走统一路径。
