## 一句话目标
管理员能一键封号且**即时踢出**（不等 token 过期）；高频操作用户被**通用限流**兜底；异常使用（失败风暴/异常消耗/限流频发）自动**生成告警**进 admin 中心可确认。

## 现状盘点（决定 chunk 粒度）
| 需求 | 已有 | 缺口 |
|---|---|---|
| ①封号 | `users.status`(ACTIVE/DISABLED/LOCKED,V1) · `PUT /{id}/status` 端点+`@AuditLog`+`user:manage` · 登录/refresh 拒非 ACTIVE · `UserManageView.vue` 有禁用/启用按钮+statusMap · `SessionService.clearSession` | **封号后旧 access token 15min 内仍有效**（JwtFilter 不查 status，仅校验 sid 黑名单）→ 需「封号即清 session」即时失效；禁用 reason 留痕；防自封/封最后超管；LOCKED 状态 UI 缺 |
| ②限流 | 登录/注册域 Redis 滑动窗口 + `RATE_LIMIT`/`LOGIN_LOCKED` + `authLoginLocked`/`registerRateLimited` 指标 | **无通用 API 限流**（对话/媒体生成高频端点裸奔） |
| ③告警 | `BizMetrics` 全埋点（login/llm/media/memory）·Micrometer→Prometheus | **无异常判定+通知**（仅有 chat 域 `MemoryNotification` 站内信，非运维告警）；无通用告警表/中心页 |

## Chunk 分解（6 chunk）

### Chunk 1 — 封号即时失效（需求①核心）
**目标**：admin 禁用/锁定用户后，该用户当前 access token **下一次请求即 401**，无须等 15min 过期。

**动作（伪代码）**：
```
SessionService:
  + clearAllSessions(userId):  // 单 session 模型 = 删 1 个 key
      redisTemplate.delete(SESSION_PREFIX + userId)   // try/catch 降级（Redis 故障不阻封号）

UserController.updateUserStatus(id, body):  // 已存端点
  status = body.get("status"); reason = body.get("reason")
  校验 status ∈ {ACTIVE, DISABLED, LOCKED}
  防自封：if id == 当前登录用户id → 403 自封禁止
  防锁死：if status∈{DISABLED,LOCKED} 且 目标是最后一名持 user:manage 的超管 → 403
  user.setStatus(status); userMapper.updateById(user)
  if status ∈ {DISABLED, LOCKED}:
      sessionService.clearAllSessions(id)   // ← 即时踢出，JwtFilter.isCurrent 下一请求立拒
  // @AuditLog action 按 status 细化：ban_user / unban_user / lock_user（detail 带 reason）
```
**涉及文件（5）**：
- `auth/service/SessionService.java`（+clearAllSessions）
- `auth/controller/UserController.java`（updateUserStatus 加 reason/防护/细化 action）
- `auth/controller/UserController` 的 `@AuditLog` action 改 `ban_user`
- `common/audit/AuditLabelDictionary.java`（action 码→中文，若用）
- `frontend/src/views/admin/UserManageView.vue`（禁用弹窗加 reason 输入 + LOCKED 选项；启用按钮同路径）

**依赖**：现有 Redis session 基建（`SESSION_PREFIX+userId` 单 key）。

**验证**：
- 单测 `clearAllSessions` 删 key + Redis 故障降级不抛。
- 单测自封/最后超管防护返回 403。
- E2E：u1 登录 → admin 禁用 u1 → u1 刷新页面 401（SESSION_KICKED）→ admin 启用 u1 → u1 重新登录成功。

**坑**：
- *性能*：clearAllSessions 单 key delete，零性能负担（非每请求查库，复用 JwtFilter 已有的 isCurrent Redis 路径）。
- *并发*：admin 封号瞬间用户正在发长请求 → 该请求照常完成（已过 filter），**下一请求**才拒。属可接受语义（不强拆在途）。
- *降级*：单点登录开关关（`AUTH_SINGLE_SESSION_ENABLED=false`）→ isCurrent 不校验 → 封号即时失效失效！→ clearAllSessions 仍写一个「封号标记」Redis key，JwtFilter 在「单点登录关」时额外查此标记（或更简：封号强制开单点登录语义）。**决策：另起 `ban:user:{id}` 标记 key，JwtFilter 在 isCurrent 之后加一行 ban 标记校验（Redis 有即拒），与单点登录开关解耦。**
- *误操作*：禁用自己/唯一超管 → 平台锁死 → 必须防护。

### Chunk 2 — 通用限流拦截器基建（需求②基建）
**目标**：任意端点贴注解即享 per-user（未登录按 IP）滑动窗口限流。

**动作（伪代码）**：
```
@RateLimit(action="chat_send", max=20, window=60)   // 注解，可标在 Controller 方法

RateLimiter (抽通用组件，复用 AuthService.checkRateWindow 逻辑):
  check(key, max, windowSec):
      // Redis 原子 INCR + EXPIRE（首次才 EXPIRE）
      long n = redis.opsForValue().increment(key)
      if n == 1: redis.expire(key, windowSec)
      return n <= max

RateLimitInterceptor (HandlerInterceptor, preHandle):
  if !ratelimit.enabled: 放行（降级）
  读 SecurityContext.userId（无则 clientIp）
  key = "ratelimit:user:" + uid + ":" + action
  if !rateLimiter.check(key, max, window):
      bizMetrics.apiRateLimited(action)         // 新埋点
      raise RATE_LIMIT("操作过于频繁，请稍后再试")
  放行

WebMvcConfig: registry.addInterceptor(rateLimitInterceptor)
            .addPathPatterns("/api/**")
            // 但实际拦截由方法注解决定（无注解 → 放行）

BizMetrics: + apiRateLimited(action) 指标 api.rate_limited{action}
application.yml: ratelimit.enabled（${RATE_LIMIT_ENABLED:true}）
```
**涉及文件（7）**：
- `common/ratelimit/RateLimit.java`（注解，新建）
- `common/ratelimit/RateLimiter.java`（通用窗口，新建）
- `common/ratelimit/RateLimitInterceptor.java`（新建）
- `common/WebMvcConfig.java`（或现有 web 配置类，注册拦截器）
- `common/metrics/BizMetrics.java`（+apiRateLimited）
- `resources/application.yml`（开关）
- `common/exception/GlobalExceptionHandler.java`（RATE_LIMIT 已映射 429，确认文案）

**依赖**：Redis（已有）、Spring MVC 拦截器注册。

**验证**：
- 单测 `RateLimiter.check` 窗口计数 + EXPIRE 首次设置 + 超限返回 false。
- 单测拦截器：注解端点连续打 max+1 次 → 第 max+1 次 429；不同用户互不影响；关开关 → 不限。
- 性能：Redis 单次 INCR+条件 EXPIRE，亚毫秒，可承受。

**坑**：
- *性能*：每请求一次 Redis 往返。热端点（对话）高并发 → Redis QPS 压力。规避：INCR+EXPIRE 合并（Lua 脚本一次性，省往返）；或本地+Caffeine 两级（**后续再说**，先 Redis 单级够用）。
- *降级*：Redis 故障 → check 抛异常 → 拦截器 try/catch 放行（可用性 > 限流，与登录域一致）。
- *误拦*：阈值须可配（env），且热更（用 SystemSettingService 读，不重启）。**决策：阈值走配置 + 关键项走 SystemSetting 可后台调。**
- *未登录路径*：登录/注册端点本身限流已在 AuthService，不重复挂；白名单公开放行端点不挂。

### Chunk 4 — 运维告警表 + 判定引擎（需求③基建）
**目标**：异常用户行为自动生成结构化告警记录，可查可统计。

**动作（伪代码）**：
```
V104__ops_alerts.sql:
  ops_alerts(
    id BIGINT IDENTITY PK,
    created_at TIMESTAMPTZ,
    level VARCHAR(16),        -- INFO/WARN/ERROR
    rule_code VARCHAR(64),    -- frequent_ops/login_locked/media_fail_storm/llm_fail_storm/abnormal_spend
    user_id BIGINT NULL,      -- 可空（系统级）
    source VARCHAR(32),       -- auth/llm/media/chat/ratelimit
    message VARCHAR(512),
    detail_json JSONB,        -- 已脱敏
    status VARCHAR(16),       -- NEW/ACK/CLEARED
    ack_by BIGINT NULL, ack_at TIMESTAMPTZ NULL
  )
  索引：idx_ops_alert_status_created(status,created_at)、idx_ops_alert_user(user_id)
  -- 不继承 BaseEntity（append-only 语义，ACK 是唯一 UPDATE）

OpsAlertService.raise(level, ruleCode, userId, source, message, detail):
  去重：Redis key "opsalert:dedup:{rule}:{user}" TTL=窗口（同 rule+user 窗口内只记 1 条）
  if 未去重命中: insert ops_alerts(status=NEW)

OpsAlertRules（判定，复用 Redis 窗口计数，不扫表）:
  - 限流触发：RateLimitInterceptor 429 时 → 短窗累计 ≥N 次 → raise(WARN, frequent_ops)
  - 登录锁定：authLoginLocked 触发 → raise(WARN, login_locked)
  - 媒体失败风暴：mediaTaskTerminal(fail) 短窗累计 ≥N → raise(ERROR, media_fail_storm)
  - LLM 失败风暴：llmCall(fail) 短窗 ≥N → raise(ERROR, llm_fail_storm)
  - 异常消耗：llm_usage_logs 单用户短窗积分 ≥阈值 → raise(WARN, abnormal_spend)
```
**涉及文件（8）**：
- `db/migration/V104__ops_alerts.sql`（新建）
- `common/opsalert/OpsAlert.java`（实体，新建）
- `common/opsalert/OpsAlertMapper.java` + `OpsAlertMapper.xml`（新建）
- `common/opsalert/OpsAlertService.java`（raise + 去重，新建）
- `common/opsalert/OpsAlertRules.java`（规则常量 + 窗口计数，新建）
- `common/ratelimit/RateLimitInterceptor.java`（Chunk2 接 raise frequent_ops）
- `auth/service/AuthService.java`（login_locked 处接 raise）
- `common/metrics/BizMetrics.java` 调用处 / `billing` 失败处接 raise（media/llm fail storm、abnormal_spend）
- `resources/application.yml`（阈值 ops.alert.* ）

**依赖**：现有 BizMetrics 埋点、Redis。

**验证**：
- 单测 `raise` 去重（同 rule+user 窗口内只 1 条）。
- 单测各规则窗口计数达阈值 → raise。
- 单测 detail_json 脱敏（手机号/邮箱打码，复用 LogMasker）。

**坑**：
- *告警风暴*：异常持续 → 告警刷量。规避：去重 Redis TTL 窗口（同 rule+user 5min 1 条）+ level 限速。

- *幂等*：raise 去重保证；ACK 并发用条件 UPDATE（WHERE status='NEW'）。
- *容量*：ops_alerts 增长 → CLEARED 行定期归档（**后续再说**），先靠索引 + status 查询不拖。

## 技术坑点预判（汇总）

| 坑 | 场景 | 规避 |
|---|---|---|
| **性能-Redis QPS** | Chunk2 每请求 INCR，对话热端点高并发 | Lua 脚本合并 INCR+EXPIRE 省往返；阈值热更避免调参重启 |
| **性能-告警判定扫表** | Chunk4 若查 audit_logs/llm_usage_logs 找异常 | **禁扫表**，全走 Redis 窗口计数（埋点瞬间累加） |
| **缓存失效/降级** | Redis 故障 | 限流降级放行（可用性优先，与登录域一致）；封号 ban 标记降级放行但 DB status 仍阻 refresh/新登录 |
| **并发竞争** | 多 admin 同时 ack 同告警；同时封同用户 | ack 条件 UPDATE WHERE status='NEW'（影响 0 行 → 200 幂等）；封号 setStatus 无并发风险（终态覆盖） |
| **单点登录开关耦合** | `AUTH_SINGLE_SESSION_ENABLED=false` 时 isCurrent 不校验 → 封号即时踢出失效 | 独立 `ban:user:{id}` 标记 key，JwtFilter 单独校验，与单点登录解耦 |
| **告警风暴** | 异常持续刷量 | raise 去重（rule+user 窗口 TTL）+ level 限速 |
| **误拦/误封** | 阈值过低误伤；admin 误封自己/唯一超管 | 阈值偏宽松+可后台调；封号端点自封/最后超管防护 |

## 安全检查清单（P3 逐项验证）

- [ ] **鉴权**：封号端点 `user:manage`（已存）；告警中心 `system:ops:read`（新 seed）；限流拦截器对所有认证用户生效。
- [ ] **输入校验**：封号 status ∈ {ACTIVE,DISABLED,LOCKED}；reason 长度限制；告警筛选参数防注入（MyBatis #{}）。
- [ ] **越权**：普通用户不能调封号/告警接口（权限门控 + 测试覆盖）。
- [ ] **审计**：封号/解封（ban_user/unban_user）进 audit_logs（@AuditLog 已接线，细化 action）；限流 429 进 BizMetrics；告警 ACK 可留审计（可选）。
- [ ] **脱敏**：告警 message/detail_json 出口过 LogMasker（手机/邮箱/apiKey 打码），禁 PII 原文；限流 Redis key 用 userId 不含用户名。
- [ ] **防滥用**：封号防自封/最后超管锁死；限流阈值可配；webhook URL 不进日志。
- [ ] **不可篡改**：ops_alerts 不进 audit_logs hash 链（独立表），但 ACK 留 ack_by/ack_at 痕迹。

## 功能联动点清单

| 联动 | 触发 → 联动对象 | 预期变化 | 边界（反向/半选/批量） |
|---|---|---|---|
| **封号↔会话** | admin 禁用 u1 → u1 session | 即时清 session，下一请求 401 | 反向：启用 u1 → u1 须重新登录（旧 session 已清，不自动恢复） |
| **封号↔前端列表** | 禁用 → UserManageView 该行 | 状态 Tag 变「禁用」(warning)，按钮变「启用」 | 批量：多选封多个用户（若加批量按钮）→ 各自 session 清 |
| **限流↔告警** | RateLimitInterceptor 429 → OpsAlertRules | 短窗累计达阈值生成 frequent_ops 告警 | 反向：用户停止超频 → 窗口过期 → 不再生成新告警（已有告警不自动清） |
| **限流↔前端提示** | 429 → 对话/媒体页 | toast「操作过于频繁」 | 边界：SSE 流中不触发（限流挂提交端点） |
| **告警↔侧栏 badge** | 新告警 NEW → 侧栏 badge +1 | 轮询 stats 反映 | 反向：ACK → badge -1；CLEARED 不计 |
| **告警 ACK↔状态** | admin 点确认 → 该行 | status ACK + ack_by/at | 并发：两人同时 ack → 条件 UPDATE，幂等 |
| **封号↔在途任务** | u1 有进行中媒体任务 → 封号 | **不中断已提交任务**（仅阻新请求/新登录） | 边界：任务正常完成产出，u1 无法再提交新任务 |

## 术语表
- **封号即时失效**：管理员禁用用户后，该用户已签发的 access token 无须等 15min 自然过期，下一次请求即被拒。
- **滑动窗口限流**：Redis 计数器 + TTL，统计「最近 N 秒内次数」，超阈值拒绝。
- **告警去重**：同一规则+同一用户在去重窗口（如 5min）内只生成 1 条告警，防风暴。
- **ACK（确认处理）**：admin 在告警中心标记某条告警「已处理」，状态 NEW→ACK，从未处理 badge 减除。
- **ban 标记 key**：独立于单点登录的 Redis 键 `ban:user:{id}`，JwtFilter 校验它实现封号即时踢出，不受单点登录开关影响。
