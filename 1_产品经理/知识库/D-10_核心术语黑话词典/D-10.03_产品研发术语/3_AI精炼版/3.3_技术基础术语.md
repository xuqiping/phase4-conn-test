## 核心口径详解

### API（应用编程接口）

**PM需要理解的三层**：
1. **是什么**：两个系统之间的"约定"——调用方按约定格式发请求，提供方按约定格式返回数据
2. **为什么重要**：API是前后端协作的契约，API文档的质量直接决定联调效率
3. **PM需关注的点**：接口定义是否覆盖需求、调用频率限制、异常处理

**API文档关键字段**：URL路径 / HTTP方法 / 请求参数 / 返回格式 / 错误码 / 限流策略

**⚠️ PM常见问题**：
- "接口报404"→不一定是Bug，可能是URL拼错或接口未上线
- "接口太慢"→需要与后端讨论是查询优化、加缓存还是异步处理

### SDK vs API

| 维度 | API | SDK |
|---|---|---|
| 本质 | 通信约定 | 封装好的工具包 |
| 接入方式 | 按协议自行实现 | 引入代码包直接调用 |
| 灵活性 | 高，自由度高 | 低，受SDK设计约束 |
| 学习成本 | 需理解协议细节 | 开箱即用 |
| 典型场景 | 后端间通信 | 移动端接入（如支付SDK/地图SDK） |

### 前端 / 后端 / 全栈

**前端三件套**：HTML（骨架）/ CSS（样式）/ JavaScript（交互）
- Web前端：浏览器中运行
- 移动端：iOS(Swift)/Android(Kotlin)/跨平台(React Native/Flutter)
- 小程序：微信/支付宝等平台内运行

**后端技术栈**：编程语言 + 框架 + 数据库 + 中间件
- 常见语言：Java/Go/Python/Node.js
- 框架举例：Spring Boot(Java)/Django(Python)/Gin(Go)

**⚠️ PM注意**：
- "前端改个按钮"≠5分钟→可能是涉及状态管理/组件复用/多端适配
- "后端加个字段"≠简单→可能涉及数据库迁移/接口兼容/历史数据

### 微服务 vs 单体架构

| 维度 | 单体 | 微服务 |
|---|---|---|
| 部署 | 一个大包整体部署 | 各服务独立部署 |
| 扩展 | 整体扩展 | 按需扩展单个服务 |
| 团队 | 集中式团队 | 按服务拆分小团队 |
| 复杂度 | 代码复杂，部署简单 | 代码简单，运维复杂 |
| 适用 | 早期/小团队 | 规模化/大团队 |

**⚠️ PM不必深究技术细节，但需理解**：微服务拆分会影响需求拆分和排期——跨服务需求需要多团队协调。

### 埋点/打点

**口径核心**：
1. **埋点类型**：前端埋点（客户端采集，灵活但可能丢数据）/ 后端埋点（服务端采集，准确但漏页面行为）
2. **埋点三要素**：事件名（What）/ 触发时机（When）/ 属性参数（Which+How）
3. **PM职责**：定义"埋什么"（埋点需求文档），研发负责"怎么埋"

**⚠️ 常见问题**：
- 前后端埋点数据不一致→去重口径不同（前端设备去重 vs 后端账号去重）
- 埋点粒度过细→数据量暴增，成本上升，不做分析=白埋
- 遗漏关键埋点→上线后发现无法复盘，无法量化效果

### DevOps 与 CI/CD

**DevOps**不是岗位，是文化+实践+工具链。

**CI/CD流水线**（PM需理解交付节奏）：
```
代码提交 → 自动构建 → 自动测试 → 自动部署（Staging）→ 人工验证 → 生产发布
```

**PM关注点**：
- CI/CD成熟度决定发布频率（日发 vs 周发 vs 月发）
- 发布自动化程度越高→小步快跑越可行
