# 问题
## 纯提问待解答类
1. 如果长年累月的使用，总结记忆有很多导致上下文爆炸，该设计方案是否有解决方案
   - **答：有，而且这是新模型专门要解的点。**
   - 大白话：系统会定期把一堆流水账“压扁”成精炼的总结条；召回历史时优先读这些总结，已经被总结吃掉的内容不会再重复塞进上下文。如果总结还是太多，会先读“标题”再决定展开哪几条。标签也会先筛选，不会把全部标签都灌进 prompt。所以用久了上下文不会爆炸。
2. 现在标签库中有哪些字段？跟UI展示对应关系是什么？
   - **答：标签库（`memory_tags`）主要存这些字段：**
     - `subject`：主体，比如“我”“表哥”
     - `topic`：主题，比如“居住”“爱好”
     - `label`：展示给用户看的标签名
     - `aliases`：别名，系统内部用来判断“兴趣”其实就是“爱好”
     - `anchor_embedding` / `anchor_tokens`：语义召回用的锚点，用户平时看不到
   - UI 对应关系：普通用户在前端只看到 `label` 和 `subject:topic` 形式的展示；只有作者本人在“标签库管理页”才能看到别名等全部字段。安全上别名和锚点不对外暴露。
3. 记忆面板中，流水账留的全部和仅raw有什么区别？
   - **答：区别就是有没有经过 LLM 提炼。**
   - “全部”：已提炼（`gen_done=true`，有 L0/L1/L2）和只存原文（`gen_done=false`）的流水账都显示。
   - “仅 raw”：只显示还没提炼、只有原始对话内容（`raw_content`）的那些。
   - 补充：raw 有 90 天自动清理机制，`gen_done=false` 且超过 90 天会被 worker 软删。
4. 目前turn流水账有哪些相关内容？原文，概要L1，总结L2？
   - **答：turn 上存的内容分这几层：**
     - `raw_content`：原文，原始 INPUT/OUTPUT 对话
     - L0：标签，格式是 `subject:topic`，比如 `我:居住`
     - L1：一句话概要
     - L2：结构化详述
   - 注意：L1/L2 是单条 turn 自己的提炼层；`memory_summaries` 表里的“总结”是把很多条 turn 压缩后的产物，不是 turn 上的字段。
5. turn流水账相关内容中，L0是不是跟标签库中的`主体：主题`对应？
   - **答：是的，基本对应。**
   - L0 标签就是 `subject:topic` 这种形式，会归一写入 `memory_tags` 标签库。不过一个 turn 可以贴多个标签（多个 `subject:topic`），所以是“标签库里的条目”和“turn 上打的标签”之间的对应关系，不是一对一。
6. 召回是根据什么召回？是先通过embedding看标签库是否有符合的subject、topic、label、aliases、anchor_embedding、anchor_tokens是否有符合要求的粗筛，然后再去总结/流水账中对标签筛选后再进行精筛？请给我写出当前真实的完整流程

## 需修复类 — 当前是否存在与修复方案

### 修复1：标签没有优先复用，动作被当成新标签

**当前是否真实存在：存在。**

证据：
- `MemoryTagResolver` 已经实现了写时标签归一（精确槽位、aliases 命中、anchor+LLM 批判、新建四路径），但它是**被动接收** LLM 生成的 `subject/topic/label`。
- `MemoryGenerator` 的生成 prompt 里没有告诉 LLM：
  - 优先复用已有标签；
  - 不要把“调整/移除/修改”这类动作当成新标签；
  - 状态变化应沿用原标签（如“个人信息”）。
- 所以 LLM 看到“记忆测试侠不用了，只保留啊平”这类话，很容易造出一个新标签“记忆称呼调整”，而不是复用已有的“个人信息”。

**修复方案：**
1. **prompt 注入已有标签白名单**：生成前查出该用户 `memory_tags` 已有标签，以 `subject:topic - label` 列表形式写进 prompt，让 LLM 优先从中挑选。
2. **prompt 加规则说明**：明确写“标签只记录事实状态/归属类别，不记录动作。若用户在修改某个已有类别下的事实，仍沿用原标签，不要新建。”
3. **后处理兜底**：LLM 返回的新标签若与某已有标签在 `subject:topic` 上高度接近，或 label 是“XX调整/XX修改/XX移除”这类动作词，优先尝试复用对应已有标签；复用失败再由 `MemoryTagResolver` 正常走 aliases/anchor 路径。
4. **前端给手动归一入口**：标签库页允许 owner 把“记忆称呼调整”这类误建标签合并/设别名为“个人信息”。

### 修复2：项目赋权入口找不到

**当前是否真实存在：功能已实现，但入口/命名可能不明显。**

证据：
- 后端有 `MemoryRosterController`：
  - `GET /api/chat/memory/projects/{pid}/roster` 花名册
  - `GET /api/chat/memory/projects/{pid}/recall-acl` 读取授权矩阵
  - `PUT /api/chat/memory/projects/{pid}/recall-acl` 配置授权
- 前端 `MemoryManagerPanel.vue` 有“项目 ACL”页签，引用了 `MemoryProjectAclPanel.vue`，可以选项目、看花名册、勾 reader×target 矩阵。
- 所以赋权能力已经存在，只是页签叫“项目 ACL”，对普通用户不够直观。

**修复方案：**
1. **页签名改直白**：把“项目 ACL”改成“项目赋权”或“项目记忆权限”。
2. **顶部说明强化**：当前说明是“项目召回 ACL：配置「谁能读到谁的流水账」”，可改成“项目赋权：配置项目内每个成员能召回谁的记忆（owner 默认可读全部）”。
3. **权限不足时明确提示**：如果当前用户不是 owner/recall_admin，面板显示“仅项目 owner 或 recall_admin 可配置赋权”，而不是仅灰掉复选框。

### 修复3：字数不超过10字时不应生成 L1/L2，且展示要写明原文/概要/总结

**当前是否真实存在：存在。**

证据：
- `MemoryPrefilter` 里 `MIN_INPUT_LEN = 2`，只有低于 2 字才判“过短”。
- 没有“10 字及以下不生成 L1/L2”的规则。
- 展示端如果 L1/L2 为空，当前可能直接不显示或显示空白，没有明确提示“未生成”。

**修复方案：**
1. **生成侧加阈值**：在前置过滤或 `MemoryGenerator` 中增加规则——某侧原文 trim 后字符数 ≤ 10 时，只产 L0标签，不产L1/L2。
2. **展示侧加文案**：在记忆面板展示 turn 时，固定显示三行：
   - 原文：xxx
   - 概要：未生成（原文过短）
   - 总结：未生成（原文过短）
   或者在 UI 上直接标注“原文过短，未提炼”。
3. **扩展前置过滤 reason**：把“过短”阈值从 2 提升到 10，并记录 reason，方便展示和日志。超过 10 字仍正常走生成流程。
