### C1 · 聊天流式审计用户名透传（问题 #7）

**目标**：SSE 流式发消息审计行不再空 userId/username。

**动作**：
1. **裸线程透传 MDC**：`ChatController.doStream` 的 `new Thread(() -> {...})` 入口处，先快照请求线程 MDC（`Map<String,String> ctx = MDC.getCopyOfContextMap()`），线程体内 `try { if(ctx!=null) MDC.setContextMap(ctx); ... } finally { MDC.clear(); }`。与既设的 `SecurityContextHolder.setContext` / `BillingContext.set` 并列。
2. **auditSendMessage 显式盖戳兜底**：`ChatSessionService.auditSendMessage(Long userId, ...)` 内，构造 AuditLogEntity 后、`record` 前，显式 `if(userId!=null) row.setUserId(userId);` + 从 SecurityContext/JWT 取 username `if(row.getUsername()==null) row.setUsername(<从 SecurityContext 取或查 users 表>)`。参考 [AuthService.auditAuth:319-320](#) 范式。
   - username 兜底优先级：MDC（C1.1 已修）> SecurityContext principal/credentials > 跳过（不查库，避免每条消息一次 SELECT）。
3. **复用既有装饰器**：若裸线程改用 Spring 管理的 `ThreadPoolTaskExecutor`（已配 `MdcContextTaskDecorator`）更彻底——评估 `doStream` 是否必须裸线程（流式响应需在原线程写 SSE？若是，保留裸线程 + 手动透传 MDC；若可提交池，改提交）。

### C2 · 个人文件记忆纳入召回标签聚合（问题 #3 主断点）

**目标**：上传的文件经 ingestion READY 后，其标签能进入召回②聚合候选，`collectFileCards` 可命中。

**动作**：
1. **聚合 SQL 补一路**：`MemoryTagMapper.xml` `findPersonalRecallTags` 的 UNION 加：
   ```
   SELECT unnest(tag_ids) FROM memory_asset_memories
   WHERE user_id = #{userId} AND ingest_status='READY' AND deleted=0 AND tag_ids IS NOT NULL
   ```
   与既有 turns/summaries 两路并列 DISTINCT。
2. **门控条件复核**：`MemoryRecallPipeline.java:215` ⑥.5 文件召回门控现条件 `scope.personalOn() && !selectedTagIds.isEmpty()`。修后 selectedTagIds 可含文件标签 → 门控通过 → `collectFileCards` 用 selectedTagIds 查 `findReadyByTagOverlap`（`tag_ids && selectedTagIds` 数组重叠）→ 命中。
3. **次断点（上传即问）兜底**：评估是否需"刚上传 PROCESSING 文件"也召回。设计权衡：
   - 选项 A（推荐）：不破坏 READY 闸，前端 `scheduleStatusRefresh` 轮询到 READY 后提示用户"文件已就绪可提问"。PROCESSING 文件召回会注入半成品，质量差。
   - 选项 B：上传即同步 ingest（阻塞上传响应到 READY），用户体验差（上传卡顿）。
   - **选 A**，前端 chip 状态 PROCESSING→READY 时加可问提示。

**涉及文件（≤6）**：
- [MemoryTagMapper.xml](agent-platform/backend/src/main/resources/com/superprogrammer/chat/mapper/xml/MemoryTagMapper.xml)（findPersonalRecallTags）
- [MemoryRecallPipeline.java](agent-platform/backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryRecallPipeline.java)（门控复核，可能不动）
- [ChatInput.vue](agent-platform/frontend/src/components/chat/ChatInput.vue)（READY 提示，选项 A）
- 测试：MemoryTagMapperTest（聚合含文件标签）/ MemoryRecallPipelineTest（fileCards 非空）

### C3 · 项目删除级联补全（问题 #5）

**目标**：删项目后，`memory_project_links` / `memory_project_user_grants` / `memory_entry_coverage` 不残留悬空行；召回侧 link 查询不返回已删项目。

**动作**：
1. **hook 补清 3 表**：`MemoryLifecycleHookService.onProjectDeleted(projectId)` 在现有 6 表清理后，补：
   - `memory_project_links`：`WHERE parent_project_id=projectId OR child_project_id=projectId` 硬删（双向）。
   - `memory_project_user_grants`：`WHERE project_id=projectId` 硬删。
   - `memory_entry_coverage`：`WHERE entry_id IN (该项目的 entries)` 或 `summary_id IN (该项目的 summaries)`。注意 entries 在 hook ⑥已硬删、summaries 在①已软删——entry_coverage 需在 entries 软删前先查 id 集合，或改删除顺序（先 coverage 后 entries）。
2. **删除顺序修正**：当前顺序 summaries(软)→summary_coverage→members→scopes→settings→rules+entries。插入 entry_coverage 清理在 entries 删除前（entries 硬删后无法反查 entry_id）。
3. **召回侧防御**：`MemoryProjectLinkMapper.xml` `findActiveChildIds` 加 `AND EXISTS (SELECT 1 FROM projects p WHERE p.id=parent_project_id AND p.deleted=0)`（双保险，即使 hook 漏也挡悬空链）。`listInvolving` 同理判 deleted 兜底 projectName。
4. **grants/links 对称**：grants 表同理补召回侧 `findActiveGrantedProjectIds` 判 projects.deleted。

### C4 · entry 方向 + INPUT 收录关系（问题 #2 + #4 合并）

**目标**：流水账 INPUT/OUTPUT 都能显"收录于:项目X"；项目总结区分来源方向（INPUT/OUTPUT/综合）。

**动作**：
1. **entry 加 direction 列**：迁移 V94 `ALTER TABLE memory_project_entries ADD COLUMN source_direction VARCHAR(10)`（值 INPUT/OUTPUT，记 entry 蒸馏时的源 turn 方向；若混两侧可 NULL 或 BOTH）。
2. **写入侧记录方向**：`MemoryGenerationService.buildRoutingInput` / `MemoryRoutingService` 落 entry 时，`source_direction` 取该 entry 实际来源 turn 的 direction（OUTPUT turn→OUTPUT，INPUT turn→INPUT）。
3. **source_turn_id 覆盖 INPUT**：当前 `MemoryGenerationService.java:155` `outputTurn!=null ? outputTurn : inputTurn` 优先 OUTPUT。改为**配对挂**：
   - 方案 A（推荐）：entry 维持单 source_turn_id（OUTPUT），但**额外存 source_turn_input_id**（新列）指向配对 INPUT turn。查询 `findProjectIndexByTurnIds` 改 `source_turn_id IN (...) OR source_turn_input_id IN (...)`。
   - 方案 B：改 source_turn_id 为 OUTPUT + 新增 INPUT 挂载表。重，不选。
   - **选 A**，单列追加，旧数据 source_turn_input_id=NULL 兼容。
4. **查询侧回填 INPUT**：`MemoryProjectEntryMapper.findProjectIndexByTurnIds` UNION 补 `source_turn_input_id IN (...)` 一路。`MemoryTurnViewService.batchProjectIndex` 不变（已传所有 turn id）。
5. **项目总结按方向归类**：`MemoryConsolidationTxService.writeProjectSummaryAndCoverage` 不再恒 BOTH。按该批 entries 的 `source_direction` 多数/分布决定 summary.direction：
   - 全 INPUT → INPUT；全 OUTPUT → OUTPUT；混合 → BOTH。
   - 或按用户总结请求的 direction 参数过滤 entry（INPUT scope 只取 INPUT entry）。与 P3c 个人总结方向透传一致。
6. **前端 tag v-if 放宽**：`MemorySummarySection.vue` direction tag 现排除 BOTH。若用户想"综合也显"，改 v-if 显三者；或保持隐 BOTH（综合是默认态，显=噪音）。**建议**：INPUT/OUTPUT 显 tag，BOTH 显"综合"弱 tag（与个人总结一致口径）。

   - 若 worker 没跑（@EnableScheduling 关 / 线程池满）→ 配置/运维问题。

## 技术实现坑点预判与规避措施

| 技术点/功能块 | 可能的坑 | 规避措施 | 验证方式 |
|---|---|---|---|
| （C1）裸 `new Thread()` vs MDC ThreadLocal | MDC 不跨线程自动继承，流式审计 userId/username 全 null | 线程入口快照+setContextMap，finally clear；auditSendMessage 显式盖戳双保险 | mock 裸线程断言 row 非 null |
| （C1）SSE 流式必须在原线程写响应 | 改提交 ThreadPoolTaskExecutor 可能破坏 SSE 写 | 评估保留裸线程+手动透传 MDC（不动线程模型） | 流式响应仍正常推送 |
| （C2）`memory_asset_memories.tag_ids` 数组重叠 SQL | PG `&&` 操作符需 GIN 索引，无索引全表扫 | 表数据量小（个人文件记忆），先不加索引，量大再加 | explain 看一眼（可选） |
| （C2）文件标签 vs 对话标签语义不重叠 | LLM 给文件建的主题词与对话 tag 命名风格不同，即使进候选也 `&&` 空命中 | 文件入库时 tag 归一复用 `tagResolver.resolve`（已走，:196-208），与个人 tags 库同源；候选进聚合后由 LLM selector 跨域选 | 单测 seed 同 tag 文件+turn 命中 |
