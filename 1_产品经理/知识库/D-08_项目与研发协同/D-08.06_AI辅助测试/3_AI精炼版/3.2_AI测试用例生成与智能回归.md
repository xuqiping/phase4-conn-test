# 3.2 AI测试用例生成与智能回归

## AI测试用例生成

### 生成方式

| 输入源 | 生成方式 | 覆盖率 | 局限 |
|---|---|---|---|
| PRD/用户故事 | LLM提取功能点→生成验收测试用例 | 正向场景70-80% | 边界case/异常流/跨模块交互弱 |
| 代码diff | 分析代码变更→生成针对性回归用例 | 变更相关场景60-70% | 无法理解高层业务意图 |
| API文档 | OpenAPI/Swagger→接口测试用例 | 接口覆盖90%+ | 业务逻辑组合遗漏 |
| 用户行为日志 | 分析真实用户路径→生成探索测试 | 关键路径可达 | 长尾场景遗漏 |

> "AI能完成70%以上的测试用例编写，以前需要一个测试干一周的活，现在AI辅助下一个初级测试两天就能搞定。"[来源:搜狐/行业分析 | 📚中 | 2026-07]

### 质量三角

AI生成测试用例的质量取决于三个维度的平衡：

```
     完备性（覆盖面）
         ▲
        /|\
       / | \
      /  |  \
     /   |   \
    /    |    \
   /_____|______\
 覆盖率    精确性（不误报）
           ↘
         可维护性
```

- **完备性↑**：AI倾向于生成大量"看着对"但实际冗余的用例
- **精确性↑**：严格过滤伪阳性，但可能漏掉真实的边界case
- **可维护性↑**：用例简洁易懂，但AI重新生成时可能与上一版不一致

### PM核心关注

| 关注点 | 原因 | PM行动 |
|---|---|---|
| AI生成用例的验收标准对齐 | AI可能"自作主张"添加未要求的测试场景 | 要求AI逐条映射回用户故事 |
| 边界case覆盖 | AI在边界条件上较弱 | 人工补充边界case清单 |
| 测试数据质量 | AI可能生成不合理的测试数据 | 审查测试数据集的合理性 |

## 智能回归测试

### 核心问题

每次代码变更后，回归测试要不要全量跑？传统二选一：
- **全量回归**：安全但慢（小时级），持续交付的瓶颈
- **冒烟+手动选择**：快但风险高，漏测概率高

### AI智能回归的解法

| 方法 | 原理 | 回归缩减率 |
|---|---|---|
| **影响分析** | 分析代码diff的调用链→定位受影响模块→只跑该模块相关测试 | 60-80% |
| **风险评分** | AI评估每个测试的"失效概率"→高风险优先→低风险跳过 | 50-70% |
| **历史关联** | 基于历史"哪个变更→哪些测试失败"的关联模型 | 40-60% |
| **测试分组** | 按功能域/风险等级分组→不同变更触发不同组 | 取决于分组粒度 |

### 影响分析工作流

```
1. 代码提交 → 2. CI触发影响分析
    → 3. AI识别变更涉及的模块/API/数据流
    → 4. 匹配关联测试用例集
    → 5. 生成"最小回归集"
    → 6. 执行回归 → 7. 结果报告
```

> PM核心洞察：智能回归的关键不是"省了多少测试时间"，而是"在有限时间内，先跑最可能失败的测试"——这本质上是**质量风险的优先级排序**。

### 智能回归的局限

| 局限 | 说明 | 应对 |
|---|---|---|
| 间接影响遗漏 | A改→B调B→B调C，AI可能只看到A→B | 补充架构级依赖图 |
| 配置变更影响 | 纯配置修改（如开关/阈值）不在代码diff中 | 配置变更加入影响分析输入 |
| 跨服务影响 | 微服务架构下，服务间影响难以静态分析 | 集成测试不可跳过 |
