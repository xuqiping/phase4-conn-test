# 技术团队管理 Workflow

## Purpose

为技术团队建设提供从组织架构设计、人才梯队建设到研发流程规范的完整执行路径。覆盖创业团队0→100人演进、双通道职级体系、Platform Engineering、Trunk-Based Development、可观测性体系和效能度量。

## Prerequisites

- 用户已明确团队规模（当前人数、6个月/1年目标人数）
- 用户已明确团队阶段（创始期/早期/成长期/规模化）
- 用户已明确行业属性（互联网/金融/医疗/政企/AI原生）

## Steps

### Step 1: 团队组织架构设计

**Goal**: 完成团队架构选型、角色定义、交互模式设计和股权/激励方案。
**Completion criterion**: 组织架构图产出，角色职责清晰，股权方案经合伙人/律师确认，团队章程发布。

**A. 组织模型选择矩阵**
| 模型 | 适用规模 | 特点 | 典型案例 |
|------|----------|------|----------|
| 扁平式 | 0-5人 | 创始人直管，快速决策 | 早期创业 |
| 层级式 | 5-20人 | 技术Leader+小组长分层 | 传统互联网公司 |
| Squad/Tribe | 20-150人 | 跨职能小队自治 | Spotify |
| 超级个体+AI | 1-5人+AI | 极少人+大量AI Agent | Cursor模式 |

**B. Conway定律与Team Topologies**
- Conway定律："系统架构镜像组织沟通结构"→组织架构设计先于系统架构
- 四种团队类型：
  - Stream-aligned（流对齐）：面向业务价值流的全栈团队，占~80%
  - Enabling（赋能）：帮助流对齐团队提升能力（如基础设施辅导）
  - Complicated-subsystem（复杂子系统）：深度专业知识模块（如算法/支付）
  - Platform（平台）：为其他团队提供内部平台和服务
- 四种交互模式：XaaS（平台即服务）/ Collaboration（协作）/ Facilitating（辅导）/ As-is（现状）
- 反模式：每个团队都是Platform（无业务产出）、Stream-aligned团队过多依赖Platform（排队等待）

**C. Squad/Tribe模型**
- Squad：5-9人跨职能自组织小队（前端+后端+产品+设计+QA），自治开发
- Tribe：40-150人业务域聚合（多个Squad），共享基础设施和目标
- Chapter：同职能横向组织（如所有后端工程师），能力提升
- Guild：兴趣社区跨组织（如"AI应用"Guild），知识分享
- 案例：Spotify模型虽非标准Scrum但影响深远，体现了敏捷自组织适配

**D. AI时代团队架构（5层）**
- 执行层：代码生成/测试/文档 → Cursor/GitHub Copilot（AI替代重复劳动）
- 协调层：任务调度/进度跟踪 → Multi-Agent编排（AI辅助项目管理）
- 决策层：技术选型/架构评审 → AI辅助ADR（AI提供选项，人做决策）
- 创意层：方案探索/头脑风暴 → GPT-4/Claude（AI扩展思路）
- 战略层：技术路线/人才规划 → Human-in-the-Loop（AI分析数据，人定方向）

**E. 团队规模演进（0→100人）**
- 创始期（0-5）：全栈多面手，Slicing Pie动态股权（按贡献分配）
- 早期（5-15）：首位专业化角色（DevOps/前端），ESOP池20-25%建立
- 成长期（15-50）：Squad结构，Platform Team组建，邓巴数（150）约束管理跨度
- 规模化（50-100）：Tribe/Chapter矩阵，人才密度优先于扩张速度
- 超级个体模式：1名超级工程师+AI Agent团队，5人工作量压缩至1人（Cursor模式）

**F. 股权与激励**
- ESOP池：20-25%，4年Vesting+1年Cliff
- Slicing Pie：早期动态股权，按时间+资金+知识产权+关系贡献分配
- 薪酬结构：固定70%+绩效20%+长期激励10%（RSU/期权）
- 特别激励：项目奖金/专利奖/技术分享奖
- Trio决策制：Product Manager + Tech Lead + Designer三人核心决策

**G. 远程协作**
- Async First：文档驱动，减少同步会议
- Follow-the-Sun：时区接力（如SF→伦敦→班加罗尔）
- 季度线下集结：每季度1次全员线下（team bonding+战略对齐）
- 工具：Notion（文档）/ Loom（异步视频）/ Linear（项目管理）/ Deel（跨境雇佣）

**输出物**: `团队组织架构文档_团队名.md`（含架构图、角色定义、交互模式、股权方案、远程协作规范）。

### Step 2: 技术人才梯队建设

**Goal**: 建立双通道职级体系、人才盘点机制、招聘流程和35+转型路径，确保组织持续拥有高质量人才。
**Completion criterion**: 职级体系发布，九宫格盘点完成≥1轮，招聘SOP运行，Bar Raiser培训完成。

**A. 双通道职级体系**
| 层级 | M管理序列 | P专业序列 |
|------|-----------|-----------|
| 初级 | M1主管 | P5/P6 |
| 中级 | M2经理 | P7 |
| 高级 | M3总监 | P8 |
| 专家 | M4 VP | P9 |
| 高管 | M5 CXO | P10 |
- 职级对标：阿里P序列/字节序列/腾讯T序列
- P序列薪酬对标管理层，同级别待遇对等
- 能力标准：每级定义"能独立做什么""产出影响力范围""所需技能深度"

**B. 九宫格人才盘点**
| 绩效\潜力 | 低潜力 | 中潜力 | 高潜力 |
|-----------|--------|--------|--------|
| 高绩效 | 专业深耕 | 核心骨干 | ★明星人才（晋升+保留） |
| 中绩效 | 观察改进 | 稳定贡献 | 潜力培养（辅导+项目） |
| 低绩效 | 淘汰/转岗 | 绩效改进（PIP） | 监控辅导 |
- 盘点频率：每半年1次，结合360度评估+绩效数据
- 明星人才：立即晋升/加薪/赋予挑战性项目
- 淘汰机制：低绩效+低潜力，3个月内转岗或离职

**C. AI时代能力模型**
- 技术深度：至少一个领域专精+系统设计能力
- AI协作：熟练使用AI编程工具+Agent编排+Prompt Engineering
- 系统思维：能将技术决策与业务价值关联
- 领域知识：深入理解所在行业（金融/医疗/电商等）
- 35+转型路径：架构师（T系统设计）/ 技术管理（M带团队）/ AI+领域专家（新赛道）

**D. 招聘策略**
- Take-Home Project：真实任务评估（如"设计一个API+写测试"），时间4-8小时
- Bar Raiser面试法：独立于用人部门的高标准面试官，一票否决权
- Reverse Recruiting：主动吸引而非被动筛选（技术博客/开源贡献/会议演讲）
- 校园招聘：实习转正为主渠道（转化率>60%），ACM/开源贡献者定向招募
- 人才密度优先：Netflix理念——1名A级人才产出>3名B级人才，宁缺毋滥

**E. 面试流程**
- 简历筛选：技术关键词+项目深度+开源贡献
- 技术面试：算法（LeetCode中等）+ 系统设计 + 代码实操
- 行为面试：STAR法则（Situation/Task/Action/Result）+ 文化契合度
- Bar Raiser面试：独立评估，确保不低于团队平均水平
- 工作试用（可选）：1-2周带薪试用，真实项目验证

**F. 内部流动与保留**
- 内部Transfer：满18个月可申请转岗，降低流失
- 轮岗计划：技术→产品→运营的短期轮岗（3个月），拓宽视野
- 离职面谈：分析流失原因，识别系统性问题

**输出物**: `人才梯队建设手册_组织名.md`（含职级体系标准、九宫格盘点模板、招聘SOP、面试题库、35+转型路径）。

### Step 3: 研发流程规范与效能度量

**Goal**: 建立覆盖需求→设计→编码→测试→部署→运维的全链路研发流程，配置效能度量体系。
**Completion criterion**: 研发流程文档发布，CI/CD流水线运行，可观测性平台部署，DORA基线建立。

**A. 需求管理**
- Living Requirements：活文档随代码演进，Git版本化管理
- ADR（Architecture Decision Record）：重大技术决策记录（背景/决策/后果/状态）
- C4模型：Context（系统上下文）→ Container（容器）→ Component（组件）→ Code（代码），分层可视化架构
- DDD（领域驱动设计）：识别限界上下文→上下文映射→指导微服务拆分
- RFC流程：异步技术方案讨论，文档优先于会议

**B. 编码与代码审查**
- 编码规范：Lint自动检查+SonarQube质量门禁+圈复杂度≤15
- 版本控制：Trunk-Based Development（主干开发）→ 短生命周期分支（<1天）→ Feature Flag控制发布
- Code Review：至少1人审查+AI辅助检测+审查清单（逻辑/边界/可测试性/安全性）
- 安全左移：SLSA供应链安全+SBOM+安全扫描融入CI

**C. 测试策略（测试金字塔）**
| 层级 | 占比 | 类型 | 工具 |
|------|------|------|------|
| 单元测试 | 70% | 函数/类级别 | Jest/pytest |
| 集成测试 | 20% | 模块/服务级别 | Spring Test |
| E2E测试 | 10% | 用户流程级别 | Cypress/Playwright |
- 契约测试：Pact（消费者驱动契约）
- 混沌工程：Chaos Mesh/Litmus验证系统韧性
- 测试门禁：覆盖率>80%，突变测试>70%

**D. CI/CD流水线**
- 代码提交→自动构建→单元测试→集成测试→安全扫描→渐进式发布
- 渐进式发布：Feature Flag（灰度开关）→ 灰度发布（1%→5%→20%）→ 蓝绿/金丝雀 → 全量
- Platform Engineering：构建IDP（内部开发者平台），开发者自助获取环境/数据库/部署能力
- FinOps：云成本监控，预算告警，资源优化

**E. 运维监控（SRE）**
- 可观测性三大支柱：Metrics（Prometheus指标）+ Logs（ELK日志）+ Traces（Jaeger链路追踪）
- SLI/SLO/Error Budget：
  - SLI：服务质量指标（如P99延迟）
  - SLO：服务质量目标（如P99<200ms 99.9%时间）
  - Error Budget：1-SLO，耗尽则暂停非紧急发布
- On-Call：轮值制+Runbook自动化+Blameless Post-Mortem无责复盘
- 告警分级：P0立即/P1 1h/P2 4h

**F. 效能度量（DORA+SPACE）**
- DORA四指标（精英团队标准）：
  - 部署频率：按需（多次/天）
  - 变更前置时间：<1天
  - 变更失败率：<5%
  - 恢复时间（MTTR）：<1小时
- SPACE框架（开发者体验五维）：
  - Satisfaction（满意度）
  - Performance（绩效）
  - Activity（活动量）
  - Collaboration（协作）
  - Efficiency（效率）
- 价值流映射：从需求提出到上线交付的全流程，识别瓶颈（如"等待测试环境"平均3天）
- PDCA持续改进：计划→执行→检查→行动，每季度迭代

**输出物**: `研发流程规范_组织名.md`（含需求管理SOP、编码规范、测试策略、CI/CD配置、可观测性Dashboard、DORA度量看板）。
