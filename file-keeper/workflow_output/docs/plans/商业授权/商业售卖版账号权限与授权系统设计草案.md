## 1. 当前已确认的核心方向

File Keeper 商业售卖版第一版采用“授权服务 + Web 管理后台 + 桌面客户端权限门禁”的方案。

第一版目标是尽快形成可售卖闭环：

- 不接入在线支付。
- 不做订单系统。
- 不同步文件收藏、剪贴板历史、截图内容等本地业务数据。
- 通过线下收款 + 管理后台手动审核/授权完成售卖流程。
- 服务端只负责账号、审核、模块授权、设备绑定、匿名试用、离线授权缓存策略。

## 2. 已确认技术栈与目录结构

### 2.1 服务端

- 目录：`file-keeper/server/`
- 技术栈：Spring Boot + PostgreSQL + Redis
- 约定参考当前项目根目录 `CLAUDE.md`：
  - Spring Boot 3.x
  - Java 17
  - PostgreSQL
  - Redis
  - JWT access token + refresh token
  - 统一响应结构
  - Flyway 数据库迁移

### 2.2 Web 管理后台

- 目录：`file-keeper/admin-web/`
- 技术栈：Vue 3 + TypeScript + Vite + Naive UI
- 用途：超级管理员通过浏览器审核用户、授权模块、管理设备和配置系统策略。

### 2.3 桌面客户端

- 现有 Tauri 2 + Vue 3 + TypeScript + Rust 客户端继续保留。
- 新增登录、注册、设备指纹、权益拉取、模块门禁能力。
- 本地数据仍留在本地，不上传到服务端。

## 3. 已确认业务规则

### 3.1 权限模块

第一版按 3 个主模块授权：

1. 文件管理：`files`
2. 进程管理：`processes`
3. 剪贴板：`clipboard`

截图/OCR 暂归入剪贴板模块，不单独成模块。

### 3.2 普通账号来源

- 普通用户可以自行注册。
- 注册后必须先验证联系方式。
- 验证通过后进入待审核状态。
- 管理员审核通过并授权后，用户才能使用登录账号对应的授权模块。

### 3.3 注册/登录标识

注册和登录支持两种账号标识：

- 邮箱
- 手机号

用户可以使用邮箱或手机号注册/登录。

注册时必须验证注册所用联系方式：

- 邮箱注册：验证邮箱验证码。
- 手机号注册：验证短信验证码。

### 3.4 管理员后台

采用独立 Web 管理后台，不内置在桌面客户端中。

超级管理员可以：

- 查看注册用户。
- 审核用户。
- 禁用/启用用户。
- 分配用户可使用的模块。
- 设置模块授权到期时间。
- 设置账号允许绑定的设备数量。
- 设置账号最大离线缓存时间。
- 查看、解绑、禁用用户设备。
- 查看匿名设备试用状态。
- 配置系统默认策略。

### 3.5 第一版不接支付

第一版不接入在线支付和订阅。

售卖流程：

1. 用户注册。
2. 用户完成联系方式验证。
3. 用户线下付款。
4. 管理员在后台审核并授权模块。
5. 用户登录客户端后获得对应模块权限。

### 3.6 登录用户离线缓存

登录授权用户的离线缓存时长由管理员配置。

- `offline_cache_minutes > 0`：登录用户可在指定时间内离线使用已授权模块。
- `offline_cache_minutes = 0`：登录用户必须联网校验授权。

注意：该离线缓存只适用于已登录且已授权用户。

### 3.7 免费/未登录用户必须联网

免费用户和未登录用户必须联网才能使用。

- 匿名全功能体验必须联网校验。
- 长期单模块免费模式必须联网校验。
- 未登录状态不允许使用离线授权缓存。
- 如果无法连接服务端，匿名/未登录用户不能使用任何模块。

### 3.8 匿名/免费用户权益生命周期

未注册/免费用户的体验规则调整为：

1. 首次识别设备后，获得 7 天全功能体验。
2. 7 天全功能体验期间，3 个主模块都可使用。
3. 7 天结束后，进入长期免费模式。
4. 长期免费模式只能选择 1 个主模块使用。
5. 长期免费模块每 30 天可更换一次。
6. 匿名/免费用户必须联网使用。

### 3.9 已注册但未审核用户

已注册但未被管理员审核/授权的用户：

- 可以登录。
- 看到账号“待审核”提示。
- 仍可按匿名设备权益使用。
- 如果设备还在 7 天全功能期，则可继续全功能体验。
- 如果 7 天已过，则按长期单模块免费模式使用。

### 3.10 授权到期后的处理

登录账号授权到期后，客户端降级为匿名设备权益。

- 不完全禁用所有功能。
- 回退到该设备对应的匿名/免费权益。
- 同时提示用户续费或联系管理员重新授权。

### 3.11 设备唯一识别与绑定模式

设备唯一识别支持两种模式：

1. 多因素设备指纹 + 服务端生成 deviceId。
2. 更严格的强硬件绑定模式。

默认建议采用多因素设备指纹。

强硬件绑定模式作为更高强度策略，适用于需要更强防绕过的场景。

设备策略应支持配置，以兼顾防绕过和误伤用户的风险。

### 3.12 账号设备数量

每个账号允许绑定/登录的设备数量由管理员配置。

- 默认值由系统配置决定。
- 管理员可按用户调整。
- 超出设备数量上限时，服务端拒绝新设备绑定。
- 用户需联系管理员解绑旧设备或提高设备上限。

## 5. 已确认设计第 2 段：账号、角色、模块权限、设备模型

### 5.1 用户表 `users`

用途：保存注册用户和管理员账号。

建议字段：

- `id`
- `email`
- `phone`
- `password_hash`
- `status`
- `role`
- `max_devices`
- `offline_cache_minutes`
- `created_at`
- `updated_at`

`status` 可选值：

- `pending_verification`：待验证联系方式。
- `pending_review`：已验证，待管理员审核。
- `active`：已启用。
- `disabled`：已禁用。

`role` 可选值：

- `super_admin`
- `user`

约束：

- `email` 和 `phone` 至少有一个。
- `email` 唯一。
- `phone` 唯一。
- 注册时验证注册所用联系方式。

### 5.2 用户模块授权表 `user_module_entitlements`

用途：按用户 + 模块记录授权。

模块 code 第一版固定：

- `files`
- `processes`
- `clipboard`

建议字段：

- `user_id`
- `module_code`
- `enabled`
- `expires_at`
- `granted_by`
- `granted_at`

规则：

- 管理员可以给一个用户开启任意 1-3 个模块。
- 每个模块可以有独立到期时间。
- 授权过期后，该模块不再作为登录授权使用。
- 授权过期后，客户端回退到匿名权益。

### 5.3 用户设备表 `user_devices`

用途：记录登录账号绑定过的设备。

建议字段：

- `user_id`
- `device_id`
- `device_name`
- `fingerprint_hash`
- `binding_mode`
- `status`
- `first_seen_at`
- `last_seen_at`

`binding_mode` 可选值：

- `balanced`：多因素设备指纹。
- `strict`：强硬件绑定。

`status` 可选值：

- `active`
- `disabled`

规则：

- 登录时客户端上报设备指纹。
- 服务端生成或匹配 `device_id`。
- 如果 active 设备数超过 `users.max_devices`，拒绝新设备绑定。

### 5.4 匿名设备试用表 `anonymous_device_trials`

用途：记录未登录/免费用户设备权益。

建议字段：

- `device_id`
- `fingerprint_hash`
- `binding_mode`
- `full_trial_started_at`
- `full_trial_ends_at`
- `free_module_code`
- `free_module_selected_at`
- `free_module_next_change_at`
- `last_seen_at`
- `status`

规则：

- 免费/未登录用户必须联网校验。
- 第一次识别设备时创建记录。
- 创建记录时开始 7 天全功能体验。
- 7 天内 3 个模块都可用。
- 7 天后只能使用 `free_module_code` 对应的 1 个模块。
- 如果还没选择长期免费模块，客户端提示选择。
- 只有到达 `free_module_next_change_at` 后才允许更换免费模块。

### 5.5 系统配置表 `system_settings`

用途：保存全局策略。

建议配置：

- `anonymous_full_trial_days = 7`
- `default_free_module_change_days = 30`
- `default_binding_mode`
- `default_max_devices`
- `default_offline_cache_minutes`
- `allow_anonymous_usage`

## 6. 已确认设计第 3 段：桌面客户端权限判断与界面交互

### 6.1 客户端新增授权状态层

建议新增：

- `src/stores/authStore.ts`
- `src/api/auth.ts`
- `src/api/entitlement.ts`
- `src-tauri/src/commands/device.rs`

### 6.2 启动流程

客户端启动后：

1. Rust 生成设备指纹。
2. 前端读取本地登录 token。
3. 如果有登录 token，请求 `/client/entitlements/current`。
4. 如果没有登录 token，请求 `/client/anonymous/entitlements/current`。
5. 前端保存统一的权益快照。
6. UI 根据权益快照决定模块是否可进入。

### 6.3 权益快照结构

客户端只消费统一权益快照，而不是直接理解数据库细节。

建议结构：

```ts
interface EntitlementSnapshot {
  mode: 'authenticated' | 'anonymous'
  onlineRequired: boolean
  offlineUsableUntil?: number
  modules: {
    files: { allowed: boolean; reason?: string }
    processes: { allowed: boolean; reason?: string }
    clipboard: { allowed: boolean; reason?: string }
  }
  anonymousTrial?: {
    fullFeatureTrialEndsAt?: number
    freeModuleCode?: 'files' | 'processes' | 'clipboard'
    nextChangeAt?: number
  }
  account?: {
    status: 'pending_review' | 'active' | 'disabled'
    authorizationExpiresAt?: number
  }
}
```

### 6.4 模块门禁

当前 `App.vue` 使用 `currentTab` 切换模块。

第一版可在切换 Tab 时拦截：

- 模块允许：正常进入。
- 模块不允许：显示未授权面板。
- 匿名 7 天后未选择免费模块：提示选择 1 个长期免费模块。
- 免费模块每月更换未到时间：显示下次可更换时间。
- 登录用户授权过期：提示联系管理员续期或重新授权。

### 6.5 登录/注册界面

新增登录/注册入口：

- 支持邮箱或手机号 + 密码登录。
- 支持邮箱验证码注册。
- 支持短信验证码注册。
- 注册成功后进入待审核状态。
- 登录成功后刷新权益快照。
- 未审核用户显示等待审核提示，但仍可按匿名权益使用。

### 6.6 离线行为

匿名/未登录用户：

- 必须联网。
- 无法连接服务端时，所有模块不可用。
- 显示“免费体验需要联网校验”。

登录授权用户：

- 根据服务端返回的 `offlineUsableUntil` 使用离线授权缓存。
- 缓存未过期：允许使用已授权模块。
- 管理员配置离线缓存时间为 0：离线不可用。
- 缓存过期：提示联网刷新授权。

### 6.7 模块内功能

第一版只按 3 个主模块做门禁：

- 文件管理
- 进程管理
- 剪贴板

截图/OCR 跟随剪贴板模块。

## 8. 规则冲突与已对齐结果

前面曾讨论过“未登录只能选择 1 个模块、每月可换一次”。后续用户补充为：

- 免费/未登录用户先有 7 天全功能体验。
- 7 天后再进入长期 1 个模块免费模式。
- 免费/未登录用户必须联网才能使用。

因此当前最终规则为：

```text
匿名设备首次使用
  ↓
必须联网识别设备
  ↓
7 天全功能体验
  ↓
体验期结束
  ↓
选择 1 个长期免费模块
  ↓
每 30 天可更换一次免费模块
```

## 9. 已确认设计第 5 段：安全、风控、错误处理、测试策略

### 9.1 设备指纹与防绕过

设备指纹不要只依赖一个字段。第一版建议 Rust 侧采集多因素信息，组合后哈希上报服务端：

- Windows SID 或当前用户 SID
- 机器名
- 主板/BIOS 标识
- 磁盘序列号
- CPU/系统硬件信息
- File Keeper 安装 ID

服务端不要保存原始硬件信息，只保存：

- `fingerprint_hash`
- `fingerprint_version`
- `binding_mode`
- 部分脱敏摘要，例如设备名、系统版本

设备绑定模式：

- `balanced`：允许部分因素变化，只要综合相似度达到阈值就认为是同一设备。
- `strict`：关键硬件字段变化后认为是新设备，需要重新绑定或管理员处理。

这样可以兼顾：

- 防止清本地配置反复白嫖 7 天全功能。
- 减少换用户名、改机器名这类小变化导致误伤。
- 给高风险场景启用强硬件绑定。

### 9.2 匿名免费用户风控

匿名/未登录用户必须联网校验，所以服务端要控制：

- 每个设备只允许一次 7 天全功能体验。
- 7 天后只能选择 1 个长期免费模块。
- 长期免费模块 30 天才能更换一次。
- 禁用的匿名设备不能继续试用。
- 同一 IP 短时间创建大量匿名设备记录时限流。
- 同一设备频繁变化指纹时标记为风险设备。

管理后台可以提供：

- 查看匿名设备详情。
- 禁用匿名设备。
- 手动重置试用，但作为管理员高级操作，并记录审计日志。

### 9.3 注册、验证码、登录风控

公开注册需要基础防刷。

验证码：

- 邮箱/短信发送频率限制。
- 同一邮箱/手机号每天发送次数限制。
- 同一 IP 每小时发送次数限制。
- 验证码有效期，例如 10 分钟。
- 验证码错误次数限制。

注册：

- 邮箱唯一。
- 手机号唯一。
- email 和 phone 至少一个。
- 联系方式验证通过后才进入 `pending_review`。
- 未验证账号不能进入管理员审核队列。

登录：

- 连续失败 5 次后短时间锁定账号或要求等待。
- refresh token 存 Redis，可撤销。
- 禁用用户后立即让 refresh token 失效。
- access token 短有效期，refresh token 长有效期。

### 9.4 管理员安全

管理后台要比客户端更严格：

- 管理员接口全部要求 `role = super_admin`。
- 管理员登录失败限流。
- 管理员操作写审计日志：
  - 审核用户
  - 禁用/启用用户
  - 修改模块授权
  - 修改到期时间
  - 修改设备上限
  - 解绑/禁用设备
  - 重置匿名设备试用
  - 修改系统配置
- 超级管理员初始账号通过初始化脚本或环境变量创建，不开放公开注册成为管理员。
- 后续可以扩展二次验证，但第一版可先不做。

### 9.5 客户端错误处理

客户端应该把错误分成几类，而不是直接显示技术错误。

网络不可达：

- 匿名用户：提示“免费体验需要联网校验，请连接网络后重试。”
- 登录用户：如果离线缓存有效，继续使用；否则提示联网刷新授权。

账号待审核：

- 提示“账号已注册，正在等待管理员审核；审核前仍可使用当前设备免费权益。”

账号被禁用：

- 登录授权不可用。
- 回退匿名权益前要看设备匿名状态是否可用。
- 提示联系管理员。

授权过期：

- 降级为匿名权益。
- 提示续费或联系管理员重新授权。

设备数量超限：

- 提示“当前账号绑定设备数量已达上限，请联系管理员解绑旧设备或增加设备数量。”

模块未授权：

- 显示未授权面板。
- 提供登录/注册入口。
- 登录用户显示联系管理员授权。

### 9.6 权限判断原则

权限判断要在两个层面做。

前端 UI 门禁：

- 控制 Tab 是否可进入。
- 控制按钮、快捷键入口、设置项是否可用。
- 给用户明确提示。

Rust 命令/本地能力前置检查：

- 关键本地命令不能只靠前端隐藏按钮。
- 例如进程结束、截图/OCR、剪贴板监听这类能力，应在调用前检查当前授权快照。
- 第一版可先由前端集中控制，后续补 Rust 侧关键命令校验；最终商业版建议 Rust 侧也做关键保护。

### 9.7 测试策略

服务端测试：

- 用户注册：邮箱/手机号、验证码、重复注册。
- 登录：成功、失败、禁用账号、待审核账号。
- 模块授权：启用、禁用、过期。
- 设备绑定：首次绑定、设备上限、禁用设备。
- 匿名试用：首次 7 天全功能、7 天后单模块、30 天更换限制。
- 离线缓存策略：0 分钟、非 0 分钟、授权过期。
- 管理员 API 权限：普通用户不能访问管理接口。

客户端测试：

- 启动时有 token / 无 token 的权益拉取。
- 匿名用户网络不可达时禁用模块。
- 7 天全功能期允许 3 个模块。
- 7 天后只允许所选免费模块。
- 登录用户授权模块可进入，未授权模块显示提示。
- 授权过期后回退匿名权益。
- 离线缓存有效/过期的行为。

管理后台测试：

- 用户列表筛选。
- 审核用户。
- 分配模块和到期时间。
- 设置设备数和离线缓存时间。
- 禁用/解绑设备。
- 修改系统配置。

## 10. 已确认设计第 6 段：实施阶段拆分与第一版 MVP 范围

建议将商业授权系统拆成 6 个实施阶段，避免一次性同时改服务端、管理后台、桌面客户端、设备风控和模块门禁导致风险过高。

### 10.1 阶段 1：服务端基础与核心数据模型

目标：先把授权服务跑起来。

包含：

- 新建 `file-keeper/server/`。
- Spring Boot 基础工程。
- PostgreSQL + Flyway。
- Redis 配置。
- 统一响应结构。
- 用户表。
- 用户模块授权表。
- 用户设备表。
- 匿名设备试用表。
- 系统配置表。
- 管理员审计日志表。
- 初始化超级管理员。

不包含：

- 真实短信/邮件服务接入。
- 桌面客户端改造。
- 管理后台 UI。

验收标准：

- 服务端能启动。
- 数据库迁移能跑通。
- 能创建超级管理员。
- 基础表结构完整。

### 10.2 阶段 2：账号注册、验证、登录、管理员审核 API

目标：把账号生命周期做通。

包含：

- 邮箱/手机号注册。
- 验证码发送与校验。
- 密码登录。
- JWT access + refresh。
- `pending_verification` → `pending_review` → `active`。
- 禁用/启用用户。
- 管理员审核用户。
- 登录失败限流。
- refresh token Redis 存储与撤销。

第一版验证码可以先做两档：

- 开发环境：验证码写日志或固定测试码。
- 生产环境：预留邮件/短信 provider 接口。

验收标准：

- 用户可注册。
- 联系方式验证后进入待审核。
- 管理员可审核。
- 用户审核后可登录。
- 禁用用户无法继续刷新 token。

### 10.3 阶段 3：模块授权、设备绑定、匿名权益 API

目标：让服务端能返回统一权益快照。

包含：

- 管理员设置用户模块授权。
- 管理员设置每个模块到期时间。
- 管理员设置设备数上限。
- 管理员设置离线缓存时间。
- 登录用户上报设备指纹并绑定设备。
- 超出设备上限拒绝新设备。
- 匿名设备创建 7 天全功能体验记录。
- 7 天后选择长期免费模块。
- 长期免费模块 30 天更换限制。
- `/client/entitlements/current`。
- `/client/anonymous/entitlements/current`。
- `/client/anonymous/free-module`。

验收标准：

- 登录用户能拿到授权模块列表。
- 匿名设备首次请求能拿到 7 天全功能权益。
- 7 天过期后只能选择 1 个模块。
- 服务端 API 能表达匿名用户 `onlineRequired = true`。
- 授权过期后服务端返回不可用模块。

### 10.4 阶段 4：Web 管理后台 MVP

目标：管理员可以不用数据库手工操作。

包含：

- 新建 `file-keeper/admin-web/`。
- 管理员登录页。
- 仪表盘。
- 用户列表。
- 用户详情。
- 审核用户。
- 禁用/启用用户。
- 设置模块授权和到期时间。
- 设置设备上限。
- 设置离线缓存时间。
- 用户设备列表。
- 解绑/禁用设备。
- 匿名设备列表。
- 系统设置页。

不包含：

- 复杂图表。
- 支付。
- 运营报表。
- 多管理员权限分级。

验收标准：

- 管理员可以完成从看到用户注册到授权用户模块的完整流程。
- 管理员可以处理设备超限。
- 管理员可以查看匿名试用设备状态。

### 10.5 阶段 5：桌面客户端登录、注册、权益快照

目标：客户端能接入服务端，但先不强拦所有模块。

包含：

- Rust 侧设备指纹命令。
- 前端 `authStore`。
- 前端 `entitlementStore` 或在 `authStore` 内维护权益状态。
- 登录界面。
- 注册界面。
- 验证码流程。
- 启动时拉取匿名权益。
- 登录后拉取登录权益。
- 本地保存 token。
- refresh token 流程。
- 授权状态显示。
- 7 天全功能倒计时显示。
- 账号待审核提示。
- 服务端不可达提示。

验收标准：

- 未登录客户端启动后能显示 7 天全功能状态。
- 用户可注册、登录。
- 登录后能看到账号状态和授权模块。
- 服务端不可达时，未登录用户看到不可用提示。

### 10.6 阶段 6：桌面客户端模块门禁与商业版收口

目标：真正按权益控制模块使用。

包含：

- `App.vue` Tab 切换门禁。
- 文件管理模块门禁。
- 进程管理模块门禁。
- 剪贴板模块门禁。
- 截图/OCR 跟随剪贴板授权。
- 未授权模块面板。
- 7 天后选择长期免费模块界面。
- 每月更换免费模块入口。
- 登录用户离线缓存。
- 授权过期后降级匿名权益。
- 关键本地能力入口的前端保护。
- 重要 Rust 命令的二次权限校验可以作为该阶段后半部分或紧随其后的强化任务。

验收标准：

- 7 天全功能期内，未登录用户联网时可用 3 个模块。
- 7 天后，未登录用户只能用选中的 1 个模块。
- 未登录用户断网时不能使用模块。
- 登录用户只能进入被授权且未过期的模块。
- 登录用户离线缓存有效时可以继续使用授权模块。
- 离线缓存过期或设置为 0 时，登录用户必须联网刷新授权。
- 授权过期后回退匿名权益。

### 10.7 第一版 MVP 不做的内容

为了尽快售卖，第一版不做：

- 在线支付。
- 自动订阅。
- 订单系统。
- 发票/账单。
- 文件收藏云同步。
- 剪贴板历史云同步。
- 团队空间。
- 多级管理员角色。
- 复杂运营报表。
- 自动版本更新。
- 公告推送。
- 第三方登录。

### 10.8 推荐实施顺序

推荐顺序：

1. 先做阶段 1-3：服务端授权闭环。
2. 再做阶段 4：管理后台 MVP。
3. 最后做阶段 5-6：桌面客户端接入和门禁。

原因：

- 先有服务端，客户端才能拿到真实权益。
- 先有管理后台，才方便手动授权和测试售卖流程。
- 桌面客户端最后接入，能减少反复改接口导致的返工。
