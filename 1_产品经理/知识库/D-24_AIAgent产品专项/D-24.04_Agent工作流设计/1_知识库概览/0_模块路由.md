# D-24.04 Agent工作流设计

## 是什么

**Agent 工作流设计（Agent Workflow Design / Agent Orchestration）**：决定 Agent "怎么把一个大任务从头跑到尾还不崩"的工程方法论——让 Agent 从一次性 prompt-response 进化为可持续几十步、上百步工具调用的闭环系统。如果说 D-24.01 形态选型回答"Agent 应该长什么样"、D-24.03 工具调用回答"Agent 怎么调单个工具"，那么 D-24.04 工作流设计回答的是"Agent 怎么把这些工具按什么顺序、什么规则、什么容错策略、什么中止条件串成完整任务闭环"——它是 Agent 从 Demo 到生产的最后一公里，也是 2026 年 Agent 工程最核心的差异化能力。[来源:腾讯云《Agent Harness：2026年AI工程的核心范式》| 🔍高 | 2026-06]

**核心认知——Agent 可靠性瓶颈不在模型，在 Harness（线束）**：
2026-06 Martin Fowler 专门撰文提出 "Harness Engineering（线束工程）" 术语，Anthropic 同期发布《长时运行 Agent 的有效线束》报告，OpenAI Codex 团队用这套方法生成超 100 万行生产代码、零手动输入。共识是：**Agent = Model + Harness**——决定 Agent 能否可靠完成长任务的，不是模型本身，而是包裹在模型外面的执行系统（Harness）。LangChain 在 Terminal Bench 2.0 上不换模型只改 Harness，分数从 52.8% 跃升到 66.5%（排名前 30 外 → 前 5）；Vercel 把 Agent 工具数从 15 减到 2，准确率从 80% 跳到 100%、Token -37%、速度 ×3.5。这是 D-24.04 的元理论支柱。[来源:腾讯云/Anthropic《Effective Harnesses for Long-Running Agents》| 🔍高 | 2026-06]

**四大子维度（覆盖 L3 取值边界）**：
1. **任务拆解与编排**：单 Agent 怎么把复杂任务拆步骤跑——ReAct（思考→行动→观察循环）/ Plan-and-Execute（先规划再执行）/ Tree-of-Thoughts（树形探索）/ Reflection（自我反思改进）/ 混合编排
2. **错误恢复与重试**：跑崩了怎么不起来——重试 / 降级 / 绕路 / 重规划 / 人工接管五级恢复策略 + 反思循环 + Loop Engineering（2026 第 4 次范式跃迁）
3. **Human-in-the-Loop（HITL）**：什么操作必须人审、什么可以全自动——人工审核 / 人工确认 / 人工接管三档 + 副作用分级护栏
4. **状态管理**：长任务怎么不丢状态——上下文压缩 Compaction / 文件系统持久化 / 检查点 Checkpoint / Ralph Loop 重启注入 / Context Rot 对抗

[来源:腾讯云《Agent设计模式全景图——从ReAct到Multi-Agent》| 🔍高 | 2026-05]

## 核心要素

| 要素 | 说明 | 典例 |
|---|---|---|
| **执行循环（Execution Loop）** | Agent 反复 推理→工具调用→观察→续推 的基本闭环，是所有工作流的地基 | ReAct 循环；Claude Code 模型决策只占 1.6%，剩下 98.4% 全是循环/Harness |
| **任务拆解模式** | 把大任务切片的方式，决定可中断性/可恢复性/并行度 | ReAct（一步一动）/ Plan-and-Execute（先规划后执行）/ Planner-Worker（拆给子 Agent） |
| **重规划（Re-planning）** | 执行中发现原计划走不通时，重新规划而非硬刚 | Reflexion 反思循环；Planner 模式第 4 步失败回滚到第 4 步重做 |
| **错误恢复五级策略** | 工具失败 / 参数错 / 上下文溢出 / 死循环 / 越权 时的分级应对 | 重试 → 降级 → 绕路 → 重规划 → 人工接管 |
| **Human-in-the-Loop（HITL）** | 不可逆/高风险操作的人工介入节点设计 | 人工审核（输出后审查）/ 人工确认（执行前批准）/ 人工接管（接管任务） |
| **副作用护栏分级** | 按 可逆性×严重度 给操作打护栏等级，Hook 确定性拦截 | 可逆=查询/读取放行；不可逆=删数据/转账/发布强制 HITL |
| **上下文压缩（Compaction）** | 上下文逼近窗口上限时智能卸载/总结，对抗 Context Rot | Claude Code 五层 context 压缩；工具输出大头尾保留+卸载到文件系统 |
| **检查点与状态持久化** | 长任务运行中持久化中间状态，崩溃可恢复 | 文件系统持久化（最基础 Harness 原语）；LangGraph checkpoint；AGENTS.md 记忆文件 |
| **Ralph Loop / Loop Engineering** | 钩子拦截 Agent 退出尝试，在新上下文注入原提示词强制续跑；2026 第 4 次范式跃迁 | "你不应该再给 Agent 写 prompt，应该设计给 Agent 写 prompt 的 loop"（Peter Steinberger 2026-06 推文） |
| **生命周期钩子（Hook）** | 工具调用前/后/预完成/错误时插入确定性逻辑，prompt 管不住的框架来堵 | DECO 三层 Hook：偷懒检测/越权拦截/失忆补偿 |
| **反漂移检测** | 检测 Agent 重复编辑同一文件/反复调用同一工具/绕圈 | LangChain Harness 加反漂移后让 Agent 不再卡死循环 |
| **自我验证循环** | 让 Agent 跑测试/查日志/截图自检，强制走完 checklist 才能"完成" | 写代码→跑测试→查日志→修 bug 闭环 |

## 为什么Agent PM必须懂Agent工作流设计

1. **长任务可靠性瓶颈不在模型，在 Harness**——LangChain 不换模型只改 Harness，Terminal Bench 2.0 从 52.8%→66.5%（前 30 外→前 5）；Vercel 工具 15→2，准确率 80%→100%；Claude Code 模型决策逻辑只占 1.6%、98.4% 全是 Harness。PM 不懂工作流设计（即 Harness 设计）就只触到 Agent 的 1.6%，永远做不出生产级 Agent。[来源:腾讯云/Anthropic《Effective Harnesses for Long-Running Agents》| 🔍高 | 2026-06]
2. **40% Agentic AI 项目将在 2027 前被叫停**——Gartner 预测 2026 年 40% 企业应用引入 AI Agent（2025 不到 5%），但同期 40%+ 项目因成本失控和扩展性差被叫停。根本原因不是模型不行，是工作流设计（错误恢复/状态管理/HITL）没扛住长任务。PM 必须懂工作流设计才能让 Agent 真上生产而非停留在 Demo。[来源:51CTO《从ReAct到Loop Engineering》| 🔍高 | 2026-07]
3. **80% 企业 Agent 曾越出预设边界**——Salesforce 数据 80% 企业 AI Agent 曾越出预设边界行动；OpenClaw 事件 AI 疯狂删邮件无视停止指令；这些都不是模型问题，是工作流设计（HITL 护栏 + 紧急制动 + 副作用分级）失职。PM 是 HITL 设计的第一责任人，工程团队只是执行者。[来源:网易《一文讲透Harness Engineering》| 🔍高 | 2026-03]
4. **Loop Engineering 是 2026 第 4 次范式跃迁**——LLM → Prompt Engineering → Agent → Loop Engineering。Peter Steinberger 2026-06 推文："你不应该再去给编程 Agent 写 prompt，应该设计一套能给你的 Agent 写 prompt 的循环"。从"手写 prompt"到"设计能写 prompt 的 loop"是质变，PM 必须理解这个范式才能跟上 2026 Agent 工程前沿。[来源:百家号/知乎《Loop Engineering》| 🔍高 | 2026-06]
5. **Reflection/Plan-and-Execute 不是炫技是工程必需**——简单 ReAct 任务 3 步崩 2 次；复杂任务一个 Agent 从头做到尾容易半途而废。Planner 模式做代码审查实测：8 分钟 → 2.5 分钟、误判率 15% → 4%（拆 10 个子任务并行 + Evaluator 汇总）。设计模式不是让 Agent 更聪明而是更可靠，PM 必须会按任务复杂度选模式。[来源:腾讯云《Agent设计模式全景图》| 🔍高 | 2026-05]
6. **Context Rot 是长 Agent 的隐形杀手**——上下文窗口填满后模型推理和任务完成能力会逐渐变差（不是断崖是缓慢腐烂），跑了几十次工具调用后 Agent 开始"忘记"原始目标、重复编辑同一文件、绕圈。Vercel 减工具之所以能让准确率 80%→100%，核心就是缓解了 Context Rot。PM 必须懂 Compaction/检查点/Ralph Loop 才能设计出能跑百步的 Agent。[来源:腾讯云 Harness 报告 | 🔍高 | 2026-06]

## 常见误区

- **误区1：模型够强就不需要复杂工作流**——2026 共识：模型再强也只是 1.6%，Harness（工作流）占 98.4%；同一模型不同 Harness 差 7 倍效果（Claude Code SWE-bench 100% vs 裸 tool_calling 14%）。Bitter Lesson 警示：手工编码的"聪明"逻辑会被新模型一次次摧毁，必须保持 Harness 轻量、可丢弃
- **误区2：Agent 工作流 = ReAct 循环**——ReAct 是起点不是终点；它适合 90% 简单场景（3-10 步），但复杂长任务需 Plan-and-Execute + Reflection + 多 Agent 编排 + Compaction；只用 ReAct 的 Agent 跑 20 步以上必崩
- **误区3：错误恢复 = 让 Agent 重试**——重试只是 5 级恢复的第 1 级；只重试会陷入死循环（生产级 Agent 故障分布中工具调用死循环占 31% 最大类）。需配套：指数退避+限次 + 失败模式分析 + 降级 + 重规划 + 人工接管
- **误区4：HITL 是工程团队的事不是 PM 的事**——HITL 设计核心是"哪些操作必须人审"，这是业务/产品决策不是工程决策。删数据/转账/发布/邮件发送等不可逆操作的护栏等级必须 PM 拍板；DECO 实践证明 "prompt 管不住的，框架来堵"，但框架堵什么由 PM 定义
- **误区5：上下文窗口够大就不用 Compaction**——Context Rot 是缓慢腐烂不是断崖，200K 窗口在第 50 次工具调用后模型也变笨；Compaction 不是为了"塞下"而是为了"保持推理质量"。Claude Code 五层压缩 + Vercel 减工具都是为了对抗 Context Rot
- **误区6：状态管理 = 数据库存状态**——文件系统才是 Harness 最基础的状态原语（Anthropic 报告原话）；Agent 写文件比写数据库更通用、更可观测、更适合多 Agent 协作；LangGraph checkpoint 也基于文件系统语义
- **误区7：把 Loop Engineering 当成又一种 prompt 技巧**——Loop Engineering 是范式跃迁不是技巧：从"人写 prompt 给 Agent"变成"人设计 loop，loop 自动写 prompt 给 Agent"。Ralph Loop 在干净上下文中重新注入原提示词强行续跑——这是结构而非措辞
- **误区8：Hook 护栏写进 prompt 就够了**——prompt 约束 LLM 不可靠（DECO 实测 LLM 会偷懒/越权/失忆），必须代码层 Hook 确定性拦截；prompt 是建议、Hook 是法律
