## 二、文档引用关系

```
Phase 0
  ├─ 项目分析报告.md ──→ Phase 1 输入
  └─ AGENTS.md（初版） ──→ Phase 1/2/3 持续引用

Phase 1
  ├─ PRD.md ──→ Phase 2 plan.md 引用（来源规格）
  ├─ security_strategy.md ──→ Phase 2 plan.md 引用（安全检查清单对照）
  ├─ performance_goals.md ──→ Phase 2 plan.md 引用（性能考虑）；Phase 4 引用（性能评测对比）
  ├─ testing_strategy.md ──→ Phase 3 判定是否产测试方案
  ├─ file_structure.md ──→ Phase 2/3/4/6 AI 上下文
  └─ db_schema.md ──→ Phase 3 建表参考

Phase 2
  └─ plan.md ──→ Phase 3 逐 chunk 勾选执行
       ├─ 引用 PRD.md
       ├─ 引用 security_strategy.md
       └─ 引用 performance_goals.md

Phase 3
  ├─ 测试方案.md ──→ Phase 4 人工验收基准
  ├─ Feature Map ──→ Phase 4 review 验证一致性；Phase 6 变更时查调用链
  ├─ User-Ops ──→ Phase 4 逐项傻瓜式验证
  ├─ 功能 README ──→ 最终汇编成项目文档
  ├─ 开发进度文件 ──→ 持续更新
  └─ AGENTS.md ──→ 持续织入更新

Phase 4
  ├─ 引用 Phase 3 测试方案（人工验收）
  ├─ 引用 Phase 3 User-Ops（逐项验证）
  ├─ 引用 Phase 3 Feature Map（review 一致性）
  ├─ 引用 performance_goals.md（性能评测）
  ├─ 产出 快速启动速查表 ──→ Phase 5 部署时参考；Phase 6 变更时同步
  └─ 产出 验证/测试/性能/review 记录

Phase 5
  ├─ 引用 Phase 4 快速启动速查表（联动维护）
  ├─ 产出 部署手册 ──→ Phase 6 变更时同步
  └─ 迭代方向 ──→ 新增功能回 Phase 1/2；改/删已有进 Phase 6

Phase 6
  ├─ 引用 Feature Map（查调用链）
  ├─ 引用 User-Ops（若 UI 流程有变需同步）
  ├─ 引用 快速启动速查表（端口/服务变更时同步）
  ├─ 引用 部署手册（部署相关变更时同步）
  ├─ 引用 PRD（更新真相源）
  ├─ 复用 Phase 2 plan / Phase 3 实施 / Phase 4 验证 / Phase 5 部署
  ├─ 产出 影响评估 + 变更记录
  └─ 更新 Feature Map / User-Ops / 功能 README / AGENTS.md / 快速启动速查表 / 部署手册
```

## 三、文档分类：一次性的 / 重复更新的 / 按需产出的

### 3.1 一次性文档

项目生命周期内通常只产一次，除非发生根本性变化。

| 文档 | 说明 |
|------|------|
| `workflow_output/docs/项目分析/项目分析报告.md` | 商业分析，项目方向不变则不重写 |
| `workflow_output/docs/specs/PRD.md` | 需求规格，只迭代维护，不重复产出 |
| `workflow_output/docs/specs/architecture.md` | 架构规格，架构大改才重写 |
| `workflow_output/docs/specs/db_schema.md` | 数据模型，基础模型不变 |
| `workflow_output/docs/specs/testing_strategy.md` | 测试策略，整体策略不变 |
| `workflow_output/docs/specs/security_strategy.md` | 安全策略，安全体系不变 |
| `workflow_output/docs/specs/performance_goals.md` | 性能目标，目标不变 |
| `workflow_output/docs/file_structure.md` | 目录结构，结构大改才重写 |
| `workflow_output/docs/deploy/部署手册.md` | 部署环境，环境不变只更新 |
| `workflow_output/docs/run-guide/快速启动速查表.md` | 项目首次跑通产一次，启动方式有变才更新 |

### 3.2 重复更新文档

每次新增/修改/删除功能、每次迭代、每次变更都要更新。

| 文档 | 更新时机 |
|------|---------|
| `workflow_output/项目规范约束/AGENTS.md` | 每一轮对话结束，若产出通用能力就织入 |
| `workflow_output/开发进度/开发进度总览.md` | 每一轮对话结束 |
| `workflow_output/开发进度/<功能名>/*` | 每一轮对话结束 |
| `workflow_output/docs/feature-map/<功能名>.feature-map.md` | 每个功能完成时产；代码改了要更新 |
| `workflow_output/docs/user-ops/<功能名>用户操作手册.md` | UI 流程/入口/异常恢复有变就同步 |
| `workflow_output/docs/changes/变更记录.md` | 每次改/增/删已有功能追加一条 |
| `workflow_output/docs/plans/<功能名>.plan.md` | 每个新功能/大变更出一次 |

### 3.3 按需产出文档

只在特定条件下产出。

| 文档 | 产出条件 |
|------|---------|
| `workflow_output/docs/测试方案/<功能名>测试方案.md` | 仅当功能需要人工交互测试（UI/主观体验/真实第三方/需人工确认） |
| `workflow_output/docs/user-ops/<功能名>用户操作手册.md` | 仅 B/C 类用户可见功能（A 类纯技术功能不产） |
| `workflow_output/docs/run-guide/快速启动速查表.md` | 项目首次跑通或启动方式有变 |
| `workflow_output/docs/deploy/部署手册.md` | Phase 5 部署上线时 |
| `workflow_output/docs/changes/影响评估-<变更名>.md` | Phase 6 改/增/删已有功能前 |
| 性能评测报告 | Phase 4 对照 performance_goals 评测 |
| 桌面端测试记录 | 涉及桌面客户端（PyQt/Tauri/Electron） |
| 用户操作手册全量验证记录 | Phase 3 产了 User-Ops 时 |
| review 记录 | Phase 4 spawn 第二个 AI 审查时 |

## 四、进度文件专项

### 4.1 哪些文件属于进度跟踪

| 文件路径 | 类型 | 说明 |
|---------|------|------|
| `workflow_output/开发进度/开发进度总览.md` | 全局进度汇总 | 所有功能的进度汇总表 |
| `workflow_output/开发进度/<功能名>/<功能名>开发进度总览.md` | 功能级进度总览 | 单个功能全貌 |
| `workflow_output/开发进度/<功能名>/<功能名>开发进度1.md ... n.md` | 逐轮对话进度 | **每一轮对话结束**立即记录 |
| `workflow_output/开发进度/<功能名>/总路由.md` | 索引文件 | 文件数过多或总 tokens 超限时使用 |
| `workflow_output/docs/plans/<功能名>.plan.md` | 计划 + 进度勾选 | 每步 `- [ ]` 复选框，Phase 3 逐个勾选 |

### 4.2 是否有全局进度文件把控整个项目

**有** — `workflow_output/开发进度/开发进度总览.md` 是全局进度文件，汇总所有功能的状态（未开始 / 进行中 / 完成 / 暂停），并记录「沉淀的通用规范」和「下一步开发安排」。

### 4.3 进度文件什么时候更新

**不是等某个 chunk 或功能做完才更新，而是每一轮对话结束都必须更新。**

- **全局进度总览**：每一轮对话结束，同步更新。
- **功能进度总览**：每一轮对话结束，同步更新。
- **功能逐步骤进度**：每一轮对话结束，立即在 `开发进度n.md` 记录。
- **plan.md 勾选**：每完成一个 chunk，在 plan.md 里标为 done。

### 4.4 进度文件内容要求

#### 文档/理论类工作

| 字段 | 说明 |
|---|---|
| 步骤 | 本轮具体做了什么 |
| 产出文件 | 产出了什么文档 |
| 文件路径 | 文档最终存放位置 |
| 被谁引用 | 谁会读（AI / 开发 / 测试 / 决策者 / 运维）|
| 引用位置 | 在后续哪个 Phase 或哪份文档里会被引用 |

#### 代码类工作

| 字段 | 说明 |
|---|---|
| 实现功能 | 本轮实现了什么功能点 |
| 对应 plan.md / PRD 编号 | 该功能在计划或 PRD 中的出处 |
| 涉及文件 | 改动了哪些代码文件 |
| 代码位置 | 关键函数/类/路由的位置 |
| 测试情况 | 跑了什么测试，结果如何 |
| 是否 commit | commit 信息或 SHA |

### 4.5 进度文件是否会拆分

**会拆分** — 按功能拆分子目录，并按轮次拆文件：

```
workflow_output/开发进度/
├── 开发进度总览.md            ← 全局
└── <功能名>/
    ├── 总路由.md                ← 文件数过多或总 tokens 超限时使用
    ├── <功能名>开发进度总览.md   ← 功能级
    ├── <功能名>开发进度1.md       ← 第 1 轮对话
    ├── <功能名>开发进度2.md       ← 第 2 轮对话
    └── <功能名>开发进度n.md       ← 第 n 轮对话
```

### 4.6 5000 tokens 硬限制

**工作流已明确规定：所有 Phase 3 产出文档不得超过 5000 tokens。**

| 场景 | 处理方式 |
|---|---|
| 单个 `开发进度n.md` 接近 4000 tokens | 预警，准备收尾 |
| 单个 `开发进度n.md` 达到 5000 tokens | 新建 `开发进度<n+1>.md` |
| 一个功能的进度文件数量过多、查找困难 | 建 `总路由.md`，按轮次/主题索引 |
| Feature Map 过大 | 拆技术清单/建表注解子文件 |
| User-Ops 过大 | 按子功能拆分 |
| 功能 README 过大 | 拆用户地图/技术说明 |
| 测试方案过大 | 按正常/异常/边界/桌面端拆分子文件 |

> 📌 建议：若一个 `开发进度n.md` 超过 5000 tokens，先反思本轮对话是否粒度太大；其次才是拆分文件。拆分后必须用总路由或索引保持可导航。

## 六、关键结论

1. **文档总数**：工作流定义了约 20+ 种文档模板，分布在 8 个 Phase + 横切层。
2. **引用主线**：`PRD → plan → 代码 → Feature Map/User-Ops → 验证 → 部署`，规格是「唯一真相源」。
3. **Phase 6 是文档同步的关键节点**：改/删功能时必须同步更新 Feature Map、User-Ops、快速启动速查表、部署手册、PRD、功能 README、测试方案。
4. **进度文件设计**：全局总览 + 按功能拆分，天然控制文件规模，但未明确 tokens 上限。
5. **按需产出设计合理**：测试方案、User-Ops、桌面端测试、性能评测等都不强制产出，避免文档膨胀。
