# 4.2 协议集成 SOP 与模板

## SOP 1·MCP Server 搭建（5 步）

**目标**：把外部工具/数据源封装成 MCP Server，让 Agent 能用 MCP 调用
**适用**：单 Agent / 多 Agent / 任意场景

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 选 Transport：本地 IDE 用 stdio，云端/多用户用 HTTP+SSE 或 Streamable HTTP | Transport 决策 |
| 2 | 按 MCP SDK（TypeScript/Python/Java/Rust/Go/C# 至少 6 种官方 SDK）搭建 Server 骨架 | Server 代码骨架 |
| 3 | 定义 Tool/Resource/Prompt：每个工具写 name/description/inputSchema（JSON Schema）/handler | Tool 定义清单 |
| 4 | 鉴权与限流：HTTP 模式必加 Bearer Token / API Key / OAuth；高负载加速率限制 | 鉴权与限流策略 |
| 5 | 升级 2026-07-28 修订版能力：加 Telemetry/Metrics/Tracing/Invocation Log/Audit Trail | 治理方案 |

**MCP Server 设计模板（精简）**：
- Server name / version / description
- Transport（stdio / HTTP+SSE / Streamable HTTP）
- Tools 列表（每个含 name/description/inputSchema/handler/permission）
- Resources 列表（每个含 uri/description/mimeType）
- Prompts 列表（每个含 name/description/arguments）
- 鉴权方案 + 限流策略
- 治理能力（Telemetry / Audit / Invocation Log）

## SOP 2·A2A 多 Agent 互联（6 步）

**目标**：让 Agent 能通过 A2A 互相委派任务（跨厂商/跨生态 Agent 互联）
**适用**：多 Agent 协作 / Swarm / 自主 Agent

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 为每个 Agent 设计 AgentCard（well-known/agent-card.json），含能力描述与接口 | AgentCard 文件 |
| 2 | 实现 task/send / tasks/get / tasks/cancel JSON-RPC 端点 | A2A Server 端点 |
| 3 | 实现 SSE 流式进度推送（Task 状态机：submitted→working→input-required→completed→cancelled→failed） | 任务状态机 |
| 4 | 定义 Artifact 结构（任务的最终产出物格式），跨厂商约定 | Artifact Schema |
| 5 | 加鉴权层（每个 Agent 的 API Key / OAuth）；防范恶意 Agent 冒充 | 鉴权方案 |
| 6 | 加 Telemetry（任务成功率/平均时长/失败原因），便于多 Agent 系统调优 | 监控看板 |

**A2A AgentCard 模板（精简）**：
```json
{
  "name": "code-review-agent",
  "description": "Code review agent specialized in TypeScript projects",
  "version": "1.0.0",
  "capabilities": ["code-review", "typescript", "best-practices"],
  "endpoints": {
    "taskSend": "/a2a/task/send",
    "taskGet": "/a2a/task/{id}",
    "taskCancel": "/a2a/task/{id}/cancel"
  },
  "auth": { "type": "bearer", "scheme": "apiKey" },
  "skills": ["typescript-review"]
}
```

## SOP 3·AG-UI 前端集成（5 步）

**目标**：让 Agent 过程实时推送前端，前端可视化 Agent 规划/工具调用/状态/人审
**适用**：所有需前端可视化的 Agent（人机协同/自主/多 Agent 强烈推荐）

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 选前端 SDK（React/Vue/Svelte），用 CopilotKit 提供的官方 SDK | SDK 集成 |
| 2 | 后端实现 AG-UI 事件流端点（HTTP+SSE），订阅 16 种标准事件类型 | 事件流端点 |
| 3 | 前端组件订阅事件：TextMessageChunk（对话流）/ ToolCallEvents（工具可视化）/ StateSnapshot（状态同步）/ HumanApprovalRequest（人审） | 前端组件 |
| 4 | 加 State Sync：Agent 后端状态变更→ SSE 推送 → 前端状态同步（避免黑盒等结果） | 状态同步方案 |
| 5 | 人审节点设计（人机协同必做）：定义审批触发器/审批人/审批结果回传 | 人审 SOP |

**AG-UI 事件流设计模板（精简）**：
- 端点：HTTP+SSE，事件 16 种类型
- 必选事件：TextMessageChunk / ToolCallStart / ToolCallEnd / StateSnapshot / RunError
- 人机协同加：HumanApprovalRequest / HumanApprovalResponse / HumanInputRequest
- State Sync 策略：每次 Agent 状态变更推送 1 次
- 错误处理：RunError 事件触发前端降级 UI

## SOP 4·Skills 能力封装 + ACP 边缘协同（5 步）

**目标**：把领域 know-how 打包成 Skills；如适用，加 ACP 边缘协同
**适用**：有领域专长（产品经理方法论/法务/医疗/工业）；边缘/IoT Agent 加 ACP

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 拆解领域 know-how：把方法论/规范/最佳实践拆成 Skill 单元（每个 Skill 是一段指令集+方法论） | Skill 拆解清单 |
| 2 | 按 Anthropic Skills 格式打包：name/description/instructions/examples/version | Skills 包 |
| 3 | 发布与复用：发布到内部 Skills 仓库或 Anthropic 生态（如适用） | Skills 仓库 |
| 4 | （边缘场景）集成 ACP：IBM Bee Agent Framework 实现 Agent 间上下文共享与本地协同 | ACP 集成 |
| 5 | 加 Skills 版本管理与冲突消解：多 Skill 加载时优先级与冲突解决策略 | Skills 治理方案 |

**Skills 打包模板（精简）**：
```yaml
name: product-manager-requirement-analysis
description: 产品经理需求分析方法论 Skills，加载后 Agent 获得需求拆解/优先级排序/MVP 划分能力
version: 1.0.0
instructions:
  - 需求拆解：用 KANO 模型分类基本/期望/兴奋型需求
  - 优先级：用 MoSCoW+RICE 双方法排序
  - MVP 划分：用 Walking Skeleton 方法
examples:
  - input: "用户要做一个AI客服"
    output: "需求拆解：必选-知识库问答/可选-情绪识别/可选-自动转人工..."
```

## 常见坑清单

- 立项阶段不做协议选型，开发后期才发现协议不匹配，集成成本翻倍
- MCP 用旧版上生产，缺可观测/可审计/可治理能力，出问题无法回溯
- A2A 未做鉴权层，恶意 Agent 冒充调用导致数据泄露
- AG-UI 未做 State Sync，前端等结果黑盒，用户体验差
- Skills 多加载无冲突消解，多 Skill 指令互相矛盾
- 国内合规场景未预留 Adapter 层，国标一旦正式化后改造成本巨大
