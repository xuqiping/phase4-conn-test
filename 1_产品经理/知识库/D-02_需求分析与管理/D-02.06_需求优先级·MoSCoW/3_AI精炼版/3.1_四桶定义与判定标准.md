# 3.1 四桶定义与判定标准

## 定义

MoSCoW优先级框架源自DSDM（动态系统开发方法），是**四桶分类优先级模型**——将需求分为Must-have/Should-have/Could-have/Won't-have四类，核心价值在于**强迫PM在资源约束下做出显式取舍**，特别是"Won't"桶的声明——不做什么和做什么同样重要。[来源:DSDM Consortium | 🔍高]

> 核心判断：MoSCoW不是排序框架而是**分类框架**——它不解决"Must桶内的10个需求先做哪个"（需RICE辅助），它解决的是"这4个需求根本不该做"（Won't桶）。

## 四桶定义与判定标准

### Must-have（必须有）

| 维度 | 标准 |
|---|---|
| **定义** | 没有这个需求，产品/项目**不可交付**、不可上线 |
| **判定问题** | "如果不做这个需求，我们能上线吗？" → 不能=Must |
| **常见类型** | 合规要求、核心流程、安全修复、合同承诺 |
| **资源占比建议** | ≤60%的资源（超过=Must膨胀→需重新审视） |
| **常见混淆** | "重要"≠Must——需求可以很重要但不是"缺了不可运行" |

### Should-have（应该有）

| 维度 | 标准 |
|---|---|
| **定义** | 重要但**可暂缓**的需求——不做不会导致不可交付，但做了有显著价值 |
| **判定问题** | "如果这个版本不做，下个版本补上行吗？" → 行=Should |
| **常见类型** | 效率提升、体验优化、覆盖率扩充 |
| **资源占比建议** | ~20%的资源 |
| **常见混淆** | Should≠"不太重要"——Should是重要但可延迟 |

### Could-have（可以有）

| 维度 | 标准 |
|---|---|
| **定义** | **锦上添花**——做了增加价值，不做也无妨 |
| **判定问题** | "如果永远不做这个需求，有人会抱怨吗？" → 不会=Could |
| **常见类型** | 微优化、边缘场景、视觉美化 |
| **资源占比建议** | ~10%的资源（时间允许才做） |
| **常见混淆** | Could≠"不值得做"——可能是创新方向但优先级低 |

### Won't-have（这次不做）

| 维度 | 标准 |
|---|---|
| **定义** | **明确排除**——本次/本版本/本Sprint不做，可能以后做 |
| **判定问题** | "我们能不能明确告诉相关方，这次不做？" → 能=Won't |
| **常见类型** | 无差异需求、反向需求、超出范围的需求 |
| **关键价值** | **Won't桶是MoSCoW最有价值的桶**——显式声明"不做"比隐式忽略更有效 |
| **常见混淆** | Won't≠"永远不会做"——只是"这次不做"，下次可能升桶 |

## Must桶膨胀的识别与治理

Must桶膨胀是MoSCoW最常见的问题——所有需求都成了"必须有"：

| 信号 | 原因 | 治疗方法 |
|---|---|---|
| Must占比>60% | 利益方不愿接受低优先级 | 回到判定问题："没有这个需求能上线吗？" |
| Won't桶为空 | 不敢拒绝任何人 | 强制要求Won't桶≥10%的需求 |
| Everything is priority 1 | 优先级通胀 | 改用RICE量化排序，再按分位数切为M/S/C/W |
| "老板说都是Must" | 政治压力 | 用MVP思维："如果只能做3个功能，哪3个？" |

## MoSCoW vs "高/中/低"优先级

| 维度 | MoSCoW | 高/中/低 |
|---|---|---|
| 分类数量 | 4桶 | 3档 |
| 隐式vs显式 | 显式声明"不做"(Won't) | 没有"不做"档→需求不会被真正砍掉 |
| 资源约束意识 | Must≤60%规则 | 无资源约束意识 |
| 取舍压力 | 强迫取舍（Won't桶必须填） | 无取舍压力→"都是高优先级" |
| 可操作性 | 直接驱动Sprint排期 | 需再翻译为"做/不做" |

> MoSCoW的核心价值不在分类本身，而在**Won't桶的声明效应**——"我们这次不做X"比"X是低优先级"有效100倍。[来源:📚训练知识 | 📚中]
