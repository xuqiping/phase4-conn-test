# 5.1 案例集（10 例）

## 案例 1：Anthropic Claude Code 100% vs 裸 tool_calling 14% —— 模型vs框架归因标杆

**背景**：2026 Anthropic 披露同一 Claude 模型，Claude Code 应用框架下任务成功率 100%，而裸 tool_calling 基线仅 14%——同模型不同框架，结果差 7 倍。这是 2026 Agent 评测领域最具冲击力的归因案例，直接动摇"模型决定一切"的旧认知。[来源:Anthropic / CSDN 2026-03 | 🔍高 | 2026]

**手法**：固定模型，对比不同 Harness 工程设计。Claude Code 的 100% 来自五层 Compaction（L1 工具输出截断 / L2 历史总结 / L3 Dump 文件 / L4 AGENTS.md / L5 Reset+Ralph Loop）+ AGENTS.md 记忆文件 + Ralph Loop 长任务恢复 + 工具精简（Anthropic 自身案例：15 个工具精简到 2 个）+ 工具调用容错。裸 tool_calling 基线无任何 Harness 工程，模型直接面对原始多步任务。差距归因——7 倍差距全部归因于 Harness 工程设计，模型本身零差异。[来源:Anthropic / CSDN | 🔍高 | 2026]

**影响**：确立"模型 vs 框架归因"是 2026 Agent 评测核心命题。过去评测假定"换模型→换结果"，本案例证明"换框架→换结果"幅度可能更大（7 倍差距 vs 模型间通常 20-50% 差距）。直接催生 Harness Engineering 范式（案例 10）与"模型分 vs 框架分"归因实验设计（本叶子 § 4.2 T6）。

**启示**：① 同模型换框架是 Agent 评测归因的标配实验——不做就误判优化方向（会去换模型而错过框架优化）；② 7 倍差距说明 Harness 工程 ROI 远高于模型升级 ROI——团队应优先优化框架而非堆模型；③ 五层 Compaction + AGENTS.md + Ralph Loop + 工具精简 + 工具容错是可复用的五项框架级提升手段；④ "工具精简 15→2"反直觉但高 ROI——工具越多选择越难；⑤ 模型评测结果必须配框架归因报告才有意义。

## 案例 2：SWE-bench —— 编码类 Agent 持续迭代基准（主流基准标杆）

**背景**：SWE-bench 是 2025-2026 编码类 Agent（AI Coding / IDE / Copilot）的事实标准评测基准，覆盖 GitHub Issue 修复等真实编码任务。SOTA 持续迭代，是衡量 AI 编码能力进化曲线的核心标尺。[来源:SWE-bench 官方 / CSDN | 🔍高 | 2025-2026]

**手法**：从真实 GitHub 仓库抓取 Issue + 对应 PR，要求 Agent 在仓库代码库内自主定位 bug + 修改代码 + 通过测试用例。评测任务成功率 + 通过测试用例比例。SOTA 在 2026 持续推高，Anthropic Claude Code / Cursor / GitHub Copilot 等头部编码 Agent 均以 SWE-bench 为对外披露的核心指标。SWE-bench 还衍生出 SWE-bench Verified（人工验证子集）等更可信版本，应对污染与可信度质疑。[来源:SWE-bench / Anthropic | 🔍高 | 2026]

**影响**：SWE-bench 成为编码 Agent 领域"事实标准基准"——任何编码 Agent 产品对外宣称能力必须有 SWE-bench 分数对标。直接推动编码 Agent 评测从"主观 Demo"转向"客观基准"。同时催生污染治理实践——SWE-bench Verified 子集是行业应对训练污染的标准动作。

**启示**：① 编码类 Agent 评测必选 SWE-bench——这是本叶子 § 4.2 T2 选型决策树第一推荐；② SOTA 持续迭代意味着评测要持续跟踪，去年 SOTA 今年可能已落后；③ Verified 子集启示——任何主流基准都需要污染治理机制；④ 真实仓库 + 真实测试用例是高质量 Agent 基准的设计哲学；⑤ 与本叶子 § 4.1 第3段基准选型直接联动。

## 案例 3：TAU-bench（τ-bench）—— 工具调用类 Agent 中水位基准（主流基准标杆）

**背景**：TAU-bench（τ-bench）是 2025-2026 工具调用类 Agent（工具调用 / 客服 / Copilot）的主流评测基准，覆盖工具选择 + 工具执行 + 多步协同整个工具调用链路。当前 SOTA 处中水位——既非接近满分（说明任务有难度）也非极低（说明任务设计合理）。[来源:TAU-bench 论文 / 知乎 | 🔍高 | 2025-2026]

**手法**：构造多步工具调用任务——Agent 需选择正确工具 + 传入正确参数 + 处理工具返回结果 + 决定下一步。评测工具调用正确率三连（Tool Selection Accuracy / Tool Execution Success / Multi-Step Coherence）。覆盖客服 / 工单 / Copilot 场景。中水位 SOTA 说明工具调用 Agent 仍有巨大优化空间，特别是 Multi-Step Coherence——单步正确率高但多步累积后大幅下降（呼应对应 35% 累积效应）。[来源:TAU-bench / 知乎 | 🔍高 | 2026]

**影响**：TAU-bench 与 SWE-bench 形成"工具调用 vs 编码"双主流 Agent 基准格局。推动"工具调用正确率三连"成为 Agent 评测标配——这成为本叶子 § 3.1 Agent 区别 LLM 评测的标志指标。中水位 SOTA 提醒行业——工具调用 Agent 远未成熟，需持续优化。

**启示**：① 工具调用类 Agent 评测必选 TAU-bench——本叶子 § 4.2 T2 选型决策树推荐；② 工具调用正确率三连是 Agent 评测区别 LLM 评测的标志——必须配齐；③ 中水位 SOTA 提醒——别被 Demo 漂亮误导，工具调用 Agent 实际能力远未成熟；④ Multi-Step Coherence 是最敏感指标——单步 90% 十步后可能 35%，是评测多步 Agent 的核心；⑤ 客服 / Copilot 场景 TAU-bench 是首选。

## 案例 4：Tool Decathlon（ICLR'26）—— 长程真实任务 sota<30%（最真实基准）

**背景**：2026 ICLR 论文 Tool Decathlon 提出"真实多样长程 Agent Tool 任务"评测基准，与 SWE-bench / TAU-bench 不同——它专注长程（多步、跨域、真实工具）场景。关键数据：SOTA 不超过 30%——这是 6 大基准中最低水位，说明它最贴近真实世界、最难。[来源:Tool Decathlon ICLR'26 / 知乎 / Berkeley | 🔍高 | 2026]

**手法**：构造 10 类真实工具的跨域长程任务——Agent 需要在一个任务内跨多个工具、跨多个领域、跨多个会话步骤完成任务。SOTA < 30% 的低水位来自三个真实特征：① 工具多样性高（10 类）② 任务长程（多步累积错误）③ 真实世界参数与异常（非合成）。这与 SWE-bench（专注单一领域编码）/ TAU-bench（专注工具调用但相对短程）形成差异化定位。Tool Decathlon 还专为 MCP Agent（Model Context Protocol 工具生态）评测预留扩展位。[来源:ICLR'26 / 知乎 | 🔍高 | 2026]

**影响**：Tool Decathlon 让行业看到"真实世界的 Agent 难度被严重低估"——SOTA < 30% 意味着最先进的 Agent 在真实长程任务上 70% 都做不好。推动 MCP 生态评测标准化。直接支撑 Gartner 88% 项目无法跨越生产鸿沟的结论——因为真实长程任务 70% 不达标。

**启示**：① 长程真实任务 Agent 必选 Tool Decathlon——这是本叶子 § 4.2 T2 选型决策树推荐；② SOTA < 30% 是对行业"Agent 已成熟"叙事的现实矫正；③ 真实世界 Agent 评测必须有低水位基准——只有 SOTA 接近满分的基准会让团队误判；④ MCP 生态评测是未来方向——Tool Decathlon 已预留扩展；⑤ 多步错误累积（35% 效应）在长程任务中被放大——Multi-Step Coherence 是评测重点。

## 案例 5：MAST —— 多 Agent 87% 失败率（多 Agent 失败模式基准）

**背景**：MAST（Multi-Agent System Testbench）是多 Agent 系统失败模式评测基准。来自 Berkeley 等团队 2026 研究——多 Agent 系统 87% 失败率。这是 6 大基准中唯一专注多 Agent 失败模式的基准，填补了 D-24.05 多 Agent 协作评测的空白。[来源:MAST / Berkeley / 知乎 | 🔍高 | 2026]

**手法**：构造多 Agent 协作任务——多个 Agent 共享状态 / 通信 / 分工 / 汇总。系统化分类多 Agent 失败模式——通信失败 / 状态不一致 / 任务分配错误 / 汇总错误 / Agent 死锁 / Agent 抢占等。87% 失败率覆盖所有多 Agent 系统类型——从同构 Agent 群到异构 Agent 团队。MAST 不只测成功率，还诊断失败模式——这是它与 SWE-bench / TAU-bench 的差异化定位。[来源:MAST / Berkeley | 🔍高 | 2026]

**影响**：MAST 让行业第一次量化"多 Agent 系统到底多难"——87% 失败率远高于单 Agent 系统。直接支撑 D-24.05 多 Agent 协作的工程难度警示——多 Agent 不是简单堆 Agent 数量，而是复杂的系统工程。推动多 Agent 评测从"成功率"扩展到"失败模式诊断"——只有诊断失败模式才能优化。

**启示**：① 多 Agent 系统评测必选 MAST——本叶子 § 4.2 T2 选型决策树推荐；② 87% 失败率证明多 Agent 系统工程难度远高于单 Agent——不是堆 Agent 数量那么简单；③ 失败模式诊断比成功率更重要——只有诊断失败模式才能优化（呼应 D-24.05 § 4.1 多 Agent 失败模式分析）；④ 多 Agent 评测必须联动 D-24.05 § 4.1 多 Agent 协作设计——形成"设计→评测"闭环；⑤ 多 Agent 上线前必须跑 MAST，不然上线后 87% 失败将成为生产事故。

## 案例 6：Gartner 88% 项目失败 + 4.2 倍故障率 —— 行业警示案例

**背景**：Gartner 2026-07 行业报告——88% Agent 试点项目无法跨越生产鸿沟（从 Demo 到生产的鸿沟），无评测体系 Agent 上线后故障率 4.2 倍于成熟项目。这是 2026 下半年 Agent 评测领域最权威的行业警示。腾讯云等多家中文媒体转述。[来源:Gartner / 腾讯云 2026-07 | 🔍高 | 2026-07]

**手法**：Gartner 调研大量 Agent 试点项目，发现 88% 项目在"Demo 漂亮 → 生产事故"的鸿沟前止步。根因分析——这些项目缺乏可观测性与科学评估体系，只跑 Demo 不做评测。无评测体系 Agent 上线后故障率 4.2 倍于有评测体系的成熟项目。报告进一步指出——行业正从"Demo 驱动"转向"度量驱动"，Agent 进入"质量内建"时代。[来源:Gartner / 腾讯云 | 🔍高 | 2026-07]

**影响**：88% 与 4.2 倍两个数字成为 2026 下半年 Agent 评测领域最常被引用的行业警示数字。直接推动"Demo→度量"范式跃迁（详见案例 10）成为行业共识。推动可观测性与评测体系成为 Agent 上线的"硬性基建"——不再是可选项。

**启示**：① 88% 项目无法跨越生产鸿沟——意味着不做评测体系的 Agent 项目 12% 才能落地，PM 必须把评测列入路线图而非临时补；② 4.2 倍故障率证明评测体系的投入 ROI 极高——成本可控且失败代价显著降低；③ "Demo 驱动 → 度量驱动"是范式跃迁——团队必须从"展示能力"转向"度量能力"；④ 质量内建是 Agent 时代新主线——评测不是上线后补的环节，是开发期就内建的能力；⑤ 本叶子 § 4.1 第1段评测需求诊断的失败代价评估直接对标这两个数字。

## 案例 7：KRAFTON AI LLM-as-Judge 30% 偏差 —— 评测方法警示案例

**背景**：KRAFTON AI 研究团队 2026 系统化研究 LLM-as-Judge（用 LLM 评测 LLM）的偏差，发现 LLM-as-Judge 有 30% 评测偏差——即 30% 的评测结果与人工评测不一致。这是 2026 LLM-as-Judge 偏差治理领域的"敲钟研究"。同期 BabelJudge（arXiv 2606.22329 2026-06）/ MM-JudgeBias（Seoul/NAVER/KAIST 2026-05）/ WebDevJudge（ICLR'26 Oral）等系列研究针对不同偏差类型深化。[来源:KRAFTON AI / arXiv 2606.22329 / ICLR'26 | 🔍高 | 2026]

**手法**：KRAFTON 系统化分类 LLM-as-Judge 四种偏差——位置偏差（答案顺序影响评测） / 跨语言偏差（非英语评测不准，BabelJudge 治理）/ 多模态组合偏差（图文组合偏差，MM-JudgeBias 治理）/ 场景特化偏差（通用 Judge 在特定场景不准，WebDevJudge 治理）。并提出 Continuous Eval Pipeline 四层 Judge 系统（L1 单点 → L2 多 Judge 投票 → L3 Meta-Eval → L4 自适应）治理 30% 偏差。[来源:KRAFTON / BabelJudge / MM-JudgeBias / WebDevJudge | 🔍高 | 2026]

**影响**：30% 偏差基线成为 LLM-as-Judge 领域的"标准对标数字"——告诉业界"裸 LLM-as-Judge 不可信，必须治理"。直接推动 Continuous Eval Pipeline 四层 Judge 系统成为工程化标配。催生 BabelJudge / MM-JudgeBias / WebDevJudge 等专项偏差治理工具链。

**启示**：① LLM-as-Judge 不能裸跑——30% 偏差基线意味着裸跑的评测结果完全不可信，必须治理；② 四类偏差必须逐项治理——本叶子 § 4.2 T3 Judge 系统配置表是直接对策；③ Continuous Eval Pipeline 四层 Judge 系统是工程化标配——至少配 L1+L2，关键任务配 L3；④ 专项偏差治理工具（BabelJudge 跨语言 / MM-JudgeBias 多模态 / WebDevJudge 场景特化）按需选；⑤ L3 Meta-Eval "评评测的 Judge"是治理偏差的元方法——治理者也要被治理。

## 案例 8：Token 燃烧炉 —— 成本失控反面教材

**背景**：2026-07-13 腾讯云披露 Token 燃烧炉事故——Agent 陷入死循环思考，单次对话消耗数十万 Token。这不仅造成单笔巨额账单，更暴露 Agent 成本失控是生产事故级问题。这是 2026 Agent 评测领域成本维度的标志性反面教材。[来源:腾讯云 2026-07-13 | 🔍高 | 2026-07-13]

**手法**：Agent 在复杂任务中陷入死循环——反复调用推理但始终无法收敛到答案，每轮消耗数千到数万 Token，单次对话累积达数十万 Token。根因分析——缺乏 Token 归因与预算熔断机制：① 没有实时 Token 计数（不知道烧了多少）② 没有业务维度归因（不知道哪个场景烧）③ 没有预算硬限制（超限不熔断）④ 没有熔断降级（不切换 cheaper 模型）⑤ 没有成本告警（超标不告警）。腾讯云提出治理五层（L1 实时计数 → L2 业务归因 → L3 预算硬限制 → L4 熔断降级 → L5 成本告警）。[来源:腾讯云 2026-07-13 | 🔍高 | 2026-07]

**影响**：Token 燃烧炉成为 2026 Agent 成本评测与治理的标志性反面教材。直接推动行业把"成本维度"作为 Agent 评测四维框架之一（之前的 Agent 评测普遍只看准确率）。推动 Token 五层治理成为 Agent 成本治理标配——本叶子 § 4.2 T5 可观测看板直接落地。

**启示**：① 只看准确率不看成本是 Agent 评测第二大错——Token 燃烧炉证明成本失控等同于生产事故；② Token 五层治理是底线——本叶子 § 4.2 T5 直接对标；③ Agent 死循环是真实风险——必须在 Harness 层防御（不只是评测层）；④ 成本敏感场景必须配效率智能体（固定预算最大化成功率）；⑤ 本案例与本叶子 § 4.1 第7段可观测建设直接联动。

## 案例 9：EdgeOne Makers 内置三件套 —— 可观测工程标杆

**背景**：腾讯云 EdgeOne Makers 在 2026 推出"内置可观测三件套"——Logs 日志 + Metrics 指标 + Traces 链路追踪开箱即用，Agent 开发者无需自建可观测基础设施。是 2026 国内 Agent 可观测工程化的标杆产品。[来源:腾讯云 EdgeOne Makers 2026 | 🔍高 | 2026]

**手法**：把可观测三件套（Logs/Metrics/Traces）作为 Agent 平台的"内置基建"——开发者部署 Agent 时自动获得完整的可观测能力，无需自建 ELK + Prometheus + Jaeger。同时针对 Agent 独特挑战做优化——非确定性输出（多次运行统计）/ 复杂调用链（深嵌套追踪）/ 成本敏感（Token 计数）/ 延迟波动（P99 看板）。这让小团队也能拥有大厂级的 Agent 可观测能力。[来源:腾讯云 EdgeOne Makers | 🔍高 | 2026]

**影响**：EdgeOne Makers 思路成为小团队 Agent 可观测的参考标杆——"内置三件套"成为 Agent 平台标配能力方向。推动 Agent 可观测从"自建基础设施"转向"平台内置开箱即用"——大幅降低团队接入可观测的门槛。同期 LangSmith / Arize Phoenix / Langfuse 等 LLMOps 平台爆发，形成完整的 Agent 可观测工具生态。

## 案例 10：字节 JD 评测闭环到 RL + Harness Engineering 范式跃迁 —— 闭环与范式升级标杆
