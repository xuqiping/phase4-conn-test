# 3.1 埋点基础与三大模式

## A.01 核心定义

**数据采集（Data Collection/Tracking）** 是将用户在产品中的行为转化为可度量数据的过程，是数据分析的地基——没有采集就没有分析。埋点(Tracking/Instrumentation)是数据采集的核心实现方式。

**一句话定位**：数据采集是产品的"传感器"——把用户每一步行为翻译成数据，让分析师和产品经理看到"用户在做什么"。

## A.04 边界与不含什么

**数据采集包含**：埋点方案设计、事件与属性定义、采集模式选型、数据质量管理、隐私合规、采集架构选型。

**数据采集不含**：指标体系设计（→D-06.01）、数据分析方法（→D-06.03~06）、数据仓库架构（→D-06.09）、数据可视化（→D-12）。

## D.01 定义域

| 维度 | 说明 |
|---|---|
| 核心问题 | "怎么把用户行为变成可分析的数据？" |
| 适用对象 | 产品经理、数据分析师、前端/移动端开发 |
| 典型使用 | 新功能埋点设计、数据问题排查、采集方案评审 |
| 不适用 | 纯日志运维监控、财务数据报送 |

## I.01 核心术语

| 术语 | 定义 |
|---|---|
| 埋点(Tracking) | 在代码中植入数据采集逻辑，记录用户行为 |
| 事件(Event) | 用户的一个行为或系统的一个动作（如"点击购买按钮"） |
| 属性(Property) | 事件的附加信息（如"商品ID=123"） |
| Tracking Plan | 埋点方案的规范文档，含所有事件/属性定义 |
| 代码埋点 | 在源代码中硬编码采集逻辑 |
| 可视化埋点 | 通过可视化界面圈选元素自动埋点 |
| 全埋点/无埋点 | SDK自动采集所有用户交互行为 |
| ID Mapping | 跨设备/跨端关联同一用户的身份标识 |
| 数据脱敏 | 隐藏/替换敏感信息（如手机号138****5678） |
| 数据上报 | 从客户端向服务端发送采集数据的过程 |

## 三大采集模式对比

| 维度 | 代码埋点 | 可视化埋点 | 全埋点/无埋点 |
|---|---|---|---|
| **原理** | 开发在代码中写采集逻辑 | 运营通过可视化工具圈选元素 | SDK自动采集所有交互 |
| **精度** | 最高（行为明确定义） | 中等（依赖元素识别） | 低（大量冗余数据） |
| **灵活性** | 最高（自定义事件+属性） | 中等（预定义事件类型） | 低（无法自定义属性） |
| **开发成本** | 高（需发版） | 低（运营自助） | 最低（SDK一次集成） |
| **维护成本** | 高（代码变更需更新埋点） | 中等（元素变化需重新圈选） | 低（SDK自动适配） |
| **漏采风险** | 人工遗漏 | 元素识别失败 | 极低 |
| **数据质量** | 依赖规范执行 | 依赖圈选准确度 | 需事后筛选 |
| **适用阶段** | 成熟产品、核心路径 | 迭代快速、运营驱动 | 早期探索、全量监控 |
| **典型工具** | 自建/神策/Mixpanel | GrowingIO/Sensors | Heap/神策AutoTrack |

**最佳实践**：三种模式**混合使用**——核心路径用代码埋点保精度，运营需求用可视化埋点降低成本，全量兜底用全埋点防漏采。[来源: 神策数据最佳实践 | 置信度:🔍高]
