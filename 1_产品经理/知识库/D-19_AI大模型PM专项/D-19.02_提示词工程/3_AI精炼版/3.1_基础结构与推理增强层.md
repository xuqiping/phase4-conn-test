# 3.1 基础结构与推理增强层

## 一、L1 基础结构层

基础结构层是任何提示词的骨架，给模型提供清晰的角色/目标/步骤/格式约束。2026年的基础结构远比2023年的"你是一个专家..."成熟。

### 1.1 主流结构化模板

| 模板 | 结构 | 适用场景 | 来源 |
|---|---|---|---|
| **CREATE** | Context(上下文)·Request(请求)·Explanation(解释)·Action(行动)·Tone(语气)·Extras(附加) | 通用任务 | [CSDN CREATE框架 | 🔍高 | 2026-05] |
| **CRISPE** | Capacity(能力)·Role(角色)·Insight(洞察)·Statement(声明)·Personality(个性)·Experiment(实验) | 角色/创意类 | 📚中 |
| **RISEN** | Role(角色)·Instruction(指令)·Steps(步骤)·End state(目标)·Narrowing(约束) | 复杂多步任务 | 📚中 |
| **RACE** | Role·Action·Context·Expectation | 简单任务快速结构化 | 📚中 |
| **TRACE** | Task·Request·Action·Context·Example | 任务+示例驱动 | 📚中 |

**结构化原则（4条铁律）**：[来源:提示词工程深度全解 | 🔍高 | 2026-06]
1. **角色要具体**：不写"你是专家"，写"你是深耕8年的B端SaaS PM"
2. **目标可量化**：不写"写好文章"，写"输出1500字±100字、5段结构、每段有数据"
3. **步骤明示**：复杂任务明示步骤顺序，简单任务可不写
4. **格式强约束**：要结构化输出必加JSON Schema/表格字段定义

### 1.2 上下文工程（Context Engineering）

上下文工程是2026年提示词工程的核心能力——动态注入相关知识/历史/示例到提示词：

| 上下文类型 | 注入方式 | 适用 |
|---|---|---|
| 静态上下文 | 固定的领域知识/规则 | 简单场景、规则稳定 |
| 动态检索上下文 | RAG从知识库检索Top-K | 私有知识/企业文档 [详见 D-19.08] |
| 历史上下文 | 会话历史/摘要/项目记忆 | 多轮对话/Agent任务 [详见 D-19.07] |
| 动态Few-shot | 根据输入动态选相似示例 | 任务多样化、固定示例不够 |
| 工具调用结果 | Function Call返回值 | Agent调用外部API/DB |

**上下文预算管理**：[来源:Context工程实践 | 📚中]
- Token预算：总上下文=系统提示+用户输入+上下文注入+输出预留，硬约束模型上下文窗口
- 优先级：系统提示>用户输入>动态上下文>few-shot>历史
- 摘要压缩：长历史压缩为摘要+最近K轮原文

### 1.3 输出格式约束（Format）

| 约束方式 | 实现 | 适用 |
|---|---|---|
| JSON Mode | OpenAI response_format=json_object | 结构化数据下游处理 |
| Structured Output | OpenAI/Anthropic JSON Schema | 严格字段+类型约束 |
| 表格Markdown | 提示词中给表格示例 | 简单结构化展示 |
| XML标签 | Claude擅长XML结构化输出 | 复杂层级输出 |
| Pydantic模型 | DSPy/LangChain定义Pydantic | Python工程化 |

**红线**：[来源:工程化实践 | 📚中]
- 不强制格式=下游解析失败+流程断裂
- JSON Mode需提示词中明确"输出JSON"
- Structured Output需提供JSON Schema
- 兜底：模型偶发不遵守格式需重试+正则修复

### 1.4 Few-shot示例选择

| 方式 | 实现 | 适用 |
|---|---|---|
| Zero-shot | 不给示例，直接任务 | 简单任务、模型能力够 |
| 固定Few-shot | 给2-5个固定高质量示例 | 任务模式稳定 |
| 动态Few-shot | 根据输入语义检索相似示例 → 用示例选择器 | 任务多样化 |
| 思维链Few-shot | 给带推理过程的示例 | 复杂推理任务 |

**示例选择最佳实践**：[来源:示例选择实践 | 📚中]
- 示例质量>数量：3个高质量好过10个低质量
- 多样性：示例应覆盖不同子场景而非同质化
- 与输入相似度：动态Few-shot优先选语义相近示例
- 反例也有效：给"不要这样输出"的反例

## 二、L2 推理增强层

推理增强层通过引导模型多步推理+自校验来突破"直接给答案"的能力天花板。

### 2.1 Chain-of-Thought (CoT 思维链)

**核心**：让模型"think step by step"显式推理再给答案。Google 2022论文证明CoT让GPT-4数学推理能力突破性提升。

**触发方式**：[来源:CoT原论文 | 🔍高]
- Zero-shot CoT：直接加"Let's think step by step"
- Few-shot CoT：给带推理过程的示例
- Auto-CoT：自动生成推理链示例

**适用**：数学/逻辑/多步推理类任务
**不适用**：简单事实查询、创意生成

### 2.2 Tree-of-Thoughts (ToT 思维树)

**核心**：让模型在每步推理后生成多个候选思路→评估→选最优继续，类似搜索树。 [来源:ToT原论文(Princeton) | 🔍高]

**结构**：
```
问题 → 思路1/思路2/思路3 → 评估（哪个更优）→ 选最优继续
                            → 思路1.1/1.2/1.3 → 评估 → ...
```

**适用**：复杂决策/规划/创意发散（24点/创意写作/方案设计）
**成本**：Token消耗高、延迟长

### 2.3 Self-Consistency (自洽性)

**核心**：多次采样同一推理路径→取多数投票结果，提升答案稳定性。 [来源:Self-Consistency原论文 | 🔍高]

**适用**：答案离散+推理路径多样（数学题/选择题）
**成本**：需多次调用，成本×N

### 2.4 Self-Refine / Self-Critique (自校验反思)

**核心**：模型生成答案后→自我批判→基于批判重写，迭代提升。

**流程**：
```
生成初版 → 自我批判(找问题) → 基于批判重写 → 再批判 → ... → 满意输出
```

**适用**：写作/代码/方案类需多次打磨的任务
**与Reflexion区别**：Self-Refine是单Agent自我批判；Reflexion是Agent失败后基于外部反馈反思

### 2.5 推理增强的组合使用

| 任务类型 | 推荐组合 | 理由 |
|---|---|---|
| 数学/逻辑推理 | CoT + Self-Consistency | 推理路径多样+取多数稳定 |
| 复杂决策 | ToT | 多思路搜索最优 |
| 写作/方案 | Self-Refine | 多次打磨提升质量 |
| 简单事实 | Zero-shot | 不需要推理增强 |
| 创意生成 | ToT + Self-Refine | 发散+收敛 |
