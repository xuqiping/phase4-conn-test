# 3.3 自动化测试与度量体系

## 自动化测试ROI

### ROI计算框架

```
自动化ROI = (手动测试成本 × 重复次数 - 自动化开发成本 - 维护成本) / 自动化总投入

其中：
- 手动测试成本 = 单次手动执行耗时 × 人工时薪
- 重复次数 = 预计运行次数（跨迭代/回归/环境）
- 自动化开发成本 = 编写+调试脚本耗时 × 工程师时薪
- 维护成本 = 每次脚本更新耗时 × 更新次数 × 工程师时薪
```

**盈亏平衡点**：一般自动化脚本运行**3-5次**后开始产生正ROI。[来源:📚训练知识 | ⚠️待核实- 具体次数因场景而异]

### 何时自动化 vs 手动

| 维度 | ✅值得自动化 | ❌不值得自动化 |
|---|---|---|
| 执行频率 | 每次回归/每次部署必跑 | 只跑一次的一次性验证 |
| 稳定性 | 业务逻辑稳定、UI不频繁变更 | UI/交互频繁改版、需求不稳定 |
| 复杂度 | 数据驱动、参数组合多 | 需要主观判断（视觉/体验） |
| 价值 | 核心路径、支付/安全等高风险 | 探索性测试、UX评估 |
| 环境 | 可在CI/CD中自动触发 | 需要特定硬件/人工干预 |

[来源:Martin Fowler "TestPyramid" | 📚高 | 2012]

### 自动化三不原则

1. **不为覆盖率而自动化**：100%自动化率≠100%质量保障，探索性测试不可替代
2. **不自动化不稳定用例**：Flaky Test比没有自动化更糟——它消蚀团队对测试的信任
3. **不一次性全部自动化**：按风险优先级逐步推进，优先自动化核心路径回归

[来源:Google Testing Blog "Flaky Tests" | 📚高 | 2020]

## 自动化层级与工具谱系

### 按测试类型分的自动化优先级

```
优先级1（必自动化）：冒烟测试、核心路径回归、API集成测试
优先级2（应自动化）：数据驱动测试、参数组合测试、性能基准测试
优先级3（按需自动化）：E2E UI测试、跨浏览器兼容测试
不推荐自动化：探索性测试、可用性测试、视觉审美评估
```

### 常见工具矩阵

| 层级 | 工具 | 适用场景 | PM关注点 |
|---|---|---|---|
| 单元测试 | Jest/pytest/JUnit | 开发者自测 | 覆盖率是否达标 |
| API测试 | Postman/Newman/RestAssured | 接口契约验证 | 接口变更是否触发回归 |
| UI自动化 | Cypress/Playwright/Selenium | 用户路径验证 | 脚本维护成本vs价值 |
| 性能测试 | JMeter/k6/Gatling | 负载与压力 | TPS/P99是否达标 |
| 安全扫描 | Snyk/OWASP ZAP/SonarQube | 漏洞检测 | 高危漏洞是否阻塞发布 |

## 覆盖率度量体系

### 三层覆盖率

| 覆盖率类型 | 定义 | 度量方法 | PM关注点 |
|---|---|---|---|
| 代码覆盖率 | 代码被测试执行到的比例 | 行覆盖/分支覆盖/路径覆盖 | 分支覆盖率≥80%为常见目标 |
| 需求覆盖率 | 需求被测试用例覆盖的比例 | 需求→测试用例追踪矩阵 | 每个P0/P1需求至少1条验证用例 |
| 场景覆盖率 | 用户关键场景被E2E覆盖的比例 | 用户旅程→E2E用例映射 | 核心业务路径100%覆盖 |

### 覆盖率陷阱

| 陷阱 | 表现 | 正解 |
|---|---|---|
| 高代码覆盖率≠高质量 | 80%行覆盖但只测了happy path | 关注**分支覆盖率**而非行覆盖率 |
| 需求100%覆盖≠质量够 | 每个需求只1条用例，边界未测 | 需求覆盖率+关键边界专项补充 |
| 覆盖率数字驱动 | 为达标而写无效断言 | 覆盖率是"必要非充分"指标，不独立使用 |

[来源:📚训练知识] [来源:Martin Fowler "TestCoverage" | 📚高 | 2012]

## 质量看板设计

### PM质量看板四域

```
┌─────────────────────────────────────────────────┐
│              质量看板（Quality Dashboard）         │
├──────────────┬──────────────┬────────────────────┤
│  发布健康域   │  缺陷趋势域   │   自动化效率域      │
│ ·质量门状态   │ ·新增vs关闭   │ ·自动化率          │
│ ·逃逸率      │ ·Open P0/P1  │ ·Flaky Rate       │
│ ·MTBF       │ ·按模块分布   │ ·脚本维护成本       │
├──────────────┴──────────────┴────────────────────┤
│              覆盖率域                              │
│ ·代码覆盖率趋势 ·需求覆盖率 ·核心路径E2E覆盖       │
└─────────────────────────────────────────────────┘
```

### 看板设计三原则

1. **可行动**：每块数据都要能驱动一个决策（如"逃逸率>10%时启动漏测复盘"）
2. **可归因**：数据要能下钻到具体模块/团队/变更（如"缺陷增量来自支付模块的2次重构"）
3. **可趋势**：展示时间序列而非快照（如"近6个Sprint逃逸率走势"而非"当前逃逸率=6%"）

[来源:📚训练知识] [来源:Google DORA Metrics | 📚高 | 2022]

### 度量治理规则

- **不唯指标论**：指标是辅助决策的信号灯，不是替代判断的自动挡
- **不指标博弈**：如果团队开始为达标而"优化"指标本身（如把P1降为P2来降低P1数量），说明指标设计有问题
- **定期校准**：每季度审视指标是否仍然反映真实质量，淘汰失灵指标
