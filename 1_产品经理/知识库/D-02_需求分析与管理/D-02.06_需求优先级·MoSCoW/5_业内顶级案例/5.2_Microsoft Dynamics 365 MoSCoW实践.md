# 5.2 Microsoft Dynamics 365 MoSCoW实践

## 案例

Microsoft Dynamics 365作为企业级SaaS+本地部署混合产品，功能需求来自全球客户、合作伙伴和内部战略。面对数百个需求竞争有限的开发资源，Dynamics 365团队使用MoSCoW框架进行版本规划。

## Dynamics 365的MoSCoW适配

| DSDM标准 | Dynamics 365适配 | 原因 |
|---|---|---|
| 四桶分类 | 四桶+**每桶内部RICE排序** | 大量需求需桶内精排 |
| Must≤60% | Must≤50%（更严格） | 企业级产品Must延迟=客户业务中断 |
| Won't声明 | Won't声明+**客户沟通邮件** | 企业客户需要正式告知 |
| 时间盒 | 半年版本周期+月度更新 | 企业级发布节奏 |

## 关键实践

1. **Must来自合同**：Dynamics 365的Must不靠PM"感觉"，而是来自合同承诺、合规要求和已宣布的路线图
2. **Should来自大客户VP**：Should需求由VP级客户成功经理提报，而非所有客户
3. **Could来自产品创新**：Could桶是产品团队的"创新实验场"——测试新想法
4. **Won't需正式沟通**：Won't需求通过客户沟通邮件正式告知，避免"以为在做"的误解

## 对PM的启示

> Dynamics 365案例证明：**MoSCoW在企业级产品中的核心价值不是PM的内部工具，而是跨组织对齐的沟通语言**——客户、销售、研发都用同一套四桶逻辑对话。[来源:Microsoft公开产品管理实践 | 📚中]
