# Implementation Plan for 反馈中心

> Phase 2 产出。Phase 3 逐步勾选执行。只含伪代码，不含真代码。
> 来源规格：[../specs/反馈中心设计.md](../specs/反馈中心设计.md)
> 拍板：三台合并为一个「反馈与帮助」模块三 tab。

## 背景与目标

- 19x#1 建议台：用户提需求（记录用户名快照+可附截图），admin 审核回复，结果通知用户。
- 19x#2 提问台：用户提问，admin markdown 回答，可公开为 FAQ（作者脱敏）。
- 19x#3 说明台：admin 维护 markdown 帮助文章，分类+发布开关，全员可读。

## 技术实现坑点预判与规避措施

| 技术点/功能块 | 可能的坑 | 规避措施 | 验证方式 |
|---|---|---|---|
| **附件属主串号** | 用户提交时挂别人的 fileId → 越权读他人文件 | 提交时逐 fileId 校验属主=提交人（FileStorageService 读侧门控已是 owner-or-admin，提交侧再加属主校验防挂号）；附件只许挂建议（问答不含附件） | 单测：挂他人 fileId 400 |
| **FAQ 脱敏遗漏** | 公开问答把提问人用户名透给全员 | FAQ VO 无 username 字段（不是置空是**字段不存在**，防模板误取）；admin VO 才有；SQL 层 FAQ 查询不 SELECT username | 单测：FAQ 响应体 grep 无 username |
| **slug 唯一 vs 软删** | 文章软删后 slug 仍占坑，重建同 slug 409 | 软删时 slug 改写 `原slug__del_{id}`（service 层同步做，与删除同事务）；或拍板文章**硬删**（内容在审计/回收站无需求）——取硬删+二次确认，简单且无占坑 | 单测：删后重建同 slug 成功 |
| 审核并发双击 | 两 admin 同时审同一条 → 重复通知/状态错乱 | 条件 UPDATE 抢 PENDING（FeedbackReviewService 先例），0 行=409「已审核」 | 单测并发抢态 |
| 回答后修改答案 | ANSWERED 再调 answer → 重复通知骚扰用户 | answer 端点允许 OPEN→ANSWERED 与 ANSWERED→ANSWERED（改答案），**仅首次落 ANSWERED 发通知**；改答案不发 | 单测：改答案无新通知 |
| markdown XSS | 用户/admin 输入带脚本 | 渲染统一走 `renderMarkdown`（html:false 既有 XSS 免疫）；存储原文不回显 HTML | 单测：`<script>` 输入渲染为文本 |
| **通知轮询压力** | 每 3s ×在线用户打 count 接口 | count 走 `(user_id) WHERE read_at IS NULL` 部分索引；响应极小；与既有记忆铃铛同模式已验证 | 性能验证 §性能 |
| 限流误伤正常用户 | 5 次/分对正常提建议够用，但报错文案要人话 | @RateLimit 触发返 429+「提交太频繁，请稍后再试」；前端 toast | 单测第 6 次 429 |
| 附件清理 | 建议删除（软删）后附件文件孤儿 | 拍板：附件不做级联删除（文件配额本就约束，孤儿成本可忽略）；**不做**定时清理（运维考量表落字） | — |
| 菜单权限三处漏注册 | modules.ts/Sidebar/router 任漏一处 → 菜单不见或路由 403 | Step 7 单列注册 checklist 逐项勾；accessGuard 纯函数单测覆盖新 module key | 单测+手测 |

## 安全检查清单

- [ ] **鉴权/授权**：用户侧登录即可但本人数据强过滤（service 层 userId）；admin 侧 `feedback:manage`/`help:manage` 双码分离（审核与内容管理不同人可分管）
- [ ] **输入校验**：title≤120、content≤4000、answer≤8000、附件≤3 个；slug 正则 `^[a-z0-9-]+$`；DTO @Valid + DB 长度双卡
- [ ] **限流**：建议/提问提交各 5 次/分/用户
- [ ] **XSS**：markdown html:false；通知 message 纯文本
- [ ] **越权**：附件属主校验；FAQ 无 username；我的文章列表 service 层强制 self
- [ ] **审计**：审核/回答/关闭/文章发布下架 全 @AuditLog
- [ ] **并发**：审核抢态条件 UPDATE；通知幂等（同一审核只发一次——抢态天然保证）
- [x] **加密/CORS/依赖**：无新面，无新增包（markdown-it 既有）

## 性能考虑与验证计划

- [ ] 建议/提问/FAQ 列表分页走 (status,created_at)/(is_public,answered_at) 索引 p95<300ms
- [ ] FAQ 检索 LIKE 'kw%' 前缀（标题+内容），百级数据量无压力；量上万再评估 pg_trgm
- [ ] 通知 count 部分索引 p95<100ms
- [ ] 文章正文 slug 唯一索引直达 p95<100ms
- [ ] Phase 4：反馈中心三 tab 首屏 <1s

## 功能联动点清单

| 触发动作 | 联动对象 | 预期变化 | 边界（反向/取消/批量） |
|---|---|---|---|
| 提交建议 | 我的建议列表 | 新增 PENDING 行 | 提交中按钮防重；附件上传失败整体回滚不入库（先传文件后提交表单，fileId 引用有效即可） |
| admin 审核建议 | 建议状态 + 通知 + 用户铃铛 | 状态翻转+reply 落库+通知+铃铛 count+1 | 反向=审核不可撤销（拍板：无「撤销审核」，改判只能再发一条说明？**改判支持**：ADOPTED↔REJECTED 可再 review，重发通知；CLOSED 终态不可改）；并发双击 409 |
| admin 回答提问 | 提问状态 + 通知 | OPEN→ANSWERED+answer 落库+通知 | 改答案不重发通知；isPublic 勾选→FAQ 立即可见；**取消公开**→FAQ 消失但我的提问仍可见答案 |
| admin 发布/下架文章 | 用户说明台目录 | 出现/消失 | 下架后直链 404；无草稿列表给用户 |
| 用户读通知 | 铃铛 count | count-1 | 点击通知跳对应 tab 并标记已读；全部已读有入口 |
| 删除文章（硬删） | slug 占用 | 释放 slug | 二次确认；被删文章用户端立即 404 |
| 建议附件 | 文件配额 | 占用提交人配额 | 建议删除不释放配额（拍板不做级联删）；超配额上传时既有 413 文案 |

## 运维考量清单

| 类别 | 决策 | 说明 |
|---|---|---|
| 可观测性 | **做** | 提交/审核/回答/发布 INFO 日志带 id+operator；限流触发 WARN |
| 配置开关 | **做（轻）** | modules.ts `feedback` 模块开关（既有机制），出问题整体隐藏入口不摘代码 |
| 可回滚 | **做** | V141 全新表——回滚 DROP TABLE 块注释备录（数据丢需确认）；V142 权限码 DELETE 回滚块；代码回滚即功能消失无残留 |
| 限流/熔断/降级 | **做（限流）** | 提交限流本期；无第三方依赖无需熔断 |
| 运维入口 | **后续再说** | 批量关闭水帖/导出建议：本期 SQL 手工；量上来再做 admin 批量操作 |
| 告警阈值 | **不做** | 无资源指标；审核积压暂靠 admin 页面自觉（量大再加未处理计数徽标——Sidebar 轮询先例已有，列为后续） |
| 容量/性能预案 | **做（评估）** | 三表量级千级/年，无分区需求；通知表只增不删——读已超 90 天的可定期归档，**后续再说**（本期量忽略） |

## 术语表

| 术语 | 大白话 | 例子 |
|---|---|---|
| **抢态** | 带状态前提的更新，改 0 行=被别人抢先 | 两 admin 同审一条只有一个成功 |
| **用户名快照** | 提交时抄存用户名，改名不影响历史 | 老建议仍显示当时的名字 |
| **脱敏** | 公开视图藏起敏感字段 | FAQ 看不到提问人是谁 |
| **slug** | 文章英文短链名 | `/help/articles/how-to-charge` |
| **部分索引** | 只给符合条件的行建索引 | 未读通知才进索引，count 飞快 |
| **硬删** | 真把行删掉（相对软删标 deleted） | 文章删除释放 slug |
