# 3.1 定义边界与测试策略

## 定义

测试质量（Testing & Quality Assurance）是PM在研发协同中保障交付质量的**底线能力**——理解测试策略设计、质量门设定、缺陷管理与自动化测试的价值边界，确保"上线"不等于"上线就出问题"。PM不需要写测试用例，但必须**能定义"什么是够好的质量"、能评估测试覆盖是否充分、能在进度与质量间做有依据的取舍**。[来源:ISTQB Foundation Level Syllabus v4.0 | 📚高 | 2023]

> 核心判断：测试的目的不是"证明没有bug"，而是"在可用成本内尽可能发现并消除高风险缺陷，为发布决策提供信息"。[来源:Myers《软件测试的艺术》| 📚高 | 2011]

## 核心术语

| 术语 | 英文 | 定义 | PM关注点 |
|---|---|---|---|
| 单元测试 | Unit Test | 对最小可测单元（函数/类）的隔离测试 | 开发自测覆盖，不改需求不追加 |
| 集成测试 | Integration Test | 模块间接口与交互的测试 | 关注模块边界的数据流与异常 |
| 端到端测试 | E2E Test | 从用户视角模拟完整业务流的测试 | 验证关键用户路径可达 |
| 冒烟测试 | Smoke Test | 上线前对核心功能的快速验证 | 每次部署必跑，过不了冒烟不上线 |
| 回归测试 | Regression Test | 变更后确认原有功能未被破坏的测试 | 自动化回归是持续交付的基石 |
| 性能测试 | Performance Test | 验证系统在负载下的响应与稳定性 | 关注TPS/P99/资源水位是否达标 |
| 安全测试 | Security Test | 发现系统安全漏洞的测试 | 合规/支付/隐私场景必须覆盖 |

[来源:ISTQB Glossary v4.0 | 📚高 | 2023] [来源:📚训练知识]

## 测试金字塔与测试奖杯

### 经典测试金字塔（Mike Cohn, 2009）

```
        /  E2E  \          ← 少量（慢、贵、脆弱）
       / 集成测试  \         ← 适量
      /   单元测试    \       ← 大量（快、便宜、稳定）
```

- 塔底单元测试（70%）、塔中集成测试（20%）、塔顶E2E测试（10%）
- 原则：**越底层越多、越快越便宜、越稳定越值得自动化**
- 适用：后端逻辑密集型产品、微服务架构

[来源:Cohn《Succeeding with Agile》| 📚高 | 2009]

### 测试奖杯模型（Kent C. Dodds, 2018）

```
         ___
        / E2E \           ← 极少（1-5%）
       /集成测试  \          ← 最多（~70%）
      /   单元测试   \        ← 适量（~20%）
     /    静态分析     \       ← 基础层（ESLint/TypeScript）
```

- 核心差异：**集成测试成为最大层**，因为现代前端/全栈应用中，组件间集成是bug高发区
- 静态分析作为最底层，代码未运行即可发现类型错误和规范违反
- 适用：前端/全栈应用、SPA、React/Vue生态

[来源:Kent C. Dodds Blog "The Testing Trophy" | 📚高 | 2018]

### PM选型指南

| 产品类型 | 推荐模型 | 理由 |
|---|---|---|
| 后端服务/API | 金字塔 | 逻辑密集，单元测试ROI最高 |
| 前端应用/SPA | 奖杯 | UI状态+API集成是缺陷高发区 |
| 移动端 | 金字塔变体 | UI自动化极脆弱，倾斜到逻辑层 |
| 数据/AI产品 | 金字塔+专项 | 基础金字塔+数据质量测试+模型评估 |

## 测试策略设计四要素

PM参与测试策略讨论时，必须确认四个要素被覆盖：

1. **测什么**：基于风险优先级选择测试范围——核心路径必测，边缘场景按风险选测
2. **怎么测**：手动/自动化/探索性测试的比例分配
3. **何时测**：Shift-Left（越早越好）vs 按阶段（单元→集成→E2E→UAT）
4. **测到什么程度**：覆盖率目标（代码/分支/需求覆盖率）+ 质量门阈值

[来源:ISTQB Foundation Level Syllabus v4.0 | 📚高 | 2023]

## 使用频率与场景

| 场景 | PM核心动作 | 频率 |
|---|---|---|
| 需求评审 | 明确验收标准，定义"质量够好"的阈值 | 每个需求 |
| 迭代规划 | 与QA约定测试范围与策略 | 每个Sprint |
| 上线决策 | 审视质量门结果，做Go/No-Go判断 | 每次发布 |
| 缺陷涌现 | 分析缺陷趋势，判断是否阻塞发布 | 按需（高频） |
| 复盘 | 漏测分析，改进测试策略 | 每次线上事故后 |
