# 3.2 用量计费与打包组合策略

## 一、用量计费策略

### 1.1 为什么用量计费重新崛起

传统SaaS按席位订阅假设"边际成本趋零"——多一个用户不多花钱。AI打破了这一假设：一个重度用户的AI推理成本可能是一个轻度用户的100倍。按席位定价在重度用户上亏钱，在轻度用户上收太多——用量计费让收费与成本对齐。

### 1.2 用量计量点选型

计量点是用量计费的核心——选错计量点会导致"客户看不懂在收什么费"或"收不到核心价值"。

| 计量点 | 收什么 | 适合 | 案例 | 优势 | 风险 |
|---|---|---|---|---|---|
| **Token** | AI推理消耗的token量 | AI API/平台 | OpenAI/Anthropic API | 精确对齐成本 | 客户看不懂"1k token是什么" |
| **API调用次数** | 每次API请求计一次 | 开发者工具/PaaS | Twilio/Stripe API | 简单清晰 | 调用价值差异大(1次调用可能很贵或很便宜) |
| **存储容量** | 按GB/TB存储量计 | 云存储/数据库 | AWS S3/Snowflake | 线性可预测 | 存储成本持续下降趋势 |
| **计算资源时间** | 按计算使用时间计 | 云计算 | AWS EC2/Snowflake | 精确对齐计算成本 | 客户难预估使用时间 |
| **任务数** | 每完成一个任务计 | 自动化/工作流 | Zapier(任务次数) | 业务结果可感知 | 任务复杂度差异大 |
| **成果数** | 每产生一个业务成果计 | AI客服/营销 | Intercom Fin($0.99/resolution) | **直接锚定业务价值** | 成果定义和校验复杂 |

[来源:用量计费选型/OpenView+ProfitWell | 🔍高 | 2026]

### 1.3 计量点选型3原则

1. **客户可感知**——计量单位必须是客户能理解和预测的。"Token"对开发者可感知但对业务人员不可感知；"解决的对话数"对业务人员可感知
2. **与价值正相关**——计量单位增长应与客户获得价值增长正相关。"API调用次数"可能正相关也可能不(一次调用价值很大)；"成果数"强正相关
3. **与成本正相关**——计量单位应尽量对齐成本结构。Token与AI成本强正相关；API调用与服务器成本中等相关

### 1.4 配额与超额计费设计

**标准模式**：基础套餐含X配额 + 超出部分按Y单价追加

| 设计要素 | 说明 | 常见做法 |
|---|---|---|
| **基础配额** | 套餐内包含的用量 | 如"100万Token/月""1万次API调用/月" |
| **超额单价** | 超出配额后的单价 | 阶梯递减(量大优惠)或固定单价 |
| **配额重置周期** | 配额按月/按年重置 | 按月重置(对齐月费)最常见 |
| **配额结转** | 未用完的配额是否结转 | 通常不结转(促使用足) |
| **包量折扣** | 预购大量配额享折扣 | 如预购100万Token比按需便宜20% |

### 1.5 预算可控设计（B端关键）

B端客户年度预算审批制——用量不可预测是用量计费在B端的最大障碍。必须设计"预算可控"机制：

| 机制 | 做法 | 效果 |
|---|---|---|
| **用量封顶(Cap)** | 设月度用量上限，超封顶停止服务或通知升级 | 客户知道"最多花多少" |
| **预算告警** | 用量达到50%/80%/100%时自动通知客户 | 客户及时调整用量或预算 |
| **承诺量折扣(Commit)** | 承诺月消费量，换折扣价 | 客户锁定预算+获折扣；供应商获可预测收入 |
| **熔断机制** | 用量异常飙升时自动暂停(防误操作/恶意调用) | 防止预算黑洞 |
| **混合定价(订阅+用量)** | 基础订阅费含一定配额+超出按用量计 | B端有固定预算底线+灵活性 |

[来源:AWS/Snowflake用量计费设计 | 🔍高 | 2026]

### 1.6 防作弊设计

用量计费可能被刷量攻击或滥用：

| 风险 | 防范 |
|---|---|
| **恶意刷量** | 异常调用频率检测+IP限制+限流 |
| **重复计费刷量** | 幂等性设计(同一请求不重复计费) |
| **成果计费刷量** | 成果质量校验+人工抽检+异常成果不计费 |
| **共享账号规避席位** | 并发会话检测+设备指纹+异常登录告警 |

## 二、打包组合策略

### 2.1 打包的本质

打包(Bundling)是把多个产品/功能组合成一个包装以一个价格出售。核心逻辑是**价值互补**——A产品对客户X值100，B产品对客户X值50；但A+B打包对客户值200(因为互补)。打包价150让客户觉得"比单买划算"同时比单买收入高。

### 2.2 打包vs拆包决策矩阵

| 策略 | 做法 | 优势 | 风险 | 适合 |
|---|---|---|---|---|
| **纯打包** | 只卖全家桶，不单卖 | 简化选择+提升客单价+防御竞品单品切入 | 高价门槛挡住小客户+蚕食单品收入 | 多产品互补的生态型(Microsoft 365) |
| **纯拆包** | 每个产品独立定价 | 客户灵活选+低门槛 | 客单价低+管理成本高+竞品可逐个击破 | 产品间弱关联 |
| **打包+拆包并存** | 既卖全家桶又可单买 | 覆盖全分层+全家桶有折扣优势 | 定价复杂度高+可能蚕食 | **最常见推荐** |

### 2.3 打包定价公式

```
打包价 = Σ单品价格 × 打包折扣率

常见打包折扣：
- 双品打包：8折(省20%)
- 三品打包：7折(省30%)
- 全家桶：6折(省40%)

原则：打包折扣让客户"省到感知到"但仍比单买总和高
```

### 2.4 平台包+增购模块策略

SaaS平台型产品常用"基础平台包+模块增购"策略：

| 层级 | 内容 | 定价 |
|---|---|---|
| **平台基础包** | 核心平台功能(如CRM核心) | 按席位订阅($25-$500/人/月) |
| **增购模块** | 高级功能模块(如营销自动化/AI分析) | 独立加购(按席位加价或按用量) |
| **行业包** | 行业定制功能(如金融合规/医疗EMR) | 按行业包定价(溢价) |
| **专业服务** | 实施/培训/咨询 | 按项目/天/合同定价 |

### 2.5 蚕食效应分析

打包可能蚕食单品收入——客户从单买A(100/月)改为买A+B打包(150/月)，虽然客单价升了50但B可能本来能单独卖80。

| 蚕食类型 | 表现 | 应对 |
|---|---|---|
| **高价值品被打包稀释** | B产品单独值80但打包后被算成50 | 设打包折扣不低于7折 |
| **客户只想要一个但被迫买全家桶** | 客户因为高打包价而流失 | 必须保留单买选项 |
| **打包折扣蚕食高端定价** | 高端客户发现打包更划算→从Enterprise降级到打包 | 打包功能不得包含Enterprise独有功能 |

### 2.6 纯打包 vs 自由组合的前沿趋势

2025-2026年出现"产品化自助配置"趋势——客户在价格页上像"搭积木"一样选功能模块，系统自动计算总价：
- **优势**：客户按需付费感知公平+降低销售介入成本+PLG自助转化
- **风险**：选择过多导致决策困难+组合不可控导致技术支持复杂
- **折中方案**：提供3-4个标准化打包 + 2-3个可选增购模块（而非完全自由组合）
