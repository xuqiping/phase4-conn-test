## 案例：Amazon 微服务与双披萨团队

### 基本信息

- **案例名称**：Amazon微服务架构使能自治团队——两个披萨团队
- **时间**：2000s-至今
- **主角**：Amazon（Jeff Bezos提出理念，技术团队落地）

### 背景

2000年代初期，Amazon仍是一个单体应用（obidos系统）：数十个团队在同一代码库上协作，每次部署需要跨团队协调，发布周期以月计。随着业务高速增长，单体架构成为瓶颈——一个团队的变更可能影响所有团队。Bezos在2002年发出著名的"API Mandee"内部备忘录：所有团队必须通过API通信，不允许直接访问其他团队的数据存储 [来源:Stevey's Google Blog/Amazon内部回忆录|置信度:📚中|此备忘录真实性有争议但影响被广泛确认]。

### 技术手法与迭代链

**1.0 双披萨团队原则（2000s初期）**

- 核心理念：一个团队的规模不应超过"两个披萨能喂饱的人数"——约6-10人
- 目的：减少沟通成本、加快决策速度、增强团队所有权
- 关键约束：每个团队必须有明确的业务边界和独立的可交付成果
- 团队结构：产品经理+技术负责人+5-8名工程师，团队对所负责的服务端到端负责 [来源:Bezos访谈/Amazon文化描述|置信度:🔍高]

**2.0 微服务拆分与API强制（2002-2006）**

- 将单体应用按业务能力（而非技术层）拆分为独立服务
- API Mandee强制：团队间只能通过服务化API交互，禁止直接数据库访问
- 内部服务收费模型：团队使用其他团队的服务需要"付费"——模拟市场机制倒逼服务质量
- 技术产出：AWS本身是这套内部服务化架构的外部化——EC2/S3最初都是内部服务 [来源:AWS发展史/《Working Backwards》|置信度:🔍高]

**3.0 持续部署与运维自治（2006-2015）**

- 每个双披萨团队有自己的部署流水线，可独立部署
- "You build it, you run it"——与Netflix同类原则，Amazon也是早期推行者
- 内部部署工具Apollo/Spinnaker（后开源给Netflix）支持每日数千次部署 [来源:AWS re:Invent技术分享|置信度:📚中]

**4.0 挑战与调整（2015-2026）**

- 过度拆分问题：数百个服务带来治理复杂度——依赖链难以追踪、跨团队调试困难
- "两个披萨"被重新审视：部分团队因服务碎片化导致"披萨太多、服务太碎"
- Amazon内部推动"服务合并"和平台工程——用内部开发者平台屏蔽基础设施复杂度 [来源:技术社区讨论/The Pragmatic Engineer|置信度:📚中]

### 影响后果

- 双披萨团队成为全球研发组织设计的参考模型，影响了Spotify Squad模型
- 微服务架构从Amazon内部分离为AWS，成为全球最大云平台
- API强制通信原则深刻影响了SOA/微服务设计理念
- "You build it, you run it"与Netflix同类实践共同塑造了DevOps文化

### 教训启示

1. **团队边界决定架构边界**——Conway's Law的主动运用：不是"先搭架构再分团队"，而是"按业务能力分团队，架构自然跟随"
2. **自治≠无协调**——双披萨团队自治的基础是清晰的API契约和内部市场机制，砍掉协调但保留接口
3. **微服务有过度拆分风险**——Amazon自己在规模扩大后遇到"服务碎片化"问题，拆分需要判断粒度
4. **内部服务收费是精妙的市场机制**——模拟外部市场压力，倒逼团队提供高质量API，但需要成熟的计量和计费基础设施
5. **产品经理在双披萨团队中角色关键**——PM是团队对外的唯一接口，需要同时理解业务和技术边界
