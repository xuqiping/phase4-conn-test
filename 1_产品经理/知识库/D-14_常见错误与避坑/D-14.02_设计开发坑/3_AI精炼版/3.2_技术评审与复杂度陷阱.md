## 技术评审坑

### 1. PM不参加技术评审 [A.04][I.01]

这是PM最大的技术认知盲区根源——不参加技术评审=主动放弃对方案可行性的理解权。[来源:📚训练知识 | 置信度:🔍高]

| 不参评的后果 | 链式影响 |
|---|---|
| 不了解技术方案限制 | PM承诺的功能实际上做不到/做不好 |
| 不掌握技术债现状 | 新需求可能踩老坑，但PM不知道老坑在哪 |
| 丧失技术判断力 | 被开发的"做不到"或"要3周"牵着走，无法判断合理性 |
| 需求-技术脱节 | PRD写的方案技术上不是最优解，开发自行决定后与PM预期不符 |

> PM的职业竞争力之一(I.01)：能在技术评审中提出有效问题——不是写代码，而是判断技术方案的"是否合理/是否有遗漏/是否满足用户场景"。这不是技术能力，是产品判断力。[来源:Marty Cagan《Inspired》| 置信度:🔍高]

**PM参加技术评审的最低参与清单**：
1. 确认技术方案是否覆盖了所有用户体验场景
2. 确认性能指标（响应时间/并发量）是否满足用户预期
3. 确认技术债影响——此方案是否会增加未来迭代的成本
4. 确认降级方案——上线出问题时如何最快恢复

### 2. 不评估技术债 [D.01][D.02]

技术债是代码层面的"隐形成本"——PM看不见，但它是项目延期的头号杀手。[来源:Martin Fowler Technical Debt | 置信度:🔍高]

| 技术债类型 | PM应关注的信号 | 不处理的后果 |
|---|---|---|
| 代码债 | "这个地方先这么写，以后再重构" | 每次碰这个模块都是灾难，修改成本指数增长 |
| 架构债 | "单体先上，后面再拆微服务" | 任何改动都有全站级联风险 |
| 数据债 | "字段先这么存，后面再改" | 数据迁移成本随数据量指数增长 |
| 测试债 | "先手动测，后面再补自动化" | 回归测试成本线性增长，最终不可承受 |

> 核心框架(D.02)：技术债就像金融债——适度可以，但必须"还本付息"。PM的角色是：1)知道技术债存在 2)评估其对产品迭代的影响 3)在排期中为还债留出资源。[来源:📚训练知识 | 置信度:🔍高]

**PM评估技术债的3问法**：
1. 这个方案的技术债在哪？(让开发明确指出)
2. 不还债的话，哪些后续迭代会受影响？(量化影响)
3. 还债需要多少资源？什么时候还？(排期决策)

### 3. 低估复杂度 [I.03]

| 复杂度类型 | PM低估的表现 | 实际复杂度 |
|---|---|---|
| 状态空间复杂度 | "不就是增删改查吗" | 多角色+多状态+权限组合→状态爆炸 |
| 数据复杂度 | "数据量不大" | 数据关联+历史版本+并发操作→一致性难题 |
| 集成复杂度 | "对接一个API而已" | 第三方API稳定性+网络抖动+超时重试→可靠性挑战 |
| 边界条件复杂度 | "正常流程这样走" | 网络断开/并发冲突/数据为空/权限变更→异常分支数>正常分支 |

> 原则(I.03)：PM评估复杂度的错误方式=只看"正常路径"。正确方式=数状态×数边界条件×数集成点。一个简单的"用户下单"，涉及的状态机可能有20+个状态、50+个转换。[来源:📚训练知识 | 置信度:🔍高]

**复杂度快速估算法**：

```
预估复杂度 = 核心状态数 × 角色数 × 集成点数 × 边界条件系数(1.5-3x)

示例："用户下单"
- 核心状态：待支付/已支付/配送中/已完成/已取消/退款中/已退款 = 7
- 角色：买家/卖家/平台 = 3
- 集成点：支付/库存/物流 = 3
- 边界系数：2x
- 预估复杂度 = 7 × 3 × 3 × 2 = 126
- >50 = 高复杂度，需要技术方案评审+排期缓冲
```

### 4. 忽视性能基线 [E.03][I.10]

性能不是"开发的事"——PM设定的体验标准直接决定性能要求。[来源:Google PageSpeed Insights | 置信度:🔍高]

| PM忽视性能的信号 | 用户影响 | 数据支撑 |
|---|---|---|
| 不设首屏加载时间 | 用户等>3秒就离开 | 53%移动用户在3秒后离开 [来源:Google/SOASTA | 置信度:🔍高] |
| 不设接口响应时间 | 操作卡顿感 | >200ms用户感知延迟，>1s用户会离开 |
| 不设并发量基线 | 高峰期系统崩 | 大促/热点事件流量可能是日常10-100倍 |
| 不设资源体积上限 | 弱网用户白屏 | 页面>3MB在3G网络需10+秒 |

**PM必须定义的性能基线** [I.10]：

| 指标 | 推荐基线 | 否则 |
|---|---|---|
| 首屏可交互时间(FCP) | ≤1.8秒 | 用户流失 |
| 接口P99响应时间 | ≤500ms | 操作卡顿 |
| 核心路径错误率 | ≤0.1% | 用户投诉 |
| 可用性SLA | ≥99.9% (月度) | 不可接受 |

> 关键洞察(I.12)：性能不是压测阶段的事——是设计阶段就要定的基线。PM在设计时如果要求"同时加载100条记录"，就等于定义了性能需求。如果到了压测才发现做不到，返工成本是设计阶段的10倍。[来源:📚训练知识 | 置信度:🔍高]

### 5. 避险技法 [I.07]

| 技法 | 时机 | PM行动 |
|---|---|---|
| 复杂度预评估 | 需求评审时 | 用"状态×角色×集成×边界"公式快速估算 |
| 技术债排期 | 每个迭代 | 至少留10%迭代容量给技术债 |
| 性能基线前置 | PRD中明确 | 写入PRD的"非功能性需求"章节 |
| 参评最低清单 | 每次技术评审 | 场景覆盖/性能/技术债/降级4问 |
| 灰石标记 | 技术评审后 | 标记高风险技术点→进入上线前重点验证 |
