## 节点一：需求调研

| 维度 | 内容 |
|---|---|
| **输入** | 业务方/用户反馈/数据洞察/竞品变化/战略方向 |
| **输出** | 需求池条目（含来源/场景/预期价值）、用户访谈记录、数据洞察报告 |
| **验收标准** | ①需求有明确来源和场景描述 ②区分"用户说的"和"用户要的" ③标注优先级初判 |
| **负责人** | PM |
| **常见坑** | ①把"老板说的"当需求，不加分析 ②只听不说——缺失反问和深挖 ③需求描述只有"做什么"没有"为什么" |

**关键机制**：需求调研的核心不是"收集需求"，而是"发现需求背后的真实问题"。用户说"我要一个导出功能"，真实需求可能是"我需要每周给老板汇报数据"——前者是方案，后者是问题。

## 节点二：分析定义

| 维度 | 内容 |
|---|---|
| **输入** | 需求池条目、业务上下文、技术约束 |
| **输出** | PRD/MRD（含功能范围/用户故事/验收标准/优先级/非功能需求） |
| **验收标准** | ①功能范围明确（做什么+不做什么） ②用户故事可测试 ③边界条件/异常流已覆盖 ④技术方案评审通过 |
| **负责人** | PM |
| **常见坑** | ①PRD只写"正常流"不写异常流 ②功能边界不清导致开发理解歧义 ③非功能需求（性能/安全/兼容）遗漏 |

**关键机制**：PRD不是"功能说明书"，而是"问题→解决方案的论证"——每个功能点都要回答"为什么这样做"而非只写"做这个"。

## 节点三：设计评审

| 维度 | 内容 |
|---|---|
| **输入** | PRD、交互线框图/高保真原型、技术方案初稿 |
| **输出** | 评审通过的交互设计稿、技术方案书、修改清单（评审意见闭环） |
| **验收标准** | ①设计方案覆盖PRD所有功能点 ②技术方案可行且不遗漏边界 ③评审意见全部闭环 |
| **负责人** | PM+设计+技术Lead共担 |
| **常见坑** | ①评审会变成"拍脑袋会"——不提前看材料 ②评审不闭环——提了意见不改不追 ③设计和技术脱节——各做各的 |

**关键机制**：设计评审是投资回报率最高的质量门——修改设计稿的成本远低于修改代码的成本。此节点多花1天，下游节省10天。

## 节点四：研发排期

| 维度 | 内容 |
|---|---|
| **输入** | 评审通过的设计稿+技术方案、需求优先级、团队容量 |
| **输出** | Sprint计划/里程碑排期、任务拆分(WBS)、风险清单 |
| **验收标准** | ①每个任务有明确负责人和工时估算 ②依赖关系已标注 ③预留buffer(通常15-20%) |
| **负责人** | PM+技术Lead |
| **常见坑** | ①排期不含测试/部署时间 ②忽略依赖关系导致关键路径阻塞 ③排期=承诺——不留buffer |

**关键机制**：排期不是"承诺日期"，而是"基于当前信息的最佳预估"。敏捷思维下，排期用于对齐预期而非绑定死线。

## 节点五：测试验收

| 维度 | 内容 |
|---|---|
| **输入** | 开发完成的可测试版本、Test Case、验收标准（来自PRD） |
| **输出** | 测试报告、Bug清单（分级）、PM验收结果 |
| **验收标准** | ①P0/P1 Bug=0 ②P2 Bug有修复计划 ③核心流程Smoke Test通过 ④PM按PRD逐项验收 |
| **负责人** | QA+PM |
| **常见坑** | ①测试不覆盖边界/异常流 ②PM不验收直接上线 ③Bug修复引入新Bug(回归不足) |

**关键机制**：PM验收≠随便看看——应按PRD逐条对照，形成结构化验收记录（通过/不通过+原因）。

## 节点六：上线发布

| 维度 | 内容 |
|---|---|
| **输入** | PM验收通过的版本、发布清单、灰度/全量策略、回滚方案 |
| **输出** | 上线通知、灰度数据报告、发布后验证结果 |
| **验收标准** | ①灰度期间无P0事故 ②核心指标无明显退化 ③回滚方案已验证 ④运营/客服已同步 |
| **负责人** | PM+运维/DevOps |
| **常见坑** | ①上线即走——不监控数据 ②不通知运营/客服 ③无灰度直接全量 ④没有回滚方案 |

**关键机制**：上线是"开始"不是"结束"——上线后的前24小时是最关键的风险窗口。

## 节点七：运营迭代

| 维度 | 内容 |
|---|---|
| **输入** | 上线后数据、用户反馈、运营效果、下一期需求 |
| **输出** | 数据复盘报告、迭代需求池更新、优化方案 |
| **验收标准** | ①核心指标达成情况评估 ②用户反馈收集与归类 ③迭代需求录入需求池 |
| **负责人** | PM+运营 |
| **常见坑** | ①"上线即完成"心态 ②只看PV/UV不看核心目标达成 ③用户反馈无人跟进 |

**关键机制**：运营迭代不是"做完就不管"，而是"上线→验证→优化"闭环的起点。每个功能上线后都应该有1-2周的数据验证期。
