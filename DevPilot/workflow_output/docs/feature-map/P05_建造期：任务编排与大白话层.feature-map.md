## 2. 技术原理大白话

### 2.1 任务编排器为什么顺序执行？
`Scheduler::run_round` 按 `chunk_no` 升序取 `pending` tasks。因为 plan 审批时已经按依赖排好序，后一个 chunk 可能依赖前一个的文件，所以必须串行。

### 2.2 事件流怎么不丢？
runner 里每发生一个阶段/输出就调用回调；commands 把事件先收进 `Vec`，等 `run_task/run_round` 结束后再一次性写库。这样避免在异步 runner 执行期间长期持有 DB 写锁。

### 2.3 checkpoint 为什么能回滚？
每个 task 成功/失败后，runner 会提交一次 git commit。`rollback_to_checkpoint` 做 `git reset --hard <commit>`，并把下游 task 重置为 `pending`。代码回去了，任务状态也回去了，不调用模型所以不扣 Token。

### 2.4 大白话翻译层怎么工作？
`PlainText` 组件读全局 `plainMode` 开关。开启时先查本地术语表，术语用 `TermBubble` 悬停解释；整句走 cheap 模型翻译成中文。失败时回退原文，避免界面卡住。

### 2.5 驾驶舱数据从哪来？
进度仍来自状态机快照；缺陷/覆盖率/消耗来自当前 open round 的 tasks 实时查询。Dashboard 在 `snapshot.phase` 变化时重新拉取。

## 3. 建表注解（本地 SQLite）

| 表 | 用途 | 关键字段 | 关联 |
|---|---|---|---|
| tasks | chunk 任务队列 | round_id, chunk_no, status, instructions, cost_cents | 属于 rounds；运行时被 scheduler 消费 |
| task_events | 任务执行过程日志 | task_id, event_type(narrative/raw/error/checkpoint), message | 属于 tasks；只增不改 |
| checkpoints | 每次 task 完成后的 git 存档点 | task_id, git_commit, summary_plain, title, status | 与 tasks 一一对应；rollback 的目标 |
| rounds | 迭代轮次 | project_id, seq, status | 包含 tasks；open round 是当前工作轮次 |

## 4. 运维与降级

- **LLM 失败**：scheduler/摘要/翻译均回退到原文或标记失败，不阻塞流程。
- **git 失败**：rollback/summarize 命令返回 `GIT` 错误码，前端显示大白话提示。
- **DB 写锁**：所有写经 `Db::write`（Mutex 串行化），事件批量 flush。
- **事件回放**：task_events 落库，断网/刷新后可重新 `list_task_events`。
