# 3.2 基准与Harness工程

## 一、Harness Engineering 范式跃迁

[来源:CSDN《Harness Engineering 深度研究报告 2026》/新浪科技《这才是 AI Coding 绝招 Agent Harness》| 🔍高 | 2026-07]

**核心命题——从 LLM 驱动到 Harness 驱动**：
2026 AI 行业完成从"LLM 驱动"到"Harness 驱动"的智能体架构革命。Salesforce 推出类似概念，开源社区自发形成通用测试集。Agent Harness（自动化评估/基准测试框架）火爆核心原因：解决 AI Agent 从"玩具"走向"工具"的核心瓶颈——**无法量化、无法对齐、无法确信**。

**Harness Engineering 三大支柱**（CSDN Agent Harness 综述 2026-05）：

| 支柱 | 装什么 | 工程实现 |
|---|---|---|
| **Observability 可观测性** | 每次模型调用、工具调用、检索、报错、重试、token 成本、延迟都要能追踪 | Logs/Metrics/Traces 三件套 |
| **Verification 验证与评估** | 结果对不对？失败到底是模型错了、工具错了、上下文错了，还是测试环境错了？ | LLM-as-Judge + 失败模式归因 |
| **Iteration 迭代闭环** | 评测结果回流到框架/策略优化与 RL 训练 | Continuous Eval Pipeline + 字节 JD 闭环 |

**范式跃迁的含义**：
- 旧范式：调 prompt → 看 demo → 上线 → 翻车
- 新范式：建 Harness → 量化指标 → 归因失败 → 闭环优化 → 上线有信心

## 三、基准选型决策树

```
1. Agent 是 AI Coding Agent 吗？
   → 是 → SWE-bench（编码基准标杆）
2. Agent 是工具调用 Agent（客服/工单）吗？
   → 是 → TAU-bench（τ-bench）
3. Agent 是长程跨软件真实任务（用 MCP）吗？
   → 是 → Tool Decathlon（ICLR'26 标杆，sota<30% 说明最真实）
4. Agent 是通用 AI 助手（多模态+多步）吗？
   → 是 → GAIA
5. Agent 是 Web/浏览器 Agent 吗？
   → 是 → WebArena
6. Agent 是多 Agent 系统（MAS）吗？
   → 是 → MAST（Berkeley 14 失败模式 + 87% 失败率基线）
7. 其他场景 → 多基准交叉验证（避免单一基准过拟合）
```

**选型原则**：
- 真实优先：Tool Decathlon 真实世界 MCP 任务 > 合成任务
- 多基准交叉：避免单一基准过拟合，至少 2 个基准交叉验证
- 场景匹配：编码选 SWE-bench、工具选 TAU-bench，不能反过来

## 四、模型 vs 框架归因（Claude Code 100% vs 14%）

[来源:CSDN《这才是 AI Coding 绝招 Agent Harness 到底是什么》/D-24.04 案例 | 🔍高 | 2026-03]

**范式命题——同模型不同框架，结果差 7 倍**：
Claude Code 在 SWE-bench 上跑出 100% 完成率（含 Compaction + AGENTS.md + Ralph Loop + 工具精简 15→2 等 Harness 工程），而裸 tool_calling（同 Claude 模型但无 Harness）只有 14%。**7 倍差距**全部归因于 Harness 工程设计，与模型能力无关。

**模型 vs 框架归因方法**：

| 归因方法 | 怎么做 | 结论判读 |
|---|---|---|
| **同模型换框架** | 固定模型（如 Claude Sonnet 4.5），切换不同 Harness（裸 tool_calling vs Claude Code vs LangGraph ReAct） | 大差距→框架决定胜负，需改 Harness |
| **同框架换模型** | 固定 Harness（如 Claude Code），切换不同模型（Claude vs GPT-4o vs Gemini） | 大差距→模型决定胜负，需升级模型 |
| **二维正交实验** | 多模型 × 多框架矩阵跑分 | 区分"模型×框架"交互效应 |

**为什么框架归因是 2026 核心命题**：
- 88% Agent 项目失败多数是框架不行（不是模型不行）
- 字节 JD 明确要求"将评测结果闭环到框架与策略优化"——框架优化是评测闭环的核心目标
- D-24.04 工作流设计的 Compaction / ReAct / Reflexion / Human-in-the-Loop 即"框架层优化"——评测回答"这一层好不好"

**Claude Code 100% 的 Harness 工程要素**（D-24.04/D-24.06 联动）：
1. 五层 Compaction（L1 工具输出截断 → L2 历史总结 → L3 Dump 文件 → L4 AGENTS.md → L5 Reset+Ralph Loop）——防 Context Rot
2. AGENTS.md 记忆文件——跨会话关键约束持久化
3. Ralph Loop——崩溃后自动续跑重建
4. Vercel 减工具 15→2——工具数控制缓解 Context Rot，准确率 80%→100%
5. 工具调用容错 + 重试——失败恢复率高

## 五、评测集数据污染治理

[来源:腾讯云《告别评测集过拟合》| 🔍高 | 2026-07-11]

**三大危机**：

| 危机 | 表现 | 治理 |
|---|---|---|
| **数据污染（Data Contamination）** | 主流评测集已被纳入训练语料，跑分虚高 | Continuous Eval 自适应评估集+线上流量评 |
| **语义鸿沟（Semantic Gap）** | MMLU 90% 不代表能处理公司报销审批流程 | 业务专属评测集+真实场景任务（Tool Decathlon）|
| **价值对齐缺失** | 跑分高但生产中价值低 | 价值指标（业务 KPI）+ 任务完成率并重 |

**治理方法**：
1. **Continuous Eval 自适应评估**——用线上流量实时评估，避免过拟合静态评测集
2. **业务专属评测集**——基于自家业务数据建评测集（如"报销审批流程"评测集）
3. **OOD 泛化测试**——用分布外数据测，看是否泛化
4. **多基准交叉验证**——至少 2-3 个基准交叉跑分，避免单基准过拟合
5. **防污染机制**——评测集不对外公开，定期轮换，避免被纳入训练语料

## 六、SWE-Bench / TAU-Bench 工程化（闭环到 RL）

[来源:字节跳动 2026-07 大模型 Agent 框架工程师 JD | 🔍高 | 2026-07]

**字节 JD 的评测工程化要求**：
"建设面向 Agent 的评测能力，将 Benchmark（如 SWE-Bench、TAU-Bench 等）工程化为可持续迭代的评估集与指标体系，并将评测结果闭环到框架与策略优化；支撑 RL 训练"

**工程化五步法**：
1. **Benchmark 选取**——按场景选 SWE-Bench（编码）/ TAU-Bench（工具）/ Tool Decathlon（长程）
2. **工程化适配**——把学术 benchmark 适配到自家 Agent 框架（API 适配+任务标准化）
3. **指标体系建立**——基于 12 指标体系 + 4 维框架（D-24.07 § 3.1）
4. **可持续迭代评估集**——评测集随 Agent 进化持续轮换+扩容+防污染
5. **闭环到 RL**——评测结果 → 框架/策略优化 → RL 强化学习训练 → 模型迭代 → 再评

**闭环到 RL 的具体路径**：
- 评测集 → 生成 RL 训练数据（成功轨迹作正样本、失败作负样本）
- 评测指标作 RL reward 信号
- 短板指标集中优化（如 Tool Selection 准确率低 → 集中训练工具选择）
- 持续 RL → 评测 → 再 RL 的飞轮
