# 功能测试 Workflow

## Purpose

为软件功能验证提供从需求分析、测试策略制定、用例设计、探索性测试到缺陷管理与根因分析的完整执行路径。覆盖手工测试思维模型、六大用例设计方法、SBTM探索性测试框架、缺陷全生命周期管理及AI辅助测试生成。

## Prerequisites

- 用户已提供需求规格（PRD/用户故事/功能说明）或待测系统可访问
- 用户已明确测试目标（发布前验证/回归测试/竞品对比/算法伦理验证）
- 用户已明确质量要求（行业合规等级/缺陷逃逸率目标/覆盖率门槛）

## Steps

### Step 1: 需求分析与测试策略制定

**Goal**: 理解系统功能需求与风险画像，制定测试策略（范围/方法/资源/优先级），输出测试计划。
**Completion criterion**: 测试计划通过评审，明确测试范围、方法选择、资源分配、风险项和准入/准出标准。

**A. 需求可测试性评审**
- 读取需求文档（PRD/用户故事/接口文档），提取功能点清单
- 对每个功能点评估可测试性：
  - 输入域是否明确？（取值范围/类型/约束）
  - 输出预期是否可验证？（返回值/UI变化/副作用）
  - 状态转换是否清晰？（初始态→触发条件→目标态）
  - 边界条件是否定义？（最大值/最小值/空值/并发量）
  - 异常场景是否覆盖？（网络中断/权限不足/数据冲突）
- 若需求存在模糊点 → 标记为风险项，与产品经理确认后补充澄清

**B. 风险驱动测试策略（RBT）**
- 采用FMEA方法对每个功能模块评估风险优先级数（RPN = 严重度S × 发生度O × 探测度D）
- RPN分级：
  - RPN > 200：必须设计专项测试，100%覆盖
  - RPN 100-200：核心路径覆盖，边界值重点测试
  - RPN < 100：冒烟测试覆盖，监控即可
- 测试优先级：P0阻塞（100%覆盖）→ P1高优（核心路径）→ P2正常（主路径）→ P3低优（冒烟）→ P4延后（监控）
- 参考案例：某支付系统"扣款+退款"链路RPN=240，专项设计幂等性/并发/超时/对账测试

**C. 测试思维模型选择**
- 根据项目特性组合应用六种思维模型：
  - 黑盒思维：面向用户可见功能（输入→输出验证）
  - 白盒思维：面向复杂算法/状态机（代码路径/条件覆盖）
  - 系统思维：面向多模块交互（集成场景/数据流转/时序依赖）
  - 逆向思维：面向安全关键功能（攻击面/异常注入/降级验证）
  - 用户思维：面向UX流程（真实操作路径/误操作容忍/无障碍访问）
  - 风险思维：面向高RPN模块（FMEA驱动/失效模式专项验证）
- 高风险领域（金融/医疗/航空）→ 六维思维模型全部启用，增加算法伦理验证

**D. 测试范围与资源规划**
- 测试范围：功能模块清单（含In-Scope和Out-Scope）
- 测试环境：开发环境/测试环境/预发布环境/生产环境（右移验证）
- 测试数据：真实数据（脱敏）/合成数据/边界值数据集
- 时间估算：按功能点 × 复杂度系数 × 测试方法耗时估算
- 准入标准：开发完成自测通过/单元测试覆盖率≥80%/无P0阻塞缺陷
- 准出标准：所有P0/P1用例通过/P2通过率≥95%/缺陷逃逸率目标达成

**E. AI辅助策略制定（可选）**
- 使用LLM（通义千问/GPT-4）基于PRD生成初步测试策略草案
- RAG检索历史同类项目测试策略作为参考
- 人工审核AI输出：补充业务语境、修正风险评估偏差、确认合规要求

**输出物**: `测试计划_项目名称.md`（含功能清单、RPN评估表、测试策略、资源计划、准入准出标准）。

### Step 2: 测试用例设计

**Goal**: 将需求规格转化为可执行、可度量、可追溯的测试用例集合，覆盖功能路径、边界场景、异常分支和配置组合。
**Completion criterion**: 用例集合通过评审，需求覆盖率≥95%，关键路径覆盖率100%，用例可独立执行并产生明确Pass/Fail结果。

**A. 用例设计技术选择**
- 根据功能特性选择设计方法（可组合使用）：
  - 输入条件多取值明确 → **等价类划分 + 边界值分析**
  - 有明确状态转换 → **状态转换图法**
  - 端到端业务流程 → **场景法（BDD Gherkin）**
  - 配置项多组合爆炸 → **组合测试（Pairwise/ACTS）**
  - 多条件多动作规则 → **判定表法（DMN 1.4）**
  - 经验驱动快速测试 → **错误推测 + 检查清单**
- 技术组合决策树已在测试策略中明确，此处按策略执行

**B. 等价类划分（ABA三步法）**
- Analyze（分析输入域）：识别所有输入参数及其类型/范围/约束
- Bisect（切分等价类）：每个输入划分为有效等价类（合法输入）和无效等价类（非法输入）
- Anchor（选取锚点值）：每个等价类选取1个代表性值，无效类每个取1个
- 原则：一条用例覆盖多个有效类（正向用例），一条用例只覆盖一个无效类（反向用例，便于定位）
- AI辅助：LLM基于接口字段自动识别有效/无效等价类，准确率75-85%，人工审核后确认

**C. 边界值分析（BAR三轮回归法）**
- Boundary（识别边界）：对每个输入域识别最小值/最大值/临界值
- Analyze（分析有效域）：确认边界两侧的有效/无效区间
- Robust（扩展健壮性）：增加min-1、min、max、max+1四值边界，浮点数用BigDecimal处理精度问题
- 案例：年龄输入框边界18-60岁 → 测试值：17（无效）、18（有效）、19（有效）、59（有效）、60（有效）、61（无效）

**D. 判定表法（CARE四步法）**
- Condition（识别条件）：列出所有输入条件（如"用户已登录"/"余额充足"/"商品有库存"）
- Action（识别动作）：列出所有输出动作（如"允许下单"/"提示余额不足"/"提示库存不足"）
- Reduce（合并冗余规则）：相邻规则仅差一个条件且动作相同则合并（M1/M2合并）
- Evaluate（覆盖率评估）：确保MC/DC覆盖（航空/汽车DAL-A强制100%）
- 工具：DMN 1.4标准，使用Camunda/dmn-js执行验证

**E. 状态转换图法（STAR四步法）**
- State（状态识别）：识别系统所有离散状态（如"未登录"/"已登录"/"购物车有商品"/"订单已提交"）
- Transition（转换梳理）：列出所有触发事件和状态转换路径
- Algorithm（覆盖算法选择）：
  - 0-switch：每个状态至少到达一次
  - 1-switch：每对相邻转换至少覆盖一次
  - N-switch：长路径覆盖（关键业务流程）
- Run（执行与回归）：用例执行后，状态机变更时自动识别受影响用例集
- 前沿：TLA+形式化验证（AWS S3/DynamoDB工业级实践），LangGraph AI Agent状态机测试

**F. 场景法（SAGA四步法 + BDD Gherkin）**
- Story（用户故事）：从PRD提取用户目标（如"作为买家，我想下单购买商品"）
- Actor（角色识别）：买家/卖家/管理员/系统
- Goal（目标拆解）：下单 → 选商品 → 填地址 → 支付 → 确认 → 发货
- Action（动作场景化）：
  - 基本流（Happy Path）：正常完成目标的最短路径
  - 替代流（Alternative）：有效但非主路径的分支（如"使用优惠券"）
  - 异常流（Exception）：导致目标失败的路径（如"支付超时"）
- BDD格式：`Given [前置条件] When [触发动作] Then [预期结果]`
- 强制要求：每个Feature至少3个Sad Path Scenario
- 工具：Cucumber/SpecFlow/pytest-bdd/Karate

**G. 组合测试（Pairwise/ACTS）**
- 适用：多配置项组合爆炸（如5浏览器×5 OS×3分辨率×4语言=1200种组合）
- 算法：Pairwise（覆盖所有两两组合）将1200种压缩至42个用例
- 工具：PICT（Microsoft）/ACTS（NIST）/Hypothesis（Python属性测试）
- 案例：某Web应用用Pairwise生成42条用例覆盖100%配对，实测发现3个三元组合才触发的缺陷

**H. 用例评审与维护**
- 评审标准：LIFE四阶段法
  - Lifecycle（全生命周期追溯）：每条用例关联需求ID、设计文档、代码模块
  - Inspection（评审）：团队评审会议，检查冗余/遗漏/模糊/不可执行项
  - Fitness（健康度评估）：用例失效率监控（1年后35-50%，2年后60%+）
  - Evolve（持续演进）：季度清理日删除失效用例，补充新需求用例
- 五维覆盖率矩阵：需求覆盖 / 代码覆盖 / 变更覆盖 / 风险覆盖 / AI生成覆盖
- 度量：用例总数、需求覆盖率、评审通过率、失效率趋势

**输出物**: `测试用例集_项目名称/`（含等价类表、边界值表、判定表、状态转换图、BDD Feature文件、Pairwise配置表）。

### Step 3: 探索性测试与UX验证

**Goal**: 通过结构化探索性测试发现预定义用例未覆盖的未知缺陷，并完成用户体验定量评估。
**Completion criterion**: SBTM Session报告产出，包含发现的缺陷、风险项、覆盖率评估；UX指标达标或已记录改进项。

**A. 探索性测试规划（SBTM框架）**
- Charter设计：明确测试目标（如"探索支付流程在高并发下的异常处理"）、范围、时间、资源
- Session执行单元：90分钟 = 5min Setup（环境准备）+ 75min Testing（探索执行）+ 10min Wrap-up（记录整理）
- Debrief汇报：15-30分钟，测试人员向利益相关者汇报发现，确认缺陷优先级

**B. Tour方法论执行**
- 根据测试目标选择Tour类型：
  - 地标Tour（Landmark）：验证核心用户路径（如"注册→登录→下单→支付"）
  - 反叛Tour（Rebel）：故意做错（如"不填必填项直接提交"/"输入超长字符串"）
  - 破坏者Tour（Destroyer）：尝试崩溃（如"快速连续点击"/"网络切换中操作"）
  - 通宵Tour（Overnight）：长时间运行检测内存泄漏/连接池耗尽
  - 古董商Tour（Antique）：旧数据兼容性（如"用3年前的账号登录"/"导入历史数据"）
  - 超模Tour（Supermodel）：UI外观一致性（多分辨率/多浏览器/深色模式）
  - 收藏家Tour（Collector）：收集所有输出（导出文件格式/邮件模板/日志内容）
  - 指南书Tour（Guidebook）：严格按文档操作，验证文档准确性

**C. 用户体验与可用性测试**
- HEART框架评估：
  - Happiness（满意度）：NPS评分/应用商店评分/客服反馈情感分析
  - Engagement（参与度）：日活跃/功能使用频率/会话时长
  - Adoption（采用率）：新功能7日留存/功能发现率
  - Retention（留存率）：7日/30日/90日留存曲线
  - Task Success（任务成功率）：核心流程完成率/错误率/完成时间
- SUS评分：10项5点量表，总分×2.5，62分以下不及格，78分良好
- 无障碍测试：WCAG 2.1 AA合规（EAA 2025年6月欧盟生效）
- 生理指标（可选）：眼动追踪（Tobii Pro）/ 面部情感识别 / GSR/HRV

**D. AI辅助探索性测试**
- 字节FastBot：基于强化学习模仿"专家测试员"行为，每日5000+探索式会话
- AI生成探索 Charter：LLM基于系统架构生成高价值探索方向
- 人机协作：AI执行大规模探索（24×7），人类专家聚焦业务语境判断和伦理验证

**输出物**: `探索性测试报告_项目名称.md`（含Session记录、缺陷清单、风险项、UX评估结果）。

### Step 4: 缺陷管理与根因分析

**Goal**: 建立完整的缺陷生命周期管理流程，确保缺陷被高效追踪、修复、验证，并通过根因分析驱动质量改进。
**Completion criterion**: 缺陷闭环SLA达成（新缺陷4h内Triage/P0 30min分配），根因分析报告产出，预防措施已落地。

**A. 缺陷提交与报告规范（CLEAR五步法）**
- Concise（简洁标题）：`[模块] 动词+对象+现象`，如"[支付] 输入负数金额后系统崩溃"
- Locate（精准定位）：错误页面URL/接口路径/日志TraceID/环境信息
- Evidence（完整证据）：截图/录屏（Loom）/日志片段/请求响应数据
- Actual vs Expected（红绿对比）：实际结果 vs 预期结果，一目了然
- Reproducible（可复现）：步骤编号化，环境前置条件明确，复现率标注
- 单页原则：一张A4/一屏内含全部核心信息，目标：开发理解时间<1分钟

**B. 缺陷分类与定级（六维矩阵）**
- 维度1 严重度（Severity）：Blocker（系统不可用）/ Critical（核心功能失效）/ Major（主要功能异常）/ Minor（次要问题）/ Trivial（建议优化）
- 维度2 优先级（Priority）：P0（立即修复）/ P1（本周修复）/ P2（下个迭代）/ P3（排期）/ P4（监控）
- 维度3 影响面：单用户 / 部分用户 / 全量用户 / 合作伙伴 / 监管合规
- 维度4 业务价值：直接营收影响 / 用户体验 / 运营效率 / 品牌声誉
- 维度5 修复成本：1小时 / 1天 / 1周 / 需架构改造
- 维度6 风险等级：数据安全 / 资金风险 / 合规风险 / 舆论风险
- AI辅助：FastBot"Bug Auto-Tag"自动推断Severity和Priority，准确率87%，人工确认

**C. 缺陷Triage与分配**
- TRIAGE七步法：Track（接收）→ Review（审阅）→ Identify（识别类型）→ Assign（分配）→ Gauge（评估优先级）→ Escalate（升级）→ Evaluate（持续评估）
- SLA标准：新缺陷4小时内完成Triage，P0缺陷30分钟内分配Owner
- AI Triage：LLM+团队历史数据Fine-tuning，分类准确率91%、定级87%、分配85%
- 重复检测：Sentence-BERT语义向量相似度，召回率>95%，避免重复修复
- 中小团队方案：n8n + OpenAI + Jira 搭建零成本Triage流水线

**D. 修复验证与回归（FIXER六步法）**
- Find（定位根因）：代码走读/日志分析/调试追踪
- Isolate（隔离影响）：评估修复范围（单模块/跨模块/数据迁移）
- eXecute（执行修复）：编码修复，遵循团队Code Review规范
- Evaluate（影响评估）：开发Fix前必须评估影响模块/接口/用户量级
- Regression（回归验证）：
  - 修复必验证：每个Fix配套Fix Verification Test
  - 边界必回归：修复涉及模块跑边界值回归
  - 关联必检查：代码依赖分析识别受影响模块强制回归
- Evaluate（复发评估）：监控生产环境，确保同类缺陷不再出现

**E. 根因分析（ROOT四步法）**
- Recognize（识别问题）：从缺陷报告中提炼核心问题
- Observe（观察数据）：收集日志/监控/用户反馈/变更历史
- Understand（理解根因）：
  - 5Why分析法：连续追问3-5层"为什么"直至根因
  - 鱼骨图：从人/机/料/法/环/测六维度分析
  - 8D报告：D1-D8结构化问题解决（团队组建→问题描述→临时措施→根因→纠正措施→验证→预防→结案）
- Transform（转化为改进）：预防措施落地，流程/工具/培训更新
- AI辅助RCA：微软RCA Copilot准确率75%，RCA时间从3天降至4小时
- 关键原则："无责备复盘"（Blameless Postmortem），聚焦系统改进而非个人追责

**F. 缺陷度量与质量门禁联动**
- 北极星指标：缺陷逃逸率（Defect Escape Rate, DRE），目标<10%
- 三层质量门禁：
  - 提交门禁：SonarQube + ESLint + 单测覆盖率≥80%
  - 构建门禁：集成测试100%通过 + P1缺陷=构建失败
  - 发布门禁：全量回归100% + P0缺陷=发布失败
