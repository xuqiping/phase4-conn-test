## 一、背景与目标

把现有单一「账密+钉钉」认证体系升级为**多通道安全认证**，覆盖设计文档 §1.2 的四项范围：

1. 邮箱验证 + 找回密码（现有注册邮箱不验证=垃圾注册+找回漏洞，最大缺口）
2. 手机号验证码登录/注册（新号自动建号）
3. 微信扫码登录/注册（WxJava + 开放平台）
4. 账密登录优化（条件滑块 + 异地登录提醒）

**核心改造**：新增 `user_credential` 凭证表解耦多登录方式（独立账号+可绑定合并），延续现有 `bind_type`/单点登录 sid/防爆破/审计 全套既有能力，只补缺口不重写。

## 二、术语表

| 术语 | 大白话 | 简单案例 |
|---|---|---|
| user_credential（凭证表） | 一个用户可有多条"登录凭证"记录，每条对应一种登录方式（密码/邮箱/手机/微信/钉钉）。`identifier` 是该方式的唯一标识（邮箱地址/手机号/openid） | 用户绑了邮箱+手机 → 两条凭证，任一都能登录 |
| credential_type | 凭证类型枚举：PASSWORD/EMAIL/PHONE/WECHAT/DINGTALK | PASSWORD 的 identifier=username，PHONE 的 identifier=手机号 |
| verified（凭证已验证） | 该凭证是否通过了真实性校验（邮箱点过激活链接/手机收过验证码/微信授权过）。**未验证的邮箱凭证不可用于找回密码** | 老用户邮箱迁移时 verified=FALSE，需登录后验证才可用于找回 |
| bind_type（现有） | users 表的登录方式标记：password/dingtalk/phone/wechat。建号时写死，用于区分账号来源 | 手机注册的账号 bind_type='phone' |
| SMS Pumping（短信轰炸/吸费） | 攻击者用你的短信接口往大量手机号或高价国际号发短信，一夜烧光余额。**第二大经济损失攻击** | 机器人往 1 万个号码各发一条 = 烧 450 元 |
| 滑块验证码（captcha） | 发短信/登录前先让用户拖动滑块拼图，后端校验轨迹。机器人过不了=根本发不出短信。用 AJ-Captcha | 用户点"获取验证码"→先弹滑块→通过才发短信 |
| state 参数（OAuth） | 跳转微信授权时带的一个随机串，回调时原样带回校验。**防 CSRF**：攻击者伪造回调骗你给错误账号发 token 时不带正确 state 就被拒 | 跳转时 state=abc123 存 Redis，回调 state≠abc123 直接拒 |
| 异地登录提醒 | 登录成功时用 ip2region 离线库查当前 IP 归属地，与上次登录归属地比对，跨省则发邮件提醒（防被盗号后用户不知情） | 上次上海这次黑龙江 → 发"您的账号刚在黑龙江登录"邮件 |
| login:fail（现有） | 登录失败计数 Redis 键前缀，账号 5 次锁 15min / IP 20 次封 1h。本次复用 | 同号输错 5 次密码 → 锁 15min |
| session:\<userId\>（现有） | 单点登录会话键，一个用户只存一个 sid。重置密码后删此键 = 踢该用户所有会话 | reset 密码后 redisTemplate.delete("session:"+userId) |

## 三、技术实现坑点预判与规避措施

| 技术点/功能块 | 可能的坑 | 规避措施 | 验证方式 |
|---|---|---|---|
| **凭证表并发注册** | 同邮箱/手机并发注册两次都通过唯一性检查 → 两次 insert → 唯一约束报错 500 | 靠 `uk_credential_type_identifier` 部分唯一索引兜底；service 层 catch `DuplicateKeyException` 转 `CONFLICT` 友好话术 | 并发压测同邮箱注册 10 次，断言只有 1 次成功 |
| **存量邮箱迁移** | 老用户 email 本就没验证，迁移写 verified=TRUE 会让假邮箱可用于找回密码=漏洞 | 迁移时 EMAIL 凭证 **verified=FALSE**，老用户需登录后点"验证邮箱"激活 | 查迁移后数据，所有 EMAIL 行 verified=false |
| **手机号格式** | 国际号段被用于 SMS Pumping（高价号吸费）；非数字字符注入 | 正则 `^1[3-9]\d{9}$` 严格只放国内号；DTO 加 `@Pattern` | 传 +852xxxxxxxx / 138-0013-8000 都被拒 |
| **滑块绕过** | 攻击者抓包拿一次 captchaToken 反复用 | captchaToken 用完即删（AJ-Captcha 二次校验后 Redis 删 key），单次有效 | 同一 token 连续提交两次，第二次拒 |
| **短信限流键膨胀** | Redis 限流键不设 TTL 会无限堆积 | 所有 `sms:limit:*` 键 `expire` 设窗口时长；滑动窗口用 INCR+EXPIRE 原子（Lua 或先 INCR 后 EXPIRE） | 查 Redis `sms:limit:*` 键都有 TTL |
| **微信回调 token 传递** | JWT 放 query string 会进 server log/referer 泄漏 | 用 URL fragment（`#/login?token=xxx`），fragment 不发往服务器、不进 referer | 抓 Nginx access log 看不到 token |
| **WxJava 初始化** | AppID 未配置时 Bean 初始化失败拖垮启动 | `@ConditionalOnProperty(name="app.auth.wechat.enabled", havingValue="true")` 守卫，未配置时 Bean 不创建、Controller 返回"未开启" | 启动时 wechat.enabled=false 不报错 |
| **阿里云 SDK 超时** | 阿里云 SMS/DM 接口偶发慢，同步调用拖垮登录链路 | SDK 客户端设 connectTimeout=3s/readTimeout=5s；超时降级返回"发送失败请重试"，不阻塞 | 模拟阿里云 10s 不响应，登录接口 <6s 返回 |
| **重置密码踢会话** | 现有 `clearSession(userId, sid)` 只删匹配 sid 的键；重置密码要踢该用户**所有**会话 | 直接 `redisTemplate.delete("session:" + userId)`（单会话模型，键里只有一个 sid） | 重置后用旧 access token 调 /api/auth/me，应 401 |
| **ip2region 库加载** | xdb 文件 11MB，每次查询都加载文件 = 毛刺 | 用 `Searcher.newWithBuffer()` 一次性加载到 byte[] 内存常驻，查询走内存（官方推荐） | 启动日志确认库加载一次 |
| **N+1：用户多凭证查询** | 登录时先查 users 再查 credentials = 2 次查询；列表页用户+凭证= N+1 | 登录路径 2 次可接受；列表/设置页用 JOIN 或 `selectByUserId` 批量一次拿全部凭证 | 设置页打开查日志只有 1 条凭证查询 SQL |
| **审计日志批次** | 新增多个 auth action（sms_login/wechat_login/password_reset/email_verify），漏配 AuditLabelDictionary 会显示原始 key | 新增 action 全部加进 `ACTION_LABEL.auth` Map；Phase 3 跑一遍看 UI 不显示原始 key | 审计日志页搜"password_reset"显示中文 |
| **CORS/回调** | 微信回调是 GET 跨域（从微信域名跳回），CORS 预检和 SecurityConfig permitAll 都要放行 | SecurityConfig 加 `/api/auth/login/wechat/callback` permitAll；SecurityEndpointRegistry.PUBLIC_PATHS 同步 | 微信扫码能正常回调拿 token |
| **vue-tsc 类型** | 新增多个 DTO/组件类型，前端 build 类型检查失败 | 边写边 `npm run build` 过 vue-tsc；复杂类型用 `interface` 不用松散 any | `npm run build` 通过 |

## 四、安全检查清单

对照设计文档 §5 攻防清单，Phase 3 每项必须实际验证并打勾：

- [ ] **鉴权/授权**：所有 `/api/auth/*` 公开端点确认在 SecurityConfig + SecurityEndpointRegistry 两处同步放行；已登录态端点（绑定/解绑凭证、改密）校验 `userId == 当前登录用户`
- [ ] **输入校验**：手机号 `@Pattern(^1[3-9]\d{9}$)`；邮箱 `@Email`；密码走现有 `PasswordPolicy`；用户名 `@Size(3,50)`；所有 token `@Size` 上限防超长攻击；验证码 `@Pattern(^\d{6}$)`
- [ ] **数据加密**：密码 bcrypt（复用现有 PasswordEncoder）；邮件/短信 AccessKey 为“管理员 DB AES 加密配置优先、环境变量兜底”，微信 AppSecret 仍走环境变量；reset_token/email_verify_token 用 `SecureRandom` 32 字节
- [ ] **审计日志**：register/login（已有）+ sms_code_send/sms_login/wechat_login/password_forgot/password_reset/email_verify/credential_bind/credential_unbind 全部经 `AuditLogService`，detail 只带 reason 码不含敏感原文
- [ ] **错误处理**：找回密码统一话术（"若账号存在，重置链接已发送"）；账密登录统一"用户名或密码错误"；不区分号是否存在/码是否正确
- [ ] **CORS/CSRF**：微信回调 GET 放行；OAuth state 参数防 CSRF；滑块 captchaToken 单次有效防重放
- [ ] **限流**：注册（现有 IP/用户名双窗口）；短信发码（号 60s/号 10 次/天/IP 30 次/天）；找回（账号 3 次/h/IP 10 次/h）；登录失败（现有 5 锁/20 封）
- [ ] **依赖安全**：WxJava 4.6.0+ / 阿里云 SMS SDK 3.0+ / AJ-Captcha 2.2.0+ / ip2region 2.7.0+，提交前 `mvn dependency:tree` 看无高危 CVE（用 OWASP dependency-check 插件扫，项目若已有则复用）
- [ ] **会话安全**：重置密码后 `delete session:<userId>` 踢所有会话；改密同样踢；JWT fragment 传递不进 log
- [ ] **账号枚举防护**：找回统一话术；手机登录不区分新旧号；注册"用户名已存在"保留（用户体验必要，靠限流防探测）

## 五、性能考虑与验证计划

- [ ] **查询效率**：`user_credential` 表 `(credential_type, identifier)` 唯一索引 + `(user_id)` 索引已覆盖登录/设置页查询；无 N+1（见坑点表）
- [ ] **缓存策略**：短信验证码/限流计数/reset_token 走 Redis（短 TTL，不缓存业务数据）；ip2region 库内存常驻（一次性加载）
- [ ] **并发处理**：凭证并发注册靠 DB 唯一约束兜底；短信发码 Redis INCR 原子计数；无重型并发场景
- [ ] **资源使用**：无大文件/大数据集；ip2region.xdb 11MB 启动加载一次常驻内存可接受
- [ ] **第三方依赖超时**：阿里云 SMS/DM 设超时（见坑点表）；微信 OAuth API 走 WxJava 默认超时；超时降级不阻塞主流程
- [ ] **性能验证（Phase 4）**：登录接口 P95 < 500ms（含 DB+Redis）；发短信接口 P95 < 1.5s（含阿里云调用）；ip2region 查询 < 1ms

## 六、功能联动点清单

> 最容易"主功能做完就以为完事"而漏掉的部分。每条写明触发/联动/预期/边界。

| # | 触发动作 | 联动对象 | 预期变化 | 边界（反向/半选/批量） |
|---|---|---|---|---|
| L1 | 注册成功 | users + user_credential + 发验证邮件 | 建号 status=ACTIVE + PASSWORD 凭证 verified=TRUE + EMAIL 凭证 verified=FALSE + 邮件入队 | 邮件发送失败不阻断注册（降级，邮件可重发）；同一邮箱重复注册被唯一约束拒 |
| L2 | 邮箱激活成功 | user_credential.EMAIL | verified=FALSE→TRUE + verified_at=now | token 过期/已用 → 拒，提示重新发送；同账号重复激活幂等 |
| L3 | 手机验证码登录（新号） | users + user_credential + 角色分配 | 建号 + PHONE 凭证 verified=TRUE + 分配 user 角色 + 发 JWT | 号已存在 → 直接登录不建号；并发同号注册靠唯一约束兜底 |
| L4 | 微信扫码登录（新号） | users + user_credential + 角色分配 | 建号 + WECHAT 凭证 verified=TRUE + 分配 user 角色 + 发 JWT | unionid 已存在 → 直接登录；unionid 变更（极少）→ 更新凭证 identifier |
| L5 | 重置密码成功 | user_credential.PASSWORD + Redis session | 更新 secret + **删除 session:\<userId\> 踢所有会话** | 旧 access token 立即失效（黑名单可选，单点删除已足够，access 15min 自然过期）；reset_token 用完即删防重放 |
| L6 | 改密成功（设置页） | user_credential.PASSWORD + Redis session | 同 L5 + 必须验旧密码 | 旧密码错 → 拒；新旧相同 → 拒 |
| L7 | 绑定新凭证（设置页） | user_credential | 新增一行（EMAIL/PHONE/WECHAT）+ verified 按验证流程 | 已被他人绑定 → CONFLICT 拒；自己已绑同类型 → 提示已绑定 |
| L8 | 解绑凭证（设置页） | user_credential（软删） | 至少保留 1 种可用凭证，防止账号无法登录 | 解绑最后一个 → 拒（"至少保留一种登录方式"）；解绑 PASSWORD 且无其他凭证 → 拒 |
| L9 | 账密登录失败 ≥3 次 | 前端滑块开关 + 后端 captcha_required | 下次登录前端强制弹滑块 | 登录成功后计数清零 → 不再要求滑块；锁定期内仍要求 |
| L10 | 异地登录 | 邮件提醒 | 登录成功 + 当前 IP 省份≠上次 → 异步发提醒邮件 | 首次登录（无历史）→ 不提醒；同省 → 不提醒；邮件失败不阻塞登录 |
| L11 | 禁用用户（现有） | 所有登录通道 | DISABLED 用户所有通道（账密/手机/微信/钉钉）登录都拒 | 现有账密/钉钉已校验 status；手机/微信新通道登录前同样校验 status=ACTIVE |
| L12 | wechat.enabled=false | 前端扫码 Tab + 后端 Controller | 前端不显示微信 Tab；后端 /login/wechat/* 返回"未开启" | 钉钉同理（现有模式）；切换开关前端需刷新 |

### Chunk A · 凭证表 + DB 迁移 V102 + CredentialService 基础

**目标**：建凭证表 + 迁移存量 + 提供凭证 CRUD 服务，作为所有通道的基础。

**涉及文件（≤6）**
- `backend/src/main/resources/db/migration/V102__auth_multi_credential.sql`（新）
- `backend/.../auth/entity/UserCredential.java`（新）
- `backend/.../auth/mapper/UserCredentialMapper.java`（新）
- `backend/.../auth/service/CredentialService.java`（新，基础 CRUD）
- `backend/.../auth/dto/CredentialVO.java`（新，用于设置页展示）
- `backend/.../common/exception/ErrorCode.java`（补 `CREDENTIAL_LOCKED_LAST_ONE(42204,"至少保留一种登录方式")`、`EMAIL_NOT_VERIFIED(42205,"邮箱未验证，无法用于找回")`）

**动作（伪代码）**
1. **V102 迁移**（幂等）：
   - `users` 加列 `phone/wechat_unionid/wechat_openid`（`IF NOT EXISTS`）
