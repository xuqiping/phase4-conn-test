## 需求池结构与分类

### 一、三层结构

需求池推荐采用**Epic → Feature → Story**三层结构：

| 层级 | 定义 | 典型粒度 | 生命周期 |
|---|---|---|---|
| Epic | 重大业务目标/战略方向 | 跨季度 | 季度级 |
| Feature | 可独立交付的用户价值单元 | 跨Sprint | 月级 |
| Story | 可在一个Sprint内完成的具体任务 | 1-2周 | Sprint级 |

**示例**：
```
Epic: 提升新用户留存
├── Feature: 新手引导优化
│   ├── Story: 引导流程3步→1步
│   ├── Story: 引导页增加进度条
│   └── Story: 引导完成率埋点
├── Feature: 首单激励
│   ├── Story: 新用户优惠券弹窗
│   └── Story: 首单免运费标识
└── Feature: 社交裂变
    ├── Story: 邀请好友奖励
    └── Story: 新用户专属优惠码
```

### 二、需求分类标签体系

每条需求应有以下标签维度：

| 标签维度 | 选项 | 用途 |
|---|---|---|
| 来源 | 用户反馈/销售内部/竞品/数据/管理层 | 追溯需求来源 |
| 类型 | 新功能/优化/Bug/技术债/合规 | 区分需求性质 |
| KANO类别 | 必备/期望/魅力/无差异/反向 | 优先级参考(→D-02.04) |
| 优先级方法 | RICE/ICE/四象限/MoSCoW | 标注用哪种方法排序 |
| 影响面 | 全量/大/中/小/极小 | ROI粗筛 |
| 紧急度 | P0(阻断)/P1(紧急)/P2(正常)/P3(低) | 区分紧急与重要 |

### 三、需求池的分层管理

```
┌─────────────────────────────────────┐
│          产品路线图(Roadmap)          │ ← 季度级Epic
├─────────────────────────────────────┤
│         版本需求池(Release Backlog)   │ ← 版本级Feature
├─────────────────────────────────────┤
│       Sprint需求池(Sprint Backlog)   │ ← Sprint级Story
├─────────────────────────────────────┤
│          冰箱区(Icebox)              │ ← 未排期/低优先级
└─────────────────────────────────────┘
```

**各层职责**：

| 层 | 内容 | 管理人 | 更新频率 |
|---|---|---|---|
| Roadmap | 3-6个月的Epic | PM+管理层 | 季度 |
| Release Backlog | 下1-2个版本的Feature | PM | 双周 |
| Sprint Backlog | 当前Sprint的Story | PM+团队 | 每日 |
| Icebox | 未排期需求 | PM | 需要时 |

### 四、Scrum vs Kanban的需求池差异

| 维度 | Scrum需求池 | Kanban需求池 |
|---|---|---|
| 结构 | 三层(Epic/Feature/Story) | 扁平(所有需求一列) |
| 排期 | 按Sprint批量拉入 | 按WIP限制逐条拉入 |
| 优先级 | Sprint Planning时排序 | 随时排序，Top 1做 |
| 适用 | 固定迭代节奏的团队 | 流式交付的团队 |

### 五、需求池的准入标准

**新需求进入需求池的最低标准（Definition of Ready for Backlog）**：

1. 需求描述完整（Who/What/Why）
2. 来源可追溯
3. 已初步评估影响面
4. 无明显重复（已做去重检查）
5. 有初步的KANO/优先级分类

**不满足准入标准的需求**：放入"待完善区"，不进入正式需求池。
