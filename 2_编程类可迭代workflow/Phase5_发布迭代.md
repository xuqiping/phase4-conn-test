# Phase 5 · 发布迭代

> 类型：流程步骤 · **Phase 5**（主链收尾，连接下一轮）
> 版本：v1.5（v1.1 增部署环境与傻瓜式部署流程；v1.2 明确 CI = 本地最小质量门 check_all 搬上服务器；v1.3 每轮迭代收尾必做上下文文件 review（防衰变/防膨胀）；v1.4 给出最小 CI 定义 + GitHub Actions yaml 骨架（check_all + Flyway validate + 构建），全绿才允许部署；v1.5 加「接入可观测性」动作 + 监控告警说明.md 产物（日志/指标/健康检查接入 + 告警规则表），与 Phase 6 删功能清告警闭环；v1.6 加「多环境配置说明」产物（dev/local/staging/prod 配置差异对照 + 机密项管理），L2/L3 必产；**v1.7 加「质量与漂移度量」（每轮迭代手填：缺陷规格内/外 + 文档同步待办 + spec 覆盖率 + 漂移趋势）**）
> 定位：vibe coding 唯一值得继承的东西——**快速迭代节奏**。但用 SDD 的纪律来迭代，而不是裸奔。

## 目标

把验证通过的版本发出去，收真实反馈，决定下一轮做什么。软件是活的，Phase 5 不是终点，是回到 Phase 1/2 的入口。

## 输入

- Phase 4 验证通过的版本

## 动作清单

1. **发最小可用版（MVP）**：不要等「完美」才发布。能解决核心场景就发，越早收到真实信号越好。
2. **【v1.1 增】部署上线 + 产出部署手册**：把版本部署到服务器，并在 `workflow_output/docs/deploy/部署手册.md` 产出（骨架见 [项目模板/workflow_output/docs/deploy/_模板.部署手册.md](项目模板/workflow_output/docs/deploy/_模板.部署手册.md)），记录：
   - **服务器环境要求**：CPU / 内存 / 磁盘 / 操作系统
   - **软件清单**：要装什么（JDK / Node / Redis / MySQL / Nginx…）+ 版本 + **去哪下载** + **本机/服务器是否已有安装包 + 安装包位置**
   - **傻瓜式部署步骤**：Step 0~6 照着勾（装软件 → 放代码&配置 → 建库建表（Flyway）→ 构建 → 启动 → 开机自启）
   - 配置项说明、部署后验证清单、回滚方案
   > 部署手册是"照着做就能上线"的傻瓜指南。**"本机是否有安装包 / 位置"是实例信息，换机器必须重填。** 本地启动见 Phase 4 的快速启动速查表。
3. **接自动化质量门**（铁律 #9）：CI/CD、lint、类型检查、code review bot——让机器自动抓错，AI 才飞得起来。**【v1.2】CI 不是从零建**：Phase 0 骨架就带上的本地最小质量门 `scripts/check_all`（lint + 类型检查 + 测试）在 Phase 3 已全程使用，Phase 5 的 CI 只是把**同一份 check_all** 搬到服务器上跑（push 触发 → 跑 check_all → 全绿才允许部署），检查标准本地与线上一致。**【v1.4】最小 CI 定义**：项目模板带 `.github/workflows/ci.yml` 骨架（push/PR 触发 → 跑 check_all → Flyway 迁移校验 `validate` → 构建产物），任一步失败阻断、全绿才放行；定义与各平台适配写进部署手册「六、最小 CI」。部署只接 CI 全绿的产物。
4. **【v1.5】接入可观测性（埋了不接 = 白埋）**：Phase 2「运维考量清单」要求埋的日志 / 指标 / 健康检查，部署后必须接进收集与告警，并在 `workflow_output/docs/ops/监控告警说明.md` 产出（骨架见 [项目模板/workflow_output/docs/ops/_模板.监控告警说明.md](项目模板/workflow_output/docs/ops/_模板.监控告警说明.md)），记录：
   - **可观测性三支柱接入清单**：日志（含轮转策略，防撑爆磁盘）+ 关键指标（QPS/错误率/响应时间/资源）+ 健康检查（uptime 监控）。
   - **告警规则表**：每条 = 告警项 | 阈值 | 严重度 | 通知方式 | 处理预案 | **关联功能**（这列是 Phase 6 删功能清告警的依据）。
   - **通知渠道与值班**：什么严重度用哪个渠道、on-call 排班、升级路径、静默规则。
   - **应急处理流程**：确认 → 止血优先 → 定位 → 修复 → 复盘。
   > 与 Phase 6 闭环：删功能时删本文件对应告警行（否则误报）；加功能时补行。L1 小工具可省，L2/L3 必产。
5. **【v1.6】理清多环境配置**：在 `workflow_output/docs/config/多环境配置说明.md` 产出（骨架见 [项目模板/workflow_output/docs/config/_模板.多环境配置说明.md](项目模板/workflow_output/docs/config/_模板.多环境配置说明.md)），记录：
   - **环境清单**：local / dev / staging / prod 各自用途、谁用、数据来源、是否对外（不是每个项目都四套，按需删）。
   - **配置项总表**：每个配置项一行，列 dev/staging/prod 取值 + 来源（`.env` / 环境变量 / 配置中心）+ **敏感级别**（公开/内部/机密）。
   - **机密项铁律**：DB 密码 / JWT 密钥 / API key 等机密项**只写来源 + 占位符（`<see vault>`）**，真值放 vault / `.env`（`.gitignore` 必含），绝不进仓库/文档/代码明文。
   - **按环境切换的行为**：调试开关 / mock / 日志级别 / source map 等行为差异——**生产列必须是最保守值**（默认关/mock 关/日志 WARN+）。
   > 与部署手册分工：部署手册管「生产这台机器怎么装」（实例信息），本文件管「跨环境配置差异」（配置项级），两份的生产行必须一致。L1 小工具 local+prod 两套够用可省，L2/L3 必产。
6. **收数据 + 反馈**：用量数据、用户反馈、bug 报告。这是下一轮规格的输入。
7. **规划下一轮**：基于反馈分两类走——**新增功能**回 **Phase 1**（改规格）或 **Phase 2**（新功能直接出 plan）；**改 / 删已有功能**进 **Phase 6 变更管理**（先做影响评估再动手，别直接改存量）。迭代闭环。
8. **沉淀项目实例**：把这次实跑的经验写回各 Phase 的「避坑点」，项目副本归档进 `1_实例产物/`。
9. **【v1.3】上下文文件 review（每轮迭代收尾必做）**：核对 AGENTS.md / file_structure.md / 各 XX约束.md——① 与代码现状是否有矛盾（过期规则删掉或改写）；② `last_updated` 是否更新；③ 是否膨胀超标（AGENTS.md 聚焦每次必读规则，细节拆 XX约束.md，定期瘦身）。上下文文件当代码管：快变项目至少每轮迭代 review 一次。
10. **【v1.7】填质量与漂移度量（每轮迭代收尾必做）**：在 `workflow_output/开发进度/开发进度总览.md` 的「质量与漂移度量」表填一行——本轮缺陷数（规格内/规格外）、文档同步待办数、关键功能 spec 覆盖率、漂移率趋势。**不求精确，求趋势可见**：规格外缺陷多 → spec 有洞，回 Phase 1 补 AC；文档同步待办长期不降 → 同步机制失效；漂移率连续两轮 ↑ → 停下排查流程。

## 避坑点

- **不要追求一次性大而全**。一个人公司的弹药有限，小步快跑、早发早纠偏是生存策略。
- 反馈不照单全收——回到 Phase 0 的商业判断，区分「真需求」和「噪音」。
- 每轮迭代结束，把踩过的坑沉淀回本工作流的 Phase 文件，让流程本身也迭代。
- **【v1.1】部署手册的"软件清单"要写死下载源 + 本机安装包位置**：别只写"装个 Redis"——三个月后你忘了去哪下、本机到底装没装，又得从头查。生产敏感配置（数据库密码、JWT 密钥）**别写明文进手册**，用占位符 + 单独安全存储。
- **【v1.1】部署手册和快速启动速查表要联动维护**：换了端口 / 加了服务（如新增 Redis），两份文档都要更新，否则一份对一份错会误导。
