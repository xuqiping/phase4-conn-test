# 规格 · 自助充值（支付宝/微信）+ 充值记录字段补全 + 账单总览用户余额

> Phase 1 修复规格。实现必须与本文一致；来源为 2026-08-21 人工测试问题 **7x 未解决 #1/#2**、**20x 未解决 #1**。
> 用户已拍板（2026-08-21）：①**支付架构 + 接口先落，真实商户后接**——先落可全链路测试的 mock 通道，支付宝/微信真实通道留配置位；②**不建人民币金额钱包**——只记流水，「金额余额」类需求用累计充值金额回答。
> 关联：[积分计费系统规格](积分计费系统.md)｜[项目组与积分划拨设计](项目组与积分划拨设计.md)｜[积分计费系统 Feature Map](../feature-map/积分计费系统.feature-map.md)。

## 1. 目标

1. **用户自助充值**：用户在我的钱包页发起充值 → 生成支付订单 → 扫码/mock 支付 → 渠道异步回调 → 积分入账。渠道抽象层支持 mock（本期可测）、支付宝、微信（骨架，配置商户资料后启用）。
2. **充值记录字段补全**（7x#1）：充值记录列表展示——用户充值账号（平台用户名）、渠道付款账号（如支付宝付款账号）、充值金额（¥）、对应充值积分、充值后用户剩余积分、该用户历史累计充值（金额 + 积分）。
3. **账单总览增强**（20x#1）：admin 账单页新增「用户余额」视图——全用户当前积分余额、累计充值积分、累计充值金额，顶部给全平台合计卡片。

## 2. 非目标（本期不建）

- ❌ 人民币金额钱包 / 金额消费（用户已拍板不建）。
- ❌ 真实支付宝/微信商户对接的沙箱联调（无商户资质；接口与配置位预留，拿到资质后仅需实现渠道类并配置）。
- ❌ 退款到渠道（原路退回）——`REFUNDED` 状态保留语义，本期只落 admin 积分回收（现有），渠道退款列为后续项。
- ❌ 充值赠送/优惠券/首充活动。
- ❌ 发票。

## 4. 数据模型（Flyway `V139__payment_recharge.sql`；若上游占用则顺延）

```sql
-- 4.1 payment_order 补列
ALTER TABLE payment_order ADD COLUMN payer_account VARCHAR(128) NULL;   -- 渠道付款账号（支付宝账号/微信openid），回调时回填
ALTER TABLE payment_order ADD COLUMN expire_at   TIMESTAMPTZ NULL;      -- 订单过期时间（创建时=now+30min）
ALTER TABLE payment_order ADD COLUMN idem_key    VARCHAR(64) NULL;      -- 创建幂等键（防重复下单）

-- 状态机扩展：PENDING → PAID / CLOSED（过期或用户取消）；PAID → REFUNDED（后续）
-- 若 V65 的 status 有 CHECK 约束：DROP 旧 CHECK，重建含 'CLOSED'；FAILED 保留（回调验签失败/入账失败人工处置用）

-- 4.2 启用渠道单号幂等（V65 注释的索引正式落地）
CREATE UNIQUE INDEX uk_payment_channel_order
    ON payment_order (channel, channel_order_id)
    WHERE channel_order_id IS NOT NULL;

-- 4.3 创建幂等键唯一（防双击/重试重复下单）
CREATE UNIQUE INDEX uk_payment_idem ON payment_order (user_id, idem_key) WHERE idem_key IS NOT NULL;

-- 4.4 修复 V93 拼写（正确表单数，保持 IF role exists 守卫）
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname='agent_app') THEN
    EXECUTE 'REVOKE DELETE, TRUNCATE ON payment_order FROM agent_app';
  END IF;
END $$;

-- 4.5 常用查询索引
CREATE INDEX idx_payment_user_status ON payment_order (user_id, status, created_at DESC);
CREATE INDEX idx_payment_status_expire ON payment_order (status, expire_at) WHERE status = 'PENDING';
```

**不新建表**。充值记录 = `payment_order`（PAID）JOIN `points_ledger`（type=RECHARGE, ref_id=orderId，取 `balance_after` 作「充值后剩余积分」）；累计充值 = `SUM(amount_yuan)/SUM(points_granted) WHERE status='PAID'` 按用户聚合。

## 5. 支付域设计

### 5.1 状态机

```
创建(PENDING, expire_at=+30min)
  ├─ 渠道回调验签通过 + 金额一致 → PAID（同事务：状态翻转 + 积分入账 + 流水）
  ├─ 过期关闭任务扫到 → CLOSED
  └─ 用户主动取消 → CLOSED
PAID → REFUNDED（本期不落，仅语义保留）
```

- 状态翻转一律**条件 UPDATE**（`WHERE id=? AND status='PENDING'`），0 行 = 已处理 → 幂等返回成功（回调重复/超时重推不重复入账）。
- 入账复用 `grantWithLedger(channel, channelOrderId)`：同一事务写 PAID + 余额 + RECHARGE 流水；`uq_payment_channel_order` + `uq_ledger_ref` 双兜底。

### 5.2 渠道抽象

```java
public interface PaymentChannelService {
    String channel();                                   // MOCK / ALIPAY / WECHAT
    PrepayResult precreate(PaymentOrderEntity order);   // 返回二维码串/跳转串/mockToken
    NotifyResult verifyAndParse(HttpServletRequest req); // 验签+解析 → (channelOrderId, payerAccount, amountYuan)
    ChannelOrderQuery query(String channelOrderId);      // 主动查单（对账/补单用）
}
```

- 路由：`PaymentChannelRouter` 按 channel 找实现；未配置商户资料的渠道 `enabled=false` 时下单直接 400「该渠道未开通」。
- **MOCK 通道（本期落地）**：precreate 返回 mockToken；前端 mock 收银台「模拟支付成功/失败」按钮 → 走**同一个回调端点**（mock 验签 = HMAC(服务端配置密钥, token)）→ 全链路可测。mock 通道由配置 `billing.payment.mock-enabled` 控制，**生产必须 false**，启动时若 profile=prod 且 mock 开启则告警日志。
- **ALIPAY / WECHAT 通道（本期骨架）**：实现类留空抛 `CHANNEL_NOT_CONFIGURED`；配置项 `billing.payment.alipay.*`（appId/merchantPrivateKey/alipayPublicKey/notifyUrl）、`billing.payment.wechat.*`（mchId/appId/apiV3Key/certPath）入 `application.yml` 占位，**密钥一律环境变量注入，禁止入库入仓**。

### 5.3 端点

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/billing/payment/orders` | 登录 | 创建充值单 `{amountYuan, channel, idemKey}` → 校验金额区间（1~100000）→ 金额×当前 ratio 档位算 points_granted 快照落单 → PENDING + precreate 返回 |
| GET | `/api/billing/payment/orders/{id}` | 登录(本人) | 查单状态（前端轮询用） |
| POST | `/api/billing/payment/orders/{id}/cancel` | 登录(本人) | PENDING→CLOSED（条件 UPDATE） |
| POST | `/api/billing/payment/notify/{channel}` | **匿名放行 + 验签** | 渠道异步回调；验签失败 400；成功按 5.1 入账；返回渠道约定应答串 |
| GET | `/api/billing/me/recharges` | 登录 | 我的充值记录（分页）：金额/积分/渠道/付款账号/状态/充值后余额 |
| GET | `/api/billing/admin/recharges` | `points:recharge` | 全平台充值记录（分页，筛用户/渠道/状态/日期），字段见 §6 |
| GET | `/api/billing/admin/user-balances` | `usage:view` | 全用户余额视图（分页）：当前积分余额、累计充值积分、累计充值金额；响应头带全平台合计（Σ余额、Σ充值积分、Σ充值金额） |

安全细则：
- notify 端点 `SecurityConfig` 匿名放行但**必须过渠道验签**；验签含金额复核（回调金额 == 订单金额，不符 → FAILED + 安全事件 + 告警）。
- 创建订单 `@RateLimit(action="payment_create", max=10, windowSeconds=60)`；idemKey 前端每次表单会话生成 UUID（复用 `WalletAdminView` 模式）。
- 过期任务：`@Scheduled` 每分钟扫 `PENDING AND expire_at<now` → CLOSED（批量条件 UPDATE，单批 200）。
- 对账：`/api/billing/admin/reconcile` 扩展一节「渠道在途」——PENDING 超 10 分钟未关 + PAID 无对应 RECHARGE 流水的异常列表。
- 全部状态翻转写审计（`@AuditLog` / `AuditLogService.fromMdc`）。

## 6. 充值记录与账单总览字段口径

### 6.1 充值记录行（用户端 + admin 端共用 DTO）

| 字段 | 来源 |
|---|---|
| 用户充值账号 | `users.username`（JOIN） |
| 渠道付款账号 | `payment_order.payer_account`（回调回填；未回填显「—」） |
| 充值金额 | `amount_yuan` |
| 对应充值积分 | `points_granted` |
| 充值后剩余积分 | `points_ledger.balance_after`（ref_type='PAYMENT', ref_id=orderId, type='RECHARGE'；取不到显「—」） |
| 状态 / 渠道 / 时间 | payment_order |
| 历史累计充值 | 行级不带；**列表顶部汇总条**：该用户 Σ amount_yuan(PAID)、Σ points_granted(PAID)（admin 查某用户时显示；用户端看自己恒显示） |

> 「用户最大积分总额（历史所有的充值金额汇总）」口径拍板：**累计充值金额 + 累计充值积分**两个数并列展示，不做「峰值余额」语义（峰值需全量流水回放，无业务价值）。

### 6.2 账单总览「用户余额」视图（20x#1）

- admin 账单页新增 tab「用户余额」：表格列 = 用户名、当前积分余额（`user_points_balance.balance_points`，无钱包行显 0）、累计充值积分、累计充值金额、最近充值时间；按余额/累计排序；分页。
- tab 顶部 3 张合计卡：全平台用户余额合计、累计充值积分合计、累计充值金额合计。
- SQL：`users LEFT JOIN user_points_balance LEFT JOIN (SELECT user_id, SUM(...) FROM payment_order WHERE status='PAID' GROUP BY user_id)`；合计卡用同口径 `SUM` 全表聚合（数据量小，无需物化）。

## 8. 安全策略

1. **验签**：所有回调先验签再解析；mock 通道用服务端 HMAC 密钥（`billing.payment.mock-secret`，环境变量），真实渠道用各自公钥/平台证书。
2. **金额复核**：回调金额 ≠ 订单金额 → 拒绝入账、状态 FAILED、写安全事件（复用 SecurityEvent 体系）+ 审计。
3. **幂等三道**：渠道单号唯一索引（DB 约束）→ 条件 UPDATE 状态翻转（并发）→ `uq_ledger_ref` 流水兜底。回调重复投递返回成功但不重复入账。
4. **防重放**：验签内容含时间戳/nonce（真实渠道原生支持）；mock 的 HMAC 内容含 expire 时间戳。
5. **越权**：查单/取消/我的记录走 SecurityContext userId + service 层本人校验；admin 端走权限码。
6. **密钥管理**：渠道密钥/证书全部环境变量；`application.yml` 只留 key 名占位；日志脱敏（禁止打印签名原文、证书、payer 完整账号—— payer_account 落库前做掩码？不落掩码，admin 需要完整排查，**日志中掩码**：`ali***@example.com` 形式）。
7. **限流**：下单 10 次/分钟/用户；notify 端点全局限流 + 异常 IP 入安全事件。
8. **传输**：notifyUrl 必须 HTTPS（部署 checklist 项）。

## 术语表

| 术语 | 大白话 | 例子 |
|---|---|---|
| **幂等**（idempotent） | 同一操作重复执行 N 次，效果和执行 1 次一样 | 支付回调网络重推 3 次，积分只加 1 次 |
| **条件 UPDATE** | 带状态前提的更新，前提不成立就改 0 行，用来防并发抢状态 | `WHERE status='PENDING'` 已被别的线程改成 PAID 时，本次改 0 行 → 知道已被处理 |
| **验签** | 渠道用私钥给回调内容签名，我方用公钥/密钥校验，确认回调真是支付宝/微信发的、没被篡改 | 防伪造「付款成功」刷积分 |
| **precreate（预下单）** | 先在我方建订单再找渠道要支付二维码/链接 | 微信 Native 下单返回 code_url 生成二维码 |
| **ratio 档位** | 充值金额→积分的换算率，按金额分档 | `points_ratio_tier`：充 100¥=10000 分 |
| **backstop（兜底）** | 最后一道数据库约束保险，代码全失效时 DB 也能拦住错账 | `uq_ledger_ref` 唯一索引 |
