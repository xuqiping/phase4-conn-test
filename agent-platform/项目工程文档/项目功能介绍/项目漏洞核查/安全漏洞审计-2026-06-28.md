## 漏洞 1 · Sidecar 回调端点未鉴权 + userId 客户端自填

**定位**：`POST /api/runtime/callbacks/nodes/execute`
- [RuntimeCallbackController.java:18](../../../backend/src/main/java/com/superprogrammer/runtime/controller/RuntimeCallbackController.java#L18) — 端点无任何鉴权注解
- [SecurityConfig.java:45](../../../backend/src/main/java/com/superprogrammer/auth/security/SecurityConfig.java#L45) — `.requestMatchers("/api/runtime/callbacks/**").permitAll()` 放行
- [RuntimeNodeCallbackService.java:85,91](../../../backend/src/main/java/com/superprogrammer/runtime/service/RuntimeNodeCallbackService.java#L85) — `request.getUserId()` 直接灌进 `ragScopeResolver.resolveNodeKbs(...)` 和 `ragRetrievalService.retrieveEvidence(...)`

### 大白话
这个接口是给 Python sidecar（工作流执行器）回调 Java 用的——sidecar 跑到「检索节点」「Agent 节点」时，回头让 Java 干活。设计上它信任「调用方是自家 sidecar」，所以没加登录校验。**但「信任」没落实成任何凭据**——既没有共享密钥，没有签名，没有 IP 白名单。结果就是：**任何人都能冒充 sidecar 调这个接口**。

更糟的是，接口要干哪些活（以谁的身份检索知识库、执行谁的 Agent），靠的是请求体里的 `userId` 字段——**而这个字段是调用方自己填的**。等于说「我是谁」由对方说了算。

### 攻击案例
黑客不用登录，直接发这个请求：
```http
POST /api/runtime/callbacks/nodes/execute
Content-Type: application/json

{
  "sourceType": "RETRIEVAL",
  "sourceId": "<某个工作流节点配置>",
  "userId": 1001,           ← 填受害者 ID（比如老板、财务）
  "input": { "query": "公司本月薪资明细" }
}
```
服务器收到 → 用 `userId=1001` 去检索**该受害者有权访问的全部知识库** → 把命中的证据文本（可能就是薪资表）塞进 `output.text` 返回。黑客**没花一分钱 token、没登录**，就把别人的知识库内容掏走了。

换个 `sourceType` 还能冒充任意 agent 所有者触发 SKILL/AGENT 执行，白嫖 LLM、读到别人的 prompt 模板。

### 修法
1. 回调端点加**共享密钥**：sidecar 出站请求带 Header `X-Runtime-Token: <预共享密钥>`，Java 用独立 `RequestMatcher` 校验该头；密钥从环境变量读，不进仓库。
2. 叠加**内网白名单 IP** 校验（sidecar 与 Java 同机房）。
3. **`userId` 禁止从请求体取**——改从 `executionId → 执行日志.triggeredBy` 反查（执行日志是 Java 自己写的，可信）。
4. 若短期难改，临时措施：SecurityConfig 收回 permitAll，要求 sidecar 携带一个 system 账号的 JWT。

### 验证（修复后）
- 不带 `X-Runtime-Token` 调用 → 401/403。
- 带正确 token 但 `userId` 与 `executionId` 对应的 triggeredBy 不一致 → 用反查值，拒绝请求体 userId。

## 漏洞 2 · DB 密码 + JWT 密钥硬编码进仓库

**定位**：[application.yml:20,70](../../../backend/src/main/resources/application.yml#L20)
```yaml
# 第 20 行
password: ${DB_PASSWORD:aa64221886}          ← 真实 DB 密码当默认值
# 第 70 行
secret: ${JWT_SECRET:bXlTdXBlclNlY3JldEtleUZvckFnZW50UGxhdGZvcm1Qcm9qZWN0MjAyNg==}
                                             ← JWT 密钥默认值（base64 解开 = mySuperSecretKeyForAgentPlatformProject2026）
```

### 大白话
`${DB_PASSWORD:aa64221886}` 的意思是「优先用环境变量 DB_PASSWORD，**如果没设，就用 `aa64221886`**」。问题在于这个兜底默认值是个**看起来很真的密码**，并且**随代码一起提交进了 git**——任何能看到代码的人（员工、外包、开源后、仓库泄露）都拿到了它。

JWT 密钥同理。JWT 是「登录令牌」，服务器用它签名来证明「这个令牌是我发的」。**密钥一旦泄露，谁都能自己伪造令牌**，冒充任意用户、任意角色，连登录都不用。

代码里有句注释警告「生产务必设 JWT_SECRET」，但**默认值本身是真的、且已进 git**——只要某次部署忘设环境变量，这个默认值就生效，密钥即等于公开。

### 攻击案例
**案例 A（拖库）**：某人拿到代码仓库（哪怕是离职员工 local 副本），看到 `aa64221886`，如果生产环境恰好没改 DB 密码（很可能没改，因为改了代码里默认值还在、且没人会主动改）→ 直接连数据库 `psql -h ... -U postgres -W`，输 `aa64221886` → 拖走全部用户、记忆、知识库。

**案例 B（伪造身份）**：拿到 JWT 密钥 `bXlT...`，本地用代码同款算法签一个令牌：
```python
jwt.encode({"sub": 1, "role": "admin"}, "mySuperSecretKeyForAgentPlatformProject2026", algorithm="HS256")
```
得到一个**合法的 admin 令牌** → 带上它调任意接口 → 你现在是超级管理员，能管所有用户、所有知识库、所有配置。连密码都不用知道。

### 修法
1. **立刻轮换**（运维动作，不等代码）：
   - 改 PostgreSQL 密码
   - 重新生成 JWT 密钥（`openssl rand -base64 64`），重启所有服务
2. 代码改：默认值清空
   ```yaml
   password: ${DB_PASSWORD:}      # 空默认值，启动时未注入则连接失败（显式失败 > 静默用弱默认）
   secret: ${JWT_SECRET}          # 无默认值，未注入启动失败
   ```
3. git 历史里这两把密钥**永远删不掉**（可追溯），所以轮换是必须的，光改代码不够。
4. 加启动校验：密钥为空或等于已知弱默认值 → 抛异常拒绝启动。

### 验证（修复后）
- 删掉环境变量启动 → 服务拒绝启动并报错。
- `git log -p application.yml` 能看到历史里的明文 → 确认轮换已生效（旧密钥作废）。

## 漏洞 3 · 用户级 LLM endpoint SSRF

**定位**：[UserLlmController.java:38-51](../../../backend/src/main/java/com/superprogrammer/llm/controller/UserLlmController.java#L38)（createProvider / test 仅需登录，无 `@RequirePermission`）+ [LlmGateway.java:74-92](../../../backend/src/main/java/com/superprogrammer/llm/LlmGateway.java#L74) `findProvider` 用用户填的 endpoint 构造 WebClient。`[审计报告]`

### 大白话
平台允许用户配置「自己的 LLM 供应商」（自填 API 地址 + key）。服务器拿到这个地址后，每次聊天/向量化都会**主动去请求它**。

问题是：**这个地址没有任何限制**。用户可以填一个内网地址或云服务器内部地址，让服务器替他去访问——服务器在内部网络里能看到的的东西，用户原本看不到，现在借服务器的手就能看到了。这叫 SSRF（服务端请求伪造）。

### 攻击案例
黑客创建一个「自定义 LLM 供应商」，`apiEndpoint` 填：
```
http://169.254.169.254/latest/meta-data/iam/security-credentials/
```
（这是 AWS/云平台给服务器实例发临时凭证的内部地址）。平台服务器收到聊天请求 → 去请求这个地址 → 云厂商的临时 AccessKey 被当作「LLM 响应」返回。更狠的是 `OpenAICompatibleProvider.embed` 失败时**会把响应体片段拼进异常消息回显**（[审计报告]）→ 黑客在前端报错里直接看到云凭证 → 拿去操作你的云资源。

填 `http://10.0.0.5:8080/admin` 之类的内网管理面同理。

### 修法
1. endpoint 做协议+主机白名单：禁止 `127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`（云元数据）、`::1`、`fc00::/7`。
2. 禁用 HTTP 重定向跟随（防 302 绕过）。
3. embed/异常路径**不回显响应体**给客户端。
4. 可选：自定义 endpoint 仅 admin 可配，普通用户只继承全局 provider。

### 验证（修复后）
- 创建 provider 填 `http://127.0.0.1/` → 被拒。
- 填正常公网 LLM 地址 → 通过。

## 漏洞 4 · 执行日志越权读 / 越权标记失败

**定位**：[ExecutionController.java:74](../../../backend/src/main/java/com/superprogrammer/execution/controller/ExecutionController.java#L74)（`GET /api/executions?workflowId=X` 调 `listByWorkflowId` 只按 workflowId 过滤）+ [ExecutionController.java:119](../../../backend/src/main/java/com/superprogrammer/execution/controller/ExecutionController.java#L119)（`POST /api/executions/{id}/reject` 直调 `failExecution` 无归属校验）。`[审计报告]`

### 大白话
工作流每次执行都会留日志（谁触发的、跑了什么节点、出错信息、输入参数）。查日志和「驳回执行」这两个接口**没校验这日志是不是你的**——只要登录，拿别人的 workflowId 或执行 id 就能看/能操作。

讽刺的是，**同一个 controller 的其他接口（approve/retry）做对了**归属校验，就这两处漏了，属于复制粘贴时漏改。

### 攻击案例
**案例 A（偷看）**：黑客调 `GET /api/executions?workflowId=88`（88 是别人的工作流），服务器只按 workflowId 查 → 返回别人全部执行日志，含 `triggeredBy`、节点输入（可能含敏感参数）、错误堆栈。

**案例 B（破坏）**：黑客看到别人有个审批节点正在等批，调 `POST /api/executions/{别人的id}/reject` → 服务器直接 `failExecution` 把它标记失败，**别人的工作流被强行打断**。

### 修法
1. `listByWorkflowId` → 改调带 `userScope` 的版本，service 内追加 `triggeredBy` 过滤（admin 传 null）。
2. `reject` → 先 `getVisibleExecutionLog(id, userScope)` 校验归属，再 `failExecution`。

### 验证（修复后）
- 用户 A 查 B 的 workflowId → 返回空或 403。
- A reject B 的执行 → 403。

## 漏洞 5 · 文件下载 IDOR（本审计起点）

**定位**：`GET /api/files/{fileId}` [FileController.java:31](../../../backend/src/main/java/com/superprogrammer/file/controller/FileController.java#L31) + [FileStorageService.java:61](../../../backend/src/main/java/com/superprogrammer/file/service/FileStorageService.java#L61) `load()` 零归属校验。`[已核实]`

### 大白话
平台上传的文件（知识库文档、Excel、附件）每个有个 fileId。下载接口**只认 fileId 不认人**——谁拿到 fileId 就能下，不问这文件是不是他的。fileId 是 UUID 不可猜，但会从分享链接、浏览器历史、日志、网络抓包里泄露。

### 攻击案例
用户 B 上传了 `财务报表.xlsx`，系统返回 fileId `abc123.xlsx`。这个 fileId 出现在某次分享链接 / 日志 / B 的浏览器历史里，被用户 A 看到。A 直接调 `GET /api/files/abc123.xlsx`，带自己的登录 token → 服务器不查归属，直接把 B 的财务报表字节流返回 → A 下载到 B 的文件。

### 修法
见《Excel 多 Sheet 导入设计》§10：新增 `stored_files` 表记 owner，`load(fileId, userId)` 强校验归属（单一咽喉点），`FileController.get` 改调带 userId 版本。

### 验证（修复后）
- A 用 B 的 fileId 调下载 → 403。

## 漏洞 6 · 聊天/记忆原文大面积落 INFO 日志

**定位**：
- [AgentRoutingStrategy.java:35](../../../backend/src/main/java/com/superprogrammer/engine/strategy/AgentRoutingStrategy.java#L35) `log.info("..., message={}", userMessage)` 打印**完整聊天原文**
- [MemoryService.java](../../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 105/159/197/274/304/325/330/462 多处 `log.info` 打印抽取出的记忆事实（`facts={}`、`value={}`、`首条[{}]`）
- [MemoryBlockClassifier.java:35](../../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryBlockClassifier.java#L35) 打印 `key:value` 记忆原文
- [MemoryConflictJudge.java](../../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 多处打印 LLM 抽取结果

`[审计报告]`

### 大白话
日志本来是给开发排查问题用的。但代码把**用户聊天的完整内容**和**系统从聊天里抽出来的记忆**（这两样是高敏感 PII）按 INFO 级别写进了日志文件。任何能看日志的人——运维、SRE、日志平台管理员、甚至日志被采集到第三方平台——都能直接读到所有用户的私聊和记忆。

### 攻击案例
用户在聊天里输入「我的银行卡号是 6228...，密码是...」。系统抽取出这条记忆存进个人记忆库，同时 [MemoryService](../../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 的 `log.info("facts={}", facts)` 把「银行卡号 + 密码」原样写进 `app.log`。运维同事查日志时一眼看到；若日志接了 ELK/云日志服务，第三方也能检索到。

### 修法
1. 这类日志统一降级为 DEBUG，生产默认不开。
2. 必须记的，脱敏：只记长度/hash/id，去掉 `value`/`facts` 对象/正文明文。
3. 日志平台对 chat/memory 模块的日志设访问 ACL。

### 验证（修复后）
- 生产日志 level=INFO 时，grep 银行卡号/聊天正文 → 0 命中。

## 漏洞 7 · 异常内部 message 透出客户端

**定位**：
- [GlobalExceptionHandler.java:64-74](../../../backend/src/main/java/com/superprogrammer/common/exception/GlobalExceptionHandler.java#L64) 兜底把 `e.getMessage()` 截断 300 字返回客户端
- [ChatWebSocketHandler.java:70,86](../../../backend/src/main/java/com/superprogrammer/chat/websocket/ChatWebSocketHandler.java#L70) `sendError("执行失败: " + error.getMessage())`
- [ChatController.java:159](../../../backend/src/main/java/com/superprogrammer/chat/controller/ChatController.java#L159) SSE `StreamEvent.error(ex.getMessage())`

`[审计报告]`

### 大白话
程序出错时，原始错误信息可能含数据库 SQL、表名、Java 类名、文件路径、堆栈——这些都是给开发看的内部细节。直接塞给前端，等于给黑客递情报：他知道了你的表结构、用了什么库、文件长啥样，就能针对性地构造下一步攻击。

### 攻击案例
黑客故意构造一个畸形请求触发数据库异常。服务器返回 `{"code":500,"msg":"ERROR: relation \"users\" does not exist\n..."}` —— 黑客从报错里知道了用户表叫 `users`、用的是 PostgreSQL、甚至 SQL 片段。结合漏洞 2 拿到的 DB 密码，精准拖库。

### 修法
1. 兜底分支固定返回「服务器内部错误」，`e.getMessage()` 只写后端 `log.error`。
2. WS/SSE 错误通道同样改固定话术。
3. 业务异常（`BusinessException`）可保留业务 message（那是受控的）。

### 验证（修复后）
- 触发 NPE/SQL 异常 → 客户端只收到「服务器内部错误」，无表名/类名。

## 漏洞 8 · Agent 读端点缺权限注解 + prompt 回显

**定位**：[AgentController.java:36-66,113-120](../../../backend/src/main/java/com/superprogrammer/agent/controller/AgentController.java#L36)（`GET /api/agents`、`/api/agents/{id}`、`/api/agents/{id}/skills`、`/api/skills/{id}`、`/api/agents/{id}/access`、`POST /api/agents/{id}/copy` 无 `@RequirePermission`）。`[审计报告]`

### 大白话
Agent 的「查看详情」接口没挂权限注解，只靠 service 层判断。问题在于详情里会返回 **prompt 模板**（Agent 的核心机密——它是怎么被调教的、系统提示词长啥样）。如果 service 的可见性判断有遗漏，任何登录用户就能尝试枚举别人的 Agent，偷看人家的 prompt。

### 攻击案例
公司 A 部门精心调了一个「销售话术 Agent」，prompt 里写满了话术策略。B 部门员工调 `GET /api/agents/{A的agentId}`，若 service 可见性收口不全 → 直接拿到完整 prompt → 抄走话术。

### 修法
1. 读类端点补 `@RequirePermission("agent:read")`。
2. service 层用 `AgentPermissionService.resolveAccess` 校验 canReadPrompt，非 owner/非授权用户遮蔽 prompt 字段。

### 验证（修复后）
- 非授权用户查他人 Agent → 拿不到 prompt 字段。

## 漏洞 9 · 开放注册无速率限制

**定位**：[AuthController.java:22-26](../../../backend/src/main/java/com/superprogrammer/auth/controller/AuthController.java#L22) `POST /api/auth/register` permitAll 开放注册，无速率限制/验证码/邀请码。`[审计报告]`

### 大白话
注册接口任何人都能无限调。黑客写个脚本，1 分钟注册一万个账号。每个账号都能用平台的 LLM 配额、记忆、知识库——等于白嫖资源、占满配额，还可能拿账号去当跳板利用漏洞 3 的 SSRF。

### 攻击案例
黑客脚本批量调 `/api/auth/register`（user1~user10000）→ 平台多出一万账号 → 每个都去配一个内网 endpoint 触发 SSRF（漏洞 3）→ 一万倍放大攻击面；或单纯烧光平台 LLM token 配额导致正常用户用不了。

### 修法
注册接口加速率限制（IP + 用户名维度），或改邀请码/管理员开通制。

### 验证（修复后）
- 同 IP 短时间注册超过阈值 → 429。

## 漏洞 10 · 删文档不清磁盘文件（数据残留）

**定位**：[KnowledgeDocumentService.java:93](../../../backend/src/main/java/com/superprogrammer/knowledge/service/KnowledgeService.java#L93) `delete()` 只删 DB 行 + nodes + 向量，**不删物理文件**；`FileStorageService` 无 `delete` 方法。`[已核实]`

### 大白话
用户删掉知识库里的文档，以为文件没了。实际上数据库记录删了，**原始文件字节还躺在服务器磁盘上**，没人清。时间一长，删掉的敏感文件（含 PII）全堆在硬盘里，谁有服务器访问权谁就能翻出来。

### 攻击案例
用户上传含身份证号的 Excel → 用完删掉 → 文件名从知识库消失，但 `uploads/workflow-inputs/abc123.xlsx` 还在磁盘。半年后服务器磁盘被备份/被运维拷走/被下线转卖 → 删掉的身份证号又泄露了。

### 修法
见《Excel 多 Sheet 导入设计》§10.5：`FileStorageService` 加 `delete(fileId)`，文档删除 / 解析完成后清字节。这也修了文件 orphan 泄漏。

### 验证（修复后）
- 删文档后，磁盘上对应 fileId 文件不存在。

## 漏洞 11 · `/ws/chat` permitAll 握手鉴权待确认

**定位**：[SecurityConfig.java:47](../../../backend/src/main/java/com/superprogrammer/auth/security/SecurityConfig.java#L47) `.requestMatchers("/ws/chat").permitAll()`，认证依赖 HandshakeInterceptor。`[审计报告-待确认]`

### 大白话
WebSocket 聊天通道在 SecurityConfig 里放行了，靠握手拦截器验 token。**但本次审计没深入 WsConfig**，不确定握手时是不是真验了 token、无效 token 是不是真拒绝了。如果握手拦截器有漏洞或没接上，匿名用户就能连聊天通道。

### 攻击案例（假设握手未验）
黑客不开 token 直接连 `ws://server/ws/chat` → 若握手拦截器没拦 → 连上聊天通道 → 冒充/监听。

### 修法
补查 `WebSocketAuthInterceptor` / WsConfig：握手阶段对 query token 做 JWT 校验，失败立即拒绝连接（返回 401，不升级 WebSocket）。

### 验证（修复后）
- 无 token / 错 token 连 ws → 握手被拒（HTTP 401，不升级协议）。

## 附：已核实干净的点（无需动）

- **密钥回传**：`LlmProviderVO`/`UserLlmProviderVO` 无 apiKey 字段；实体 `apiKeyEnc` 经 `AesEncryptService` 加密落库；只回 `hasApiKey` 布尔位。

- **多数按-id 端点**：KB/文档/节点/权限/记忆/用户级 provider 等均有归属校验（`canRead`/`canWrite`/`canManage`、userId 过滤、`@PreAuthorize`）。
