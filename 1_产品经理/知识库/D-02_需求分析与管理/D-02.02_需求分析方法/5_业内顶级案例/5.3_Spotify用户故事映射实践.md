# 5.3 Spotify 的用户故事映射实践

## 背景

Spotify管理着数千名工程师和数百个Squad（小队），需求规模远超一般公司。其需求分析的核心方法是**用户故事映射+持续交付**，确保大规模团队也能保持需求的全局一致性和局部敏捷性。[来源:Spotify Engineering Blog | 📚中 | 2019]

## 故事映射在大规模团队中的实践

### 三层故事地图

```
Level 1: 公司级故事地图（年度路线图）
  → 几十个Epics，按战略主题组织
  → 全公司可见，对齐方向

Level 2: Tribe级故事地图（季度计划）
  → 5-8个Squad共享的故事地图
  → 识别跨Squad依赖

Level 3: Squad级故事地图（迭代执行）
  → 精细到Story级别
  → 每日更新
```

### 跨Squad依赖处理

| 依赖场景 | Spotify的实践 | 效果 |
|---|---|---|
| 两个Squad做关联功能 | 共享故事地图节点+联合规划 | 避免接口不一致 |
| 一个Squad需要的API另一个Squad做 | API优先——先定义接口再实现 | 前后端不阻塞 |
| 三个以上Squad共享数据 | 数据契约——统一Schema定义 | 数据不冲突 |
| 不确定依赖的影响 | "3个Amigos"会——PM+Design+Tech一起看 | 早期发现依赖 |

## 故事映射的具体做法

### 骨干建立

Spotify的骨干不是"功能列表"，而是**听音乐的完整旅程**：

```
发现音乐 → 选择音乐 → 播放音乐 → 管理音乐 → 分享音乐
   │           │           │           │           │
 搜索      播放列表     播放控制     收藏库      社交分享
 推荐       排行榜       歌词显示     离线下载    协作列表
 浏览       Radio        队列管理     导入       演出信息
```

### MVP切片策略

Spotify的MVP不是"功能最少"，而是**旅程最短**：

| 切片 | 包含 | 不包含 | 验证假设 |
|---|---|---|---|
| MVP1 | 搜索→播放→收藏 | 推荐/社交/离线 | 用户愿意用流媒体替代下载吗？ |
| MVP2 | +推荐+Radio | 社交/协作 | 算法推荐能增加使用时长吗？ |
| MVP3 | +社交+协作 | — | 社交功能能提高留存吗？ |

## 故事映射如何发现遗漏

Spotify在故事映射中发现的典型遗漏：

| 遗漏 | 发现方式 | 影响 |
|---|---|---|
| "离线播放"场景遗漏 | 骨干"播放音乐"切片时发现——没网怎么办？ | 补充离线缓存Story |
| "多设备切换"场景遗漏 | "播放控制"行内发现——手机播到一半换电脑怎么办？ | 补充设备切换Story |
| "家长控制"角色遗漏 | 角色覆盖检查时发现——小孩怎么用？ | 补充家长控制Feature |
| "播客"活动遗漏 | 骨干只有"音乐"没有"播客" | 新增Podcast活动行 |

## PM收获

1. **故事映射的骨干=用户旅程，不是功能分类**——按"用户做什么"而非"系统有什么"组织
2. **MVP=最短可验证旅程，不是最少功能数**——验证假设才是目的
3. **大规模团队的依赖管理靠"共享节点"**——同一个Story出现在两个Squad的地图上
4. **遗漏在地图上自然暴露**——纵向看旅程完整性，比横向看需求列表有效得多
