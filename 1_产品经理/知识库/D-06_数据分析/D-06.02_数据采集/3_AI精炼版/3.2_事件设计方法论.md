# 3.2 事件设计方法论

## I.06 4W1H事件设计模型

[来源: 人人都是产品经理埋点系列, 2025 | 置信度:🔍高 | 2025-11]

### 五要素定义

| 要素 | 问题 | 埋点映射 | 示例 |
|---|---|---|---|
| **Who** | 谁做的？ | 用户ID/设备ID/用户属性 | user_id=U123, 会员等级=gold |
| **When** | 什么时候？ | 事件时间戳+上报延迟 | timestamp=2026-07-12T10:30:00 |
| **Where** | 在哪里做的？ | 页面路径/模块ID/来源 | page=商品详情, source=搜索结果 |
| **What** | 做了什么？ | 事件名+业务属性 | 事件=加购, 商品ID=P456, 价格=¥99 |
| **How** | 怎么做的？ | 操作方式/路径 | 入口=推荐位, 从首页→搜索→详情→加购 |

### 事件设计三原则

1. **面向业务而非面向UI**：事件名用"加购"而非"点击加购按钮"——UI会变但业务语义不变
2. **穷尽属性不多重复**：属性覆盖业务分析需要但避免冗余（如商品ID和商品名只需一个），名称可通过维度表关联
3. **层级语义统一**：事件名格式= `对象_动作`（如`product_addToCart`），全产品统一风格

## I.07 事件命名规范

### 推荐命名模板

```
[模块]_[对象]_[动作]
```

| 合规示例 | 不合规示例 | 原因 |
|---|---|---|
| product_detail_view | 点击商品详情 | 面向UI不面向业务 |
| order_pay_complete | 付钱 | 太笼统无法区分 |
| search_result_click | click_search | 风格不统一 |
| coupon_apply_submit | 优惠券 | 无动作、太模糊 |

### 属性设计规范

| 属性类型 | 规范 | 示例 |
|---|---|---|
| 标识属性 | 必传，用于关联和去重 | order_id, product_id |
| 分组属性 | 用于分组分析 | category, channel, platform |
| 度量属性 | 可用于聚合计算 | price, quantity, duration |
| 上下文属性 | 描述事件发生的环境 | referrer, ab_test_group, version |

### 属性数据类型

| 类型 | 说明 | 示例 |
|---|---|---|
| String | 文本类型 | product_name="iPhone 15" |
| Number | 数值类型 | price=6999 |
| Boolean | 布尔类型 | is_vip=true |
| DateTime | 时间类型 | register_time=2026-07-12 |
| Array | 数组类型 | tags=["新品","促销"] |

## I.09 从指标到事件的映射方法

业务指标 → 用户行为 → 埋点事件的推导链：

```
NSM: 月活跃买家购买次数
  → Output: 购买转化率
    → 用户行为: 浏览商品→加购→下单→支付
      → 埋点事件:
        product_detail_view(商品详情浏览)
        product_addToCart(加购)
        order_create(下单)
        order_pay_complete(支付完成)
```

**原则**：指标体系定义"看什么"，事件设计实现"怎么采集"——二者必须一一对应，否则指标无法计算。[来源: 数据采集最佳实践 | 置信度:📚中]

## B.01 核心路径优先级

埋点不可能一步到位，按优先级分轮建设：

| 优先级 | 范围 | 典型事件数 | 时间 |
|---|---|---|---|
| P0 核心转化路径 | 注册→激活→付费→留存全链路 | 10~15个 | 第1周 |
| P1 关键功能模块 | 搜索/推荐/分享/客服等 | 15~30个 | 第2~3周 |
| P2 辅助分析场景 | 活动页/运营位/AB实验 | 20~50个 | 第4周+ |
