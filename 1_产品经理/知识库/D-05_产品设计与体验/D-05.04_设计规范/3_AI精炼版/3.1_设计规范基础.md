## 定义与边界

**设计规范（Design System）**：一套由设计令牌、组件库、模式库、原则文档和工具链组成的**可执行约束体系**，确保产品族在视觉、交互和代码层面的**一致性**与**可扩展性**。

> 严格区分：**Design System ≠ UI Kit**。UI Kit 是静态视觉素材包（色板/控件截图），Design System 是"活的约束"——含语义规则、版本管理、贡献机制与代码实现。 [来源:📚训练知识 | 置信度:🔍高]

### 核心价值三角

| 价值维度 | 说明 | 量化指标 |
|---|---|---|
| 一致性 | 同品牌跨产品体验统一，减少用户认知成本 | 设计偏差率 ↓30~50% |
| 效率 | 复用代替重造，设计→开发交接时间缩短 | 设计→开发周期 ↓40~60% |
| 可扩展性 | 新功能/新业务线快速接入，无需重新造轮子 | 新页面搭建时间 ↓50~70% |

[来源:Nathan Curtis "Design Systems" 2024 再版数据 | 置信度:📚中]

### 边界（不是什么）

- ❌ 不是静态样式文档：必须有代码实现与工具链绑定
- ❌ 不是一人维护的UI Kit：必须有多角色贡献模型
- ❌ 不是一次交付品：必须是持续演化的活体系
- ❌ 不是设计独占物：PM/开发/QA都是使用者和贡献者

### 常见误区

| 误区 | 真相 | 典型后果 |
|---|---|---|
| "先做全再做产品" | 应随产品渐进而生长 | 耗时数月建规范，上线即过时 |
| "规范=限制创意" | 规范释放创意到高阶问题 | 基础决策反复做，无精力创新 |
| "一个人维护就够了" | 核心团队+外围贡献者生态 | 维护者离职=规范死亡 |
| "规范取代设计决策" | 规范覆盖80%常规，20%需设计判断 | 过度一致，产品失去个性 |
| "令牌=变量命名" | 语义令牌承载决策意图，不仅是别名 | 改主色要改200处而非1处令牌 |

### 核心术语

| 术语 | 定义 | 示例 |
|---|---|---|
| Design Token | 设计决策的最小可编程单元（名=值+语义） | `color-brand-primary: #1677FF` |
| 语义令牌 |携带使用意图的令牌（区别于原始值令牌） | `color-interactive-primary` → `color-brand-primary` |
| 组件（Component） | 可复用的UI单元（含视觉+交互+代码） | Button、Modal、DatePicker |
| 变体（Variant） | 同一组件的视觉/行为维度变化 | Button: primary/secondary/ghost |
| 模式（Pattern） | 解决特定UX问题的组件组合 | 表单校验模式、空状态模式 |
| Schema-As-Code | 设计规范以机器可读格式（YAML/JSON）定义的范式 | Figma Variables + Token Studio 导出 |
