## 本轮范围：WP1 Step3（C1 关联建议）

### RelationSuggestionWorker（`knowledge/relation/RelationSuggestionWorker.java`）

- **数据源**：`rag_retrieval_logs.evidence_l2`——SUPPORTED 且证据非空的近窗口 trace（默认 14 天，`suggestionLookbackDays`）；cursor 分批（id > cursor，LIMIT 500）防大表一次性载入
- **统计**：每条 trace 证据行抽 documentId 去重（TreeSet 升序）→ 两两无序对组合，a<b 规范化（对齐 ck_kdrs_pair）；脏 JSON 跳过该条不阻断
- **过滤链**：文档批查存在性（逻辑删缺席）→ 同库限定（跨库对丢弃）→ 共现 ≥ `suggestionMinCoRecall`（默认 3）→ 已有边（四类型任一、任一方向，单 SQL 双向 IN）跳过 → 既有建议行 ADOPTED/IGNORED 占位跳过（不重提）、PENDING 续算（count/样本 hash/lastSeen 刷新）
- **写法**：只建议绝不自动建边；upsert 按 uq_kdrs(kb,a,b) 兜底并发/重跑；@Scheduled 每日 03:17（避开整点），`run()` public 供测试/运维手动触发；catch-all 错误日志（不影响主链，次日重试）
- **开关**：`rag.recall.relation.suggestion-enabled`（关 → 不再生成新建议；已有建议照常可采纳/忽略）

### RelationSuggestionService（`knowledge/relation/RelationSuggestionService.java`）

- **listByKb**：仅 canManage（建议页是治理视图）；PENDING 按共召回次数降序；批量标题防 N+1；悬挂建议（任一端已删）过滤
- **adopt**：委托 `DocumentRelationService.create` 复用六路校验——建议流不能绕过建边不变式；方向由 fromDocId（必须 ∈ {docIdA, docIdB}）+ relationType 四选一指定；建议生成后手动建过边 → 采纳遇「已存在」按成功收口；置 ADOPTED
- **ignore**：置 IGNORED，worker 不再重提该对
- **建议行不物理删**（偏离 plan 原文「删建议」）：状态位占住 uq，等价防重 + 留审计痕迹
- **幂等门**：仅 PENDING 可操作，已处理 → BAD_REQUEST「建议已处理」

### Controller（`KnowledgeRelationController` 扩展，Step3 三端点）

- GET `/api/knowledge/relations/suggestions?kbId=`（knowledge:write）
- POST `/suggestions/{id}/adopt`（knowledge:write + @AuditLog kb_relation_suggestion_adopt，body=RelationSuggestionAdoptRequest{fromDocId, relationType, note≤200}）
- POST `/suggestions/{id}/ignore`（knowledge:write + @AuditLog kb_relation_suggestion_ignore）
- Service 层逐请求 canManage 复核（Controller 注解仅粗档位，同 Step1 惯例）
