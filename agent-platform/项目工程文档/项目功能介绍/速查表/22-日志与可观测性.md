# 22 - 日志与可观测性

## 功能简介
后端日志输出策略：控制台 + 全量文件 + ERROR-only 文件三通道；MyBatis SQL 走 slf4j 可分级过滤（治刷屏）；记忆/LLM 关键链路 INFO 可观测。线上问题审查靠文件，快速翻障靠 ERROR 文件。

## 配置位置

### 后端
- Logback 配置：[logback-spring.xml](../../backend/src/main/resources/logback-spring.xml)（三 appender，接管 Spring 默认）
- 级别 + 文件名：[application.yml](../../backend/src/main/resources/application.yml) `logging.*`
- MyBatis SQL 走 slf4j：`mybatis-plus.configuration.log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl`

## 三 appender

| Appender | 输出 | 级别 | 滚动 |
|---|---|---|---|
| `CONSOLE` | 控制台（彩色） | INFO+ | — |
| `FILE` | `${LOG_FILE}`（默认 `logs/agent-platform.log`） | INFO+（全量审查） | 50MB × 30 天 × 上限 2GB |
| `ERROR_FILE` | `${ERROR_LOG_FILE}`（默认 `logs/error.log`） | **ERROR only**（`ThresholdFilter`） | 20MB × 30 天 × 上限 1GB |

- 路径可用环境变量覆盖（见 [99-部署要求](99-部署要求.md) §八）：`LOG_FILE` / `ERROR_LOG_FILE`。
- 日志级别由 `application.yml` `logging.level.*` 驱动（Spring Boot 应用层覆盖，XML 不重复声明 logger 级别）。

## 日志级别策略（application.yml）

| 包 | 级别 | 理由 |
|---|---|---|
| `com.superprogrammer` | INFO | 保留业务关键链路（记忆/LLM/RAG），砍 DEBUG 噪声 |
| `com.superprogrammer.*.mapper`（5 个 mapper 包） | WARN | **SQL（DEBUG）不刷屏**。调试某 mapper 时单降该包到 DEBUG |
| `org.apache.ibatis` | WARN | MyBatis 自身日志降噪 |
| `org.springframework.security` | INFO | 砍「Securing GET / Set SecurityContextHolder」每请求一行 |
| `org.springframework.web` | INFO | 请求分发降噪 |

> **历史坑**：曾用 `mybatis-plus.configuration.log-impl: StdOutImpl` → SQL **绕过 slf4j 裸打 stdout**，不受级别控制，`IndexJobWorker` 每 5s 轮询 SQL 刷屏。改 `Slf4jImpl` 后 SQL 进 slf4j，按 mapper 包名 WARN 即静默。

## 正常背景噪声（不是 bug）
- `SELECT ... knowledge_index_jobs ... FOR UPDATE SKIP LOCKED`（Total: 0）每 5s 一次 = [IndexJobWorker.poll()](../../backend/src/main/java/com/superprogrammer/knowledge/service/IndexJobWorker.java) 认领 RAG 索引队列（`knowledge.index.poll-ms:5000`）。队列空也照打，`Total: 0` 为正常。详见 [14-知识库RAG-基础](14-知识库RAG-基础.md)。
- 改 `Slf4jImpl` + mapper WARN 后此噪声已消除。

## 关键可观测日志（排查用）

### 记忆管线（[09](09-个人记忆与冲突解决.md)）
- `processMemory userId=... 抽取facts=...` / `processFacts ...` — 抽取入口
- `记忆抽取失败: ...` — extract 异常被吞（[MemoryService.extractFacts](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) catch）→ 记忆静默不落库
- `记忆注入 userId=... mode=... → 注入N字符 / 不注入` — 注入分流结果
- `applyClean 细化更新/失败 key=...` — 写库结果
- `LLM调用 model=doubao-seed-2.0-code provider=...` — 记忆 judge 模型调用
- `没有找到支持模型 'doubao-seed-2.0-code' 的Provider` — 云端缺 chat provider（记忆静默失败主因之一）

### LLM（[18](18-LLM供应商与网关.md)）
- `LLM调用失败 [provider=...]` / `embedding 调用失败` — provider 调用异常（WebClient 超时已修复：10s connect + 30s response，见 [RB-001](../项目漏洞核查/运行时bug.md)；超时异常会以 `LLM调用失败` 落日志）

## 排查命令（线上）

```bash
# 快速翻障（只看 ERROR）
tail -f logs/error.log

# 发条消息后看记忆走到哪步
grep -E "processMemory|记忆抽取失败|记忆注入|LLM调用|applyClean|没有找到支持模型" logs/agent-platform.log

# 看 Tomcat 线程是否被打满（io-8080-exec-N 的 N 逼近 200 = 线程耗尽）
grep -oE "io-8080-exec-[0-9]+" logs/agent-platform.log | sort -u | tail

# 临时调试某 mapper SQL（不改全局）：把 application.yml 对应 mapper 包降到 DEBUG 后重启
```

## 已知相关缺陷
- [RB-001 死亡螺旋](../项目漏洞核查/运行时bug.md)：LLM WebClient 无超时 → 线程挂死 → 记忆空 + 轮询超时风暴。**根因 P0（WebClient 超时）与 P1（前端连续超时判定）均已修复入码，待上云验证**；残留 P1 为 LlmGateway 有界重试/熔断。日志配置本身不是根因，但降噪后能看清 RB-001 的真实错误（之前被 SQL 刷屏淹没）。

## 前端
前端日志走浏览器 devtools console，无文件落盘。Axios 错误经 [request.ts](../../frontend/src/api/request.ts) 拦截器统一 `useMessage().error` 弹出（4s）。
