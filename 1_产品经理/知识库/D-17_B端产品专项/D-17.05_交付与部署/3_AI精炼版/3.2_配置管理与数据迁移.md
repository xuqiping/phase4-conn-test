# 3.2 配置管理与数据迁移

## 一、配置化管理方法论

### 配置化的4层模型

| 层级 | 内容 | 实现方式 | PM角色 |
|---|---|---|---|
| **L1 字段配置** | 表单字段增删改、必填规则、默认值 | 后台配置界面 | 定义配置能力边界 |
| **L2 流程配置** | 审批流、状态机、业务规则引擎 | 可视化流程编排 | 设计规则引擎灵活度 |
| **L3 权限配置** | 角色权限、数据权限、字段权限 | RBAC/ABAC模型 | 设计权限模型粒度 |
| **L4 界面配置** | 布局、主题、菜单、Portal | 主题引擎+拖拽布局 | 定义可配置范围 |

**设计原则**：能配置不定制。每多一个配置点，意味着少一个定制需求。但配置能力本身也是开发成本——需在"配置灵活度"与"开发ROI"间权衡。 [来源:配置化设计原则 | 📚中]

### 定制vs配置决策树

```
客户需求
  ├─ 产品标准功能能覆盖？ → 走标准功能（L1）
  ├─ 不能覆盖，但能通过配置实现？ → 走配置（L2-L4）
  ├─ 配置无法实现：
  │   ├─ 该需求是否多客户共性？ → 纳入产品路线图（未来L1），当前临时定制
  │   ├─ 仅该客户独有？
  │   │   ├─ 客户付费覆盖定制成本？ → 走定制（L3），签CR
  │   │   └─ 客户不付费 → 拒绝或替代方案
```

**定制审批的3条红线**（PM必须把关）：
1. 定制改动核心架构 → 拒绝（影响所有人）
2. 定制不可维护/不可升级 → 拒绝（技术债）
3. 定制ROI为负（维护成本>客户付费）→ 拒绝（亏本生意）

### 配置漂移（Configuration Drift）管理

多环境（Dev/Test/Staging/Prod）间的配置不一致是B端交付高频事故源：
- **预防**：配置即代码（Config as Code），所有配置变更走版本管理，环境间通过流水线同步
- **检测**：定期配置对比（diff），发现漂移立即告警
- **修复**：以生产环境为基准，其他环境对齐

[来源:配置管理实践 | 📚中]

## 二、数据迁移方法论

数据迁移是B端交付最大风险源——**70%的交付延期与数据迁移有关**。 [来源:行业实施经验 | 📚中]

### 数据迁移5步法

| 步骤 | 活动 | 产出物 | 关键风险 |
|---|---|---|---|
| **① 数据调研** | 梳理源系统数据结构、数据量、数据质量 | 数据调研报告 | 调研不充分→迁移方案设计错误 |
| **② 数据清洗** | 去重、去脏、补全、标准化 | 清洗规则文档+清洗后数据集 | 清洗规则与客户对不齐→返工 |
| **③ 字段映射** | 源字段→目标字段的映射规则 | 字段映射表 | 映射歧义（一对多/多对一/无对应） |
| **④ 迁移执行** | 全量/增量迁移、校验 | 迁移执行报告 | 迁移中断/数据丢失/性能影响 |
| **⑤ 校验与确认** | 数据准确性校验、客户签字 | 数据验收单 | 校验不充分→上线后才发现错误 |

### 数据质量评估6维度

| 维度 | 含义 | 度量 |
|---|---|---|
| 完整性 | 必填字段是否缺失 | 缺失率<1% |
| 准确性 | 数据是否正确反映业务 | 错误率<0.5% |
| 一致性 | 多系统间同一实体数据是否一致 | 不一致率<2% |
| 唯一性 | 是否有重复记录 | 重复率<0.1% |
| 时效性 | 数据是否为最新状态 | 更新延迟<24h |
| 合规性 | 是否含敏感数据需脱敏 | 敏感字段100%脱敏 |

[来源:数据治理DAMA框架 | 🔍高]

### 数据映射的3类难点

1. **结构差异**：源系统是一张宽表，目标是多张关联表→需要拆分+关联关系重建
2. **枚举差异**：源系统"状态=A/B/C"，目标系统"状态=1/2/3/4"→需要枚举映射表，且需处理"源有目标无"的边界
3. **业务规则转换**：源系统没有某字段但目标系统必填→需要根据业务规则推导填充（如根据手机号推断归属地）

### 迁移策略选择

| 策略 | 适用场景 | 风险 |
|---|---|---|
| **一次性全量迁移** | 数据量小、可停机 | 迁移失败需全量回滚 |
| **分批迁移** | 数据量大、可按维度拆分 | 分批数据一致性 |
| **增量迁移+切换** | 不能长时间停机 | 切换窗口数据同步 |
| **双写过渡** | 零停机要求、核心系统 | 双写一致性+性能影响 |

### 回滚预案设计

数据迁移必须预设回滚方案：
- **快照回滚**：迁移前对目标库做快照，失败时恢复快照
- **标记回滚**：迁移数据打标记，失败时按标记批量删除
- **时间点回滚**：利用数据库PITR能力恢复到迁移前时间点
- **回滚决策机制**：PM+技术负责人+客户三方约定"什么程度的数据错误触发回滚"，避免现场犹豫不决
