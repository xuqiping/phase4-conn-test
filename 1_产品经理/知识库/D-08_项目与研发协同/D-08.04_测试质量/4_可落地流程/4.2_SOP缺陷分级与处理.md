# SOP：缺陷分级与处理

## 适用场景

所有软件缺陷从发现到关闭的全生命周期管理。适用于产品经理、测试工程师、开发工程师、项目经理共同遵守。

## 缺陷分级定义

### P0 — 致命缺陷（Blocker）

| 维度 | 定义 |
|---|---|
| 影响范围 | 核心业务流程完全中断，影响≥30%用户 |
| 典型表现 | 系统崩溃/数据丢失/支付失败/安全漏洞被利用/主流程100%不可用 |
| 用户体验 | 用户完全无法完成核心操作 |
| 举例 | 下单支付后订单消失；登录后白屏；用户数据被篡改 |

### P1 — 严重缺陷（Critical）

| 维度 | 定义 |
|---|---|
| 影响范围 | 核心功能严重受损或主要替代路径受阻，影响5%-30%用户 |
| 典型表现 | 核心功能异常但有替代路径/数据计算错误/重要非功能指标严重偏离 |
| 用户体验 | 核心操作体验严重退化，用户需绕路完成 |
| 举例 | 搜索结果排序错误；导出报表数据不完整；特定机型无法打开页面 |

### P2 — 一般缺陷（Major）

| 维度 | 定义 |
|---|---|
| 影响范围 | 非核心功能异常或核心功能轻微受损，影响<5%用户 |
| 典型表现 | UI错位/边界条件处理不当/操作效率降低/非关键数据展示异常 |
| 用户体验 | 不影响核心操作，但体验降级 |
| 举例 | 表单校验提示不清晰；特定浏览器下样式偏移；导出文件名乱码 |

### P3 — 轻微缺陷（Minor）

| 维度 | 定义 |
|---|---|
| 影响范围 | 极少数用户受影响，或仅影响体验细节 |
| 典型表现 | 文案错误/视觉微调建议/体验优化建议/极低概率触发 |
| 用户体验 | 几乎无感知或仅需轻微适应 |
| 举例 | 英文环境混入中文标点；帮助文档链接跳转偏慢；图标对齐差1px |

### P4 — 建议类（Trivial）

| 维度 | 定义 |
|---|---|
| 影响范围 | 无功能影响，纯优化建议 |
| 典型表现 | 交互优化/性能微调/代码可维护性/可访问性改进 |
| 用户体验 | 不影响使用 |
| 举例 | 增加快捷键支持；优化加载动画；改善色弱用户可读性 |

## 升级时间线

| 级别 | 响应时限 | 修复SLA | 验证SLA | 升级触发 |
|---|---|---|---|---|
| **P0** | 15分钟内确认 | 2小时内修复/缓解 | 修复后30分钟内验证 | 超1小时未修复→升级至VP级 |
| **P1** | 1小时内确认 | 24小时内修复 | 修复后4小时内验证 | 超12小时未修复→升级至Director级 |
| **P2** | 4小时内确认 | 当前迭代内修复 | 修复后8小时内验证 | 跨迭代未修复→纳入下迭代Must |
| **P3** | 24小时内确认 | 30天内修复 | 修复后24小时内验证 | 超30天→自动降级或关闭 |
| **P4** | 48小时内确认 | 纳入Backlog排期 | 修复后常规验证 | 超过90天未排期→关闭并记录 |

## 缺陷Triage会议流程

### 会议设置

| 项目 | 规范 |
|---|---|
| 频率 | P0/P1高发期：每日；常规期：每周2次（周二/周四） |
| 时长 | ≤30分钟 |
| 参与人 | PM + Tech Lead + QA Lead（≤5人） |
| 输入 | 新增未分级缺陷列表 + 待修复超SLA缺陷列表 |

### 执行流程

**阶段1：新增缺陷分级（15-20分钟）**

1. QA Lead逐条展示新增缺陷（标题+复现步骤+截图/录屏）
2. 三方快速对齐分级——
   - 分级一致→记录
   - 分级不一致→PM从业务影响角度裁决（1分钟原则，超时标"待定"）
3. 每条缺陷分配Owner + 预期修复时间

**阶段2：超SLA缺陷处置（5-10分钟）**

1. 过超SLA缺陷清单
2. 每条确认：卡在哪个环节？需要什么帮助？
3. 需要 escalation 的标注升级级别和目标接收人

**阶段3：遗留P2+审查（5分钟）**

1. 当前版本遗留P2+数量确认
2. 是否影响质量门判定？（→4.1 Agent质量门评估）
3. 下一版本修复计划确认

### Triage决策规则

| 场景 | 决策 |
|---|---|
| 修复成本高但影响小 | 降级（如P2→P3）或转需求 |
| 同一功能多个P3聚类 | 合并升级为P2 |
| 无法复现 | 标注"待复现"，保留7天，7天后无法复现→降级为P4 |
| 第三方依赖导致 | 标注"外部阻塞"，单独跟踪，不计入团队修复SLA |

## 缺陷生命周期

```
新建(New) → 已确认(Confirmed) → 处理中(In Progress) → 已修复(Fixed) → 验证中(Verifying) → 已关闭(Closed)
                                                    ↘ 无法复现(Can't Reproduce) → 已关闭
                                                    ↘ 延期(Deferred) → 重新打开(Reopened)
新建(New) → 非缺陷(Not a Bug) → 已关闭
新建(New) → 重复(Duplicate) → 已关闭
```

### 状态流转规则

| 转换 | 触发条件 | 执行人 |
|---|---|---|
| New → Confirmed | Triage会议确认分级 | QA Lead |
| Confirmed → In Progress | 开发开始修复 | 开发工程师 |
| In Progress → Fixed | 开发提交修复代码并自测通过 | 开发工程师 |
| Fixed → Verifying | 代码合入测试环境 | QA工程师 |
| Verifying → Closed | 验证通过（回归+原Case） | QA工程师 |
| Verifying → Reopened | 验证失败/引入新问题 | QA工程师 |
| Fixed → Deferred | 经Triage同意延期 | PM（业务权衡后） |
| New → Not a Bug | 确认为预期行为/配置问题 | QA Lead |
