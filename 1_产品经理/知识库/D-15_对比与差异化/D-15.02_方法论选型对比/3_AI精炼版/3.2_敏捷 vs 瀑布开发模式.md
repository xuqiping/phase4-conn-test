## 一、2种开发模式定义

### 瀑布开发（Waterfall）

**定义**：经典的线性开发模式，按"需求→设计→开发→测试→部署→维护"顺序推进，每个阶段完成后进入下一阶段，不可回溯。

**核心理念**：前期充分规划→按计划执行→最终交付。强调文档完整性、需求冻结、阶段验收。

**适用场景**：需求明确且稳定、合规要求高（金融/医疗/政府）、外包项目（需合同约束）。

### 敏捷开发（Agile）

**定义**：迭代式开发模式，将大项目拆分为多个短周期迭代（Sprint，通常1-4周），每个迭代交付可用的增量产品，持续收集反馈并调整方向。

**核心理念**：小步快跑→持续交付→快速反馈→拥抱变化。强调工作软件胜过文档、响应变化胜过遵循计划。

**适用场景**：需求不确定或快速变化、C端互联网产品、初创团队验证MVP。

## 二、6维深度对比

| 对比维度 | 瀑布 | 敏捷 |
|---|---|---|
| **开发节奏** | 一次性大版本（数月~年） | 短周期迭代（1-4周/Sprint） |
| **需求管理** | 前期冻结，变更走变更流程 | 持续演进，每个迭代可调整 |
| **文档密度** | 高（需求文档/设计文档/测试文档齐全） | 低（用户故事/看板/轻量文档） |
| **反馈时机** | 末期（用户在最终交付后才看到产品） | 早期+持续（每个迭代都有可演示的增量） |
| **风险控制** | 前期规划消除风险（但风险往往后期才暴露） | 持续反馈降低风险（早期发现问题早期调整） |
| **团队协作** | 职能分工明确（PM/设计/开发/测试各司其职） | 跨职能团队（共同负责交付） |
| **度量指标** | 里程碑完成率/缺陷密度 | 速率（Velocity）/燃尽图/迭代交付率 |
| **客户参与** | 前期需求+末期验收 | 持续参与（每个迭代评审） |

## 三、适用场景决策

### 瀑布更适合的场景

1. **需求高度确定**：如政府系统、银行核心系统——需求来自法规/标准，不会频繁变化
2. **合规/安全要求极高**：医疗设备软件、航空航天系统——需要完整的文档链和阶段验收
3. **外包/合同项目**：甲方需要明确的交付物清单和验收标准
4. **大规模基础设施**：如数据库迁移、系统升级——出错代价极高，需要前期充分验证

### 敏捷更适合的场景

1. **需求不确定**：C端互联网产品——用户需求在快速变化，需要持续验证
2. **MVP验证**：初创产品——需要快速验证假设，而非完美规划
3. **竞争激烈**：市场窗口短，需要快速迭代抢占先机
4. **技术探索**：AI/新技术产品——技术方案不确定，需要实验性开发

### 常见误区

| ⚠️误区 | ✅事实 |
|---|---|
| "敏捷=不要文档" | 敏捷是"刚好够用的文档"，不是无文档。关键决策和架构仍需记录 |
| "敏捷=不要计划" | 敏捷有计划（迭代计划/发布计划），只是计划更短周期、更灵活 |
| "瀑布=过时" | 瀑布在特定场景（合规/外包/基础设施）仍是最优选择 |
| "选了敏捷就不能用瀑布元素" | 混合模式（Hybrid）是大型组织的常态 |

## 四、混合模式（Hybrid）

### 瀑布-敏捷混合的3种常见形态

| 混合模式 | 结构 | 适用场景 |
|---|---|---|
| **瀑布式规划+敏捷式执行** | 前期用瀑布做整体规划和架构设计，执行阶段拆为敏捷迭代 | 大型产品开发：整体方向确定但功能细节需迭代 |
| **核心瀑布+边缘敏捷** | 核心系统用瀑布（合规要求），周边功能用敏捷 | 金融/医疗产品：核心交易用瀑布，运营/报表用敏捷 |
| **敏捷式规划+瀑布式发布** | 用敏捷迭代开发，但发布走瀑布式阶段审批 | B端SaaS：开发快速迭代，但客户升级需审批和排期 |

### 选型决策清单

- [ ] 需求是否高度确定且稳定？（是→倾向瀑布）
- [ ] 是否有严格的合规/审计要求？（是→倾向瀑布）
- [ ] 是否是外包/合同项目？（是→倾向瀑布）
- [ ] 是否需要快速验证用户假设？（是→倾向敏捷）
- [ ] 团队是否有敏捷经验？（否→先小范围试点）
- [ ] 产品是否是C端互联网产品？（是→倾向敏捷）
- [ ] 是否需要同时满足"规划确定性"和"执行灵活性"？（是→考虑混合模式）

## 五、Scrum框架速览（敏捷的主流实践）

| 元素 | 说明 |
|---|---|
| **角色** | Product Owner（需求优先级）+ Scrum Master（流程守护）+ Development Team（执行） |
| **事件** | Sprint（迭代）+ Sprint Planning（计划会）+ Daily Standup（站会）+ Sprint Review（评审会）+ Sprint Retrospective（回顾会） |
| **产物** | Product Backlog（需求池）+ Sprint Backlog（迭代需求）+ Increment（增量产品） |
| **核心指标** | Velocity（速率）= 每个迭代完成的故事点数 |
