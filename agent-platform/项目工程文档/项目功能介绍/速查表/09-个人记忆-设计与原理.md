# 09 - 个人记忆:设计与原理

> 从 [09-个人记忆与冲突解决.md](09-个人记忆与冲突解决.md) 拆出。本文件只收**算法 why / 数据模型设计**,速查(API/端点/设置 key)看主表,版本历史与待办看 [09-个人记忆-演进与待办.md](09-个人记忆-演进与待办.md)。

## 记忆检索模式总览

四模式,系统设置 `rag.memory.retrieval-mode` 切换:

| 模式 | 机制 | 召回方式 | 兜底 |
|---|---|---|---|
| **LLM_FULL_CONTEXT**(默认,向后兼容) | 全量 `confidence≥0.5` 灌入 | 无定向 | — |
| **EMBEDDING_VECTOR** | query → pgvector `<=>` top-K(`similarity≥0.35`,`LIMIT 5`) | 向量 | 无命中不注入 |
| **VECTOR_KEYWORD**(V31) | 向量 top-K ∪ 关键词(实体列) → 去重截断(`HYBRID_MAX=8`) | 混合 | 0命中 → LLM-key |
| **LLM_KEY**(V38,推荐) | 锚点语义两阶段:扩 query → anchor 向量+BM25 RRF → LLM 三维精排 | 锚点+精排 | 见下文 |

## 混合检索原理(VECTOR_KEYWORD,V31)

纯向量只看"表面语义像不像",不看"逻辑上相不相关"——"女儿3岁" embed 靠近 {年龄/儿童},"带女儿去玩" embed 靠近 {游玩/景点},余弦距离远 → 漏召。任何纯向量方案救不了,换 embed 模型也不行。

混合召回三段式([MemoryService.buildHybridContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)):
1. **向量 top-K**(既有链路,`findTopKByVector`)。
2. **关键词召回**([UserMemoryMapper.findByKeyword](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java)):query 分词(CJK 2-gram + 字母数字整段,[MemoryService.tokenize](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java),`KEYWORD_MAX=8`)→ ILIKE 命中 `entities::text` / `memory_key` / `memory_value` / `memory_key_zh` / `block_label`(五列并查,无 top-K LIMIT,仅 LIMIT 200 防病态)。**per-block_label 阈值筛选**([MemoryService.applyKeywordPerBlockThreshold](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)):按 block_label 分组,各组各自阈值 N(设置 `rag.memory.keyword-per-block-threshold`,默认10,0=禁用);组内 ≤ N 全留,组内 > N 则命中 `entities`/`memory_key`/`memory_key_zh`(高优)的行不卡阈值全留、低优(`memory_value`/`block_label` 命中)补到 N。取代旧全局 LIMIT 10。噪声 gram(如"去玩")天然自滤——不是任何召回词子串就撞不上五列。
3. **并集 0 命中 → LLM-key 兜底**([MemoryService.filterRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) → [selectRelevantKeysBlocks](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java)):拉全部 clean 记忆,**一次 LLM 三维**(keys/keys_zh/blocks)挑相关,按选中 key 装载 value 注入。即"先加载标签→LLM 判→再加载内容"的正确落地,**仅漏召时触发,非常驻路径**(省 token+加速,不每轮加 LLM)。
- 任一子链路异常不致命:向量挂→仅关键词;关键词挂→仅向量;都空→兜底;兜底也空→不注入(return null)。
- LLM 兜底 prompt(`SELECT_KEYS_PROMPT`)召回优先("宁多选"),避免漏。

## 实体标签 + 召回词袋(V31/V32)

治"实体桥接"漏召:英文 `memory_key`(如 `child_name`)+ value 可能只是专名("啊闪"),桥接词"女儿"无处可搜 → query「带女儿去玩」0 命中(纯从 value 抽 entities 永远抽不到"女儿",因为 value 里没有)。

### 列
- `user_memories.entities` JSONB([V31 迁移](../../backend/src/main/resources/db/migration/V31__user_memories_entities.sql),可空,老行 NULL=仅参与向量)。
- `user_memories.memory_key_zh` TEXT([V32 迁移](../../backend/src/main/resources/db/migration/V32__user_memories_memory_key_zh.sql),可空)存中文主标签("女儿")。

### 写入
[MemoryConflictJudge.extract](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 顺带抽 key_zh + entities 召回词袋(**0 额外 LLM 调用**,复用既有 extract)。entities 四类 = ① key_zh 标签(必含)② 同义变体 1-3(女儿→孩子/小孩/闺女;公司→单位/企业)③ value 专名 ④ **所属类别泛称/上位词**(V38 F1/F2)。例 `value="啊闪" key=child_name key_zh="女儿"` → `entities:["女儿","孩子","小孩","啊闪",...]`。**角色词必含**(value 只有专名时从 key 语义补角色词+变体),否则 query 用称谓时召回不到。

### 上位词召回词袋(F1/F2)
9 类覆盖全部 block 标签,每类列 9 个 2+ 字上位词候选:配偶/孩子/父母/宠物→家人/家庭/亲属;公司/职位/单位→工作/职业/职场;过敏/病史/身高体重→健康/身体/体质;住址/城市/搬家→居住地/住址/居住;学校/专业/学历→教育/学历/学业;爱好/口味/运动→偏好/爱好/喜好;电话/邮箱/微信→联系方式/联系/通讯;收入/工资/房贷→财务/收入/资产;名字/年龄/生日→基本信息/个人/档案。**上位词至少 5 个、能多则多往 8-10 靠(上限 10),严禁单字**(单字不进 2-gram 分词召不回 + 高频噪声)。**EXTRACT_PROMPT(新对话)+ BATCH_ENTITIES_PROMPT(回填/重抽)两 prompt 同步此规则**。总词袋 `共 ≤20 个`(硬,`readEntities` 截断 20、每词 ≤8 字符)。改 prompt 后老数据吃新规则靠「重抽关键词」端点。

### 三列并查 + per-block 阈值(V34)
[findByKeyword](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) 搜 `entities::text OR memory_key OR memory_value OR memory_key_zh OR block_label`(五列并查),任一命中即召回。`memory_key` 让英文键(child_name)成召回锚点;`block_label` 让 query 命中信息块标签(如「家庭」)即召回整块记忆。per-block 阈值:按 block_label 分组各自阈值 N(默认10,0=禁用),组内 > N 时优先留高优(entities/memory_key/memory_key_zh 命中,不卡阈值),低优(memory_value/block_label)补到 N。

### 老数据维护(两个互补端点)
- **回填实体标签** `POST /api/system/settings/rag-memory/backfill-entities`(admin,`role:manage`)→ [MemoryService.backfillEntitiesAsync](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java):查 `entities IS NULL OR memory_key_zh IS NULL`(补 V31 老数据 + 回填过但缺 key_zh 的行),≤20 条/批 [batchExtractEntities](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 异步跑。幂等(空 entities→`[]`、空 keyZh→`""` 标记已处理),不 bump `updated_at`,进度日志 `memoryBackfill`。
- **重抽关键词** `POST /api/system/settings/rag-memory/reextract-entities`(admin,`role:manage`)→ [MemoryService.reextractEntitiesAsync](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java):全量重抽 entities([findAllMemories](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) 无 NULL 过滤)。保留 key_zh 不动、重 embed anchor;fail-safe 抽空保留旧 entities 防回归;不 bump `updated_at`;进度日志 `memoryReextract`。
- **排坑**:点完按钮后日志刷屏 `SELECT ... knowledge_index_jobs ... FOR UPDATE SKIP LOCKED` 是 [IndexJobWorker.poll()](../../backend/src/main/java/com/superprogrammer/knowledge/service/IndexJobWorker.java) 每 5s 认领 **RAG 索引队列**的正常背景噪声,**和记忆回填无关**。回填走独立线程 `memoryTaskExecutor`、前缀 `memoryBackfill`。验证:grep `memoryBackfill`——0 行打「无待回填行」,跑了打「待回填 N 行/chunk 完成/完成 X 行」;info 级,日志级别 ≥ WARN 看不到。

### 前端
记忆面板加「名称」列(key_zh)+「信息块」列(blockLabel)+「创建」列(createdAt)。

## 三维合并筛选(key × key_zh × block_label,一次 LLM,V38)

> 演进:单维 key 筛 → 双维度(key+block,2 次 LLM)→ **三维合并(key+key_zh+block,1 次 LLM)**。
> 入口 [MemoryService.filterRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) → `selectRelevantMemories`(三路径共用)+ [MemoryConflictJudge.selectRelevantKeysBlocks](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java)(一次 LLM 出 keys/keys_zh/blocks 三数组)。

**动机**:
- 单维 key 筛:同 key 多行重复刷 token + block 维未筛。
- 双维度 2 次 LLM:key 维、block 维分开调,多花一次 round-trip + token;且 LLM 只看英文 key+value,**看不到中文 key_zh**,英文名(`spouse_name`)语义弱时易漏选。
- 三维合并:① 一次 LLM 同时选 keys/keys_zh/blocks,**砍第二次调用**;② prompt 输入带 `妻子(spouse_name): 阿斐`(key_zh 进**选择**,不再只展示),LLM 一眼懂语义;③ 三维 AND 交集,key_zh 维对英文名弱场景双保险。

**三步(Java 剔重 + 1 次 LLM)**:
1. **剔重**:`distinct memory_key`(每行带 key_zh/value)+ `distinct block_label`(null→"")。
2. **一次 LLM 三选**:[selectRelevantKeysBlocks](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 灌 `key_zh(key): value` 列表 + block 列表 → 输出 `{"keys":[...], "keys_zh":[...], "blocks":[...]}`(召回优先,宁多选;prompt `SELECT_KEYS_BLOCKS_PROMPT`)。
3. **三维 AND 交集装配**:候选 = `memory_key∈keys 且 memory_key_zh∈keys_zh 且 block_label∈blocks` 的记忆行。key_zh 空白行(老数据无标签)通配通过该维,不误杀。
4. **注入收口**:只输出 **key(按 `key-language`:EN=memory_key / ZH=memory_key_zh / BOTH=中英并列)+ value**;`category`/`block_label`/`entities`/`confidence` 全丢。

**生效范围(三路径共用 `filterRelevantKeys`)**:
- **LLM_FULL_CONTEXT 超阈值两阶段**(本文下节)。
- **VECTOR_KEYWORD 0 命中 LLM-key 兜底**([buildHybridContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) → `llmFallbackContext`,共享同一筛,自动受益)。
- **LLM_KEY 模式 LLM 精排**([buildLlmKeyContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) step ③)。

**容错**:单次 LLM 失败/解析失败 → 不注入(`return null`,宁缺毋滥)。三维任一为空集 → AND 结果空 → 不注入。剔重 Java 端(`Stream`),不新增 DB 查询。

## 标签语言 + 全量超阈值两阶段(V33)

两个系统设置(均在 [RagMemorySettingsTab.vue](../../frontend/src/components/settings/RagMemorySettingsTab.vue),admin):
- **记忆标签语言** `rag.memory.key-language` = `EN`(默认,向后兼容) / `ZH` / **`BOTH`(中英双选)**。控**注入上下文里 key 的展示语言**——[MemoryService.formatLine](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java):EN 用 `memory_key`;ZH 用 `memory_key_zh`(空回退英文 key);**BOTH 中英并列** `memory_key_zh(memory_key)`(如 `女儿(child_name)`)。仅展示层,不影响 key 匹配/去重/冲突(始终用英文 `memory_key`)。
- **全量记忆阈值** `rag.memory.full-context-threshold` = int(默认 20,0=禁用)。仅 **LLM_FULL_CONTEXT** 模式生效:记忆条数 > 阈值 且 query 非空 → 不再全量灌 value,改**三维合并筛选**(上节)。省 token + 治联想泄漏。LLM 失败/三维均空 → 不注入(宁缺毋滥);query 空/未超阈值 → 走原全量。VECTOR_KEYWORD / EMBEDDING_VECTOR 已是定向召回,不受此阈值影响。
- 设置走 `system_settings` KV 表 upsert,**无需 Flyway 迁移**。VO/Request 加 `keyLanguage` + `fullContextThreshold` 两字段([RagMemorySettingsVO](../../backend/src/main/java/com/superprogrammer/system/dto/RagMemorySettingsVO.java))。

## 锚点语义召回(V38)

> 目标:百万 key 规模下治「纯向量/混合漏召」+ 预览透出召回全过程。阶段 A–D + F1/F2 已落地,E(联调)/F3-F4(backfill force + 联调)待续。详尽开发清单见 [09-个人记忆-优化升级开发落地](09-个人记忆-优化升级开发落地.md)。

### 数据层(V38 迁移 `V38__user_memories_anchor_recall.sql`)
- 召回锚点列:`anchor_embedding halfvec(2048)`(语义粗筛主通道)+ `anchor_tokens text` + `anchor_tokens_tsv tsvector GENERATED STORED`(BM25 通道,jieba 分词后空格串)。
- 索引:`idx_user_memories_anchor_hnsw`(halfvec 余弦 HNSW)+ `idx_user_memories_anchor_tsv`(GIN)。
- 锚点文本 = `block_label + memory_key_zh + memory_key + entities(展开)`([MemoryService.buildAnchorText](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java),null 安全),embed 模型同 value(`MEMORY_EMBED_MODEL`),**独立于 value embedding 不替代**。
- mapper([UserMemoryMapper](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java)):`findTopKByAnchor`(`anchor_embedding <=>` top-K)+ `findAnchorBm25`(`ts_rank(anchor_tokens_tsv, plainto_tsquery)`,带 `SCOPE_FILTER`)。`<=>` 须 XML 转义 `&lt;=>`。IT [UserMemoryMapperAnchorIT](../../backend/src/test/java/com/superprogrammer/chat/mapper/UserMemoryMapperAnchorIT.java) 9/9。
- 写入侧:applyClean / processFacts embed 段 / merge 同步落 anchor 两列(复用 embed 调用,0 额外 LLM)。

### LLM_KEY pipeline([MemoryService.buildLlmKeyContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java))
① [QueryExpansionService](../../backend/src/main/java/com/superprogrammer/knowledge/service/QueryExpansionService.java) 多 qHalf 扩 query → ② 每 qHalf `findTopKByAnchor` + `findAnchorBm25` → [RrfFusion](../../backend/src/main/java/com/superprogrammer/knowledge/service/internal/RrfFusion.java) 加权融合(向量 > 词法)→ 粗筛 top-N(默认 40)→ ③ LLM 三维精排(key × key_zh × block,[selectRelevantKeysBlocks](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) **一次调用**出三数组;`rerank` 可关跳③直注 top-N)→ ④ 注入选中 key+value → ⑤ [MemoryQueryCache](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryQueryCache.java).getRerankKeys 缓存(TTL 60s)。异常降级:扩展挂→单 qHalf;向量挂→仅 BM25;都空→`return null`(不回退全量)。

## 项目记忆 scope(V33,纯可见性标签)

引入「项目」概念:**总记忆(global) + 单独项目记忆**。对话可选 scope;**一条记忆可同时属多个 scope**(global + 多项目,多对多可见性);新事实落当前会话 project;用户可手动改记忆 scope 归属。老数据/老会话向后兼容(= 今天行为)。

> ⚠ V33 纯可见性标签模型**已被 V34 混合模型取代**(唯一索引 scope-orthogonal 但 dedup scope-filtered → 写目标切项目再添同 key 撞墙)。本节保留设计背景,V34 是当前态,见下。

### 锁定设计
1. **Project = 全新实体**,与 Agent 解耦。
2. **归属 = 私有 + 可共享**(`project_members`)。鉴权走 service(owner/member/admin),不用 `@RequirePermission`。
3. **Scope = 多对多可见性,非分区**。`user_memories.is_global` + 关联表 `user_memory_projects`。唯一索引 V29 `(user_id,memory_key) WHERE conflict_id IS NULL` **不动**(冲突按 user+key 在可见集判,与 scope 正交)。
4. **读/写分离**:
   - 读(注入)= 扁平对称开关集(`mem_include_global` 勾 + `mem_read_project_ids` 每项各勾)。三组合全支持:关总记忆只读项目 / 关某项目读其他 / 同开 global+多项目。
   - 写(新事实落点)= 单独 `session.project_id`(null=global)。
5. **新事实**:`is_global=(project_id==null)`;project 写目标 → 挂 `user_memory_projects`。

### 数据表([V33__project_memory_scope.sql](../../backend/src/main/resources/db/migration/V33__project_memory_scope.sql))
- `projects`(owner=created_by)。
- `project_members`(共享:role `OWNER/EDITOR/VIEWER`,UNIQUE(project_id,user_id))。
- `user_memory_projects`(memory↔project 多对多可见性标签,PK(memory_id,project_id))。
- `user_memories.is_global BOOLEAN NOT NULL DEFAULT true`(老行=今天行为)。
- `chat_sessions` 三列:`project_id`(写目标,NULL=global)/ `mem_include_global`(读开关,默认 true)/ `mem_read_project_ids BIGINT[]`(读开关)。

### 后端
- **Project 领域**:实体 [Project](../../backend/src/main/java/com/superprogrammer/project/entity/Project.java) / [ProjectMember](../../backend/src/main/java/com/superprogrammer/project/entity/ProjectMember.java);Mapper `ProjectMapper` / `ProjectMemberMapper`;DTO ProjectVO/ProjectCreateRequest/ProjectMemberVO/ProjectShareRequest;[ProjectService](../../backend/src/main/java/com/superprogrammer/project/service/ProjectService.java)(CRUD + 共享 + `canAccess`/`canManage`/`listAccessibleProjectIds`);Controller `/api/projects`。

### V33 抓出的 2 个生产回归(已修)
1. **[UserMemoryMapper](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) 向量查询 `<=>` 未 XML 转义**:`<script>` XML 模式下 halfvec 余弦算子裸 `<` 非法 → `SAXParseException` → bean 创建失败 → **整 ApplicationContext 启动崩**。修:4 处 `<=>` → `&lt;=>`。

## 项目记忆 home + 可见性混合(V34,取代 V33 纯可见性标签)

V33「一条记忆属多 scope」是可见性标签语义,但唯一索引 V29 仍 `(user_id,memory_key)` scope-orthogonal → **用户实测撞墙**:global 已有 `child_name`、写目标切到项目 1 再加女儿名 → INSERT 撞 `uk_user_memories_user_key_clean` 报「记忆写入失败:child_name」。根因:dedup 查询 scope-filtered(只看写目标 scope),但唯一索引无视 scope → 写目标看不到的老行把 INSERT 顶爆。用户需求 = **两件事都要**:① 每个项目独立存自己的 `child_name`(global/P1/P2 各一条共存);② 一条记忆也能跨项目共享。纯可见性标签模型(V33)和纯分区模型都只能满足其一 → 改**混合模型**。

### 两套正交概念
| 概念 | 列 | 管什么 |
|---|---|---|
| **home(写归属/唯一性槽)** | `user_memories.home_project_id`(NULL=global home) | key 在 `(user, home)` 内唯一;决定"能不能再插" |
| **可见性(读注入/共享)** | `is_global` + `user_memory_projects`(V33 既有,不动) | 决定"读时哪些 scope 拉它" |

一条记忆 = 恰好一个 home + 任意多可见性标签。
- **每项目独立**:`(home=NULL, key=child_name)` / `(home=P1, key=child_name)` / `(home=P2, key=child_name)` 三条不同 home → 唯一索引放行共存。
- **跨项目共享**:`(home=P1, key=child_name)` 想让 P2 也见 → `user_memory_projects` 加 P2 行;想让 global 也见 → `is_global=true`。home 仍只 P1 → 不与 P2-native 那条撞唯一约束。

### 读语义(确认方案 A,保持现状)
读侧零改动。`SCOPE_FILTER` 先按开关踢无关项目,剩的里面同 key 多条 → **全注入** LLM(global 一条 + 项目一条都进 prompt,符合"总记忆+项目记忆并存"心智,不项目级覆盖)。home 不参与读可见性过滤。

### 数据表([V34__user_memories_home_scope.sql](../../backend/src/main/resources/db/migration/V34__user_memories_home_scope.sql))
- `user_memories.home_project_id BIGINT NULL`(写归属;NULL=global home)。
- 删旧 scope-orthogonal 索引:`DROP INDEX uk_user_memories_user_key_clean`。
- 新 home-aware 唯一(`COALESCE` 解 PG NULL distinct 问题,-1 哨兵):
  ```sql
  CREATE UNIQUE INDEX uk_user_memories_user_key_home
    ON user_memories (user_id, memory_key, COALESCE(home_project_id, -1))
    WHERE conflict_id IS NULL;
  ```
- 回填:`is_global=true` 行 `home_project_id` 默认 NULL(无需动);`is_global=false` 行从 `user_memory_projects` 取首个 `project_id` 作 home(多挂取最小 id)。**坑(IT 抓出)**:回填 UPDATE 初版带 `m.deleted = 0` 过滤 → Flyway `42703` 炸(**user_memories 表无 `deleted` 列**——不走 BaseEntity 软删约定),整 ApplicationContext 起不来;删该过滤后通。
- `is_global`/`user_memory_projects`/`chat_sessions` 三列全保留(可见性 + 写目标 + 读开关,语义不变)。
