# 3.3 HITL 与状态管理与 Harness 工程

## 一、本碎片定位

本碎片把 D-24.04 的两个偏"治理"的子维度（HITL + 状态管理）和一个元理论（Harness 工程）合并讲，因为三者本质都是"用框架而非 prompt 管住 Agent"。错误恢复（3.2）解决"崩了怎么起来"，HITL/状态/Harness 解决"怎么不崩、崩了不丢、不犯大错"。

## 二、Human-in-the-Loop（HITL）三档

### 2.1 HITL 介入程度谱系

| 档位 | 名称 | 介入时点 | 典型场景 | PM 设计点 |
|---|---|---|---|---|
| L1 | **人工审核** | 输出后 | 内容生成（邮件/文案/代码 review） | 默认 Agent 跑完，人后置审；快但风险中 |
| L2 | **人工确认** | 执行前 | 不可逆操作（删数据/转账/发布/邮件发送） | Agent 到达 dangerous 动作前停下，等人点"批准"；中速但安全 |
| L3 | **人工接管** | 任务中 | 反复失败/越权风险/超出能力边界 | Agent 整个任务交给人处理；最慢但兜底 |

### 2.2 三档决策矩阵：可逆性 × 严重度

| | 可逆操作 | 不可逆操作 |
|---|---|---|
| **低严重度**（查询/读取/草稿） | 全自动，无需 HITL | L1 人工审核 |
| **中严重度**（修改数据/发内部消息） | L1 人工审核 | L2 人工确认 |
| **高严重度**（删数据/转账/发布/对外邮件/法律行为） | L2 人工确认 | L3 人工接管 |

[来源:腾讯云 HITL 设计 / CSDN Agent 护栏 | 🔍高 | 2026-06]

### 2.3 副作用分级护栏（Hook 强制执行）

副作用不是写在 prompt 里让 Agent "自觉"——prompt 约束 LLM 不可靠（DECO 实测 LLM 会偷懒/越权/失忆），必须代码层 Hook 确定性拦截：
- **可逆操作**：放行（查询/读取/写草稿）
- **不可逆操作**：Hook 拦截 + 弹人工确认按钮（删/改/发布/转账/对外发邮件）
- **高危操作**：Hook 直接禁用 + 升级人工接管（财务账户操作/法律行为/不可逆批量删）

DECO 三层 Hook 防护见本章第五节。
[来源:DECO 团队实践 / 网易《一文讲透 Harness Engineering》| 🔍高 | 2026-03]

## 三、状态管理

### 3.1 为什么要状态管理

长任务跑几十上百步，中间崩溃怎么恢复？答案是把状态持久化。状态管理决定三件事：（1）崩溃可恢复——从最近的 checkpoint 续跑；（2）多 Agent 共享——多个 Agent 共享一份文件系统状态；（3）上下文卸载——把大块上下文 dump 到文件释放 token。

### 3.2 文件系统持久化——最基础 Harness 原语

**Anthropic《长时运行 Agent 的有效线束》报告原话**：文件系统是最基础、最通用、最可观测的 Agent 状态原语，比数据库更适合 Agent。

理由：
- **可观测**：开发者直接看文件就知道 Agent 干了啥（数据库要看表）
- **可恢复**：crash 后从文件直接续（数据库要恢复事务）
- **便于多 Agent 共享**：多个 Agent 读写同一份文件即可（数据库要协调 schema）
- **天然支持 Compaction**：上下文 dump 到文件就是持久化

实践：Claude Code / Cursor / Manus 等主流 Agent 都把工作状态写成 markdown / json 文件（如 AGENTS.md / CLAUDE.md / Context.md），这是 2026 主流做法。

[来源:Anthropic《Effective Harnesses for Long-Running Agents》报告 | 🔍高 | 2026-06]

### 3.3 Checkpoint（检查点）

文件系统之外的精细化状态管理：每完成一个关键子任务，把 Agent 的（messages / plan / subtask_progress / tool_results）序列化成 checkpoint。崩溃后从最近 checkpoint 还原。LangGraph 的 checkpoint 机制是代表实现（语义基于文件系统）。

### 3.4 Compaction（上下文压缩）—— 对抗 Context Rot

**Context Rot（上下文腐烂）**：上下文窗口被填满后模型推理和任务完成能力会逐渐变差——不是断崖，是缓慢腐烂。第 50 次工具调用后模型开始"忘记"原始目标、重复编辑同一文件、绕圈。Vercel 减工具之所以能让准确率 80%→100%，本质就是缓解 Context Rot。
[来源:腾讯云 Harness 报告 / Anthropic Harness 报告 | 🔍高 | 2026-06]

**Claude Code 五层 Compaction 策略**（逐层升级）：
1. **工具输出大头尾保留**：工具返回大段文本时，保留头尾 + 中间用 "…（已省略 X 行）…" 占位
2. **历史消息分区总结**：把超阈值的历史 messages 用 LLM 总结成 1 段，替换原 messages
3. **状态 dump 到文件系统**：把已完成子任务的工具输出 dump 到 markdown 文件，prompt 里只留指针（"详见 state/阶段1.md"）
4. **AGENTS.md 记忆文件**：把全局约束/已完成项/未完成项/关键决策写成 AGENTS.md，每轮会话开头注入
5. **会话级 reset + Ralph Loop 注入**：上下文已彻底腐烂时，清空上下文，用 Ralph Loop 把"原始目标+已完成状态"压缩重注入，强制续跑（详见 3.2）

**Compaction 核心原则**：Compaction 不是为了"塞下"，是为了"保持推理质量"——200K 窗口在第 50 次工具调用后模型也变笨，必须主动卸载。

[来源:Claude Code 文档 / Anthropic Harness 报告 | 🔍高 | 2026-06]

## 四、Ralph Loop 的状态注入机制（与 3.2 联动）

3.2 讲了 Ralph Loop 是"钩子拦截退出 + 干净上下文注入原提示词强制续跑"。这里讲它和状态管理的关系：

- Agent 跑几十步后 Context Rot 严重，决定"退出"
- Ralph Loop Hook 拦截退出，从文件系统 / checkpoint 取出"原始目标 + 已完成状态 + 失败原因"
- 压缩成一段新 prompt
- 清空 Agent 上下文
- 注入新 prompt，Agent 续跑

**意义**：Agent 不再受限于单次会话上下文窗口——状态被外置到文件系统，可无限续跑。这是把长 Agent 从"单次会话极限"解放出来的关键工程。

[来源:GitHub Ralph Loop / 知乎 Loop Engineering | 🔍高 | 2026-06]

## 五、Hook 生命周期钩子 + DECO 三层防护

### 5.1 Hook 是什么

Hook 是在工具调用前/后/预完成/出错时插入的确定性代码逻辑——不依赖 LLM 自觉，框架层强行拦截。**prompt 是建议，Hook 是法律**。

### 5.2 生命周期常见 Hook 点

| Hook 点 | 触发时点 | 典型用途 |
|---|---|---|
| `pre_tool_call` | 工具调用前 | 参数校验 / 副作用分级拦截 / 权限检查 |
| `post_tool_call` | 工具返回后 | 结果 schema 校验 / 输出截断 / 敏感数据脱敏 |
| `pre_task_complete` | Agent 标记完成前 | checklist 验证 / 测试是否跑通 / 强制走完验证 |
| `on_error` | 出错时 | 结构化错误处理 / 升级恢复策略 |
| `on_exit_attempt` | Agent 试图退出时 | Ralph Loop 拦截 + 重新注入提示词 |
| `on_drift` | 反漂移检测触发 | 拦截重复调用 / 强制重规划 |

### 5.3 DECO 三层 Hook 防护

DECO 团队总结三层 Hook 护栏，覆盖 LLM 不可靠的三大症状：
1. **偷懒检测 Hook**：检测 Agent 是否"声称已完成但 checklist 没跑全"——`pre_task_complete` 时强制验证测试是否真的通过
2. **越权拦截 Hook**：`pre_tool_call` 时按副作用分级矩阵拦截不可逆操作，强制 HITL 确认
3. **失忆补偿 Hook**：上下文腐烂时（`on_drift` 触发）从文件系统/AGENTS.md 重注入关键状态

**核心命题（DECO 创始团队原话）**："prompt 管不住的，框架来堵。"

[来源:DECO 团队实践 / 网易《一文讲透 Harness Engineering》| 🔍高 | 2026-03] *（完整案例见模块5）*

## 六、Harness 工程元理论

### 6.1 Agent = Model + Harness

**Harness（线束）**：包裹在模型外面的执行系统总称——执行循环、工具调度、错误恢复、状态管理、HITL、Hook 护栏、Compaction 全是 Harness。2026-06 Martin Fowler 专门撰文提出 "Harness Engineering" 术语，Anthropic 同期发布《长时运行 Agent 的有效线束》报告。共识：**Agent 的可靠性 98% 来自 Harness，只有 2% 来自模型本身**。
[来源:Martin Fowler《Harness Engineering》/ Anthropic 报告 | 🔍高 | 2026-06]

### 6.2 三组铁证数据

- **LangChain**：不换模型只改 Harness，Terminal Bench 2.0 从 52.8% → 66.5%（排名前 30 外 → 前 5）
- **Vercel**：工具数 15 → 2，准确率 80% → 100%、Token -37%、速度 ×3.5——纯 Harness 调整
- **Claude Code**：SWE-bench 上模型决策逻辑只占 1.6%，剩下 98.4% 全是循环/Harness——模型只是 Harness 的"推理引擎"

三条数据共同证明：决定 Agent 长任务可靠性的是 Harness 不是模型。PM 不懂 Harness 工程=不懂 Agent 工作流设计，就只触到 Agent 的 1.6%，永远做不出生产级 Agent。
[来源:腾讯云 Harness / Anthropic Harness 报告 / Vercel 工程博客 | 🔍高 | 2026-06]

### 6.3 Bitter Lesson 的 Agent 版本

Rich Sutton 的 Bitter Lesson 在 Agent 工程的翻版：手工编码的"聪明"工作流逻辑会被新一代模型一次次摧毁（模型变强后手工护栏变成限制）。**Harness 必须保持轻量、可丢弃**——不要把太多业务智慧硬编码进 Harness，否则下次模型升级你的 Harness 反而拖后腿。

实践含义：
- 能让模型自己决策的别用 Hook 拦（Hook 只管安全底线）
- 能用通用模式的别用定制流程（ReAct/Plan-and-Execute 优先于自创流程）
- Compaction 策略要可热替换，新模型窗口变大就改策略

[来源:腾讯云 Harness / Anthropic 报告 | 🔍高 | 2026-06]

## 七、Harness 工程三原则总结

| 原则 | 含义 | 反例 |
|---|---|---|
| **框架优先于 prompt** | 可靠性靠 Hook/Compaction 框架，不靠 LLM 自觉 | 把"不要删数据"写进 prompt 期待 LLM 遵守 |
| **轻量可丢弃** | 别把业务智慧硬编码进 Harness | 把"什么邮件算重要"硬编码进 Hook |
| **文件系统优先** | 状态优先写文件，少用数据库 | 长任务全存数据库，崩溃后无法恢复 |
