# 已解决（2026-08-14）

## 1. 为什么rag检索要这么久 —— 已解释 + 两处真实性能修复

**耗时构成（Phase4/14x 实测，trace 逐段计量）**：

| 阶段 | 实测耗时 | 说明 |
|---|---|---|
| Query 向量化（qwen3-vl-embedding） | ~300ms | 必要开销 |
| 混合召回 + PG 复核 | ~150ms | 含权限/版本/Hash 复核 |
| qwen3-rerank 重排 | ~250ms | 专用模型，快 |
| **小计：纯检索** | **~0.7-2s** | 「检索调试」Tab 即此量级 |
| 事实提炼（glm-5.1） | 4-17s | **大头**：两次 LLM 生成调用之一 |
| 答案合成（glm-5.1） | 1-4s | |

**"久"的不是检索，是 Grounded Answer 的两次 LLM 调用**；且为保证引用经过校验，页面等完整答案生成后一次显示（不逐 token 展示未验证文本），体感更久。

**本轮顺带修掉的两个真实延迟/失败问题**：
1. 事实提炼 maxTokens=1200 被截断 → JSON 断尾报「未返回合法 JSON」（`RagConfig` 放宽至 3000）；
2. 无长度约束时 glm-5.1 对长证据逐条复述 → 输出 1200+ token，生成 >30s 撞超时（提炼提示词加强精简约束：只输出 JSON、value≤60字、只提关键事实）。修复后同类问题 4-8s 返回。

**想快的路径**：「检索调试」Tab 只跑检索不生成答案（~1-2s）。

## 5. L0 摘要和原文一样？L1/L2 是什么？参与检索吗？ —— 已解释（数据库实证）

三层语义（以差旅制度文档实测）：
- **L1 = 文档级摘要**：`SUMMARIZING` 阶段 LLM 生成，存 `knowledge_documents.l1_metadata`（summary/outline/importantRules）。你在检索调试看到的浓缩摘要就是它。**参与检索**（L1 摘要向量化粗筛 + 注入上下文）。
- **L0 = 章节级节点（SECTION）**：承载章节标题+聚合内容，用于结构层级与引用定位（如「第一章 报销标准」）。**当前不单独向量化**（实测 embed 数 L0=0）。
- **L2 = 段落级原文（PARAGRAPH）**：**核心检索单元**（实测 embed 数 L2=5/5，向量检索全部落在 L2）。

**为什么看起来 L0=原文**：本文档每章恰只有 1 个段落 → 章节聚合内容 = 该段落原文，属结构重合而非摘要失效；真正的摘要在 L1 层（对比 l1_metadata 的浓缩 summary 即可确认）。章节含多段落的大文档中 L0 会是整章聚合。

## 6. 一个问题涉及多条答案会怎样？能全召回吗？ —— 已验证（浏览器实测）

QueryPlan 按问题类型动态定证据预算：精确题 ~2 条、流程题 ~10 条、**列表/比较题最多 20 条**，且限制单一文档挤满上下文（来源多样性）+ 缺主题时补检索 1-2 轮（继承原权限/版本范围）。
实测「列出全部条款」：三章全部召回，逐条回答（机票/酒店/餐补/审批/时限/生效），引用 [1][2][3]，并自动做冲突核查说明（无冲突）。

## 7. 各反馈类型提交后会发生什么？ —— 已解释（代码实证）

提交 → `PENDING` 入待审核队列（**不直接改变线上排序/召回**）。管理员在反馈审核里一次性裁决：
- **通过（APPROVED）**：成为**黄金集候选**，供评测数据集（Recall/MRR/nDCG 与发布门禁）使用——影响的是下一轮 Pipeline 评测与灰度，不是即时排序；
- **拒绝（REJECTED）**：留档，不进黄金集；
- 状态只能从 PENDING 变更一次，防重复审核。
四种类型的语义：结果不相关（召回质量问题）/ 内容已过期（数据治理，提示更新文档版本）/ 引用错误（Citation 校验问题）/ 答案不完整（证据预算/补检索问题）。
