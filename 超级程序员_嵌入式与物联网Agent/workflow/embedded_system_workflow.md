# 嵌入式系统开发 Workflow

## Purpose

为嵌入式开发项目提供从芯片选型、硬件设计、固件开发、RTOS配置、通信协议集成到安全启动与OTA升级的完整执行路径。覆盖单片机（MCU）、ARM嵌入式、Linux嵌入式驱动、树莓派应用开发四大方向，支持用户根据项目需求选择合适的技术栈。

## Prerequisites

- 用户已明确项目目标（功能需求、性能指标、功耗约束、成本预算、量产规模）
- 用户已提供目标应用场景（消费电子、工业控制、汽车电子、医疗设备、智能家居等）
- 若涉及硬件设计，需确认是否已有PCB设计能力或外包计划

## Steps

### Step 1: 需求分析与架构选型

**Goal**: 确定处理器架构（MCU/ARM/Linux/树莓派）、核心芯片型号、操作系统层级，输出选型决策矩阵。
**Completion criterion**: 生成一份包含架构对比、芯片型号、理由说明的选型报告，经用户确认。

**A. 提取需求约束**
- 读取用户输入的性能指标（CPU频率、内存大小、外设接口数量）
- 提取功耗约束（电池供电/市电/能量采集，目标续航时间）
- 提取成本约束（单台BOM成本上限、量产规模）
- 提取安全合规要求（功能安全等级如ASIL、信息安全认证如PSA、行业编码规范如MISRA C）
- 提取实时性要求（硬实时/软实时/无实时要求）

**B. 架构选型决策**
- 若项目为低功耗传感器节点（电池供电、简单控制、无线通信）→ 选择 **MCU方向**（Cortex-M0+/M3/M4/M33/M55/M85或RISC-V）
- 若项目为中等复杂度嵌入式应用（RTOS多任务、丰富外设、边缘AI推理）→ 选择 **ARM Cortex-M/A方向**（Cortex-M7/M85/A53/A55/A76）
- 若项目为复杂多媒体/网络/AI应用（需要运行Linux、驱动开发、多核异构）→ 选择 **Linux嵌入式方向**（RK3588/i.MX8/全志/树莓派CM5）
- 若项目为快速原型验证或边缘AI部署（需要PoC到量产路径、社区生态丰富）→ 选择 **树莓派方向**（Pi 5/CM5/Pico 2）

**C. 芯片选型矩阵**
- 对每个候选芯片，评估以下维度并打分（1-5分）：
  - 性能（CoreMark/Dhrystone分数、AI算力TOPS）
  - 功耗（活动/睡眠/深度睡眠电流）
  - 成本（芯片单价+外围BOM成本）
  - 生态（SDK成熟度、IDE支持、社区活跃度、示例代码丰富度）
  - 供应链（供货稳定性、生命周期承诺、国产替代可行性）
  - 安全（TrustZone/安全启动/加密引擎/PSA Certified等级）
- 输出选型决策表，标注推荐芯片及备选方案

**D. 工具链与开发环境确认**
- IDE：Keil MDK / VS Code + ARM GCC / STM32CubeIDE / ESP-IDF / PlatformIO
- 调试器：J-Link / ST-Link / DAP-Link / OpenOCD
- 仿真/虚拟原型：QEMU / ARM Fast Models（Linux方向必备）
- 版本控制：Git + 子模块管理（SDK作为子模块引入，避免直接修改）

**输出物**: `选型报告_项目名称.md`，包含架构决策、芯片选型矩阵、工具链清单、风险提示。

### Step 2: 硬件设计与最小系统搭建

**Goal**: 完成硬件原理图设计和PCB Layout规划，搭建可调试的最小系统，通过硬件基础功能验证。
**Completion criterion**: 最小系统上电后，调试器可正常连接，芯片能进入调试模式，电源/晶振/复位三大基础信号测量通过。

**A. 最小系统设计**
- 电源设计：
  - 若电池供电 → 选择LDO（噪声低）或DCDC（效率高），计算功耗预算和续航时间
  - 若市电供电 → 设计AC-DC模块，预留EMI滤波和浪涌保护
  - 去耦电容策略：每个电源引脚"一大一小"（10uF+100nF）贴近放置
- 晶振设计：
  - 计算负载电容（CL = (C1*C2)/(C1+C2) + Cstray），确保晶振下方禁止走线
  - 若使用内部RC振荡器（如STM32 HSI），评估精度是否满足通信协议要求
- 复位设计：RC复位电路（典型R=10KΩ, C=100nF，延迟10ms），加手动复位按钮
- 调试接口：SWD（2线：SWCLK+SWDIO）优先，预留JTAG（5线）仅当需要Boundary Scan时

**B. 外设接口规划**
- 有线通信：UART（调试日志/Modbus）/ SPI（高速传感器/Flash）/ I2C（低速传感器/EEPROM）/ CAN（汽车/工业）
- 无线通信：BLE（低功耗短距离）/ Wi-Fi（高带宽）/ LoRa（远距离）/ Matter（智能家居）
- 模拟外设：ADC（传感器采集，注意参考电压稳定性）/ DAC（模拟输出）/ PWM（电机/LED控制）
- 数字外设：GPIO（通用IO，注意3.3V/5V电平转换）/ Timer（PWM输入捕获）/ DMA（大数据量传输免CPU干预）

**C. EMC与可靠性设计**
- PCB Layout：电源层和地层完整，高速信号线阻抗匹配，敏感模拟信号远离数字噪声
- EMC预合规：从设计阶段参考CISPR 32 / IEC 61000-4-x标准，预留EMI滤波和屏蔽位置
- 安全设计：高压隔离（光耦/数字隔离器）、ESD保护（TVS二极管）、过流保护（PTC/保险丝）

**D. 硬件验证**
- 上电测试：测量各电源轨电压（允许偏差±5%），示波器观察电源上电时序
- 晶振起振测试：示波器测量晶振波形，频率偏差<±50ppm
- 调试接口测试：连接调试器，确认可读取芯片ID、可单步执行
- 电流测量：活动模式/睡眠模式/深度睡眠模式分别测量，与功耗预算对比

**输出物**: `硬件设计文档_项目名称.md`（含原理图说明、PCB Layout要点、BOM清单、验证测试报告）。

### Step 3: 固件开发与RTOS配置

**Goal**: 完成底层驱动初始化、RTOS任务划分、应用逻辑实现，固件可通过编译并在目标硬件上运行。
**Completion criterion**: 固件成功烧录，RTOS多任务调度正常，关键外设驱动验证通过，无HardFault或Watchdog复位。

**A. 编程语言与规范**
- 若选择C语言 → 遵循MISRA C:2012规范（汽车/医疗/航空强制要求）
  - 所有硬件寄存器访问加`volatile`
  - 禁止动态内存分配（`malloc/free`），使用静态分配或内存池
  - 函数长度<60行，圈复杂度<10
- 若选择Rust语言（安全关键新驱动试点）→ 使用Rust for Linux（6.15+）或embedded-hal生态
  - 编译期消除Use-after-free/空指针/数据竞争
  - 注意：2026年Rust嵌入式仍处早期，生态成熟度评估为关键风险

**B. 启动代码与初始化**
- 启动流程：Reset Handler → 系统时钟初始化 → 外设时钟使能 → 堆栈初始化 → 跳转到main()
- 外设初始化顺序：GPIO → UART（调试用）→ Timer → 中断NVIC配置 → DMA → 通信外设（SPI/I2C/CAN）
- 时钟树配置：HSE外部晶振→PLL倍频→系统时钟，确保各总线时钟（AHB/APB）在规格范围内

**C. RTOS配置与任务设计**
- RTOS选型：
  - FreeRTOS（Cortex-M事实标准，40%+份额，生态最成熟）
  - Zephyr（增长最快，300+开发板，原生Matter支持）
  - RT-Thread（国产生态壮大，组件丰富）
  - 若Linux方向 → 使用PREEMPT_RT补丁（Linux 6.12主线化）或Xenomai双核方案
- 任务划分原则：按功能/优先级/执行周期拆分
  - 高优先级（1-10ms周期）：传感器采集、紧急中断处理
  - 中优先级（10-100ms周期）：数据预处理、通信协议栈
  - 低优先级（>100ms周期）：日志记录、状态机维护、UI更新
- 同步机制：
  - 队列（Queue）：任务间通信+天然同步+数据缓冲（首选）
  - 互斥量（Mutex）：共享资源保护，启用优先级继承防止优先级翻转
  - 信号量（Semaphore）：资源计数/事件通知
  - 事件组（Event Group）：多条件组合唤醒
- 内存管理：任务栈静态分配（`StaticTask_t`），启用栈溢出检测（Stack Overflow Hook）

**D. 中断与并发设计**
- ISR设计原则：尽可能短（<10μs），只做标志置位或数据入队，复杂处理延后到任务
- 中断优先级分组：抢占优先级+子优先级，确保关键中断不被延迟
- DMA双缓冲设计：解决数据生产与消费速率不匹配问题
- Cache一致性（Cortex-A/Linux方向）：DMA传输前后执行DSB+DMB屏障指令，或使用Non-cacheable内存

**E. 低功耗优化（电池供电项目）**
- 核心原则："能睡就睡、能慢就慢、能关就关"
- Tickless模式：RTOS空闲时关闭SysTick，进入睡眠/深度睡眠/待机模式
- 外设门控：不用的外设时钟全部关闭
- 实测各模式电流：活动模式、睡眠模式（CPU停外设运行）、深度睡眠（大部分时钟停）、待机（仅RTC运行）
- 能量采集评估：若适用，计算太阳能/振动/射频能量采集功率是否满足系统需求

**输出物**: `固件源码_项目名称/`（含启动代码、驱动层、RTOS配置、应用层、CMake/Makefile构建脚本）。

### Step 4: 通信协议集成与联调

**Goal**: 完成设备与外部系统（传感器、网关、云端）的通信协议集成，实现数据可靠收发。
**Completion criterion**: 通信协议栈编译通过，收发数据包抓包/逻辑分析仪验证正确，误码率/丢包率达标。

**A. 有线通信协议**
- UART：配置波特率（常用115200/921600）、数据位8、停止位1、无校验；用于调试日志和Modbus RTU
- SPI：配置CPOL/CPHA模式（与从设备匹配）、时钟频率（不超过从设备上限的80%）、CS片选控制
- I2C：配置时钟频率（标准100KHz/快速400KHz/高速3.4MHz），注意上拉电阻计算（典型4.7KΩ）
- CAN：配置波特率（工业常用250K/500K/1M），验收滤波器设置，注意终端电阻120Ω

**B. 无线通信协议**
- BLE：配置GAP角色（Central/Peripheral/Observable）、GATT服务与特征值、连接间隔与从机延迟（平衡功耗与响应）
- Wi-Fi：STA模式优先（节省AP资源），配置低功耗模式（DTIM间隔调整），注意FCC/CE/SRRC认证
- LoRa：配置扩频因子SF（高SF=远距离低速率，低SF=高速率低距离）、带宽BW、编码率CR
- Matter over Thread：使用Zephyr/FreeRTOS+Matter SDK，配置设备类型（灯/开关/传感器）、配网流程（QR码/手动配对）

**C. 网关/云端协议**
- MQTT：配置Broker地址（EMQX/HiveMQ/AWS IoT Core）、ClientID（唯一）、Topic分层命名（`/{product}/{device}/{type}/{action}`）、QoS策略（telemetry用QoS 0，控制指令用QoS 1，OTA用QoS 2）
- CoAP：适用于资源受限节点，配置Observe订阅、Blockwise分块传输
- HTTP/HTTPS：适用于非实时大数据上报，配置TLS 1.3证书链

**D. 协议联调与验证**
- 逻辑分析仪/示波器抓取物理层波形，验证时序（建立时间/保持时间/时钟边沿）
- 串口助手/Wireshark抓包验证数据帧格式和协议状态机
- 压力测试：连续发送1000包，统计丢包率（目标<0.1%）和延迟（目标<100ms）
- 异常测试：拔掉通信线→恢复→验证自动重连和断网续传

**输出物**: `通信协议配置文档_项目名称.md`（含协议参数表、抓包分析、压力测试报告）。

### Step 5: 固件安全与OTA升级

**Goal**: 实现安全启动、固件签名验证、加密OTA升级机制，确保设备在部署后的全生命周期安全。
**Completion criterion**: 安全启动验证通过（非法固件拒绝启动），OTA双分区升级成功且可回滚，通过PSA Certified Level 1或等效安全评估。

**A. 安全启动（Secure Boot）**
- 信任链构建：ROM Bootloader（信任根）→ 二级Bootloader → 应用固件，每级验证下一级的数字签名
- 签名算法：ECDSA P-256（资源受限设备）或 RSA-2048（性能充裕设备）
- 密钥管理：私钥存储在HSM离线环境，公钥哈希烧录到芯片OTP/efuse区域，量产锁定
- 防降级（Anti-rollback Counter）：版本号存储在防篡改区域，拒绝旧版本固件
- 调试端口保护：量产时通过芯片熔丝位永久关闭JTAG/SWD调试接口

**B. 加密与隔离**
- 若芯片支持TrustZone-M → 划分安全世界（密钥存储/加密运算）与非安全世界（应用逻辑）
- 若不支持TrustZone → 使用软件加密库（mbedTLS/TinyCrypt），AES-128-GCM加密敏感数据
- 安全存储：关键配置（Wi-Fi密码、MQTT证书）存储在芯片内部Flash的加密分区或外部SE安全芯片

**C. OTA升级方案**
- 分区设计：A/B双分区（运行区A + 更新区B），或三分区（A/B + 恢复区Recovery）
- 升级流程：
  1. 设备接收OTA manifest（含版本号、哈希、签名、差分包URL）
  2. 验证manifest签名合法性
  3. 下载差分包（Delta OTA可减少70-90%传输量）
  4. 写入更新区B，计算哈希验证完整性
  5. 原子切换启动标志到分区B
  6. 首次启动健康检查（看门狗+自检程序），失败则回滚到分区A
- OTA工具链：Mender（开源，支持A/B分区）、RAUC（Linux方向）、自定义Bootloader实现

**D. 安全测试**
- 篡改测试：修改固件一个字节，验证安全启动拒绝启动
- 回滚测试：刷入旧版本固件，验证Anti-rollback Counter拒绝
- 断电测试：OTA写入过程中随机断电10次，验证分区完整性检查和自动回滚
- 密钥提取测试：尝试通过调试接口/故障注入读取密钥存储区，验证保护有效性

**输出物**: `安全设计文档_项目名称.md`（含信任链架构、密钥管理策略、OTA流程图、安全测试报告）。

### Step 6: 边缘AI/TinyML部署（如适用）

**Goal**: 在MCU或边缘设备上部署量化后的AI模型，实现端侧推理，满足实时性和功耗约束。
**Completion criterion**: 模型成功部署，推理延迟和精度满足项目指标，功耗在预算范围内。

**A. 适用性评估**
- 若项目涉及模式识别（振动异常/语音唤醒/简单图像分类）且延迟要求<100ms → 进入TinyML流程
- 若项目需要复杂视觉推理（多目标检测/语义分割）→ 建议使用独立NPU芯片（Hailo-8L/地平线征程6）或树莓派+AI加速器方案

**B. 模型选型与训练**
- 时序异常检测：1D-CNN / LSTM / Autoencoder
- 简单图像分类：轻量CNN（MobileNetV3 / EfficientNet-Lite）
- 关键词唤醒：Depthwise Separable CNN + GRU
- 训练框架：TensorFlow / PyTorch → 使用项目采集的数据集训练，目标精度>90%

**C. 量化与转换**
- 训练后量化（PTQ）：权重从FP32→INT8，精度损失通常<1%
- 量化感知训练（QAT）：若PTQ精度损失过大，在训练过程中模拟INT8运算
- 模型转换：
  - STM32方向：STM32Cube.AI工具将TensorFlow/PyTorch模型→C代码
  - ESP32方向：ESP-DL库或TFLite Micro
  - 通用方向：TFLite Micro / ONNX Runtime / CMSIS-NN

**D. 部署与优化**
- 推理流水线：传感器采集→预处理（归一化/滤波/FFT）→模型推理→结果输出→动作触发/消息上报
- 内存优化：使用XIP（Execute In Place）从Flash直接执行模型，减少RAM占用
- 功耗优化：事件触发推理（只在检测到异常振动/声音时唤醒CPU），非连续运行

- 延迟验证：测量单次推理耗时（目标<50ms@MCU主频480MHz）
- 功耗验证：测量推理期间电流峰值，计算对电池续航的影响
