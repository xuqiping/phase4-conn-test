# 3.2 Computer Use 深度

## 一、Computer Use 本质与定位

**Computer Use（计算机操控）**：模型通过截屏识别界面 + 生成鼠标键盘指令（点击坐标/输入文字/按键），操控真实的计算机 GUI 界面。这是工具调用的"最后手段"——当目标软件没有 API 可用时，用 GUI 操控绕过接口层直接操作界面。

**与 Function Calling 的关键区别**：
- Function Calling = 模型输出结构化JSON → 应用调API → 结果精确可靠
- Computer Use = 模型输出鼠标键盘指令 → 截屏识别界面 → 操作不精确且慢
- Function Calling是毫秒级API调用；Computer Use是秒级截屏+识别+操控
- Function Calling对/错明确（参数校验）；Computer Use存在截屏识别错误率（界面变化/DPI/弹窗遮挡）

**2026行业共识**：能API就不Computer Use，能MCP就不自研。Computer Use仅在以下场景使用：
1. 目标软件无API（legacy系统/桌面软件无开放接口）
2. 需要操控浏览器完成多步Web交互（填表/登录/导航）
3. 需要跨多个软件协同操作（Excel+邮件+浏览器联动）

## 三、Computer Use Agent 颠覆浏览器安全模型（2026重大风险）

2026-02 腾讯玄武实验室发布《AI 浏览器爬虫安全白皮书》，指出 Computer Use Agent 对传统浏览器安全模型的颠覆是最容易被低估的风险：[来源:腾讯玄武实验室 | 🔍高 | 2026-02]

**浏览器过去二十年依赖的六道安全防线，在 Computer Use Agent 面前全部失效**：

| 安全防线 | 原本防御什么 | Computer Use下为何失效 |
|---|---|---|
| **1. 同源策略** | 防止A站脚本读写B站数据 | Agent可同时看到所有标签页，一个页面可操控另一个站点的操作 |
| **2. 站点隔离** | 防止跨站数据泄露 | Agent截屏可看到所有打开的标签页内容，无隔离 |
| **3. CSRF令牌** | 防止跨站请求伪造 | Agent发起的请求都是first-party，令牌验证通过 |
| **4. SameSite Cookie** | 防止Cookie跨站发送 | Agent操控的是真实浏览器，Cookie自动携带 |
| **5. 来源校验** | 防止伪造请求来源 | Agent发起的请求来源是真实页面，校验通过 |
| **6. 跨域隔离** | 防止跨域资源访问 | Agent可操控浏览器在任意域执行操作 |

**根因**：Computer Use Agent 把浏览器从"用户端工具"变成了"AI服务器端执行环境"——浏览器安全模型的设计前提是"用户在操控浏览器"，但 Computer Use 下是"AI在操控浏览器"，所有基于"人类用户"假设的安全机制全部失效。

**PM必须懂得的安全设计**：
1. Computer Use Agent 不能有跨标签页操控权限（隔离每个标签页）
2. 敏感操作（转账/删除/发布）必须在Agent操控层加人工确认
3. Computer Use会话应使用独立浏览器实例（不携带用户已有Cookie/会话）
4. 截屏数据不能持久化存储（隐私+安全双风险）

## 四、Computer Use 的工程化挑战

| 挑战 | 根因 | 影响 | 缓解方案 |
|---|---|---|---|
| **截屏识别误差** | 界面DPI/分辨率/动态加载/弹窗遮挡 | 点击坐标偏移→操作错误 | 多截屏校验+元素定位辅助+错误重试 |
| **操作延迟高** | 截屏→识别→生成指令→执行→再截屏 | 单步操作3-10秒，任务耗时膨胀 | 批量操作指令+缓存界面状态+并行操控 |
| **界面变化不可控** | 网页改版/弹窗/验证码 | 操作流断裂 | 状态机设计+异常检测+人工接管备选 |
| **副作用不可逆** | GUI操作无"撤销"（点了"删除"就删了） | 数据丢失/误操作 | 不可逆操作前截图确认+人工确认Hook |
| **隐私泄露风险** | 截屏包含敏感信息（密码/私聊/财务） | 截屏数据泄露 | 截屏脱敏+不持久化+会话隔离 |
| **安全模型失效** | 六道防线全部失效 | 跨站攻击/数据泄露 | 独立浏览器实例+标签页隔离+权限边界 |

## 五、Computer Use vs Function Calling 决策框架

**PM决策树**：
```
目标软件有API吗？
├─ 是 → Function Calling（高效、可靠、安全）
│   └─ API在MCP生态中吗？
│       ├─ 是 → MCP工具调用（标准化、可发现）
│       └─ 否 → 自定义Function Calling
└─ 否 → 需要操作GUI吗？
    ├─ 是 → Computer Use（最后手段）
    │   ├─ 操作涉及不可逆动作吗？
    │   │   ├─ 是 → Computer Use + 人工确认Hook
    │   │   └─ 否 → Computer Use（可接受风险）
    │   └─ 操作仅限浏览器吗？
    │       ├─ 是 → 浏览器专用Agent（Comet/Operator类）
    │       └─ 否 → 桌面Computer Use（Anthropic Computer Use API）
    └─ 否 → 不需要工具调用
```

**决策原则**：
1. **API优先**：有API绝不Computer Use（效率差100倍+安全风险高100倍）
2. **MCP优先**：有MCP Server绝不自研（标准化+生态+可发现）
3. **Computer Use是最后手段**：仅在无API且必须GUI操控时使用
4. **不可逆操作必加护栏**：Computer Use的下拉/点击/提交按钮中，涉及删除/转账/发布的必须人工确认
