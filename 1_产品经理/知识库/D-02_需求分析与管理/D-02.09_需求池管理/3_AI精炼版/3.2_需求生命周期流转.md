## 需求生命周期流转

### 一、完整状态机

```
新建 → 评估 → (确认/打回/搁置) → 排期 → 开发 → 验收 → (通过/返工) → 上线 → 归档
  ↑                    |                    |         |
  └──── 重新提交 ←─────┘                    └─ 返工 ←─┘
```

### 二、各状态定义与规则

| 状态 | 定义 | 进入条件 | 停留时长建议 | 负责人 |
|---|---|---|---|---|
| 新建 | 需求已提交但未评估 | 提交人填写完整需求描述 | ≤3天 | PM |
| 评估 | PM正在分析需求价值与可行性 | 满足准入标准 | ≤5天 | PM+Tech Lead |
| 确认 | 评估通过，等待排期 | Impact+复杂度已评估 | — | PM |
| 打回 | 评估不通过（无价值/不可行） | 明确打回原因 | — | PM |
| 搁置 | 有价值但当前不排期 | 标注搁置原因+重评时间 | — | PM |
| 排期 | 已分配到Sprint/版本 | Sprint Planning确认 | ≤2Sprint | PM+团队 |
| 开发 | 研发团队正在实现 | 开发启动 | 按Story点 | 研发 |
| 验收 | PM/业务方验收 | 功能开发完成 | ≤3天 | PM+业务方 |
| 返工 | 验收不通过需修改 | 验收问题清单 | ≤3天 | 研发 |
| 上线 | 已发布到生产环境 | 验收通过+发布审批 | — | 运维 |
| 归档 | 需求生命周期结束 | 上线后数据回收 | — | PM |

### 三、关键流转规则

**1. 新建→评估（准入检查）**：
- 需求描述完整？
- 无明显重复？
- 有来源标注？

**2. 评估→确认/打回/搁置（决策点）**：
- 确认：有价值+有资源 → 进入排期队列
- 打回：无价值/不可行 → 通知提交人+记录原因
- 搁置：有价值但当前不做 → 标注"搁置原因"+"重评日期"

**3. 排期→开发（Definition of Ready）**：
- 用户故事完整（As a...I want...So that...）
- 验收标准明确
- 技术方案已评审
- 无外部阻塞

**4. 验收→上线（Definition of Done）**：
- 功能验收通过
- 性能测试通过
- 文档已更新
- 上线方案已确认

### 四、需求变更处理

**原则**：需求不变更才是例外，变更才是常态——关键是**变更的可控性**

| 变更类型 | 处理方式 | 影响范围 |
|---|---|---|
| 排期中变更 | 评估影响→调整排期→通知Stakeholder | 低 |
| 开发中变更 | 评估返工成本→PM+Tech Lead审批→调整Story | 中 |
| 上线后变更 | 走新需求流程（不"偷偷改"） | 高 |
| 紧急变更(P0) | 走紧急通道→跳过部分评审→事后补记录 | 最高 |

**变更审批矩阵**：

| 影响范围 | PM可批 | PM+Tech Lead | PM+管理层 |
|---|---|---|---|
| 范围不变+排期延迟<1周 | ✅ | | |
| 范围小变+排期延迟1-2周 | | ✅ | |
| 范围大变/跨版本 | | | ✅ |

### 五、需求退役与归档

**哪些需求应该退役**：
1. 已上线 + 数据回收完成 → 归档
2. 搁置超过6个月 → 自动退役（除非重新激活）
3. 打回后3个月未重新提交 → 关闭

**归档信息**：
- 需求全描述+变更记录
- 实际交付结果 vs 预期
- 上线效果数据
- 经验教训
