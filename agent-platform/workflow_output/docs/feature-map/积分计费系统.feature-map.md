## 一句话描述
全平台预付积分钱包——用户充值积分，调任意大模型（文本/embedding/视频/图片）按价表实时扣积分；用户只见积分，管理员见真实 token+¥+积分。

## 调用链路（关键路径）

```
对话/RAG/记忆/视频提交
  →① 预检 PointsWalletService.canAfford(userId) balance>0？ no→拦截
  → 真调用 LlmGateway.chat/chatStream/embed  或  MediaGenTaskWorker
      ├─② 采集(异步) UsageCollector → llm_usage_logs   [审计·admin 看真 token]
      └─③ 计费(同步事务): token→PricingService→¥→RatioService→积分
              → PointsWalletService SELECT FOR UPDATE balance + INSERT ledger
      ├ 失败 → refund() 逆向退
  → 用户视图读 balance+ledger(显积分) ；admin 读 usage_logs(真 token+¥+积分)
```

## 技术清单与原理注解（大白话版）

### 1. 计费咽喉（出口归户）— `llm/LlmGateway.java`

- **采用技术**：网关出口拦截 + 显式 userId 优先 + ThreadLocal 上下文兜底
- **一句话原理**：所有大模型调用统一过 `LlmGateway`，出口处按 userId 采 token、算钱、扣积分——新模块只要调 gateway 就自动计费，免改。
- **大白话展开**：把计费逻辑收口在「必经之路」（gateway 出口），而不是散落在每个调用点。谁调 chat/stream/embed 谁就自动被计费，调用方只管传 userId。
- **大白话案例**：像地铁闸机——不管你从哪个口进（对话/RAG/记忆），出站（gateway 出口）都得刷卡计费，不用每个口各配一个收费员。
- **为什么用它**：13+ 调用方零回归接入；记忆管线异步线程显式传 userId 也照扣（不依赖请求上下文）。
> 📌 批注：异步 fire-and-forget 线程（如记忆生成）拿不到请求 ThreadLocal，**必须显式传 userId**，否则 `resolveBillingUser` 回退 `BillingContext.current()` 为 null → 仅采不扣（漏扣）。记忆管线 9 调用点全显式传，安全。

### 2. 预检>0 + 后扣实际 — `PointsWalletService`

- **采用技术**：调用前只验余额>0，调用后按真实用量扣
- **一句话原理**：文本/流式的真实 cost 调用完才知道，所以先放行后扣，估不准就宁可后扣不预估。
- **大白话案例**：像先吃饭后结账——不预估你这顿多少钱（估不准会误拦/多扣），吃完按真实菜单算，吃超了下顿前拦住。
> 📌 批注：不做预估预扣（用户决策）。**S1 起「瞬时欠款」模型作废**：V80 CHECK 余额非负 + SQL 守卫单语句拒扣，透支笔直接拒（余额不足报错），不再允许扣成负数。

### 3. 并发扣减行锁防超支 — `PointsWalletService` + 单语句守卫

- **采用技术**：同步事务内单语句 `UPDATE ... SET balance=balance+delta WHERE balance+delta>=0 RETURNING`（行锁含在 UPDATE 里）+ INSERT 流水；S1 起 0 行返 null = 拒扣转业务错
- **一句话原理**：扣钱时把这用户的余额行锁住，并发扣减排队，杜绝两个线程同时读到旧余额各扣一遍超支；S1 把「查再扣」两步合成一句，连竞态窗都关死。
- **大白话案例**：像取款——柜员锁住你的账户本（行锁），一笔一笔改，不会两人同时取光；S1 后柜员还会在改之前先看余额够不够，不够直接拒，不再允许先取成透支。
> 📌 批注：扣减**同步在调用线程**，不走异步池（异步池满会丢任务）；采集才异步。单行写 <5ms。并发 20 线程不超支由 PointsWalletConcurrencyIT 实证。

### 4. 两层分权视图（积分 vs 真 token）

- **采用技术**：价表标 ¥，积分 = ¥ × 阶梯比例；用户视图读 balance/ledger 显积分，admin 读 usage_logs 见真 token+¥+积分
- **一句话原理**：用户只看积分（¥×比例换算），看不到原始 token 和钱；管理员看全量真实成本。
- **大白话案例**：像游戏厅——玩家只见游戏币（积分），老板才看每台机器真实电费+收入（token+¥）。
> 📌 批注：用户查询硬过滤 `WHERE user_id=currentUser`（ownership）；usage_logs 不含 prompt/回答原文，无 PII。

### 5. 流式 usage side-channel 采集

- **采用技术**：`AtomicReference<TokenUsage>` side-channel + provider 末 chunk usage 回灌 + `doOnComplete` 扣减
- **一句话原理**：流式输出（SSE）的 token 用量在最后一个 chunk 才回，用一个外层变量接住，不改动 Flux 流本身。
- **大白话案例**：像水管末端的流量计——水流（SSE 流）不变，只在出口装个表（AtomicReference）记总流量。
> 📌 批注：不改 Flux，SSE 输出字节级回归（13 调用方零回归）。

### 6. 视频/图片独立计费 — `MediaBillingService`

- **采用技术**：视频按 token（Ark 回 usage）或按秒（admin 切）；图片按张（stub 预留）
- **一句话原理**：视频/图片积分**独立计，不与文本 token 加总**——像素换算≠分词，混算没意义。
> 📌 批注：见 SeedDance feature-map 踩坑批注。图片无真 provider，价表+wallet 分支 stub，上线再接。媒体扣减以 taskId 锚 `uq_ledger_ref`，重复扣被唯一约束拦 = 恰好一次生效（S1 起单列 INFO 日志，不与真失败混淆）。

### 7. 幂等防重放 + 每日对账（S1 · SEC-FR-121/123）

- **采用技术**：`runIdempotent` 骨架——`idempotency_keys` 占位（ON CONFLICT DO NOTHING）与业务写同事务，撞键核 user_id+scope 后返首次结果；`BillingReconcileService` 每日 FULL OUTER JOIN 对「余额 vs Σ流水」
- **一句话原理**：重试/双击/网络重发同键只办一次；账目每天自动对一遍，不平只告警绝不自动修（修账必须人工，对账程序自身不能成为篡改面）。
- **大白话案例**：幂等像快递取件码——同码只放一次件，再来人出示同码只给看「已取」回执；对账像银行日终轧账，轧不平立刻喊人，柜员系统自己绝不动账。
> 📌 批注：占位与业务写同 @Transactional，失败整体回滚不留死键（拒扣后同键可重试）；同键不同金额/跨用户撞键 = 疑似重放，写 `idempotency_conflict` 审计。

### 8. 价表导出/导入/模板（7x-2）— `PricingConfigService` + `PricingConfigController`

- **采用技术**：镜像 LLM 供应商 export/import 那套（DTO + upsert + 200 上限 + 逐行容错）
- **一句话原理**：导出全量价表为 JSON 备份；模板联动 `availablePricingModels()`（已排除已配置模型）预填未配置行；导入按 `(providerId+model+kind+hasReference)` upsert——存在覆盖价格刷新 effective_from，不存在新建。
- **大白话案例**：像 Excel 导入导出——先下载空白模板（已帮你列好要填的行），填完价格上传，系统自动覆盖/新建。
> 📌 批注：价表无加密（与供应商含明文 Key 不同），导出无需二次确认；导入逐行校验复用 `validatePricingRule` + provider/model/category 复核，非法行进 errors 不中断整体；无内存缓存需 reload。

### 9. 视频参考定价维度（7x-3）— `pricing_rule.has_reference` + `PricingService` fallback

- **采用技术**：`has_reference BOOLEAN NOT NULL DEFAULT FALSE`（V95）+ 查询谓词 + fallback 编排
- **一句话原理**：VIDEO 同模型可配两行（false=无参考价/兜底，true=有参考价）；计费时按任务实际是否带参考视频命中对应行，查不到精确行回退 false 行。
- **大白话案例**：像快递加急费——普通件（无参考）一个价，加急件（带参考视频）另一个价；只配普通价时加急件也按普通价收（fallback）。
> 📌 批注：worker 算 hasReference **必须**从 `request.getAttachments()` 的 `kind=="video"` 判，不用 taskType（IMAGE2VIDEO 被重载不可靠）；**首尾帧参考图（kind=="image"）不算参考视频**；只配 true 不配 false 时无参考任务会 fallback 失败报「无价表」。

### 10. 视频任务审查标志（7x-4）— `MediaTaskVO.hasReference` 计算字段

- **采用技术**：VO 计算字段（不入库，按 inputAttachments 实时算）+ 推送参数已脱敏落库复用
- **一句话原理**：任务详情/历史/画布明确标注是否有参考视频；推送参数（submittedRequest + providerRequestSnapshot）已存在，Canvas 只需保留字段 + 接面板，**无需新 DB 列**。
- **大白话案例**：像快递单上的「加急」标签 + 内含物清单——标签一眼区分，清单可查实际寄了什么。
> 📌 批注：hasReference 与定价维度 has_reference 是不同字段——前者是任务侧实时算（供展示/审查），后者是价表行配置维度（供计费命中）。两者口径一致（都按 kind=="video" 判）。

### 迁移脚本：`V66__billing_pricing.sql`
- **作用**：建模型价表 + 阶梯比例表（admin 配）。

#### 表：`user_points_balance`（积分余额）
> 大白话：**一行 = 一个用户的积分钱包**。**S1 起不可负**（V80 CHECK 硬约束：透支笔直接拒扣，欠款模型作废）。

| 字段 | 类型 | 用途 | 约束 |
|---|---|---|---|
| user_id | BIGINT | 谁 | UNIQUE、非空 |
| balance_points | DECIMAL(14,2) | 当前积分 | 非空，默认 0，**CHECK ≥0（V80）** |

#### 表：`points_ledger`（积分流水）
> 大白话：**一行 = 一笔积分变动**（充值/消耗/退款/admin grant）。append-only，对账用。**S1 加 `uq_ledger_ref(ref_type,ref_id,type)` 唯一约束 = 同一来源同类型只记一笔（恰好一次）**；生产 agent_app 账号被 REVOKE UPDATE/DELETE 物理拒改。

| 字段 | 类型 | 用途 | 约束 |
|---|---|---|---|
| user_id | BIGINT | 谁 | 索引 |
| type | VARCHAR(16) | RECHARGE/CONSUME/REFUND/ADMIN_GRANT | 非空 |
| delta_points | DECIMAL(14,2) | 变动量（扣为负） | 非空 |
| balance_after | DECIMAL(14,2) | 当时余额（可重建对账） | 非空 |
| ref_type/ref_id | | CHAT/EMBED/VIDEO/IMAGE/PAYMENT/ADMIN + 关联 id | V80 起 (ref_type,ref_id,type) 唯一 |
| remark | VARCHAR(256) | 备注（admin 充值可填，空走默认文案） | 可空 |

#### 表：`idempotency_keys`（幂等键，S1 · V80）
> 大白话：**一行 = 一把「只办一次」的钥匙**。充值/扣减带键来，先 `INSERT ... ON CONFLICT DO NOTHING` 占位——占上了才办正事，撞键回查首次流水原样返回结果。

| 字段 | 类型 | 用途 | 约束 |
|---|---|---|---|
| idem_key | VARCHAR(128) | 幂等键（调用方生成） | **全局 UNIQUE** |
| user_id / scope | | 键属谁 / 属哪个业务域（billing.grant/billing.charge） | 撞键时核验身份用 |
| result_ref | VARCHAR(64) | 首次业务流水 id（回填） | 撞键返首次结果的指针 |

> 📌 批注（Phase4 交叉审查实证）：撞键**必须先核 user_id+scope 再返结果**——键全局唯一，不核则跨用户同键会回返他人 balance_after（余额泄露信道）。核验不过 = 疑似重放，审计 + CONFLICT。

#### 表：`pricing_rule`（模型价表）
> 大白话：**一行 = 一个模型形态的单价配置**。admin 配，按 effective_from 取调用时价。

| 字段 | 类型 | 用途 |
|---|---|---|
| kind | VARCHAR(8) | CHAT/EMBED/IMAGE/VIDEO |
| model | VARCHAR(128) | 模型名 |
| price_input/output_per_million | DECIMAL | 文本每 1M token input/output 价（¥） |
| video_billing_mode | VARCHAR(8) | TOKEN/SECOND（视频） |
| price_per_second / price_per_image | DECIMAL | 视频按秒 / 图片按张 |
| effective_from | TIMESTAMPTZ | 生效时间（查调用时价） |

#### 表：`points_ratio_tier`（阶梯比例）
> 大白话：**一行 = 一个 ¥ 区间换多少积分**。充值与消耗共用。

| 字段 | 类型 | 用途 |
|---|---|---|
| min_amount/max_amount | DECIMAL | ¥ 区间（max null=∞） |
| ratio | DECIMAL(10,4) | 每 ¥ 换多少积分 |

#### 表：`llm_usage_logs`（审计日志）
> 大白话：**一行 = 一次模型调用的真实消耗记录**。admin 看真 token+¥+积分。

| 字段 | 类型 | 用途 |
|---|---|---|
| kind | VARCHAR(8) | CHAT/EMBED/IMAGE/VIDEO |
| tokens_input/output | INT | 真 token 数 |
| cost_yuan / points_consumed | DECIMAL | 当时算的 ¥ 和积分 |
| status | VARCHAR(16) | SUCCESS/ESTIMATED/FAILED |

#### 表关联
- **`points_ledger.user_id` → `user_points_balance.user_id`（一对一逻辑）**：一个用户一个钱包，多笔流水。
  > 像「银行账户 ↔ 交易明细」。
- **`payment_order.user_id` → `user_points_balance.user_id`**：充值订单关联用户；MVP channel=ADMIN 直 PAID，Phase2 接自助支付。
> 📌 批注：余额/流水/日志皆 append-only 或单行 update，**不加软删四字段**，靠 created_at + 分区归档。
