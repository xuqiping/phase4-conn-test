## 质量与漂移度量（每轮迭代手填，看趋势不求精确）

> 每轮迭代（Phase 5 收尾）填一行。目的：让「流程是否起效、文档是否可信」有量化信号，不只靠感觉。对齐 brownfield SDD 业界指标（Drift Rate / Regression Rate / Spec Coverage）。

| 轮次 / 日期 | 本轮缺陷（规格内 / 规格外） | 文档同步待办数 | 关键功能 spec 覆盖率 | 漂移率趋势 |
|---|---|---|---|---|
| v2 升级轮 2026-08-27 | 规格内 0 / 规格外 1（菜单栏层2 无效——PRD 边界未写透） | 11（v1 漂移 7 + v2 新增 4，含已记档/已修复 2） | v2 核心链路 8/8 AC = 100% | →（持平，发现项已全记档） |

**指标口径**：
- **缺陷（规格内 / 规格外）**：本轮发现的 bug，按「PRD/AC 有写 = 规格内（实现没做好）」「PRD/AC 没写 = 规格外（需求漏了）」分。**规格外多 = spec 覆盖有洞**，回 Phase 1 补 AC。
- **文档同步待办数**：上方「规格漂移待办」未清项数 + 已知文档失同步项数。**趋降才健康**，长期不降 = 文档同步机制失效。
- **关键功能 spec 覆盖率**：核心链路功能有「PRD 的 FR/AC + plan Step + 测试」全覆盖的比例。L2/L3 目标 ≥80%。
- **漂移率趋势**：综合规格外缺陷数 + 文档同步待办数判 ↑（变糟）/ →（持平）/ ↓（改善）。连续两轮 ↑ = 流程告警，停下排查。

## 子目录与文件拆分约定

```
workflow_output/开发进度/
├── 开发进度总览.md            ← 本文件（全局入口）
├── <功能名>/                    ← 活跃功能
│   ├── 总路由.md                ← 当该功能进度超过 5000 tokens 时使用
│   ├── <功能名>开发进度总览.md   ← 该功能全貌（不超过 5000 tokens，否则用总路由拆）
│   ├── <功能名>开发进度1.md       ← 第 1 轮对话
│   ├── <功能名>开发进度2.md       ← 第 2 轮对话
│   └── ...
└── archive/                     ← 已交付功能归档区
    └── <功能名>/
        ├── <功能名>开发历程总结.md  ← 压缩版（关键决策/踩坑/最终结果，≤5000 tokens）
        ├── 开发进度1.md ... n.md    ← 原始逐轮文件（移入，不删）
        └── 开发进度总览.md           ← 原功能总览（移入）
```

### 归档机制（防进度文件失控膨胀）

逐轮 `开发进度n.md` 累积几十上百个后，新会话加载成本高、噪音大。功能交付后执行归档：

1. **压缩**：通读该功能所有 `开发进度n.md`，产 `<功能名>开发历程总结.md`（≤5000 tokens），只留**关键决策、踩过的坑、最终结果、关联 ADR/PRD 编号**——扔掉过程噪音。
2. **移档**：原始逐轮文件 + 功能总览移入 `archive/<功能名>/`（不删除，git + archive 双留痕）。
3. **总览瘦身**：本文件「功能进度汇总」表删该功能行，移到「已归档功能」一行摘要。
4. **保留**：Feature Map / User-Ops / 功能 README / 测试方案**不归档**（它们是长期参考，不是过程记录），留在原位。

### 单文件 5000 tokens 限制规则

- **所有** Phase 3 产出的文档都受此限制：开发进度、Feature Map、User-Ops、功能 README、测试方案等。
- 撰写前先估算当前文件 tokens；接近或超过 5000 时，停止追加，改为：
  1. 在该功能目录下新建下一个编号文件（如 `开发进度3.md`）；
  2. 或在目录下新建「总路由.md」，对已有文件做摘要并指向它们。
- **推荐模式**：
  - 文件还不多、只超 5000：直接拆成 `开发进度n.md`。
  - 文件已很多、查找困难：建 `总路由.md`，按主题/轮次汇总，链接到各具体文件。
