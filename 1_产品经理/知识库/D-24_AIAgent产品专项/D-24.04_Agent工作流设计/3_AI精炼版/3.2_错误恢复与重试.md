# 3.2 错误恢复与重试

## 一、错误恢复为什么是 Agent 的"生死线"

生产级 Agent 故障分布（2026-07 行业统计）：工具调用死循环占 31% / 参数校验失败占 24% / 上下文溢出占 18% / 越权误操作占 15% / 其他占 12%。前四类全部归"错误恢复"范畴——Agent 跑崩了能不能起来，决定 Agent 是生产还是 Demo。**模型本身不会"恢复错误"，恢复能力 100% 来自 Harness（工作流框架）**。这是 D-24.04 的硬核模块。

[来源:知乎《生产级 Agent 故障分布》/ CSDN 工具调用死循环 | 🔍高 | 2026-07]

## 二、五级恢复策略总览

| 级别 | 名称 | 触发条件 | 做法 | 成本 |
|---|---|---|---|---|
| L1 | **重试 Retry** | 工具瞬时失败（超时/限流/网络抖动） | 同参数重试 + 指数退避 + 限次（默认 3） | 最低 |
| L2 | **降级 Fallback** | 工具返回质量差 | 切换备选工具或简化参数走较慢但可靠替代 | 低 |
| L3 | **绕路 Detour** | 当前路径走不通但有等价替代路径 | 换一组工具组合达到等价结果 | 中 |
| L4 | **重规划 Re-plan** | 多步连续失败/原计划整体不可行 | 回到 Planner 重新规划剩余子任务 | 高 |
| L5 | **人工接管 Human Takeover** | 涉及不可逆操作/反复失败超阈值/越权风险 | 中止 Agent，转人工处理 | 最高 |

**核心原则**：从低成本到高成本逐级升级——先重试、再降级、再绕路、再重规划、最后人工。不要一上来就重规划（成本高），也不要死磕重试（死循环）。

[来源:腾讯云《Agent错误恢复与重试》| 🔍高 | 2026-06]

## 三、L1 重试机制的三个工程细节

1. **指数退避（Exponential Backoff）**：第 1 次重试等 1s，第 2 次 2s，第 3 次 4s，第 4 次 8s……对抗限流。叠加抖动（jitter）避免雪崩同步重试。
2. **限次（Max Retry）**：默认 3 次，超过即升级到 L2/L3/L4。**死循环第一祸因就是没限次**——Agent 以为"再试一次肯定成"无限重试，正是 31% 工具调用死循环的最大子类。
3. **失败模式分析**：重试之前先看错误类型——4xx（参数错）重试无意义直接 L4 重规划；5xx（服务错）可以重试；超时可以重试+调大 timeout。无脑重试是反模式。

[来源:CSDN 生产级 Agent 重试 | 🔍高 | 2026-07]

## 四、L4 重规划与反思循环 Reflexion

**重规划（Re-plan）** 才是 L4 的核心：原计划走不通时不是硬刚，而是回到 Planner 用"当前已完成状态 + 失败信息"重新规划剩余步骤。这个"重新规划"在 Reflexion 模式下表现为"反思 → 经验 → 重跑"。

**反思循环 Reflexion**：
- 主 Agent 完成子任务后，Reflector（独立 LLM 调用）评估这一步做得对吗、哪里可改进
- 反思结果写入"经验记忆"
- 下一轮主 Agent 带着经验再跑
- 用语言化反馈替代数值 reward，本质是 verbal reinforcement

**工程要点**：必须有客观验证信号托底（编译通过/测试 pass/JSON 校验通过）；否则 Reflector 自评就是自欺欺人。Reflexion 不是万能药，没信号的任务不要套。

[来源:Reflexion 论文 Shinn et al. / 腾讯云 Agent设计模式 | 🔍高 | 2025-12/2026-05]

## 五、Loop Engineering —— 2026 第 4 次范式跃迁

### 5.1 范式跃迁序列

LLM（2020）→ Prompt Engineering（2022）→ Agent（2023）→ **Loop Engineering（2026）**。每次跃迁本质都是"把人做的事丢给系统"：手写回答 → 手写提示词 → 手写 Agent 流程 → 设计给 Agent 写提示词的 loop。

[来源:百家号/知乎《Loop Engineering：2026第4次范式跃迁》| 🔍高 | 2026-06]

### 5.2 核心命题

Peter Steinberger（OpenClaw 创建者，现已加入 OpenAI）2026-06 推文："你不应该再去给编程 Agent 写 prompt，应该设计一套能给你的 Agent 写 prompt 的循环。"

翻译：人不再手写一次性 prompt，而是设计一个"循环结构"，循环每轮自动生成新 prompt 喂给 Agent，让 Agent 持续续跑。

[来源:Peter Steinberger Twitter / 知乎 Loop Engineering | 🔍高 | 2026-06]

### 5.3 Ralph Loop —— 最具代表性的 Loop 实现

**机制**：Agent 长任务跑到中途常出现"上下文已腐烂/Agent 想退出"的情况。Ralph Loop 用钩子拦截 Agent 的退出尝试，在干净上下文中重新注入"原始目标 + 已完成状态"的压缩提示词，强制 Agent 续跑。

```
loop:
  result = Agent.run(prompt)             # 一次 Agent 会话
  if result.is_complete: break
  if Agent.tries_to_exit:                # 拦截退出
    prompt = ReconstructPrompt(          # 重新构造提示词
      original_goal,
      Agent.completed_state,
      Agent.failure_reason
    )
    Agent.reset_context()                # 清干净上下文
    continue                             # 续跑
```

**为什么有效**：原本 Agent 上下文腐烂后只能放弃，Ralph Loop 把"放弃"变成长跑的必经一环——每次退出都是重启，不是终止。这是把"上下文管理"从 prompt 层上升到 loop 结构层的范式转换。

[来源:GitHub Ralph Loop / 知乎 Loop Engineering | 🔍高 | 2026-06]

### 5.4 Loop Engineering vs 传统 Agent 工作流

| 维度 | 传统 Agent 工作流 | Loop Engineering |
|---|---|---|
| 控制层 | 单次 prompt → Agent 跑 | 多轮 loop 自动写新 prompt 喂 Agent |
| 上下文管理 | 累加日志式，跑长必烂 | 每轮清干净，重注入必要状态 |
| 终止判定 | Agent 自己说"我做完了" | Loop 检查完成条件 + 拦截退出 |
| 失败处置 | 抛错或重试 | 重构 prompt + 续跑 |
| 适用场景 | 中短任务 | 长任务 / 不可预测长度任务 |

Loop Engineering 不取代 Agent 工作流，而是在更高层包裹工作流——它是"工作流的工作流"。

[来源:知乎 Loop Engineering | 🔍高 | 2026-06]

## 六、反漂移与死循环检测

死循环（31% 故障根因）的典型表现：
- Agent 反复调用同一工具相同参数
- Agent 反复编辑同一文件同一行
- Agent 在 ReAct 循环里来回自问自答
- Agent "完成"了任务但目标根本没达成

**反漂移检测（Anti-Drift Detection）**：
- **工具调用去重**：相同 tool+params 连续 3 次直接拦
- **工具调用历史指纹比对**：相同指纹触发警示
- **输出变化检测**：文件 hash / 工具输出 diff 不变触发警示
- **限步**：单 Agent 会话工具调用次数硬上限（默认 50 次）

LangChain Harness 加反漂移检测后让 Agent 不再卡死循环——这是 Harness 工程的典型功效（Harness 元理论见 3.3）。

[来源:LangChain Harness 报告 / 网易《一文讲透 Harness Engineering》| 🔍高 | 2026-06/2026-03]

## 七、五级恢复与模式依赖关系

五级恢复不是任意切换的，依赖 3.1 的拆解模式：

| 恢复级别 | 模式依赖 | 不具备该模式时的退路 |
|---|---|---|
| L1 重试 | 无依赖 | 任意模式可做 |
| L2 降级 | 无依赖 | 任意模式可做 |
| L3 绕路 | 需 Tool 库备选工具 | 多工具注册 |
| L4 重规划 | **必须是 Plan-and-Execute / Planner-Worker** | ReAct 模式无重规划，直接升级 L5 |
| L5 人工接管 | 无依赖但需 HITL 设计 | 详见 3.3 HITL 三档 |

**推论**：纯 ReAct 长任务没有 L4 能力，崩了只能 L5 接管——这是"单一 ReAct 不许跑超过 20 步"选型红线的根因。
