# 3.2 上下文工程与 Context Rot 对抗

## 一、Context Engineering 范式跃迁（2025-2026）

### 从 Prompt Engineering 到 Context Engineering

**核心命题**：2025 年 Andrej Karpathy 提出"prompt engineering 应该让位给 context engineering"；2026-02 Mitchell Hashimoto（HashiCorp 联合创始人）提出"engineer the harness"；2026-06 Boris Cherny（Anthropic Claude Code 负责人）直言"我不觉得 prompt 是核心，context 才是 Agent 时代的核心战场"。

**范式本质区别**：

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| 关注点 | 怎么"写好指令" | 怎么"工程化上下文" |
| 核心动作 | 调措辞 / 调结构 / 调示例 | 设计注入/压缩/卸载/检索策略 |
| 心智模型 | "写一封好信" | "设计一个信息系统" |
| 优化对象 | 单次 prompt 文本 | 完整上下文生命周期 |
| 2026 共识 | 边际效益递减 | 核心战场 |

[来源:博客园《从 Prompt 到 Context：2026 Agent 时代的核心战场》/腾讯云 Loop Engineering | 🔍高 | 2026-01/07]

**PM 认知要点**：
- Context Engineering 不是"调 prompt 的高级说法"——它是把上下文当信息系统来工程化
- 三大支柱：上下文注入（该给什么）/ 上下文压缩（该删什么）/ 上下文检索（该找什么）
- 与 D-24.04 Harness 工程联动——Context Engineering 是 Harness 的核心组件

## 二、Context Rot 机理（长 Agent 的隐形杀手）

### Context Rot（上下文腐烂）定义

**核心机理**：上下文窗口填满后，模型推理和任务完成能力会逐渐变差——不是断崖式失败，而是缓慢腐烂。

### Context Rot 三大表征

| 表征 | 机理 | 后果 | 典型案例 |
|---|---|---|---|
| **Lost in the Middle** | 超长上下文中，首尾信息回忆率显著高于中段 | 中段关键信息被忽略 | 长文档中段约束被遗忘 |
| **二次方注意力成本** | 注意力计算复杂度随上下文长度二次方增长 | 长上下文经济不可持续（$15/百万 token，长会话单次推理几美元） | 长任务成本爆炸 |
| **提示缓存脆弱** | 每条新消息改变缓存键 | 缓存命中率下降，成本回升 | 长对话缓存失效 |

[来源:B站《2026 Agent 记忆架构深度解析》/腾讯云《Agent 记忆机制详解》| 🔍高 | 2026-03/07]

### Context Rot 触发条件

- 上下文窗口超过 50% 填充率 → 推理质量开始下降
- 第 50 次工具调用后 → 模型开始"忘记"原始目标
- 工具数过多（15+）→ 模型对工具描述分心（Vercel 15→2 实证）
- 历史过长未压缩 → 中段信息被稀释

**关键认知**：扩展的上下文窗口应被视为"复杂单会话任务的扩展工作记忆"，而非"持久记忆系统的替代品"。200K 窗口也救不了 Context Rot。

## 三、Compaction 压缩（Claude Code 五层标杆）

### Claude Code 五层 Compaction 架构

Anthropic Claude Code 团队的五层上下文压缩是 2026 标杆实践：

| 层级 | 策略 | 触发条件 | 效果 |
|---|---|---|---|
| **L1 工具输出截断** | 大输出只保留头尾，中间省略 | 单次工具输出 > 阈值 | 单次工具结果不爆 |
| **L2 历史总结** | 把早期对话/工具历史总结成要点 | 上下文填充率 > 50% | 释放上下文空间 |
| **L3 Dump 到文件** | 把状态/中间产物写到文件系统 | 上下文临界 / 需持久化 | 上下文卸载 + 可恢复 |
| **L4 AGENTS.md** | 把稳定指令/约束写进记忆文件 | 跨会话约束持久化 | 跨会话不丢约束 |
| **L5 会话 Reset + Ralph Loop** | 清空上下文，重新注入原提示词续跑 | Context Rot 严重 / 死循环 | 干净上下文重启 |

[来源:Anthropic《Effective Harnesses for Long-Running Agents》/腾讯云 | 🔍高 | 2026-06]

### Compaction 策略选型

| 策略 | 适用场景 | 优势 | 风险 |
|---|---|---|---|
| **总结压缩** | 历史对话/工具结果 | 保留要点 | 总结可能丢信息 |
| **卸载到文件** | 中间产物/状态 | 可恢复 | 需检索回填 |
| **选择性保留** | 关键约束/原始目标 | 保核心 | 需识别关键信息 |
| **渐进式披露** | 工具列表/记忆条目 | 按需加载 | 需元信息设计 |
| **会话 Reset** | Context Rot 严重 | 干净重启 | 需 Ralph Loop 续跑 |

## 四、提示缓存（Prompt Caching）优化

### 提示缓存机理

| 机制 | 说明 |
|---|---|
| **稳定前缀缓存** | 系统提示/工具定义等稳定前缀缓存，命中大幅降成本 |
| **缓存键敏感** | 每条新消息改变缓存键，长对话缓存命中率下降 |
| **命中率与新鲜度权衡** | 缓存越多越省钱但上下文越旧；反之亦然 |

### 提示缓存设计原则

1. 稳定前缀前置（系统提示/工具定义/ Few-shot 示例）
2. 动态内容后置（用户输入/工具结果/对话历史）
3. 长对话分段缓存（按会话段缓存，平衡命中率与新鲜度）
4. 监控缓存命中率（< 50% 需优化结构）

[来源:腾讯云/博客园 Context Engineering 系列 | 🔍高 | 2026]

## 五、Goldilocks Zone（恰到好处区间）

### Goldilocks Zone 定义

**核心命题**：上下文不是越多越好，也不是越少越好——存在"刚刚好区间"。

| 上下文量 | 状态 | 后果 |
|---|---|---|
| 太少 | 模型乱猜 | 幻觉 / 错误执行 |
| 刚刚好 | 模型精准推理 | 高质量输出 |
| 太多 | 模型分心 | Context Rot / 中段遗忘 |

### Goldilocks Zone 三要素配比

| 要素 | 配比原则 | 典型问题 |
|---|---|---|
| **工具描述** | 严格区分相似工具的数据范围，含 Tool Use Examples | 工具数 15+ 会分心 |
| **记忆条目** | 按需检索 Top-K，不全量灌入 | 全量灌入引发 Context Rot |
| **历史对话** | 总结压缩 + 选择性保留关键节点 | 全量保留成本爆炸 |
| **示例（Few-shot）** | 精选 3-5 个，覆盖边界场景 | 示例过多稀释注意力 |

## 六、渐进式披露（Progressive Disclosure）

### 渐进式披露机理

**核心思想**：按需加载工具元信息/记忆条目，避免一次性灌满上下文。

**Skills 渐进式披露模式**：
- L1：工具列表只暴露名称+一句话描述（元信息）
- L2：调用时加载完整工具定义+参数
- L3：执行时加载示例+注意事项

**记忆渐进式披露模式**：
- L1：记忆库只暴露摘要索引
- L2：推理时检索 Top-K 相关记忆
- L3：深入时加载完整记忆条目

[来源:博客园《从 Prompt 到 Context》/Anthropic Skills | 🔍高 | 2026-01]

**PM 认知要点**：
- 渐进式披露是缓解 Context Rot 的核心策略——Vercel 工具 15→2 本质就是渐进式披露
- 工具数控制 + 记忆 Top-K + 历史总结 = 渐进式披露三件套
- 与 D-24.02 Skills 联动——Skills 是能力模块化，本质就是渐进式披露

## 七、长任务上下文持久化

### 长任务上下文持久化三策略（与 D-24.04 状态管理联动）

| 策略 | 机制 | 适用场景 | 代表 |
|---|---|---|---|
| **文件系统持久化** | Agent 把状态写到文件（最基础 Harness 状态原语） | 所有长任务 | Anthropic 报告原话：文件系统是最基础 Harness 状态原语 |
| **检查点 Checkpoint** | 定期保存上下文快照，崩溃可恢复 | 需崩溃恢复的长任务 | LangGraph checkpoint |
| **记忆文件 AGENTS.md** | 把稳定约束/指令写进记忆文件 | 跨会话约束持久化 | Claude Code AGENTS.md |

[来源:Anthropic《Effective Harnesses for Long-Running Agents》/LangGraph | 🔍高 | 2026-06]

### 长任务上下文设计原则

1. 文件系统优先（最基础、最可观测、最适合多 Agent 协作）
2. 检查点密度按任务长度配（30 分钟任务每 5 分钟，百步任务每 10 步）
3. 崩溃恢复注入原始目标（Ralph Loop 模式：干净上下文 + 原提示词续跑）
4. Compaction 周期配合检查点（压缩后立即打 checkpoint）
