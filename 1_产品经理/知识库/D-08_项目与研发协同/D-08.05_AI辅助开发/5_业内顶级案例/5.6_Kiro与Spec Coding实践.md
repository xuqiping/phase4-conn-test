# 5.6 Kiro与Spec Coding——从氛围到规范的范式转换

## 案例名称+时间+主角

- **案例名称**：AWS Kiro推行Spec Coding——AI编程的下一个范式
- **时间**：2026年
- **主角**：Amazon Web Services（AWS）

## 背景

当行业沉迷于Vibe Coding的"零门槛编程"时，AWS的Kiro选择了相反方向——**先写Spec再写代码**。Kiro是AWS推出的AI编程IDE，核心创新是Spec-Driven Development：开发者定义精确规格（Spec），AI按规格生成代码，Hook自动验证合规。

## 手法/链条

1. **Spec优先**：项目启动时先写Spec（功能规格+接口约束+测试规范），而非直接写代码
2. **三种模式切换**：
   - **Vibe模式**：探索阶段，快速原型
   - **Spec模式**：规格阶段，精确定义
   - **Hook模式**：验证阶段，自动检查代码是否符合Spec
3. **Hook自动化验证**：关键节点（pre-commit/pre-push）自动触发Spec合规检查
4. **与AWS深度集成**：Lambda/DynamoDB/CloudFormation的Spec模板，一键生成基础设施代码

## 影响后果

**正面**：
- Spec Coding显著减少AI幻觉——Spec是约束，代码是自由度，约束让AI输出更确定
- Hook机制是"AI编程的CI/CD"——自动化验证比人工Review更可靠
- PM可以写Spec（本质上就是PRD的代码化），推动PM更深入参与开发流程

**负面**：
- 绑定AWS生态——非AWS项目适配成本高
- Spec编写本身有学习曲线——不是所有团队都愿意"先写Spec再写代码"
- AWS生态外影响力有限

## 教训启示

1. **Spec Coding是Vibe Coding的成人礼**：原型用Vibe，生产用Spec——两者不矛盾而是递进
2. **PM的新技能**：写Spec本质上就是写"可执行的PRD"——PM天然适合这个角色
3. **Hook=AI编程的自动化测试**：传统开发有CI/CD，AI编程需要"Spec CI"——自动验证代码是否符合Spec
4. **PM实践**：在团队推进"从Vibe到Spec"转型时，PM负责起草第一版Spec模板（→4.3模板），推动团队养成"先Spec后Code"的习惯
