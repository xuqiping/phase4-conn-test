## 一、RICE评分表

### 1.1 评分标准说明

| 维度 | 定义 | 评分标准 |
|------|------|---------|
| **Reach（覆盖面）** | 每个季度受影响的用户数量 | 按目标用户百分比换算为数值 |
| **Impact（影响度）** | 对单个用户的影响程度 | 3=巨大影响，2=高影响，1=中等影响，0.5=低影响，0.25=极低影响 |
| **Confidence（信心度）** | 对R和I评估的信心 | 100%=高信心（有数据支撑），80%=中等信心，50%=低信心（猜测） |
| **Effort（工作量）** | 需要的人月投入 | 按前端+后端总人月计算，1人月 = 1人工作1个月 |

**RICE得分公式：** (Reach × Impact × Confidence) / Effort

## 三、MVP范围定义

### 3.1 MVP核心路径

```
登录 → Agent大厅（浏览/搜索/筛选）→ Agent详情（查看能力/接口）→ 工作流编排（拖拽/配置）→ 执行 → 查看结果
```

**任何一个环节断开，MVP即不可用。**

### 3.2 MVP功能清单

| 模块 | 功能点 | 页面 |
|------|--------|------|
| 登录页 | 用户名密码登录、密码修改 | 1个页面 |
| Agent大厅 | 卡片展示、分类筛选、搜索 | 1个页面 |
| Agent详情 | 基本信息展示、接口规范展示 | 1个页面 |
| 工作流编辑器 | 画布拖拽、节点连线、参数配置、执行、历史 | 1个页面 |
| 系统管理 | 用户管理、角色权限 | 2个页面（用户列表、角色配置） |

**MVP页面总数：6个核心页面**

### 3.3 MVP不做的事

- 不做App
- 不做SSO
- 不做实时协作
- 不做Agent自建
- 不做多语言
- 不做Agent市场

### 3.4 MVP技术基线

| 层 | 技术选型 |
|----|---------|
| 前端 | Vue 3.4+ / TypeScript / Element Plus / Vue Flow |
| 后端 | Spring Boot 3.2+ / Java 17 / MyBatis Plus |
| 数据库 | PostgreSQL 15 |
| 缓存 | Redis 7 |
| 认证 | JWT (RS256) |
| 部署 | Docker Compose |

## 五、优先级决策原则

### 5.1 决策框架

当需求发生冲突时，按以下优先级排序：

1. **核心路径完整性** > 功能丰富度（路径断了，功能再多也没用）
2. **数据安全** > 用户体验（安全是不可协商的底线）
3. **用户覆盖面** > 单用户深度（先让多数人能用）
4. **差异化价值** > 行业标准（检查清单和工作流编排是护城河）
5. **技术可行性** > 商业理想（不确定的技术方案先做POC验证）

### 5.2 需求变更流程

```
提出变更 → 影响分析（工作量+风险）→ RICE重评 → 优先级调整审批 → 更新Backlog
```

变更审批权限：
- P0-P1级别变更：产品负责人 + 技术负责人联合审批
- P2级别变更：产品负责人独立审批
- 新增Won't have功能：需团队全员讨论决定
