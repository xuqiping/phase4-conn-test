# 3.4 与KANO组合策略

> 本碎片是D-02.04·3.4"组合策略"的**RICE视角补充**——KANO视角的组合逻辑详见D-02.04。

## RICE视角：为什么RICE需要KANO

| RICE的局限 | KANO的补充 |
|---|---|
| RICE不知道需求"不满足会怎样" | KANO的M类=不满足则严重不满→无论RICE多低都该做 |
| RICE不知道需求"是惊喜还是基线" | KANO的A类=惊喜→即使RICE高也可能是"锦上添花" |
| RICE的Impact是主观分 | KANO的Better-Worse提供数据化的Impact参考 |
| RICE不知道需求会漂移 | KANO的动态追踪揭示需求从A→O→M的演化 |

## 交叉决策矩阵

| KANO类别 | RICE高分 | RICE低分 | 决策逻辑 |
|---|---|---|---|
| **M(必备)** | 必做+高价值=**最高优先** | 必做+低量化分=**仍须做** | M类需求无论RICE多少都必须做——不做的风险>做的成本 |
| **O(期望)** | 高价值+线性收益=**高优先** | 低量化+期望属性=**需验证** | O+低RICE→可能是Reach估错或Impact被低估 |
| **A(魅力)** | 差异化亮点+高量化=**冲** | 差异化但量化低=**资源允许则做** | A类是创新方向，低RICE可能因Confidence低→补充数据后再评 |
| **I(无差异)** | 高量化但用户不在乎=**砍** | 低量化+不在乎=**坚决不做** | I+高RICE是典型陷阱——数据好看但用户无感 |

## 四种典型冲突及应对

### 冲突1：低RICE但KANO必备(M)

```
案例：安全合规修复
RICE = 500人×0.5 Impact×80% Confidence / 4人月 = 50分（排名靠后）
KANO = M（不修=合规风险+用户不满）

决策：无视RICE排名，直接列入Must-do
原因：RICE的Impact未量化"不做的风险"→用RICE-M(M=∞)修复
```

### 冲突2：高RICE但KANO无差异(I)

```
案例："高级主题定制"功能
RICE = 10000人×1 Impact×80% Confidence / 2人月 = 4000分（排名第1）
KANO = I（90%用户不在意，10%觉得有点意思）

决策：砍掉或极低优先级
原因：RICE高估了Impact（实际是I类→真实Impact≈0.25）
修正：Impact从1→0.25，RICE = 1000分（排名大幅下降）
```

### 冲突3：高RICE且KANO魅力(A)

```
案例：AI自动摘要功能
RICE = 5000人×2 Impact×50% Confidence / 3人月 = 1667分
KANO = A（惊喜+差异化）

决策：高价值创新方向→先做小规模验证提高Confidence
行动：Confidence从50%→80%（通过Beta测试）→RICE升至2667分
```

### 冲突4：Confidence极低的RICE

```
案例：新市场功能
RICE = 80000人×3 Impact×50% Confidence / 6人月 = 20000分（看似第1）
但Confidence=50%意味着"纯猜测"

决策：先做验证实验获取数据→而非直接开干
原因：0.5的Confidence把RICE砍半=10000分（可能不是真正最高）
```

## 组合决策流程（RICE主导版）

```
1. 所有需求先跑RICE评分 → 基础排序
2. 用KANO标注每个需求的M/O/A/I类别
3. 冲突校验：
   - M类但RICE低 → 提升至Must-do（加M权重）
   - I类但RICE高 → 下调Impact → 重算RICE
   - A类且Confidence低 → 标记"需验证" → 验证后重评
4. 输出最终优先级清单（含RICE得分+KANO标注+调整说明）
```
