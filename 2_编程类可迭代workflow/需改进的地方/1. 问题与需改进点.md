## 一、数据库与数据模型层

### 1. 缺「全局数据库设计文档」产出（原第 1 条完善版）—— P0 ✅ 已落地（2026-08-02）

- **问题**：当前没有任何一份文档能回答「全项目有哪些表、每张表每个字段是什么（中文说明/类型/约束/默认值/枚举取值）、表与表之间怎么关联、用的是 Flyway 哪个版本脚本建的」。
- **现状（部分已覆盖）**：v1.6 起 Feature Map 有「建表注解」（表用途/字段用处/表关联），Phase 1 也列了 `specs/db_schema.md`——但：① Feature Map 是**按功能**的碎片视角，没有全局 ER 总图和数据字典；② `db_schema.md` **没有模板骨架**（`项目模板/workflow_output/docs/specs/` 下只有 PRD.md）；③ 没有「表 ↔ Flyway 版本号 ↔ 所属功能」的对照清单，改表时不知道哪个 V 脚本建的。
- **世界级参照**：SDD 各框架都把数据模型作为规格一等公民；企业实践普遍要求 ERD + 数据字典（data dictionary）入库管理、随迁移演进。
- **改进建议**：
  1. 补 `项目模板/workflow_output/docs/specs/db_schema.md` 模板，固定 sections：① **全局 ER 图**（用 mermaid `erDiagram`，AI 友好、可 diff）；② **逐表数据字典**（表名 | 中文用途 | 字段名 | 类型 | 约束/索引 | 默认值 | 枚举取值含义 | 中文说明）；③ **表关联说明**（一对多/多对多 + 大白话比喻）；④ **Flyway 版本清单**（版本号 | 变更内容 | 对应功能 | 日期）。
  2. 规则：Phase 1 建初版；每次 Flyway 新脚本执行后**必须回写** db_schema.md（并入 Phase 3/6 出口条件）；Feature Map 的建表注解保持「本功能视角的速查」，db_schema.md 是「全局权威版」，二者分工写清。
  3. db_schema.md 超 5000 tokens 时按业务域拆分（`db_schema.<域>.md` + 总路由）。

### 2. specs 模板严重缺失 —— P1 ✅ 已落地（2026-08-02）

- **问题**：Phase 1 规定产 6 份规格（PRD / architecture / db_schema / testing_strategy / security_strategy / performance_goals），但 `项目模板/workflow_output/docs/specs/` 下**只有 PRD.md 一个模板**，其余 5 份全靠每次现编，格式漂移、覆盖率靠自觉。
- **改进建议**：补齐 5 个模板骨架（每个含固定 section 骨架 + 术语表 section + 出口自查清单），并更新 `0_文档产物与引用关系总览.md` 配套表。

## 二、规格层（Phase 1）

### 3. 需求写法缺「结构化可测试语法」，验收标准不可执行 —— P0 ✅ 已落地（2026-08-02）

- **问题**：PRD 目前是自然语言用户故事，「完成」的定义靠人读感觉。AI 实现时容易「表面满足、边界漏做」，Phase 4 验收也没有逐条可断言的基准。
- **世界级参照**：AWS Kiro 原生用 **EARS 语法**（`WHEN [条件] THE SYSTEM SHALL [行为]` / `WHILE` / `IF-THEN` / `WHERE`）写需求，2026 年用 SMT 求解器做需求矛盾检测；require-kit 等工具把 EARS 转成 **BDD 场景（Given/When/Then）** 直接驱动测试。行业规则：**每条功能需求至少映射一条验收标准，每条验收标准必须可独立测试**。
- **改进建议**：
  1. PRD 模板加「验收标准」section：每个功能用 **编号 + EARS 或 Given/When/Then** 写 1~n 条验收标准（如 `AC-LOGIN-03: WHEN 密码连续错误5次 THEN 系统锁定账户15分钟`）。
  2. 已有「功能联动点清单」天然适合 EARS 的 IF-THEN/WHEN 句式，两处统一。
  3. Phase 4 验收时**逐条 AC 打勾**，通过/不通过有可追溯记录（替代现在「亲眼看一遍」的模糊验收）。

### 4. 缺「需求 → 验收 → 计划 → 代码 → 测试」追溯编号体系 —— P1 ✅ 已落地（2026-08-02）

- **问题**：PRD 条目、plan chunk、测试用例、commit 之间没有公共编号，出问题时无法回答「这个需求到底实现没、测了没、在哪」。
- **世界级参照**：Kiro/Spec Kit 的 tasks.md 每条任务回链 requirement 编号；SDD 插件提供 traceability-check。
- **改进建议**：定一套轻量编号（需求 `FR-xxx` / 验收 `AC-xxx` / plan chunk 内引用 FR 号 / 测试方案用例引用 AC 号 / commit message 带 FR 号）。进度文件的「对应 plan.md/PRD 编号」字段已有雏形，升级为全链路。

### 5. 规格与代码「漂移」无检测机制 —— P1 ✅ 已落地（2026-08-02）

- **问题**：规格是「唯一真相源」只是口头约定——实现偏离规格后，spec 不会自己更新，三个月后 spec 与代码两张皮（这是 2026 年 SDD 社区公认的头号痛点，OpenSpec 也因此被诟病）。
- **世界级参照**：OpenSpec 用 `/opsx:sync` 在合并前强制同步；Claude SDD 插件有 `reconcile`（检测并解决 spec↔code 漂移）；Augment Code 建议用 **Drift Rate**（契约测试失败数、spec 修订频率）量化漂移。
- **改进建议**：
  1. Phase 4 review 环节加「**spec 符合性检查**」动作：让第二个 AI 对照 PRD/plan 逐条核对实现，输出漂移清单（多做了/少做了/做偏了）。
  2. Phase 6 已有文档同步，补一条硬规则：**变更 PR 合并前 spec 必须已同步**（sync-before-merge），不允许「先合代码、spec 回头补」。
  3. 进度总览加「规格漂移待办」栏，记录已知未同步项。

## 三、计划层（Phase 2）

### 6. plan 缺任务依赖图与并行化地图 —— P2 ✅ 已落地（2026-08-03）

- **问题**：plan.md 是线性步骤列表，没标哪些 chunk 可并行、哪些有先后依赖。一个人用影响小；一旦上多 agent / worktree 并行（铁律 #5、#7 都提到），没有依赖图就无法安全分工。
- **世界级参照**：Spec Kit 的 tasks.md 明确标 `[P]` 可并行任务与依赖顺序；Kiro 的 tasks.md 是 dependency-sequenced。
- **改进建议**：plan 模板加「依赖与并行化」小节：每步标注 `依赖: 步骤n` 或 `[P] 可并行`；并行开发时按此分配 worktree。

### 7. 缺 ADR（架构决策记录）—— P1 ✅ 已落地（2026-08-02）

- **问题**：「为什么选 WebSocket 不选 SSE」「为什么用逻辑删除」这类关键决策，目前散落在进度文件和聊天里，一个月后没人记得为什么，AI 新会话还会「好心」改回去。
- **世界级参照**：ADR（Architecture Decision Record）是行业标准——轻量 markdown 记录 背景/选项/决定/后果。
- **改进建议**：加 `workflow_output/docs/adr/ADR-<n>-<标题>.md`（模板：背景 | 备选方案 | 决定 | 理由 | 后果/代价）。触发时机：Phase 1 架构决策、Phase 3 中任何「推翻常规做法」的决定。Feature Map 的「为什么用它」字段可回链 ADR 编号。

## 四、实现层（Phase 3）

### 8. 5000 tokens 上限等文档规则全靠自觉，无自动化校验 —— P1 ✅ 已落地（2026-08-02）

- **问题**：tokens 上限、进度更新、文档同步这些硬规则，执行全靠 AI/人记得，实际项目里必漏（`agent-platform` 实跑中已出现进度文件失控的苗头）。
- **世界级参照**：Kiro 的 **Agent Hooks**（文件保存/提交时自动触发校验）；Claude Code 的 **hooks**（编辑后自动跑 lint/检查）；Spec Kit 有 `/speckit.analyze` 做一致性校验。
- **改进建议**：
  1. 项目模板加 `.claude/settings.json` hooks 骨架：如 PostTool 后跑「文档 token 估算脚本」，超 4000 预警。
  2. 加一个简单的 `scripts/check_docs.py`（或 node 版）：扫描 `workflow_output/` 列出超限文件、失效链接、孤立文档；纳入 commit 前自检和 Phase 4 出口。
  3. prompt 模板里固化「每轮结束前跑检查脚本」的动作。

### 9. 本地开发期缺自动化质量门（CI 太晚才接）—— P0 ✅ 已落地（2026-08-02）

- **问题**：CI/CD 目前排在 Phase 5 才接，意味着整个 Phase 3/4 期间 lint、类型检查、测试全绿都靠口头确认。铁律 #9 说「AI 在能自动抓错的环境里才飞得起来」——没有自动反馈环，AI 的错潜伏到很晚。
- **世界级参照**：Anthropic 最佳实践强调「**encoded self-checks**」——把 lint/typecheck/test 建成确定性检查，让 AI 交付前自查；业界标准是 pre-commit hook + 最小 CI 从项目第一天就有。
- **改进建议**：
  1. 「最小质量门」从 Phase 0 项目骨架就带上：后端 `mvn compile + test`、前端 `tsc --noEmit + lint + test` 的一条命令封装（如 `scripts/check_all.bat/sh`）。
  2. 项目模板加 pre-commit / husky 骨架（或至少把「commit 前必跑 check_all」写死进 AGENTS.md 和 implement prompt）。
  3. Phase 5 的 CI 只是把这套本地检查搬到服务器，不是从零建。

### 10. 缺上下文工程的「隔离/压缩」落地策略 —— P2 ✅ 已落地（2026-08-03）

- **问题**：上下文打包（铁律 #3）只说了「喂什么」，没说「怎么防膨胀」。长会话里上下文稀释、旧信息干扰是当前实跑中的真实痛点。
- **世界级参照**：Anthropic context engineering 四板斧：**Write**（存外部）/ **Select**（只取相关）/ **Compress**（压缩摘要）/ **Isolate**（subagent 独立窗口）。
- **改进建议**：
  1. 明确「大任务拆 subagent」的判定线（如：独立调研、批量机械修改、review → 开 subagent，主会话只留结论）。
  2. 长会话约定：每个功能开工 = 新会话 + 读 Phase3.1 速查 + 进度文件（已有雏形，写成硬规则）。
  3. CLAUDE.md/AGENTS.md 本身要克制——2026 年经验是**聚焦的 400 token 上下文文件常优于 4000 token 的**，AGENTS.md 防膨胀规则（定期瘦身、拆 XX约束.md）需补进避坑点。

### 11. 上下文文件衰变无治理 —— P1 ✅ 已落地（2026-08-02）

- **问题**：AGENTS.md / CLAUDE.md / file_structure.md 随项目演进会过时、互相矛盾，没有 review 节奏，AI 读到过期规则反而被带偏。
- **世界级参照**：2026 context engineering 治理实践——上下文文件当代码管：标明 `last_updated`、定期 review（快变项目每月）、跨文件矛盾检查（CLAUDE.md vs AGENTS.md vs prompts）、显式 **anti-patterns 段落**（「不要做什么」比「要做什么」更防 AI 翻车）。
- **改进建议**：① AGENTS.md 模板加「禁忌清单（anti-patterns）」section 和文件头 `last_updated`；② Phase 5 每轮迭代收尾加「上下文文件 review」勾选项；③ Phase 4 review 时顺带检查各上下文文件是否与现状矛盾。

### 12. 进度文件长期累积无归档/压缩机制 —— P2 ✅ 已落地（2026-08-03）

- **问题**：「每一轮对话必更新进度」实跑后会产生几十上百个进度文件，新会话加载成本高、噪音大。目前只有拆分规则，没有「完结后怎么办」。
- **改进建议**：功能完结时加「**进度归档**」动作：把 `开发进度1..n.md` 压缩成一份 `<功能名>开发历程总结.md`（关键决策、踩坑、最终结果），原始文件移入 `archive/` 子目录或直接删除（git 历史已留痕）。全局开发进度总览只保留活跃功能详情 + 完结功能一行摘要。

## 五、验证层（Phase 4）

### 13. review 缺结构化清单与对抗式验证 —— P1 ✅ 已落地（2026-08-02）

- **问题**：「spawn 第二个 AI review」只有一句「这个函数有错或可改进吗？」，太随意——review 质量完全看 prompt 当时写得怎么样，不同轮次标准不一。
- **世界级参照**：Kiro 2026 有 hunk 级 AI review；业界做法是**分维度审查清单**（正确性/安全/性能/规格符合/可读性）+ **对抗式验证**（让 AI 专门试图反驳「这代码没问题」）+ AI-on-AI 多模型交叉。
- **改进建议**：
  1. 升级 `4-review.prompt.md` 为结构化清单：按维度逐项过，每项输出「确认无问题 / 发现：xxx」；强制包含「对照 PRD 验收标准逐条核对」「对照安全清单」「试图找出三个最可能藏 bug 的地方」。
  2. 高危功能（钱、权限、数据删除）规定**换模型**交叉审 + 人必审。

### 14. 验收标准无法自动执行，测试金字塔缺位 —— P2 ✅ 已落地（2026-08-03）

- **问题**：自动化测试「写并跑」没有结构约定——单测/集成/E2E 各写多少？覆盖率目标？全靠临场。验收标准（条目 3 解决后）也没有转成可执行测试的路径。
- **世界级参照**：BDD 场景直接生成测试骨架；property-based testing（Kiro 2026 把 EARS 转属性测试）；测试金字塔（单测多、E2E 少）。
- **改进建议**：① testing_strategy.md 模板加测试金字塔配比与关键路径覆盖率目标（如核心链路 80%）；② 约定「每条 AC 优先转成自动化测试，转不了的才进人工测试方案」——这能把人工测试方案的使用范围收得更准；③ E2E 只保关键路径（桌面端已有此原则，推广到全端）。

## 六、发布层（Phase 5）

### 15. CI/CD 只有一句话，缺最小 CI 定义 —— P1 ✅ 已落地（2026-08-02）

- **问题**：「接 CI/CD」没有说最小必须有什么，一个人公司容易一拖再拖。
- **改进建议**：部署手册模板加「最小 CI 清单」：push 触发 → lint + typecheck + 单测 + 构建 + Flyway 迁移校验（validate），全绿才允许部署；给出 GitHub Actions / Gitee Go 的起步 yaml 骨架。

### 16. 监控告警/看板的「接入动作」缺位 —— P1 ✅ 已落地（2026-08-02）

- **问题**：Phase 2 运维考量要求埋日志/指标/健康检查，但 Phase 5 没有「把这些埋点接进监控告警」的动作——埋了没人看 = 白埋。Phase 6 还规定删功能要清告警，但没有地方说告警最初在哪建。
- **改进建议**：Phase 5 动作清单加「**接入可观测性**」：日志收集（至少文件+轮转）、健康检查接入（uptime 监控）、关键指标告警（错误率/响应时间/磁盘）配置并记录到部署手册；产物加 `workflow_output/docs/ops/监控告警说明.md`（告警项 | 阈值 | 通知方式 | 处理预案），与 Phase 6 的「删功能清告警」闭环。

### 17. 依赖供应链安全与 secret 扫描无落地工具 —— P1 ✅ 已落地（2026-08-02）

- **问题**：security_strategy 提了依赖安全、部署手册提了别写明文密钥，但都没有工具落点和检查时机。
- **世界级参照**：2026 标配——Dependabot/Renovate 自动依赖升级 + `npm audit`/OWASP Dependency-Check 进 CI + **gitleaks** 类 secret 扫描进 pre-commit/CI。
- **改进建议**：security_strategy.md 模板加三节：依赖扫描工具与频率、secret 管理（.env 规范 + 扫描工具 + 泄漏应急）、安全更新响应 SLA（高危漏洞多久内修）。最小 CI 里挂上扫描命令。

### 18. 缺多环境配置管理规范 —— P2 ✅ 已落地（2026-08-03）

- **问题**：dev / 本地 / 生产 的配置差异（端口、数据库、密钥、开关）没有文档约定，部署手册只覆盖生产。
- **改进建议**：补 `workflow_output/docs/config/多环境配置说明.md`（文档总览里已列为「可能的补充」，建议对正式产品升级为标配）：每个配置项 = 各环境取值 | 来源（.env/环境变量/配置中心）| 敏感级别。

### 19. 缺对外 API 文档产出 —— P2 ✅ 已落地（2026-08-03）

- **问题**：前端联调、第三方对接靠翻代码。对「前后端分离 + 一个人全栈」场景，API 契约不清是联调返工主因。
- **改进建议**：约定 Phase 1 architecture 里定 API 契约（路径/入参/出参/错误码，可用 OpenAPI 简表）；Phase 3 接口完成即同步。小项目可合并进 architecture.md，对外开放的才单独产 `docs/api/`。

## 七、变更层（Phase 6）

### 20. 规格变更缺结构化 delta 格式 —— P2 ✅ 已落地（2026-08-03）

- **问题**：Phase 6 要求「更新 spec 并记录为什么改」，但怎么改没格式——直接在 PRD 上原地改，历史演进不可见，也看不出这次到底动了哪些需求。
- **世界级参照**：**OpenSpec delta** 是 2026 brownfield SDD 的标志性设计——变更只写 `## ADDED / MODIFIED / REMOVED Requirements`，合并时再同步进主 spec；天然支持多变更并行、可 review、可追溯。
- **改进建议**：变更记录模板升级为「变更规格 delta」：每条变更列出涉及的需求编号 + ADDED/MODIFIED/REMOVED + 原因；实施完成后 delta 回写 PRD 正文（sync），delta 文件归档。与条目 5 的 sync-before-merge 规则配套。

### 21. 缺质量/漂移度量指标 —— P2 ✅ 已落地（2026-08-03）

- **问题**：流程是否起效、文档是否可信，没有量化信号，全靠感觉。

### 22. 文档体系重，缺按项目规模的「最小必需集」裁剪表 —— P0 ✅ 已落地（2026-08-02）

- **问题**：全套 20+ 文档产物，正式产品该全走，但方法论只说「一次性脚本可跳过」——中间地带（小工具、内部系统、MVP 首版）没有明确裁剪指引，实操中要么全背（负担重、坚持不下来）要么全扔（失控）。
- **世界级参照**：SDD 社区的共识是「按上下文配工具」——prototype 用 vibe、production 用 SDD；Allegro 建议显式定义每级的必经产物。
- **改进建议**：在 `0_工作流总览.md` 加「**文档分级裁剪表**」：

  | 级别 | 场景 | 必产 | 可省 |
  |---|---|---|---|
  | L0 一次性脚本 | 跑完就扔 | 无（允许 vibe） | 全部 |
  | L1 小工具/MVP | 短期验证 | PRD 简版 + plan + 进度 + commit 纪律 | User-Ops、Feature Map 注解、性能/安全独立文档、部署手册 |
  | L2 正式产品 | 长期维护 | 全链 | —— |
  | L3 对外/合规 | 有第三方依赖方 | 全链 + API 文档 + ADR + 监控告警 + 安全 SLA | —— |

  并明确「级别可升降，升级时补产物」。

### 23. AI 工具生态产物滞后于 2026 现状 —— P1 ✅ 已落地（2026-08-02）

- **问题**：可复用 prompt 只有 `.github/prompts/`（Copilot 格式）。当前实际主力工具（Claude Code）有更高效的载体没用上：**Skills**（把重复流程固化成技能）、**subagents**（专职 agent 定义）、**hooks**（确定性自动化）、**斜杠命令**、**@导入** 防重复。
- **改进建议**：
  1. 项目模板加 `.claude/` 骨架：`skills/`（如「功能收尾」技能 = README+FeatureMap+UserOps+进度 一条龙）、`agents/`（reviewer 子 agent 定义）、`settings.json` hooks（见条目 8/9）。

  3. 评估是否直接采用/借鉴 Spec Kit 或 OpenSpec 半自动化现有流程（见条目 24）。
