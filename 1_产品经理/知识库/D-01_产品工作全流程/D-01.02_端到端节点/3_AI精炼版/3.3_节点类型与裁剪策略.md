## 按产品类型裁剪节点

七节点是完整版，不是所有产品都需要全流程。**核心原则：节点数 = 交付物传递关系数**——如果某两个角色间不存在"交付物传递"，该节点可合并或跳过。

### C端小功能（快速迭代）

| 裁剪策略 | 说明 |
|---|---|
| 合并"调研+分析" | 小功能不需单独调研，PM直接出需求 |
| 合并"设计评审"为"PRD自审" | 改动小，设计在PRD中描述即可，无需单独评审会 |
| 跳过"灰度"→直接AB测试 | C端小功能用AB测试替代灰度 |
| 压缩周期 | 1个Sprint(2周)内完成全链路 |

**适用**：按钮颜色调整、文案修改、小功能增删

### C端大功能（标准七节点）

| 裁剪策略 | 说明 |
|---|---|
| 保留全部七节点 | 交付物传递关系完整，不可省略 |
| 设计评审强制 | 大功能设计疏漏代价极大，必须评审 |
| 灰度+AB | 大功能必须灰度发布+AB测试 |

**适用**：新功能模块、重大改版、支付链路

### B端标准交付

| 裁剪策略 | 说明 |
|---|---|
| 增加"POC验证"节点 | 在分析定义后增加概念验证环节 |
| 增加"客户验收(UAT)" | 测试验收后增加客户方验收 |
| 增加"部署实施"节点 | 上线发布拆分为"部署+上线"两步 |
| 增加SLA确认 | 上线前确认SLA条款 |

**适用**：SaaS标准版交付、企业软件项目

### B端定制项目

| 裁剪策略 | 说明 |
|---|---|
| 增加"需求确认会签" | 客户方签字确认需求，避免后续扯皮 |
| 增加"方案评审(客户参与)" | 技术方案由客户方参与评审 |
| 增加"培训交付" | 上线后包含用户培训环节 |
| 增加"维保交接" | 项目交付后进入维保期 |

**适用**：大客户定制项目、政府项目

### 内部工具

| 裁剪策略 | 说明 |
|---|---|
| 合并"调研+分析+设计" | 内部需求方就是同事，口头确认+简单PRD即可 |
| 弱化"设计评审" | 内部工具无需精益求精 |
| 跳过"灰度" | 内部用户可控，直接上线 |
| 强化"数据埋点" | 内部工具上线后需要数据证明价值 |

**适用**：运营后台、数据看板、审批系统

## 节点间传递标准

| 上游节点 | 下游节点 | 传递物 | 质量门 |
|---|---|---|---|
| 需求调研 → | 分析定义 | 需求条目(含场景/来源) | 需求有"为什么"非只"做什么" |
| 分析定义 → | 设计评审 | PRD(含验收标准) | 功能边界清+异常流覆盖+技术可研 |
| 设计评审 → | 研发排期 | 评审通过的设计稿+技术方案 | 评审意见闭环+无未决问题 |
| 研发排期 → | 测试验收 | 可测版本+Test Case | 代码Review通过+冒烟测试通过 |
| 测试验收 → | 上线发布 | 测试报告+PM验收记录 | P0/P1=0+PM签字 |
| 上线发布 → | 运营迭代 | 上线通知+灰度数据 | 核心指标不退化+回滚方案就位 |
