# 3.2 不确定性管理与容错闭环

## 一、不确定性的根因

AI产品的不确定性并非缺陷而是本质——传统软件"输入确定→输出确定"，AI产品"输入模糊→输出概率"。四种不确定性根因：

| 根因 | 表现 | 来源 |
|---|---|---|
| **幻觉（Hallucination）** | 一本正经胡说八道，编造事实/引用/数据 | 模型概率生成本质 |
| **错误（Error）** | 计算/推理/工具调用错误 | 模型能力边界+工具失败 |
| **偏见（Bias）** | 群体/性别/地域/文化偏见 | 训练数据偏见 |
| **越狱（Jailbreak）** | 被诱导输出违规/有害内容 | 安全对齐不完善 |

> 2026数据：>50%外部AI安全威胁由提示词注入与越狱攻击主导；15%内部员工违规操作向公有云大模型上传敏感数据 [来源:腾讯云AI Infra安全 | 🔍高 | 2026-04]。详见 [D-19.06 AI风险合规](../../D-19.06_AI风险合规/1_知识库概览/0_模块路由.md)

## 二、容错闭环四件套（核心方法论）

应对不确定性的核心方法论——**可解释 + 可纠错 + 可撤销 + 可降级**四件套，缺一不可：

### 2.1 可解释（Explainability）

让用户理解"AI为什么这么输出"：

| 手段 | 说明 | 典例 |
|---|---|---|
| **引用溯源** | 输出附带来源链接 | Perplexity/百度文心一言/必应Copilot |
| **思考过程展示** | 推理模型展示CoT链路 | OpenAI o1/Claude/DeepSeek-R1的思维过程 |
| **置信度标注** | 标"我不确定"或概率 | 高风险场景明示置信度 |
| **错误承认** | 主动说"我不知道" | 模型自我认知边界兜底 |
| **影响因子** | 解释关键变量 | 决策类AI展示决策依据 |

> 设计要点：透明≠堆全部推理细节（认知负荷），而是关键节点可见+用户可深入展开

### 2.2 可纠错（Correctability）

让用户能让AI改对，而不是只能"重新生成"：

| 纠错方式 | 说明 | 典例 |
|---|---|---|
| **重新生成** | 整体重来 | ChatGPT"重新生成" |
| **局部编辑** | 用户改一处AI重生成其余 | Notion AI/Cursor Composer |
| **精准反馈** | 标记"这段不对"定向修改 | GitHub Copilot Chat高亮反馈 |
| **定向重生成** | 指定维度重做（"更简短/更正式/换数据源"）| Claude"改写风格" |
| **批注对话** | 在生成结果上批注讨论 | Figma AI/Cursor Composer |

> 设计要点：纠错粒度越细体验越好，但实现成本和模型能力要求越高

### 2.3 可撤销（Undoability）

AI操作可回退，鼓励用户尝试：

| 撤销机制 | 说明 | 典例 |
|---|---|---|
| **历史快照** | 每次AI操作前后存快照 | Notion AI版本历史 |
| **版本对比** | 多版本并列对比选最优 | Cursor Composer多版本对比 |
| **Undo栈** | 标准Ctrl+Z | Cursor/GitHub Copilot |
| **草稿-正式双轨** | AI生成进草稿,用户确认才生效 | 邮件起草/代码评审建议 |
| **沙箱预览** | 改动先在沙箱生效，确认才应用 | Devin代码沙箱 |

> 红线：删邮件/改代码/下单/转资金等高风险动作必须有Undo或二次确认

### 2.4 可降级（Graceful Degradation）

AI出错或服务不可用时的优雅降级路径：

| 降级路径 | 说明 | 典例 |
|---|---|---|
| **错误解释** | 友好说"出了什么问题" | 避免生硬技术报错 |
| **替代建议** | 给备选方案 | "我无法处理A，但可以B/C？" |
| **转人工** | AI无法处理转人工客服 | 客服Bot兜底转人工 |
| **重试机制** | 智能重试（换参数/换模型）| 模型超时自动切换备用模型 |
| **本地兜底** | 云端宕机时本地小模型兜底 | 边缘小模型兜底关键功能 |
| **明确边界** | 直接说"这个我做不了" | 防止硬撑导致幻觉 |

## 三、反馈纠错闭环设计

容错的最终目标是"用户纠错→数据回流→AI改进"闭环：

```
用户输入 → AI输出 → 用户反馈(点赞/重写/取消/批注) → 数据回流 → 模型/Prompt优化 → 下次输出更准
```

| 反馈类型 | 设计要点 | 数据用途 |
|---|---|---|
| **显性反馈** | 点赞/点踩/星级 | 训练偏好模型/Reward Model |
| **行为反馈** | 复制/编辑/放弃/重试 | 训练采纳率/重写率指标 |
| **纠错反馈** | 用户改了什么 | SFT/DPO训练数据 |
| **批注反馈** | 文字详细反馈 | 微调训练数据 |
| **场景反馈** | 在什么场景下用 | 帮助场景识别与路由 |

> 红线：反馈数据必须有"用户授权采集"前置，符合数据隐私合规（详见 D-16.01 数据隐私）

## 四、人在环路（HITL, Human-in-the-Loop）

AI辅助 + 人类决策 = 高风险场景标准范式：

| HITL强度 | 适用场景 | 设计要点 |
|---|---|---|
| **AI建议人决定** | 高风险决策（金融/医疗/法律） | AI给建议+置信度，人最终决策 |
| **AI执行人确认** | 中风险执行（删邮件/改代码/审批） | AI生成动作草稿，人确认后执行 |
| **AI执行人监督** | 低风险执行（智能回复/分类） | 人可见可干预，AI默认执行 |
| **AI全自主** | 极低风险（订阅管理/清理） | 仅事后通知，不需HITL |

> HITL设计关键：找到"AI效率提升"与"人类责任可控"的平衡点，避免"全自动高风险"或"全人工低效率"两个极端

## 五、可撤销性设计专门讨论

为什么"可撤销"在AI产品里特别重要：
- AI输出不确定，用户会想"试试看"，没有Undo就不敢试
- AI操作可能有副作用（删数据/改文件），Undo让副作用可控
- Undo鼓励探索，提升用户黏性
- Undo是建立AI信任的关键——用户知道"出错能回退"才敢放手用

实现层面：
| 操作类型 | 撤销方式 |
|---|---|
| 生成内容（文本/图像/代码）| 版本历史 |
| 修改文件/数据 | Git-like diff/事务回滚 |
| 执行动作（发邮件/下单/转账）| 草稿-确认双轨 |
| 修改配置 | 配置版本/快照 |
| 不可逆动作（删除/燃烧）| 二次确认+保留N天可恢复 |

## 六、个性化记忆与体验

2026主流AI产品已普遍支持个性化记忆：

| 记忆类型 | 典例 | 设计要点 |
|---|---|---|
| **偏好记忆** | ChatGPT Custom Instructions/Memory | 用户可查看/编辑/清除 |
| **项目记忆** | Claude Projects/ChatGPT GPTs | 项目级隔离，不污染其他对话 |
| **会话记忆** | 多轮对话上下文 | 自动管理，长对话会压缩 |
| **长期记忆** | AI陪伴产品/AI助手 | 跨会话持续累积，需遗忘机制 |

记忆设计红线：
- **透明性**：用户能查看AI记住了什么
- **可控性**：用户能编辑/删除记忆
- **隔离性**：项目/角色间记忆不混用
- **遗忘机制**：过时记忆要主动遗忘，避免污染
- 详见 [D-19.07 长期记忆系统专项](../../D-19.07_长期记忆系统专项/1_知识库概览/0_模块路由.md)

## 七、错误恢复路径设计

任何AI产品都必须预设"AI出错时怎么办"的恢复路径：

| 错误类型 | 恢复路径 |
|---|---|
| 模型超时/服务不可用 | 重试→切备用模型→本地兜底→友好报错 |
| 输出格式异常 | 解析失败→自动修正→降级为纯文本 |
| 幻觉/事实错误 | 用户反馈→记录→重生成→加入黑名单 |
| 越狱/有害输出 | 阻断→转人工审核→记录攻击模式 |
| 工具调用失败 | 重试→换工具→降级为"AI仅建议，人执行" |
| Agent长流程失败 | 检查点回退→人工介入→重新规划 |
