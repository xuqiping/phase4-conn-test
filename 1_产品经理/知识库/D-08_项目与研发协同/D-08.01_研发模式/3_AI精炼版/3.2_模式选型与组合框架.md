## 模式选型与组合框架

产品经理不必替团队选定研发模式，但必须理解：不同的产品阶段、团队规模和市场节奏，对研发模式有结构性约束。选错模式的代价远大于"选了不够完美"的代价。

[来源：DORA 2019-2025行业基准 + Larman大规模敏捷模式 | 置信度：A]

## 一、三维选型决策树

### 决策维度1：产品阶段

| 产品阶段 | 核心挑战 | 推荐模式 | 理由 |
|---|---|---|---|
| **0→1(探索期)** | 需求不确定、需快速试错 | **Scrum** 或 **Scrum+Kanban** | Sprint提供交付节奏+反馈循环；时间-boxed迭代容器化不确定性 |
| **1→N(成长期)** | 需求涌入、需快速上线 | **Scrum** 过渡到 **DevOps** | 业务增长要求更高部署频率；自动化基础设施开始投资 |
| **成熟期** | 稳定+微创新并行 | **双轨敏捷(探索轨Scrum+交付轨Kanban/DevOps)** | 探索新功能用Scrum，稳定功能用Kanban持续流动 |
| **衰退期** | 维护为主、变更少 | **Kanban** + 极简运维 | 低频变更不需迭代仪式，WIP限制防止有限人力过载 |

### 决策维度2：团队规模

| 规模 | 推荐模式 | 关键配置 |
|---|---|---|
| **1-5人** | Kanban 或 轻量Scrum | 跳过Scrum仪式，聚焦可视化+WIP限制；若需承诺节奏用1周Sprint |
| **5-9人** | Scrum | 经典配置：1个Scrum团队，PO+SM+Dev，2周Sprint |
| **10-30人** | Scrumban 或 多Scrum团队 | 2-4个Scrum团队+Scrum of Scrums；或统一Kanban看板跨团队 |
| **30-100人** | SAFe 或 LeSS | SAFe适合矩阵组织+合规需求；LeSS适合产品导向+强自组织 |
| **100+人** | SAFe + DevOps平台 | 加权:SAFe提供节奏对齐+依赖管理；DevOps平台提供技术自动化+跨团队发布 |

### 决策维度3：市场节奏

| 市场节奏 | 推荐模式 | 典型行业 |
|---|---|---|
| **日级发布**(每天多次) | **DevOps** + Feature Flag | 互联网/游戏/A/B测试驱动 |
| **周级发布**(1-2次/周) | **Kanban** 或 **Scrum(1周Sprint)** | SaaS/电商/内容平台 |
| **月级发布**(1次/月) | **Scrum**(2-4周Sprint) | 企业软件/B端SaaS/金融 |
| **季度级发布**(1-2次/年) | **瀑布/V模型** + 变更控制 | 医疗器械/航空/政府/银行核心 |

## 二、混合模式详解

现实中的团队极少使用"纯"模式。混合不是妥协，而是基于约束的理性选择。

### 2.1 Scrumban

**定义**：Scrum的节奏与角色 + Kanban的流动与WIP限制。核心思路：保留Sprint结构但取消Sprint承诺，改用WIP限制管理流量。

**适用信号**：
- Scrum团队频繁被中断请求打扰（Bug、生产事件、紧急需求）
- Sprint计划总被打破，团队对Sprint Goal失去信心
- 需要Scrum的回顾与透明度，但需要Kanban的灵活性

**关键配置**：
- 保留Sprint节奏(2周)用于回顾和规划，但不做Sprint Commitment
- 采用Kanban看板可视化，设置WIP Limit(通常每人1-2项)
- 按需拉取而非计划分配；优先级由PO实时调整看板顺序
- 引入服务级别预期(SLA)： Expedite(<24h)、Fixed Date、Standard、Intangible

**产品经理关注点**：Scrumban削弱了"何时交付"的可预期性——你需要从"承诺式"转向"概率式"预估（基于历史Lead Time分布预测交付时间）。

[来源：Corey Ladas Scrumban + Anderson Kanban蓝书 | 置信度：A]

### 2.2 双轨敏捷(Dual-Track Agile)

**定义**：探索轨(Discovery)与交付轨(Delivery)并行运行。探索轨用设计思维+用户研究验证假设；交付轨用Scrum/Kanban持续交付已验证需求。

**架构**：
```
探索轨：  用户访谈 → 假设定义 → 原型测试 → 伪代码验证 → 需求就绪
              ↕                 ↕                 ↕
交付轨：  Backlog → Sprint执行 → 集成测试 → 灰度发布 → 全量上线
```

**核心原则**：
- 探索1-2周跑完一个假设，交付1-2周跑完一个Story——节奏对齐
- 探索产出不是PRD，而是"已验证的用户需求+验收标准"
- 双轨不是两个团队，而是同一团队两种工作模式
- 最大的失败模式：探索轨变成"没有产出的研究"，交付轨变成"没有验证的堆功能"

**产品经理角色**：双轨敏捷中PM是探索轨的Driver——你负责设计假设-验证实验，而不是写PRD等交付。

[来源：Marty Cagan Inspired + Jeff Gothelf Lean UX | 置信度：A]

### 2.3 SAFe(Scaled Agile Framework)

**定义**：大规模敏捷框架，在Portfolio→Program→Team三层对齐节奏，以PI(Program Increment，8-12周)为规划单位。

**核心机制**：
- **ART(Agile Release Train)**：50-125人的虚拟组织，按PI节奏交付
- **PI Planning**：每PI开始时2天全员对齐，识别跨团队依赖
- **System Demo**：每2周跨团队集成演示，验证端到端价值
- **Inspect & Adapt**：每PI结束时量化回顾+改进

**适用信号**：
- 超过50人协同开发同一产品/产品线
- 跨团队依赖频繁且不可预测
- 组织需要Portfolio级投资优先级对齐
- 合规要求强制需要大量文档和审计追踪

**产品经理关注点**：
- SAFe中PM升格为Product Manager(战略) + Product Owner(战术)
- PI Planning是你的主战场——需要在2天内让5-10个团队对齐目标
- SAFe的"重量"是代价——确保你确实需要它，而不是"想显得正规"

**局限**：被批评为"敏捷的名义、瀑布的实质"；过度流程化可能窒息创新；不适合需求快速变化的小团队。

[来源：SAFe 6.0官方框架 + Critical分析(Facebook/Spotify反例) | 置信度：A]

## 三、选型决策流程（产品经理可操作版）

```
Step 1：识别主约束
  ├─ 合规强制文档追溯？→ 瀑布/V模型（选1，不可跳过）
  ├─ 团队<5人？→ Kanban
  ├─ 需求正在探索？→ Scrum
  └─ 已经有CI/CD且团队>10人？→ DevOps

Step 2：叠加次约束
  ├─ 中断频繁？→ +Kanban WIP限制
  ├─ 需要探索+交付并行？→ +双轨敏捷
  ├─ 超过50人？→ +SAFe对齐层
  └─ 安全合规要求？→ +DevSecOps

Step 3：验证选型
  ├─ 模式的核心假设是否与当前环境匹配？
  ├─ 团队是否具备该模式所需的最小能力？
  └─ 组织是否愿意承受该模式的变革成本？

Step 4：设置3个月回顾点
  └─ 度量指标恶化 → 触发选型复盘
```

[来源：作者基于DORA与敏捷实践综合 | 置信度：B]

## 四、选型常见陷阱

| 陷阱 | 表现 | 解法 |
|---|---|---|
| **跟风选型** | "大厂都在用DevOps" | 先评估自身约束，再参考行业标杆 |
| **名义改实不改** | 开Scrum站会但仍然瀑布式交付 | 审查：是否有Sprint Goal？DoD？增量可发布？ |
| **多重模式混用** | 同一团队同时跑Scrum+Kanban+瀑布 | 一个团队一套主模式，可叠加补充元素 |
| **忽略文化维度** | 只改流程不改考核——"Sprint交付"仍按里程碑考核 | CALMS模型：Culture→Automation→Lean→Measurement→Sharing |
| **一步到位** | 从瀑布直接跳DevOps | 渐进演进：瀑布→Scrum→DevOps，每步3-6个月稳固 |

[来源：DORA 2025"AI放大器"结论的推演+变革管理实践 | 置信度：B]
