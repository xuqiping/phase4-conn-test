# 3.2 Agent核心架构与自主性谱系

## 一、Agent核心架构：五件套

工程意义上的 Agent 不是"会调工具的 LLM"，而是一套**五件套**闭环系统。任一组件缺位都会退化成"LLM + 工具调用"，而非Agent。

```
┌─────────────────────────────────────────────┐
│              Agent 闭环系统                  │
│                                             │
│  [感知] → [规划] → [工具调用]               │
│              ↑          ↓                   │
│           [记忆] ← [执行/反思]              │
└─────────────────────────────────────────────┘
```

### 1. 感知（Perception）

- **职责**：接收用户输入、环境状态、工具返回，并将其结构化为 Agent 可处理的"上下文"
- **关键能力**：多模态理解（文本/图像/代码/结构化数据）、上下文压缩、状态追踪
- **产品决策点**：感知粒度（全量上下文 vs 滑动窗口 vs 选择性关注）、是否引入向量检索做长上下文召回
- **常见错误**：把感知等同于prompt拼接——缺少环境状态追踪（如游标位置的实时感知、文件树的快照）

### 2. 规划（Planning）

- **职责**：把用户高层目标分解为可执行步骤序列，并动态调整
- **主流范式**（详见二）：ReAct / Plan-and-Execute / Reflexion / Tree-of-Thought
- **产品决策点**：规划粒度（粗任务/细步骤）、规划频率（一次性 vs 每步重规划）、是否暴露规划给用户
- **常见错误**：让Agent一次性规划100步——长链路规划错误率指数累积，应"滚动规划"（规划2-3步，执行1步，再规划）

### 3. 工具调用（Tool Use）

- **职责**：选择并调用外部工具/函数/API，把工具返回值喂回上下文
- **核心机制**：Function Calling（OpenAI 2023首创）/ Computer Use（Anthropic 2024）/ Cloud Sandbox（2025主流）
- **产品决策点**：工具粒度（粗粒度少工具/细粒度多工具）、工具发现机制（静态列表 vs 动态MCP发现 vs 文档化RAG）、副作用工具的确认机制
- **深度见**：[3.1 形态对比](3.1_五形态全景与深度对比.md) 中的工具调用差异；D-24.03 工具调用专项

### 4. 记忆（Memory）

- **职责**：跨步骤、跨会话持久化状态，突破上下文窗口限制
- **三种记忆类型**：
  - **工作记忆**：当前任务的上下文窗口内信息（短时，易丢失）
  - **情景记忆**：本次会话内的事件流（用session store）
  - **长期记忆**：跨会话的用户知识/偏好/历史（向量库+知识图谱）
- **产品决策点**：记忆什么（任务状态/用户偏好/工具返回值/错误教训）、记忆检索机制（向量/时序/重要性评分）、隐私与遗忘机制
- **常见错误**：把记忆等同于RAG——记忆需"写入/检索/遗忘/更新"完整闭环，只有检索无更新等于只读历史

### 5. 执行与反思（Execution & Reflection）

- **职责**：执行规划步骤、检验结果、识别错误、自我纠错
- **关键能力**：自校验（结果schema校验、单元测试、回滚）、反思（Reflexion范式——失败后生成教训注入下次）、错误恢复
- **产品决策点**：反思频率（每步/每阶段/失败时）、是否暴露反思日志给用户、错误恢复策略（重试/换工具/回退/求助人）
- **常见错误**：只执行无反思——错误会沿链路放大；纯自反思无外部校验——Agent的"自我感动"无法识别系统性错误

> Agent = 感知 + 规划 + 工具调用 + 记忆 + 执行反思 五件套闭环。少任何一件，只是"LLM + 工具调用"。[来源:Anthropic Building Effective Agents | 🔍高 | 2024-12]

## 二、主流架构范式：四种Planning模式

| 范式 | 核心机制 | 适用任务 | 优势 | 劣势 | 典型实现 |
|---|---|---|---|---|---|
| **ReAct** | Reason+Act交替——思考一步→调一次工具→观察→再思考 | 短-中链路、信息检索型任务 | 简单、可解释、错误局部化 | 长任务易陷局部最优、无全局规划 | 早期LangChain Agent、ReAct原论文 |
| **Plan-and-Execute** | 先规划完整步骤序列→再逐步执行→执行偏差触发重规划 | 中-长链路、目标明确的任务 | 全局视野、可控、可中断 | 规划错误代价大、重规划成本高 | BabyAGI、LangChain Plan-Execute |
| **Reflexion** | 失败后生成"教训"reflection→注入下次尝试的上下文 | 试错可恢复任务（编码、解题） | 自我纠错、错误学习 | 反思质量依赖模型、可能强化错误 | Reflexion原论文、Devin自纠错 |
| **Tree-of-Thought (ToT)** | 树状展开多条思考路径→评估剪枝→选最优分支 | 搜索型问题（24点、创意写作、规划） | 探索多元解、突破线性思维 | 成本高（N倍推理）、对评估函数敏感 | ToT原论文、LangChain ToT |

### 范式选择决策树

```
任务是否需要探索多元路径？
├─ 是 → Tree-of-Thought
└─ 否 → 任务链路长度？
        ├─ 短(≤5步) → ReAct
        └─ 长(>5步) → 是否可试错恢复？
                      ├─ 是 → Reflexion增强的Plan-and-Execute
                      └─ 否 → Plan-and-Execute + 人机协同checkpoint
```

> 范式不是互斥的：2026主流Agent框架(如LangGraph、Claude Code)多采用**混合范式**——Plan-and-Execute做骨架、ReAct做局部、Reflexion做纠错、ToT做关键决策点。 [来源:LangGraph 文档 | 🔍高 | 2026-07]

## 三、自主性谱系：L1-L5

自主性是Agent最核心的产品属性之一。参考自动驾驶分级思路，Agent自主性可分五级：

| 等级 | 名称 | 定义 | 人介入 | 对应形态 | 典型产品 |
|---|---|---|---|---|---|
| **L1** | 工具增强助理 | LLM + 工具调用，每步都需人确认 | 每步 | 单Agent | 早期ChatGPT with tools |
| **L2** | 受监督Agent | Agent自主规划执行低风险步骤，高风险需人审批 | 关键节点 | 人机协同Agent | Cursor Agent+Review、Copilot Workspace |
| **L3** | 条件自主Agent | 任务级自主，满足条件全自主，越界触发人审 | 边界外 | 单Agent/多Agent | Devin（编码任务）、Claude Code（沙箱内） |
| **L4** | 高度自主Agent | 端到端自主完成领域任务，异常自恢复，仅结果交付人 | 异常时 | 多Agent/自主Agent | Manus、Anthropic 5-Agent系统 |
| **L5** | 全自主Agent | 给目标出结果，路径完全自主，跨域自适应 | 极少 | 自主Agent/Agent团队 | 前沿探索，无成熟产品 |

### 自主性升级的核心约束

- **L1→L2**：需引入风险分级 + Human-in-the-Loop 节点设计
- **L2→L3**：需引入沙箱/隔离环境 + 强schema校验 + 可回滚机制（无回滚则不敢放权）
- **L3→L4**：需引入自我反思 + 多Agent冗余 + 完备的记忆与状态管理系统
- **L4→L5**：需解决目标对齐（目标偏移检测）+ 跨域工具发现 + 长期价值约束（运行数千步仍不偏航）

> 自主性等级不是越高越好：L5 在高风险领域是灾难。产品决策应"任务风险×可逆性"驱动——可逆+低风险才能高自主，不可逆+高风险必须 L2 以下。 [来源:Agent自主性分级研究 | 📚中 | 2026]

## 四、单Agent三大结构性缺陷

为什么需要多Agent？因为单Agent有三种**结构性**缺陷，非模型能力提升可解：

### 缺陷1：上下文窗口压力（Context Pressure）

- **机理**：单Agent承担全流程，工具返回、中间状态、反思日志全堆在单一上下文，长任务必然溢出
- **表现**：长任务后段出现"忘记前文"、"重复已完成的步骤"、"工具调用参数错乱"
- **缓解手段**：上下文压缩、向量记忆外部化、滚动窗口——治标不治本
- **根本解**：多Agent分工——每个Agent只持有自己负责子任务的上下文，主Agent只汇聚结果

### 缺陷2：单点故障（Single Point of Failure）

- **机理**：单Agent错误无校验机制，错误沿链路放大
- **表现**：早期一步规划错，后面所有步骤都基于错误前提；工具调用幻觉无第二Agent兜底
- **缓解手段**：Reflexion自反思——但"自我感动"难识别系统性错误
- **根本解**：Critic Agent 专门做校验，Executor-Critic 分离打破自洽陷阱

### 缺陷3：能力天花板（Capability Ceiling）

- **机理**：单一模型在所有领域都顶尖不现实，单Agent能力受模型边界限制
- **表现**：跨领域任务（如"写代码+写文案+做财务分析"）某一环节明显掉链子
- **缓解手段**：模型路由（按任务切模型）——但路由本身是新的单点
- **根本解**：多Agent专业化——每个Agent绑定最擅长的模型与工具集

> 三大缺陷不是模型不够强，而是**架构局限**。GPT-5或Claude 4.5再强，单Agent在长链路复杂任务中仍会撞这三堵墙。这是多Agent协作在2026成为主流的底层逻辑。 [来源:Anthropic 多Agent报告 | 🔍高 | 2026-06]

## 五、架构选型方法

### 选型决策矩阵

| 任务特征 | 推荐架构 | 推荐自主性 | 推荐形态 |
|---|---|---|---|
| 短链路+领域单一+低风险 | ReAct 单Agent | L3 | 单Agent |
| 中链路+目标明确+可试错 | Plan-Execute + Reflexion | L3-L4 | 单Agent/多Agent |
| 长链路+跨域+复杂 | 多Agent + Critic + Plan-Execute | L3 | 多Agent协作 |
| 组织级+长期运行 | Agent团队 + 层级编排 | L3-L4 | Agent团队 |
| 高风险+合规要求 | 人机协同 + Plan-Execute + 强护栏 | L2 | 人机协同Agent |
| 可逆+低风险+目标明确 | 自主Agent + Reflexion + 沙箱 | L4 | 自主Agent |

### 三条选型红线

1. **不可逆操作不要 L3 以上**：删除生产数据、发送对外邮件、执行支付——必须 L2 人审
2. **高风险领域不要纯自主**：医疗、法律、金融交易——必须 L2 即使牺牲效率
3. **长链路不要单Agent**：超过 10 步的规划——必须多Agent或Plan-Execute+checkpoint

> 架构选型的本质是"用复杂度换可靠性"——简单的单Agent能满足就不要上多Agent；多Agent的通信开销与调试成本远超想象。先单Agent跑通，撞墙再升级。 [来源:Agent架构选型实践 | 📚中 | 2026]

## 六、2026 前沿观察

- **"框架比模型大7倍影响"**：Claude 在 SWE-bench 上，用 claude_code 框架达 100% 完成，而裸 tool_calling 仅 14%——同模型，框架（架构+工作流+护栏）的差距是7倍。架构选型不是辅助决策，是核心决策。[来源:Anthropic 内部技术分享 via 翁荔 SEAGym | 🔍高 | 2026-06]
- **翁荔 SEAGym 自进化评测**：指出"框架/harness 影响远超模型本身"——同一模型挂不同 harness，性能差几个数量级。Agent产品的核心竞争力在架构层而非模型层。[来源:SEAGym 论文 | 🔍高 | 2026]
- **Agent SDK 与 Managed Agents 趋势**：Claude API 演进路径——Messages原语 → AgentSDK（封装五件套）→ Managed Agents（托管编排）。架构正在从"自己拼组件"走向"平台托管"，但**架构选型决策不会消失，只是抽象层级上移**。[来源:Anthropic API演进 | 🔍高 | 2026-07]
