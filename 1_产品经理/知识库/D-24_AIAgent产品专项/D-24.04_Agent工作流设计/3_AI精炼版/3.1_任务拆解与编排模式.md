# 3.1 任务拆解与编排模式

## 一、为什么"如何拆任务"是工作流设计的核心

Agent 工作流的本质是"怎么把大任务拆成可串/可并/可中断/可恢复的子步骤，再按某种控制流跑到完成"。任务拆解决定三件事：（1）**可恢复性**——一个子任务崩了能不能只回滚到该子任务；（2）**并行度**——拆出的子任务能不能并行加速；（3）**可验证性**——拆出的子任务能不能单独判断成功失败。选择不同的拆解模式直接决定 Agent 的可靠性上限。

[来源:腾讯云《Agent设计模式全景图——从ReAct到Multi-Agent》| 🔍高 | 2026-05]

## 二、五种主流编排模式深度

### 2.1 ReAct（Reasoning + Acting）—— 一切 Agent 的起点

**机制**：Thought → Action → Observation 循环。每一步模型先推理（Thought：我应该做什么），再调一个工具（Action），拿到结果（Observation），推理下一步。整个上下文是一条线性追加的日志。

**伪代码**：
```
loop:
  thought = LLM.reason(history)          # 推理该做什么
  if thought.is_final_answer: break
  action = LLM.choose_tool(history)      # 选工具+生成参数
  obs = tool.execute(action)             # 执行
  history.append(thought, action, obs)   # 累加入上下文
```

**适用边界**：3–10 步的线性任务；每步工具可独立判断成功；任务有明确终止信号。
**崩点**：
- 上下文越长模型越笨（Context Rot），20 步以上开始绕圈
- 没有全局规划，遇到岔路靠模型临时判断，错误级联放大
- 工具失败时没有重规划能力，只会原地重试 → 死循环

[来源:ReAct原始论文 Yao et al. / 腾讯云 Agent设计模式 | 🔍高 | 2025-10/2026-05]

### 2.2 Plan-and-Execute（先规划后执行）—— 长任务主力

**机制**：分 Planner / Executor 两阶段。Planner 一次性生成结构化子任务列表（顺序+依赖），Executor 按序逐个执行子任务，每完成一步把结果回填给 Planner，Planner 决定是否重规划。

**伪代码**：
```
plan = Planner.generate(goal)            # 一次性规划全局
for subtask in plan:
  result = Executor.run(subtask)
  state.update(subtask, result)
  if result.failed or need_replan:
    plan = Planner.replan(goal, state)   # 重规划而非硬刚
return aggregate(state)
```

**适用边界**：10–50 步长任务；子任务有依赖关系；中途可能出现"原计划走不通"（需重规划）。
**崩点**：
- Planner 生成的计划本身质量决定全局——计划错则全错
- 重规划成本高（要重新走一遍 Planner 模型调用）
- 不擅长探索性任务（计划本身是未知的）

**Plan-and-Execute 与 ReAct 关系**：ReAct 是"边走边想"，Plan-and-Execute 是"先想好再走+走不通再想"。后者引入"重规划"能力，是 ReAct 不具备的——这是长任务主力不是 ReAct 的根本原因。

[来源:Plan-and-Execute 论文 / 腾讯云 Agent设计模式 | 🔍高 | 2025-11/2026-05]

### 2.3 Tree-of-Thoughts（树形思维）—— 探索性任务

**机制**：维护一棵搜索树，每个节点是一个推理状态，模型对每个节点 branched 生成多个候选下一步（thought），用 evaluator 评分，beam search 走得分最高的分支。失败可回溯到父节点换分支。

**适用边界**：探索性任务（数学/逻辑推理/创意生成）；有可量化的状态评估函数；解空间大需剪枝。
**崩点**：
- 模型 N² 调用成本（每层多分支 × 多深度）
- 状态评估函数难定义，评估错就是瞎剪枝
- 不适合"做动作"的工程任务，主要适合纯推理任务

**与 ReAct 关系**：ToT 是 ReAct 的"广度版"——ReAct 单线深入，ToT 多线探索+回溯。

[来源:Tree of Thoughts 论文 Yao et al. / 腾讯云 Agent设计模式 | 🔍高 | 2025-11/2026-05]

### 2.4 Reflexion（反思循环）—— 自我纠错

**机制**：在主 Agent 之外加一个 Reflector（反思者）。每轮主 Agent 完成子任务后，Reflector 用一个独立 LLM 调用评估"这一步做得对吗、哪里可改进"，把反思写入"经验记忆"，下一轮主 Agent 带着经验再跑。本质是用 verbal reinforcement（语言化强化）替代 RL：用自然语言反馈而非数值 reward。

**伪代码**：
```
memory = []                              # 经验记忆
for attempt in range(max_attempts):
  result, trace = Agent.run(task, memory)
  critique = Reflector.critique(trace, result)   # 反思
  memory.append(critique)                # 沉淀经验
  if result.success: break
```

**适用边界**：可重试任务（代码、测试、配置）；有客观验证信号（编译通过/测试 pass）；Reflector 评估靠谱。
**崩点**：
- 反思本身可能被"幻觉污染"——Reflector 编造不存在的错误
- 必须有客观验证信号托底，否则就是自欺欺人
- 经验记忆注入又增加上下文 token，加剧 Context Rot

**与 Plan-and-Execute 关系**：Reflexion 是"重规划"的轻量替代——不重新规划全局，只在失败处加经验再跑一次。

[来源:Reflexion 论文 Shinn et al. / 腾讯云 Agent设计模式 | 🔍高 | 2025-12/2026-05]

### 2.5 混合编排（Planner-Worker + Reflection）—— 工程主流

工程上没有人只用单一模式，2026 主流长 Agent 都是混合编排：

- **Planner-Worker**：主 Agent（Planner）做完计划后，把子任务下发给并行子 Agent（Worker），各 Worker 独立执行后由 Planner 汇总。这是 Plan-and-Execute 的多 Agent 化版本（多 Agent 细节见 D-24.05）。
- **ReAct 兜底**：每个 Worker 内部仍是 ReAct 循环跑子任务。
- **Reflexion 兜底**：Worker 失败时加反思重试。
- **Evaluator 把关**：Planner 拿到 Worker 结果后，调 Evaluator（独立 LLM）判断是否达标，不达标重做。

混合编排的工程价值在于"按任务阶段选最匹配模式"：规划阶段用 Planner / 执行阶段用 ReAct / 验证阶段用 Evaluator / 失败阶段用 Reflexion。

[来源:腾讯云 / Anthropic 多 Agent 报告 | 🔍高 | 2026-05/06]

## 三、模式选型决策框架

| 任务特征 | 推荐模式 | 理由 |
|---|---|---|
| 线性短任务（3–10 步），每步独立可验证 | ReAct | 简单可靠，无需规划开销 |
| 10–50 步长任务，子任务有依赖 | Plan-and-Execute | 可恢复、可重规划、可并行 |
| 探索性任务，解空间大需剪枝 | Tree-of-Thoughts | 多分支搜索+回溯 |
| 可重试任务，有客观验证信号 | Reflexion | 自我纠错，语言强化 |
| 复杂长任务，多子任务可并行 | Planner-Worker + Reflection | 分工+反思组合，工程主流 |
| 跨域/跨工具超长任务（50+步） | Plan-and-Execute + Multi-Agent + Compaction | 必须配套状态管理（见3.3） |

**选型红线**：
- 单一 ReAct 不许跑超过 20 步（Context Rot 必崩）
- 探索性任务不要套 Plan-and-Execute（计划本身是未知的不该硬规划）
- 没有客观验证信号的任务不要套 Reflexion（反思会自欺欺人）
- 50+ 步任务必须有 Compaction + 文件系统状态持久化配套（见 3.3）

[来源:腾讯云 Agent设计模式选型 / Anthropic Harness 报告 | 🔍高 | 2026-05/06]

## 四、各模式可靠性对照表

| 维度 | ReAct | Plan-and-Execute | ToT | Reflexion | 混合编排 |
|---|---|---|---|---|---|
| 最佳步数 | 3–10 | 10–50 | 5–20（推理） | 3–15 | 10–100+ |
| 可恢复性 | 差（从头重跑） | 好（回滚子任务） | 好（回溯父节点） | 中（重跑+经验） | 好（多层回滚） |

| 工程成熟度 | 高 | 高 | 中 | 中 | 高（2026主流） |
