## 背景

多 Agent 智能体平台需要选择完整的技术栈。核心需求包括：

- **前端**：需要支持复杂的拖拽式工作流画布编辑器、暗色主题系统、响应式布局
- **后端**：需要支持 REST API、JWT 认证、异步执行引擎、数据库访问
- **数据库**：需要存储结构化数据（用户、Agent、工作流定义、执行日志），支持 JSON 字段

选型原则：
1. 团队熟悉度优先
2. 社区活跃度和生态成熟度
3. 与项目需求的匹配度
4. 长期可维护性

## 决策1：前端框架 — Vue 3

### 候选方案

#### Vue 3

| 维度 | 评估 |
|------|------|
| Composition API | 原生支持，逻辑复用能力强，适合复杂组件 |
| TypeScript 支持 | 一等公民支持，Volar 提供优秀的类型推导 |
| 生态工具链 | Vite + Pinia + Vue Router，官方维护，一致性好 |
| 工作流画布 | Vue Flow 是专为 Vue 3 设计的流程图库，与框架深度集成 |
| 学习曲线 | 中低，模板语法直观 |
| 性能 | Proxy 响应式 + 编译优化，性能优异 |
| 社区 | 国内社区活跃，文档完善，中文资源丰富 |

#### React 18

| 维度 | 评估 |
|------|------|
| Hooks API | 函数式组件 + Hooks，逻辑复用灵活 |
| TypeScript 支持 | 良好，但类型推导不如 Vue 的 Volar |
| 生态工具链 | 极其丰富但碎片化（状态管理有 Redux/Zustand/Jotai 等） |
| 工作流画布 | React Flow 成熟，但需要 React 生态全套 |
| 学习曲线 | 中高，JSX + Hooks 心智模型较复杂 |
| 性能 | 虚拟 DOM diff，需要手动优化（useMemo/useCallback） |
| 社区 | 全球最大的前端社区 |

### 对比决策矩阵

| 评估维度 | 权重 | Vue 3 | React 18 |
|---------|------|-------|----------|
| 工作流画布适配性 | 25% | 9 | 8 |
| 开发效率 | 20% | 9 | 7 |
| TypeScript 支持 | 15% | 9 | 8 |
| 学习曲线 | 15% | 8 | 6 |
| 社区生态 | 10% | 8 | 10 |
| 性能 | 10% | 9 | 8 |
| 团队熟悉度 | 5% | 9 | 6 |
| **加权总分** | 100% | **8.75** | **7.35** |

### 决策理由

选择 Vue 3 的核心理由：
1. **Vue Flow 是决定性因素**：Vue Flow 是为 Vue 3 深度定制的流程图库，开箱即用的节点拖拽、连接、缩放能力，完美匹配工作流编辑器需求。使用 React 意味着选择 React Flow + 全套 React 生态，迁移成本高。
2. **Composition API 适合复杂组件**：工作流编辑器涉及大量状态管理（节点、边、选中状态、拖拽状态），Composition API 可以将相关逻辑组织在一起，比 React Hooks 更直观。
3. **国内生态优势**：Element Plus 组件库、中文文档完善，降低开发和问题排查成本。

## 决策2：后端框架 — Spring Boot

### 候选方案

#### Spring Boot 3.x (Java 17+)

| 维度 | 评估 |
|------|------|
| 开发效率 | 自动配置、Starter 依赖管理，开箱即用 |
| ORM 支持 | MyBatis-Plus / JPA / 原生 JDBC 均可集成 |
| 安全框架 | Spring Security 成熟，JWT 集成方案丰富 |
| 异步支持 | @Async + ThreadPool + CompletableFuture |
| 社区生态 | Java 生态最大框架，企业级最佳实践丰富 |
| 性能 | 单请求性能中等，但在本项目中不是瓶颈 |
| 部署 | 内嵌 Tomcat，JAR 一键部署 |
| 团队熟悉度 | 高，Java 是团队主力语言 |

#### Node.js (Express/NestJS)

| 维度 | 评估 |
|------|------|
| 开发效率 | 高，动态语言开发速度快 |
| ORM 支持 | Prisma / TypeORM / Sequelize |
| 安全框架 | Passport.js / 自定义中间件 |
| 异步支持 | 原生 async/await + 事件循环，I/O 密集型场景优秀 |
| 社区生态 | npm 生态极其庞大 |
| 性能 | I/O 密集型优秀，CPU 密集型（工作流执行引擎）较差 |
| 部署 | 单线程，需要 PM2 集群模式 |
| 团队熟悉度 | 中，团队以 Java 为主 |

### 对比决策矩阵

| 评估维度 | 权重 | Spring Boot | NestJS |
|---------|------|-------------|--------|
| 工作流执行引擎支持 | 20% | 9 | 5 |
| 安全框架成熟度 | 15% | 10 | 7 |
| ORM 支持 | 15% | 9 | 8 |
| 团队熟悉度 | 15% | 10 | 6 |
| 开发效率 | 10% | 8 | 9 |
| 部署运维 | 10% | 8 | 7 |
| 社区生态 | 10% | 9 | 7 |
| 性能 | 5% | 7 | 8 |
| **加权总分** | 100% | **9.00** | **6.75** |

### 决策理由

选择 Spring Boot 的核心理由：
1. **执行引擎需要多线程**：工作流执行涉及 Agent 调用、条件判断、并行执行等，Java 的 ThreadPool + CompletableFuture 比 Node.js 单线程模型更适合 CPU 密集型任务。
2. **Spring Security 生态成熟**：JWT + RBAC 的安全方案在 Spring 生态中有大量成熟实现，开箱即用。
3. **团队技术栈匹配**：团队以 Java 为主，Spring Boot 是最熟悉的框架。

## 决策3：数据库 — PostgreSQL

### 候选方案

#### PostgreSQL 15+

| 维度 | 评估 |
|------|------|
| JSON 支持 | JSONB 类型，支持索引，适合存储工作流节点配置和执行日志 |
| 扩展性 | 丰富的扩展生态（pg_trgm 全文搜索、PostGIS 地理等） |
| SQL 标准兼容 | 高度兼容 SQL 标准 |
| 性能 | 复杂查询性能优秀，适合多表关联 |
| 并发控制 | MVCC，读写不阻塞 |
| 数据类型 | 丰富的数据类型（数组、JSON、UUID、枚举等） |
| 运维 | 中等复杂度，工具链成熟 |

#### MySQL 8.0

| 维度 | 评估 |
|------|------|
| JSON 支持 | JSON 类型支持，但功能和索引不如 PostgreSQL JSONB |
| 扩展性 | 插件生态较小 |
| SQL 标准兼容 | 中等兼容 |
| 性能 | 简单查询性能优秀，复杂查询不如 PostgreSQL |
| 并发控制 | InnoDB MVCC，但写操作可能阻塞读 |
| 数据类型 | 基本类型齐全，JSON 支持较基础 |
| 运维 | 简单，工具链成熟，国内使用广泛 |

### 对比决策矩阵

| 评估维度 | 权重 | PostgreSQL | MySQL |
|---------|------|-----------|-------|
| JSON 支持（工作流配置） | 25% | 10 | 6 |
| 数据类型丰富度 | 15% | 9 | 7 |
| 复杂查询性能 | 15% | 9 | 7 |
| 运维复杂度 | 10% | 7 | 9 |
| 社区支持 | 10% | 8 | 9 |
| 扩展性 | 10% | 9 | 6 |
| 团队熟悉度 | 10% | 7 | 9 |
| 国内部署支持 | 5% | 7 | 9 |
| **加权总分** | 100% | **8.60** | **7.30** |

### 决策理由

选择 PostgreSQL 的核心理由：
1. **JSONB 是决定性因素**：工作流节点配置（config 字段）、执行日志的输入输出（input/output 字段）都需要存储灵活的 JSON 数据。PostgreSQL 的 JSONB 类型支持 GIN 索引，可以在 JSON 字段上高效查询。MySQL 的 JSON 类型功能较弱。
2. **GENERATED ALWAYS AS IDENTITY**：PostgreSQL 15 的标识列语法比 MySQL 的 AUTO_INCREMENT 更符合 SQL 标准，且支持更好的序列控制。
3. **丰富的数据类型**：PostgreSQL 原生支持 UUID、数组、枚举等类型，减少应用层的类型转换。
4. **复杂查询性能**：工作流执行需要多表关联（workflow + nodes + edges + agents），PostgreSQL 的查询优化器更成熟。

## 最终技术栈确认

| 层次 | 技术 | 版本 | 说明 |
|------|------|------|------|
| 前端框架 | Vue 3 | 3.4+ | Composition API + Script Setup |
| 前端构建 | Vite | 5.x | 极速 HMR，构建优化 |
| 状态管理 | Pinia | 2.x | Vue 3 官方推荐 |
| UI 组件库 | Element Plus | 2.x | Vue 3 企业级组件库 |
| 工作流画布 | Vue Flow | 1.x | 节点拖拽 + 连接 + 缩放 |
| HTTP 客户端 | Axios | 1.x | 请求/响应拦截器 |
| 后端框架 | Spring Boot | 3.2+ | Java 17+ |
| 安全框架 | Spring Security | 6.x | JWT Filter 链 |
| ORM | MyBatis-Plus | 3.5+ | 单表 CRUD + 复杂 XML SQL |
| 数据库 | PostgreSQL | 15+ | JSONB + 丰富数据类型 |
| 缓存 | Redis | 7.x | Token 黑名单 + 权限缓存 |
| 连接池 | HikariCP | 5.x | Spring Boot 默认 |
| 接口文档 | SpringDoc (Swagger) | 2.x | OpenAPI 3.0 |
