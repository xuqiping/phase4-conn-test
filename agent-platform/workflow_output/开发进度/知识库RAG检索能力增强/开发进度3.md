### Step6：AttachmentContentInjector 三路注入（commit 见 git log）

- **`knowledge/attachment/AttachmentContentInjector.java`**（新）：node metadata `attachMode` 命中后三路分流——
  1. 文本类：`attachmentText` 直注（上传时已预提取截 8000，此处按 `maxInjectChars` 可配复裁），零 IO 零 LLM；
  2. 图片：Redis 缓存（key=sha256(fileRef|visionModel|promptVersion)）命中直取；miss 实时 VLM——`fileStorageService.load(fileId, doc.createdBy, false)` 服务端以 **docOwner 身份**读原件（保密库请求者 fileRef 403 与注入正交），base64 → image+text 双 part `LlmRequest`（复用识图通道），**计费归户 docOwner**（`chat(req, createdBy)`，非检索请求者），`timeoutMs=2500` 超时/故障/空返回一律降级 `（原件内容暂缺）`；成功写缓存；
  3. 其余（PDF 等预提取失败）：不注入——node content 本身已是描述+关键词。
  - 注入块格式 `[附件 {originalName}] 内容：…`；超上限截断+「已截断，可下载原件查看全文」标注。
- **`AttachmentVisionCache.java`**（新）：StringRedisTemplate get/put，`rag:attach:vision:` 前缀，TTL 默认 30d（可配）；**Redis 任何故障按 miss 处理**（get null/put 静默丢+warn）——缓存只是省钱通道，不做检索单点。
- **RagRetrievalService 接线**：注入点在 `step8LoadEvidence`（I3 复校后）——/retrieve 调试与聊天 EvidenceResult 两条路径共用；注入块拼进 `Evidence.content` → **预算/事实提炼/答案生成同享**（fitToBudget 统一裁剪，天然计入证据预算）。📎 标志独立于注入成败：kill switch 关/文档已删/降级 → 标志保留内容仅描述。
- **标志透传三处**：`RagRetrieveVO.CitationVO`/`EvidenceVO` + `CachedPayload.CitationRef` 各 +`attachment` 布尔（缓存命中回放徽标不丢；旧缓存条目缺字段反序列化=false）；`buildVo` 引用构造点补 `.attachment()`（测试揪出：citations 有三个 builder 位点，漏了 buildVo 那处）。
- **配置**：`rag.recall.attachment.*`——`enabled`（kill switch：VLM 通道故障/费用异常回「仅描述」基线）/`maxInjectChars=8000`/`visionTimeoutMs=2500`/`visionMaxTokens=1024`/`visionCacheTtlDays=30`/`visionPromptVersion=v1`（进缓存 key，改提示词→全量重新识图）。
- **缓存失效（plan ④项偏离）**：不动 AnswerCacheService——Step2 的 `computeKnowledgeSnapshot` 双聚合已覆盖：附件换版→节点重建（新 id/新 content_hash）→快照变→旧答案缓存自然 miss。VLM 识图文本只在 Redis（TTL 30d）不入 DB 快照：识图文案变化不触发答案重算（可接受，答案缓存有自身 TTL）。
- **运维埋点**：识图命中/miss 实时完成（info，含 docId/model/chars）/降级（warn，含 err）全覆盖；traceId 走检索线程 MDC 既有格式。
