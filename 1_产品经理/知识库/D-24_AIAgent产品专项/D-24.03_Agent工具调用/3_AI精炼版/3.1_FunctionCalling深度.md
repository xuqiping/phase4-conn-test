# 3.1 Function Calling 深度

## 一、Function Calling 本质与工作原理

**本质**：Function Calling 不是模型"真的在调用函数"——模型只是根据你给的 Schema 描述，输出一段结构化 JSON（工具名+参数），你的代码解析 JSON → 调真实函数 → 把结果塞回对话 → 模型继续推理。整个过程模型完全依赖你写的 Schema 描述：描述含糊→传错参数，类型没说清→传错类型。这不是玄学，是工程问题。[来源:牛客科技Agent工程师学习路线 | 🔍高 | 2026-04]

**工具调用全流程（5步闭环）**：
1. **工具注册**：应用把可用工具列表（JSON Schema）告诉模型
2. **模型决策**：模型根据用户请求+工具描述，选择工具并生成参数（JSON）
3. **应用执行**：应用侧解析 JSON → 调真实函数/API → 获取结果
4. **结果返回**：把工具执行结果塞回对话上下文
5. **模型续推**：模型根据结果继续推理——可能直接回答，也可能发起新的工具调用

## 二、OpenAI vs Anthropic Schema 对比

| 维度 | OpenAI | Anthropic |
|---|---|---|
| **工具定义字段** | `name` / `description` / `parameters` / `strict`(可选) | `name` / `description` / `input_schema` |
| **参数Schema格式** | JSON Schema对象（type/properties/required） | JSON Schema对象（type/properties/required） |
| **严格模式** | `strict: true` 强制Schema校验，模型输出必须100%匹配Schema | 无独立strict字段，但依赖Schema描述精确性 |
| **工具列表结构** | `tools`参数为list，每项`{"type":"function","function":{...}}` | `tools`参数为list，每项直接是工具定义对象 |
| **强制调用** | tools存在时可强制工具调用，不自动fallback至自然语言 | 模型自主决策是否调用工具 |
| **API演进** | 2026 Responses API统一运行时，支持strict+并行调用 | Messages原语→多层Agent运行时演进中 |

[来源:OpenAI/Anthropic官方文档 | 🔍高 | 2026-07]

**PM选型建议**：追求参数可靠性选OpenAI strict mode（强制校验，杜绝参数幻觉）；追求灵活性和模型推理能力选Anthropic（Claude在复杂工具链推理上更强）；2026最佳实践是"Anthropic模型+strict-like校验层"（应用侧自建Schema校验补充）。

## 三、参数幻觉根因分析与防治

**参数幻觉（Parameter Hallucination）**：模型在生成工具调用参数时，产生类型错误、值错误、参数缺失、参数编造等问题。这是生产环境Agent第一杀手——2026-07生产级Agent故障分布中，参数校验失败占24%（仅次于工具调用死循环31%）。[来源:知乎生产级Agent故障分布 | 🔍高 | 2026-07]

**典型参数幻觉案例**：
- **类型幻觉**：模型把`amount`期望number填成字符串"100元"（带单位），把`currency`期望ISO 4217字符串填成数字1 → 支付创建失败
- **值幻觉**：模型编造不存在的枚举值（如status填"PENDING"但实际只有"pending"/"completed"）
- **缺失幻觉**：模型遗漏required参数（如调转账工具漏填`recipient`）
- **多余幻觉**：模型编造Schema中不存在的参数（如给查询API加`force`参数）

**参数幻觉根因**：
1. **Schema描述模糊**：描述没说清参数含义、单位、格式 → 模型靠猜（"金额"没说单位→填"100元"含单位）
2. **类型定义缺失**：没明确type是number还是string → 模型选错类型
3. **枚举不完整**：枚举值列表不全 → 模型编造不存在的值
4. **缺少示例**：纯文字描述不如示例直观 → 模型理解偏差
5. **工具过多**：10+工具列表让模型"看花眼" → 选错工具连带参数错

[来源:CSDN Function Calling参数类型系统 | 🔍高 | 2026-07]

**参数幻觉防治（5层防线）**：
1. **Schema层**：描述清晰+类型明确+枚举完整+示例补充+strict mode强制校验
2. **校验层**：应用侧JSON Schema校验（Pydantic/Zod等），类型/必填/枚举/范围全检
3. **反馈层**：校验失败时结构化错误信息回传模型（"amount期望number不带单位，你传了'100元'，请传100"），让模型自我纠错
4. **重试层**：参数错误自动重试（限3次），超限升级为人工干预
5. **监控层**：参数错误率监控+告警，错误率超阈值触发Schema优化

## 五、JSON Schema 设计原则

**核心原则**：Schema是模型的"工具使用说明书"——写得好模型准确调用，写得差模型频繁出错。

**6条Schema设计原则**：
1. **描述清晰精准**：用1-2句话说清工具做什么+什么时候用+不做什么；关键词前置（"查询订单状态，输入订单ID，返回订单当前状态"）
2. **类型明确无歧义**：每个参数必须标type（string/number/boolean/array/object）；金额用number不用string；日期用string+format:"date-time"
3. **枚举完整闭合**：枚举值必须列全，不留"等"字；用enum字段而非description描述可选值
4. **必填项标注**：required字段明确哪些参数必须填；可选参数在description说清默认值
5. **示例辅助理解**：复杂参数加example字段（"amount": {"type":"number", "example": 100, "description":"金额，数字类型，不带单位"}）
6. **Token预算控制**：工具描述占Token预算，10+工具时每个描述控制在100Token内；超出用分域加载

## 六、工具选择算法（模型如何选对工具）

模型选工具不是"读所有工具描述然后选最匹配"，而是受以下因素影响：
- **描述匹配度**：用户请求与工具description的关键词重合度
- **工具数量**：工具越多选择困难（10个以内最佳，20+需分域）
- **上下文影响**：前序对话可能误导工具选择（"刚才用了查询工具"→继续选查询）
- **参数可填性**：模型会倾向选"我能填出参数"的工具（即使选错）
- **工具名歧义**：名字相似的工具（query_order vs query_order_history）易混淆

**PM设计工具列表的建议**：
- 工具名唯一辨识度高（不相似、不歧义）
- 描述关键词不重叠（query工具的description别都写"查询"）
- 控制单Agent工具数≤10，超出用多Agent分工或动态发现
- 工具列表按使用频率排序（高频在前，模型更易选到）
