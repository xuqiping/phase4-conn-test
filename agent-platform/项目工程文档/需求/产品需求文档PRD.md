# PRD 产品需求文档 — 多Agent智能体平台

> 版本: 1.0 | 日期: 2026-05-25 | 作者: 产品团队 | 状态: 初稿评审中

---

## 一、产品概述

### 1.1 产品名称

**SuperCoder Agent Hub** — 多Agent智能体协作平台

### 1.2 产品愿景

将"超级程序员Agent"系统从文件驱动的命令行工具，升级为可视化、可协作的Web平台，让开发者和团队能像使用App Store一样发现Agent，像使用Figma一样编排工作流，从而将软件工程自动化门槛降到最低。

### 1.3 产品定位

| 维度 | 说明 |
|------|------|
| 目标市场 | 国内中小型研发团队（10-200人） |
| 核心价值 | 软件工程全生命周期Agent编排与自动化执行 |
| 差异化优势 | 15个预置专业Agent + 51个工程检查清单，开箱即用 |
| 竞品对标 | Dify（通用AI平台）、n8n（自动化工作流）、Coze（Bot平台） |
| 不做什么 | 不做通用AI对话、不做Agent市场交易、不做IDE插件 |

### 1.4 产品目标

| 目标 | 衡量指标 | MVP目标值 |
|------|---------|----------|
| 用户获取 | 注册用户数 | 100人（内测期） |
| 用户激活 | 首周创建工作流数 | ≥ 1个工作流/用户 |
| 用户留存 | 4周留存率 | ≥ 40% |
| 核心价值验证 | 工作流执行成功率 | ≥ 85% |

## 二、目标用户与使用场景

### 2.1 目标用户

| 用户角色 | 典型画像 | 核心诉求 | 占比 |
|---------|---------|---------|------|
| 开发者 | 28岁全栈工程师，个人项目为主 | 快速找到Agent，编排工作流提升效率 | 65% |
| 团队负责人 | 35岁技术Leader，管理8人团队 | 标准化团队流程，质量可控 | 25% |
| 企业管理员 | 42岁CTO，管理50人团队 | 安全合规，效率可度量 | 10% |

### 2.2 核心使用场景

**场景A — 个人开发者快速探索（日频）**
> 开发者张明打开平台，在Agent大厅浏览分类，找到"代码审查Agent"并查看详情。确认能力后，在工作流编辑器中拖入"编码Agent→代码审查Agent→测试Agent"，配置参数后执行。全程5分钟完成一个"编码-审查-测试"自动化流程。

**场景B — 团队标准化流程（周频）**
> 团队负责人李芳创建"标准开发流程"工作流模板，包含需求分析→架构设计→编码→代码审查→测试→部署6个Agent节点，并在关键节点嵌入检查清单。设为团队模板后，8名团队成员可直接复用。

**场景C — 管理员权限管控（月频）**
> CTO王磊为新项目组开通"部署Agent"使用权限，设置审批流程。月末查看统计看板，发现团队使用"测试Agent"的工作流成功率最高，决定推广最佳实践。

## 三、功能需求详述

### 3.1 登录认证

#### 3.1.1 登录页

**页面路由：** `/login`

**页面布局：**
```
┌──────────────────────────────────────────────────┐
│                                                    │
│   ┌──────────────────┐   ┌──────────────────────┐ │
│   │                  │   │  SuperCoder           │ │
│   │   品牌插画/      │   │  Agent Hub            │ │
│   │   产品截图       │   │                       │ │
│   │                  │   │  ┌─────────────────┐  │ │
│   │                  │   │  │ 用户名          │  │ │
│   │                  │   │  └─────────────────┘  │ │
│   │                  │   │  ┌─────────────────┐  │ │
│   │                  │   │  │ 密码            │  │ │
│   │                  │   │  └─────────────────┘  │ │
│   │                  │   │  [□ 记住我]           │ │
│   │                  │   │  ┌─────────────────┐  │ │
│   │                  │   │  │    登  录       │  │ │
│   │                  │   │  └─────────────────┘  │ │
│   └──────────────────┘   └──────────────────────┘ │
│                                                    │
└──────────────────────────────────────────────────┘
```

**功能规则：**

| 规则ID | 规则描述 |
|--------|---------|
| LOGIN-R01 | 用户名：4-20位字母、数字、下划线 |
| LOGIN-R02 | 密码：8-32位，必须包含大小写字母、数字、特殊字符中至少3种 |
| LOGIN-R03 | 登录失败提示统一为"用户名或密码错误"，不区分是哪个错误 |
| LOGIN-R04 | 连续5次失败锁定账户15分钟，锁定期间登录提示"账户已锁定" |
| LOGIN-R05 | 登录成功后颁发JWT Access Token（2小时）和Refresh Token（7天） |
| LOGIN-R06 | Access Token过期后使用Refresh Token无感刷新，Refresh Token过期跳转登录页 |
| LOGIN-R07 | 登录成功后跳转到Agent大厅页（`/hall`） |
| LOGIN-R08 | 已登录用户访问`/login`自动跳转到Agent大厅 |
| LOGIN-R09 | 密码输入框支持显示/隐藏密码切换 |

**数据流：**
```
前端表单 → POST /api/auth/login → AuthService.validate()
  → 成功：返回 { accessToken, refreshToken, user } → 存入localStorage + Pinia Store
  → 失败：记录login_attempts → 返回错误信息
```

#### 3.1.2 密码修改

**入口：** 右上角用户头像下拉菜单 → "修改密码"

**规则：**
- 必须输入旧密码进行验证
- 新密码不能与旧密码相同
- 新密码需满足复杂度要求（同LOGIN-R02）
- 修改成功后当前Token失效，需要重新登录

## 五、数据埋点方案

### 5.1 埋点原则

- 关键行为必埋：登录、Agent浏览、工作流创建、工作流执行
- 前端埋点优先：用户行为在前端捕获，通过统一SDK上报
- 数据量可控：高频操作（如鼠标移动）不埋，业务关键节点才埋
- 隐私合规：不采集用户密码、代码内容等敏感信息

### 5.3 埋点技术方案

```
前端埋点SDK (event-tracker.js)
  │
  ├── 自动采集：page_view, stay_duration
  ├── 手动埋点：track(eventName, params)
  ├── 本地缓冲：批量上报（每10条或每5秒）
  │
  ▼
POST /api/events/batch → EventService.batchSave()
  → 写入 Redis List（实时消费）
  → 异步落库 PostgreSQL events表
  → 按日聚合写入统计汇总表
```

**events表结构：**
| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGSERIAL | 主键 |
| event_name | VARCHAR(64) | 事件名 |
| user_id | BIGINT | 用户ID |
| session_id | VARCHAR(36) | 会话ID |
| params | JSONB | 事件参数 |
| client_timestamp | TIMESTAMP | 客户端时间 |
| server_timestamp | TIMESTAMP | 服务端时间 |
| ip_address | INET | 客户端IP |
