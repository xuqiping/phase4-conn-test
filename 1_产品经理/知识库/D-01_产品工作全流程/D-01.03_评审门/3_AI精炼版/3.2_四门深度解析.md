## 门一：立项评审（要不要做）

**触发条件**：新方向/新功能首次进入正式排期前

**评审材料**：
- 产品提案（1-2页）：问题/用户/解决方案/预期价值/资源预估
- 市场验证数据（如有）
- 与已有产品线的冲突/互补分析

**评审参与人**：PM Lead + 业务负责人 + 技术Lead + 设计Lead

**评审标准**：

| 评审项 | Go标准 | Kill信号 |
|---|---|---|
| 问题真实性 | 有用户反馈/数据佐证 | 纯"觉得有用"，无验证 |
| 用户价值 | 清晰的目标用户+场景 | "所有人都能用"（=没人在用） |
| 可行性 | 技术可研初步通过 | 需要核心架构改造 |
| 战略一致性 | 与产品方向一致 | 与核心产品冲突 |
| ROI预估 | 预期价值>投入2倍+ | 投入产出不合理 |

**常见错误**：
- 立项评审变成"汇报大会"——老板说做就做，没有真正的Go/Kill决策
- 只评"做什么"，不评"值不值得做"——缺少ROI维度
- 立项评审通过=排期开始，中间没有需求评审→细节在开发中才暴露

**反例**：某大厂立项"AI助手"只因竞品做了，无目标用户场景验证，开发3个月后因"没人用"下线 [来源:公开报道(隐去公司) | 置信度:📚中]

## 门二：需求评审（做什么/怎么做）

**触发条件**：PRD完成，设计/开发即将启动前

**评审材料**：
- PRD（含功能范围/用户故事/验收标准/异常流）
- 交互线框图/原型
- 技术可行性评估

**评审参与人**：PM + 设计 + 前端/后端开发 + QA

**评审标准**：

| 评审项 | Go标准 | Kill/Hold信号 |
|---|---|---|
| 功能边界 | 做什么+不做什么明确 | 边界模糊，开发者理解不一 |
| 验收标准 | 每个功能可测试 | "上线再看"——无标准 |
| 异常流 | 空态/错误态/边界态≥3个 | 只有正常流 |
| 技术可行性 | 方案已评审通过 | 关键技术未验证 |
| 非功能需求 | 性能/安全/兼容已标注 | 漏掉非功能项 |

**常见错误**：
- 需求评审不提前看材料→现场才看→2小时讨论不完
- 评审意见不记录→评完就忘→修改无追踪
- "需求评审=功能讲解会"——PM讲一遍就过了，没有质疑和挑战
- 评审后PRD改了但不通知开发者→开发按旧版实现

**评审效率优化**：
- **提前24h分发材料**：所有参与人评审前必须读完
- **异步预审**：评审前通过文档评论收集问题→会上只讨论未闭环的
- **时间盒**：需求评审不超过1小时，超时问题另行讨论
- **结论模板**：Go/Kill/Hold + 修改清单 + 闭环时限

## 门三：上线准入Go-NoGo（能不能上）

**触发条件**：测试完成，准备发布前

**评审材料**：
- 测试报告（P0/P1 Bug状态）
- PM验收记录
- 灰度/AB策略
- 回滚方案
- 上线后监控指标+告警阈值
- 运营/客服同步清单

**评审参与人**：PM + QA + 技术 + 运维/DevOps

**评审标准**：

| 评审项 | Go标准 | NoGo信号 |
|---|---|---|
| P0 Bug | =0 | 存在P0 |
| P1 Bug | =0（或有明确修复计划+不影响核心流程） | P1影响核心流程 |
| PM验收 | 通过签字 | PM未逐项验收 |
| 灰度策略 | 明确灰度比例+观察周期 | 无灰度直接全量（高风险产品） |
| 回滚方案 | 方案已验证 | 无回滚方案 |
| 监控告警 | 核心指标大盘+告警就位 | 未设监控 |
| 客服同步 | FAQ已提供 | 客服不知道新功能 |

**Go-NoGo仪式**：
- 快速（15-30分钟）：逐项过标准，有问题就NoGo，没就Go
- 不讨论"怎么做"——那是之前门的事
- 唯一决策：上还是不上

**常见错误**：
- Go-NoGo变"上线确认会"——走个过场就上了
- 不设NoGo红线——什么都能上
- 缺少回滚方案——上线出问题手忙脚乱

## 门四：复盘（做得怎么样）

**触发条件**：功能上线1-2周后（数据验证期结束）

**评审材料**：
- 核心指标达成数据
- 用户反馈归纳
- Bug/事故回顾
- 时间线：计划vs实际

**评审参与人**：PM + 设计 + 开发 + QA + 运营

**评审标准**：

| 评审项 | 关键问题 |
|---|---|
| 目标达成 | 核心指标是否达到预期？ |
| 过程回顾 | 哪些节点超时/质量不达标？ |
| 教训提炼 | 如果重来会怎么做？ |
| 后续动作 | 优化/扩展/下线的方向？ |

**复盘不是追责会**：
- 目标是"学习"不是"追究"
- 用5-Why分析法深挖根因，不止于表面
- 结论必须转化为Action Item（有人、有期限、可追踪）

**常见错误**：
- 复盘变"庆功会"——只说好的不说问题
- 复盘变"批斗会"——追责不学习
- 复盘无Action——"知道了"但不改
