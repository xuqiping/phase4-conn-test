# 3.5 AI辅助开发新术语（2025-2026）

> 本碎片收录2025-2026年AI辅助开发领域涌现的新术语。这些术语正在快速演化，定义尚未完全收敛，标注 ⚠️待核实（口径演化中）。

|---|---|---|---|

## 核心口径详解

### Vibe Coding（氛围编程）

**定义**：由计算机科学家 Andrej Karpathy 于2025年2月提出，描述一种全新的编程方式——开发者通过自然语言与AI对话来编写代码，不需要精通编程语法，只需能清楚表达想法。[来源:Andrej Karpathy社交平台发布 | 置信度:🔍高 | 日期:2025-02]

**核心特征**：
1. **人类只说需求**：用自然语言描述目标，AI负责写代码
2. **不追求代码理解**：开发者不需要完全理解AI生成的每行代码
3. **快速原型**：从想法到原型速度极快（分钟级）

**⚠️ 局限与争议**：
- "90-95%的Vibe Coding项目活不过两周"——代码能跑但没人敢改 [来源:知乎专栏综述 | 置信度:📚中 | 日期:2026-02]
- 缺乏工程规范→可维护性差、技术债快速积累
- 不适合大型/团队项目→代码风格不统一、缺乏测试覆盖
- ⚠️待核实（口径演化中）：Vibe Coding的适用边界仍在讨论中

**PM关注点**：
- 小团队/个人用Vibe Coding做MVP原型可行
- 企业级产品慎用→必须配合SDD或人工Code Review
- "用AI写代码"≠Vibe Coding，Vibe Coding特指不审视代码的"放手"模式

### SDD（规范驱动开发）

**定义**：2025年AI辅助编码领域涌现的方法论，核心理念是"先写规范（Spec），规范驱动AI生成代码"。与Vibe Coding的"随意描述"对立，强调结构化的需求描述作为AI代码生成的前置输入。[来源:CSDN/SDD工具链文献交叉验证 | 置信度:🔍高 | 日期:2025-2026]

**核心流程**：
```
编写Spec → Spec验证 → AI代码生成 → 自动化测试 → 人工审核
```

**SDD vs Vibe Coding**：

| 维度 | Vibe Coding | SDD |
|---|---|---|
| 需求描述 | 口头/随意/模糊 | 结构化/标准化/精确 |
| 代码质量 | 不确定，凭运气 | 可控，Spec即合约 |
| 可维护性 | 差，无人理解代码 | 好，Spec即文档 |
| 适用规模 | 个人/小项目 | 团队/企业级 |
| 学习成本 | 低 | 中（需学Spec格式） |

**PM理解要点**：
- SDD本质是"用更好的PRD驱动AI写代码"——PM写Spec的能力变重要
- Spec ≠ PRD：Spec更结构化、更面向代码生成，PRD更面向业务需求
- ⚠️待核实（口径演化中）：SDD工具链（Kiro/Spec Kit/Tessl）仍在快速迭代

### Harness Engineering（马具工程）

**定义**：由网易智企提出的概念，指"通过规范、流程和控制机制约束AI行为的工程方法"——如同给马上马具（Harness），让AI在受控范围内工作。[来源:界面新闻/网易智企 | 置信度:📚中 | 日期:2026-05]

**核心要素**：
1. **规范（Rules）**：定义AI编码的行为边界
2. **流程（Process）**：约束AI的工作流顺序
3. **控制（Control）**：对AI输出的审查和验证机制

**PM理解要点**：Harness Engineering是SDD的工程化延伸——从"写好Spec"到"全流程管控AI"。

### PM在AI辅助开发时代的术语变化

**2025-2026术语演进趋势**：
- PRD → Spec：需求描述向结构化、可机器解析方向演化 ⚠️待核实
- Code Review → AI Code Review + 人工审核：AI承担初筛
- 估算（SP）→ AI辅助估算：基于代码库历史的自动Story Point建议
- "写需求"→"写Spec+验证AI输出"：PM角色从需求编写者扩展为需求架构师
