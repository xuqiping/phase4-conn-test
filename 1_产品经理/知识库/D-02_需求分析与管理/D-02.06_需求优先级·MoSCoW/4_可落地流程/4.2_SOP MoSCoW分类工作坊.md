# 4.2 SOP MoSCoW分类工作坊

## 适用场景

PM需对一批需求进行MoSCoW分桶，确保Must不膨胀、Won't有声明。

## SOP步骤

### Phase 1：准备（30分钟）

| 步骤 | 操作 |
|---|---|
| 1.1 需求清单确认 | 每个需求有描述+KANO标签+RICE评分（如有） |
| 1.2 参与者 | PM+技术负责人+业务代表 |
| 1.3 打印标准 | 四桶判定标准（3.1碎片）人手一份 |

### Phase 2：分类（60-90分钟）

| 环节 | 操作 | 产出 |
|---|---|---|
| **Must确认** | 逐一确认："没有这个需求能上线吗？"→不能=Must | Must清单 |
| **Must占比检查** | 计算Must总Effort/总产能 → >60%则需降桶 | Must占比 |
| **降桶协商** | 对Must中RICE最低的需求协商：能否降为Should？ | 调整后Must |
| **Should分类** | 剩余需求中按RICE排序→前30-60%为Should | Should清单 |
| **Could分类** | 剩余中非Won't的→Could | Could清单 |
| **Won't声明** | 明确列出不做+原因 | Won't声明书 |

### Phase 3：确认与归档（15分钟）

| 步骤 | 操作 |
|---|---|
| 3.1 业务方签字 | Must和Won't清单需业务方确认 |
| 3.2 Sprint排期 | Must→Sprint Backlog, Should/Could→待排队列 |
| 3.3 归档 | 分类结果+讨论记录 |

## Must治理检查清单

```
□ Must占比≤60%资源？
□ 每个Must都能回答"没有这个能上线吗？"→不能
□ Won't桶不为空？（至少有2-3个Won't）
□ Won't的声明含原因+预计重评时间？
□ Could桶有明确的"捡漏"规则？
□ 业务方已确认Must和Won't？
```

## 常见问题

| 问题 | 应对 |
|---|---|
| 业务方坚持全是Must | "如果只能做3个呢？" → 迫使排序 |
| Won't怕得罪人 | "Won't≠不做，只是本次不做，下次可能做" |
| Must实在降不下来 | 拆分需求：核心=Muster，增强=Shoulder |
