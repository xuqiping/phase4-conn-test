# 3.1 多Agent拓扑与编排模式

## 一、多 Agent 必要性判定（先决策"该不该拆"）

在所有拓扑选型之前，最该回答的问题是**要不要拆**。错误地拆会把单 Agent 能搞定的任务搞成多 Agent 协调爆炸（65% 企业 MAS 失败的根本原因）。

### 1.1 Anthropic 智能阈值论

> "一旦智能达到一定阈值，多智能体系统就成为扩展性能的关键方式。" —— Anthropic 2026-06《Scaling Intelligence through Multi-Agent Collaboration》

阈值未到前 MAS 是负担：底层模型能力不够时，N 个弱 Agent 协调失败的概率叠乘（每个 Agent 失败率 10%，3 个串联即 27% 失败率）。阈值到达后 MAS 才成为性能放大器：N 个强 Agent 通过并行 + 关注点分离 + 上下文隔离能显著超越单 Agent。

[来源:Anthropic | 🔍高 | 2026-06]

### 1.2 何时该拆（拆的三大成立条件，三者必须同时满足）

1. **关注点分离成立**——任务能拆为 N 个子任务，每个子任务需要不同的工具集 / 提示词 / 探索路径。Anthropic 5-Agent 研究系统：每个 Subagent 工具集不同（搜索/Workspace/数据库）→ 减少路径依赖。
2. **并行探索成立**——子任务可并行执行而非严格串行。串行推理任务强制拆只会徒增协调开销。
3. **上下文隔离成立**——单 Agent 上下文窗口装不下全部子任务信息。否则单 Agent + 长上下文压缩更稳健（Cognition Devin 路线）。 [来源:Anthropic / Cognition via 知乎 | 🔍高 | 2026-06]

### 1.3 何时不要拆（不拆红线）

| 场景 | 不拆理由 |
|---|---|
| 串行推理任务（数学证明 / 长逻辑链） | 拆了之后 Agent 间上下文传递损失推理链 |
| 单 Agent 上下文窗口够装 | 强行拆只增加协调成本不增加价值 |
| 任务本身简单（5 步以内） | 协调开销 >> 拆分收益 |
| 模型能力阈值未到 | N 个弱 Agent 叠乘失败率 |
| 没有客观验证信号 | Validator Agent 会"橡皮图章"通过 |
| Real-time 交互（延迟敏感）| 协调开销通常引入 2-5 倍延迟 |

[来源:Redis Blog / Berkeley | 🔍高 | 2026-04/07]

### 1.4 Anthropic vs Cognition 路线分歧（行业必懂）

- **Anthropic 路线**：MAS 在复杂任务上比单 Agent 高 90.2% 研究质量（Orchestrator-Worker 架构，5 个 Subagent）。代价是 15 倍 token 消耗。
- **Cognition（Devin）路线**：单 Agent + 长上下文压缩 + 精细调度更稳健、好用、成本低。
- **PM 决策准则**：若任务并行探索价值 > 15 倍 token 成本，选 Anthropic 路线；若任务强串行 + 上下文可压缩，选 Cognition 路线；不要"为 MAS 而 MAS"。

[来源:Anthropic / Cognition via 知乎 | 🔍高 | 2026-06]

## 二、八种主流拓扑深度

### 2.1 Orchestrator-Worker（中央调度）—— 行业最高频

**结构**：1 个 Orchestrator（编排者）+ N 个 Worker。Orchestrator 理解任务 → 制定计划 → 分发子任务给 Worker → 各 Worker 执行后汇报 → Orchestrator 聚合输出。

**适用**：任务能清晰拆为多个独立子任务 + 最终结果需要统一聚合输出。研究任务 / 数据采集 / 多源汇总。

**崩点**：Orchestrator 单点瓶颈——它崩全崩。缓解：Orchestrator 状态必须 Checkpoint 持久化。

[来源:腾讯云 // 知乎 7 种模式 | 🔍高 | 2026-04/05]

### 2.2 Hierarchical（层级）—— 组织隐喻

**结构**：树状拓扑。顶层 Orchestrator → 中层 Manager Agent（多个）→ 底层 Worker Agent（更多）。每层只与上下层通信。

**适用**：复杂任务需要分层分解（如软件研发：CTO Agent → 前端/后端/测试 Manager → 各自多个 Engineer Agent）。Anthropic 建议从最简单模式起步时这是第二步演进。

**崩点**：层级过深 → 信息逐层失真（每个 Manager 各自压缩一次）。最多 3 层是工程经验上限。

### 2.3 Peer-to-Peer（点对点）—— Agent 自治

**结构**：无中心，每个 Agent 直接与其他 Agent 通信。Agent 自主决定是否请求其他 Agent 帮助。

**适用**：高自治场景 + Agent 数量少（<5）。P2P 适合 Agent 之间地位平等 + 任务动态生成。

**崩点**：Agent 数量 >5 后通信复杂度 O(N²) 爆炸，死锁/活锁高频出现。生产环境慎用。

### 2.4 Star（星型）—— 路由器模式

**结构**：1 个中心 Router Agent + N 个外围 Worker。Router 只负责路由决策不执行实质工作。比 Orchestrator-Worker 更"轻"——Router 不聚合输出，只转发。

**适用**：客服中心 / 工单分发 / 意图识别后路由到专门 Agent。

**崩点**：Router 误判是头号失败源。Router 必须有"低置信度时不动"机制（留人工或返回 FAQ）。

[来源:人人都是产品经理 // 腾讯云 | 🔍高 | 2026-04/06]

### 2.5 Mesh（网状）—— 完全联通

**结构**：每个 Agent 与其他所有 Agent 互联。完全分布式协作。

**适用**：极少。学术研究多 / 工程实践少。复杂群体涌现场景。

**崩点**：N>4 后通信复杂度爆炸，工程上几乎不可控。Berkeley 失败案例分析中 Mesh 拓扑的死锁率超过 70%。

### 2.6 Generator-Validator（评估器-优化器）—— 最简单最广泛

**结构**：2 个 Agent：Generator（生成）+ Validator（评估）。Generator 输出 → Validator 评估 → 不通过则反馈给 Generator 重来。循环至通过或达最大迭代次数。

**适用**：代码生成（Coder + Tester）/ 客服回复起草（草稿员 + 审核员）/ 创作修订。Anthropic 建议的"起步模式"。

**崩点**：Validator 与 Generator 共享同源 prompt 会导致"橡皮图章"——Validator 永远说 OK。Berkeley 实测：Validator 必须有独立评测集或 lint 规则才能真正把关。 [来源:Berkeley | 🔍高 | 2026-07]

### 2.7 辩论模式（Debate）—— 反幻觉利器

**结构**：N 个 Agent 围绕同一问题独立作答 → 互相反驳 → 最终投票或仲裁 Agent 终裁。

**适用**：高风险决策（医疗诊断 / 法律建议 / 投资）。降低单 Agent 幻觉。

**崩点**：N 个 Agent 用同一个底层模型时辩论会"集体同质化幻觉"。必须用不同模型或不同 prompt 派系才能产生差异化观点。

[来源:腾讯云《多 Agent 协作架构》| 🔍高 | 2026-04]

### 2.8 群体模式（Swarm）—— 大规模协作

**结构**：大量 Agent（10+）通过简单本地规则协作，涌现出集体行为。AutoGen Swarm 命名由此而来。

**适用**：极少工程实践。OpenAI Swarm 框架尝试但已被 Agentic Loop 范式取代。当前阶段"群体涌现"主要是失败涌现而非智能涌现。

**崩点**：行为不可预测 / 调试困难 / 失败级联无法追溯。Gartner 警告：群体模式生产环境慎用。

[来源:OpenAI Swarm / Gartner | 🔍高 | 2026]

## 三、Anthropic 五大工作流模式（与上面对照补充）

Anthropic 2026 提出"工作流 vs 智能体"二分法已成行业共识。五大工作流模式：

1. **提示链（Prompt Chaining）** = 串行 Pipeline。前一个 Agent 输出直接作为后一个输入。
2. **路由（Routing）** = Star 拓扑 + Router 决策。Router 分类后选 Worker。
3. **并行化（Parallelization）** = 一个任务拆为 N 子任务并行 + 最后汇总。Orchestrator-Worker 的并行版。
4. **编排者-执行者（Orchestrator-Worker）** = Orchestrator 动态决定子任务和顺序（不是预先规划）。
5. **评估器-优化器（Evaluator-Optimizer）** = Generator-Validator。

**与"智能体循环"关系**：五大工作流是"预定义控制流"，"智能体循环"是"模型自主决定控制流"。2026 主流是混合——外层用智能体循环、内层用工作流模式。

[来源:Anthropic // 阿里天池 | 🔍高 | 2026-06/07]

## 四、角色划分（Planner / Coder / Reviewer / Tester / Executor / Verifier / Orchestrator）

| 角色 | 核心职责 | 工具集典型 | 不能兼任 |
|---|---|---|---|
| Orchestrator | 整体编排 / 任务分发 / 聚合输出 | 状态管理 + Checkpoint | 任何 Worker |
| Planner | 任务拆解 / 顺序规划 / 重规划 | 无外部工具（纯推理） | Executor（不能既规划又执行） |
| Coder/Executor | 执行子任务（写代码 / 调 API） | 代码执行 / API 调用 | Reviewer（橡皮图章） |
| Reviewer | 评估 Coder 输出是否合规 | lint / 评测集 | Coder |
| Tester | 跑测试验证 | 测试框架 / CI | Coder |
| Verifier | 全局验收最终交付 | 黄金集 / 端到端测试 | Orchestrator |
| Router | 意图分类与派发 | 分类模型 | Worker |
| Arbitrator | 仲裁 Agent 冲突 | 规则引擎 / 优先级表 | 任何冲突方 |

[来源:腾讯云 / 人人都是产品经理 | 🔍高 | 2026-04/05]

## 五、三基因轴（10 种编排模式 DNA）

腾讯云 2026-07《一文解析多 Agent 编排架构模式全景》提出三基因轴框架：

- **控制拓扑轴**：集中（Orchestrator/Star/Hierarchical）vs 分布（P2P/Mesh/Swarm）
- **通信模式轴**：直接（请求-响应）vs 共享（黑板/共享内存）vs 委托（A2A/Skill）
- **状态管理轴**：无状态 vs 有状态 vs Checkpoint

任何 MAS 拓扑都可分解为这三个轴的组合。 例：Orchestrator-Worker = 集中 + 委托 + Checkpoint；Star = 集中 + 直接 + 无状态；辩论 = 分布 + 共享 + 无状态。

[来源:腾讯云 | 🔍高 | 2026-07]

## 六、MAST 分类法（Multi-Agent System Taxonomy）

Berkeley 2026-07 多 Agent 失败研究提出的 MAST 分类法，按四维度归因：

- **Specification（规格）**：任务规格不清导致 Agent 不知道做什么 → 79% 失败归因之一
- **Coordination（协调）**：Agent 间协调失败 / 信息丢失 / 死锁 → 79% 失败归因之二
- **Interdependence（相互依赖）**：Agent 间依赖未识别导致级联失败
- **Execution（执行）**：单 Agent 执行失败被放大

[来源:Berkeley / 知乎 | 🔍高 | 2026-07]

## 七、拓扑选型决策框架

| 任务特征 | 推荐拓扑 | 理由 |
|---|---|---|
| 串行推理 / 长逻辑链 | **不要拆** | 单 Agent + 长上下文压缩（Cognition 路线） |
| 复杂研究 / 多源汇总 | **Orchestrator-Worker** | 关注点分离 + 并行探索 + 聚合汇总 |
| 多角色组织协作（团队）| **Hierarchical（≤3 层）** | 模拟真实组织分工 |
| 客服 / 工单分发 | **Star（Router）** | 路由决策轻量 + Worker 各司其职 |
| 高风险决策降低幻觉 | **辩论（N Agent）** | 多视角分歧 + 仲裁 |
| 代码生成 + Review + Test | **Hierarchical + Generator-Validator** | Coder ↔ Tester 循环 + 统一编排 |
| 起步 / 简单场景 | **Generator-Validator** | Anthropic 建议的最简模式 |
| 跨组织 Agent 互联 | **Hierarchical + 契约化** | A2A 协议 + 契约 + 超时熔断 |

**选型红线**：
- 单 Worker 内部 ReAct 循环不许超 20 步（Context Rot 必崩）
- Hierarchical 层级不许超 3 层（信息失真）
- P2P/Mesh 中 Agent 数量不许超 5（O(N²) 通信爆炸）
- 辩论模式 N 个 Agent 必须用不同模型或不同 prompt 派系（否则集体同质化幻觉）
- Generator 与 Validator 不许共享同源 prompt（否则橡皮图章）
