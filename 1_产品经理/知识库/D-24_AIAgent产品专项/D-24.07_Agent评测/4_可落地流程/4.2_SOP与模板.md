# 一、4 套 SOP

## SOP 1：评测体系从0设计（先决策该不该上、上什么）—— 1-2 小时

**目标**：80% 评测体系过度设计源于 Demo 阶段就过度设计评测。本 SOP 保证 1-2 小时内决策"该不该上 + 上四维哪几维 + 选哪 2-3 个基准 + 是否上 LLM-as-Judge"。[来源:Gartner 2026-07 / 51CTO 2026 四维框架 12 指标 | 🔍高 | 2026]

**步骤**：
1. **诊断四问**（15 分钟）：① Agent 是否到了 MVP 完成准备上线？② 是否遭遇"Demo 漂亮但生产事故"？③ 是否需要向 ROI/合规汇报可信度量？④ 是否计划闭环到 RL？四问全否 → 暂缓
2. **失败代价评估**（15 分钟）：类比 Gartner 88% 项目无法跨越生产鸿沟 + 4.2 倍故障率，评估本场景不评的代价
3. **Agent vs LLM 评测差异判定**（15 分钟）：动态闭环（状态/多步/工具）触发？是 → 必须 Agent 评测；否（单轮 QA）→ 可继续 LLM 评测
4. **四维框架与 12 指标配齐**（30 分钟）：用模板 T1《评测指标配置表》四维并行 + 12 指标按场景裁剪
5. **基准选型**（30 分钟）：用模板 T2《基准选型对照表》按 Agent 类型选 2-3 个基准——至少 1 个领域基准 + 1 个通用基准 + 1 个失败模式基准（如 MAST）

**关键判定标准**：编码→SWE-bench，工具调用→TAU-bench，长程真实→Tool Decathlon（sota<30%），通用→GAIA，Web→WebArena，多 Agent→MAST（87% 失败率）；只看准确率是 Agent 评测第一大错，必须四维并行。

## SOP 2：LLM-as-Judge 设计（避免 30% 偏差）—— 2 小时

**目标**：KRAFTON AI 研究——LLM-as-Judge 有 30% 评测偏差。本 SOP 保证 Judge 设计 2 小时内完成四层 Judge 系统 + 四类偏差治理。[来源:KRAFTON AI / BabelJudge arXiv 2606.22329 / MM-JudgeBias Seoul NAVER KAIST 2026-05 / WebDevJudge ICLR'26 Oral | 🔍高 | 2026]

**步骤**：
1. **偏差基线认知**（15 分钟）：对标 KRAFTON 30% 偏差基线，明确本场景可接受偏差阈值（建议 ≤10%）
2. **四类偏差治理**（30 分钟）：用模板 T3《Judge 系统配置表》逐项配——位置偏差（随机化 + 双向）/ 跨语言偏差（BabelJudge）/ 多模态组合偏差（MM-JudgeBias）/ 场景特化偏差（WebDevJudge 类）
3. **Continuous Eval Pipeline 四层 Judge 系统**（30 分钟）：L1 单点 Judge → L2 多 Judge 投票 → L3 Meta-Eval（评评测的 Judge）→ L4 自适应 Judge
4. **Judge 选型与组合**（20 分钟）：人工（最准最贵）/ LLM（中）/ 规则（便宜但仅适用规则化任务）/ 混合
5. **Judge 校准**（25 分钟）：人工标注子集（建议 ≥200 例）校准 LLM Judge 偏差，偏差超阈值调参或换 Judge 模型

**关键产出**：偏差治理方案 + 四层 Judge 系统 + Judge 选型 + 校准基线。

## SOP 3：红队与安全评测（防注入防删库）—— 2 小时

**目标**：OpenClaw 越权删邮件、PocketOS 自主删库。本 SOP 保证红队设计 2 小时内完成三层防护 + 自动化红队工具链。[来源:Microsoft Azure AI Red Teaming Agent / ASB / OpenClaw / PocketOS 事故 | 🔍高 | 2026]

**步骤**：
1. **红队必上判定**（10 分钟）：破坏性操作 / 敏感数据 / 自主决策权限高 → 必上；纯信息查询 → 可暂缓
2. **工具链选型**（20 分钟）：Azure AI Red Teaming Agent（自动化红队攻防）+ ASB AI Safety Benchmark（安全基准评测）+ 自建补充
3. **三层安全防护**（40 分钟）：用模板 T4《红队测试 checklist》逐项配——输入层（防注入）/ 执行层（防滥用）/ 输出层（防泄露）
4. **反面教材防护核查**（20 分钟）：OpenClaw 越权删邮件 / PocketOS 自主删库 / Stanford/MIT/CMU 94% 记忆投毒（如本 Agent 有跨会话记忆需联动 D-24.06 § 4.1 第6段）
5. **红队频次与回归**（15 分钟）：上线前必测 + 季度回归 + 重大版本回归 + 红队结果入库可追溯
6. **跨会话记忆联动评估**（15 分钟）：如本 Agent 含跨会话记忆 → 联动 D-24.06 § 4.2 记忆安全自查清单 + 94% 投毒防御

**关键产出**：红队必上判定 + 工具链 + 三层防护 + 反面教材核查 + 跨会话安全联动 + 红队频次机制。

## SOP 4：可观测建设（防 Token 燃烧炉）—— 2 小时

**目标**：2026-07-13 Token 燃烧炉事故——Agent 陷入死循环单次对话消耗数十万 Token。本 SOP 保证可观测建设 2 小时内完成三件套 + 五层 Token 治理。[来源:腾讯云 2026-07-13 Token 燃烧炉 / EdgeOne Makers / LangSmith/Langfuse/Phoenix | 🔍高 | 2026-07]

**步骤**：
1. **可观测三件套配置**（30 分钟）：用模板 T5《可观测看板》配 Logs 日志（ELK）+ Metrics 指标（Prometheus）+ Traces 链路追踪（Jaeger/OpenTelemetry）
2. **Agent 独特挑战应对**（20 分钟）：非确定性输出→多次运行统计 / 复杂调用链→追踪 / 成本敏感→Token 计数 / 延迟波动→P99 而非均值
3. **Token 燃烧炉治理五层**（30 分钟）：L1 实时 Token 计数 → L2 业务维度归因 → L3 预算硬限制 → L4 熔断降级 → L5 成本告警
4. **LLMOps 平台选型**（20 分钟）：LangSmith / Arize Phoenix / Langfuse（自托管开源）/ Braintrust / Promptfoo（Anthropic 在用）——小团队优先 EdgeOne Makers 类内置方案
5. **告警与回归机制**（20 分钟）：成功率 <基线告警 / Token> 预算告警 / P99>SLA 告警 / 每周回归 + 每月归因报告

**关键产出**：三件套配置 + Agent 独特挑战应对 + 五层 Token 治理 + LLMOps 平台 + 告警与回归。
