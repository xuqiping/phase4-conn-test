# 3.3 埋点规范与治理

## I.10 Tracking Plan（埋点方案文档）

Tracking Plan是埋点治理的核心载体——所有事件/属性的统一定义、归属、状态管理。

### Tracking Plan必含字段

| 字段 | 说明 | 示例 |
|---|---|---|
| 事件名 | 标准化命名 | product_detail_view |
| 事件描述 | 业务含义一句话 | 用户浏览了商品详情页 |
| 采集模式 | 代码/可视化/全埋点 | 代码埋点 |
| 属性列表 | 事件携带的所有属性 | product_id, category, price |
| 属性定义 | 每个属性的类型/取值/必传 | product_id: String, 必传 |
| 触发时机 | 事件何时上报 | 页面加载完成后 |
| 责任人 | 产品/开发负责人 | 张三(产品)/李四(开发) |
| 状态 | 草稿/待开发/已上线/已废弃 | 已上线 |
| 版本 | 埋点版本号 | v2.1 |
| 关联指标 | 该事件支撑哪些指标 | 商品详情浏览率 |

## E.03 埋点常见坑

| 坑 | 症状 | 根因 | 修复 |
|---|---|---|---|
| 重复上报 | 同一事件计数偏高 | 页面刷新/断网重连导致重复上报 | 上报去重(ID+时间戳窗口) |
| 漏采 | 事件计数异常低 | 埋点代码未覆盖所有入口/条件分支 | 代码Review+自动化检测 |
| 属性缺失 | 属性值为空 | 后端字段未传入/前端取值逻辑错误 | 必传属性校验+默认值 |
| 命名冲突 | 同名事件含义不同 | 不同开发者自行定义未协调 | 统一事件字典+CR流程 |
| 版本漂移 | 旧版事件仍在上报 | 代码中移除埋点但旧版App仍在使用 | 事件版本化管理+兼容策略 |
| 时区混乱 | 时间对不上 | 客户端时区与服务端不一致 | 统一UTC+展示层转换 |

## I.06 埋点治理三板斧

### 1. 统一事件字典

- 全公司唯一的事件定义中心（单文件或平台）
- 新事件必须申请+审核，禁止私自埋点
- 事件命名、属性、口径全量对齐

### 2. 埋点CR流程

```
产品提需求 → 撰写埋点设计文档 → 数据团队Review → 开发实现 → 测试校验 → 上线验证
```

### 3. 定期审计

| 审计项 | 频率 | 方法 |
|---|---|---|
| 事件完整性 | 每月 | Tracking Plan vs 实际上报事件对比 |
| 属性填充率 | 每周 | 空值率报表，>5%需修复 |
| 重复上报率 | 每周 | 同一ID+时间窗口去重比率 |
| 废弃事件清理 | 每季度 | 连续3月无人使用的事件标记废弃 |
