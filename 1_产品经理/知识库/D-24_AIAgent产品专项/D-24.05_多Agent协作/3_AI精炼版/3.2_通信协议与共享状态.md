# 3.2 通信协议与共享状态

## 一、三种通信原语

MAS 中 Agent 之间通信本质就是"信息怎么传"。所有通信机制归为三种原语，所有协议栈都是这三种原语的工程化封装。

### 1.1 Blackboard 黑板模式

**机制**：所有 Agent 共享一个"黑板"（key-value 存储 / 关系型表 / 文档库）。每个 Agent 把自己的产出写到黑板，需要的 Agent 从黑板读。Agent 之间不直接通信，通过黑板间接协作。

**适用**：高度协作场景——Agent 之间需要参考别人发现的。Anthropic 5-Agent 研究系统本质就是 Blackboard——Subagent 把检索结果写到共享 context，LeadResearcher 从共享 context 读。同时是跨 Agent 状态同步的主力模式。

**崩点**：黑板上信息过载 → 每个 Agent 都要扫描全表 → 上下文爆炸；并发写竞争（多 Agent 同时写同一 key）需要锁机制。

[来源:腾讯云 / 知乎 | 🔍高 | 2026-04/05]

### 1.2 Message Bus 消息总线

**机制**：所有 Agent 连接到一个中央消息总线，通过 publish/subscribe 模式通信。Agent 发布消息到主题，订阅该主题的 Agent 接收。

**适用**：事件驱动流水线作业 + 系统不断扩展新 Agent 场景。新 Agent 只要订阅主题就能加入协作，无需修改其他 Agent。

**崩点**：消息丢失 / 顺序错乱 / 重复消费。需要消息队列基础设施（Kafka/RabbitMQ/Redis Streams）支撑。

### 1.3 SharedMemory 共享内存

**机制**：Agent 共享一块内存区域或共享文件系统（Git 仓库 / 共享文件夹 / 数据库）。Agent 通过读写共享内存间接协作。

**适用**：需要持久化状态 + 多 Agent 操作同一产物。代码工程团队协作 = Git 仓库作共享内存。

**崩点**：并发冲突 / 脏读 / 状态不一致。必须有锁或版本控制机制。生产环境重构陷阱之一：框架状态存在内存里 → 进程重启会话全丢。 [来源:福建开沿科技框架横评 | 🔍高 | 2026-07]

### 1.4 三种原语选型决策

| 场景 | 推荐原语 | 理由 |
|---|---|---|
| 跨 Agent 引用其他 Agent 发现 | Blackboard | 共享 context 直接读到 |
| 事件驱动流水线（前 Agent 产出触后 Agent）| Message Bus | 发布订阅解耦 |
| 多 Agent 操作同一产物（代码/文档）| SharedMemory | 持久化状态 + 版本控制 |
| 跨组织 Agent 互联 | A2A + AgentCard | 标准化协议 + 发现机制 |
| 高吞吐流式协作 | MessageBus + SSE | 异步流式 |

[来源:腾讯云 / 微博 | 🔍高 | 2026-04]

## 二、四协议栈分工（MCP / A2A / ACP / Skill）

2026 是 Agent 联网元年，多 Agent 通信协议已形成四协议栈格局。

### 2.1 MCP（Model Context Protocol）—— Agent ↔ 工具/资源

- **定位**：Anthropic 2024-11 推出，2026-07 Linux Foundation AI Agents Foundation 治理。标准化"Agent 调用工具 / 读取资源"。MCP 注册 Server 突破 10 万。
- **解决**：让 Agent 今天的数据库、明天的搜索、后天的文件系统调用走同一套协议。
- **典型用**：单 Agent 内部工具调用（D-24.02 详述规范）。

[来源:Anthropic / Linux Foundation | 🔍高 | 2026-07]

### 2.2 A2A（Agent-to-Agent Protocol）—— Agent ↔ Agent

- **定位**：Google 2025-04 Cloud Next 发布，2026 Linux Foundation 治理，2026-07 v1.0 GA。标准化"Agent 找 Agent 帮忙"。
- **核心原语**：AgentCard（Agent 名片，暴露 capability）/ Task（任务生命周期状态机）/ JSON-RPC（线格式）/ SSE 流式（实时推送）。
- **解决**：让不同公司、不同平台、不同框架的 Agent 互相发现、互派任务、互同步状态。
- **典型用**：跨组织 Agent 互联（Salesforce Agent ↔ ServiceNow Agent ↔ 自研 LangChain Agent）。

[来源:Google / chenxutan.com | 🔍高 | 2026-07]

### 2.3 ACP（Agent Communication Protocol）—— Agent ↔ 边缘 Agent

- **定位**：IBM Bee ACP。标准化"Agent 调度边缘 Agent"（如边缘设备上的轻量 Agent）。处理边缘协同场景。

### 2.4 Skill（Agent Capability Module）—— Agent 内置能力模块

- **定位**：Anthropic Skills + OpenAI 都推的能力模块化封装。把多 Agent 编排变成 Markdown 文件调用。Anthropic 推 Skill 后 API 账单和延迟同时暴跌 50%+。
- **何时用 Skill 而非 MAS**：当子任务可以"无状态调用"——既不需要 Subagent 持续上下文，也不需要双向通信——直接挂 Skill 更高效。Skill 是 MAS 的轻量替代。 [来源:Anthropic / 腾讯新闻 | 🔍高 | 2026-01]

### 2.5 四协议栈组合范式

| 协议 | 用途 | 何时选 |
|---|---|---|
| MCP | Agent 调工具 | 单 Agent 内部工具调用 / 多 Agent 各自调自己工具 |
| A2A | Agent 找 Agent | 跨 Agent 任务派发 / 跨组织 Agent 互联 |
| ACP | 边缘协同 | 边缘 Agent 协同 / 物联网场景 |
| Skill | 能力模块化 | 子任务无状态可调用 / 减少 MAS 编排开销 |

工程实践组合：MCP（工具栈）+ A2A（跨 Agent）+ Skill（无状态能力）通常一起用。ACP 只在边缘场景用。

## 三、共享状态管理

### 3.1 三层状态模型

- **无状态（Stateless）**：每个 Agent 调用独立，不依赖前次调用。简单可扩展但难以做长任务。
- **有状态（Stateful）**：Agent 持有跨调用状态。典型为对话历史。崩点：状态丢失则任务断。
- **Checkpoint（持久化状态）**：状态定期 Checkpoint 到持久化存储（数据库/文件系统）。崩了能从最近 Checkpoint 恢复。Orchestrator-Worker 必备。

### 3.2 分布式状态机（Distributed State Machine）

跨 Agent 状态同步的工程化方案——把整个 MAS 流程建模为状态机，每个状态转移由具体 Agent 触发，状态持久化到共享存储。

**例**：客服工单状态机 = 待处理 → 处理中（被某 Worker 接单）→ 待人工（升级）→ 已完成 → 已关闭。每个状态转移由特定 Agent 触发，状态持久化到工单数据库。所有 Agent 通过查工单状态判断是否到自己介入。

**崩点**：状态不一致（多 Agent 同时改状态）→ 死锁。Gartner 65% 多 Agent 项目失败中"状态不一致"是主要原因之一。 [来源:Gartner / 腾讯云 | 🔍高 | 2026-07]

### 3.3 Compaction（状态压缩）—— 与 D-24.04 共用

长任务共享状态会膨胀，必须定期 Compaction：
- L1 状态摘要：保留最近 N 步原始状态，更早压缩为摘要
- L2 关键事实提取：从历史状态提取关键事实存独立记忆
- L3 子任务结果归档：完成子任务结果归档为最终交付物 + 元数据指针
- L4 共享 context 重写：定期用新 Agent 重写主 context（Anthropic Subagent 把检索结果浓缩为高信号 tokens）
- L5 完整历史归档：原始日志冷存储

[来源:Anthropic / D-24.04 | 🔍高 | 2026-06]

## 四、冲突解决机制

多 Agent 同时操作同一资源或对同一问题有不同答案时，必须有冲突解决机制。

### 4.1 投票（Voting）

N 个 Agent 独立作答 → 多数决定。适合辩论模式降低幻觉。

**崩点**：N 个 Agent 同源会集体同质化投票。必须用不同模型或不同 prompt 派系。

### 4.2 仲裁（Arbitration）

冲突升级到独立 Arbitrator Agent 终裁。仲裁 Agent 用规则引擎 + 优先级表决策。

**适用**：高风险决策（合同审批 / 医疗诊断）。

### 4.3 优先级（Priority）

按预设优先级矩阵决定哪个 Agent 答案胜出。例：法务 > 风控 > 财务。

**适用**：组织型审批链 Hierarchical 拓扑。

### 4.4 契约化协作（Contract-based Coordination）—— 2026 共识

Gartner 2026-07 报告指出，行业已从"自由对话"转向"契约化协作"。每个 Agent 暴露标准化接口契约（输入 schema / 输出 schema / SLA / 失败重试策略），调用方按契约调用，违反契约由超时熔断兜底。

**契约四要素**：
1. **输入契约**：参数 schema + 校验规则
2. **输出契约**：返回 schema + 质量保证
3. **SLA 契约**：响应时间上限 / 吞吐量下限
4. **失败策略契约**：明确定义失败时返回什么 / 重试多少次 / 兜底是什么

契约化是 2026 协同可信时代的基础。 [来源:Gartner / 腾讯云《驯服多智能体混沌》| 🔍高 | 2026-07]

## 五、同步 vs 异步策略

### 5.1 请求-响应（同步）

调用方阻塞等待被调用方返回。简单可靠但延迟叠加。

**适用**：必须等结果才能继续的场景。

### 5.2 事件驱动（异步）

发布消息到总线后立即返回，订阅者异步处理。

**适用**：长任务 / 高吞吐 / 解耦场景。事件驱动流水线是 MessageBus 的典型用法。

### 5.3 流式 SSE（Server-Sent Events）

被调用方持续推送进度/中间结果，调用方实时接收。A2A v1.0 GA 标配。

**适用**：长任务实时反馈 / 用户需要看进度。Anthropic Claude 研究系统用 SSE 实时推送 Subagent 进度。 [来源:Google A2A | 🔍高 | 2026-07]

### 5.4 选型决策

| 场景 | 推荐策略 |
|---|---|
| 必须 etc 结果才能继续 | 同步请求-响应 |
| 长任务 + 高吞吐 | 异步事件驱动 |
| 用户需要看进度 | SSE 流式 |
| 跨组织不信任方 | 异步 + 契约化（对方挂了我有兜底） |

## 六、超时熔断与死锁预防

### 6.1 超时熔断（Circuit Breaker）

每个 Agent 调用必须有超时阈值。超过阈值熔断器打开 → 调用方立即返回兜底结果 → 不阻塞整个 MAS。

**三层熔断**：
- L1 调用级熔断：单次 Agent 调用超时（30秒/分钟级）
- L2 Agent 级熔断：某 Agent 连续 N 次失败，熔断该 Agent 一段时间
- L3 流程级熔断：整个 MAS 流程超时，触发全局兜底（人工 / 默认回复）

### 6.2 死锁预防

Berkeley 14 种失败模式之一是"循环死锁"——Agent A 等 Agent B，Agent B 等 Agent A。

**预防措施**：
- 禁止 Agent 间循环依赖（A 不能调 B 同时 B 调 A）
- 所有跨 Agent 调用必须有最大调用深度限制
- 引入 wait-die 或 wound-wait 算法处理死锁
- 异步任务必须有超时强制完成

[来源:Berkeley / 腾讯云 | 🔍高 | 2026-07]
