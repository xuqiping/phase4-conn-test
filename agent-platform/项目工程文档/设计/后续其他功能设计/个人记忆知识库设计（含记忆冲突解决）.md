# 记忆冲突交互式解决 — 设计文档

> 创建：2026-06-21
> 范围：用户长期记忆（`user_memories`）的冲突检测与交互式解决
> 依据：M6 记忆抽取实测（2026-06-20）暴露的冲突缺陷
> 关联代码：`chat/service/MemoryService.java`、`chat/service/ChatSessionService.java`、`chat/entity/UserMemory.java`

---

## 1. 背景与问题

### 现状
`MemoryService.upsertMemory`（[MemoryService.java:139](backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java#L139)）按 `(userId, memoryKey)` 字符串匹配：
- 命中同 key → 直接覆盖 value（无历史、无冲突检测）
- 未命中 → 插入新行

`memoryKey` 由抽取 LLM 自由命名，不稳定。

### 实证缺陷（2026-06-20 M6 补测）
发「女儿小红 5 岁」→ 再「更正为儿子小明 3 岁」，终态 DB：
- `child_1_name=小红`（女儿名，**未覆盖**）
- `子女概况=儿子小明`（新 key，与上行矛盾共存）
- `child_1_age 5岁→3岁`（同 key 静默覆盖，无历史）
- `has_daughter=小明`（key/value 语义错配垃圾）
- `child_1_gender=男`

**结果**：新旧矛盾全在库（女儿+儿子同时存在）+ 语义错配行。`buildMemoryContext` 注入全量（conf≥0.5，皆 1.0）→ 下游 LLM 收到矛盾上下文。

### 根因
1. LLM 自由命名 key 不稳定 → 同概念不同 key → 不命中 upsert → 矛盾共存
2. 偶然命中 key → 静默覆盖，无版本/无历史
3. 零冲突检测、无人工确认

---

## 2. 目标

- 新事实入库前，**语义归类到信息块**（block），与同块旧记忆比对
- 检测到语义冲突时，**不自动覆盖**，改用自然语言问用户保留哪条
- 用户 NL 回复后执行删除/保留决定
- 用户不答（无关/超时）→ **两条都入库并打冲突标志（FLAGGED）**，以后调用时直观可见「此记忆有冲突」
- 分块免人工维护（不靠枚举）

## 3. 非目标

- 不做记忆版本历史/审计日志（YAGNI，留未来）
- 不做多实例崩溃恢复 outbox（单实例部署，留未来）
- 不做前端 UI（后端端点 + VO 就绪，前端阶段6 一并做）
- 不改 RAG 向量知识库（`knowledge_*` 独立子系统，不碰）

---

## 4. 架构总览

```
用户消息
  ├─ 正常 LLM 回复（不变）
  └─ async: extractMemoriesAsync（仅记忆模式 ON）
        ↓ 抽取事实 K 条（LLM，已有）
        ↓ 每条事实：
        ① embed → 同 user 最近记忆 cosine
        │    ├ sim≥0.6 → 继承最近记忆的 block_label
        │    └ sim<0.6 → 新块（LLM 候选名一次性种子）
        ② 块非空 → LLM 冲突判定（batch，新事实 vs 同块成员）
        │    ├ 无冲突 → 直接入库（clean）
        │    ├ 有冲突 + 会话锁空 → 建 PENDING memory_conflicts，
        │    │     锁 session，助手下条改发 askText
        │    └ 有冲突 + 锁忙 → 直接 FLAGGED
```

**入口拦截**（`sendMessage`/`sendMessageStream` 开头）：每次先查 session 的活跃 PENDING：
- 活跃 → 答复路由（判用户这条是不是在答冲突）
- 超时 → 懒触发 FLAGGED
- 无 → 正常聊天

## 5. 数据模型（Flyway V27）

```sql
-- user_memories 加 3 列
ALTER TABLE user_memories ADD COLUMN block_label VARCHAR(100);
ALTER TABLE user_memories ADD COLUMN embedding halfvec(2048);   -- 记忆聚类专用（与 RAG 的 knowledge_embeddings_doubao 无关）
ALTER TABLE user_memories ADD COLUMN conflict_id BIGINT;        -- 指向 memory_conflicts，null=干净
CREATE INDEX idx_user_memories_block ON user_memories(user_id, block_label);
-- 暂不加 HNSW：每 user 几百条，brute-force `<=>` ORDER BY LIMIT 够；规模涨再加 hnsw(embedding halfvec_cosine_ops)

-- 冲突表（PENDING 待决 + FLAGGED 共存）
CREATE TABLE memory_conflicts (
  id                   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id              BIGINT NOT NULL REFERENCES users(id),
  session_id           BIGINT REFERENCES chat_sessions(id),   -- 锁持有者
  block_label          VARCHAR(100),
  new_memory           JSONB NOT NULL,        -- {category,key,value,confidence}
  new_embedding        halfvec(2048),          -- 复用，免二次 embed
  existing_memory_ids  BIGINT[] NOT NULL,      -- 冲突的旧记忆 id
  ask_text             TEXT,                   -- 给用户的 NL 提问
  status               VARCHAR(20) NOT NULL DEFAULT 'PENDING'
                       CHECK (status IN ('PENDING','FLAGGED','RESOLVED')),
  resolution           VARCHAR(20),            -- KEEP_NEW/KEEP_OLD/KEEP_BOTH/DISCARD/FLAGGED
  created_at           TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
  resolved_at          TIMESTAMP WITH TIME ZONE,
  expires_at           TIMESTAMP WITH TIME ZONE   -- created_at + 10min
);
CREATE INDEX idx_memconf_session_pending ON memory_conflicts(session_id) WHERE status='PENDING';
CREATE INDEX idx_memconf_user_flagged ON memory_conflicts(user_id) WHERE status='FLAGGED';
-- 并发保证：每会话≤1 活跃 PENDING
CREATE UNIQUE INDEX uq_memconf_session_pending ON memory_conflicts(session_id) WHERE status='PENDING';
```

**不变量**：
- PENDING 时新事实**不入 user_memories**（快照存 memory_conflicts.new_memory），旧冲突行原样留
- FLAGGED 时新事实入库，新旧行 `conflict_id` 都指同一 conflict 行 → 分组
- RESOLVED 后相关行 `conflict_id` 置 null（loser 已删）

## 6. 分块机制（embed 聚类，免维护）

### 归块算法
```
new_fact → embed (doubao-embedding-vision, 2048)
  → SELECT block_label, embedding <=> ? AS dist
      FROM user_memories WHERE user_id=? AND embedding IS NOT NULL
      ORDER BY dist LIMIT 1
  → sim = 1 - dist
  ├ sim≥0.6 → block_label = 近邻行的 block_label（继承）
  └ sim<0.6 → block_label = LLM 候选名（新块种子，一次性）
```

### 稳定性保证
- 新块：block 候选名由**抽取调用本身**产出——扩展 `EXTRACTION_PROMPT`（[MemoryService.java:28](backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java#L28)）让 LLM 每条事实多输出一个 `block` 候选字段。该候选名**仅在 sim<0.6 开新块时被采用**（一次性种子）；sim≥0.6 时被近邻继承的 block_label 覆盖、丢弃。故候选名不稳定也不影响（只用一次）
- 同块后续事实：**不问 LLM 块名**，靠 embedding 近邻继承
- 结果：块名定一次后冻结，无「家庭/家庭信息/子女」漂移

### 模型
- 抽取 + judge + 答复路由：默认全 `doubao-seed-2.0-code`（统一），`RagConfig.memory.judgeModel` 可配轻模型 hook（judge/路由优先切轻模型降本）
- embed：`doubao-embedding-vision`（同 RAG provider，不同表）

### 参数（`RagConfig` 可调）
- `memory.blockSimThreshold` = 0.6（归块门槛）
- 模型复用 `doubao-embedding-vision`（与 RAG 同 provider，不同表）

## 7. 冲突检测（LLM judge，batch 1 次/消息）

仅当事实落入**非空块**时触发（新块无成员 → 跳过 → 直插）。

```
input:
  new_facts: [{idx, category, key, value}]   # 本消息抽出的 K 条
  block_members: [{id, key, value}]           # 同块全部旧记忆
output JSON:
  [{factIdx, isConflict, conflictingIds[], askText}]
```

- `askText` = 给用户的 NL 提问，如「你之前记着有个女儿小红，现在说有个儿子小明，保留哪条？」
- batch：K 条事实合并 1 次调用（不每条 1 call）
- 模型默认 `doubao-seed-2.0-code`（统一），`RagConfig.memory.judgeModel` 可配轻模型 hook
- 失败 → fail-safe「无冲突」直插（绝不丢新事实）

**为何 embed 判不了冲突**：女儿/儿子向量高度相似（同主题，高 cosine）却矛盾。embed 只管分组，矛盾判定靠 LLM 语义 judge。

## 8. 会话锁交互

### 8.1 PENDING 创建
冲突检测命中 + 该 session 无活跃 PENDING：
- INSERT memory_conflicts（status=PENDING, session_id, new_memory 快照, new_embedding, existing_memory_ids, ask_text, expires_at=now+10min）
- **不插** user_memories（新事实暂存快照）
- 旧冲突行原样留

### 8.2 入口拦截（sendMessage / sendMessageStream 开头）
每次进来先查 `memory_conflicts WHERE session_id=? AND user_id=? AND status='PENDING'`：
- **查到 + expires_at>now**（活跃）→ 走答复路由（8.3）
- **查到 + expires_at≤now**（超时）→ 懒触发 FLAGGED（8.5），当无 PENDING 处理后续
- **没查到** → 正常聊天流程

懒过期：不加 `@Scheduled`，下次访问才清。

### 8.3 答复路由（1 次 LLM）
```
input: 用户新消息 + ask_text
output: {isAnswer:bool, decision:KEEP_NEW|KEEP_OLD|KEEP_BOTH|DISCARD|UNCLEAR}
```
- `isAnswer=true && decision≠UNCLEAR` → 执行决定（8.4），PENDING→RESOLVED，助手回短确认，**跳过主 LLM**（这条是答复不是查询）
- `isAnswer=false`（无关）→ FLAGGED（8.5），PENDING→FLAGGED，然后**正常处理这条消息**（用户在聊别的）
- `UNCLEAR` → 当无关处理（FLAGGED）

### 8.4 决定执行
| decision | 动作 | conflict_id |
|----------|------|-------------|
| KEEP_NEW | 插新（embedding+block）+ 硬删 conflictingIds | 新行 null |
| KEEP_OLD | 丢新（不插）+ 旧留 | 旧 null |
| KEEP_BOTH | 插新 + 旧留（用户明选都留→不打标）| 新旧 null |
| DISCARD | 删旧 + 不插新 | — |
| FLAGGED | 插新 + 新旧 conflict_id 都指本行 | 新旧都指本 conflict |

执行后 conflict 行 status=RESOLVED（或 FLAGGED），resolved_at=now。

### 8.5 FLAGGED（无关/超时/UNCLEAR）
- 插新事实入 user_memories（embedding+block_label）
- UPDATE 新行 + 旧 conflictingIds 行 `conflict_id = 本 conflict.id`
- conflict 行 status=FLAGGED

## 9. FLAGGED 可见性（3 处「直观看到」）

### 9.1 buildMemoryContext 注入（下游 LLM 可见）
flagged 行加前缀，counterpart 值经 conflict_id join 取：
```
[⚠️冲突] child: 儿子小明 （与旧记录"女儿小红"冲突，待澄清）
```
conf<0.5 的记忆不注入（现有规则不变）；flagged 但 conf≥0.5 仍注入（带冲突标）。

### 9.2 /memories VO 加字段
`UserMemoryVO` 加：`conflictId / conflictStatus / conflictWith`（counterpart 摘要）。前端阶段6 建好后展示 flag。

### 9.3 冲突端点（方案 B，list + resolve）
- `GET /api/chat/memories/conflicts` → 按 conflict 分组返回 FLAGGED：
  ```json
  [{"conflictId":101,"block":"家庭信息",
    "candidates":[{"id":7,"value":"女儿小红"},{"id":8,"value":"儿子小明"}],
    "status":"FLAGGED","askText":"..."}]
  ```
- `PUT /api/chat/memories/conflicts/{id}/resolve` body `{"decision":"KEEP_NEW"}` → 原子解决（8.4），一次调用两边联动 + 清 conflict_id
- 权限：用户私有资产，按 current userId 隔离（同 `/memories`），无需 knowledge/chat 权限

## 11. 边界与降级

- **锁忙时又冲突**（一条消息抽多事实、或 PENDING 中再来冲突）→ 直接 FLAGGED（不等问）
- **WORKFLOW/AGENT 抽取**：经 ChatSessionService 有 sessionId → 锁适用；回调式无后续用户消息 → 懒过期 → FLAGGED（可见即可）
- **LLM/embed 失败**：抽取已有 catch+log；judge 失败 → fail-safe 无冲突直插；路由失败 → 当无关 FLAGGED。**绝不丢新事实**
- **并发**：partial unique `WHERE status='PENDING'` on session_id → 物理保证每会话≤1 PENDING
- **gate**：记忆模式 OFF → 全链路跳过（含拦截/judge/embed），现状不变

## 12. token / 成本

每消息（记忆模式 ON + 抽出≥1 事实）：
- 抽取 chat：≈现状（+~20 加 block 字段）
- embed：K 次，**不算 chat token**（embed API 独立，几 token，~分钱，async）
- 冲突判定 chat：~300-500 tok（仅块内成员），仅事实落入非空块时
- 答复路由 chat：~150 tok，仅存在 PENDING 时（罕见）

**典型增量 ~300-500 chat tok/消息，全 async**。对比主回复本身常 500-2000 tok（同步）→ 增量约半条回复量，关键路径外。

embed 聚类是**省 token** 的：没 embed 则需把全量记忆灌 prompt（灾难）；有 embed 则 judge 只看块内几条（恒定小）。

## 13. 测试计划（统一留阶段7）

关键用例：
1. 女儿→儿子 + 答「保留儿子」→ KEEP_NEW 旧删新留 clean，conflict_id null
2. 女儿→儿子 + 下条聊天气 → FLAGGED 两行带标 + buildMemoryContext 注入见 `[⚠️冲突]`
3. 超时（expires_at<now）→ 下次访问懒触发 FLAGGED
4. 新块首事实（sim<0.6）→ 无判定直插
5. 同块非矛盾（加妻子名）→ judge isConflict=false 直插
6. 锁忙再来冲突 → 直接 FLAGGED
7. GET conflicts 分组正确 + PUT resolve 原子（两边联动 + 清 id）
8. gate 记忆模式 OFF → 0 embed/judge/拦截调用
