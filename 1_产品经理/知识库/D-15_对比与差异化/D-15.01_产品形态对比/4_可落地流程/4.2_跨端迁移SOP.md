## 概述

当产品需要从一种端迁移到另一种端（如App→小程序、Web→App、小程序→App）时，直接照搬功能是最大的坑。本SOP提供6步标准流程，确保迁移过程中功能裁剪合理、用户体验连贯、技术债务可控。

## 6步标准流程

### Step 1：功能清单盘点与分类

**目标**：把现有端的所有功能按"迁移必要性"分类

**操作**：
1. 导出现有端的完整功能清单（含使用频次、用户覆盖率数据）
2. 按4类标记每个功能：

| 分类 | 定义 | 迁移策略 |
|---|---|---|
| **P0-必须迁移** | 核心价值功能，高频使用 | 优先迁移，保证功能完整 |
| **P1-应该迁移** | 重要但非核心，中频使用 | 第二批迁移，可简化实现 |
| **P2-可以裁剪** | 低频/边缘功能 | 评估ROI，ROI低则不迁移 |
| **P3-不应迁移** | 原端特有能力（如App传感器→Web无法实现） | 明确告知用户替代方案或下线 |

**输出物**：功能迁移分类表（含P0-P3标记+频次数据+迁移优先级）

### Step 2：目标端约束分析

**目标**：明确目标端的技术/体验/分发约束，确定"能做什么"和"不能做什么"

**检查清单**：

| 约束类别 | 检查项 | App | Web | 小程序 |
|---|---|---|---|---|
| 技术能力 | 目标端是否支持所有P0功能？ | □ | □ | □ |
| 包体积/加载 | P0功能的资源体积是否在目标端限制内？ | □ | □ | □ |
| 性能 | P0功能在目标端的性能是否可接受？ | □ | □ | □ |
| 分发 | 目标端的分发渠道是否能覆盖目标用户？ | □ | □ | □ |
| 支付 | 目标端的支付方式是否满足业务需求？ | □ | □ | □ |
| 推送 | 目标端的触达能力是否满足留存需求？ | □ | □ | □ |

**输出物**：目标端约束分析报告（含不可迁移功能清单+替代方案）

### Step 3：功能裁剪与适配设计

**目标**：针对P0-P2功能，设计在目标端的适配方案

**裁剪原则**：
1. **核心场景不裁**：P0功能的核心路径必须完整迁移，不可简化
2. **边缘场景可砍**：P0功能中的边缘分支（如设置项的高级配置）可裁剪
3. **交互范式适配**：不能照搬原端交互——App的滑动手势→Web改为点击/拖拽
4. **信息密度调整**：App→小程序需降低信息密度（屏幕更小、操作更轻量）

**适配设计模板**：

| 原端功能 | 原端交互 | 目标端交互 | 裁剪内容 | 理由 |
|---|---|---|---|---|
| （示例）商品筛选 | 左侧面板多条件筛选 | 顶部筛选弹窗 | 去掉"价格区间滑块" | 小程序屏幕小，弹窗空间有限 |

| | | | | |

### Step 4：数据与账号打通

**目标**：确保用户在迁移后的端上能无缝使用原有账号和数据

**关键检查**：
- [ ] 账号体系是否打通？（同一用户在两端登录后数据是否同步）
- [ ] 核心业务数据是否跨端可见？（如订单/收藏/历史记录）
- [ ] 权限体系是否一致？（B端尤其重要）
- [ ] 支付/订单是否跨端可查？
- [ ] 数据同步延迟是否可接受？

**常见坑**：
- App用第三方登录（微信/Apple ID），Web端没有对应登录入口
- 小程序数据存在微信生态内，App端无法读取
- B端产品的权限配置在原端完成，新端未同步导致用户无权限

### Step 5：灰度发布与验证

**目标**：分阶段验证迁移质量，降低风险

**灰度策略**：
1. **内部测试**（1周）：团队内测，验证P0功能完整性
2. **小范围灰度**（2周）：5-10%用户，收集反馈+监控核心指标
3. **扩大灰度**（2周）：30-50%用户，对比原端和新端的核心指标差异
4. **全量发布**：100%用户，保留原端入口1-2个月作为过渡

**核心监控指标**：

| 指标 | 原端基线 | 新端目标 | 告警阈值 |
|---|---|---|---|
| 核心功能完成率 | | | 下降>5% |
| 用户停留时长 | | | 下降>15% |
| 崩溃率 | | | >0.5% |
| 用户投诉率 | | | 上升>20% |
| 转化率（关键漏斗） | | | 下降>3% |

### Step 6：原端下线与用户引导

**目标**：有序引导用户从原端迁移到新端，平稳过渡

**操作**：
1. **双端并存期**（1-2个月）：两端均可使用，新端提供"迁移引导"提示
2. **引导迁移**：原端显示"新版本体验更好"引导，但不强制
3. **功能冻结**：原端停止新功能开发，仅修复严重bug
4. **逐步下线**：先下线P2/P3功能，再下线P1，最后下线P0
5. **原端公告**：提前30天通知用户原端下线时间，提供FAQ和客服支持

## 常见坑总结

| ⚠️常见坑 | ✅推荐做法 |
|---|---|
| 直接1:1照搬原端功能到新端 | 按目标端约束做功能裁剪和交互适配 |
| 只测功能不测性能，上线后卡顿 | 灰度期重点监控性能指标（加载/渲染/响应） |
| 账号/数据未打通，用户体验断裂 | 上线前完整验证跨端账号同步和数据一致性 |
| 一次性全量切换，出问题无法回退 | 分阶段灰度，保留原端入口作为兜底 |
| B端产品忽略权限/审批流迁移 | 权限体系迁移优先级=P0，必须完整验证 |
