# 11 - 工作流执行与编排引擎

## 功能简介
Java 侧编排引擎：根据对话模式（默认对话/Agent 路由/工作流）选择执行策略，构建执行上下文、变量存储，调用 LLM/Skill 执行器，并对接 Runtime Sidecar 完成实际工作流图执行。

## 后端 (backend) — `engine` 包
- 上下文：`engine/context/`
  - [ExecutionContext.java](../../backend/src/main/java/com/superprogrammer/engine/context/ExecutionContext.java) — sessionId/mode/agentId/workflowId/ragEnabled
  - [VariableStore.java](../../backend/src/main/java/com/superprogrammer/engine/context/VariableStore.java) — 变量存取
- 路由：`engine/router/` AgentRouter、RoutingResult
- 策略：`engine/strategy/`
  - [ExecutionStrategy.java](../../backend/src/main/java/com/superprogrammer/engine/strategy/ExecutionStrategy.java) — 策略接口
  - DefaultChatStrategy（默认对话）
  - [AgentRoutingStrategy.java](../../backend/src/main/java/com/superprogrammer/engine/strategy/AgentRoutingStrategy.java)（Agent 路由）
  - WorkflowStrategy（工作流）
- 编排入口：[OrchestrationEngine.java](../../backend/src/main/java/com/superprogrammer/engine/OrchestrationEngine.java)（`engine` 包根）
- 执行器：`engine/executor/`
  - LlmCallHandler、SkillExecutor、StepActionHandler、StepResult
- 编排仅由 `chat/service/ChatSessionService` 触发；工作流直接执行由 `WorkflowController` 直调 `RuntimeExecutionService`（不经 `WorkflowService`，也不经 engine 编排）。

## 前端 (frontend)
无独立 UI（执行结果通过对话流式 / 执行监控页展示，见 [13-执行监控](13-执行监控.md)）。

## Sidecar 联动
- Java 引擎通过 `runtime` 包网关下发执行请求，见 [12-Runtime-Sidecar执行](12-Runtime-Sidecar执行.md)。

## 数据表
执行记录见 `execution_logs` / `execution_step_logs`（[13-执行监控](13-执行监控.md)）。注：不存在 `executions` 表，执行记录主表即 `execution_logs`。

## 实战落地：提示词增强工作流（wf16，2026-07-04）
**痛点**：原 wf16 = START→SKILL(提示词增强/小富贵人设)→END 单链。skill 的 systemPrompt 写「我会先问您几个问题、几轮互动」，但 SKILL 节点 = 单次 LLM 调用，问完即 END，**不暂停收答案**→厂商窗口能多轮、工作流里"断"。

**根因（架构）**：工作流 sidecar 跑有向图，每节点 = 一次 invoke 执行一次，跑完走下一节点。**SKILL 节点没有"模型暂停问用户、用户答了再回到同一 LLM"语义**——这只有 HUMAN_INPUT 节点（图级 WAITING_INPUT 暂停）能做。即"**节点边界 ≠ 对话边界**"。厂商对话窗口是连续会话线程，暂停-续跑是聊天循环本身免费给的；工作流得把每一轮显式画成节点。

**固定链方案（落地）**：把 skill 人设里的「要问的事」拆成 N 个 HUMAN_INPUT 串起来，答案攒齐喂 skill 一次出结果。
- wf16 重构：START(inputKey=prompt, nodeAlias=start) → HUMAN_INPUT(bg, 问背景) → HUMAN_INPUT(goal, 问目标) → HUMAN_INPUT(style, 问风格) → SKILL(提示词增强) → END。
- 每个 HUMAN_INPUT 设 nodeAlias + inputKey；skill 的 `promptTemplate` 拼接 `{{prompt}}/{{background}}/{{goal}}/{{style}}`。
- **变量贯通验证**：sidecar `callback_input` 把上游 HUMAN_INPUT 答案按「平铺 key + 别名.key」两形态合并进 skill 输入（`background` + `bg.background`、`goal` + `goal.goal`…），Java `VariableStore.renderTemplate` 直接解析。

**额外坑（skill 内部）**：skill 2 原有 step2（model=doubao-seed-2.0-code、空 system、模板 `{{new_prompt}}`）会把 step1 生成的增强 prompt **重新执行**一遍→输出无关内容（Coach Bot 健身教练）。改 step2 systemPrompt=「原样输出器，勿执行勿回答」、model=glm-5.1，让其 verbatim 回吐 new_prompt。

**LLM provider 选型**：本环境 doubao/kimi 配的是 `/api/coding` 编码端点（出固定人设或超时）、deepseek key 未配（401）、k2.6 时通时断。**glm-5.1**（`/api/anthropic` 标准端点+有效 key）稳。最终两 step 均用 glm-5.1。

**验证**（playwright）：发「优化客户经理AI培训提示词」→ 问背景(30人/2h/息壤)→问目标(3条)→问风格(趣味/案例/点名)→ 输出完整 B/R/O/KR/S 增强提示词（时间轴表+真实案例+话术模板+2次点名互动+防幻觉条款）。截图 `wf16-enhanced-output.png`。

**结论**：多轮交互在工作流里**必须画出来**（HUMAN_INPUT 链 或 Phase 2 环），不能塞进一个 SKILL 节点的人设指望它自转。动态环（LLM 自决问什么/几轮）需补 CONDITION 节点编辑器 UI（待做）。
