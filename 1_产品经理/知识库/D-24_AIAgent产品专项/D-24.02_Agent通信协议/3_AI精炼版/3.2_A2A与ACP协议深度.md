# 3.2 A2A 与 ACP 协议深度：Agent 间协作与边缘协同

## 一、A2A 是什么：Google 发起的 Agent 间对讲机

**A2A（Agent-to-Agent Protocol）**：Google 于 2025-04 在 Google Cloud Next 发布的开放协议，用于标准化"Agent 与 Agent"之间的任务委派、跨厂商互操作、协作产出。业内类比"智能体间对讲机"。基于 HTTP+SSE+JSON-RPC 设计，2026 年进入 v1.0 GA（General Availability），从 50 个创始伙伴扩展到 150+ 组织参与。[来源:Google A2A | 🔍高 | 2025-04/2026]

**A2A 解决什么问题**：
- 协议前时代——多Agent 协作只能用厂商专属编排（LangGraph 只能在 LangChain 生态、CrewAI 只能在 CrewAI 生态、AutoGen 仅限 Microsoft/OpenAI 模型），跨厂商 Agent 互联只能定制开发
- A2A 时代——任何遵循 A2A 协议的 Agent 都能互相发任务、跟踪进度、传输产出（Agent Card 自描述、Task 生命周期管理、Artifact 产出物标准），跨厂商 Agent 互联从"定制 N×M"降为"标准 N+M"

## 二、A2A 核心架构

| 组件 | 作用 |
|---|---|
| **AgentCard** | Agent 的自描述清单（能力/接口/鉴权/版本），由 Agent 在固定路径 `/.well-known/agent-card.json` 暴露，让其他 Agent 自动发现并理解能力 |
| **Task** | A2A 任务的全生命周期对象（submitted/working/input-required/completed/cancelled/failed），支持长时任务、异步响应 |
| **Message/Part** | 任务内消息单元，Part 可承载文本/文件/数据结构；多模态产出（如 Agent 输出图片/JSON） |
| **Artifact** | 任务最终产出物（结构化输出），独立于 Message stream 用于最终交付 |
| **Transport** | HTTP+SSE+JSON-RPC 双向通信；SSE 推送任务进度更新，JSON-RPC 同步控制消息 |

**A2A 任务生命周期**：
1. Client Agent 通过 AgentCard 发现 Remote Agent 的能力
2. Client Agent 发送 task/send 请求（含任务描述）
3. Remote Agent 进入 working 状态 → SSE 推送进度增量
4. 如需更多输入 → 进入 input-required 状态等待 Client 补充
5. 任务完成 → 进入 completed 状态 → 返回 Artifact
6. 中途可 cancel → 进入 cancelled 状态

## 三、A2A 生态规模与采纳（2026 现状）

| 指标 | 数值 | 来源 |
|---|---|---|
| GA 状态 | v1.0 GA | Google Cloud Next 2026 [来源:Google | 🔍高 | 2026] |
| 参与组织 | 150+ | Google A2A 官方 [来源:Google A2A | 🔍高 | 2026] |
| 创始伙伴 | 50+（Salesforce/AWS/SAP/Workday/Atlassian/ServiceNow/Box/Cohere/MongoDB等） | Google Cloud Next 2025 [来源:Google | 🔍高 | 2025-04] |
| 与 MCP 关系 | 互补不竞争，MCP=Agent↔工具层，A2A=Agent↔Agent 层 | Google 官方声明 [来源:Google/Anthropic 联合声明 | 🔍高 | 2025-04] |

**A2A vs LangGraph/CrewAI/AutoGen 多Agent 框架**：
- A2A 是**协议层**——定义 Agent 间通信标准，厂商中立，跨生态互操作
- LangGraph/CrewAI/AutoGen 是**框架层**——定义 Agent 编排逻辑（DAG/状态机/对话），通常绑定单一生态
- 同一个多Agent 产品可以"用 LangGraph 做内部编排 + A2A 做跨厂商 Agent 互联"——两层并存互补

## 四、ACP 是什么：IBM 主导的边缘智能体上下文层

**ACP（Agentic Context Protocol 或 Agent Communication Protocol，业界有混称）**：IBM 在 Bee Agent Framework 中主导推动的开放协议，定位为"边缘与本地协同场景下的智能体通信与上下文共享协议"。是与 MCP、A2A 并列的第三大 Agent 协议。业内类比"边缘智能体的近场通讯协议"。[来源:IBM Bee Agent Framework | 🔍高 | 2026]

**ACP 独有的双层面设计**：
- **通信连接层（Communication Layer）**——Agent 之间的消息传递与任务委派（功能上与 A2A 部分重叠，但 ACP 强调本地与边缘场景，而非跨广域的厂商互操作）
- **智能体上下文层（Agentic Context Layer）**——Agent 之间的上下文/记忆/状态共享，让边缘设备上的 Agent 能在低带宽/断连/本地化场景下共享上下文，不需要全量回传云端

> ACP 与 MCP/A2A 的关键差异是**强调边缘本地协同与上下文共享**：MCP 是"Agent 调云端工具"，A2A 是"云端 Agent 间委派"，ACP 是"边缘 Agent 间共享上下文/协同执行"——三者覆盖云-边-端全域。

## 五、ACP 适用场景

| 场景 | 为何选 ACP 而非 MCP/A2A |
|---|---|
| IoT/工业 Agent 边缘协同 | 边缘设备带宽低/断连频繁，需本地上下文共享，A2A 强依赖云通信不适用 |
| 本地多 Agent 协作 | 多个本地 Agent（如 IDE Agent+文档 Agent+邮件 Agent）需低延迟协同，云端中转延迟高 |
| 离线/隐私敏感 Agent | 隐私敏感数据不可出本地，需 Agent 间本地共享上下文完成协同 |
| 设备集群协同 | 多个边缘设备（机器人/车载/家电）的本地 Agent 群协同执行 |
| 与 MCP/A2A 协同 | 云端用 MCP/A2A，边缘用 ACP，云-边-端三层协同 |

## 六、A2A vs ACP vs MCP 定位差异

| 维度 | MCP | A2A | ACP |
|---|---|---|---|
| 解决层 | Agent ↔ 工具/数据源 | Agent ↔ Agent（云/广域） | Agent ↔ Agent（边缘/本地） |
| 通信模式 | stdio + HTTP+SSE + Streamable HTTP | HTTP+SSE+JSON-RPC | 本地消息+上下文共享 |
| 核心单元 | Tool / Resource / Prompt | Task / Artifact / AgentCard | Context / Message / Local Task |
| 适用场景 | 中心化 Agent 调工具 | 跨厂商云端 Agent 协作 | 边缘本地低带宽 Agent 协同 |
| 主导方 | Anthropic → Linux 基金会 | Google | IBM Bee |
| 成熟度 | 最成熟（10万 Server） | 中（GA + 150+ 组织） | 新兴（IBM Bee 推动中） |
| 商业化 | 中-高 | 中 | 低-中 |

## 七、A2A/ACP 局限与常见坑

**A2A 常见坑**：
- AgentCard 描述模糊，导致 Client Agent 误派任务给错误 Remote Agent
- 长时任务未声明 input-required 状态，Client Agent 空等
- Artifact 结构未约定，跨厂商 Agent 输出格式不兼容
- 未做鉴权层，恶意 Agent 冒充调用导致数据泄露
- 长时任务无超时机制，Remote Agent 卡死 Client Agent 等待

**ACP 常见坑**：
- 边缘设备资源有限，Agent 上下文同步占用本地存储与算力
- 上下文共享无冲突消解机制，多个 Agent 同时写上下文导致状态错乱
- 断连后上下文版本不一致，恢复时合并报错
- 国内 IBM Bee 生态弱于海外，落地需自研补全

> A2A 是 Agent 间协作的云端标准，ACP 是 Agent 间协作的边缘标准。完整 Agent 产品（云-边-端全域）通常是 MCP（工具层）+ A2A（云端 Agent 间）+ ACP（边缘 Agent 间）+ AG-UI（前端）+ Skills（能力）组合。详见 3.3 五协议对照表与协议选型决策树。
