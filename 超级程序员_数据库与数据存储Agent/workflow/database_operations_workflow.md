# Database Operations & Tuning Workflow

## Purpose

基于数据库运维与调优知识体系，为用户提供索引优化、分库分表策略、主从复制高可用、容灾备份（3-2-1-1-0原则）等数据库运维技术支持。覆盖B+Tree索引原理、ShardingSphere中间件、Orchestrator/Patroni高可用、定期恢复演练等核心运维支柱。

## Prerequisites

- 用户已明确数据库运维/调优场景或问题
- 知识库文件 `03_数据库与数据存储.md` 及子目录文件可访问

## Steps

### Step 1: 识别数据库运维/调优需求场景

**Goal**: 明确用户的运维需求类型、数据库类型和紧迫程度
**Completion criterion**: 已确定场景标签、数据库类型、问题严重性和SLA要求

1. 读取用户消息，提取以下信息：
   - 场景类型：索引优化 / 慢查询分析 / 分库分表评估 / 高可用架构设计 / 容灾备份策略 / 数据库迁移 / 性能调优 / 故障排查
   - 数据库类型：MySQL / PostgreSQL / Oracle / SQL Server / 国产库 / MongoDB / 其他
   - 问题严重性：P0（生产故障，立即处理） / P1（性能下降，需尽快处理） / P2（预防性优化）
   - SLA要求：RTO（恢复时间目标）、RPO（数据丢失容忍度）、可用性目标（几个9）
   - 现有架构：单机 / 主从 / 集群 / 已分库分表 / 云托管RDS
   - 关键痛点：查询慢（具体耗时） / 连接数打满 / 主从延迟大 / 备份恢复未验证 / 磁盘空间告警

2. 对照知识库中的四大运维支柱初步判断：
   - 查询慢（30s→30ms优化空间） → 索引优化（B+Tree索引、执行计划分析）
   - 单库容量/性能见底 → 分库分表（ShardingSphere）或 NewSQL（TiDB/OceanBase）
   - 高可用需求 → 主从复制+Orchestrator/Patroni自动故障转移
   - 数据安全最后防线 → 容灾备份（3-2-1-1-0原则、定期恢复演练）

3. 如有信息缺失，向用户追问不超过2个澄清问题。

### Step 2: 输出数据库运维/调优方案

**Goal**: 产出针对性的运维优化、架构加固或故障处理方案
**Completion criterion**: 输出包含问题诊断、优化措施、实施步骤、验证方法

根据Step 1确定的场景，按以下分支处理：

**分支A — 索引优化与慢查询分析**：
1. 输出慢查询定位方法：slow_query_log分析、Performance Schema诊断、pt-query-digest工具。
2. 给出执行计划解读：EXPLAIN各列含义、type优化目标（避免ALL/INDEX全扫描）、Extra列警告（Using filesort/Using temporary）。
3. 输出索引优化策略：
   - B+Tree索引原理：聚簇索引/二级索引、覆盖索引、最左前缀原则、索引下推（ICP）
   - 索引设计原则：WHERE/JOIN/ORDER BY/GROUP BY字段优先、避免冗余索引、联合索引字段顺序（区分度高的在前）
   - 向量索引（AI场景）：IVF/HNSW/DISKANN选型、与关系型数据库内置向量索引对比
4. 附优化效果验证：优化前后执行计划对比、查询耗时对比、QPS提升度量。

**分支B — 分库分表与扩展性**：
1. 输出分库分表触发条件评估：单表数据量（>5000万行）、单库QPS（>1万）、磁盘容量（>80%）。
2. 给出分片策略：
   - 分片键选择原则：高基数、查询热点均匀、避免跨分片查询
   - 常见分片算法：Hash取模（均匀但扩容需迁移）、Range（顺序访问友好但热点集中）、一致性Hash（扩容迁移最小化）
   - 全局ID生成：Snowflake（时间+机器ID+序列号）、Leaf（美团分段分配）、UUID（避免）
3. 输出ShardingSphere中间件架构：ShardingProxy（独立进程，对应用透明）vs ShardingJDBC（jar包嵌入，性能更好）。
4. 附NewSQL替代评估：TiDB（MySQL协议兼容、Raft共识、HTAP）vs OceanBase（自研分布式、金融级可靠性）vs 传统分库分表（适用场景对比）。

**分支C — 主从复制与高可用**：
1. 输出复制架构选型：
   - 异步复制（默认，性能最好但可能丢数据）
   - 半同步复制（after_sync模式，主库等待至少一个从库ACK，核心系统标配）
   - MGR组复制（MySQL 8.0，Paxos共识，自动故障检测+切换）
2. 给出高可用方案：
   - MySQL：Orchestrator（可视化拓扑管理、自动故障转移、支持GTID）/ MHA（成熟但已不再维护）/ MGR（官方推荐）
   - PostgreSQL：Patroni（基于etcd/ZooKeeper的自动故障转移）/ repmgr
   - 读写分离：ProxySQL（连接池+查询路由+负载均衡）/ MaxScale
3. 输出监控要点：主从延迟（Seconds_Behind_Master/heartbeat表）、复制线程状态、GTID一致性校验。
4. 附故障演练清单：主库宕机切换、从库延迟过大降级、脑裂恢复。

**分支D — 容灾备份与恢复**：
1. 输出3-2-1-1-0备份原则解读：
   - 3份数据副本（生产+本地备份+异地备份）
   - 2种不同存储介质（磁盘+磁带/云存储）
   - 1份异地备份（物理隔离，防灾害）
   - 1份离线/不可变备份（防勒索软件）
   - 0错误（定期校验备份完整性）
2. 给出备份策略设计：
   - 全量备份（周级）+ 增量备份（日级）+ Binlog实时备份（连续）
   - 备份窗口选择（业务低峰期）、备份对生产影响评估（物理备份vs逻辑备份）
   - 云托管RDS的自动备份策略与自定义备份结合
3. 输出恢复演练方案：
   - 演练频率：季度至少1次全量恢复演练
   - 演练范围：单表恢复 → 单库恢复 → 全实例恢复 → 跨地域灾备切换
   - RTO/RPO验证：记录每次演练实际恢复时间、验证数据一致性
4. 附灾难恢复预案：灾难等级定义（单点故障/单可用区故障/全地域故障）、恢复优先级（核心业务优先）、应急联系人清单。

将结果保存到 `output/database_operations.md` 或直接在对话中呈现。

### Step 3: 验证与交付

**Goal**: 确保运维方案安全可执行、与知识库一致
**Completion criterion**: 已通过 checklist 逐项核对

1. 读取 `checklist/database_operations_workflow_checklist.md`。
2. 逐项核对输出是否覆盖要求的知识点。
3. 确认所有关键论断均能在知识库中找到支撑。
4. 如有遗漏或偏差，补充修正。
5. 向用户交付最终答案。

## Post-Workflow

1. 记录完成状态到 `task/current_task.md`。
