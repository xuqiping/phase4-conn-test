# 积分系统 7x 人工测试问题修复 · 实现计划（plan.md）

> Phase 2 产物。基于 `workflow_output/人工测试问题/7x_积分系统.md` 3 个未解决问题 + 用户追加的「视频生成后审查实际推送参数与是否有视频参考标志」需求，拆成逐步骤、可执行、经人确认的实现计划。
> **硬闸门：本计划未过审，不进 Phase 3 写码。**
> 决策已与用户确认：① 导入语义 = Upsert（存在则覆盖价格）；② 视频参考定价区分 = 布尔列 `has_reference`。

## 一、问题清单与决策

| 编号 | 问题 | 根因结论 | 修复方向 | 决策 |
|---|---|---|---|---|
| 7x-1 | 图片模型设置单价点确定报 500 | `LlmProviderMapper.selectByIdForUpdate` 用 `deleted = false`，但 PG 的 `deleted` 列是 `INTEGER`（`V6:32`）→ `operator does not exist: integer = boolean` → `BadSqlGrammarException` → 兜底返 500。**与 kind 无关，所有价表创建都会炸**，用户先配图片撞到而已 | 把 `= false` 改 `= 0`；顺手清前端 `videoBillingMode` 对非 VIDEO 的泄漏 | — |
| 7x-2 | 价目表需导出 / 按模板上传（联动全局供应商未配置模型，区分 LLM/图片/视频） | 镜像 LLM 供应商 export/import 那套 | 后端 `GET /pricing/export`、`POST /pricing/import`（upsert）、`GET /pricing/template`；前端三按钮 + 预检确认 | Upsert（按 `providerId+model+kind`，存在则覆盖价格，`effective_from=now`） |
| 7x-3 | 视频需区分有无参考视频定价（seeddance 有参考 10元/无参考 20元/百万 tokens） | `pricing_rule` 无区分维度；`findEffective` 只按 `(kind, model, providerId)` 查 | `pricing_rule` 加 `has_reference BOOLEAN NOT NULL DEFAULT FALSE`；查询加谓词 + fallback；worker 算标志传入 | 布尔列（不用通用 variant） |
| 7x-4（追加） | 视频生成后（含无限画布）需查看实际推送参数 + 明确「是否有视频参考」标志供审查 | 推送 body 已脱敏落库（`request_config.providerRequestSnapshot`），`VideoGenView` 已有 `MediaTaskRequestDetails` 面板；**仅三处缺口**：① `has_reference` 标志不存在 ② Canvas 路径丢弃审计字段、未接面板 ③ VideoGenView 历史列未标参考 | 后端 `MediaTaskVO` 加计算字段 `hasReference`（按 `inputAttachments` 里是否有 `kind=="video"` 算）；Canvas `pollVideoTask`/`hydrate` 保留审计字段，`PropertyPanel` video 块接面板；VideoGenView 任务头 + 历史列加参考标志 | 不加新 DB 列 |

## 二、术语表

| 术语 | 大白话 | 简单案例 |
|---|---|---|
| has_reference（定价维度） | 一条 `pricing_rule` 适用的视频任务「是否带参考视频」。`false`=无参考（或通用兜底），`true`=有参考视频 | seeddance 配两行：`false→20元`、`true→10元` |
| hasReference（任务展示维度） | 一次视频生成任务实际是否带了参考视频附件，按 `inputAttachments` 里 `kind=="video"` 实时算，落 `MediaTaskVO` | 用户传了 1 个 video 附件 → `hasReference=true` |
| 参考视频（reference video） | 多模态附件里 `kind=="video"` 的那一类。**首尾帧参考图（`kind=="image"`）不算参考视频**，定价与展示均不区分 | 用户上传 mp4 当参考 → 是；上传 png 当首帧 → 不是 |
| providerRequestSnapshot | 实际发给 Ark 的请求体（脱敏后）的快照，存在 `media_gen_tasks.request_config` JSONB 的 `providerRequestSnapshot` 子键。媒体 URL 被替换为 `{redacted, fileId, transport, mime, bytes, sha256}`，不含二进制 | 审计时看「真正推给模型的参数」 |
| submittedRequest | 平台收到的提交参数（脱敏后），即 `requestConfig` 去掉 snapshot 子键、去掉 data URI 后的副本 | 审计时看「用户/画布提交时填了什么」 |
| Upsert | 导入时按业务键（`providerId+model+kind`）查：存在就覆盖价格字段并刷新 `effective_from`，不存在就插入。与 LLM 供应商导入（按 `name` upsert）行为一致 | 导入一个已配的 deepseek 价表 → 原价被新价覆盖 |
| fallback 查询语义 | 查 VIDEO 价格时：先精确匹配 `(model, providerId, has_reference=X)`；若无，回退 `(model, providerId, has_reference=false)`；再无回退全局（`provider_id IS NULL`） | 不区分参考的模型只配 1 行 `false` 即可；区分的配 `false`+`true` 两行 |

### Chunk C · 视频定价 has_reference 后端（迁移 + 计费链路）

**目标**：`pricing_rule` 支持「有参考视频 / 无参考视频」双价；计费链路按任务实际是否带参考视频命中对应价。

**涉及文件（≤10）**
- `backend/src/main/resources/db/migration/V95__pricing_has_reference.sql`（新）
- `billing/entity/PricingRuleEntity.java`
- `billing/mapper/PricingRuleMapper.java`
- `billing/service/PricingService.java`
- `billing/service/MediaBillingService.java`
- `media/service/MediaGenTaskWorker.java`（`handleSucceeded` 计算标志传入）
- `billing/dto/PricingRuleRequest.java`、`billing/dto/PricingRuleVO.java`（加字段）
- `billing/service/PricingConfigService.java`（applyRequest/validatePricingRule/toVO/availablePricingModels + 判重方法签名）
- `billing/mapper/PricingRuleMapper.java`（`countConflicting...` 加 has_reference 维度）

**动作（伪代码）**
1. **迁移 V95**
   - `ALTER TABLE pricing_rule ADD COLUMN has_reference BOOLEAN NOT NULL DEFAULT FALSE;`
   - 重建查询索引：`DROP INDEX idx_pricing_lookup; CREATE INDEX idx_pricing_lookup ON pricing_rule(kind, model, has_reference, effective_from DESC);`
   - 注释 ASCII（遵循 AGENTS.md 迁移规范）。
   - **可回滚**：V95 配 `DROP COLUMN has_reference` 的 undo（项目 Flyway 是否启用 undo 以既有约定为准；至少迁移脚本内可前向兼容——DEFAULT FALSE 保证旧行为不变）。
2. **实体**：`PricingRuleEntity` 加 `private Boolean hasReference;`（默认 false）。常量 `HAS_REFERENCE_TRUE/FALSE`。
3. **Mapper**
   - `findEffective(kind, providerId, model, hasReference)`：
     ```
     SELECT * FROM pricing_rule
     WHERE kind=#{kind} AND model=#{model}
       AND effective_from <= NOW()
       AND (provider_id=#{providerId} OR provider_id IS NULL)
       AND has_reference = #{hasReference}       -- 精确匹配
     ORDER BY (provider_id IS NULL) ASC, effective_from DESC LIMIT 1
     ```
   - **fallback 由 Service 编排**（SQL 保持单一谓词）：Service 先查精确 `hasReference=X`；为空再查 `hasReference=false`（把 false 当通用兜底）；再空再退全局。这样「不区分的模型只配 false 一行」行为不变。
   - `countConflictingProviderModelKindHasRef(providerId, model, kind, hasReference)`：把现有 `countConflictingProviderModel` 扩展加 `has_reference` 维度，让 VIDEO 同模型可合法配两行（false+true 不冲突），其他 kind 默认 false。
4. **PricingService.computeCost**：加 `boolean hasReference` 参数，VIDEO 分支按上述 fallback 编排 findEffective；CHAT/EMBED/IMAGE 忽略此参（恒传 false）。
5. **MediaBillingService.chargeMedia**：加 `boolean hasReference` 参数，透传给 `computeCost`。
6. **Worker**（`handleSucceeded` ~line 216）：
   - 复用已在 scope 的 `request`（`buildRequest(task,false)` 结果，~line 148）：
     `boolean hasReference = request.getAttachments().stream().anyMatch(a -> "video".equals(a.getKind()));`
   - `chargeMedia(userId, providerId, model, kind, tokensInput, videoSeconds, imageCount, status, refId, hasReference);`
   - **不用 taskType 判断**（IMAGE2VIDEO 被重载用于 image/video/audio 参考，不可靠）。
7. **定价 DTO/Service**：
   - `PricingRuleRequest`/`PricingRuleVO` 加 `hasReference`（默认 false）。
   - `validatePricingRule`：非 VIDEO 强制 `hasReference=false`；VIDEO 允许 true/false。
   - `applyRequest`/`toVO` 透传。
   - `availablePricingModels`：对 VIDEO 候选可输出「两行候选」（false+true），让 admin 分别配；其他 kind 单行。**或**保持单行候选、由 admin 在表单里勾 has_reference 自行加第二行——选简单方案（单行候选 + 表单可勾），避免候选膨胀。
   - `createPricingRule` 判重换用 `countConflictingProviderModelKindHasRef`。

**依赖**：无（独立于 A/B/D）。

**验证**
- [ ] 迁移：本地起 PG，V95 应用后 `pricing_rule` 多列、索引重建、旧行 `has_reference=false`。
- [ ] 单测 `PricingServiceTest`：seeddance 配 false=20元 / true=10元；无参考任务命中 20、有参考命中 10；只配 false 一行时两类任务都命中 false（fallback 生效）；只配 true 没配 false 时，无参考任务报「无价表」（验证 fallback 不会无限兜底）。

## 四、技术坑点预判

| # | 坑 | 规避 |
|---|---|---|
| 1 | **PG 类型不匹配的同类隐患**（`deleted = false` 撞 INTEGER）可能在其他 mapper 复发 | Chunk A 全仓 grep `deleted = false/true`，凡 INTEGER 列改 0/1；BOOLEAN 列不动。建一条 AGENTS.md 规范：INTEGER 软删列用 0/1，BOOLEAN 列用 true/false，不混用 |
| 2 | **导入 upsert 死锁/竞态**：并发导入同一 (provider,model) 可能在 UPDATE 行锁上互等 | importAll 内部对每行先 SELECT 再 UPDATE/INSERT，单行单事务；不让用户并发导入（前端按钮 loading + 后端可加 `@Transactional` 行级处理）。极端并发由 `countConflicting...` 的二次校验兜底 |
| 3 | **fallback 查询语义陷阱**：管理员只配了 `has_reference=true` 没配 `false`，无参考任务会 fallback 失败报「无价表」 | 管理端在保存 VIDEO `has_reference=true` 行时提示「建议同时配置无参考(false) 价表」；PricingService 找不到时抛清晰业务错「视频模型 X 无参考价表未配置」而非裸 NPE |
| 4 | **taskType 不可靠**（IMAGE2VIDEO 被重载用于 image/video/audio 参考） | worker 计算 hasReference **必须**从 `request.getAttachments()` 的 `kind` 判，不用 taskType。已在 Chunk C 伪代码写死 |
| 5 | **首尾帧参考图被误算成参考视频** | hasReference 只匹配 `kind=="video"`；`kind=="image"`（首尾帧）不算。术语表已显式区分。定价 has_reference 也只对 video 参考生效 |
| 6 | **Canvas 审计字段在 hydrate 后丢失**（旧实现只存 previewUrl/fileId） | pollVideoTask + hydrateVideoPreviews 两处都要 updateNodeData 审计字段；旧节点字段缺失时按钮禁用提示，不渲染空面板 |
| 7 | **导入文件过大 / 解析慢** | 上限 200 行（同 LLM 导入）；前端预检用 `JSON.parse` try/catch；超大文件浏览器侧先 `file.size` 预判 |
| 8 | **V95 索引重建锁表**（pricing_rule 数据量大时） | `DROP + CREATE INDEX` 在小表无感；数据量大时用 `CREATE INDEX CONCURRENTLY`（PG），但 Flyway 单事务里不能用 CONCURRENTLY——评估当前数据量，若小表直接 DROP/CREATE，若大表拆迁移手运维。当前 MVP 阶段价表行数 <100，直接重建 |

## 五、安全检查清单（Phase 3 逐项验证打勾）

- [ ] **鉴权**：导出/导入/模板三 endpoint 均挂 `@RequirePermission("pricing:manage")`（admin 专属），不放宽。
- [ ] **审计**：三 endpoint 挂 `@AuditLog(module="billing", action="pricing_export"/"pricing_import"/"pricing_template_download")`，落 audit_logs。
- [ ] **输入校验**：导入逐行重跑 `validatePricingRule`（含 has_reference、价 ≥0、VIDEO 模式校验）；provider 存在 + ACTIVE + model 属于 provider + kind 匹配 category。
- [ ] **越权**：导入只按 `providerId` 定位（来自请求体），不信任 `providerName`；后端二次校验 provider 可见性（沿用现有逻辑）。
- [ ] **大小限制**：导入 ≤200 行，超限 400；单行 model 长度沿用 `@Size(max=128)`。
- [ ] **信息泄露**：导出/模板的价表 JSON 不含密钥（价表本就明文），无需脱敏；任务审查的 `providerRequestSnapshot` 已脱敏（媒体 URL → sha256/metadata），不含二进制。
- [ ] **幂等/重放**：导入是 upsert（同业务键覆盖），天然幂等；不引入新的幂等键机制（与充值扣费的 idempotency 不同维度，价表配置非资金动作）。
- [ ] **数据完整性**：V95 `has_reference NOT NULL DEFAULT FALSE` 保证存量行有值；迁移前后对账（`SELECT count(*) WHERE has_reference IS NULL` = 0）。

## 六、功能联动点清单

| 触发动作 | 联动对象 | 预期变化 | 边界 |
|---|---|---|---|
| 导入覆盖某 (provider,model,kind) 价 | 该模型后续调用计费 | 立即按新价（`effective_from=now`），因 `findEffective` 实时查库 | 导入前行：旧价；导入后行：新价。无缓存需刷新 |
| 管理员配 VIDEO `has_reference=true` 行 | 该模型有参考视频任务计费 | 命中 true 行 | 只配 true 不配 false → 无参考任务 fallback 失败报「无参考价表未配置」 |
| 管理员删/改 VIDEO 价 | 历史账不变（append-only + effective_from） | 仅影响后续调用 | 价表无删除接口，改价 = 新行 |
| Canvas 提交带参考视频任务 | worker 计 hasReference=true → 命中 true 价表 → 扣对应积分 | 任务详情/画布属性面板标「有参考」 | 首尾帧图（kind=image）不算参考视频，标「无参考」、命中 false 价 |
| 导入文件含 has_reference 字段但后端版本旧（未跑 V95） | 反序列化 | `@JsonIgnoreProperties(ignoreUnknown=true)` 保证旧后端不炸；has_reference 被忽略 | 双向兼容：新后端导出旧后端导入，has_reference 字段被忽略，按 false 落库 |
| 导入文件 providerName 与 providerId 不一致 | 定位 | 按 providerId 定位，providerName 仅展示用 | 不一致不报错，但前端预检可 warning 提示 |
| **反向**：取消参考视频附件重提任务 | 命中价表 | hasReference=false → 命中 false 行 | 与有参考时价不同 |
| **批量**：模板含 N 个未配置模型 | 导入 | 全部新增（created+=N）；已配置的不在模板里 | 模板已预过滤，正常不出现冲突 |

## 七、运维考量清单

| 项 | 做 / 不做 / 后续 | 说明 |
|---|---|---|
| **可观测性** | 做 | 导入/导出 endpoint 进 audit_logs；importAll 逐行失败原因进 `PricingImportResult.errors` 返回前端 + 后端 `log.warn`。关键路径：价表变更影响计费，已有 `@AuditLog` 覆盖 |
| **配置开关** | 不做 | 4 个修复都是确定性功能，无需灰度开关 |
| **可回滚** | 做 | V95 迁移前向兼容（DEFAULT FALSE，回滚 = DROP COLUMN）；价表 upsert 可逆（再导一次旧 JSON 覆盖） |
| **限流/熔断/降级** | 不做 | 导入是 admin 低频操作，内部 O(200) 单事务，无需限流 |
| **运维入口** | 做 | 导出 endpoint 本身就是「查/备份当前价表」的运维入口；对账沿用既有 `BillingReconcileService`，价表变更不影响余额对账 |
| **告警阈值** | 后续 | 价表配置错误（如 VIDEO 无 false 行）→ 计费时抛业务错，由现有「计费失败」链路 refund。是否加「价表缺失告警」后续再说 |
| **容量/性能** | 做 | V95 索引重建在小表（<100 行）无感；导入上限 200 行防大事务；Canvas 审计字段进 node data 增加 localStorage 占用，单任务审计 JSON <2KB，可接受 |
| **旧任务兼容** | 做 | 7x-4 审查能力对迁移前的旧视频任务：`providerRequestSnapshot` 为 null → 面板显「未记录发送快照」；`hasReference` 算字段按现有 inputAttachments 算（旧任务也有 attachments），不会全 null |
