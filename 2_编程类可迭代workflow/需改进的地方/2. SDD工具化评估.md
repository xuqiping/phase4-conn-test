# SDD 工具化评估 · 本工作流与 2026 主流工具的关系

> 类型：评估 / 决策记录（对应 `1. 问题与需改进点.md` 条目 24）
> 日期：2026-08-03
> 结论先行：**工具服务于流程，不是替代流程**。本工作流的商业前置层（Phase 0）、运维考量、功能联动点清单、大白话注解是所有现成工具都没有的优势层——保留并作为「宪法」注入任何工具的上下文。各工具的好概念**逐条吸收**进本流程，而不是整体迁移到某工具的脚手架。

## 一、评估对象（2026 现状，已核实）

| 工具 | 核心机制 | 本流程已对齐的等价物 |
|---|---|---|
| **GitHub Spec Kit** | `constitution.md`（项目宪法/steering：编码标准 + 架构决策 + 项目级规则，EARS 写法，常拆 team/project 两段）+ `specify→plan→tasks→implement` 命令链 + `/speckit.analyze` 一致性校验 | Phase 1 specs + Phase 2 plan + 方法论核心 9 铁律 + AGENTS.md（缺：单一「宪法」层） |
| **OpenSpec**（Fission-AI） | **delta 变更模型**：变更只写 `## ADDED / MODIFIED / REMOVED Requirements`，`draft → review → archive/sync` 进主 spec；轻量 CLI；防止 agent 把需求幻觉进既有 spec | Phase 6 变更规格 delta（条目 20，**已吸收**） |
| **AWS Kiro** | **EARS 需求语法** + **Agent Hooks**（保存文件时触发的事件驱动自动化，像老开发帮你抓漏）+ steering files + 走 Amazon Bedrock | PRD AC 用 EARS（条目 3）+ `.claude/hooks` + `check_docs.py`（条目 8） |

## 二、逐项结论：已吸收 / 现在吸收 / 暂不吸收

### ✅ 已吸收（本流程已有等价或更强机制）

| 工具概念 | 本流程落地 | 条目 |
|---|---|---|
| OpenSpec delta（ADDED/MODIFIED/REMOVED） | Phase 6 变更规格 delta 模板 + 回写 PRD + 归档 | 条目 20 |
| Kiro EARS 需求语法 | PRD 验收标准 section（EARS / Given-When-Then + AC 编号 + 验证方式） | 条目 3 |
| Kiro Agent Hooks（保存触发校验） | `.claude/settings.json` hooks + `check_docs.py`（token 上限/失效链接/孤立文档），并入 `check_all` | 条目 8 |
| Spec Kit spec→plan→tasks→implement 命令链 | Phase 1 specs → Phase 2 plan → Phase 3 chunk 循环（且多了 Phase 0 商业前置 + Phase 4/5/6） | 主链 |
| OpenSpec 防需求幻觉进既有 spec | sync-before-merge（spec 未同步不得合并）+ Phase 4 spec 符合性检查 + 全链路 FR/AC 追溯 | 条目 5 |
| Spec Kit `/speckit.analyze` 一致性校验 | `check_all` + `check_docs.py` + Phase 4 spec 符合性检查 | 条目 5/8/9 |

### 🟡 现在吸收：Spec Kit `constitution.md`（项目宪法）

**评估**：Spec Kit 的 constitution = 比 AGENTS.md 更高位的「不可协商原则」层（steering）。本流程现状：方法论核心 9 铁律是**全局**宪法；裁剪表底线（specs before code / commit 当存档点 / 再信任也要 review）是**项目级**底线——但散落在方法论 + 裁剪表 + AGENTS.md，**缺一个「项目自己的红线」单点**。

**决定吸收**（低成本高价值）：AGENTS.md 模板顶部加「项目宪法（不可协商）」section——把方法论底线 + **本项目特有红线**（如「支付金额永远服务端二次校算」「不可绕过 check_all 提交」）固化在最前、标 immutable，与下方可迭代的「通用规则」区分。详见下方「落地动作」。

**为什么不单建 `constitution.md`**：本流程已有 AGENTS.md 作为项目级 AI 指令入口，再建一个高位文件会造成「AGENTS.md vs constitution.md 谁是真相」的新漂移（正是条目 11 治理的跨文件矛盾）。把宪法作为 AGENTS.md 的**第一 section**，单一入口、分层清晰。

### ⏸️ 暂不吸收（记入 backlog，按需再评估）

| 想法 | 暂不做的理由 | 何时重新评估 |
|---|---|---|
| 直接用 OpenSpec CLI 管理变更 | 本流程 delta 模板已吸收其格式精髓；CLI 绑定其目录约定，与现有 `workflow_output/` 结构冲突，迁移成本 > 收益 | 团队扩大、多变更并行频繁时 |
| 整体迁移到 Spec Kit 脚手架 | 本流程的 Phase 0 商业前置 / 运维考量 / 联动点清单 / 大白话注解是 Spec Kit 没有的优势层，迁移会丢 | Spec Kit 补齐这些层时（短期不会） |
| Kiro IDE + Bedrock | 绑定 AWS + 特定 IDE；本流程工具无关（Claude Code / Codex / 任意 agent 皆可） | 团队统一上 AWS + Kiro 时 |
| 形式化需求矛盾检测（SMT 求解器） | 重型，单人/小团队 ROI 低；Phase 4 对抗式 review + spec 符合性检查已覆盖大部分 | 需求规模大到人工 review 跟不上时 |
| property-based / 形式化测试全面铺开 | 已作为 testing_strategy §2.4 进阶可选项（条目 14）；强制铺开成本高 | 核心逻辑复杂度上升时 |

## 三、原则：工具服务于流程

1. **优势层不可让渡**：Phase 0 商业前置分析、运维考量清单、功能联动点清单、大白话术语注解——这四样是现成 SDD 工具都没有、而本流程的核心差异化。任何工具化方案都必须**保留这四层**，并作为「宪法/steering」注入工具上下文。
2. **概念吸收 > 整体迁移**：好概念（delta / EARS / hooks / constitution）逐条吸收进现有 markdown 约定，保持工具无关。这样换 agent（Claude Code→Codex→Gemini）不换流程。
3. **校验机器化、判断人化**：能确定性校验的（token 上限/链接/追溯编号/漂移计数）交给 `check_all` + hooks；需要商业/体验判断的留在人在环路。
4. **流程自身也要迭代**：本评估不是终点——每次实跑真实项目后，把「哪个工具的新做法值得吸收」沉淀回 `1. 问题与需改进点.md`。
