# Requirement and Product Engineering Workflow

## Purpose

基于需求与产品工程知识框架，提供从需求收集到产品迭代演进的全链路标准化执行路径，覆盖AI-Native用研、需求结构化拆解、优先级组合排序、变更追踪RTM、PRD视觉化、数据驱动迭代六大核心能力。

## Prerequisites

- 已明确产品类型（B端企业软件/C端消费者应用/平台型产品）
- 已确定目标用户群体与核心使用场景

## Steps

### Step 1: AI-Native用户研究与需求收集

**Goal**: 运用AI-Native用研方法论完成高效需求收集，建立用户认知基线
**Completion criterion**: 输出《用户研究报告》，覆盖目标用户画像、核心痛点、使用场景，AI用研成本较传统降低80%+

依据AI-Native用研框架 [参考: Agents知识库/0_超级编程行业知识库/14_软件工程与开发全流程.md > 需求与产品工程]：
1. Discovery阶段（嗅探测试）：
   - AI Agent并行执行千场访谈（单场成本从3000元降至200元）
   - 合成用户仅用于早期Discovery，Big-5维度相关度需达0.72-0.85
   - 方法：5 Whys根因追问 + Critical Incident关键事件法 + Jakob Nielsen 5用户法则（发现85%可用性问题）
2. 需求结构化收集：
   - B端三层用户：决策者（关注ROI/效率/合规）/ 管理者（关注报表/流程/权限）/ 使用者（关注易用/快捷/稳定）
   - C端聚焦：DAU/MAU/LTV + 行为数据分析（漏斗/留存/路径）
   - 核心指标：B端关注ARR/MRR，C端关注留存率>30%次日 + NPS>30
3. 经典方法补充：
   - Kano模型问卷（分类需求为魅力/期望/基本/无差异/反向）
   - SUS可用性量表（评分>68为可用，>80.3为优秀）
执行：
- 输出《用户画像卡片》（Persona）： demographic + behavioral + needs + pain points
- 输出《需求收集清单》：按FURPS+分类（功能性/可用性/可靠性/性能/可支持性+其他约束）
- 合规预检：PIPL/GDPR告知同意、生物识别"单独同意"、AI Act高风险系统风险评估

### Step 2: 需求结构化拆解与Story Mapping

**Goal**: 将原始需求转化为结构化、可执行的用户故事体系，完成MVP切分
**Completion criterion**: 输出《用户故事地图》与《需求规格说明书》，四级粒度（Epic/Feature/Story/Task）完整，MVP范围明确

依据需求结构化拆解框架 [参考: Agents知识库/0_超级编程行业知识库/14_软件工程与开发全流程.md > 需求结构化拆解]：
1. Story Mapping八步法（Jeff Patton）：
   - 第1步：写出用户所有活动（Backbone主干）
   - 第2步：分解活动为具体任务（Walking Skeleton骨架）
   - 第3步：从左到右按时间线排列（用户旅程）
   - 第4步：从上到下按优先级排列（Must have在上）
   - 第5步：画出MVP切分泳道（第一泳道=最小可行产品）
   - 第6-8步：补充细节、验证完整性、迭代优化
2. 四级粒度对应SAFe四级体系：
   - Epic（史诗）：3-6个月，业务价值主题
   - Feature（特性）：2-4周，可交付功能块
   - Story（故事）：1-3天，用户可感知价值点
   - Task（任务）：0.5-1天，技术实现动作
3. 验收标准BDD化：
   - 使用Gherkin语法：Given（前置条件）- When（操作）- Then（期望结果）
   - 每个Story必须有至少1个验收标准
执行：
- 输出《用户故事地图》（物理墙或Miro/FigJam电子版）
- 输出《需求规格说明书》：FURPS+分类 + 用户故事清单 + 验收标准
- 验收标准用BDD Gherkin格式表达，可直接转化为自动化测试用例

### Step 3: 优先级组合排序

**Goal**: 基于多框架组合策略完成需求优先级排序，避免单一框架偏差
**Completion criterion**: 输出《需求优先级矩阵》，每个需求有明确的框架标签与排序依据，Must类需求占比≤60%

依据优先级组合框架 [参考: Agents知识库/0_超级编程行业知识库/14_软件工程与开发全流程.md > 优先级排序]：
1. RICE框架（季度Roadmap）：
   - R（Reach）：影响用户数
   - I（Impact）：影响程度（0.25/0.5/1/2/3）
   - C（Confidence）：信心度（%）
   - E（Effort）：人月投入
   - 得分 = (R × I × C) / E
2. Kano模型（战略满意度盘点，每12-18个月重做）：
   - 魅力属性（A）：带来惊喜，不做不影响满意度
   - 期望属性（O）：线性影响满意度
   - 基本属性（M）：必须有，不做极度不满
   - 无差异（I）：做与不做无影响
   - 反向（R）：做了反而降低满意度
3. MoSCoW（版本切片，Must不超过60%）：
   - Must have：不做项目失败
   - Should have：重要但可妥协
   - Could have：有则更好
   - Won't have：明确不做（防止范围蔓延）
4. WSJF（SAFe Epic排序）：
   - 价值 / (时间紧迫性 + 风险降低/机会启用 + 工作量)
5. ICE（Sprint快速排序）：
   - I（Impact）× C（Confidence）× E（Ease）
执行：
- 按场景调度框架：Roadmap级用RICE + 战略盘点用Kano + 版本切分用MoSCoW + Epic级用WSJF + Sprint级用ICE
- 输出《需求优先级矩阵》：需求ID + 名称 + RICE分 + Kano分类 + MoSCoW标签 + WSJF分 + ICE分 + 最终排序
- 定义《版本范围说明书》：本版本包含的Must/Should/Could清单

### Step 4: 需求变更追踪与RTM管理

**Goal**: 建立需求变更控制委员会（CCB）与双向追溯矩阵（RTM），确保需求覆盖率≥95%
**Completion criterion**: CCB机制运行正常，RTM覆盖率≥95%，变更影响分析（CIA五维）完整记录

依据需求变更管理框架 [参考: Agents知识库/0_超级编程行业知识库/14_软件工程与开发全流程.md > 变更管理]：
1. CCB四级审批：
   - L1：Sprint内小变更，PO审批
   - L2：跨Sprint变更，PO+Scrum Master审批
   - L3：版本级变更，产品总监审批
   - L4：战略级变更，CTO/VP审批
2. CIA五维影响分析：
   - Cost：开发成本变化
   - Impact：对现有功能的影响
   - Architecture：架构改动范围
   - Timeline：进度影响
   - Risk：新增风险
3. RTM双向追溯：
   - 正向：需求 → 设计 → 代码 → 测试用例
   - 反向：测试用例 → 代码 → 设计 → 需求
   - 覆盖率目标：需求覆盖率≥95%，测试覆盖率≥90%
执行：
- 建立《变更控制流程》：变更申请 → CIA分析 → CCB审批 → 更新RTM → 通知干系人
- 配置工具支持：Jira/Xray/TestRail实现需求-测试关联
- 输出《变更日志》：变更ID + 日期 + 申请人 + 变更内容 + CCB决策 + 影响范围

### Step 5: PRD视觉化与数据驱动迭代

**Goal**: 输出模块化、视觉化的PRD文档，建立数据驱动的产品迭代机制
**Completion criterion**: PRD通过评审，包含视觉原型+数据埋点方案+迭代指标，A/B测试满足p<0.05+功效>0.8

依据PRD与数据驱动框架 [参考: Agents知识库/0_超级编程行业知识库/14_软件工程与开发全流程.md > PRD视觉化]：
1. PRD模块化结构：
   - 产品背景与目标
   - 用户故事地图（核心流程截图）
   - 功能详述（每个Feature：用户故事+验收标准+界面原型+异常处理）
   - 非功能需求（性能/安全/兼容性）
   - 数据埋点方案
   - 发布计划与回滚策略
2. 视觉化要求：
   - Figma AI Agent实现画布级AI操作，设计Token到前端组件库1:1映射
   - 每个核心流程提供高保真原型+交互说明
   - 状态流转图（State Machine）覆盖全部业务状态
3. 数据驱动迭代：
   - 扩展信号：留存率>30%次日 + NPS>30 + 核心功能使用率>50%
   - A/B测试规范：样本量计算（功效>0.8）→ 随机分组 → 运行周期（至少1个完整业务周期）→ 统计检验（p<0.05）→ 结论与行动
   - 产品迭代路径：深度扩展（核心功能打磨）→ 广度扩展（场景覆盖）→ 平台化扩展（生态构建）
执行：
- 输出《产品需求文档（PRD）》：模块化结构 + 视觉原型嵌入
- 输出《数据埋点方案》：事件定义（Event）+ 属性（Property）+ 触发时机 + 上报规则
- 输出《A/B测试计划》：假设 + 指标 + 样本量 + 运行周期 + 成功标准

## Post-Workflow

1. 读取 `checklist/requirement_product_workflow_checklist.md`
2. 交叉验证每个用户故事、每项优先级评分、每个变更记录
3. 全部通过后输出《需求与产品工程总纲》并归档
