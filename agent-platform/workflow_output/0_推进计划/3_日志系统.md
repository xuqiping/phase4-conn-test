# 顶级日志系统 · 规划设计

> 版本：v1.0 · 2026-08-09
> 现状基线：[22-日志与可观测性](../../项目工程文档/项目功能介绍/速查表/22-日志与可观测性.md)（三通道已完成：console / app.log / error.log）
> 本文是**规划**不是实现。实施时按阶段拆 PR，每阶段独立可验收。
> 部署约束：Windows Server 单机（jar + Nginx + PG + Redis + Python sidecar），所有选型必须能跑在 Windows、资源占用小。

---

## 一、目标

| 维度 | 现状 | 目标 |
|---|---|---|
| 排障效率 | grep 文件，靠人眼串线索 | **一个 traceId 串起一次请求的全部日志（含 SQL、LLM 调用、sidecar 回调）** |
| 日志内容 | 有时间/级别/类名，缺用户/请求上下文 | 每条日志必带：时间、traceId、userId、IP、method+uri、耗时；SQL 走独立通道 |
| 审计能力 | 无操作审计（谁改了什么查不到） | 操作审计落库 + 前端可查，关键链路防篡改（见 [5_安全体系](5_安全体系.md) §D） |
| 日志检索 | 只能 tail/grep 单机文件 | Grafana 集中检索：按 traceId / userId / 模块 / 关键词秒级查询 |
| 数据安全 | 聊天原文曾落 INFO（已修 #6） | 脱敏规则制度化 + CI 门禁，防回潮 |

## 二、总体架构

```
┌─────────────┐  JSON 结构化日志(滚动文件)   ┌──────────────────┐
│ Spring Boot │ ──────────────────────────► │                  │
│  (Logback   │                              │   Grafana        │
│   + MDC)    │ ─── 操作审计 ──► PG audit_logs│  检索/看板/告警   │
└─────────────┘                              │                  │
┌─────────────┐  structlog JSON + traceId    │  ▲        ▲      │
│ Py Sidecar  │ ──────────────────────────►  │  │        │      │
└─────────────┘         │                    │  │        │      │
        采集: Grafana Alloy / Promtail ───────┘  │        │      │
        存储: VictoriaLogs 或 Loki（单二进制）─────┘        │      │
        指标: Prometheus（见 4_运维系统.md）────────────────┘      │
```

**选型结论（结合 2026 年社区共识与 Windows 单机约束）：**
- 日志库：**SLF4J + Logback 不换**（已就位），加 `logstash-logback-encoder` 输出 JSON。
- 链路 ID：**Micrometer Tracing + OpenTelemetry bridge**（Spring Boot 3 官方路径，Sleuth 已死），traceId/spanId 自动进 MDC。
- 集中存储：**VictoriaLogs**（首选，单二进制、Windows 原生、资源占用约为 ES 的 1/5，支持全文检索）或 **Grafana Loki**（备选，生态更成熟）。**不选 ELK**——ES 在 Windows 单机上吃 2GB+ 内存，杀鸡用牛刀。
- 可视化/告警：**Grafana** 一套通吃（日志 + 指标 + 告警），与运维系统（[4_运维系统.md](4_运维系统.md)）共用。

## 三、分阶段实施

### P0 · 日志规范化改造（纯后端，不动架构） — 预估 3~4 人日

| # | 事项 | 落点 | 说明 |
|---|---|---|---|
| 1 | **traceId 全链路透传** | `pom.xml` 加 `micrometer-tracing-bridge-otel`；`application.yml`：`management.tracing.sampling.probability: 1.0`；logback pattern 加 `%mdc{traceId:-},%mdc{spanId:-}` | Spring Boot 3 官方方案，自动织入 MVC/WebClient/MDC |
| 2 | **异步上下文传递** | `chat/config/MemoryTaskExecutorConfig.java` 等线程池加 `ContextPropagatingTaskDecorator` | 不加的话 @Async 方法 traceId 断链（记忆管线全是异步） |
| 3 | **用户上下文人 MDC** | 新增 `MdcUserFilter`（OncePerRequestFilter，排在 JWT filter 之后）：`MDC.put("userId"/"username"/"clientIp")`，finally 里 `MDC.clear()` | 每条日志自动带 userId——速查表 22 待办「日志需含用户」落地 |
| 4 | **SQL 独立通道** | logback 新增 `SQL_FILE` appender + logger `com.superprogrammer.*.mapper` DEBUG→sql.log（默认仍 WARN 静默，调试时开关） | 落地速查表 22 待办「sql 未分离」；用 `LOG_SQL_ENABLED` 环境变量控制 |
| 5 | **JSON 结构化输出** | `logstash-logback-encoder` 的 `LogstashEncoder`；保留 console 彩色（人类读）+ 文件 JSON（机器读）双格式 | 为 P2 采集做准备；字段含 timestamp/level/logger/traceId/userId/ip/uri/costMs |
| 6 | **请求耗时与出入参摘要** | 新增 `RequestLogFilter`：一行 INFO 记 `method uri status costMs userId traceId`；body 不记（防 PII） | 替代 Spring Security 每请求一行的噪声 |
| 7 | **脱敏制度化** | 自定义 Logback `MessageConverter`：`%mask` 转换符，正则打码手机号/银行卡/身份证/邮箱/apiKey | 在 #6 修复（INFO→DEBUG）之上再加一层兜底；正则表集中配置 |
| 8 | **sidecar 对齐** | sidecar 加 `structlog` JSON 输出；Java 回调 sidecar 时把 `traceparent` header 传过去，sidecar 记同一 traceId | 一次工作流执行跨 Java/Python 串成一条链 |

**P0 验收：**
- 发一条对话消息 → `grep <traceId> logs/*.log` 能看到：HTTP 入请求 → 路由策略 → LLM 调用 → 记忆管线（异步不断链）→ SQL → 出响应，全程同一 traceId。
- 日志中出现测试银行卡号 `6228...` → 输出为 `6228****...`。
- sql.log 独立成文件，app.log 无 SQL 刷屏。

### P1 · 操作审计落库 + 日志中心页面 — 预估 4~5 人日

| # | 事项 | 落点 |
|---|---|---|
| 1 | **audit_logs 表**（Flyway V_next） | 字段：`id, trace_id, user_id, username, module, action, target_type, target_id, detail_json, client_ip, user_agent, result, created_at`；`detail_json` 记「改了什么」的前后值摘要（不含 PII 原文） |
| 2 | **@AuditLog 注解 + AOP** | `common/audit/AuditLogAspect.java`：标注在敏感写操作上（用户/角色/权限增删改、Agent 发布、KB 删除、系统设置变更、积分调整），自动写 audit_logs；异步落库（线程池复用记忆管线配置） |
| 3 | **登录审计** | 登录成功/失败、登出、token 刷新、注册 → 全部入 audit_logs（安全事件源） |
| 4 | **前端日志中心** | `frontend/src/views/admin/logs/`：审计日志页（按用户/模块/时间/action 筛选 + 分页，复用 PageResult）；仅 `system:audit:read` 权限可见 |
| 5 | **审计保留策略** | 按月分区或定时归档；审计表只允许 INSERT/SELECT（DB 层 REVOKE UPDATE/DELETE，见安全体系 §D） |

**P1 验收：** 管理员改一次角色权限 → 日志中心 1 秒内可查到「谁在什么时间把哪个角色的哪个权限从 X 改成 Y，来源 IP」。

### P2 · 集中式日志栈（VictoriaLogs/Loki + Alloy + Grafana） — 预估 2~3 人日

| # | 事项 |
|---|---|
| 1 | 服务器装 VictoriaLogs（单 exe）+ Grafana Alloy（采集 agent，Windows 服务化用 WinSW） |
| 2 | Alloy 配置：tail `logs/*.log`（JSON 解析）+ sidecar 日志目录 → push 到 VictoriaLogs |
| 3 | Grafana 加 VictoriaLogs 数据源；预置三个视图：①按 traceId 查全链 ②按 userId 查行为 ③ERROR 实时流 |
| 4 | 保留策略：app 30 天、error 90 天、audit 180 天（落库部分另算） |
| 5 | **降级方案**：不想引入新组件就先跳过 P2——P0 的结构化日志 + P1 的审计页已覆盖 80% 排障场景，grep JSON 文件照样快 |

**P2 验收：** Grafana 输入 traceId → 3 秒内列出该请求跨 Java/sidecar 的全部日志行，按时间排序。

### P3 · 日志告警联动 — 预估 1~2 人日

- error.log 出现率突增（5min 内 >20 条）→ Grafana Alert → 钉钉 webhook（复用项目已有钉钉集成）。
- 特定模式告警：`LLM调用失败` 连续 N 次、登录失败同 IP >10 次/min（安全事件联动 [5_安全体系](5_安全体系.md)）。
- 与运维系统共用 Alertmanager/告警通道，规则清单在 [4_运维系统.md](4_运维系统.md) §三 统一维护。

## 四、配置与表设计要点

### logback-spring.xml 目标结构（P0 后）
```
CONSOLE      彩色, INFO+, 带 traceId/userId
APP_FILE     JSON, INFO+, 50MB×30天×2GB
ERROR_FILE   JSON, ERROR only, 20MB×90天
SQL_FILE     JSON, mapper DEBUG 开关式, 默认静默
```

### MDC 字段规范（全项目统一）
| key | 来源 | 说明 |
|---|---|---|
| `traceId` / `spanId` | Micrometer Tracing 自动 | 链路 ID |
| `userId` / `username` | MdcUserFilter | 未登录为 `-` |
| `clientIp` | MdcUserFilter（X-Forwarded-For 首段） | |
| `module` | logger 名推导 | agent/chat/knowledge/llm… |

### 红线（写进代码评审 checklist）
1. 任何 `log.info` 不得打印用户输入原文/记忆原文/LLM 响应原文——只打 length/hash/id。（#6 防回潮）
2. 高基数字段（userId、traceId）进日志/span，**不进 metric tag**（会撑爆 Prometheus）。
3. 新增异步提交点必须过 `ContextPropagatingTaskDecorator` 包装。
