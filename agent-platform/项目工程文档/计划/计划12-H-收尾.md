# 计划12 · H · 收尾（v2 修正版）

> 子 plan。主索引：[计划12-个人记忆重设计-实现开发计划.md](计划12-个人记忆重设计-实现开发计划.md)。设计：[总体设计 §9](../设计/个人记忆重设计-总体设计.md)。
>
> **v2 修正缘由**：v1（Phase2 写）假设「新栈线性替换 → 删 legacy」。实际 C/D/E 迭代全部偏离 plan「改 legacy」改为「建并行新栈不动 legacy」（每轮进度已记偏离），导致**活聊天路径从未切到新栈**。直接执行 v1（DROP+删）= ChatSessionService 仍读写 `user_memories` → 每次聊天运行时崩。故 H 真实工作 = **先切流，再 DROP+删**。

## 目标
活聊天切新栈 → 旧端点 404 → 旧表 DROP → 共用类瘦身 → 前端双栈期结束 → 速查表 09 重写。

## 探查结论（写码前已确认的事实）
1. **ChatSessionService 活路径全走旧栈**：召回 `memoryService.buildMemoryContext`(L249 sync/L433 stream)、写入 `memoryService.processMemory`(L284/289 sync、L499/504 stream、L592/597 agent)、`recordIncident`(L293/508/601)、活冲突拦截 `interceptConflict`(L328) 用 `conflictService.getActivePendingOrExpire/route/flag/resolve`(L330-346)。
2. **新栈入口已就绪但未接线**：召回 `MemoryRecallPipeline.recall(query, MemoryRecallScopeRequest, userId)→MemoryRecallResult.assembledText`(String，可直替 buildMemoryContext)；写入 `MemoryGenerationService.processTurnAsync(userId,sessionId,sessionProjectId,writePersonal,targetIds,input,output)`(fire-and-forget，可替 processMemory)。
3. **共用类新栈复用面**（删不净，须瘦身保留）：
   - `MemoryConflictJudge`：新栈仅 `MemoryConsolidationTxService`(L75) 调 `judgeSummaryConflict`。legacy 方法（judge/batchExtractEntities/selectRelevantKeysBlocks/zhKeyDisplay/route + EXTRACT_PROMPT）可删，留 judgeSummaryConflict+私有辅助+SummaryConflictResult。
   - `MemoryQueryCache`：新栈仅用 `evictUser`(Generation L132/Consolidation L132/ConflictResolution L96)。legacy `getCleanByBlock` 可删。
4. **活冲突拦截 UX 无新栈等价**：新栈冲突由总结 worker 产出 pending → 面板 `MemoryConsolidationController` 解决，**不在聊天中拦截下一轮**。故 `interceptConflict` + `getActivePendingOrExpire/route/flag` 整块弃（设计 §3.5 冲突走面板非聊天拦截）。
5. **incident/status UX**：新栈 fire-and-forget 静默降级（日志），无 incident 机制。`recordIncident/getAndClearIncident/getMemoryStatus` + 前端轮询弃。
6. **SystemSettingController 注入 MemoryService**(L26)：用途待 chunk 查（rag-memory settings/entities-config），迁 SystemSettingService 自承或新服务。
7. **前端旧栈**：`chat.ts` 17 个 `memories` 客户端；`MemoryManagerPanel` 首页签 legacy 记忆列表 pane；`RagMemorySettingsTab`(挂 SettingsView) legacy 读控件；M2(key-meta)/M3(entities-config)/M4(scope) 骑旧 MemoryController+SystemSettingService。

## 依赖
A-F、I2-I4、写侧 hook（全 ✅）。本迭代起 ChatSessionService 才正式用新栈。

## 阶段与 chunk（6 阶段）

### H'-1 后端切流（ChatSessionService 三路改接新栈）
- **scope 适配器**：legacy `MemoryScope(userId,includeGlobal,projectIds)` → `MemoryRecallScopeRequest`（召回）/ writePersonal+targetIds（写入）。**默认 scope = {个人 + 当前会话项目}**（保旧 auto-include 近似），方向 INOUT，时间窗 null，includeDeparted=false。建小 adapter 方法（chat/service/internal/MemoryChatAdapter 或直接内联）。
- **召回替换**：3 处 `buildMemoryContext(readScope,msg)` → `pipeline.recall(msg, scopeReq, userId).assembledText`（null/degraded → 空串兜底）。
- **写入替换**：6 处 `processMemory(writeScope,writeTargetProjectId,sessionId,msg,resp,model)` → `generationService.processTurnAsync(userId,sessionId,session.getProjectId(),writePersonal,targetIds,msg,resp)`。model 参数弃（新 generator 走配置）。
- **弃活冲突拦截**：删 `interceptConflict`(L325-348)+调用处；删 ChatSessionService 的 `conflictService`/`conflictJudge` 注入字段。
- **弃 incident**：删 `recordIncident`(L293/508/601) 调用。
- **测试**：ChatSessionService 现有单测改 mock 新栈（pipeline/generationService）；新增「默认 scope 含会话项目」「空召回不崩」「writePersonal 透传」单测。IT：一轮对话端到端写 memory_turns + 召回注入。

### H'-2 共用类瘦身（保新栈依赖）

- **MemoryQueryCache**：删 `getCleanByBlock`（legacy user_memories 缓存）；确认新栈有无 put（若仅 evict 无 put → evictUser 调用一并清，或保留防未来召回缓存）。
- **SystemSettingController 解 MemoryService 依赖**：查 L26 用途 → 迁。
- **测试**：瘦身类现有单测删 legacy 用例，留 judgeSummaryConflict/evictUser 用例。
