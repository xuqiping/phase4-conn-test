# Phase 4 · 运行验证（Run + review + 性能评测）

> 类型：流程步骤 · **Phase 4**
> 版本：v1.7（v1.1 增性能评测；v1.2 增快速启动速查表；v1.3 增用户操作手册全量验证 + 桌面端自动化测试；v1.4 增验收标准 AC 逐条核对；v1.5 review 增 spec 符合性检查；v1.6 出口加 check_docs.py 文档规则校验；**v1.7 review 升级为结构化分维度清单 + 对抗式验证 + 高危功能换模型交叉审/人必审**）
> 对应模式：**Plan-Implement-Run 的 Run 步** · 铁律：**#6 人在环路、#9 测试自动化**

## 目标

跑起来、亲眼看它工作、再用「第二个 AI」交叉审查。AI 写的代码**比人写的更需要严格验证**——它常表面正确、暗藏缺陷。

## 输入

- Phase 3 的实现（代码 + 测试）

## 动作清单

1. **Run（运行）**：让 AI 运行应用并自检。
   - Web 应用：用 Playwright MCP 导航、点击、截图、看 console / network。
   - **桌面端应用（PyQt / Tauri / Electron 等）**：按技术栈选自动化方案，核心逻辑下沉、GUI 层轻量验证——
     - **PyQt / PySide**：
       - 逻辑层用 `pytest-qt` 测控件状态、信号槽、模型视图；
       - GUI 自动化用 `PyAutoGUI` / `lackey` / `SikuliX` 模拟点击 + 截图回归；
       - 控件定位优先用 **MSAA / UI Automation**（Windows）或 Qt 的 `objectName`，**绝不用固定屏幕坐标**（分辨率/DPI 会飘）。
     - **Tauri**：
       - Rust 后端用 `cargo test` 测命令（Command）与状态；
       - WebView 前端用 **Playwright** 或 Vitest；
       - 端到端用 **`tauri-driver`**（WebDriver）驱动打包后的应用；
       - 必须在目标操作系统（Win/Mac/Linux）上跑一遍「安装 → 启动 → 核心功能 → 退出/卸载」。
     - **Electron**：
       - 用 **Playwright 的 Electron 模式** 测主进程 + 渲染进程；
       - 渲染进程业务逻辑用 Vitest / Jest；
       - 旧项目若用 Spectron，评估迁移成本，新项目不推荐。
     - **通用原则**：
       - 能下沉到业务逻辑层的，**不要依赖 GUI 自动化**；
       - GUI 自动化优先用**可访问性 API / 控件属性**，次选截图/坐标；
       - CI 环境用**容器/虚拟机 + 虚拟显示器**（Linux Xvfb、GitHub Actions `windows-latest`）；
       - 桌面端覆盖率到不了 100% 是常态，**关键路径自动化 + 次要路径人工走查**组合验收。
   - 基础设施：`terraform plan` / `apply` 到沙箱。
   - 检查应用是否已在运行，没运行就启动，耐心等启动（重试 3 次）。
2. **【v1.4 新增】验收标准逐条核对（若 PRD 有 AC section）**：对照 `specs/PRD.md` 的验收标准表，**逐条 AC 判定通过/不通过**并记录——标「自动化测试」的确认对应测试用例存在且通过；标「人工验收」的亲自操作验证。任何 AC 不通过 → 打回 Phase 3 修；**发现「实现了但 PRD 没写」的功能 = 规格漂移，要么补 AC 要么删实现**。
3. **【v1.3】用户操作手册全量验证（若 Phase 3 产了 User-Ops）**：
   - 找到 `workflow_output/docs/user-ops/<功能名>用户操作手册.md`。
   - 按表中「步骤 → 用户操作 → 界面变化 → 预期结果」**逐项执行**，不跳过任何一步。
   - 记录实际结果，用**截图或录屏**作为验收证据。
   - 发现实际与手册不符 → 先判定：是**代码 bug**（修代码）还是**手册过时**（同步更新手册和 Feature Map）。
4. **发现问题 → 修**：形成「运行→报错→修→再运行」的紧反馈环，AI 在这个环里很强。
5. **性能评测**：对照 Phase 1 的 performance_goals.md 做性能验证。
   - **关键接口响应时间**：测量核心功能的 API / 页面响应，记录 p50/p95/p99。
   - **并发测试**：模拟多用户并发访问，观察系统表现（吞吐/错误率/资源使用）。
   - **资源使用率**：CPU/内存/磁盘/网络带宽占用情况。
   - **记录性能结果**与 Phase 1 定义的目标对比，未达标则分析瓶颈（慢查询/内存泄漏/CPU 热点等）。
6. **Review（交叉审查）**（铁律 #6 招数）：
   - **spawn 第二个 AI 会话**（最好换一个模型）审查第一个 AI 的代码——**【v1.7】按 `4-review.prompt.md` 结构化清单走**：8 个维度逐项过（正确性 / 规格符合性 / 安全 / 规范一致性 / 文档一致性 / 可解释性 / 简化与复用 / 性能），每维度必须给出明确结论（✅ 确认无问题 / ⚠️ 发现），**不允许沉默维度**。**【v1.7】用 Claude Code 开发可直接 dispatch `code-reviewer` 子 agent**（`.claude/agents/code-reviewer.md`，它指向同一份 prompt，内容同源不漂移）。
   - **【v1.7】对抗式验证心法**：审查者不是来「确认没问题」的，是来**推翻「没问题」这个假设**的——带着「它一定藏了 bug」的态度审，强制输出**三个最可能藏 bug 的位置**（哪怕最后确认没问题也要列，宁误报不漏审）。
   - **【v1.7】高危功能加码**：功能触及 **资金 / 权限变更 / 数据删除 / 个人信息导出 / 外部支付与通知** 时，review **必须换模型交叉审 + 人逐行审关键路径 + 相关 AC 回归测试全绿**（含至少一条负向/边界用例）。
   - **【v1.5】spec 符合性检查（漂移检测）**：让第二个 AI **对照 PRD/plan 逐条核对实现**，输出漂移清单，按三类归类——
     - **多做了**：代码实现了但 PRD 没有的功能（→ 要么补 AC 进 PRD，要么删实现）；
     - **少做了**：PRD/plan 要求但代码没实现的（→ 打回 Phase 3 补）；
     - **做偏了**：实现了但与规格描述不一致的（→ 改实现或改规格，并记录为什么）。
     漂移清单记入 `workflow_output/开发进度/开发进度总览.md` 的「规格漂移待办」，处置完一项清一项。
   - **对照 Feature Map 验证实现一致性**：代码位置、调用链路、关键技术落点是否与 `workflow_output/docs/feature-map/` 中的记录一致；不一致 → 先确认是代码改漏还是文档过时。
   - **对照 User-Ops 验证交互一致性**（若存在）：用户操作手册里的步骤是否与实际 UI 流程一致。
   - **【v1.6】上下文文件矛盾检查**：顺带核对 AGENTS.md / file_structure.md / 通用约束.md 是否与代码现状矛盾（目录对不上、规则已失效、last_updated 过期）——过期的上下文文件会带偏 AI，发现就顺手更新。
   - 人也亲自过一遍关键路径代码。
   - 把 lint 错误、测试失败日志贴回给 AI 让它修（铁律 #9）。
7. **记录验证结果 + review 结论 + 性能评测结果**，决定是打回 Phase 3 修，还是放行 Phase 5。
8. **产出/更新快速启动速查表**：项目首次跑通（或启动方式有变）时，在 `workflow_output/docs/run-guide/快速启动速查表.md` 产出（骨架见 [项目模板/workflow_output/docs/run-guide/_模板.快速启动速查表.md](项目模板/workflow_output/docs/run-guide/_模板.快速启动速查表.md)），记录：
   - **项目组成总览**：前端 / 后端 / 数据库 / Redis / 桌面客户端等各部分是什么、代码在哪
   - **启动步骤**：每个服务/客户端怎么起——命令行命令 + 具体哪个入口文件/程序打开
   - **端口占用速查**：前端/后端/Redis/数据库 各占哪个端口
   - **查端口占用 & 关闭端口命令**：Windows（`netstat -ano | findstr :端口` → `taskkill /PID <PID> /F`）+ Linux（`lsof -i:端口` → `kill -9`）
   - 常见启动报错速查

   > 这份速查表让"换机器 / 新成员 / 几个月后的自己"**3 分钟把项目跑起来**，不用翻代码猜怎么启动。启动方式一变（换端口、加服务、加桌面客户端）就回来更新，否则会误导。

## 避坑点

- **测试不是 review 的替代品**。测试过的代码仍要 review——AI 会写「刚好通过测试但逻辑错误」的代码。
- 「spawn 第二个 AI」是性价比极高的一招，能抓出第一个模型的盲点。别省。
- **review 时要对照 Feature Map 和 User-Ops**：代码位置、调用链路、交互步骤是否与实际一致。Phase 4 发现文档与代码脱节，要及时回 Phase 3 同步更新。
- **桌面端测试别只跑开发模式**：打包后的应用（安装包）和 `npm run dev` 是两回事，发布前必须在目标系统上跑「安装 → 启动 → 核心功能 → 退出/卸载」。
- **桌面端 GUI 自动化优先用可访问性 API，别依赖固定坐标**：分辨率、系统缩放、主题都会影响坐标定位。
- 缺测试 / 缺 CI 的项目，AI 的错会潜伏到很晚才爆。Phase 1 没写测试策略的话，这里补。
