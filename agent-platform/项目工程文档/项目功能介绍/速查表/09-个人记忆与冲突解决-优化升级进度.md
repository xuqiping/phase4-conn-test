## 一、背景与动机（为什么要做）

### 1.1 实测缺陷（playwright + preview 端点 + DB 复现）

混合检索（VECTOR_KEYWORD）下，同一家人记忆：

| query | 实际注入（preview 端点实测） | 结果 |
|---|---|---|
| `我的家人` | 婚姻状态/活动地点/**配偶名阿斐**/姓名/pet 小黑（5 条） | ✅ 检出家人 |
| `我想带我家人出去玩` | 仅「活动地点:家附近」（1 条） | ❌ 家人属性全丢 |

**根因三层**（详见根因分析备忘）：
1. **关键词通道对两条 query 都 0 命中**：分词器只切 CJK 2-gram（`家人`/`我家`/`我的`），而 DB 家人记忆的召回列（entities/memory_key/memory_value/memory_key_zh/block_label）**没有任何一列含"家人"**——block_label 是「家庭信息」不是「家人」，entities 是 `{配偶/妻子/孩子/女儿/宠物...}`。用户说的"家人"永远撞不上 DB 存的"家庭"。
2. **退化成纯向量**：`我的家人` embed 靠近家庭属性 → 命中；`我想带我家人出去玩` embed 被"带…出去玩"主导 → 静态家庭属性余弦 < 0.35 阈值被切。
3. **0 命中 LLM-key 兜底没触发**：query B 命中了「活动地点」(>0)，兜底（`selectRelevantKeys`）只在 0 命中时跑 → 语义救场被跳过。

### 1.2 治标 vs 治本

- **治标（A）**：硬编码同义表"家庭→家人"。只救家庭类，每类要手写，不可扩展。❌（不采纳）
- **治标（B）**：extract LLM 给召回词袋补上位词（家人/家庭/家属…）。**单独用是开集枚举、列不全，半治本**；但作为**治本的互补增强值得做**——上位词进 entities ①救 VECTOR_KEYWORD 关键词通道（老模式也受益）②富化 LLM_KEY 的 anchor 向量（粗筛召回率↑）。详见 §2.5 + 阶段 F。
- **治本（本文主方案）**：**把语义判断交给一次 LLM，而非枚举词袋**——粗筛（语义向量+词法，scale 到百万）砍到 top-N 候选 → LLM 精排选真正相关 key。LLM 天然把"家人"映射到 `配偶名/孩子年龄` key，无需任何同义词表。
- **落地策略 = 治本（主）+ 治标B（互补）**：治本解决根因，B 低成本加召回率 + 兼顾老模式，防御纵深。二者不互斥。

### 1.3 百万 key 不可爆

方案"灌全部 key 给 LLM"在几千~几万 key 就爆（token/延迟/上下文上限）。本方案两阶段：
- **粗筛 = pgvector ANN `<=>` + BM25 倒排**，O(log N)，百万级亚秒。
- **LLM 只碰 top-N 候选（N≈40）**，不碰百万。

> 现实缓解：记忆 per-user + key 归一（V31）+ 冲突合并（KEEP_BOTH 合一条）→ 单用户 key 数收敛，百万属理论上限。但架构必须预留 scale 路径。

## 二、新增检索模式 LLM_KEY（语义两阶段召回）

### 2.1 与现有模式的关系

`rag.memory.retrieval-mode` 现有三值（[SystemSettingService](../../backend/src/main/java/com/superprogrammer/system/service/SystemSettingService.java) `getMemoryRetrievalMode`）：`LLM_FULL_CONTEXT` / `EMBEDDING_VECTOR` / `VECTOR_KEYWORD`。**新增第四值 `LLM_KEY`**，在 [MemoryService.buildMemoryContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 增一分支，调 `buildLlmKeyContext(readScope, query)`。

- **不改** scope 解析（[MemoryScopeResolver](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryScopeResolver.java)）/ [MemoryScope](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryScope.java) record / SCOPE_FILTER / 唯一索引 / home 语义。
- 新模式同样 **scope-aware**：所有粗筛 mapper 查询带 `includeGlobal + projectIds`，命中 iff `(includeGlobal AND is_global) OR 挂 user_memory_projects`，与现有读语义一字不差。

### 2.2 召回锚点（anchor）—— 治本的关键信号

现 `user_memories.embedding` 是 **value 向量**（embed `memory_value`，如"阿斐"），用于块聚类（[findNearestBlock](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) + `MEMORY_BLOCK_SIM_THRESHOLD=0.6`）。value 向量对专名/短值漂移严重（"阿斐"≈名字概念，远离"家人"）。

**新增 `anchor_embedding halfvec(2048)`**：embed **召回锚点文本** =
```
block_label + " " + memory_key_zh + " " + memory_key + " " + entities(展开)
```
例：`家庭信息 配偶名 spouse_name 妻子 爱人 老婆 阿斐` → 家族概念富集 → embed 靠近"家人" → **高召回**。锚点是"标签+词袋"语义，比 value 稳定、比 key_zh 丰富。

- **与 §2.5 协同**：若 extract 给 entities 补上位词（"家人/家庭"），anchor 文本天然含之 → 向量更靠家族概念 → 粗筛召回率再涨。治标 B 是 anchor 的免费增强。

- 复用 [LlmGateway.embed(text, RagConfig.MEMORY_EMBED_MODEL)](../../backend/src/main/java/com/superprogrammer/llm/LlmGateway.java)（`MEMORY_EMBED_MODEL="doubao-embedding-vision"`，DIM 2048）+ [HalfVecUtil.toHalfVec](../../backend/src/main/java/com/superprogrammer/knowledge/util/HalfVecUtil.java)。
- 写入侧 0 额外 LLM 调用：anchor embed 复用既有 embed 链路（applyClean/processFacts 已在 embed value，顺带 embed anchor，多一次 embed 调用但同模型同批）。

### 2.3 两阶段 pipeline（[MemoryService.buildLlmKeyContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)，新方法）

```
query（限 scope）
  │
  ├─① query 扩展（复用 [QueryExpansionService.expand](../../backend/src/main/java/com/superprogrammer/knowledge/service/QueryExpansionService.java)(query, MEMORY_EMBED_MODEL)）
  │     → ExpandedQuery(canonicalQuery, qHalfs[])：改写+HyDE，多 qvec 提升 recall
  │
  ├─② 粗筛（scale 到百万）
  │     ├ anchor 向量 top-K：每 qHalf 跑 findTopKByAnchor（pgvector ANN `<=>`，scope 过滤），fan-out 合并
  │     └ anchor BM25：anchor_tokens_tsv 上 jieba + ts_rank（复用 [JiebaTokenizer](../../backend/src/main/java/com/superprogrammer/knowledge/util/JiebaTokenizer.java) + 知识库 [bm25HitsJieba](../../backend/src/main/java/com/superprogrammer/knowledge/mapper/RagRetrievalQueryMapper.java) SQL 范式）
  │     └ RRF 融合（复用 [RrfFusion.fuseWeighted](../../backend/src/main/java/com/superprogrammer/knowledge/service/internal/RrfFusion.java)，向量权重 > 词法权重）→ top-N 候选记忆（N 默认 40）
  │
  ├─③ LLM 精排（治本步，双维度筛 §2.6，模型 MEMORY_JUDGE_MODEL="doubao-seed-2.0-code"）
  │     top-N 候选 → ① distinct memory_key 灌 LLM 选相关 key ② distinct block_label 灌 LLM 选相关 block
  │     → 交集（key∈相关 且 block∈相关）→ 注入只留 key（标签语言 EN/ZH/BOTH）+ value
  │     语义判断，不枚举同义词；"家人"→配偶/孩子 key 天然命中
  │
  ├─④ 装 value + 注入：选中 key → [formatMemories](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java)（标签语言设置感知）
  │
  └─⑤ 缓存：[MemoryQueryCache](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryQueryCache.java) 新条目 `rerank:userId:scopeSig:queryHash` → 选中 key 列表，TTL 60s，evictUser 写时失效
```

- 任一子链路异常不致命（照 VECTOR_KEYWORD 既有韧性范式）：扩展挂→单 qvec；向量挂→仅 BM25；都空→不注入（return null，不回退全量，与 EMBEDDING_VECTOR 一致）。
- **可观测性**：buildLlmKeyContext 入口/出口打 info（照 buildMemoryContext 既有日志），含 `粗筛候选数/LLM选中数/注入字符数/首条样本`。
- **成本旋钮**：`rag.memory.llm-key.rerank`（默认 true）= 关则跳过 LLM 精排直接注入 top-N（省 1 次 LLM 调用，召回粗但 0 LLM）；`rag.memory.llm-key.coarse-top-n`（默认 40）。

### 2.4 为什么复用知识库组件而不新造

| 组件 | 位置 | 复用点 |
|---|---|---|
| RrfFusion | knowledge/service/internal | 纯静态无依赖，`fuseWeighted(List<WeightedList<T>>, k)` K=60 |
| JiebaTokenizer | knowledge/util | 纯静态，`tokenize(text)`→空格串供 PG `plainto_tsquery('simple',...)` |
| QueryExpansionService | knowledge/service | `expand(query, embedModel)` 已模型参数化，传 MEMORY_EMBED_MODEL 即用 |
| LlmGateway.embed | llm | 同步 `float[2048]` |
| HalfVecUtil | knowledge/util | `toHalfVec` → `[v0,...]` |
| BM25 SQL 范式 | knowledge/mapper RagRetrievalQueryMapper `bm25HitsJieba` | tsvector + ts_rank + jieba，照搬到记忆 mapper |

> ⚠️ 知识库侧**无 rerank 模型**（`KnowledgeBase.rerankModel` 字段存了但 RagRetrievalService 不读，只有启发式 `rerankWithBoost` 线性融合）。故 LLM 精排须新写，但本质是一次 `selectRelevantKeys` 风格的 LLM 调用（已有 prompt `SELECT_KEYS_PROMPT` 可复用/改造）。

### 2.5 互补增强 — 上位词召回词袋（治标 B，与治本协同）

治本（LLM_KEY）解决根因，但召回率可被 **治标 B 低成本再抬一档**，且兼顾老模式。本质：extract 时给 entities 召回词袋补**第四类「上位词/泛称」**（V32 现三类：①key_zh 标签 ②同义变体 ③value 专名）。

- **extract 改动**（[MemoryConflictJudge.extract](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) entities 抽取 prompt）：加一条规则"补 1-2 个所属类别的泛称/上位词"。例：
  - 配偶/妻子/孩子/宠物 → 上位词 `家人`
  - 公司/职位/职级 → 上位词 `工作`
  - 过敏/病史 → 上位词 `健康`
  - 住址/城市 → 上位词 `居住地`
  - 全品类通用，非家庭专属。`readEntities` 上限 10（V32 已扩）容纳。
- **0 额外 LLM 调用**：复用 V32 既有 extract LLM（顺带抽），仅 prompt 加规则。
- **写入**：applyClean 落 entities 时含上位词（同 V32 链路，无新列）。
- **老数据回填**：V32 现查询 `entities IS NULL OR memory_key_zh IS NULL` 跳过已填行 → **需加强制重抽模式**（端点加 `force=true` 参数或新端点，重抽 entities 含上位词；幂等——重跑结果稳定）。
- **双重受益**：
  1. VECTOR_KEYWORD 关键词通道（[findByKeyword](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java) 搜 entities::text）：query"家人"撞 entities 里的"家人" → 命中。老模式直接治原 bug。
  2. LLM_KEY anchor 向量（§2.2，anchor 含 entities）：anchor 更富集 → 粗筛召回率↑。
- **局限**：仍是枚举（LLM 抽取一致性靠 prompt，偶漏）；故**不替代治本**，是增强。LLM_KEY 的 LLM 精排才是兜底语义判断。

### 2.6 双维度两阶段筛选（key + block_label，共用筛，跨模式生效）

取代旧「单维 key 筛」——旧 [MemoryService.filterRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) + [MemoryConflictJudge.selectRelevantKeys](../../backend/src/main/java/com/superprogrammer/chat/service/internal/MemoryConflictJudge.java) 一次把 `key=>value` 整包灌 LLM 选 key。问题：① 同 key 多行重复刷 token；② block 维度未筛（问「家庭」，职业/偏好块的 key 也进列表噪声）；③ 注入残留 `category`/`block_label` 占 token。

**新四步（Java 侧剔重 + 2 次 LLM 筛 + 交集）**：
1. **key 剔重**：候选的 `distinct memory_key`（始终英文 key，匹配/去重基准不变）→ `selectRelevantKeys(query, distinctKeys)` 灌 LLM 选相关 key 子集（复用 `SELECT_KEYS_PROMPT`，召回优先）。
2. **block 剔重**：候选的 `distinct block_label`（null 视作 ""）→ 新 `selectRelevantBlocks(query, distinctBlocks)` 灌 LLM 选相关 block 子集（新 prompt `SELECT_BLOCKS_PROMPT`，范式同 SELECT_KEYS）。
3. **交集装配**：保留 `memory_key ∈ relevantKeys 且 block_label ∈ relevantBlocks` 的记忆行。
4. **注入收口**：`formatLine` 只输出 **key（按 `key-language`：EN=memory_key / ZH=memory_key_zh / BOTH=`memory_key_zh(memory_key)`）+ value**；`category`/`block_label`/`entities`/`confidence` 全丢。

**三路径共用同一筛**（改造点都在 `filterRelevantKeys` + `formatMemories`，一次改三处受益）：
- **LLM_FULL_CONTEXT 超阈值两阶段**（[buildFullContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) → `filterRelevantKeys`）。
- **VECTOR_KEYWORD 0 命中 LLM-key 兜底**（[buildHybridContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) → `llmFallbackContext` → `filterRelevantKeys`）。
- **LLM_KEY 模式 LLM 精排**（§2.3 step ③，粗筛 top-N 候选进同一 `filterRelevantKeys`）。

**剔重在 Java 端做**（`Stream.distinct`），不新增 DB 查询；候选集已由粗筛/findAllClean 拉回内存。
**容错**（照旧 fail-safe）：key 筛挂→单走 block 筛；block 筛挂→单走 key 筛；都空/异常 → `return null` 不注入（宁缺毋滥，与既有 0 命中兜底一致）。
**成本**：旧单维 1 次 LLM → 双维 2 次 LLM（key + block）；2 次都吃剔重后 distinct 列表（远小于全量行），token 增量可控；MemoryQueryCache 可缓存 `relevantKeys`/`relevantBlocks` 按 queryHash（见 §4.5）。

## 三、数据表与迁移（V38）

[V38__user_memories_anchor_recall.sql](../../backend/src/main/resources/db/migration/V38__user_memories_anchor_recall.sql)（新建）：

```sql
-- ① 召回锚点向量（语义粗筛主通道）
ALTER TABLE user_memories ADD COLUMN anchor_embedding halfvec(2048);

-- ② 锚点词法 token（BM25 通道，jieba 分词后空格串 → tsvector）
ALTER TABLE user_memories ADD COLUMN anchor_tokens text;
ALTER TABLE user_memories ADD COLUMN anchor_tokens_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', coalesce(anchor_tokens, ''))) STORED;

-- ③ HNSW ANN 索引（百万 key scale 必需；halfvec 余弦）
CREATE INDEX idx_user_memories_anchor_hnsw
  ON user_memories USING hnsw (anchor_embedding halfvec_cosine_ops);

-- ④ BM25 GIN 索引
CREATE INDEX idx_user_memories_anchor_tsv ON user_memories USING gin (anchor_tokens_tsv);

-- ⑤ 回填存量（分批，Java 侧 backfill 端点跑，不在迁移里裸 embed——迁移不应调外部 LLM）
--    迁移只建结构；数据回填见「老数据回填」节。
```

**迁移坑（照 V34/V37 教训）**：
- `user_memories` **无 `deleted` 列**（不走 BaseEntity 软删）——回填 UPDATE 切勿带 `deleted=0`（V34 踩过 Flyway `42703`）。
- halfvec 算子 `<=>` 在 MyBatis `<script>` XML 模式须转义 `&lt;=>`（V33 踩过 SAXParseException → bean 崩 → 启动不起来）。新 mapper SQL 同理。
- HNSW 索引建大表（百万行）耗时——迁移里 `CREATE INDEX` 不加 `CONCURRENTLY`（Flyway 事务内），大库需拆分/手动建。dev 库小，无碍；生产上量前评估。
