## 冲突链两个关键 bug 修复(V35)

用户实测报:「我说女儿叫小红,再说叫小美,记忆直接被改了,然后才出来 pending,选保留新却提示『冲突不存在』」。playwright-mcp 复现 + DB 验证,拆出两个独立 bug,都修。

### Bug 1:跨块同 key 静默覆盖("记忆直接被修改了")
- **根因**:[MemoryService.processFacts](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 分流只看**块成员**(`getCleanByBlock` block-scoped)。新事实归块 A,但同 key 既有 clean 记忆在**别的块** → 块 A 成员空 → 走 `immediateInserts` → `applyClean` 用 `findSameKeyClean`(home-scoped,**跨块**)找到别块同类行 → 当"细化" `updateCleanMemory` 原地 UPDATE 覆盖,**绕过冲突判定**(不建 PENDING、不问用户)。
- **复现**:admin 全局 `child_name=啊闪、啊然`(**基本信息**块)→ 发「女儿叫小美」(LLM 归**家庭信息**块)→ `啊闪、啊然` 被静默改成小美,零冲突。
- **修**:分流候选集改为 **块成员 ∪ 跨块同 key 记忆**(`findCleanByHomeKey`,home-scoped):②二者皆空才 `immediateInserts`(真·新块直插);③batch judge 的 comparison set 也并入跨块同 key 行(让 LLM 看到别块同类记忆,否则漏判);conflictingIds 空时回退**该 fact 的跨块同 key 记忆**(不再误把整块成员当冲突对象)。
- **不影响**:同块同 key(既有正常路径)仍走 judge;真·新 key(无同 key 无块成员)仍直插。

### Bug 2:保留新→冲突不存在(PENDING resolve 静默回滚)
- **根因**:[MemoryConflictService.buildFromSnap](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryConflictService.java)(PENDING 路径 `insertSnap` + `flag()` + `mergePendingKeepBoth` 兜底都用)**没设 `homeProjectId`/`is_global`**——V34 home 语义改 `createFlagged` 时漏改它。→ 新行落默认 `home=null`(global)、`is_global=true`、不挂项目 → 若同 user 同 key 已有 global clean 行(V34 唯一索引 `uk_user_memories_user_key_home` = `(user,key,COALESCE(home,-1)) WHERE conflict_id IS NULL`)→ `DuplicateKeyException` → `@Transactional` **整体回滚**(`hardDelete(oldIds)` 也回滚)→ `resolve` 返 false → controller 文案「冲突不存在或无权操作」。
- **复现**:项目「测试」(home=3) 冲突 `child_name` 小红→小蓝,全局另有 `child_name=小绿`(home=null);点保留新 → `insertSnap` 落小蓝 home=null → 撞小绿 → 回滚 → conflict 仍 PENDING、253 未删、提示"冲突不存在"。
- **修**:`buildFromSnap` 加 `homeProjectId`+`isGlobal` 参数;新 `insertSnapScoped(...home, isGlobal, projectIds)` 落新行后挂 `user_memory_projects`;三个调用点全部从 **old 行继承 scope**——`resolve` PENDING 在 `hardDelete` **前**读 old 行(删完查不到)取首行的 `home_project_id`/`is_global`/`findProjectIdsByMemory`;`flag()` 同;`mergePendingKeepBoth` 兜底同。新行 = 替换 old → 理应同 scope(同 home、同可见性),不撞唯一约束。
- **FLAGGED 路径不受影响**:`createFlagged`(V34 已正确设 home+is_global+挂项目)插的新行 scope 正确,FLAGGED 的 KEEP_NEW 只 `hardDelete(old)+setConflictId(new,null)`,不走 `buildFromSnap`。
- **playwright 验证(修后)**:同一项目「测试」冲突点保留新 → 旧小红删、新小蓝落 **home=3**/is_global=f/挂 project 3,零撞库,conflict RESOLVED KEEP_NEW。

### 单测
`MemoryServiceTest` 21/21 + `ChatSessionServiceTest` 14/14 过(共 35/35,零回归)。processFacts 候选集改动不破既有同块路径。冲突 resolve/flag 的真 PG 行为 mock 单测仍跑不出——复现须打 streaming + 真 PG + 跨 home/scope 数据。

## 冲突 resolve 后 entities/memory_key_zh 变空(V38 bug)

用户报:「记忆冲突修改(解决)后,entities、memory_key_zh 等全变空了」(对应待办原 #26)。

### 根因
冲突**快照**(`memory_conflicts.new_memory` JSON)只存 `category/key/value/confidence` 四字段,丢 `keyZh`/`entities`/anchor。
- [MemoryService.processFacts](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 建快照处 `ExtractedFactSnapshot` 只取 `f.category()/f.key()/f.value()/f.confidence()/fc.br.halfvec()`,`f.keyZh()` 和 `f.entities()` 在作用域内却没传。
- [MemoryConflictService.buildFromSnap](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryConflictService.java) 不设 `setMemoryKeyZh`/`setEntities`;物化新行时 `insertMemory(m, halfvec, null, null)` anchor 两列也传 null。
- 凡走 `buildFromSnap`/直插的路径 → survivor 行 `memory_key_zh`+`entities`+anchor 全 null:
  - **KEEP_NEW(PENDING)**: `hardDelete(old)` + `insertSnapScoped` → 新行字段空。
  - **`flag()`**(超时/共存): `buildFromSnap` → 空。
  - **`createFlagged` 直插**(会话锁忙直建 FLAGGED 的新行): 创建时就空,后续 KEEP_NEW 变 survivor 仍空。
- **KEEP_BOTH 不中招**: 走 `mergeIntoRow`,`memory_key_zh`/`entities`/anchor 列不在 UPDATE 集 → COALESCE 保留旧值。

### 修(V38,7 处)
1. `ExtractedFactSnapshot` record 加 `keyZh`/`entitiesJson`/`anchorHalfvec`/`anchorTokens`。
2. `MemoryService` 建快照处算 `entitiesJson(f.entities())` + `embedAnchor(block, keyZh, key, entitiesJson)`,全传进 snap(与 applyClean 同款,每冲突 +1 anchor embed)。
3. `snapToMap` helper(HashMap 容 null)替代 `Map.of`——老/空快照字段可能 null,`Map.of` 拒 null 会抛。
4. `createPending`/`createFlagged` 写完整 JSON(8 字段)。
5. `buildFromSnap` 读出并 `setMemoryKeyZh`/`setEntities`。
6. `insertSnapScoped`/`flag()` insertMemory 透传 anchor(不再 `null,null`)。
7. `createFlagged` 直插的 m 补 `setMemoryKeyZh`/`setEntities` + anchor(FLAGGED 新行创建时就带全字段,不等 resolve)。

### 效果
KEEP_NEW 出来的 survivor 与 applyClean 正常插入路径字段一致——`memory_key_zh`/`entities` 不再空,LLM_KEY 锚点召回也能命中。

### 遗留(不值得迁移)
部署瞬间已在库的老 PENDING/FLAGGED 冲突,其 `new_memory` 仍是老格式(无 keyZh/entities),resolve 时仍落 null。属瞬态(冲突有 expire),只新建冲突起全对。老数据可被既有「记忆冲突残留清理」端点自然收敛。

## KEEP_BOTH 合并成一条(V33 待增修改 6)

「合并保留」不再双行共存。PENDING:同 key old 行 value 追加 new(去重 join `,`),survivor 清 `conflict_id` 变 clean,删多余同 key 行;FLAGGED:全组值合入 survivor(原 clean 行),删组内其余。merged value 重 embed(失败 COALESCE 保旧向量)。[MemoryConflictService.mergePendingKeepBoth/mergeFlaggedKeepBoth](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryConflictService.java) + [UserMemoryMapper.mergeIntoRow](../../backend/src/main/java/com/superprogrammer/chat/mapper/UserMemoryMapper.java);前端按钮「都保留」→「合并保留」。decision 串 `KEEP_BOTH` 不变(免迁移)。
- **flagged 隐身陷阱**:抽取去重/冲突判定只看 `conflict_id IS NULL` 行([MemoryService.classifyFact](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) `isNull(conflictId)`)。旧 KEEP_BOTH 留下的带标行(conflict 已 RESOLVED 但 `conflict_id` 未清)对抽取**隐身** → 同值被当新事实反复落库(用户实测 3 行 name = 2 旧带标 + 1 新 clean)。
- **历史脏数据清理**:admin 在 [RagMemorySettingsTab.vue](../../frontend/src/components/settings/RagMemorySettingsTab.vue)「记忆冲突残留清理」→ `POST /api/system/settings/rag-memory/cleanup-memory-residue`(admin)→ [MemoryConflictService.cleanupResolvedResidue](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryConflictService.java) 异步跑:找 `conflict_id` 非空且其 conflict 已 RESOLVED 的行,按 `(user_id, memory_key)` 分组合并成一条 clean,重 embed。幂等;进度日志 `memoryCleanup`。

### M5 — 记忆触发边界收紧:读侧 agent/工作流不注入 + 写侧回答不抽取(合并原 15+17)
合并理由:都属「何时碰记忆」边界收紧,机制独立(read gate vs write gate)但同一遍对话主链路梳理。动主链路谨慎,需单测 + IT 覆盖。

- **读侧 gate**(原 15):[MemoryService.buildMemoryContext](../../backend/src/main/java/com/superprogrammer/chat/service/MemoryService.java) 注入须仅针对**用户 chat 输入**消息。agent/工作流路径([AgentRoutingStrategy](../../backend/src/main/java/com/superprogrammer/engine/strategy/AgentRoutingStrategy.java) 等)及系统提示词、agent/工作流自带提示词**不触发记忆读取**。实现:记忆注入入口判来源(message source / 是否经 agent 路由),非用户直发跳过。需定「触发点」语义:按消息 role=USER 且非 agent 代理转发判。
- **写侧 gate**(原 17):抽取只针对用户输入内容,**回答/LLM 生成内容不入记忆**,除非用户显式要求(如「记一下…」)。现状确认:extract 触发源是用户消息还是整轮对话?若含 assistant 回复需收口为仅 user message。用户主动要求 = 检测 user 消息含「记/记住/更新记忆」等意图,或显式「保存为记忆」按钮。
  - **被动提醒(2026-07-18,冲突 1 决策)**:当本轮回答看似含值得记忆的事实(启发式判定),AI **不主动存**,而是在回答尾部轻量提示一句「如需记入记忆,跟我说『记一下…』」。存与不存的最终决定权在用户主动开口,不绕 gate。
- 交叉:M5 与 M2/M3 无依赖可独立推进;但改触发判定影响所有记忆模式,回归面广。

### 合并优先级建议
- **M1 + M4**:纯前端、用户痛点明确,先做。
- **M2**:需设计决策(value schema 影响存量数据 + 时序判定),中优先。
- **M3**:前端 tab + extract prompt,中优先。
- **M5**:动对话主链路触发判定,回归面广,最后做并配足测试。
