## 一、监控告警缺失（D.01 定义 + D.02 坑类型变体）

### 1.1 坑类型全景

| 坑类型 | 变体 | 典型后果 | 真实案例线索 |
|--------|------|----------|------------|
| 上线后无监控 | 新服务/新接口未配监控 | 问题靠用户投诉才发现，MTTR极长 | 某支付网关上线未配监控，2小时后用户大面积投诉才发现 [SRE案例集 | 置信度:0.85] |
| 告警阈值不合理 | 阈值过松漏报/过紧告警风暴 | 漏报导致问题扩大；告警风暴导致团队麻木（"狼来了"效应） | 某团队配置CPU>50%告警，每天触发200+条，全员已忽略 [运维社区 | 置信度:0.88] |
| 无值班机制 | 出问题无人响应 | 凌晨/周末问题无人处理，影响面持续扩大 | 某SaaS产品凌晨3点宕机，无值班到早上9点才处理 [V2EX | 置信度:0.80] |
| 监控维度缺失 | 只看系统指标不看业务指标 | 系统正常但业务异常（如支付成功率下降） | 某电商只监控CPU/内存，支付成功率从99.5%降到96%未发现 [PM社区 | 置信度:0.82] |

### 1.2 PM视角的监控三层模型

PM不需要写监控代码，但必须定义**看什么**：

| 层级 | 监控类型 | 典型指标 | PM职责 |
|------|----------|----------|--------|
| L1 系统层 | 基础可用性 | CPU/内存/磁盘/网络/QPS/错误率 | 确认技术团队已覆盖 |
| L2 业务层 | 业务健康度 | 核心转化率/支付成功率/搜索成功率/分享率 | **PM必须定义** |
| L3 体验层 | 用户体验 | 加载时长/PV-UV比/跳出率/NPS/客诉量 | **PM必须定义** |

> 关键原则：**L2业务指标是PM的底线**——系统指标全绿但业务指标异常，等于线上有问题。 [SRE实践 | 置信度:0.90]

### 1.3 告警阈值设计方法论

**告警金字塔**：从底到顶，告警越来越少但越来越严重

```
          /\
         /P0\        ← 立即处理，电话+短信通知（1-3条/月）
        /────\
       / P1   \      ← 30分钟响应，IM通知（5-10条/月）
      /────────\
     /   P2     \    ← 当日处理，工单记录（20-50条/月）
    /────────────\
   /     P3       \  ← 周报汇总即可（100+条/月）
  /________________\
```

**阈值设置三原则**：
1. **基线驱动**：阈值基于历史基线±Nσ设定，而非拍脑袋
2. **分级降噪**：P3→P0逐级收敛，避免告警风暴
3. **动作导向**：每条告警必须有明确的处理动作，"不知道怎么处理"的告警就是噪音

## 二、数据埋点遗漏（D.01 定义 + D.02 坑类型变体）

### 2.1 坑类型全景

| 坑类型 | 变体 | 典型后果 | 严重度 |
|--------|------|----------|--------|
| 上线后无数据可看 | 埋点完全遗漏 | 无法评估上线效果，决策靠猜 | P0 |
| 埋点位置错误 | 埋在了错误的事件/页面 | 数据存在但不可用，浪费存储 | P1 |
| 埋点参数不一致 | 同一事件不同端参数名/值不同 | 数据无法聚合分析，跨端对比失真 | P1 |
| 埋点与业务逻辑脱节 | 埋了技术事件没埋业务事件 | 有PV/UV但无转化漏斗 | P1 |
| 埋点性能影响 | 埋点SDK导致页面卡顿 | 用户体感下降，埋点自身成了bug | P2 |

### 2.2 PM视角的埋点三层设计

| 层级 | 埋点类型 | 典型事件 | PM职责 |
|------|----------|----------|--------|
| L1 页面级 | PageView | 页面曝光、来源、停留时长 | 定义页面层级和核心页面 |
| L2 事件级 | UserAction | 点击、滑动、表单提交、分享 | **定义业务事件和转化漏斗** |
| L3 业务级 | BusinessEvent | 下单、支付、注册完成、AI调用 | **定义业务成功/失败事件** |

> 关键原则：**PM先定义转化漏斗，再由漏斗推导需要哪些埋点**，而非反过来。 [数据分析实践 | 置信度:0.88]

### 2.3 埋点规范化要求

| 规范项 | 要求 | 示例 |
|--------|------|------|
| 事件命名 | `模块_动作_对象` 格式 | `order_click_submit` |
| 参数命名 | 统一驼峰/下划线，全局一致 | `userId` 或 `user_id`（全项目选一） |
| 枚举值 | 禁止magic number，使用枚举映射 | `status: "success"` 而非 `status: 1` |
| 版本标记 | 每个事件携带appVersion | `v: "3.2.1"` |
| 平台标记 | 每个事件携带platform | `platform: "ios"` |

## 三、避险技法（I.07）

### 3.1 监控告警避险 Checklist

- [ ] 上线前监控大盘已配置（L1系统+L2业务+L3体验三层）
- [ ] L2业务指标已由PM定义并确认技术团队已实现
- [ ] 告警阈值基于历史基线设定（非拍脑袋）
- [ ] 告警分级已配置（P0-P3），P0≤3条/月
- [ ] 告警通知渠道已配置（P0电话+短信，P1 IM群，P2工单）
- [ ] 值班oncall机制已建立（含周末和节假日轮值）
- [ ] 告警演练已完成（模拟P0告警，验证响应流程）

### 3.2 埋点避险 Checklist

- [ ] 转化漏斗已定义（从漏斗推导埋点需求）
- [ ] 埋点文档已评审（PM+数据+开发三方确认）
- [ ] 埋点命名规范已统一（事件名/参数名/枚举值）
- [ ] 埋点测试已完成（测试环境验证事件触发+参数完整性）
- [ ] 跨端参数一致性已验证（iOS/Android/Web/H5同事件对比）
- [ ] 埋点性能影响已评估（SDK体积+网络请求+页面加载影响）
- [ ] 埋点数据已接入分析平台（可查询+可建看板）
