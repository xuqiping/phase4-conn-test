# 3.3 失败模式与安全可观测

## 一、Berkeley 14 种失败模式（行业必懂）

Berkeley 2026-07 研究揭示：Multi-Agent 系统生产环境失败率高达 41%-86.7%（AgenTracer 单独测得 87%）。其中 79% 失败不是模型不够好、不是 GPU 不够多——是 **specification 不清晰** 与 **agent 间协调失败**。14 种失败模式按 MAST 分类法归为四类：

### 1.1 Specification 类失败（~40% 占比）

1. **任务规格模糊**：Orchestrator 给 Worker 的任务描述含糊，Worker 产出方向偏离
2. **接口契约缺失**：Agent 间调用没定义输入/输出 schema，数据传递失真
3. **成功标准未定义**：没说什么时候算"完成"，Agent 永远跑下去

### 1.2 Coordination 类失败（~39% 占比，含 79% 大头）

4. **橡皮图章 Validator**：Validator 与 Generator 共享同源 prompt → Validator 永远说 OK，Generator bug 照发不误
5. **循环死锁**：Agent A 等 Agent B，Agent B 等 Agent A → 整个 MAS 卡死
6. **状态不一致**：多 Agent 同时改同一状态 → 部分更新丢失
7. **消息丢失/乱序**：MessageBus 消息未持久化 / 顺序错乱 → Agent 收到错误信号
8. **重复消费**：同一事件被多个 Agent 重复处理 → 重复执行副作用
9. **超时级联**：单 Agent 超时引发调用方超时 → 整个调用链被拖垮

### 1.3 Interdependence 类失败

10. **路径依赖未识别**：Agent A 的输出影响 Agent B 但 B 已开始执行 → B 用了过时输入
11. **隐性依赖暴露**：两个看起来独立的 Agent 共享某个底层资源（API/数据库），并发执行时资源争用

### 1.4 Execution 类失败（被放大）

12. **单 Agent 错误级联**：单 Agent 拿错结果 → 下游所有 Agent 基于错结果继续 → 越跑越偏
13. **Context Rot 蔓延**：某 Agent 上下文腐烂产生幻觉 → 把幻觉结果传给下游
14. **工具失败放大**：单 Agent 工具调用失败 → 重试死循环 → 占满整个 MAS 吞吐量

**核心结论**：大多数场景下，**单个强 Agent + 清晰 prompt > 多个弱 Agent 协作**。这一反直觉结论是 Berkeley 研究的核心 insight。

[来源:Berkeley / 知乎 / Redis Blog | 🔍高 | 2026-07/04]

## 二、错误恢复 L1-L5（与 D-24.04 § 3.2 借鉴但不同）

多 Agent 协作的错误恢复比单 Agent 更复杂——必须考虑级联。

| 级别 | 名称 | 触发条件 | 动作 |
|---|---|---|---|
| L1 | 局部重试 | 单 Agent 单步失败 | 该 Agent 内部重试（指数退避） |
| L2 | 降级 | 单 Agent 多次重试失败 | 该 Agent 降级返回兜底结果 / 调用 Skill 备选 |
| L3 | 绕路 | 单 Agent 不可用 | Orchestrator 重新分配任务给其他 Worker |
| L4 | 重规划 | 多 Agent 协调失败 | Orchestrator 触发重规划，重组任务分配 |
| L5 | 人工接管 | 整个 MAS 失败 / 高风险步骤 | 触发人工审批告警 |

**多 Agent 特有级别**——L3 绕路与 L4 重规划是单 Agent 不具备的。

[来源:Berkeley / 腾讯云 | 🔍高 | 2026-07]

### 2.4 失败模式 → 恢复级别映射

| 失败模式 | 推荐恢复级别 |
|---|---|
| 单 Agent 上下文腐烂 | L1/L2 |
| 单 Agent 工具失败 | L1（重试）→ L3（绕路到其他 Worker）|
| Validator 橡皮图章 | L4（重规划：换 Validator prompt）|
| 循环死锁 | L4/L5（强制打破循环 + 重规划）|
| 状态不一致 | L4（重规划：恢复到最近 Checkpoint）|
| 超时级联 | L2/L3（熔断超时 Agent + 绕路）|
| 跨 Agent 攻击 | L5（立即停止 + 人工介入 + 安全审计）|

## 三、跨 Agent 攻击面与安全

### 3.1 AI Agent 全新攻击面

AI Agent 引入传统安全体系看不懂、管不住的全新攻击面：
- 提示词注入（Prompt Injection）
- 工具越权调用
- 密钥外泄
- 影子 Agent（无人监管的 Agent 出现）
- **跨 Agent 注入**：恶意输入从一个 Agent 通过 A2A 传播到其他 Agent，扩散范围比单 Agent 大 N 倍

[来源:腾讯云 AI Agent 安全解决方案 | 🔍高 | 2026-06]

### 3.2 OWASP MCP Top 10

OWASP 2026-05 推出 MCP Top 10，对工具协议层面安全问题系统总结：
- 工具供应链污染（第三方 MCP Server 被植入恶意代码）
- 提示词注入通过工具返回数据
- 上下文与权限边界失控
- 工具描述注入（恶意 MCP Server 用工具描述操控 Agent）
- 凭据泄露
- ... 完整 Top 10 见 D-24.02 详述

**多 Agent 特有**：A2A 协议下恶意 Agent 可伪装成合法 Agent 通过 AgentCard 招摇撞骗 → 必须有 AgentCard 签名验证机制。

[来源:OWASP / 腾讯云 | 🔍高 | 2026-05]

### 3.3 权限隔离与影子 Agent

- **最小权限原则**：每个 Agent 只授予完成自身任务必需的最小权限。Executor 不能给全部工具权限。
- **沙箱隔离**：高风险 Agent 必须在沙箱中运行。Manus 每任务一台云虚拟机是经典模式。
- **影子 Agent 防御**：监控所有运行的 Agent 实例，发现未授权 Agent 立即告警。
- **跨组织权限矩阵**：跨组织 Agent 互联必须有权限矩阵——A 公司 Agent 不能访问 B 公司敏感数据。

[来源:腾讯云 / OWASP | 🔍高 | 2026-06]

## 四、AgenTracer 纠错反馈与可观测

### 4.1 AgenTracer 模式

AgenTracer 是 2026-06 推出的 Multi-Agent 失败归因工具。机制：每个 Agent 调用都打 trace（输入/输出/工具调用/子调用），失败时回放 trace 找到具体哪个 Agent 哪一步出错。

**核心价值**：把"MAS 翻车但不知道谁的锅"变成"快速定位哪个 Agent 哪步错"。

[来源:腾讯云 AgenTracer | 🔍高 | 2026-06]

### 4.2 多 Agent 可观测四要素

1. **分布式追踪**：每个 Agent 调用有 trace_id + parent_id，全链路可视化（类 Zipkin/Jaeger for MAS）
2. **状态机可视化**：实时显示当前 MAS 在状态机的哪个节点
3. **Token 消耗看板**：每个 Agent 实时 token 消耗 + 累计。Token 解释 80% 性能方差，token 异常是失败前兆
4. **失败模式告警**：基于 Berkeley 14 种失败模式 + MAST 分类法建告警规则

[来源:Berkeley / Anthropic | 🔍高 | 2026-06/07]

### 4.3 token 与性能的强相关（Anthropic 实证）

Anthropic 5-Agent 系统的 token 使用量**单独解释了约 80% 的性能方差**——token 越多性能越好，但成本越高（15 倍单 Agent）。

**PM 实操**：
- 监控每个 Subagent token 消耗——异常飙升可能是 Context Rot / 死循环
- 给每个 Agent 设 token 预算上限——超过预算触发 L2 降级
- 测算每个场景 token/性能比——决定哪个场景值得 15 倍 token 换 90.2% 性能提升

[来源:Anthropic | 🔍高 | 2026-06]

## 五、协同可信工程化（2026 共识）

Gartner 2026-07 报告《驯服多智能体混沌》指出：行业从"自由对话"转向"协同可信"时代，协作的确定性已成为决定复杂任务能否落地的核心前提。三大工程化支柱：

### 5.1 形式化协议

每个 Agent 调用都用形式化协议定义（输入 schema / 输出 schema / 错误码 / SLA），不容许自然语言模糊边界。A2A + JSON-RPC 是骨架。

### 5.2 分布式状态机

整个 MAS 流程建模为状态机，状态持久化到共享存储。所有状态转移可追溯、可回放、可恢复。这是 D-24.05 § 3.2.2 共享状态管理的工程化落地。

### 5.3 超时熔断

每个 Agent 调用 + 整个 MAS 流程都配超时熔断（参见 § 6.1 超时熔断三层）。熔断打开立即返回兜底，避免雪崩。

### 5.4 三支柱与 Berkeley 14 种失败模式的关系

| Berkeley 失败类型 | 协同可信支柱 |
|---|---|
| Specification 失败（40%）| 形式化协议 |
| Coordination 失败（39%）| 分布式状态机 + 超时熔断 |
| Interdependence 失败 | 形式化协议 + 状态机 |
| Execution 失败放大 | 超时熔断 + L4 重规划 |

协同可信工程化是 Berkeley 14 种失败模式的系统性对策。

## 六、PM 安全/可观测 checklist

- ✅ 是否定义了每个 Agent 的输入/输出 schema（形式化协议）
- ✅ 是否每个跨 Agent 调用有契约（SLA + 失败策略）
- ✅ 是否所有 Agent 调用有分布式追踪（trace_id + parent_id）
- ✅ 是否每个 Agent 状态 Checkpoint 持久化
- ✅ 是否所有 Agent 设 token 预算上限
- ✅ 是否每个 Agent 最小权限原则 + 沙箱隔离
- ✅ 是否跨组织 Agent 做了 AgentCard 签名验证
- ✅ 是否有基于 14 种失败模式的告警规则
- ✅ 是否有用户可见的进度反馈（SSE 流式）
- ✅ 是否高风险步骤有 L5 人工接管触发
